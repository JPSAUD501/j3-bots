# Base prompt, v0.3

**Status:** reviewed in four council rounds. The routine and conversation cases in [`packages/prompts/evals`](architecture.md#evaluation) have run it against one small Claude model and one small GPT model; most scenarios in the behavior eval list still have no case.

The text every bot shares lives in one place, the template the server renders it from: [`packages/prompts/src/templates/base.md`](../../packages/prompts/src/templates/base.md). The bot's profile and pinned memory follow it, from [`bot.md`](../../packages/prompts/src/templates/bot.md) in the same folder. On Claude Code both go into the bot's `.j3/system.md`; on Codex the base prompt is the provider instance's `developer_instructions` and the rest is the workspace's `AGENTS.md` (see [Prompt architecture](architecture.md#how-each-layer-reaches-each-harness)).

Placeholders in double braces are filled at render time. Above the profile, the only placeholder is `{{user.name}}`, which is the same for every bot of an installation: on Codex the base prompt is set once per provider instance and shared by all bots, so anything per-bot belongs in the profile.

Some of what the prompt tells a bot is a product decision rather than wording, and changes only with a change to the product:

- **What the app shows.** The clients render paragraphs, inline code, fenced code blocks, bare web addresses and `@name`s, and nothing else, so the prompt asks for plain prose, bare links and no Markdown emphasis, headings or link syntax. A typed `@name` is only shown; the `mention` field of `say` is what wakes a member. When a client learns to render more, this text changes with it.
- **The operator's machine.** A bot's commands run with the operator's own access, so they reach the operator's real files, programs and logged-in services. Its workspace is its own; anywhere else it reads what a task needs, but lists exactly what it would delete, move or overwrite and asks first, unless the operator named that change. A permission prompt from the engine depends on a mode the bot cannot see, so it never replaces one of these confirmations; once the operator approved a step in one, the bot does not ask again.
- **Refusals are final.** A refusal comes from the engine, from the operator declining or not answering an approval, or from the system (a file the bot may not read, a command that needs `sudo`). What was refused is the effect, so reaching it in smaller pieces, through another program, a stored credential, an internal endpoint or raised privileges is the same step. A bot raises privileges only when the operator asked for exactly that. A failure for another reason may be retried.
- **Secrets take the protected route.** A bot never asks for a secret in chat; it uses the engine's `request_secret`. A secret the operator pastes anyway is their go-ahead to use it for that task. Their message already holds it, so the bot puts it in exactly one more place: it passes it to `request_secret` as `value`, which saves it to an owner-only file and returns the file's path, and commands read that file. It puts the secret nowhere else: no other tool argument, command line, environment assignment, message, file or memory. If the `value` route fails, the bot asks for a card and says once why. The engine side is **Read** at T3 Code `59651c1`: `request_secret` saves a pasted `value` to a file without a card and refuses a `value` given with `delivery: "secretRef"` (`apps/server/src/mcp/OrchestratorMcpService.ts`), and the engine keeps a copy of every tool call's arguments, `value` included, in the turn item it records for the call, with nothing redacted (`apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts:588`, for Codex; that a Claude Code session records them the same way is **Assumed**). J3 Bots keeps none of its own (**Read** in this repository): the call becomes a work step with the fixed label "Asked for a credential" and no detail (`packages/engine-t3/src/t3/toolNames.ts`), notifications and roster previews come only from `say`, and the server's record of tool calls holds only `j3` tools.
- **Sends need an authorization for that one send.** A message, email, post or comment to another person goes out only when the operator asked for that send, or a routine's saved instruction names it. It goes out as asked when it carries only what the operator said, to the people they named, from a settled account. When the bot chose something that matters (substance beyond the operator's words, or a recipient), the operator sees the exact text, the recipients and the account first, and approves that version. An edit they dictate word for word is already approved, so the bot makes exactly that change and sends; a change they only describe, or one that needs the bot's own words, recipients or account, is shown again. "Draft a reply" puts the text in the conversation; saving happens only when asked, and a saved draft is never sent. A reply that comes back is not a new approval. The account is the one the operator names now, else a pinned preference for that kind of message, else the one the answered thread came to, else the only account able to send; the bot asks only when that leaves it open, so an operator with one mailbox is never asked.
- **Getting to know the operator has an end.** Setup opens with the bot's first hello and happens only in its own conversation. While it is open, each reply closes with the first setup question not yet asked, in the reply itself rather than through `ask`: where the operator's work lives, then how they like replies, skipping what memory already answers. Each is asked once, any answer is enough and is remembered. Setup closes, with a pinned note, when both are answered, when the operator skips it, or when they hand the bot work, which it then does. Rooms, routines and teammates never get these questions.
- **A room hears only what is meant for it.** A private detail, whether it comes from the operator's own conversation, pinned memory, a private file or another conversation, stays out of a room unless the operator clearly meant it for that room; otherwise the bot leaves it out or tells the operator directly.
- **Watches end.** A routine that watches for one event ("let me know when X") ends when the event happens or at its cutoff. The bot works the cutoff out before writing the instruction: the end date or deadline the operator gave for the watch, otherwise the same local time 14 calendar days after it was asked. A date by which the operator only expects the event never changes it. The instruction holds the cutoff as a full date with its weekday, and the confirmation gives the same date. A run takes the end first: if a recent run already reported the event or the watch's end, it pauses without a message; at or after the cutoff it tells the operator once, reporting the event if it happened before the cutoff (even when this is the first run to see it) and otherwise that the watch ended, with an unreachable source named in that same message, and pauses. An event at or after the cutoff does not count. The pause is always a run's last call. A watch that never ends would keep spending the operator's allowance on something they have likely forgotten.
- **Days left open.** The days and times the operator gives are kept, in their zone, and a one-time request stays one-time; "daily" and "every morning" mean every day. Only when they leave the days open does a work subject run Monday to Friday and a personal one every day, however often it runs on those days, and the bot says which it chose. `set_routine`'s own description repeats this default, so it holds when the routines skill is not read.

Changing either template changes the prompt version every new session records, and is reviewed as a change to bot behavior.

Notes for editors:

- The prompt explains why a rule exists wherever the reason is not obvious. A bot that understands the reason applies the rule to cases the text did not foresee.
- It is written in the second person, in prose, with few absolute words. Emphasis is reserved for the few rules where a mistake cannot be undone or where the host pulls hardest the other way.
- It must stay short enough to be read on every session start. The budget is 3,000 words for `base.md`, counted as runs of non-whitespace that contain a letter or a digit, so Markdown markers do not count. A structure test enforces it.
- It is original text. See [Prior art](../research/prior-art.md).
