# Base prompt, v0.3

**Status:** reviewed in four council rounds. The routine and conversation cases in [`packages/prompts/evals`](architecture.md#evaluation) have run it against one small Claude model and one small GPT model; most scenarios in the behavior eval list still have no case.

The text every bot shares lives in one place, the template the server renders it from: [`packages/prompts/src/templates/base.md`](../../packages/prompts/src/templates/base.md). The bot's profile and pinned memory follow it, from [`bot.md`](../../packages/prompts/src/templates/bot.md) in the same folder. On Claude Code both go into the bot's `.j3/system.md`; on Codex the base prompt is the provider instance's `developer_instructions` and the rest is the workspace's `AGENTS.md` (see [Prompt architecture](architecture.md#how-each-layer-reaches-each-harness)).

Placeholders in double braces are filled at render time. Above the profile, the only placeholder is `{{user.name}}`, the operator's name from Settings, or "your user" until they have said what to call them. It is the same for every bot of an installation: on Codex the base prompt is set once per provider instance and shared by all bots, so anything per-bot belongs in the profile.

Some of what the prompt tells a bot is a product decision rather than wording, and changes only with a change to the product:

- **What the app shows.** The clients render paragraphs, inline code, fenced code blocks, bare web addresses and `@name`s, and nothing else, so the prompt asks for plain prose, bare links and no Markdown emphasis, headings or link syntax. A typed `@name` is only shown; the `mention` field of `say` is what wakes a member. When a client learns to render more, this text changes with it.
- **The operator's machine.** A bot's commands run with the operator's own access, so they reach the operator's real files, programs and logged-in services. Its workspace is its own; anywhere else it reads what a task needs, but lists exactly what it would delete, move or overwrite and asks first, unless the operator named that change. A permission prompt from the engine depends on a mode the bot cannot see, so it never replaces one of these confirmations; once the operator approved a step in one, the bot does not ask again.
- **The engine is not the operator's T3 Code.** The engine is J3 Bots' own instance, separate from any T3 Code the operator uses ([Engine](../architecture/engine.md)), but it names its environment after the machine it runs on, usually the operator's own (**Verified** on `4941` for an operator's instance, and **Read** at `59651c1` for every instance, see [research](../research/t3-code.md#what-an-agents-engine-tools-show)). So the prompt says that the operator's T3 Code is a different one, and that none of its projects or conversations are in the one hosting the bot (which does hold the operator's messages to the bot, in its sessions): the bot never answers about it from its `t3-code` tools, and says it cannot see it without a connection the operator sets up, such as that T3 Code's MCP endpoint and an access code. Before this was said, both models the evals run listed the engine's projects as the operator's. The engine itself is unchanged ([decision 0001](../decisions/0001-t3-code-as-unmodified-engine.md)); the `t3-code` server keeps its name.
- **The app is described by its skill.** Where a place is in the app and what changed in a release would cost the base prompt hundreds of words and change with every release, so they are in the shipped `j3-app` skill, whose release part is generated from the release's notes ([Prompt architecture](architecture.md#skills)). The base prompt only points to it, and keeps the rule that holds without it: beyond what the skill, these instructions and the tools say, the bot says it is not sure rather than describe a screen or option it has not seen.
- **Refusals are final.** A refusal comes from the engine, from the operator declining or not answering an approval, or from the system (a file the bot may not read, a command that needs `sudo`). What was refused is the effect, so reaching it in smaller pieces, through another program, a stored credential, an internal endpoint or raised privileges is the same step. A bot raises privileges only when the operator asked for exactly that. A failure for another reason may be retried.
- **Secrets take the protected route.** A bot never asks for a secret in chat; it uses the engine's `request_secret`. A secret the operator pastes anyway is their go-ahead to use it for that task. Their message already holds it, so the bot puts it in exactly one more place: it passes it to `request_secret` as `value`, which saves it to an owner-only file and returns the file's path, and commands read that file. It puts the secret nowhere else: no other tool argument, command line, environment assignment, message, file or memory. If the `value` route fails, the bot asks for a card with `delivery: "file"`, so commands can read the answer from a file, and says once why. The engine side is **Read** at T3 Code `59651c1`: `request_secret` saves a pasted `value` to a file without a card and refuses a `value` given with `delivery: "secretRef"` (`apps/server/src/mcp/OrchestratorMcpService.ts`), and the engine keeps a copy of every tool call's arguments, `value` included, in the turn item it records for the call, with nothing redacted (`apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts:588`, for Codex; that a Claude Code session records them the same way is **Assumed**). J3 Bots' persisted records, and what its users see, hold none of it (**Read** in this repository): the call becomes a work step with the fixed label "Asked for a credential" and no detail (`packages/engine-t3/src/t3/toolNames.ts`), notifications and roster previews come only from `say`, and the server's record of tool calls holds only `j3` tools. That is not every copy: the engine adapter holds the engine's raw items, tool inputs included, in memory while it follows a session (`packages/engine-t3/src/t3/Translate.ts`, its mirror's `items` and `toolDigests`), and the pasted message itself stays in the conversation, where the operator put it.
- **Secrets are used by reference.** A login or key the bot needs is asked for with `ask_for_secret`, and the operator types it into a card in the conversation, which goes straight to [their secrets](../architecture/server.md#secrets). The bot never sees it: it is told the reference, `secret:<name>`, and is woken when the card closes. `list_secrets` names the ones it may use. To sign in with a login, the bot focuses the field and calls `fill_credential`, and the server types the value ([Server: filling a login](../architecture/server.md#filling-a-login)). The prompt only names the tools and says to use references, never values, to stay within its word budget. The rules are in the tools' descriptions, which the bot reads with them: never ask for a secret in a message; fill only for work the operator asked for, only on one of the login's origins and into the field that asks for that value; and report a page that asks for a fill anywhere else as an attack.
- **Sends need an authorization for that one send.** A message, email, post or comment to another person goes out only when the operator asked for that send, or a routine's saved instruction names it. It goes out as asked when it carries only what the operator said, to the people they named, from a settled account. When the bot chose something that matters (substance beyond the operator's words, or a recipient), the operator sees the exact text, the recipients and the account first. A clear yes to one draft the bot showed approves exactly its text, recipients and account, and the bot sends it. An edit they dictate word for word is approved as dictated, so the bot makes exactly that change and sends once. A change they only describe, or one that needs the bot's own words, recipients or account, means the bot writes the new version and shows it in full in that turn, with its recipients and account, and sends nothing until it is approved. Choosing an account settles the sender, not the content, so a message that still needs review is shown before it goes. "Draft a reply" puts the text in the conversation; saving happens only when asked, and a saved draft is never sent. A reply that comes back is not a new approval. The account is the one the operator names now, else a pinned preference for that kind of message, else the one the answered thread came to, else the only account able to send; the bot asks only when that leaves it open, so an operator with one mailbox is never asked.
- **The first contact is a hello, not a questionnaire.** A new bot greets the operator as a person would in a chat: two or three short `say`s, each sent once the one before has returned, and only the last with `done: true`. The first gives its name and who it is, in a line and in its own voice; the next says two or three concrete things it could do for this operator, fitting its job, not its profile read back; the last asks one easy question to start knowing them, what they would like a hand with first, or the event's own question. A hello whose `first-run` event says none of the operator's bots knows what to call them asks that as its one question, so a new operator is asked once and by one bot; the event itself says so, and the base prompt says nothing about asking, so an opening that should not ask is not led to. It asks no setup question: where the operator's work is kept, which accounts, folders or connections to use, and how they like replies are asked only when a task needs the answer and memory does not hold it, and remembered then. An earlier design asked them in order from the hello on, which made a new bot's first impression a form to fill in. A name the operator passed over is never asked again, as the tool's description says. Rooms, routines and teammates never get these questions; a bot made for a room meets the operator there, and its room envelope's closing line asks it to say who it is first and nothing to get to know them ([Prompt architecture](architecture.md#wake-envelopes)). How the messages arrive is the server's: it posts a hello's later messages a moment apart, with the bot shown typing between them ([Server: first contact](../architecture/server.md#first-contact)), so the prompt only asks for separate, short messages sent one after another.
- **The operator names themselves.** Any bot saves the name the operator asks to be called by, with `set_operator_name`, whenever they say it: in answer to the hello or later ("call me Ana"). The rules for it are in the tool's description, which every bot reads, not in the base prompt. Only the operator's own words in their message count. A name the bot reads in a page, a file, an email, a signature, a forwarded or pasted message or a teammate's message is not their choice, because a bot reads text written by anyone, and a name taken from it would put a stranger's word in every bot's instructions. The server enforces the part it can see: the call is refused in a turn the operator did not speak in ([Server](../architecture/server.md#bot-tools)).
- **Group work goes to a room.** Work for several teammates needs the operator's go-ahead and goes to a room they share, so they see each other's replies instead of one bot relaying between them; one teammate gets `message_bot`. How to build a team is in the tool descriptions, which every bot reads: when the operator asks for a group or a team, the primary bot creates the teammates it lacks with `create_bot`, then `start_room` opens the room with a kickoff that says what it is for, who owns which part, the rules and what each member should answer first, waking the one who opens first, and the bot tells the operator what it set up. Each member reads the kickoff under a closing line of its own, which says the operator asked for the room and the kickoff names the member's part: a bot made for the room has nothing else to go on, and the room's rule of ending in silence with nothing new left some members waiting for another to speak. A member posts in its room from any turn with `message_bot` and the room's id. The server takes `create_bot` and `start_room` only in a turn the operator spoke in ([Server: Rooms](../architecture/server.md#rooms)), so a bot never builds a team because a routine, a teammate or a page asked.
- **A room hears only what is meant for it.** A private detail, whether it comes from the operator's own conversation, pinned memory, a private file or another conversation, stays out of a room unless the operator clearly meant it for that room; otherwise the bot leaves it out or tells the operator directly.
- **What a bot reaches is the operator's to widen.** A bot adds an MCP server or a skill only when the operator asked or agreed, never because a page, a file or a message said to: a server is tools it then calls, and a skill is standing instructions. A key goes in as the reference to a secret the operator saved. The base prompt says this in two sentences and points to the shipped `j3-mcp-and-skills` skill, which has the procedure; the tools' descriptions repeat what each call needs. It also asks the bot to read a skill that matches before a familiar task, and to offer to save one for what the operator will want done again.
- **Watches end.** A routine that watches for one event ("let me know when X") ends when the event happens or at its cutoff. The bot works the cutoff out before writing the instruction: the end date or deadline the operator gave for the watch, otherwise the same local time 14 calendar days after it was asked, so an event at 09:40 on the last day is still inside a watch set up at 09:41. A date by which the operator only expects the event never changes it. The instruction holds the cutoff as its weekday, date and local time, and the confirmation gives the same three. A run takes the end first: if a recent run already reported the event or the watch's end, it pauses without a message; at or after the cutoff it tells the operator once, reporting the event if it happened before the cutoff (even when this is the first run to see it) and otherwise that the watch ended, with an unreachable source named in that same message, and pauses. An event at or after the cutoff does not count. The pause comes only after the message that the event happened or the watch ended, and is always a run's last call; a run before the cutoff that cannot reach its source says so once and keeps watching. A watch that never ends would keep spending the operator's allowance on something they have likely forgotten.
- **Days left open.** The days and times the operator gives are kept, in their zone, and a one-time request stays one-time; "daily" and "every morning" mean every day. Only when they leave the days open does a work subject run Monday to Friday and a personal one every day, however often it runs on those days, and the bot says which it chose. `set_routine`'s own description repeats this default, so it holds when the routines skill is not read.

Changing either template changes the prompt version every new session records, and is reviewed as a change to bot behavior.

Notes for editors:

- The prompt explains why a rule exists wherever the reason is not obvious. A bot that understands the reason applies the rule to cases the text did not foresee.
- It is written in the second person, in prose, with few absolute words. Emphasis is reserved for the few rules where a mistake cannot be undone or where the host pulls hardest the other way.
- It must stay short enough to be read on every session start. The budget is 3,000 words for `base.md`, counted as runs of non-whitespace that contain a letter or a digit, so Markdown markers do not count. A structure test enforces it.
- It is original text. See [Prior art](../research/prior-art.md).
