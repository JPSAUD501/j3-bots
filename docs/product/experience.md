# Experience

This document describes what the operator does and sees. It is written from their side: the question each screen answers comes before the screen.

## Flows

### First run

The operator chooses where the bots live. In the desktop app, the first screen asks: "Use this computer" runs them on that computer, where they sleep when it sleeps, and goes straight on with nothing to type, while J3 Bots starts there; "Connect to a server" leads to the address of a machine that stays on, where the operator installed J3 Bots, and pairing with it. A browser or a phone always pairs with a server. Until the first bot exists, the app is a short the operator plays: one stage, a few bots on it, and one thing asked at a time under them. Every step can be left with its defaults: Continue always works, at once, wherever the stage is in what it is doing, and Back, the screen's or the phone's own, always goes to the step before. Left mid-way, by a closed tab or an app put away, it starts again where it was, with the name typed and the look picked.

1. **A welcome.** A few bots come down onto a stage, each into its own light (on the web and in the desktop app the stage is dark, whatever the app's appearance; on a phone it takes the app's), and one sentence says what they are: teammates that keep working on the operator's machine and subscriptions. They are alive from the moment they land: they look at a pointer or a finger that comes close, and answer a tap. Settings stays in reach from here, for signing out or changing the language.
2. **The first bot's name.** The view closes in on one of the bots, the one being made, and on the web the others step back into the dark to watch. The field starts with a person's first name, common in the language the app is in (Maya or Leo in English, Bia or Davi in Brazilian Portuguese), so the operator can just go on; they can rename the bot any time. The bot looks down at the name as it is typed, and wears it.
3. **Its look.** Twelve silhouettes and twelve colors to pick from, one pair already picked, with the bot above taking each as the operator picks, and the stage's light turning to its color. Where the bot works is not asked: J3 Bots gives every bot its own workspace.
4. **A model, only when none is connected.** If no provider can run a bot yet, one step says so in plain words. In the desktop app running the bots on its own computer, it offers a button for each harness found there, "Sign in with Claude" and "Sign in with ChatGPT (Codex)", which signs that harness in with the operator's own account through their browser, with a quiet line that the bots' usage counts toward their plan's limits; where it finds neither, how far the server's own install of each has come, as below; and, folded away, an endpoint and its key instead. Elsewhere, it gives the one command to run on the machine J3 Bots runs on and a button that copies it, and points those who would rather sign in with their own Claude or ChatGPT account to the install guide. The step updates by itself when a provider connects, and once shown it stays in the sequence, also when the operator goes back. It never holds the bot back: the operator can create the bot anyway, and it says hello once a model is connected; if the bot landed on a provider that turns out not to be there, it moves to the one that connects. Only a server with no model at all refuses the bot, as while its engine is still starting and reports no provider, so then Create waits, and the step says it can be created as soon as Claude Code or Codex can run. When no provider can run and connecting would not change that, the step lists each one with why, in one line, and one way forward, and beside a sign-in or the command, it lists the same way each provider that connecting would not fix: a harness not installed where the server runs is being installed by the server already, from the harness's maker, since it started: the step says **Installing…** with how far the download has come and **Cancel**, never the engine's own "not found"; when it did not finish, why, in one line, with **Try again**, and once cancelled, **Install**; where the server cannot install it (an older server, or a system J3 Bots installs no build for), it links to its install page with **Look again**, one that was found but failed to start offers **Try again** (and, in the desktop app running the bots on its own computer, says where the server's log is), one whose check took too long says the server checks it again on its own, with **Try again**, and one turned off on the server says only that. While the engine is still checking the providers, in the first seconds after it starts, the step says so without the command, since the check may find one ready. It does not ask for API keys. With a provider ready, this step is skipped.
5. **The bot arrives** once the server has created it, in a short finale: a light crosses the stage, the others come back into their lights and cheer, and the bot grows, with its name under it. Then it travels into the header of its conversation as that opens, and becomes the primary bot without being asked. On this computer, a bot asked for while J3 Bots is still starting there waits for it, and the arrival says so. A start that failed takes the screen instead: why, what repairs it, and Try again.
6. The conversation opens and **the bot speaks first**, as a new teammate would in a chat: two or three short messages, each arriving a moment after the one before while the bot is shown typing. The first says hello, with its name and who it is in a line, in its own voice; the next, two or three concrete things it could do for this operator, fitting its job; the last asks one easy question to start knowing them, such as what they would like a hand with first. If its job already says what to do, it says hello and starts the work instead, with the same approvals as any other work. It asks nothing about setup: where the operator's work is kept, which accounts, folders or connections to use, and how they like replies come up only when a task needs them. Stop works while it types, and drops what it had not posted yet. While none of the operator's bots knows what to call them, the first bot to say hello asks that, in a few friendly words, as its one question; a hello that failed asked nobody, so the next bot to say hello asks. It saves the answer as the operator's name, which every bot uses from then on, and a quiet line in the conversation says so; Settings shows the name live and still changes it. An operator who passes over the question is not asked again, and telling any bot later to call them something else changes the name the same way. On a server upgraded from before this question, the bots it already has have said hello, so no new bot asks; such an operator tells any bot what to call them, or sets it in Settings. A name the bot only reads, in a page, a file, a forwarded message or another bot's words, is never taken as theirs. It saves what matters in what the operator tells it as its first memories. There is no settings form to fill in. If the provider is not signed in yet, the hello waits for it. What the operator writes meanwhile waits too, and goes after the hello, as the bot's next turn: the bot greets, then answers the messages in the order they were written, also when the hello fails or stops at its provider's usage limit. A failed hello is otherwise offered again, until the operator writes. A bot another bot made for a room opens in that room instead, and never says hello in its own conversation: its first message in the room opens with who it is, then takes its part, paced the same way ([Several bots, one goal](#several-bots-one-goal)). If the operator writes first while nothing holds the hello back, before it has gone to the engine, the hello is dropped and the bot answers the message. Once the hello has gone, a message is like any other: it reaches the bot's turn while that turn runs and can redirect it, or goes next once it has ended.
7. The moment the operator hands it something real, the bot does the work, and asks only what that work needs.

Until its hello can run, the conversation says what it waits for: the usage limit's reset, at the time it resets when the provider gives one, or otherwise a connected model, with what connects one where this device is: in the desktop app running the bots on its own computer, the same sign-in buttons as step 4; on another device reaching a server the desktop app runs, a line that sends the operator to Settings → Providers in the app on that computer; elsewhere, the same command and copy button. What the operator writes meanwhile waits for the hello and goes right after it, and each message says so in the same words ("Sent when the usage limit resets", "Sent once a model is connected"); once the hello has gone, it shows as queued like any message.

### Talking to a bot

The operator picks a bot in the roster and types.

- The bot acknowledges within a second or two, in a few words, then works.
- While it works, a row where its reply will appear shows its face in that state, one line saying what it is doing right now, and how long the turn has run. The operator can open the work to see every step, but nothing forces them to.
- The conversation's header shows the bot's face and name, with no line under the name about what it is doing: that is the conversation's to show, in the row of the turn under way and in its cards.
- The answer arrives as a short message. Longer material arrives as a file or a card.
- The operator can send another message at any time. It reaches the bot mid-turn and can redirect it.
- "Stop" ends the work. It does not undo what was already done, and the bot says what was left running, if anything. It sits in the bot's details, one press from the conversation's header, while there is work to stop; the conversation itself stays about what the bot is doing. On a computer, `Ctrl+.` (`⌘.` on macOS) stops it from the conversation.

### Being asked

A bot needs a decision or permission.

- A **question** arrives as a card with a few options and, when it makes sense, room for a typed answer. Tapping an option answers it.
- An **approval** arrives as a card that names the exact action, with Allow and Deny. Allowing can be for this once or for the session.
- Both produce a notification on the operator's devices. Answering on any device resolves the card everywhere.
- While the bot waits on a card the operator has scrolled away from, "Waiting for you" floats over the end of the conversation, with an arrow toward the card, and brings it back into view.
- A question the bot asked on its own can be dismissed, which is a "no". The bot does not ask again. A question its coding tool asks mid-task has no dismiss: it waits for an answer, or for the operator to stop the bot.

### Watching the bot's browser, and taking it over

A bot shops, books or reads a site in its own browser, on the machine J3 Bots runs on.

- While the bot has a page open, a globe sits in its conversation's header, its mark breathing while the bot acts on the page. Under the line of the turn under way, a picture of the page and the site's name, taken again as the page changes and every few seconds while the bot works. It is a picture, not a live view: watching it costs nothing.
- Either opens the browser: beside the conversation on a wide window, over it on a tablet, rising from the bottom on a phone. The page is live, its site and address shown, and a line says who is acting on it: "The bot is browsing", "You have control" or "On another device". While the operator only watches, the page takes nothing they do, and the bot's pointer shows where it acts.
- **Take control** is the one primary action. Once taken, the bot cannot act on the page, and everything the operator does over it goes to the page: the pointer, the wheel, typing, a phone's keyboard on a field they tap. Back, forward, reload and the address field appear only now. **Done** gives the page back to the bot.
- When the bot asked for help on the page (a sign-in, a code, a check that a person is there), **Done** tells it the step is done, and **Can't do it** tells it the operator could not; either gives the page back. **Open browser** on that card opens the browser on the page. Its notification says what the step is and the site, "Needs your help in the browser: Sign in on example.com", never the bot's own note, so a link or a code the bot put there stays off a locked screen.
- A sign-in window the page opens shows in the browser as the bot's front page; the operator keeps control in it, and the browser goes back to the page it came from when it closes.
- Leaving the browser while in control asks once whether to give the page back to the bot. Keeping it leaves the bot waiting until the operator returns and presses Done; giving it back this way leaves a help card open, since the step may not be done.
- The operator's clipboard and files never reach the page: pasting, dropping, downloads and file pickers are out of reach in this version.

### Work that starts on its own

The operator says "every weekday morning, tell me what changed in the repo" or "let me know when the deploy finishes".

- The bot creates a routine and confirms the exact schedule it saved, in the operator's time zone.
- When the routine runs and has something to report, a message appears in the bot's conversation. It reads like the bot mentioning something it took care of, not like a system alert.
- When there is nothing to report, nothing appears. The run is still recorded in the routine's history.
- The operator pauses, edits, tests or deletes a routine from the bot's details, or by telling the bot.

### Several bots, one goal

The operator asks a bot for a team, or sets one up themselves.

- **Asking for one.** The operator tells a bot, in its conversation, something like "make me a support group, several bots". In that one turn, the bot makes the teammates the group lacks (only the primary bot can, at most five at a time), each named as a colleague would be, unless the operator named them: a first name common where the operator lives and in their language, different from the other bots' names, with the role in its title, never in the name. Each runs on the bot's own model, or on the default one while that model's provider is not ready. The bot then starts a room with them, and posts a kickoff there: what the room is for, who owns which part, the rules, and what each member should answer first. Then it says in the conversation what it set up and who owns what, under a quiet "Scout started Support" line. A bot made for the room opens there, with no hello in its own conversation: its first message in the room says who it is, and its conversation shows instead a quiet "Made by Scout for Support" line. Both lines name the room as it is called now, so a rename shows there, and open it with a tap; once it is deleted they say "a room" and open nothing. The members the kickoff names, every one by default, start on it at once; a member the kickoff gives a part answers it rather than waiting for someone else to speak. Only the operator's own word starts a team: a bot never makes teammates or rooms because a routine, another bot or something it read asked.
- **Setting one up.** The operator creates a room, adds two to six bots, and writes.

Either way, the room then works the same:

- The room's header shows its members' avatars side by side, up to three, then how many more ("+2"), and its name. The composer reads "Message Support".
- Every member reads every message in the room, the operator's and each bot's. A message that mentions nobody wakes every member at once, but the bot that wrote it, and each answers only if it has something to add, so a hello is not answered by every member. Members answering at the same moment do not see each other's replies, so two may still say the same thing, as people in a group do. The room's empty state says so.
- `@Name` speaks to that bot: only the bots a message names are woken, and they answer; the others read it the next time they are woken, with whatever came after it. `@everyone` wakes every member and asks each to answer. A bot's message can name members too, and wakes only them; one that names nobody wakes the others. Nothing under the composer says whom a message goes to: a picked mention stands out in the text as a chip with the bot's face and color, as it does in the message once sent. The operator's message reaches a member it wakes mid-turn when that member is already answering in the room, and can redirect it; what a member missed while it worked reaches it with its next turn.
- While members answer, one quiet line at the room's end says who, with their faces: "Hal is answering…", several at once, "Hal and Bo are answering…", and past three, "Hal, Bo, and 2 more are answering…". It changes in place as each one's turn ends and goes once nobody answers, whether or not they said anything.
- A message that could not go because a member it mentions left the room says so, and Send again sends it to the members it mentions who stayed, or to the room when none did.
- Bots answer each other in the room. A member also posts there from its own conversation: when the operator asks it there to start work in the room or tell the room something, it posts it itself and says it did, instead of asking the operator to write in the room. What the members said there is part of its conversation, so it answers about the room from memory, and reads the room's latest messages, or searches them, when it does not remember or needs an exact detail. It never posts from its conversation on a stale view: if others wrote in the room since it last saw it, it is shown what it missed first, and when that changes what the operator asked (the work is already done, someone already answered), it tells the operator instead of posting. It quiets down when no bot has anything to add. The room also counts rounds of bots answering each other since the operator last wrote there, the same in a room of two as in a room of six: the members' replies to the operator are the first round, the replies to those the second, and so on. From the third round its members are told the conversation is winding down and answer only what is essential; past the fourth, a bot's message is still posted but wakes nobody, and one quiet line says the bots stopped answering each other and the room waits for the operator. The operator's next message there starts the rounds again, and so does the first post they asked a member for in its own conversation, so a room that went quiet starts again from there too. A request sent while the member was already busy with something else does not count yet: the member posts it, and asks the operator to ask again once it has finished if the room stayed quiet.
- Approvals and questions never appear in a room. They go to the asking bot's own conversation, and the room shows that the bot is waiting.
- While the room's work is under way, also work a bot left running in the background for it, the room's details offer Stop. It asks first, saying what ends (what the bots are doing for the room, and the work they left running for it) and that anything else they're doing goes on.

### One bot hands work to another

- The operator asks, or the bot offers ("want me to ask Scout?").
- What the two bots say to each other goes in their **teammate conversation**, "Scout and Wren", one per pair of bots. It reads like a room: each bot's name over its messages, its avatar in its tint, the time between them, and each message that never reached the other bot marked so. The operator reads it and cannot write in it: in place of a composer, a "Read-only" mark. Its menu offers "Talk to Scout", "Talk to Wren" and "Start a room with both".
- In each bot's own conversation, a run of messages with teammates, with nothing else between them, however long it lasted, is one small line led by the first teammate's small avatar ("Wrote to Wren", "Wren wrote", "Talked with Wren · 3 messages"), which opens the teammate conversation at the run. A run with several teammates ("Talked with Wren and Pip · 4 messages") first asks which conversation to open, in a sheet on the phone. A line whose messages did not all reach their teammate says how many did not, quietly ("1 not delivered"). An urgent message that never reached the teammate still shows the recipient's conversation a card that offers to send it again.
- The reply comes back later, as its own turn. Messages between bots never make a conversation unread, never become its last line in the roster and never notify: the operator is told only when a bot has something new for them, and a bot that needs them says so.

### Changing a bot

- **Name, title, avatar, model, permission mode**: in the bot's details.
- **Job**: an editable text in the bot's details. Telling the bot "from now on, never do X" updates memory instead; the job stays a short statement of purpose.
- **Memory**: the operator can read what a bot remembers, correct a line or delete it. They can also just tell the bot to forget something.
- **Fresh start**: stops any work the bot has running and resets its working context, with nothing of the recent conversation carried over, and drops the notes that would have told it what its routines reported. The conversation history, memory, routines and files stay. Each routine keeps what its recent runs said, which is the routine's own state: a run reads it to tell what is new and not report the same thing again. Moving a bot to another provider stops its work the same way, and its new working context does carry a digest of the recent conversation.
- **Delete**: removes the bot, its conversation, memory and routines after an explicit confirmation. Files in its workspace are kept unless the operator chooses otherwise.

### Sharing a bot, and starting from one

The operator has a bot that does its job well and wants someone else to have it, or a copy to start from.

- **Share as template…**, in the bot's details and in its roster menu under More, shows everything the file will hold, in full: the profile, the job, each skill's text, each routine's instruction and schedule, the model and the permission mode. It says that the job, the skills and the routines go exactly as written, and that the bot may have written some of them, so the operator reads them for anything they would not share; one line says what never goes (memory, the conversation, files, accounts, credentials, anything else on this machine). A bot whose file would be too large to read is not shared: the screen says so, and names the largest part to shorten. On Android it ends in the system's share sheet with a `.j3bot` file; on the web and the desktop the file is downloaded, or its text copied.
- **New bot from a template** in the roster's new menu picks a `.j3bot` file. A file dropped anywhere on the web or desktop window, shared to J3 Bots on Android, or tapped where it kept its media type, leads to the same place.
- That place is a preview of everything the bot will be and do, with a note that the file came from outside J3 Bots, that what it says goes only into the new bot, and that the other bots see the new one as any teammate. It says which model the bot will run on here, and whether that replaces the template's because this server does not offer it. The permission mode starts at the template's or the default, whichever lets the bot do less, and says so when it lowered the template's; the operator can pick any mode. A mode left as it was is the server's to settle when the bot is made, by the same rule. Its routines arrive paused, to be turned on in its details.
- Nothing is created until the operator presses Create. Then the new bot's conversation opens, and it says hello as any new bot does, the things it offers coming from its job, without starting any of that work, since the template's author wrote the job, not the operator. It begins when the operator asks. A file that is too large, damaged, or from a newer J3 Bots is refused with a sentence saying which.

What a template holds and leaves out is in [Concepts](concepts.md) and [decision 0023](../decisions/0023-a-bot-template-is-a-file.md).

### Giving a bot a service

The operator wants a bot to reach something it cannot yet: their notes, their tracker, their calendar.

- **Connectors**, in Settings as **MCP and skills** and in a bot's details, opens one screen that lists what the bots added: the operator's connectors first, each with its status and who may use it, and, once its server answered, a line with the version of MCP it speaks and how many tools, resources and prompts it offers. Each says who changed it last and when: the operator, or which bot. The skills follow, those every bot shares, then each bot's own, each with the same line. J3 Bots' own skills (`j3-…`) are not listed: every bot has them, and nobody changes them. With no connector, or no skill, one line says to ask a bot to add one. There is no form to add either, and no gallery to browse: the operator asks a bot.
- **The operator asks a bot**: "connect my Linear". The bot searches the gallery and adds it; in Supervised the operator approves the step first. A key is never typed in the conversation: the bot asks for it as a secret and uses only its name. A connector that needs signing in shows a Sign in card in the conversation, and the bot says it waits for that. A server in the operator's own network, or one that needs an app the operator registers (Google, Slack), waits on their yes: a card in the conversation says it in plain words ("Ana wants to connect to a service on your own network at 192.168.1.20:8123. Allow?"), or shows how to set up the app and takes its client ID and secret, which the bot never sees; Allow and Decline. Once answered, or closed with no answer, the card says how it ended, and the bot is told and carries on. The primary bot adds one for every bot; any other bot adds one for itself. Once a connector uses a secret, no bot changes where it sends it (its address, headers, command, arguments or other variables): the bot says the operator can change a command on its page, or offers to add it again and ask for the secret anew.
- **A skill** is one a bot saved or installed, when the operator asked or agreed. A bot asked to remember a procedure offers to save it as a skill, and does when the operator agrees. A skill's page shows its text to change, where it came from at which commit, and who changed it last, and Remove asks first.
- On the phone, a connector that runs a command shows read-only, with a line that it is changed or removed from J3 Bots on the computer: the phone is no place to review a command that runs on the server. Its status, and why it is not running, read as on the computer.
- A command connector's page, on the web and the desktop, has **Change command**: its program and its variables' names as they are, its arguments and values never shown. A new value alone is saved as it is, an empty one keeping its own. Anything else (the program, the arguments, a variable's name, one added or removed, or a new value for a variable that decides what code runs) needs the arguments and each value typed again, since the command line is saved whole, and asks for a confirmation first: the whole command line, every argument as it will run, a variable that decides what code runs (such as `NODE_OPTIONS` or `PYTHONPATH`) with its value, above the program and marked as part of the line, and the name of every other variable, never its value, marking a variable that is new, one that is gone and a program that changed, and saying it runs there as the operator's user, with everything that user can reach. Before that, the form says what the server would refuse: a package `npx` or `uvx` fetches at no exact version (with an example of one), a launcher option J3 Bots cannot read past, a variable such as `PATH` that chooses which program runs, or one named twice. Nothing runs until they choose Run it. The process the old command started stops, and the new one lists its tools, which bots get as for any connector. Disconnect says the program stops and its variables' values are deleted.
- A connector's page shows its status and what fixes it: connected; needs signing in again (Sign in again); can't reach it, and why; a command that is not running, because its program is not on the computer (install it, or name it by its full path), because it stopped or could not start (check the command and its variables; it starts again when a bot next uses it, waiting longer each time), or because J3 Bots refuses to start it as it is saved, as when a variable that decides which code runs takes its value from a secret (change the command and confirm it again); needs a secret, naming the one its settings use that is missing, has no value or is not shared with every bot that uses the connector (Open Secrets, to save or share it; choosing fewer bots works too); or secrets unavailable, when the server cannot read its secrets, which keep every connector's address or command, so every connector shows it then, one that needs no key included (Open Secrets, which opens Settings over the screen; closing Settings returns to the page as it was, with anything typed in it). Its tools are listed once it is connected. It says which bots use it, changed in place, and the origin of its address or the program it runs, never the whole address or the arguments, which can carry a key. Disconnect asks first.
- A connector's tools are what its service offers now: one it adds, changes or removes reaches bots as it does, with nothing to accept. Its page lists them.
- **A service can ask the operator** in the middle of what a bot asked of it: a card in that bot's conversation, which notifies, says which service asks and that the answer goes to the service only, never to the bot. It is a short form, or a page of the service's to open, named by its address's host. Send or Open, Decline, or Not now; the bot waits meanwhile. A form never asks for a password, a key or a code: J3 Bots declines one that does before it is shown. The card says when it is no longer needed, because the bot's work ended.
- **A service's prompts** are in the composer of a bot's conversation: typing `/` lists those of the connectors that bot may use, by name, with the service beside each. Picking one asks for its arguments, if it has any, and puts the text the service writes in the draft, to read, change and send as the operator's own.
- A bot that finds its connector signed out says so with a card in its conversation, whose Sign in again opens the connector's page and starts the sign-in, or opens its form again for one that takes a key. That form starts empty, since no secret is shown again, and only what the operator types in it changes: a new key alone keeps the account or workspace typed beside it before.

What a connector is, and what a bot can and cannot do with one, is in [Concepts](concepts.md); how its secrets are kept is in [Security: connectors](../architecture/security.md#connectors).

### Knowing what it costs

- A usage view shows each provider's limit windows as the engine reports them, and which bots and routines used turns recently.
- A routine that fires often shows its run count next to its schedule.
- When a provider's limit is reached, affected bots show as blocked with the reset time, and their routines wait instead of failing repeatedly.

### Keeping J3 Bots up to date

- A newer release can't be missed. On a paired device, one dialog opens in front of the app: "J3 Bots {version} is available", one sentence on what updating does, a few lines on what's new, a link to the release notes, "Update now" and "Later". It opens the same way on the web, the desktop and the phone, for the server's release and for the app's own.
- "Update now" updates the server first, then this app. It asks first only when bots have work running, as that work stops, with "Stop and update". The dialog shows both steps: the server's as it goes (downloading, checking the download against the project's signature, getting it ready, restarting), then the app's once the server answers on the new version. The desktop app restarts into its new version, the Android app installs its own, and a browser reloads. With the server already current, only the app updates. While the server restarts, the connection line says "Updating your bots to {version}…", not that the connection was lost, and the app reconnects by itself.
- When the server's update doesn't go through, the app is left as it was. The dialog says why, gives the command to run when there is one, and offers "Try again". An app that doesn't update after its server did offers "Try again" for itself.
- "Later" puts the dialog away for a day, and a newer release brings it back sooner. One quiet line stays at the foot of the roster, above Settings (over the roster on the phone), and opens it again. A step that runs can be hidden too, and the dialog comes back when it needs the operator. Settings → About and updates keeps the versions and the channels, and its "Update now" opens the same dialog.
- How it ended is said once in a toast, and shows in Settings until the operator closes it after: "Your bots run {version}", or that the update didn't go through and the bots are back on the version before, with their data as it was. A rollback stays in Settings, with why, its details and "Try again", for as long as the server runs the version it rolled back to.
- A server that cannot update itself from a client (started by hand, run from a source checkout, run inside the desktop app elsewhere) says so, with the one command to run on its machine instead. No button is ever offered that cannot work.
- Each side has a channel, Stable or Nightly, chosen in the same place: the server's for the server, the app's for the desktop app. Moving back to Stable never installs an older version: a nightly build stays until a stable release is newer, and Settings says so.
- The desktop app updates itself, with nothing to press. A newer version found as it opens is installed before anything else shows: the window says "Updating to version {version}", with the download's progress, and the app opens again by itself on the new version. With no network, or a release that takes more than a few seconds to answer, it opens as usual and says nothing. One found while it runs is offered in the dialog, whose "Update now" restarts into it after the server's update; put off with "Later", it installs as the operator quits, and "Restart to update" in Settings brings it sooner. A restart waits for changes being saved, and says so with "Cancel restart" beside it, for an upload stuck offline. A check that could not reach the release, as on a laptop opened before its Wi-Fi connects, tries again within minutes and when the computer wakes. An install that fails says so and offers the new version's download. "Update automatically" in Settings, on at first, turns off the install at launch and at quit: then the update waits for "Update now" or "Restart to update". Nothing installs that has not matched the project's signature. On this computer the app carries the bots' server, so updating the app updates both, and the bots start once the update at launch is done.
- When the app and the server speak different versions, the screen says which one is behind. A server behind the app offers "Update the server" right there, after asking it to look for a newer release once, as it may not have looked since this app's release came out; a server that cannot update from here gives the command to run on its machine; an app behind the server updates itself, or a browser reloads. The operator is never left on a broken screen.

### Moving the bots to a server

- Bots that started on the operator's computer move to a server that stays on from Settings → Where your bots live → "Move to another server". One dialog says what goes (the conversations, memory, skills and files, the shared memory and skills, attachments, routines, rooms and secrets) and what stays: paired devices and provider sign-ins, so the operator pairs and signs in again there, and each webhook gets a new address. It asks for a passphrase for the secrets, twice, and says plainly that it can't be recovered. Then the system's save dialog asks where the file goes.
- While it exports, the dialog says so. An export that fails says why, in the export's own words, and the bots run on the computer again as before; the operator can try again at once.
- Once the file is written, the bots stop on the computer and the app says they moved: when, the file, anything the export left out (secrets it could not read, with what brings them, files whose name a server refuses, by name), and what to do on the new server: import the file, pair again, give each webhook its new address. They stay stopped, even when the computer restarts, so they never run in two places by surprise.
- From there, three ways on. "Connect to the new server" goes to its address and pairing. "Run the bots here again" asks first, then starts them on the computer as they were. "Delete the data on this computer" asks first, saying the file is their only copy until the new server runs them, and that the secrets are lost with it when the file left them out. Connected to the new server, Settings still says the old bots' data is on this computer, with the same way to delete it.

## Screens

The interface is the same three regions on every surface. On a phone they are three screens; on a wide window they sit side by side.

### Roster

Answers: who do I have, who needs me, what is each of them doing.

- One row per bot and per room: avatar, name, time of last activity, one line of status or the last message.
- Rows that need the operator (a pending question or approval, an unread result) come first and are marked.
- Pinned bots stay at the top, as large avatars with their names; a room keeps its own pin, at the top of the list.
- The operator can group bots in named sections, in an order they choose, each one folded or open. A bot is in one section at most, and deleting a section never deletes its bots: they return to the list.
- Hidden bots and rooms keep running, and still notify. They are left out of the list and reachable through search, through everything that names them (a notification, a mention, a notice, a teammate list), and through a "Hidden conversations" row at its end, which says how many there are and whether one has something unread, and lists them, each with Show. A hidden one's details say it is hidden, with Show.
- Whether a bot or room is hidden is set when it is made and when it is edited: "Hide from the list", off unless the operator turns it on, in New bot, New bot from a template, Edit, and the room's form. A bot that builds a team may hide the helpers it makes that the operator did not ask to see, and say so; once the operator has shown or hidden something, or made it themselves, no bot changes that.
- After the bots and rooms, a "Between bots" section lists each pair of bots that wrote each other, latest first: both avatars overlapped, "Scout and Wren", the last message with who said it ("Wren: …") and its time. It is not one of the operator's sections, and its rows are never unread, pinned or notified. A pair shows only while both bots are in the list, neither hidden nor deleted; the other bot's details still reach it.
- Each bot and room has a menu (right-click, the "…" or a long press) to mark it read or unread, pin it, move it to a section, make it the primary bot, hide or show it, and reach its details. The primary bot's avatar carries a small star wherever it appears.
- Search finds bots, rooms and messages, and pairs of bots by either name, hidden ones too.
- New bot and new room are one action each, and a new bot can start from a template file.
- A bot or a room that was just made, by the operator or by a bot, comes down into its row in a light of its own color and lands there, a room with its members' faces, as the rows under it make room. One that is deleted or hidden sinks away as the others close up. Nothing of this plays for the rows the roster opens with.
- The bots in the rows are alive: each blinks, breathes and now and then does something small of its own, looks at a pointer or a finger that comes close to it and at nothing further away, goes down under a press and answers a tap.

### Conversation

Answers: what did we say, what is it doing, what does it need from me.

- Messages as bubbles, the operator's on one side and the bot's on the other, with timestamps between groups.
- In a room, each bot's name stands over its run of messages and its avatar beside the last, as in a teammate conversation. The header shows the members' avatars, three at most and "+2" for the rest, the room's name and, under it, who is in it. While members answer, the room's last line names them ("Hal is answering…").
- In a bot's conversation, the header shows the bot's face and name on one line, with no line about what it is doing under it.
- Cards inline for what needs the operator (questions, approvals, credentials, a step in the bot's browser, a connector to add or sign in to) and for files.
- What only happened takes one quiet line, as small as a time between messages: messages with teammates ("Talked with Wren · 3 messages"), a routine created or changed ("Routine Morning digest created"; several in a row, "3 routines created"), the name a bot saved for the operator. Tapping one shows the rest: the teammate conversation, the routine, or the routines to pick from.
- A finished turn's work folds into one line ("Worked for 2m") that opens to show the steps.
- A connector's tool can come with its own interface, such as a table of what a shop has in stock: it shows under the turn's work line, open or folded, in a card that names the tool and its connector ("Stock · Wheelhouse"), and the operator uses it in place. What it asks of the operator waits under it in J3 Bots' own words: running one of its connector's tools as the bot (Allow, Don't allow), once per tool, unless the bot is in Full access; sending the bot a message as theirs (Send, Not now); opening a link in the browser (Open, Not now). Nothing it does reaches the bot unless the operator sends it.
- While the bot has a page open in its browser, a globe in the header, and a picture of the page under the turn under way, open the browser.
- A composer labeled with the bot's name, or the room's ("Message Support"). Attachments and dictation are in the composer; nothing else is. A file stands in the message where the operator put it ("compare [image] with [image]"), and the bot reads it there, numbered and named as in the harness's list of files. A tap on a file shows it: an image in a viewer, anything else in the app that opens it.

### Details

Answers: what is this bot, and what runs without me.

- Profile: name, title, avatar, job, with Share as template.
- Routines with their schedule, next run, last result, and a pause switch.
- Files the bot produced.
- Memory, readable and editable.
- Connectors this bot may use, each with its status, and a way to the connectors screen. With none, one line says to ask the bot to add one.
- Teammates: the teammate conversation with each bot it wrote or heard from, with the last message and its time, a deleted teammate's included.
- Model and permission mode.

### Outside those three

- **Command palette** on desktop and web: jump to a bot, a room or a message; run any action by name.
- **Settings**: ten pages, each holding what an operator looks for in one place, in three groups: **You** (name and time zone), **Notifications**, **Appearance** (theme and language, this device's); **Providers**, **Usage**, **MCP and skills** (the connectors and the skills), **Secrets** (with the bots' browser and its sign-ins); **Devices** (this device, every paired one, pairing another, and signing out), **Where your bots live** (in the desktop app and on a phone) and **About and updates**. On a wide window the list stays beside the page; on a narrow one and on a phone, the list opens each page, and Back returns to it. Each page says in one line what it holds; what cannot be undone stands apart at its end. A page that waits on the operator carries a dot in the list: providers that cannot run a bot, a connector that needs them, an update on offer, and in the desktop app this device's sign-in stored without encryption. Providers shows the engine and each provider's status, each provider that cannot run with why, the engine's own words when it gave any, and the same way forward as the first run; each harness's version, and, when a newer one is out, **Update** where the engine can install it, or that the operator updates it the way they installed it; while an update runs, Settings says so, and it says how it ended. A harness J3 Bots installed itself shows the same line, with one **Update** that J3 Bots runs: its progress and **Cancel** while it downloads and checks, that it waits for the bots using it to finish what they are doing before it switches, and how the last install or update ended; and one switch, on unless turned off, that has J3 Bots keep those copies up to date by itself. About and updates shows the server's version and channel, and in the desktop app and on a phone, the app's.
- **Updates on the phone.** When the server or the app has an update, the update dialog opens over the roster, as on the other clients, and "Update now" updates the server first and the app after it. After "Later", one quiet line over the roster says an update waits and opens the dialog again. While the server updates, the same line shows how far it has come, its restart included, in place of the line that says the server cannot be reached. It then says once how the update ended. The app updates itself as it opens: with "Update automatically" on, the default, it downloads a newer release, checks it against the project's signature and installs it with no tap, while the same line says how far it has come and that the app closes to finish; Android installs it without asking where it allows that, and asks once otherwise. An update that does not go through says so in that line, once, and the app tries again the next time it opens. Turned off in Settings → About and updates, the app's update is offered in the dialog, and Android asks to install it. The first time, the app explains Android's "Install unknown apps" before it opens that page, and goes on when the operator comes back. A phone whose server speaks another protocol shows the side that is behind, with the update that brings it forward. A server behind the app is first asked to look for releases, so the phone says none is out yet only after it has looked. An app behind its server looks for its own release as the screen opens, and has its check and its channel there, since the server may run a nightly.

## States the interface must always show

A bot is in exactly one of these, and the avatar carries it:

| State | Meaning |
| --- | --- |
| Idle | Nothing running |
| Thinking | A turn started and no visible work has happened yet |
| Working | A turn is running tools |
| Waiting | The bot asked a question or needs an approval |
| Blocked | The turn cannot continue: provider limit, error, engine unreachable |
| Done | Idle, with a result the operator has not read. It follows from the unread mark, so reading the result makes the bot idle on every device |

While a first contact's next message is a moment from arriving, the line that says what the bot is doing says "Typing", in its row and in its conversation; the avatar stays Thinking or Working.

"Working" and "stuck" must never look the same. A bot whose turn has produced no activity for a long time is shown as possibly stalled, with a way to check on it or stop it.
