# J3 Bots 0.3.1

**Draft.** The notes for the 0.3.1 release, kept here while it is prepared. The release workflow adds the install section and the Android certificate's digest.

From this release on, J3 Bots updates from the apps. Any paired device can update the server in one tap, the desktop app and the Android app update themselves, and each of them installs only a release the project signed. There is a nightly channel for whoever wants each day's changes first. It still pins T3 Code 0.1.11.

## Updating

This release still speaks **protocol 7**, so a 0.3 app and a 0.3.1 server work together, in either order. Updates are served outside the protocol, so from now on an app can bring a server on an older protocol forward ([decision 0032](https://github.com/JPSAUD501/j3-bots/blob/v0.3.1/docs/decisions/0032-updates-are-served-outside-the-protocol.md)).

- **The server:** `j3-bots update`, from its machine, this one time: a 0.3.0 server has no update routes, so an app shows the command instead of a button. It copies the databases first and runs one migration (0023: the update channel, which starts as stable). `j3-bots update --rollback` puts back 0.3.0 and the databases as they were before the update.
- **The desktop app:** the AppImage and the Windows install update themselves to 0.3.1. The deb and the Mac build link to this release. On this computer, the app's update carries its server, as in 0.3.0.
- **The web client** comes with the server.
- **The Android app:** install `j3-bots-0.3.1-android-arm64.apk` over the old one, this one time; it keeps its pairing. From 0.3.1 on, the app updates itself.

### `install.sh` now needs OpenSSL 3

`install.sh` checks the release's signature with OpenSSL 3, and refuses to run without it, before it downloads anything. Debian 12, Ubuntu 22.04 and Raspberry Pi OS bookworm ship it; on an older system, install it first. Releases before 0.3.1 have no signature, so this `install.sh` refuses them: install those with the `install.sh` on their own release page ([Releasing: what verifies a release](https://github.com/JPSAUD501/j3-bots/blob/v0.3.1/docs/operations/releasing.md#what-verifies-a-release)).

## What's new

- **Signed releases** ([#194](https://github.com/JPSAUD501/j3-bots/pull/194), [#196](https://github.com/JPSAUD501/j3-bots/pull/196)). Every release lists all of its files in `SHA256SUMS`, and `SHA256SUMS.sig` is the project key's Ed25519 signature over that list. `install.sh`, the server, the desktop app and the Android app check the signature before they trust a digest, and install nothing when either check fails. A release that someone changed after it was published, or one that names another version, doesn't pass ([decision 0031](https://github.com/JPSAUD501/j3-bots/blob/v0.3.1/docs/decisions/0031-a-release-is-signed-and-a-nightly-is-a-pre-release-of-the-next-patch.md)).
- **Update the server from any device** ([#196](https://github.com/JPSAUD501/j3-bots/pull/196), [#206](https://github.com/JPSAUD501/j3-bots/pull/206), [#211](https://github.com/JPSAUD501/j3-bots/pull/211)). The server looks for newer signed releases on its own, every few hours. Settings → About and updates shows the one on offer, with what's new. One tap updates the server: it asks first if bots have work running, then shows the download, the check, the restart, and how it ended, on every device. The update is the same `j3-bots update` as from a shell, with the same snapshot and the same rollback: if the new version doesn't start, your bots are back on the old one, with their data as it was. A server that can't update itself from here (started by hand, a checkout, no systemd user manager, no linger) shows the command to run on its machine ([Operating: from a client](https://github.com/JPSAUD501/j3-bots/blob/v0.3.1/docs/operations/operating.md#from-a-client), [decision 0033](https://github.com/JPSAUD501/j3-bots/blob/v0.3.1/docs/decisions/0033-a-client-update-runs-in-a-transient-unit.md)).
- **The desktop app checks what it downloads** ([#209](https://github.com/JPSAUD501/j3-bots/pull/209)). Before it offers "Restart to update", the app checks the download against the release's signed `SHA256SUMS`, and drops it if it doesn't match. A quiet dot on Settings says an update waits; nothing interrupts you ([decision 0034](https://github.com/JPSAUD501/j3-bots/blob/v0.3.1/docs/decisions/0034-the-desktop-app-installs-only-a-signed-download.md)).
- **The Android app updates itself** ([#212](https://github.com/JPSAUD501/j3-bots/pull/212)). It finds its own release, downloads it, checks it against the signature and asks Android to install it. The first time, it explains Android's "Install unknown apps" before it opens that page. One quiet line over the roster says when the server or the app has an update, and follows a server update through its restart ([decision 0035](https://github.com/JPSAUD501/j3-bots/blob/v0.3.1/docs/decisions/0035-the-android-app-installs-its-update-through-a-session.md)).
- **A nightly channel** ([#194](https://github.com/JPSAUD501/j3-bots/pull/194), [#196](https://github.com/JPSAUD501/j3-bots/pull/196), [#209](https://github.com/JPSAUD501/j3-bots/pull/209), [#212](https://github.com/JPSAUD501/j3-bots/pull/212)). Each day's changes to `main` that passed their checks are built, signed and published as a pre-release of the next patch, such as `0.3.2-nightly.20261201.12`. The server, the desktop app and the Android app each have a Stable or Nightly switch; stable is the default. Moving back to stable never installs an older version: it waits for a stable release newer than the nightly you run.
- **Versions that don't match** ([#209](https://github.com/JPSAUD501/j3-bots/pull/209), [#211](https://github.com/JPSAUD501/j3-bots/pull/211), [#212](https://github.com/JPSAUD501/j3-bots/pull/212)). When the app and the server speak different protocols, the app says which side is behind and offers that side's update. A server behind the app is asked to look for releases first, so the app says none is out only after it has looked.

## Not verified yet

These run in tests, on a boat VM and on the Android emulator, but not yet on the real thing:

- **No signed release exists yet.** The first nightly after this merges is the first real run of the signing, the nightly workflow and its cleanup. The workflow token creating and deleting nightly tags is **Assumed**.
- **The desktop app's check, end to end.** No AppImage or Windows installer has been updated through electron-updater against a signed release. The check is proven against the same cases as the server's.
- **The Android app on a real phone.** Everything ran on an x86_64 emulator with Android 16, against a fake release site: not the arm64 APK, not Android below 13, not GitHub's real API. An app installed from Play opening its Play page has never run.
- **A server update with bots at work.** The proof's server had no bots, so holding new work until the service stops is covered by tests only. So is a machine restart in the middle of an update.
- **A `$` in the install's path**, through the update's systemd unit, was checked on systemd 255 directly, not end to end.

## Known limits

- **macOS:** the desktop app doesn't install its own updates there; it links to the release.
- **A 0.3.0 server** can't be updated from an app: it has no update routes. Update it once with `j3-bots update` on its machine.
- **A nightly has no review** beyond the checks on `main`: whatever reaches `main` reaches every server and app on the nightly channel the next day ([Security: release signing](https://github.com/JPSAUD501/j3-bots/blob/v0.3.1/docs/architecture/security.md#release-signing)).
- **Desktop builds carry no code signature.** An update is checked against the release's signature, but the first install is trusted as far as the page it was downloaded from.
- **The server's release checks** go to GitHub without a token, so GitHub sees the server's address and the version it runs. They count against GitHub's hourly limit for requests without a token, shared by everything else on that address.

Everything listed under "Known limits" in the [0.3.0 notes](https://github.com/JPSAUD501/j3-bots/releases/tag/v0.3.0) still applies.
