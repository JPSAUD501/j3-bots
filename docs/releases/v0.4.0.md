# J3 Bots 0.4.0

**Draft.** The notes for the 0.4.0 release, kept here while it is prepared. The release workflow adds the install section and the Android certificate's digest. Parts other work is still finishing are marked `TODO(<lane>)`.

Your bots can now work in a browser you can watch and take over from any device, keep your logins in a vault they never see into, and use your services through connectors the server signs in to for them. A bot can also show a chart, a table or a diagram it built, right in its message. It still pins T3 Code 0.1.11.

The walkthrough is [A bot's browser, the vault and connectors](https://github.com/JPSAUD501/j3-bots/blob/v0.4.0/docs/operations/browser-vault-and-connectors.md).

## Updating

This release speaks **protocol 8**. A 0.3 app and a 0.4 server, or the other way round, show each other as incompatible, with a screen that says to update. Update the server and every app.

- **The server:** `j3-bots update`. It copies the databases first and runs this release's migrations. `TODO(lead)`: name them once they are numbered at merge.
- **The desktop app:** the AppImage and the Windows install update themselves. The deb and the Mac build link to this release.
- **The web client** comes with the server.
- **The Android app:** install `j3-bots-0.4.0-android-arm64.apk` over the old one; it keeps its pairing. It doesn't update itself, so until you install it, it shows the update screen.

### What changes on updating

- **No bot has the browser until you turn it on.** Until now the engine let every bot use its browser, and J3 Bots never turned that off. Now it is off for the whole engine, and each bot has a switch in its details: **Browser: Use this computer's browser**. A bot that browsed before needs its switch turned on.
- **The vault starts with no password.** Create one in the first run's step, on the first save-login card a bot shows you, or in Settings → Vault. **Nothing recovers a forgotten master password.** After every restart the vault is locked until you unlock it from any device.
- **The engine's sign-in for J3 Bots is made again** at the first start, with the right to act in the browser, and the older ones J3 Bots made are revoked. Nothing to do.
- **On Linux**, `j3-bots doctor` has a Browser line. If a bot will use the browser, run the commands it prints once, with `sudo`. They run only the system's own tools as root.

### Rolling back

`j3-bots update --rollback` to 0.3.0:

- gives every bot the browser again, since 0.3.0 has no switch;
- leaves the vault's file as it is: 0.3.0 doesn't read it, and 0.4.0 finds it again, under the same master password;
- loses the connectors you added since the update, and the cards, with the rest of the database;
- leaves the browser's profile, with your sign-ins, as it is.

## What's new

- **A bot's browser** ([#197](https://github.com/JPSAUD501/j3-bots/pull/197), [#184](https://github.com/JPSAUD501/j3-bots/pull/184), [#202](https://github.com/JPSAUD501/j3-bots/pull/202), [#204](https://github.com/JPSAUD501/j3-bots/pull/204)). A bot whose switch is on opens pages in the engine's browser on the machine J3 Bots runs on. On the web and the desktop, a globe in its header and a picture of the page under its turn open a live view of it: watch, **Take control**, and **Done** to give it back. While you hold the page, the bot can't act on it. Your pointer, wheel and keyboard go to the page, and on a phone a tap clicks, a drag scrolls and a tap on a field raises the keyboard. If your connection drops, you keep control for a minute. Every bot with the browser shares one profile, so it is signed in wherever you signed in there, and acts there as you; **Settings → Bots' browser → Sign out of all sites** ends every session in it.
- **A bot asks for help in its browser** ([#195](https://github.com/JPSAUD501/j3-bots/pull/195)). Facing a check that a person is there, a sign-in, a second factor, a QR code or a passkey, a bot doesn't try to get around it. It shows a card with the reason and the site, and its turn stops. **Open browser** takes you to the page, **Done** wakes the bot to go on from a fresh look at it, and **Can't do it** tells it you couldn't. On Android the card opens the browser on the whole screen, and notifies on a channel of its own. A card nobody answers expires after an hour, or when its page is gone.
- **The vault** ([#185](https://github.com/JPSAUD501/j3-bots/pull/185)). Your logins, with one-time codes, sealed on the server under a key that only your master password unlocks, and that is never written to disk. A bot that needs a login asks on a card, where you type it straight into the vault. **Settings → Vault** lists your logins without their values, shows one on request (hidden again after 30 seconds), shows the current one-time code, and edits, deletes and locks. Five wrong passwords make unlocking wait, up to an hour. The vault is never in an update's snapshot, so a rollback never brings back a password you changed. On Android, Settings → Vault creates the password, unlocks and locks; `TODO(V3)`: the rest, and a one-time code key added by scanning its QR code.
- **A bot fills your logins** `TODO(V2)`. With its vault switch on, a bot clicks a field and asks to fill a saved login there. The server checks that the page is one of the login's exact sites, types the value, submits a password at once, and gives the page back. The bot never sees the value, and you aren't asked each time. It can't tell which field has the cursor, so a bot that clicks the wrong field on the right site can see the password: the switch is off by default for that reason.
- **Connectors** ([#188](https://github.com/JPSAUD501/j3-bots/pull/188), [#201](https://github.com/JPSAUD501/j3-bots/pull/201), [#210](https://github.com/JPSAUD501/j3-bots/pull/210), [#198](https://github.com/JPSAUD501/j3-bots/pull/198), [#192](https://github.com/JPSAUD501/j3-bots/pull/192), [#200](https://github.com/JPSAUD501/j3-bots/pull/200)). Give a bot your notes, your tracker or your calendar. **Settings → Connectors** has a curated list (Notion, Linear, Atlassian, GitHub, Google, Slack, Stripe, Figma, Vercel, Supabase), a search of the official MCP Registry, and **Add your own** by address. You pick which bots may use each one. The server signs in for them, with OAuth or a key, keeps the sign-in in the vault, renews it, and makes the calls: no bot or app ever holds the token. A connector's tools follow the bot's permission mode, so in Supervised each call asks you first. A tool the service adds or changes waits for you to accept it. A bot can suggest a connector with a card, never add one. `TODO(G1)`: connecting a gallery entry, and reusing a service's registration. `TODO(C5)`: connectors started by a command, on the web and the desktop. `TODO(C8)`: connectors on Android. `TODO(C9)`: the bots' rules for connectors.
- **Visuals** ([#186](https://github.com/JPSAUD501/j3-bots/pull/186), [#189](https://github.com/JPSAUD501/j3-bots/pull/189)). A bot can show a page it built, a chart, a table, a diagram or a mockup, above the message that explains it, on the web, the desktop and Android. It follows your theme, and opens full screen. The page runs shut in a frame with no network and no way to reach the app, your storage or your files.

## Known limits

**Not tried for real yet:**

- **No sign-in to a real service.** Every OAuth flow ran against fake authorization servers. Signing in to Notion, Linear and Google is the owner's test of this release.
- **Google and Slack** ask for an app of your own. Their guides are drafts whose every step is **Assumed** ([Google](https://github.com/JPSAUD501/j3-bots/blob/v0.4.0/docs/operations/connector-google.md), [Slack](https://github.com/JPSAUD501/j3-bots/blob/v0.4.0/docs/operations/connector-slack.md)). Google's MCP servers are a Developer Preview that needs membership in its program, and Slack may refuse a sign-in that returns to plain `http:` on this computer.
- **A help card raised by a real model**, in a real browser, end to end. The prompts were tested with real models against a stand-in browser.
- **The browser on a Raspberry Pi, on Windows and on macOS.** On an x86-64 machine, one page with a viewer took 200–250 MB, and almost two cores while it animated without pause. A Pi will be slower: keep to a page or two.
- **A physical phone**, for the browser and the visuals: Android was tried on an emulator. A real keyboard's composition (swipe typing) and screen readers were not tried.

**Limits of this version:**

- **The bot shares your sign-ins.** Every bot with the browser acts as you on every site you signed in to there. Give it only to the bots that need it.
- **A bot's own shell is not walled off.** It runs as the server's user, so it can read the browser's cookies, and while the vault is unlocked, its key is in the server's memory. The vault and the switch keep values out of prompts, conversations and logs; a bot's permission mode is what limits its shell ([Security](https://github.com/JPSAUD501/j3-bots/blob/v0.4.0/docs/architecture/security.md#what-a-bots-shell-can-still-reach)).
- **The bot can read a page you hold.** It can't act while you have control, but it can still read the page, what you type into a field that doesn't hide it included.
- **No clipboard, downloads, uploads or file pickers** in the bot's browser, in this version.
- **On Android, the browser opens from a help card** only.
- **The web viewer on iOS Safari** may not raise the keyboard on a tap.
- **A page that doesn't repaint** may show no picture until it changes.
- **A connector signed in from the desktop or Android app** with a server elsewhere registers itself again at each sign-in. `TODO(G1)`.
- **Connector tools cost tokens on every call.** On Claude Code with a provider connection, 20 extra tools added about 4,000 tokens to each request, and 60 about 12,000. Codex keeps them out of each request. With a subscription it was not measured.
- **On Codex**, a connector call's approval asks in Codex's own words, without the call's input, and declining it does not end the call for a process that knows the bot's session and the call's input ([Security: known gaps](https://github.com/JPSAUD501/j3-bots/blob/v0.4.0/docs/architecture/security.md#known-gaps)).
- **A visual can name another site in a resource hint** (`preconnect`, `dns-prefetch`), which passes the frame's network policy. Whether the browser then connects is **Assumed**. A visual stuck in a loop stalls the other visuals in its process, and a reload may not bring them back. On iOS a visual shows as failed.

Everything listed under "Known limits" in the [0.3.0 notes](https://github.com/JPSAUD501/j3-bots/releases/tag/v0.3.0) still applies.
