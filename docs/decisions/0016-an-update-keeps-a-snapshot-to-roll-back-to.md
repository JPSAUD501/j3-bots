# 0016: An update keeps a snapshot to roll back to

**Status:** Accepted

## Context

An installed release is a folder in `<install>/versions/<version>/`, run by the `j3-bots` command, and the service's unit records the real paths of that release's Node and server bundle ([decision 0015](0015-a-release-is-a-self-contained-archive.md)). Moving to another release changes three things at once: the code the unit starts, the engine release it is pinned to, and the databases. Both J3 Bots and the engine migrate their database forward only, on the new release's first start, and an older release cannot use a database a newer one migrated: T3 Code refuses one whose migrations it does not know (**Read** at `db51b67`: `apps/server/src/cloud/servicePreflight.ts:68-77`, from `persistence/databaseMigrationHead.ts`), and J3 Bots used to start on one silently. Going back to a release therefore means going back to its databases too.

## Decision

**The installed release drives the update.** `j3-bots update [--version <version>] [--yes]` is run by the release the command points at, which can always start itself again. It works on the install it runs from: the folder whose `versions/` holds it and which holds the record of the command, `launcher`, wherever `install.sh` put it (`J3_INSTALL_DIR`, `$XDG_DATA_HOME/j3-bots` or `~/.local/share/j3-bots`). A checkout, or a release unpacked anywhere else, is refused. Data stays in the data directory, outside the install, as before.

**The unit says what runs.** With the service installed, the release that runs is the one whose Node or server bundle the unit's `ExecStart=` names in `versions/`, not the one the command runs: an update or a rollback killed after a release's `service install` wrote the unit and before the command was pointed leaves the two apart. `update` and `--rollback` start from the unit's release, so an update to the release the unit already runs only points the command at it (`j3-bots update --version <that release>`), and `--rollback` finds the snapshot taken by the update to it. `j3-bots doctor` says when the command and the unit name different releases, with that fix.

**An update survives a hangup.** The update ignores `SIGHUP` while it runs, so an SSH connection that drops does not stop it midway. The releases it runs (`engine fetch`, `service install`) run in sessions of their own, which a hangup does not reach, and their output is relayed through the update, whose writes to a terminal that is gone are dropped. A power cut or `SIGKILL` still stops it; the rule above is the recovery.

**Preparing changes nothing the service uses.** The target is the latest stable release, from the releases page's `latest` (asked for JSON), or the one `--version` names. Free space is checked first: twice the files a snapshot copies plus 1 GB where the data directory is, and 512 MB where the install is. The release is fetched as `install.sh` fetches one (`apps/server/src/install/release.ts`): its archive for this platform, checked against the release's `SHA256SUMS`, unpacked into a `.staging-*` folder in `versions/`, run once, then renamed to `versions/<version>/`; a release already there is used as it is, a folder there that is not a release is refused and kept, and the install folder and `versions/` must be this user's and not writable by every account. `J3_RELEASE_BASE_URL` points it at a mirror, as it does `install.sh`. Then the new release's own `j3-bots engine fetch` installs its engine beside the running one. Last, if the service's server says bots have work running (`GET /running-work` on the admin socket), the update asks, or needs `--yes`, since stopping the service stops that work.

**The switch is one uninterruptible sequence** (`apps/server/src/install/switch.ts`):

1. Stop the service and clear its failed state.
2. Copy, with no server running, into `<home>/backups/<time>-<from>-to-<to>/`: `config.json`, `j3.sqlite` with its `-wal` and `-shm`, and the engine's state its adapter names (`statev2.sqlite` with its `-wal` and `-shm`, and the engine's `settings.json`), each at its path relative to the home, flushed to the disk, then a `manifest.json`: when, both releases and both engine releases. A folder without a manifest is not a snapshot. Folders are 0700 and files 0600. A copy that fails is removed whole.
3. Run the new release's own `j3-bots service install`, which writes the unit with its own paths, enables and starts it, and gives up after 60 seconds without an answer from the new server. Its output is shown only when it fails: the update says what runs.
4. Wait, five minutes at most, for the service's server to answer as the new version, from the unit's main process, with its engine `ready`. The waiter decodes only `version`, `pid` and the engine state's tag from the status reply, so it reads a newer release's reply, which only adds to it. An engine reported `incompatible`, or a unit that fails, ends the wait at once. Within it, the server gives each launch of its engine 90 seconds and launches it again after a failure.
5. Point the command at the new release: the record first, then the command, each written whole under a temporary name and renamed into place, the command in exactly the form `install.sh` writes (`launcherText`), so `uninstall` still recognizes it.

**A new release that never became ready is rolled back by itself.** If step 1 or 2 fails, the old release's `service install` starts it again; the databases were not touched. If step 3 or 4 fails, the service is stopped and disabled, the snapshot is put back, and the old release's `service install` enables and starts it and is waited for the same way. The new server answered on its own socket while the update waited for its engine, so it may have accepted a message; that message is in the databases the restore moves aside, not in the ones it puts back. If putting the files back fails, the old release is not started on them. Once the new release is ready, nothing is rolled back: a failure to point the command is reported, with the service running the new release, and `j3-bots update --version <new>` points it. A failed update leaves `versions/<new>/`, the engine it fetched and its snapshot on disk; the next update that succeeds prunes them.

**A restore never leaves a home a server runs on half put back** (`restoreSnapshot` in `apps/server/src/install/snapshot.ts`). The service is disabled before it, and only the `service install` after it enables the unit again, so a reboot in between starts nothing. Every file of the snapshot is first copied beside where it goes, under a temporary name, and flushed; a failure there removes the copies and leaves the home as it was. Then a `restoring` mark is written in the snapshot's folder, every file the snapshot covers is moved out of the home into a new `replaced-<time>-<random>/` there (a write-ahead log the new release left must not stay beside a database put back), the copies are renamed into place, the folders are flushed, and the mark is removed. While a snapshot is marked, pruning keeps it, `update` refuses, `doctor` reports it, and `--rollback` restores from it again, which finishes it; each restore moves what is in the home into a folder of its own, so nothing is lost. Free space is not checked again for the automatic restore: the update's check reserved room for the snapshot and for the copies a restore makes.

**The unit is only ever written by a release's own `service install`.** There is no `current` link for the unit to start: the unit names one release's Node and bundle by their real paths, so it always names one release whole, and the switch never leaves it between two.

**`j3-bots update --rollback`** puts back the snapshot a restore has not finished from, if there is one, and otherwise the newest snapshot taken by an update to the release that runs now: after an update from A to B that worked and one from B to C that failed and rolled itself back, B runs, and the snapshot from A to B is the one, not the newer one from B to C. `doctor` names that snapshot. The release it was taken from must still be in `versions/`. Before anything changes, the install folder, `versions/` and that release's folder must be this user's and not writable by every account, as `install.sh` and the update check them, and there must be room for the copies: the snapshot's size plus 1 GB. It says when the snapshot was taken and what is lost, asks (or takes `--yes`), then stops and disables the service, puts the files back as the automatic rollback does, starts the earlier release with its own `service install`, waits for it, and points the command at it.

**Two of everything are kept.** After an update that succeeded: the two releases it moved between, the two newest snapshots, and the engine runtimes of those two releases, which `release.json` now names (`engine`). A snapshot is removed with its `replaced-*` folders, which the update's output says; one a restore has not finished from is kept. Nothing else in `versions/`, `backups/` or the engine's runtime folder is removed.

**Two installs of one engine pin can run at once.** `j3-bots update` right after `install.sh` fetches the new engine while the service may still be downloading its own first one. Each install works in a folder of its own (`<version>.work-<random>/`), takes an interrupted download over by renaming it there, so only one resumes it, and publishes by renaming what it unpacked into place with its marker; one that finds the pin published by another uses it and never removes it (`packages/engine-t3/src/t3/Install.ts`).

**A release refuses a database a newer one migrated.** On start, J3 Bots refuses a database that records a migration it does not know, naming it, as it already refused one with a gap (`apps/server/src/persistence/Migrations.ts`). Running an older release on a newer database by hand fails with that message, never silently. A snapshot does not record the migrations its databases hold: a restore always starts the release that ran on them, and that start is the check.

**Without a service**, the update copies the files and points the command, refusing while any server runs on the data directory; the operator starts the server.

## Consequences

- A rollback loses what happened after the update in the databases: conversations, rooms, routines and their runs, settings, paired devices, and the engine's threads. Bots' files are not in a snapshot, so their memory and workspaces keep what was written since. Nothing the rollback replaced is deleted: it stays in the snapshot's `replaced-*` folder until that snapshot is pruned, with it.
- An update cut off by a power cut or `SIGKILL` can leave the command on another release than the unit. Nothing runs on the wrong data: the unit names one release whole, and `doctor` says what to run.
- An engine install killed outright leaves its `<version>.work-*` folder, which no later install removes, since it cannot tell it from one that is running.
- A snapshot is about the size of the two databases. The update's free-space check and keeping two of each bound what an update leaves on disk.
- The engine's `settings.json` names the provider endpoint's base URL; the providers' key is in the engine's secret store, which is not copied.
- The check for running work and the stop are not one step: work a bot starts in between is stopped with the service.
- The automatic rollback starts the old release as its `service install` writes it, with the `PATH` and data directory of the unit it replaces.
- The first release that has `update` is the first that can be updated this way; a release from before it is replaced with `j3-bots uninstall` and `install.sh`.

## Rejected

**A `current` link that the unit starts.** The unit would no longer record what it runs, a link swapped under a running service changes its code without a restart, and moving the link does nothing for the databases.

**Copying the whole data directory.** Bots' workspaces, attachments and the engine's runtime are large, and no migration changes them. The snapshot holds what an older release cannot read after a newer one ran, and the settings beside it.

**Copying the databases while the old server runs** (SQLite's online backup). J3 Bots' and the engine's databases must be copied as one consistent pair, and the old server stops for the switch anyway.

**Having the new release drive its own update.** If it cannot start, it cannot restore the release before it. The installed release knows how to start itself.
