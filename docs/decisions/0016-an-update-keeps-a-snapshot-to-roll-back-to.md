# 0016: An update keeps a snapshot to roll back to

**Status:** Accepted

## Context

An installed release is a folder in `<install>/versions/<version>/`, run by the `j3-bots` command, and the service's unit records the real paths of that release's Node and server bundle ([decision 0015](0015-a-release-is-a-self-contained-archive.md)). Moving to another release changes three things at once: the code the unit starts, the engine release it is pinned to, and the databases. Both J3 Bots and the engine migrate their database forward only, on the new release's first start, and an older release cannot use a database a newer one migrated. Neither says so by itself: J3 Bots used to start on one silently, and T3 Code's server still does, logging only that the database's migrations diverge from its build, then fails on what it cannot read; only the check its own `t3 update` runs first refuses one (**Read** at `bc0f04d`: `apps/server/src/persistence/Migrations.ts:395-412`, `cloud/servicePreflight.ts`). Going back to a release therefore means going back to its databases too.

From 0.3.0 the desktop app can host a server of its own, on its own home. Its release changes outside any command: the app's updater, a package manager upgrading the deb, an AppImage swapped by hand. A snapshot taken by the updater would miss all but the first.

## Decision

**The installed release drives the update.** `j3-bots update [--version <version>] [--yes]` is run by the release the command points at, which can always start itself again. It works on the install it runs from: the folder whose `versions/` holds it and which holds the record of the command, `launcher`, wherever `install.sh` put it (`J3_INSTALL_DIR`, `$XDG_DATA_HOME/j3-bots` or `~/.local/share/j3-bots`). A checkout, or a release unpacked anywhere else, is refused. Data stays in the data directory, outside the install, as before.

**One transition, whoever hosts the server.** The snapshot, the switch, the wait for readiness, the rollback and the pruning are one core (`apps/server/src/transition/`) that knows nothing of an install layout or of systemd. A host gives it what only the host knows: how to stop, disable and start a release's server, what it sees of the server it started (its supervisor's view of the process, and the server's status reply), how to adopt a release once its server is ready, and how to remove the runtimes of other releases. `j3-bots update` gives the systemd service's steps, below. The desktop app gives its child process's, with its runtimes in `<userData>/server-runtime/<version>/`, and imports the core as `@j3-bots/server/transition`. The core takes `update.lock` and `server.lock` itself, so every guarantee here holds for both hosts.

**The home records what runs, and a new release starts through a transition.** `<home>/state/runtime.json`, mode 0600, names the release the home's data was last handed to, when, and after a rollback the release that failed, rolled back from. It is written whole under a temporary name, flushed, renamed into place, and its folder flushed, so a power cut leaves the old record or the new one. The core writes it three times in a transition: once the snapshot is whole and before the new release starts, it records the transition pending, from the release that ran on the snapshot's data to the new one, with the snapshot's folder; once the new release is ready (without a server to start, once the transition ends), that release, no longer pending; after a rollback, the old release, rolled back from the new one, the release that failed. A host that starts a server outside a transition records it once it is ready, keeping a rollback recorded for that release. Before a host starts release V on a home, `decideStart` answers from that record, V, the releases whose runtime the host keeps, and a rollback left unfinished:

- no record, or V recorded: start V as it is;
- V newer than the recorded U: a transition from U to V. So the snapshot is taken at the first start of a new release on a home, however the release arrived;
- a transition from U pending: a transition, for the release it was moving to, which carries it on, or for another release newer than U, which rolls the cut-off one back to U first (below); U itself is refused, since the data may be the newer release's already;
- V the release a rollback was made from: refused as rolled back, and the host starts the recorded release. It tries V again only when the person asks, and a release newer than V is a transition as usual;
- V older than U, with U's runtime kept: refused as a downgrade, and the host starts U. Only a rollback the core makes starts an older release, on the snapshot it put back;
- a record this release cannot read (a newer format, or a damaged file), a U newer than V that this computer does not have, or two versions that cannot be ordered, two builds of one version among them: refused, since nothing on this computer is known to read the home's data with V;
- a rollback that has not finished: only the release it ends on starts, through the core's rollback, which finishes it.

**A transition cut off after its snapshot is carried on, or rolled back, with that snapshot.** The next transition on the home reads the record first. When it names one pending, the home's data may already be the data of the release it was moving to, so no snapshot is taken of it, and the old release is the one the cut-off transition started from, whatever the host believed ran. A transition to the release the cut-off one was moving to carries it on: its snapshot is the one put back if that release fails. A transition to any other release first rolls the cut-off one back, as `--rollback` does (below): its snapshot put back, the old release started on it and recorded, rolled back from the release it was moving to. Only then does it move from the old release to its own, with a snapshot of the data put back, so no release ever starts on data another one migrated without having run on it. A transition to the old release itself is that rollback and nothing more. If the snapshot is gone from `backups/`, the transition is refused before it changes anything. Taking `from` from what ran, never from what a host expected, is also what an update that finds the unit on another release than the command does (below).

**A record that cannot be read is set aside only on the person's word.** A host refuses to start a release on it and says why; it never removes it by itself, since it may be a newer release's. The person can have it set aside (`setAsideRecord`): it is renamed to `runtime.json.unreadable-<time>` beside it and kept, the next start finds no record and starts the release as it is, and J3 Bots' database still refuses data a newer release migrated, naming what it does not know.

A record names its format, so a release that changes it incompatibly writes another, which an older release refuses; one that only adds fields stays readable. The CLI's service does not consult the record to decide what to start: its unit names the release it runs (below). Its update does read it, to carry a pending transition on, even to the release the unit already runs.

**The unit says what runs.** With the service installed, the release that runs is the one whose Node or server bundle the unit's `ExecStart=` names in `versions/`, not the one the command runs: an update or a rollback killed after a release's `service install` wrote the unit and before the command was pointed leaves the two apart. `update` and `--rollback` start from the unit's release, so an update to the release the unit already runs only points the command at it (`j3-bots update --version <that release>`), and `--rollback` finds the snapshot taken by the update to it. When the command runs another release than the unit, as after a rollback killed once it finished and before it pointed the command, `--rollback` refuses before it picks a snapshot, unless a rollback has not finished: it says so, with that fix, since the snapshot it would find is an older update's, not the one just rolled back. `j3-bots doctor` says when the command and the unit name different releases, with that fix.

**An update survives a hangup.** The update ignores `SIGHUP` while it runs, so an SSH connection that drops does not stop it midway. The releases it runs (`engine fetch`, `service install`) run in sessions of their own, which a hangup does not reach, and their output is relayed through the update, whose writes to a terminal that is gone are dropped. A power cut or `SIGKILL` still stops it; the rule above, and the marked rollback below, are the recovery.

**One update at a time, and no server while the databases are copied.** An update or a rollback holds an exclusive lock on `<home>/backups/update.lock` from start to end, and only then reads what runs and whether a rollback is unfinished; a second one, such as one started again after an SSH connection dropped, is refused at once and changes nothing. In the core the lock is a `TransitionLock`, which only holding the file lock makes and which lasts as long as its scope: a transition or a rollback runs under it, one at a time, and one asked for while another runs, or after the scope closed and the file lock was let go, is refused before any of its steps. While it copies the databases into a snapshot, and while it puts them back, it also holds the home's `server.lock`, the lock a running server holds, so no server, in the service or outside it, runs on the files then, and one that holds them fails the copy before it starts. Before it stops anything, an update that finds no service running tries that lock, so a server outside the service is refused while nothing has changed. `j3-bots uninstall` holds `update.lock` too, on a home a server took, so it is refused while an update or a rollback runs and removes nothing. Both locks are SQLite's, which the kernel releases when the process ends.

**`backups/` stays on the data directory's filesystem.** A restore moves the home's files into the snapshot's folder by renaming them, which cannot cross filesystems, so with `backups/` on another disk, as a link to an external drive on a Pi makes it, every restore would stop part way with the service disabled. Before it stops anything, an update and `--rollback` compare the device (`st_dev`) of `backups/`, through a link, with that of each folder of the home a restore moves files from, and refuse when they differ (`backupsElsewhere` in `snapshot.ts`). The core's snapshot step checks the same for every host, so an app, which has no check of its own before it stops the server, refuses there, before any snapshot is taken, and starts the release that ran again. When `backups/` is a link, the refusal gives the commands that put the folder it points to in its place; a rollback this stopped part way then finishes with `--rollback`, since its mark and copies are what it left, and nothing of the home had been moved yet.

**Preparing changes nothing the service uses.** The target is the latest stable release, from the releases page's `latest` (asked for JSON), or the one `--version` names. Free space is checked first: twice the files a snapshot copies plus 1 GB where the data directory is, and 512 MB where the install is. The core's snapshot step checks the first again, through its host (`freeSpace`), so the app, which checks nothing before it stops the server, refuses there, before any snapshot is taken, and starts the release that ran again; until there is room, each try does the same: at every start, or, for a release it rolled back from before, at each Try again. The release is fetched as `install.sh` fetches one (`apps/server/src/install/release.ts`): its archive for this platform, checked against the release's `SHA256SUMS`, unpacked into a `.staging-*` folder in `versions/`, run once, then renamed to `versions/<version>/`; a release already there is used as it is, a folder there that is not a release is refused and kept, and the install folder and `versions/` must be this user's and not writable by every account. `J3_RELEASE_BASE_URL` points it at a mirror, as it does `install.sh`. Then the new release's own `j3-bots engine fetch` installs its engine beside the running one. Last, if the service's server says bots have work running (`POST /running-work` on the admin socket, which, when none runs, holds new work until the service stops), the update asks, or needs `--yes`, since stopping the service stops that work.

**The switch is one uninterruptible sequence** (`apps/server/src/transition/switch.ts`), here as `j3-bots update` runs it:

1. Stop the service and clear its failed state.
2. Copy, holding the home's `server.lock`, into `<home>/backups/<time>-<from>-to-<to>/`: `config.json`, `j3.sqlite` with its `-wal` and `-shm`, and the engine's state its adapter names (`statev2.sqlite` with its `-wal` and `-shm`, and the engine's `settings.json`), each at its path relative to the home, flushed to the disk, then a `manifest.json`: when, both releases and both engine releases. A folder without a manifest is not a snapshot: it is a copy cut off, by a power cut or `SIGKILL`, which the next pruning removes. Folders are 0700 and files 0600. A copy that fails is removed whole. Then, still holding the lock, record the transition pending with that snapshot. A transition carrying one on skips this step and uses its snapshot.
3. Run the new release's own `j3-bots service install`, which writes the unit with its own paths, enables and starts it, and gives up after 60 seconds without an answer from the new server. Its output is shown only when it fails: the update says what runs.
4. Wait, five minutes at most, for the service's server to answer as the new version, from the unit's main process, with its engine `ready`. The waiter decodes only `version`, `pid` and the engine state's tag from the status reply, so it reads a newer release's reply, which only adds to it. An engine reported `incompatible`, or a unit that fails, ends the wait at once. Within it, the server gives each launch of its engine 90 seconds and launches it again after a failure.
5. Point the command at the new release (the host's adopt step): the record first, then the command, each written whole under a temporary name and renamed into place, the command in exactly the form `install.sh` writes (`launcherText`), so `uninstall` still recognizes it.
6. Record the new release in `state/runtime.json`.

The desktop app's steps differ only in 3 and 5: it starts the release's server as its own child process, and has no command to point. It runs the core in its main process, under Electron's own Node (24.22.1, whose `node:sqlite` takes the locks: **Verified** on Linux), as part of starting its server, and reads the home's record and acts on it under the home's `update.lock`, as `j3-bots update` does. Its probe waits for each status answer as long as a release may take to get ready, or until the server exits: the server reads its admin pipe only once it serves, and a request given up on closes the pipe for good (a release took about 20 s to serve on a Windows guest). Quitting the app waits for that start, so a transition ends, with its record and pruning, before the app does. The release it rolled back from is offered again only on the person's word, from the app's connection line (**Try again**).

**A new release that never became ready is rolled back by itself.** If step 1 or 2 fails, the old release's `service install` starts it again; the databases were not touched. If step 3 or 4 fails, the update rolls back to the snapshot, as `--rollback` does (below). A transition carrying one on rolls back to its snapshot even when step 1 fails, since the data may be the new release's. Once the old release is ready again after a rollback, it is recorded, rolled back from the new one, which a host reads as an update that failed and does not try again by itself. The new server answered on its own socket while the update waited for its engine, so it may have accepted a message; that message is in the databases the rollback moves aside, not in the ones it puts back. Once the new release is ready, nothing is rolled back: a failure to point the command is reported, with the service running the new release, and `j3-bots update --version <new>` points it. A failed update leaves `versions/<new>/`, the engine it fetched and its snapshot on disk; the next update that succeeds prunes them.

**A rollback is one marked state, from its first change until the old release runs** (`apps/server/src/transition/switch.ts`, and `restoreSnapshot` in `apps/server/src/install/snapshot.ts`). Before it stops anything, it writes a `restoring` mark in the snapshot's folder: the release it ends on, the snapshot's `from`, and how far it got. Then it stops and disables the service, so a reboot starts nothing; copies every file of the snapshot beside where it goes, under a temporary name, and flushes them (`copying`); moves every file the snapshot covers that is in the home into a new `replaced-<time>-<random>/` there, since a write-ahead log the new release left must not stay beside a database put back, renames the copies into place and flushes the folders (`swapping`); then the home holds the snapshot (`restored`). That folder is made, and flushed, before the home first changes, even with nothing to move. So a mark that cannot be read, as a failing disk may leave it, is taken for `copying` while the snapshot's folder holds no `replaced-*`: nothing was put back. With one, the stage is not known (`unread`), and the rollback carries it on from the start, copying everything again and moving what the home holds into another `replaced-*`. Each stage is written whole, under a temporary name renamed over the mark, and flushed. The old release's own `service install` then enables and starts it, the update waits for it the same way, records it, rolled back from the new one, and only then removes the mark. A record that cannot be written fails the rollback at that step with the mark kept, at `restored`, so the next `--rollback` only starts the old release and records it, without copying the snapshot again. While the mark is there, a cut anywhere, a power cut or `SIGKILL` included, leaves one state: `update` refuses, pruning keeps the snapshot, `doctor` gives `j3-bots update --rollback` as the fix, and a server, a `service install` or an `engine fetch` refuses the home before it writes anything there, whoever runs it, unless it is the release the rollback ends on and the stage is `restored`. `--rollback` carries on from the mark: from `copying` it copies again, from `swapping` it uses the copies already made, only moving aside what is not in place yet, and from `restored` it only starts the old release. Nothing is deleted: each pass moves what is in the home into a folder of its own. Free space is not checked again for the automatic rollback: the update's check reserved room for the snapshot and for the copies a restore makes. What is said while the mark is there names what the stage holds off, never the service's state, which a cut right after the mark leaves enabled and running: until `restored` no server starts on the home, and then only the release the rollback ends on. `doctor`'s Server, Service and Command checks say what they find; one that finds something wrong gives the Snapshot check's fix instead of its own.

**A rollback that has put nothing back may be given up, on the person's word.** A snapshot that cannot be put back, as when a file of it was lost to a failing disk, fails `copying` every time, and the mark keeps every server off the home. While the mark says `copying`, the home is as the rollback found it: the data of the release the snapshot was taken for, its `to`, which may have migrated it. So `j3-bots update --rollback --abandon`, under the update lock, after the same checks of the install's folders and a question (or `--yes`), records that release as the one the home's data is handed to, with nothing pending, removes the copies a cut left beside their place and then the mark, starts that release's own `service install`, waits for it as an update does, and points the command at it (`abandonRollback` in `transition.ts`). The snapshot stays. From `swapping` or `restored` it refuses: the home holds part or all of the snapshot, and only finishing the rollback makes it whole. So it does when the mark cannot be read and a `replaced-*` folder says a swap had begun. The release the snapshot was taken from is never started on that data. A cut while it runs leaves the mark, and it is run again, or the record already written and the mark gone, with the service stopped, which `doctor` reports as any stopped service.

**The unit is only ever written by a release's own `service install`.** There is no `current` link for the unit to start: the unit names one release's Node and bundle by their real paths, so it always names one release whole, and the switch never leaves it between two.

**`j3-bots update --rollback`** finishes a rollback that has not, if there is one, and otherwise puts back the newest snapshot taken by an update to the release that runs now: after an update from A to B that worked and one from B to C that failed and rolled itself back, B runs, and the snapshot from A to B is the one, not the newer one from B to C. `doctor` names that snapshot, or, while the command runs another release than the unit, says `--rollback` waits for it to be pointed. The release it was taken from must still be in `versions/`. Before anything changes, the install folder, `versions/`, that release's folder and the command's must be this user's and written by no other account, in folders no other account may change, as `install.sh` and the update check them ([decision 0015](0015-a-release-is-a-self-contained-archive.md)), and there must be room for the copies still to make, plus 1 GB: the snapshot's size, less copies a cut-off rollback left, and none once its copies are made. It says when the snapshot was taken and what is lost, asks (or takes `--yes`), then rolls back as above, points the command at the earlier release, and records it, rolled back from the later one. A failure to point the command comes after the mark is gone, and is reported with the fix `j3-bots update --version <earlier>`.

**Two of everything are kept.** After an update that succeeded: the two releases it moved between (in `versions/` for the CLI, `server-runtime/` for the app), the two newest snapshots, and the engine runtimes of those two releases, which `release.json` now names (`engine`). A snapshot is removed with its `replaced-*` folders, which the update's output says; one whose rollback has not finished is kept. A copy cut off before its manifest is removed too: a folder named as a snapshot that holds nothing a copy does not write, so no rollback's mark and no `replaced-*`, and whose `manifest.json` is missing or is not JSON at all, as a cut while it was written leaves it. One whose manifest is JSON but does not decode, as a newer release's may not, or cannot be read, stays, and so does one with anything else in it. Pruning runs under the update lock, which every copy holds, so it never meets one being made. Nothing else in `versions/`, `backups/` or the engine's runtime folder is removed.

**One install of an engine pin runs at a time.** `j3-bots update` right after `install.sh` fetches the new engine while the service may still be downloading its own first one. An install holds an exclusive lock on `<version>.lock` beside the pin's folder while it downloads into `<version>.partial` and unpacks into `<version>.staging`; another says that it waits for another install of the engine, so an update started during the service's first download does not sit silent, then waits for it, without blocking its process, as long as that one runs, and finds the pin installed and uses it (`packages/engine-t3/src/t3/Install.ts`). The lock is the same SQLite lock as `server.lock` and `update.lock`, one helper in `@j3-bots/processes`. A download cut off, by a power cut too, is resumed by the next install, and what an install cut off after publishing left is removed.

**A release refuses a database a newer one migrated, and an engine older than the one that ran.** On start, J3 Bots refuses a database that records a migration it does not know, naming it, as it already refused one with a gap (`apps/server/src/persistence/Migrations.ts`). The engine has no such check, so J3 Bots makes it: its database records the newest engine release that ran on the home's engine data (`engine_release`), and before the engine starts the server refuses to start one older than that, naming both and `j3-bots update --rollback` (`apps/server/src/engine/EngineRelease.ts`). Both refusals are refused starts, which the desktop app shows without starting again. Running an older release on newer data by hand fails with one of those messages, never silently, even when the older release knows every migration of J3 Bots' own database. A snapshot holds the record with the engine's data it describes, and does not record the migrations its databases hold: a restore always starts the release that ran on them, and that start is the check. A server started with `J3_ENGINE_BINARY`, an engine build under test, checks and records nothing.

**Without a service**, the update copies the files and points the command, refusing while any server holds the data directory; the operator starts the server. It records the release it installed, as a transition with a server does once that server is ready.

## Consequences

- A rollback loses what happened after the update in the databases: conversations, rooms, routines and their runs, settings, paired devices, and the engine's threads. Bots' files are not in a snapshot, so their memory and workspaces keep what was written since. Nothing the rollback replaced is deleted: it stays in the snapshot's `replaced-*` folder until that snapshot is pruned, with it.
- An update cut off by a power cut or `SIGKILL` can leave the command on another release than the unit. Nothing runs on the wrong data: the unit names one release whole, and `doctor` says what to run. A rollback cut off leaves its mark, which keeps every server off the home but the one it ends on until `--rollback` finishes it, or, while it has put nothing back, `--rollback --abandon` gives it up.
- A failing disk that loses both the mark and a file of the snapshot after a swap began leaves neither way: `--rollback` fails while it copies, and `--abandon` refuses, since what is back is not known. The snapshot's `replaced-*` folders hold what each swap moved out of the home, at its path there, for a person to put back by hand.
- A `<version>.lock` file stays beside each engine pin installed: removing a lock file another process waits on would let two hold it.
- A record that cannot be written once the new release is ready is reported, not rolled back: the transition stays pending, and the next one, `j3-bots update --version <new>` for the CLI or the next launch of the app, carries it on with its snapshot and records it.
- A host that cuts the core off after the switch, while it records or prunes, leaves the transition pending or more on disk, never a release half started: the switch itself is never interrupted.
- A snapshot is about the size of the two databases. The update's free-space check and keeping two of each bound what an update leaves on disk.
- The engine's `settings.json` names the provider endpoint's base URL; the providers' key is in the engine's secret store, which is not copied.
- The check for running work and the stop are not one step: work a bot starts in between is stopped with the service.
- The automatic rollback starts the old release as its `service install` writes it, with the `PATH` and data directory of the unit it replaces.
- The first release that has `update` is the first that can be updated this way; a release from before it is replaced with `j3-bots uninstall` and `install.sh`.

## Rejected

**A `current` link that the unit starts.** The unit would no longer record what it runs, a link swapped under a running service changes its code without a restart, and moving the link does nothing for the databases.

**Copying the whole data directory.** Bots' workspaces, attachments and the engine's runtime are large, and no migration changes them. The snapshot holds what an older release cannot read after a newer one ran, and the settings beside it.

**Copying the databases while the old server runs** (SQLite's online backup). J3 Bots' and the engine's databases must be copied as one consistent pair, and the old server stops for the switch anyway.

**Having the new release drive its own update.** If it cannot start, it cannot restore the release before it. The installed release knows how to start itself.
