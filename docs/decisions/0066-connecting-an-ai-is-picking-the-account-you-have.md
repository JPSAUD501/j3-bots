# 0066: Connecting an AI is picking the account you have

**Status:** Accepted.

## Context

A person who is not technical tried the first run on a Windows computer, and its connect step stopped them. The step listed "Claude Code" and "Codex", each with the engine's own account of it ("Claude Agent CLI (`claude`) was not found on PATH", "Check Settings → Providers → Codex → Binary path"), a red line about disk space, and a Create button that could not be pressed. Nothing on it was a question they could answer.

The step was built from the engine's side. It showed every provider, in the engine's states and words, and what each needed. What the person knows is something else: they pay for Claude, or for ChatGPT. Which harness signs that account in, where it is installed and what the engine calls it are J3 Bots' business.

Three more things made it worse. The same task looked different in each place it appeared: a list of providers with fixes in the first run, another in Settings, and a bare command in a conversation whose bot was waiting. A harness still to be downloaded held the first bot back, because the server gave a bot created without a model only a provider the engine had not yet ruled out. And the way forward depended on reading: a sign-in was a button among lines of text, with nothing that said what would happen after pressing it.

## Decision

**The operator connects an AI account, Claude or ChatGPT, and never a harness.** One model says where each account stands, one set of words says it, and every screen that connects an AI draws the same parts.

- **The question is which AI they have.** A screen with no account open asks it, with one large button each: Claude, by Anthropic, and ChatGPT, by OpenAI. The harnesses' names, Claude Code and Codex, appear as each choice's subtitle and under Details, nowhere else. An account picked has the screen to itself, and the other is one press away.
- **One state per account, the same on every client** (`AiAccountState` in `client-runtime`): connected, finishing, signing in, downloading, signed out, missing, being checked, a problem, or J3 Bots still starting. It is made from the engine's status, where the server finds the harnesses, and the client's own sign-ins, so a client decides nothing about a provider that another would decide differently.
- **One button per account.** What it does follows from the state and from where the account signs in: sign in, try again, look again, or download. It is the screen's big button while something is asked of the operator, and there is none while nothing is.
- **The sign-in is drawn, not described.** Three steps in a row: a page opens in the browser, the operator signs in, they come back. The one under way stands out; the ones done are checked. Nothing is copied or pasted, and the screen says so.
- **A sign-in asked for early is kept, and survives creating the bot.** Pressed while the account still downloads, is being checked or J3 Bots is still starting, the client says the browser opens when it is done, asks for the download when the account turns out to need one that nothing started, and starts the sign-in the moment the account can take it. The app remembers the request and the account picked for as long as it runs (`AiSession` in `client-runtime`), so the operator who creates the bot meanwhile, as the step invites them to, finds the same account waiting in the conversation, and the browser opens from there. The request is acted on once, by a screen that shows the account, and never while none does. **Cancel** beside it, turning to the other account, or a download that fails drops it.
- **Words for a person; the rest under Details.** Every sentence the operator meets names the account and says what happens or what to do. No sentence outside Details says harness, CLI, engine, PATH or binary. What the engine or a sign-in said is kept word for word under a folded "Details", with the controls only someone repairing a machine wants, as stopping a download. The reasons the server gives for a failed download are worded where they are made, in `wording/engine.ts`; the places those words would put a mechanic's language in front of the operator are worded here instead, with the original under Details: an engine that is out, which the step says as J3 Bots restarting or not able to run bots, a first download J3 Bots could not switch to, and one that did not match its checksum, which is said as a download that came out damaged.
- **An endpoint is never the suggested way out of an error.** It stays, for those who run a proxy in front of their subscriptions, as one quiet "Advanced" disclosure at the foot of the screen in the app on the server's own computer. A sign-in that cannot work on a machine says so plainly and keeps the reason, which names the endpoint, under Details.
- **A first bot is made while its AI downloads.** The server gives a bot created without a model one of a provider whose harness is not installed yet, last in its order, since the server installs that harness itself once a client asks, and the engine lists Claude Code's catalog before it is there. The bot's hello waits, and the bot moves to the account that connects, which is what puts an operator who signs in to ChatGPT on ChatGPT. A provider the engine found and cannot run is still never chosen.
- **The same parts wherever an AI is connected:** the first run's step, Settings → Providers, and a conversation whose bot waits for its AI. Settings lists both accounts as cards and adds each one's version and update.
- **Where an account signs in is the one thing that differs.** In the desktop app on the server's own computer, the app runs the sign-in. From a device that reaches that app's server, the screen sends the operator to the app. Reaching an installed server, it gives the command that signs that account in, which is now part of the contract (`signInCommands`) so the server's `doctor` and the clients name the same one.

## Costs

- **A bot can wait for a download nobody asked for.** An operator who creates the bot without picking an account gets a bot on Claude's catalog while nothing downloads Claude, until the server starts such downloads by itself. Its conversation asks which AI they have and offers the download, which is the path they skipped.
- **A bot can exist that nothing will ever run.** A server that cannot install a harness for its machine (a system J3 Bots downloads no build for) now makes the first bot on Claude's catalog all the same, where it used to refuse. Its conversation says what it waits for, with the maker's page and Look again, which is the same path the refusal pointed to; but the bot is there, saying nothing, until the operator installs the harness or connects the other account.
- **The server cannot put a bot on the account the operator picked before that account is connected.** Codex lists no model until it is (**Verified**, [Engine: models](../architecture/engine.md)), so there is no model id to give the bot. The bot lands on a model the server lists and moves once the account connects. A bot whose account never connects stays where it landed.
- **Creating still waits while J3 Bots starts.** Before the engine runs, the server lists no provider and no model, and a bot's model is a required part of it in the contract. Letting a bot exist with none would change that contract and every reader of it. The wait is the engine's first start, and the step says so in one line.
- **An older server refuses what a newer client offers.** Against a server from before this decision, a client lets the operator press Create while a harness is still to be installed, and the server answers that it has no model. The step returns and says so. Protocol 11 is unchanged.
- **Details hides what an expert reads first.** The engine's words are one press further than they were, in Settings too.
- **No account's mark is drawn.** Their makers' marks are theirs, so the choice is two names. That is plainer than a row of logos, and it is what the brand rules of this repository allow.

## Rejected

- **Keeping one list of providers, with friendlier text.** It is the same screen: it still asks the person to read two entries and work out which is theirs and which line matters.
- **Signing in to both by default, or picking for them.** J3 Bots cannot know which account a person pays for, and a sign-in page for a service they do not use is the wrong turn the step exists to prevent.
- **Keeping the queued sign-in on the screen that took it.** The step invites the operator to create the bot while the account downloads, right under the line that says the browser will open. A request that died with the step broke that promise without a word, and left the conversation asking again which AI they have.
- **Starting the queued sign-in wherever the operator is.** A browser opening while they read another bot's conversation is a surprise. It opens only from a screen that shows the account and says it is coming.
- **Creating the bot on the client and sending it once the server can take it.** It would let Create be pressed while J3 Bots starts, but a bot that exists only on one device is not the bot the other devices see, and a failed start would have to be explained from a screen with no way back.
- **Letting the phone start a sign-in.** The sign-in page returns to the harness on the server's own machine, so a browser on a phone cannot finish it. Codex's code entered on any device could, and is left for when the server's sign-in for clients takes it.
