# Clients

J3 Bots has three clients: a web app, a desktop app and a mobile app. All three show the same conversations and none of them runs a bot. A bot keeps working with every client closed.

## What clients share

**`packages/contracts`** defines every request, subscription, entity and error that crosses the wire. Clients and the server decode with the same schemas.

**`packages/client-runtime`** holds everything a client does that is not drawing:

- the connection: pairing, authentication, reconnect with backoff, resuming the subscriptions that resume and re-reading the ones that start with a snapshot; no socket while the app is in the background, on a platform that says when it is (the `Lifecycle` port: a phone; a browser tab and the desktop app never are, since no push reaches them), and a new one when it returns;
- state: the roster, the open conversation, pending cards, routines and each one's recent runs, read again as the routine changes or is deleted, engine status, and the turns bots spent recently, for the usage view: the contract does not push those, so they are read when the view opens and on every reconnect while it stays open;
- presence: reporting what the operator has in view on every socket, and receiving the server's notifications;
- commands: sending a message, answering a card, stopping a bot or a room's work, each with its own idempotency key and optimistic entry;
- drafts and unsent messages;
- what opening a notification does, the same for a click in the browser and a tap on a push (`notificationOpening`, `pushOpening`): the conversation or room it is about, only while the client follows the pairing that received it (a push names it as the `deviceId` of its data, `PushData` in the contract) and the roster lists what it is about, hidden bots included; a tap before the roster loaded waits for it; anything else, data that does not decode included, opens nothing;
- what sharing from another app puts in a draft (`sharedDraft`): the shared text, with its URL on a line of its own unless the text holds it, after what the draft already holds, whose mentions stay where they are; the text whole, whatever its length, so Send says when it is too long as for typed text; and the shared files admitted against those the draft holds by the rule `attach` applies, each to upload or left out with the reason the composer gives. Nothing is sent until the operator presses Send.

**`packages/design-tokens`** holds colors, the bot palette (`botPalette.ts`), the avatar silhouettes (their names alone in `@j3-bots/design-tokens/names`, which the contract takes the avatar choices it accepts from, with the cast new bots take their avatars from), type sizes, spacing, radii, motion timings and layout sizes as data, so the web stylesheet and the mobile theme are generated from one source. One script writes both: `@j3-bots/design-tokens/web.css` for Tailwind on the web and `@j3-bots/design-tokens/uniwind.css` for Uniwind on mobile. Both name their utilities from the same tokens (`bg-background`, `text-sm`, `rounded-bubble`, `tablet:`), except fonts, which the mobile app sets itself. On mobile the colors are converted to 8-bit sRGB, so a color outside sRGB renders clipped there. A test fails when either file is stale. How an avatar's face is laid out at a size (`avatarFrame`: the eye, the antenna, the light and the signal, with the small-size proportions) is data there too, which each client draws with its own renderer (SVG on the web and on Android); its rasterizer, imported from `@j3-bots/design-tokens/raster` so a client that only draws SVG never loads the PNG encoder, draws avatars into PNG images with no image library, in Node or a browser. A notification's icon is drawn with it (`renderStillAvatar` for a bot, `renderStillRoomAvatar` for a room), and so are the tray's (`renderTrayIcon`) and every platform's app icon (`renderAppIcon`, [App icons](../design/design-language.md#app-icons)), each a Pip drawn by the same `drawAvatar`: the web's as the web client builds, the desktop window's as the app starts, and the files the native builds read, which the same script writes to `@j3-bots/design-tokens/icons/*` with their colors in `colors.json`, under the same staleness test. The avatar's model stays in `client-runtime` (`presentation/avatar.ts`): which state a bot shows, each state's pose and still form, the seeded life each bot has, and the state a notification gives its bot (`notificationState`). It is pure, and the functions a frame runs are worklets, so Android runs them on the UI thread.

**`packages/i18n`** is the translation catalog: every interface sentence in each language the contract lists (English and Brazilian Portuguese), where a sentence missing from a language, or a placeholder dropped from one, fails the typecheck. It also words notifications, so the server can write a push as the clients show one.

`client-runtime` imports nothing from a platform. Each app provides it, as services: the server's origin; a credential store (IndexedDB in the browser, the keychain or keystore on mobile, IndexedDB holding the token encrypted with the system's key on desktop); a small local store that keeps drafts and unsent messages across restarts; locks shared by the app's windows (the Web Locks API in a browser); a file uploader, which reports progress where the platform can; a source of network status; the device's time zone (`Intl` in a browser and the desktop app, the system's calendar on a phone), which the runtime gives the server on every socket; an HTTP client and a WebSocket constructor (`fetch` and the global `WebSocket`); and a secure random source. The runtime's HTTP client refuses every redirect: it asks `fetch` for `redirect: "error"`, so an answer that redirects fails the request and nothing is sent where it points. The server never redirects its own routes, and following a redirect from something in between would send a pairing code or a device token to another address, plain HTTP included. React Native's own `fetch` ignores that option and follows every redirect, so the mobile app gives the runtime `expo/fetch`, which honors it on Android and iOS (**Read** in Expo 58.0.23, `expo/src/winter/fetch` and its native modules). File uploads go through the platform's uploader. A browser's is `XMLHttpRequest`, for its progress, which cannot refuse a redirect, so the runtime takes an answer from another address as not the server's. The phone's is `expo/fetch` with `redirect: "error"`, like its other requests, and reports no progress: React Native's `XMLHttpRequest` has no way to refuse a redirect, and iOS's handler follows every one (**Read** in React Native 0.88.1, `Libraries/Network/XMLHttpRequest.js` and `Libraries/Network/RCTHTTPRequestHandler.mm`), and neither does Expo's upload task, whose options name none and whose Android client is React Native's OkHttp builder (**Read** in `expo-file-system` 58.0.14, `src/NetworkTasks.types.ts` and `FileSystemUploadTask.kt`). A file the phone uploads shows as uploading, without a percentage. The runtime exposes state as values a UI reads synchronously and watches with a listener, so any renderer can use it; React hooks over them live in `@j3-bots/client-runtime/react`.

The rule from T3 Code that J3 Bots adopts as is: **the UI stays dumb.** A component receives state and emits intent. If two clients need the same decision, the decision lives in `client-runtime`. The decisions a client makes before it draws (roster order and search, timeline grouping, message text, mentions, form edits, usage grouping, how a moment is formatted, how a cron expression reads) live in `@j3-bots/client-runtime/presentation`, free of any UI library. The sentences built from them that every client says the same way (a roster row's line, a notice, a delivery line, why a file cannot go, a time in words, who a room message goes to) are worded in `@j3-bots/client-runtime/wording`, from the catalog's sentences; the rest (schedules in words, the usage view) are still worded in the web app.

## Web

The reference client. It is served by the J3 Bots server itself, so pointing a browser at the server is enough to use J3 Bots.

- React with the React Compiler, TanStack Router, Tailwind CSS v4 with tokens as CSS variables.
- Component primitives on Base UI, in a local `components/ui` layer whose components own their look: callers pick a variant, they do not restyle.
- A virtualized conversation list that keeps the scroll position stable while messages stream in.
- Installable as a PWA, which gives phone users a working client before the native app exists.
- Browser notifications, through the service worker where one is active and from the page otherwise. The browser's permission is asked for only when the operator presses "Allow notifications in this browser" in Settings, never on load. A notification carries the pairing that received it. A click focuses a window of the app, the focused one first, or opens one at the app's root when none is open, and that window opens the conversation or room the notification is about only if it follows that pairing and the roster lists it, hidden bots included; a click that arrives before the roster loaded waits for it. Settings, the details and any dialog over it close, a save under way carries on, and the profile in Settings keeps what the operator typed. New bot holding a name, and the bot editor or the memory viewer holding an edit not saved yet, stay open, with the conversation opened under them and focus kept in them, so the click never throws typing away or sends it to the conversation, and closing the dialog lands on what the notification was about; one holding nothing closes like any dialog. When a pairing a window followed ends, here or in another tab, the window closes every notification that pairing received, and only those, so signing out or a revocation takes the bots' names and words off the screen while a newer pairing keeps what it showed; a notification whose pairing ends while the browser is still showing it is closed once shown. The first pairing a window knows also closes every notification another pairing received, so a window closed before it finished closing them leaves them only until the app next starts. A notification shows only while the browser's permission, read again as it arrives, allows it, and Settings reads the permission again when the operator comes back to the page, since not every browser reports a change made in its site settings. Every window shows the server's notifications, tagged by entry, so the browser keeps one per entry. Its icon is the still avatar of what it is about, a 192 px PNG in the theme the system is in as it shows, drawn by the rasterizer, which is not part of the app's start: a paired page with notifications allowed fetches it once it has started, so a page left open across a server upgrade already holds it; the app's icon stands in when there is no avatar to draw or the fetch failed. Chrome shows the icon in an 80 px square (**Read**: `kNotificationIconSize` in Chromium's `ui/message_center/public/cpp/message_center_constants.h`), and the systems that show it themselves give it about as much or less (**Assumed**), never as little as the 28 px below which an avatar draws its mark larger, so the image is drawn with the proportions of its own size. Drawing one takes about 20 ms in Chromium, once per notification, so nothing is cached. Browsers offer notifications only in a secure context, so a page served over plain HTTP on the local network gets none, and Settings says so; Safari on iPhone and iPad offers them only to the app added to the Home Screen, and Settings says that too. Some mobile browsers (Android's) show a notification only through a service worker (**Assumed**: not yet observed on a device).

## Desktop

An Electron shell around the web client ([decision 0012](../decisions/0012-desktop-reaches-the-server-directly.md)).

- **Its own build of the web client.** The window loads the built client from a privileged custom scheme, `j3bots://app` (`j3bots-dev://app` in development; both names are placeholders until the app's name and ids are settled), never from a dev server, a `file://` path or the server. The scheme serves only that build's files: a path outside it, or one of the server's routes, is refused, and a route without a file gets `index.html` for the client's own routing. The page is a secure context, so Web Locks, WebCrypto and notifications work as on an HTTPS origin, whatever the server is served over.
- **A server the operator names.** The first screen asks for the server's address before pairing. The main process checks it (an answer from `/api/server` that decodes as a J3 Bots server; a redirect is refused, not followed) and keeps it in the app's settings. An address without a scheme is HTTP for a loopback or private IP literal or `localhost`, and HTTPS otherwise; plain HTTP to any other host is refused, and a saved server is held to the same rule when the app starts, or dropped. The rule is `parseServerAddress` in `client-runtime`, which the mobile app uses too. Bundling a server and an engine inside the desktop app, for people who have no always-on machine, is a later step.
- **Changing server.** The pairing screen and Settings show the server with a way to change it, and so do the screens before the first roster (connecting, no bots yet), where a server that moved leaves the app, and the screen for a server of another protocol version, which tells the operator to update the app or the server so they match: the app carries its own page, so reloading only helps once one of them is updated. Under that screen, and under the pairing form when pairing fails for the same reason, the app shows its update whenever it checks for one, so an app installed older than its server reaches a newer version without opening Settings. Changing server forgets this device's pairing here: the page's IndexedDB (credential, drafts, unsent messages) is emptied, its preferences stay, and the app opens its first page, the server address screen. The device stays listed on the old server until it is removed from another device. A device token never reaches another server by construction: the credential is stored with the origin of the server that issued it and is absent for any other, the app empties that storage again right before it keeps a new server, and it keeps one only once it is written to its settings, one choice at a time.
- **The server at its own origin.** The custom scheme serves the app's own files and forwards nothing. The page calls the server with ordinary HTTP (`fetch`), `XMLHttpRequest` for uploads and WebSockets exactly as a browser does, and the server answers CORS for the app's origins.
- **A narrow bridge.** The page reaches the main process only through a preload script that exposes the current server, connecting to a server and forgetting it, sealing and opening the device token, the network status and the system's wake from sleep, restarting the app, showing a notification and closing a pairing's notifications, the clicks on them, the links to the app the operator follows, and, for updates, the update's status and its changes, a check, the restart into an update and a report of whether a save is under way, and, for the menus and the tray, the page's language, what needs the operator, the commands the menus and the global shortcut give the page, and the global shortcut's status and a change to it. Both sides decode every message with the schemas in `packages/desktop-bridge`, and the main process acts only on calls from the app's own top frame.
- **The device credential.** It is kept in the page's IndexedDB, in the same database as the drafts and the outbox, so a write's pairing check reads it in the same transaction, as in a browser. The device id and the issuing server's origin are stored in the clear for that check; the token only as the main process sealed it with Electron's `safeStorage` (the Keychain on macOS, DPAPI on Windows, a secret service on Linux), in a payload of its own that is read back only if it decodes, with how it was sealed. The sealed token is held to base64's canonical form, never empty, by the page as it reads the record and by the main process as it is asked to open one: a lenient decoder reads a value such as `A` as no bytes, which the system opens without an error. A stored value that is not a record of this server (no record, one of another server, one whose device id or server is not readable) reads as not paired. A record of this server whose sealed token is missing or not in that form is damaged storage, never a missing pairing. Otherwise opening it ends one of three ways. It opens. It decrypts to something the app did not seal (a damaged ciphertext, another profile's): that reads as not paired, like a record of another server, and the app shows the pairing screen. Or it is not opened: the system's encryption is not available, the system refuses (as while a keyring is locked, or for a key it no longer has), or the main process gives no answer within 60 seconds, long enough for the system to ask the operator to unlock a keyring, and for Chromium to give up on one that does not answer (**Verified** on Linux, Electron 44.10.1, under `xvfb-run` on a desktop session whose GNOME Keyring was locked: the first seal took 24 s before Chromium fell back to its built-in key). Of a record of this server, only a payload the system opened that is not the app's reads as not paired; a damaged record, or one not opened, is not taken for a missing pairing, which would lead the operator to pair again and leave the old pairing's drafts and unsent messages to be deleted. The app says it cannot read this device's sign-in, keeps the pairing and what is kept for it, and offers to restart the app or to change server. Trying again in the same process would not help: Chromium sets up the system's encryption once per process and keeps it (**Read** in Chromium 152.0.7977.169, the one Electron 44.10.1 ships, `components/os_crypt/async/browser/os_crypt_async.cc`), so a keyring unlocked later is seen only by a new process. For the same reason the page asks the main process to open a stored value once for as long as it stays the stored value, and every later read shares that answer: the client's start reads the credential more than once, and waits for the main process once, 60 seconds at most. The restart quits as closing the window does, so its place is saved, and keeps IndexedDB (**Verified** on Linux, Electron 44.10.1, under `xvfb-run`: the app exits with 0, its window's place is in its settings, and a new instance starts with the same arguments). An AppImage restarts as it does into an update (see Updates below), because Electron's relaunch does not restart one. Signing out deletes the stored record if its device id, read in the clear, is still the pairing being signed out, in the transaction that deletes it; it opens nothing, so it works with a keyring locked since. **Verified** on Linux, Electron 44.10.1, under `xvfb-run` with no unlocked keyring (the smoke): pairing survives a restart, the stored record holds only the sealed token, the sealed form is found in the profile's files and the token in none of them, a record the system refuses (not sealed by it) shows the screen that says the sign-in cannot be read, and one with a byte changed in the first block of its ciphertext shows the pairing screen.
- **Linux with no keyring.** The app seals and opens only while `safeStorage.isAsyncEncryptionAvailable()` says it can; where it cannot, a save fails rather than store the token as it is. A save that fails as the device pairs comes after the server spent the code and listed the device, so the pairing form says to unlock the system's keychain or keyring, offers to restart the app, and asks for a new code. On Linux with no secret service the app can use, `safeStorage` still seals, with a key built into Chromium, which only obscures the token; what it seals that way begins with Chromium's version `v10`. The app counts a token as `encrypted` on Linux only when it begins with a keyring's version, `v11` (the Secret Service: GNOME Keyring, KWallet) or `v12` (the Secret Portal), and as `unencrypted` otherwise, `v10` and any version it does not know included, so the notice errs on the side of showing (**Read** in Chromium 152.0.7977.169, `components/os_crypt/async/browser/`: `posix_key_provider.cc`, `freedesktop_secret_key_provider.cc`, `secret_portal_key_provider.h`). The app pairs anyway rather than refuse, and Settings → This device says that the sign-in is stored without encryption, as long as the record on disk says so, and that pairing the device again once a keychain or keyring is unlocked stores it encrypted. The app never seals a stored token again: IndexedDB's LevelDB files can keep the earlier, obscured copy of the same token in their log and tables after the record is replaced, so a token once stored obscured stays readable from the profile until it stops working. Only a new pairing, which issues a new token, ends that, and only then does the notice go. **Verified** on Ubuntu with Electron 44.10.1, with no unlocked keyring, whether Electron picks `basic_text` or `gnome_libsecret`: `isAsyncEncryptionAvailable()` is true while `isEncryptionAvailable()` is false, so the first cannot tell how a token is kept; what `encryptStringAsync` seals begins with `v10`; `decryptStringAsync` opens it; a ciphertext without Chromium's prefix rejects; the notice shows (the smoke). **Assumed**: with an unlocked keyring, `safeStorage` seals with the keyring's key under another version; that macOS and Windows always encrypt (not measured).
- **Network status** comes from the main process (`net.isOnline`), asked again on each of the page's `online` and `offline` events, and is sent to the page as the system wakes from sleep (`powerMonitor` `resume`), so the client tries the server at once instead of when its backoff ends.
- **Locked down as T3 Code's shell is** (**Read** at `db51b67`, `apps/desktop/src/window/DesktopWindow.ts`): context isolation, the renderer sandbox, no Node integration, no `<webview>`. The window never navigates away from the app; an `http:`, `https:` or `mailto:` link opens in the system's handler, anything else nowhere. A Content Security Policy allows scripts from the app only (its inline scripts by hash) and connections only to the app and the named server. Only notifications and clipboard writes are granted. One instance runs per profile; a second launch brings the first window forward, or focuses it as it first shows when the app is still starting, and hands over the link it was started with, if any. The window's size, place and maximized state are kept and restored onto the display it overlaps most, moved and shrunk to that display's work area so its title bar is always in reach.
- **Files.** An upload goes as in a browser: `XMLHttpRequest` from the page to the server's attachments route, with the device token, reporting progress as the body goes; the composer removing a file aborts it. Nothing of it passes through the main process. The Content Security Policy's `connect-src` holds it, as every request of the page, to the named server (a redirect included, **Assumed** from the CSP specification, which checks each one), and the client takes an answer only from the server's attachments route. **Verified** on Linux, Electron 44.10.1, under `xvfb-run`, with the page on `j3bots-dev://app` and the server's testing layer on a plain-HTTP loopback origin, upload throttled to 4 MiB/s with the DevTools protocol: the server answered the preflight from `Origin: j3bots-dev://app` with 204; a 25 MiB file, the largest a message carries, showed its progress rise from 0 to 100 % in the composer over about 7 s and arrived whole (26,214,400 bytes, identical); a second one, removed at 25 %, was cancelled (`net::ERR_ABORTED`) and never answered. An attachment the operator opens is saved, not shown in a window: the app opens no window but its own. Electron's default download handling asks where to save it (**Assumed**).
- **Notifications are the system's own.** The page decides what to show exactly as the web does (the runtime's pairing check, the permission and what is in view), and hands each notification to the main process instead of showing it, so that a click can restore a minimized window and bring it forward: the entry it is about, the title and body worded by `packages/i18n`, the still avatar as a 192 px PNG in the theme the system is in, the conversation or room it is about, and the pairing that received it. The main process decodes it (an icon must begin with PNG's signature and stay under 1 MiB), takes it only from the app's top frame, and shows it with Electron's `Notification`, one per entry, a newer one replacing it; an icon that does not decode leaves the app's. A click closes it, restores, shows and focuses the window, and hands the page what it was about and its pairing, and the page opens it under the web's rules (`notificationOpening`), only while it still follows that pairing and the roster lists what it is about. A notification has no actions: only a click opens it, since approving from one would grant without the exact command in view, which the approval card exists to show. When a pairing ends, the page tells the main process, which closes everything that pairing received; a notification sent just before is closed too, since the two requests travel in order, and the page sends none after it. Every notification also closes when another page loads in the window (a reload, or the server forgotten; a navigation the window refuses changes nothing) and when the app quits, since only that page knows when its pairing ends and a click could open nothing once it is gone; with no service worker, none outlives the app. **Verified** on Linux, Electron 44.10.1, with the development build under a headless GNOME Shell 50.1 through Xwayland, against a server on loopback with the scripted agent: a bot's message with its conversation on screen in the focused window showed nothing; with the window minimized, another window focused and another conversation open in the app, GNOME showed a banner with the bot's name and its still avatar; activating it, as a click does, restored and focused the window on that bot's conversation; and a notification still showing closed as the device signed out. Under the test driver the page kept reporting focus and visibility after the window was minimized, so the conversation was out of view through the other conversation being open, not through the window's state alone. **Assumed**: the same on macOS and Windows, and on a native Wayland session (Ubuntu's default GNOME), where Electron may run without Xwayland and GNOME can refuse focus to a window that asks without an activation token, showing that the app is ready instead; none of these run yet.
- **Links to the app.** `j3bots://bot/<id>` opens that bot's conversation, `j3bots://room/<id>` that room, and `j3bots://pair?server=<origin>&code=<code>` fills in pairing. A development build takes `j3bots-dev:` links instead, so the two never take each other's. The main process decodes a link with `AppLinkUrl` in `packages/desktop-bridge`: an id is one percent-encoded path segment (a final `/` allowed), a server is an `http:` or `https:` origin, and a code is read as a typed one is (`normalizePairingCode`). Anything else opens nothing: another host, a path beyond the id, a query on a bot or room link, a fragment, a missing, repeated or unknown parameter. A link comes from the arguments a launch is given, is handed over by a second launch on Linux and Windows (`second-instance`), or comes from the system on macOS (`open-url`). The latest one waits until the page listens; then the window is restored, shown and focused, and the page is given it. A link to a conversation or a room opens it as a notification click does, once the roster has loaded: one this server does not have leaves the screen as it is and says so, and one that arrives before the device is paired waits on the pairing screen, which says so, and opens once it is paired. Before a server is named, the server address screen says to connect and pair first, and such a link is not kept. A restart is given the app's arguments without its link, so it opens nothing by itself. **Verified** on Linux, Electron 44.10.1, under `xvfb-run` (the smoke): launched with a pairing link before any server was named, the server address screen showed the link's server and, once continued, the pairing screen its code; the code still paired when Pair was pressed, so nothing had spent it. A second launch with a link to the bot exited, and the running app opened that bot's conversation; one with a link to a bot the server does not have left the conversation on screen and said so.
  - **A pairing link only fills in; it never pairs.** Before a server is named, the server address screen starts with the link's server in its field and says where it came from, for the operator to check and continue. Once that server is kept, the page that loads next starts the pairing screen with the link's code, and the operator still presses Pair. With a server named, a link for that server puts its code in the pairing screen while the device is not paired, and a device already paired keeps its pairing and is told so. A link for another server is refused, saying so: changing server, which forgets this device's pairing, stays the operator's act.
  - **Registration.** The app names itself the handler of its scheme each time it starts. On macOS and Windows it calls Electron's `setAsDefaultProtocolClient`. The packaged macOS app also declares the scheme in its `Info.plist`, and the Linux packages in their desktop entries; the NSIS installer registers nothing (electron-builder's `protocols`, **Read** in app-builder-lib 26.16.1, `out/electron/electronMac.js`, `out/targets/LinuxTargetHelper.js:266` and `templates/nsis`). On Linux the deb registers nothing more than its entry, so removing the package leaves nothing behind. An AppImage, as T3 Code handles it (**Read** at `c6ca01b3`, `apps/desktop/src/app/DesktopLinuxUrlHandler.ts`), has no installed entry for Electron's call to name, and its executable lies in a mount that goes as it exits. So an AppImage, and a development build, writes a hidden desktop entry of its own, `j3bots-links.desktop` (`j3bots-dev-links.desktop` in development), under `$XDG_DATA_HOME/applications`. It starts the AppImage file itself, or in development Electron with the app's folder, and `--no-sandbox` when this run has it; a word of its `Exec` line is quoted only when it must be, since `xdg-open` with no desktop environment it knows reads the words as written. The app then refreshes the entries' cache with `update-desktop-database` and names the entry the default with `xdg-mime`. A step that fails is logged, and the app runs as before. An AppImage that is moved or deleted leaves its entry where it was until the app starts again. **Verified** on Ubuntu 26.04 with its xdg-utils, Electron 44.10.1, under `xvfb-run` with a D-Bus session and no desktop session, the handler registered by the development build in a temporary `XDG_DATA_HOME` and `XDG_CONFIG_HOME`: with the app running and paired, `xdg-open j3bots-dev://bot/<id>` opened that bot's conversation in it, both through `gio` (`XDG_CURRENT_DESKTOP=GNOME`) and through `xdg-open`'s own reading of the entry (none set). That second path does not unquote: a quoted `"--no-sandbox"` reaches Electron with its quotes, and Electron aborts for want of a sandbox. A program path with a space must be quoted, so that path cannot start one: the deb's own entry, whose install folder has a space, is such a case. **Assumed**: a full desktop session (GNOME, KDE), the packaged AppImage and deb, macOS and Windows; none run yet.
- **Light and dark.** The page keeps the operator's appearance and applies it before it paints, as in a browser, and reports it through the bridge. The main process keeps the last one reported in the app's settings and, as the app starts and before the window opens, sets Electron's `nativeTheme.themeSource` from it, which the title bar and the app's menus follow. The window's background is the page's canvas in the theme the window is in, and follows the theme as it changes, so what shows before the page paints is that canvas. What the system draws for the app keeps the system's theme: the main process reads it apart from `themeSource` (on Windows `shouldUseDarkColorsForSystemIntegratedUI`, on macOS the user's `AppleInterfaceStyle` default, on Linux what `nativeTheme` last said while it followed the system), draws the tray in it, and answers it to the page for a notification's icon. **Verified** on Linux (Ubuntu 26.04, x64), the development build under Xvfb with GTK's Adwaita and Adwaita dark: with each of the three choices kept, the window's background was the kept theme's canvas from its first frame, the page painted in that theme, and the system's theme read apart stayed the system's. A choice changed while the window ran turned its background to the new canvas at once. A change of the system's theme while it runs, and what a resize or a reload shows, were not seen (**Assumed**: Xvfb's GTK theme cannot change under a running app). There `themeSource` does not reach the page's `prefers-color-scheme`, which follows the system's theme alone, so the page relies on its own choice. - **Updates.** electron-updater 6.8.9 checks the latest published release at launch and every six hours ([Security: desktop updates](security.md#desktop-updates)). Settings → This device shows the app's version and where its update stands. How a build updates depends on what it can replace as the operator's user:
  - **An AppImage and a Windows install update themselves.** They download a newer version in the background, check its SHA-512 against the release's feed, and offer "Restart to update" once it is downloaded. The app never restarts by itself, nor installs as it quits, and a restart asked for while a save is under way waits for it to end: a setting, a bot's profile or memory, an action, or a draft that is sending, uploading, or changed here and not yet kept on the device, a file that just finished uploading included. An AppImage is replaced in place by electron-updater, then started again by `restartApp` (`apps/desktop/src/restart.ts`), which also serves the plain restart: a detached Bash closes the descriptors it inherited, waits for the old process to exit and starts the AppImage, so the old runtime and its mount go. It starts the file electron-updater installed to: when the operator renamed the AppImage with a version in its name, electron-updater deletes that file and installs the new version under the release's file name, `J3-Bots-x86_64.AppImage` (**Read** in electron-updater 6.8.9, `AppImageUpdater.js:72-115`). The app counts itself an AppImage only when its own executable lies inside the AppImage's mount (`APPDIR`), not because it inherited `APPIMAGE` from a process an AppImage started. An install that fails, as when the AppImage's directory is not writable, leaves the app running on its version and says the update could not be installed, apart from a check that failed; the next check tries again.
  - **A deb and a Mac build only say a newer version is out**, with a link to its release, and the operator installs it as they installed the first. A deb would need root to install, and the app never asks for it; Squirrel.Mac installs only a signed app, and builds are unsigned for now. Neither downloads anything (**Assumed** for a deb and on macOS: not yet run).
  - **A development build** checks only against a `dev-app-update.yml` of its own.

  Which events lead where is a pure state model, `apps/desktop/src/updates.ts`. **Verified** on Linux (Ubuntu 26.04, x64), with AppImages built on Linux by `electron-builder --publish never` against a feed on loopback and driven under Xvfb through DevTools:
  - The plain restart: an AppImage at 0.0.1-test exited and started again from a new mount, and the old mount was gone.
  - Into an update, renamed: an AppImage at 0.0.1-test, renamed `J3 Bots 0.0.1.AppImage` and served 0.0.2-test, downloaded it, and on "Restart to update" exited. Its file was gone, `J3-Bots-x86_64.AppImage` beside it had 0.0.2-test's SHA-512 and was the one running, and the old mount was gone.
  - A failed install: the same in a directory it could not write to. electron-updater failed with `EACCES` removing the old file, the app kept running at 0.0.1-test and reported the install as failed, and the file was untouched.

## Mobile

An Expo app for iOS and Android, in `apps/mobile`, on the Expo SDK and React Native versions T3 Code's mobile app runs (**Read** at `c1464d67`, `apps/mobile/package.json`). The native projects are generated by `expo prebuild` and never committed. `APP_VARIANT` picks one of three variants, development, preview and production, each with its own name, link scheme (`j3bots-dev`, `j3bots-preview`, `j3bots`) and app id (`dev.j3bots.mobile.dev`, `dev.j3bots.mobile.preview`, `dev.j3bots.mobile`), so they install side by side. Production is the one each release publishes, as a signed APK, which fixes its id ([decision 0017](../decisions/0017-the-android-app-is-a-signed-apk-on-the-release.md)). `eas.json` names the same three builds and holds no account.

- **A server the operator names, and pairing.** The first screen asks for the server's address, the pairing code and a name for the phone, prefilled with the device's own. Its scanner reads the QR code a paired device or `j3-bots pair` shows with `expo-camera`, decodes it as a `PairingLink` and fills in the address and the code; it never pairs by itself. The camera is asked for once, as the scanner opens; refused, the scanner offers to ask again, or the phone's settings once the system no longer lets the app ask, as Android 11 and later do after a second refusal (**Read**: Android's permissions documentation). The permission is read again whenever the app comes back to the foreground, so a camera allowed in the phone's settings opens on return. **Verified** on the Pixel 8 emulator (Android 16): the system asks as the scanner opens; refused once, "Allow the camera" asks again; refused twice, "Open the phone's settings" opens the app's page there; allowed there, the camera shows on return. On Android, `false` for a permission in any one config plugin removes it for the whole app, so every plugin that names the camera or the microphone gets the same sentence for it: `expo-image-picker` and `expo-camera` name the scanner's camera, and both of them and `expo-speech-recognition` name dictation's microphone. The scanner records nothing, so `expo-camera` takes no audio (**Verified** with `expo config --type introspect`: the manifest keeps `CAMERA` and `RECORD_AUDIO`, and iOS gets one camera sentence and one microphone sentence; and on the Pixel 8 emulator the installed app declares both, granted only once asked). Reading a code has not been run on a device: the emulator's camera shows its own moving test pattern. The address follows the same rule as the desktop app's (`parseServerAddress` in `client-runtime`), and pairing checks the server's `/api/server` before it sends the code. A paired phone opens its server's roster on the next start, if the saved server still passes that rule. One that does not is forgotten with its pairing (the credential, the device-id copy, and the drafts and unsent messages), so pairing again leaves nothing of it behind, and the pairing screen shows; if that cannot be deleted, the app says it cannot read this device's sign-in. Pairing with another server replaces the client of the first; its credential is stored with the origin of the server that issued it, so it never reaches another.
- **Changing server.** A server whose address changed (a new router, a new DHCP lease) is never reached again, so the line that says the server cannot be reached, and the screen for a server of another protocol version, offer to change server. After the operator confirms, the app signs the phone out the way sign-out does: it revokes nothing, since it is not connected, deletes that pairing's drafts and unsent messages, then its credential and the device-id copy, and shows the pairing screen with an empty address. The old entry may still show under Devices on the server, and another device can revoke it there.
- **The first run** is the web's, step for step, with the same words from `client-runtime` (`presentation/onboarding.ts`, `wording/onboarding.ts`). Its steps and the bot above them move on the design tokens' springs (`reanimatedSpring(springs.pop)` and the others), the ones the web draws as its `--ease-*` easings, so both clients move alike; its buttons press with `PressScale`, and the command that connects a provider copies with `expo-clipboard`. The system's Back goes to the step before and does nothing during the arrival; on the welcome, which has no step before it, the app leaves it to the system (**Verified** on the Pixel 8 emulator, Android 16: from the look, Back returns to the name, then to the welcome; Back pressed as the arrival starts leaves it to open the conversation).
- **Its ports.** The credential is in the system's secure storage (the keychain on iOS, the keystore on Android), readable after the first unlock and on this device only. A read that fails, or a stored value that does not decode, is not taken for a missing pairing, which would lead the operator to pair again over the unreadable credential and leave the old device listed: the app says it cannot read this device's sign-in and offers to try again or to forget the sign-in. Forgetting, after the operator confirms as for changing server, deletes the device-id copy and every draft and unsent message in one transaction, then the credential, and shows the pairing screen. Drafts and unsent messages are in SQLite, beside a copy of the paired device id that the check before every write reads in the same transaction (see [Pairing](#pairing)). The app keeps one connection to the database, and every operation on the device's storage, whichever client makes it, runs one at a time, so a client being replaced never runs a statement inside the new one's transaction. The copy follows the credential: saving one writes the copy first and, if the secure write fails, sets the copy back to what the secure storage holds; clearing one clears the copy first; reading one sets the copy to what it finds, which mends a copy left behind by a crash, or a keychain item that outlived the app's data. Locks are in process, as the app has one window. Network status comes from `expo-network`, random bytes from `expo-crypto`, HTTP from `expo/fetch`, and the socket from React Native's `WebSocket`.
- **What outlives the app.** On iOS the keychain item outlives uninstalling the app (**Assumed**: Apple documents no removal on uninstall, and nothing was run on iOS), so a reinstall goes straight to the roster of the same pairing. Changing server, or revoking the phone from another device, ends it. On Android the credential is kept out of the system's backups by `expo-secure-store`'s config plugin; the backups include the SQLite database, with drafts and unsent messages and never the credential. That is intended: they are the operator's own text and give no access to the server, and a restored phone pairs anew.
- **Plain HTTP.** iOS allows it to local networks only (`NSAllowsLocalNetworking`); whether that covers a private IP literal as well as a `.local` name is **Assumed**. Android's network security config names hosts, never address ranges (**Read**: Android's network security configuration documentation), so it cannot say "private addresses only": it allows plain HTTP, and the app refuses it before it connects to any address outside loopback and the private ranges.
- **What Hermes lacks.** On Android with React Native 0.88, Hermes has no `Intl.PluralRules`, `Intl.ListFormat` or `Array.prototype.toSorted` (**Verified** on the emulator), and the catalog and `client-runtime` use all three. The app's entry loads polyfills for them before any other module, with the rules of every language the catalog has; each installs only where the engine has none. T3 Code's app loads its Intl polyfills the same way (**Read** at `c1464d67`, `apps/mobile/src/i18n/intl-polyfills.ts`). The language is the device's unless Settings picks one.
- React Native with React Navigation's native stack, one route per screen: the roster, a bot's or room's conversation, its details, and over those the forms (New bot, a bot's profile, a room) and a memory file. On a phone they stack. From the tablet width up the roster's route shows the conversation it names beside a 280 px roster, and the conversation's own route is not used. Folding a foldable moves the open conversation to its own screen and unfolding moves it back beside the roster, each in one step that keeps what was open over it, such as the details. Folding moves the app to a display of another size and density, and Android destroys an activity that does not handle such a change itself and builds it again, which would lose what every screen held, a form's edits among them. The app's config plugin (`plugins/foldInPlace.js`) adds `density`, `orientation`, `screenLayout`, `screenSize` and `smallestScreenSize` to the main activity's `configChanges`, so the activity stays (**Verified** with `expo config --type introspect`). React Native 0.88 then lays the app out again in place at the new width and density (**Verified** on the Pixel 9 Pro Fold emulator, Android 16): with a room open beside the roster, with its details open over it, and with the details opened on the folded screen, each fold and unfold kept what was open, and Back led to the conversation, then to the roster. A half-filled New room form and a bot's profile form kept what was typed and picked across a fold and an unfold. A screen waits for the roster's first load before it says a bot or room is gone. Until then the roster says it is connecting (**Verified** on the same emulator, starting the app with the server stopped); nothing opens a conversation before that load yet, so the conversation's own wait has not shown on a device. A hidden bot's conversation opens like any other: hiding the bot from another device removed its row and left its open conversation in place, beside the roster and folded (**Verified** on the same emulator).
- **The roster** draws each bot's avatar with `react-native-svg` from the tokens' silhouettes, in 64 px rows, each stepped on the UI thread by a Reanimated frame callback while its row is in view, the list is not scrolling and the app is in the foreground ([Avatars](../design/design-language.md#avatars)); with reduced motion every avatar holds its still form. Which state an avatar and a row's line show comes from `client-runtime`. Its search finds hidden bots too, and New offers a bot or, once there are two bots, a room. Before the first bot the first run takes the whole screen, on a tablet too, with the header's way into Settings: what keeps the engine from running bots, the command that connects the providers with each provider's state, or a name for the first bot. On the unfolded Pixel 9 Pro Fold emulator the first run took the whole screen and created the first bot, and New offered only a bot until there were two (**Verified**); the engine's and the providers' states were not shown there, since the scripted provider is always ready, and the search was not run.
- **The details** answer what a bot is and what runs without the operator: its profile, its routines with a switch that pauses each and says in a toast when it could not, each opening its runs on a screen of its own, as a routine change in the conversation does, over the details (**Verified** on the Pixel 8 emulator, Android 16), the files it sent, as the conversation's file cards that open the same way, its memory, the model and permission mode it runs on, a fresh start, and deleting it, last and apart, which takes no second press until the server answers. What each line says comes from `client-runtime`'s wording, which the web's details use too. **Verified** on the Pixel 9 Pro Fold emulator, folded and unfolded, in the light theme and the dark, with a routine, a memory file and a file the bot sent written to the server's home, since the scripted agent cannot make them: the switch paused and resumed the routine on the server, the file card opened the system's chooser for its type, a fresh start said so in a toast, and deleting a bot or a room asked first, then left for the roster. - **The composer** keeps a draft per bot and room, with mentions in rooms, and sends through the runtime's outbox. - **Dictation.** While the draft is empty, the composer's trailing button dictates; while it listens it stops, and once there is text it sends again. The first press asks for the microphone (and, on iOS, for speech recognition). What the recognizer hears becomes the draft's text as it is heard, through `setDraftText` like typing, and waits there: dictation never sends. Typing stops it, and so do the draft taking no change, the conversation leaving the screen (another screen over it, on a phone) and the app leaving the foreground; a press still being prepared is not cancelled by the last two, since Android reports the app in the background while its permission dialog is open. Recognition is the platform's (`SpeechRecognizer` on Android, `SFSpeechRecognizer` on iOS) through `expo-speech-recognition`, a community module with a config plugin for continuous native generation and releases that follow the Expo SDK's major version; Expo maintains no speech recognition module (`expo-speech` speaks text). A teammate message's line goes to the other bot's conversation (**Verified** on the Pixel 8 emulator, from entries written to its database, since no engine there calls a bot's tools), and a routine change opens that routine's runs over the bot's details.
- **Opening a file.** The runtime downloads it with the device's credential and hands the app its bytes, not a `Blob`: React Native's `Blob` cannot be made from bytes (**Read** in React Native 0.88.1, `Libraries/Blob/BlobManager.js`). The app writes them to its cache, in a folder of each open's own, under the file's own name, with path separators and control characters replaced and shortened to the file system's 255 bytes. Once written, the files of opens that started earlier are deleted, and one that started later is never touched, so two opens at once never meet. `expo-file-system` then shows it in the system's viewer for its type, an app that takes `ACTION_VIEW` for it on Android, through the library's file provider, or Quick Look on iOS (**Read** in `expo-file-system` 58.0.14, `FileSystemModule.kt` and `FileSystemPreview.swift`); with no viewer for the type, the share sheet (`expo-sharing`) offers to save it or send it to an app. On Android a PDF opened in the system's PDF viewer and a PNG in Photos, through the file provider, and a file of an unknown type in the share sheet; after a second open the cache held only its folder (**Verified** on the Pixel 8 and Pixel 9 Pro Fold emulators, Android 16). Quick Look on iOS has not run on a device (**Assumed**). Nothing of the file runs in the app. The last file opened stays in the app's cache until another is opened, the app starts again, or its server is forgotten or changed, which deletes every one with the drafts and unsent messages; an open still under way then keeps nothing. The system may clear the cache sooner, and a file it cannot delete is left to it.
- Uniwind for styling, with the theme generated from the tokens: light and dark colors as Uniwind theme variants, the type scale, radii, spacing and breakpoints in px, and the touch target and touch row height. Files are resolved, which copies each into the app's cache under its name (**Read** in `expo-sharing` 58.0.22, `ResolvingShareIntentDataParser.kt`): the app reads the copy, which stays readable after the sending app lets go of the original, and takes its size from the copy, the bytes the upload sends. Only a share that carries files is resolved, because resolving a link fetches it. The share then waits, in memory and never sent, and the app opens Send to over what it shows: the shared text and how many files come with it, above the roster's rows. A new share replaces the one waiting; leaving Send to lets it go. Picking a bot or a room puts the share into its draft by the runtime's rule (`sharedDraft`, above) and opens its conversation, where the composer shows the draft with its files uploading; each file is read from its copy as it uploads. Nothing is sent until the operator presses Send. A file the draft leaves out is said with the reason the composer gives. While the draft takes no change, as when it is being sent or the drafts are loading, a pick is refused and the share keeps waiting. Drafts that could not be read are read again by the pick itself, as the composer's Try again does, since nothing else reads them again; if they still cannot be read, the pick says so and the share keeps waiting. A share with nothing a draft can take, or one that cannot be read, is said to be so rather than dropped. A text file shared as `text/plain` arrives empty, since `expo-sharing` reads only a `text/plain` share's text (**Read**, `SimpleShareIntentDataParser.kt`). **Verified** on an Android 16 emulator (Pixel 8, API 36) with a development build: a photo shared from the Files app, to the app cold and already running, opened Send to; picking a bot put it in that bot's draft, nothing reached the server until Send, and the stored file's SHA-256 matched the photo's. A link shared from Chrome went into a draft as its text. With the drafts made unreadable on purpose, a pick said so and kept the share, and the same pick put it in the draft once they could be read again. Not on iOS: there, a share sheet reaches an app through a share extension that shares an App Group with it, and signing one takes a paid Apple developer account, which the project does not have.

In a build that can receive pushes, the notifications section also says whether this phone itself shows notifications, as the web's says the browser's, with the button that allows them; in one that cannot, it says nothing of this phone ([Push notifications](#mobile), below). On a wide screen it keeps to the conversation's text column. **Verified** on the Pixel 8 emulator (Android 16): Settings opens from the first run and from the roster's header; every section shows, the notifications section with no line for this phone; a zone that does not exist is flagged once the field is left, and one typed in lower case is saved as the system names it; both themes. Not seen: the first run while the engine's status is still unknown, since it arrives with the roster.

  - **Permission.** Only "Allow notifications on this phone", in Settings' notifications section, asks for it: the section's `thisPhone` (`usePhoneNotifications`) passes the phone's access and `allow`, which calls `allowNotifications`. Not asked yet, or refused once on Android, where the system can ask again, the section shows the button; refused for good, it says the phone's settings decide, and a press that comes then opens the app's page in the system's settings, since the system would show no dialog. An answer just given in the dialog stays as it was. The access is read again whenever the app returns to the foreground, so one changed in the system's settings shows on return. A build that cannot receive pushes shows no line for this phone. Nothing asks at start, and creating the channels at start does not ask either, on Android 13 and later, for an app that targets them. On Android 12 and lower there is no permission to ask for: Android has it from Android 13, API level 33 (**Read**: Android's notification permission documentation), and before that an app's notifications are allowed from its install, so the app registers at start and the section says the phone shows them.

Once the operator refuses notifications, it ends the registration. Between two returns to the foreground, what the app already told the server is not sent again.
  - **A token for each pairing.** Expo keeps a token for each device id an app gives it, the app's installation id by default, and when the device's own token (Firebase's or Apple's) changes, `expo-notifications` posts the new one to Expo under the installation id by itself (**Read** at 58.1.8, `src/getExpoPushTokenAsync.ts` and `src/utils/updateDevicePushTokenAsync.ts`). With that one token, a server the phone left could be reached again through the next. So the app asks for each pairing's token under its own device id, a UUID shaped from a SHA-256 hash of the pairing's id, with nothing stored. The installation id's token, which no server holds, is the only one Expo moves by itself.
  - **The socket.** In the background the app keeps no socket open (`Lifecycle`, from React Native's `AppState`; iOS's `inactive`, under the notification center or the app switcher, keeps it), so the server pushes to the phone; it connects again when the app returns. The server pushes to any device with no socket open, so a push also reaches the app in the foreground while it cannot reach the server, offline or between attempts: it shows then as in the background. Only while the app is connected does a push show nothing: it raced the socket's opening, and the roster shows its entry unread. Whether Android puts the app in the background while the system's photo or document picker is open, which would close the socket until the app returns, is not known: it was not run.
  - **Channels.** On Android each kind of notification shows in a channel of its own, named in the language the app shows, and renamed when it changes, whose id is the kind the server sends as the push's `channelId` (`NotificationKind`), so the operator can silence messages and keep approvals. A push that names none, from a server older than the channels, shows with the messages.

Another pairing's push, or one about a bot or room that is gone, opens nothing; a tap before the roster loaded waits for it.

The app does not wait for that before the pairing screen accepts a new pairing; the new pairing's registration waits for it. Revoking a device deletes its registration on the server, and on the phone revoked from another device, the notifications it shows are cleared too. A server that still lists a pairing, after a sign-out it never confirmed, holds that pairing's token, and on Android, once the device's token is deleted, Expo answers it `DeviceNotRegistered`. Two cases still let that server reach the phone (**Assumed**, both). On Android, a `deleteToken` that fails, as offline, is logged and not tried again, and the old device token stays valid. Revoking the phone from that server's Devices ends them.

Such a build was not run on a device either.

### Installing the Android app

Each release has the app as `j3-bots-<version>-android-arm64.apk`, for arm64 phones, which nearly every Android phone of the last years is ([Releasing](../operations/releasing.md#what-a-release-contains)). On the phone:

1. Open the release on GitHub (Releases, on the repository's page) and download the APK under Assets.
2. Open the download. Android asks to allow the browser, or the files app, to install apps; allow it, go back, and install. Play Protect may say it does not know the app; it lets the install go on.
3. Open J3 Bots and pair it with the server: scan the QR code that Settings → Devices on a paired device, or `j3-bots pair` on the server's machine, shows.

Every later release is checked by the phone itself: it installs over the app only when it is signed with the same key. The first install has nothing to compare with, so whoever wants to check it compares the APK's signing certificate with the project's, before installing, on a computer with the Android SDK's build tools:

```sh
apksigner verify --print-certs j3-bots-<version>-android-arm64.apk
```

The command must succeed first: if it prints `DOES NOT VERIFY` or exits with an error, the APK is damaged or was changed after signing, whatever digest it shows, and must not be installed. Then every line `certificate SHA-256 digest` must read `bfd3b598e6bd1c1ccdc969076a4254fd5a3696bddd5092df44b2bb51581431ff`, the release certificate's, which each release's notes repeat. Any other value means the APK was not signed by the project.

A newer release installs the same way, over the one installed, and keeps its pairing, drafts and settings; the app does not update itself. **Verified** on the Pixel 8 emulator (Android 16) with x86_64 builds of the release variant, built unsigned and signed with `apksigner` and a test key as the release workflow does: the APK started with no Metro, paired with a server and showed the roster, and the next version, built and signed the same way, installed over it and opened on the same roster. The release APK cannot show push notifications: it is built without the Expo and Firebase projects they need. It installs beside a development build, which has another app id.

Mobile uses its own components. Web and mobile share logic, tokens and vocabulary, not React components. See [decision 0007](../decisions/0007-client-and-server-stack.md) for why, and for the alternative of a single universal codebase.

## Reaching the server

The server listens on an address the operator chooses. J3 Bots does not run a relay.

| Where the client is | How it reaches the server |
| --- | --- |
| Same machine | Loopback |
| Same network | The server's LAN address |
| Anywhere else | The operator's own private network (Tailscale, WireGuard) or their own reverse proxy with TLS |

Plain HTTP is accepted only on loopback and private address ranges. Everything else requires TLS.

## Pairing

A new client is paired with a one-time code.

1. The operator runs `j3-bots pair` on the host, which prints the code and the addresses the server listens on (while pairing is locked after failed attempts it makes no code, says until when, and `--unlock` lifts the lock: [Security](security.md#j3-bots-own-surface)), or opens Devices in an already paired client, which shows the code as text with the time it expires. A code expires in five minutes. Making one in Devices needs a connection to the server; offline, Devices says so. The code is ten characters of Crockford base32 (no `I`, `L`, `O` or `U`); clients accept it in lower case and with spaces or dashes.
2. Both also show a QR code of a pairing link, for a phone's camera: the server's own address at the path `/pair`, with the code as the fragment, `<origin>/pair#<code>`, so neither is typed. A camera opens it in the browser, where the server serves the web client at `/pair` as at any path it routes; the native app's scanner reads the same link. The path is the link's own because a browser loads the page again for a new path, while a tab already showing the app at `/` would take a new fragment alone without loading, leave the pairing screen empty and let Back and Forward bring the code back (**Verified** in Chromium). `pairing.start` answers the code with the origins another device reaches the server at, the ones `j3-bots pair` lists: its `publicOrigin` first, when one is set ([Server: configuration](server.md#configuration)), then where it listens; a server from before that field answers without it, which a client reads as none. Devices puts the origin it reaches the server at first when that is `https`, as a domain a proxy serves, or one the server offers; a plain-HTTP origin the server does not offer, such as a forwarded port, is left out. The others follow, each once, and an origin that names the reading device itself (loopback, also IPv4-mapped, or the unspecified address) never reaches a QR code. The operator can pick which one the QR code carries when there is more than one. `j3-bots pair` draws it for the first address it lists that is not `localhost` or another loopback address (the `publicOrigin`, else the first in the order the machine lists its interfaces), or for the one `--address` names, and says which address it carries. `--address` takes only a bare `http` or `https` origin (a trailing `/` at most; no path, query, fragment or user name, not even an empty one, and no other scheme), checked as typed, before the URL parser resolves a path such as `/x/..` or drops an empty `@`; it must be one the command lists or an `https` origin, and anything else is refused before a code is made. The lines that say where the link goes come first and the QR code last, so the prompt after it scrolls the text, not the code, away. Where its standard output is not a terminal, or the terminal is smaller than those lines, the QR code with its quiet zone and the prompt's row, it prints the link as text and says how large the terminal must be. With no address another device reaches, as on a server that listens on loopback only, there is no QR code, only the code. The link's schema is in `packages/contracts` (`PairingLink`), for every client to decode: the base must be a bare `http` or `https` origin as a browser writes it, the path `/pair`, no query or user name, and the fragment exactly one code, read as a typed code is (in either case, with dashes between groups) and then with the pairing code's form; anything else is refused. `parseUrl` there is built on the WHATWG `URL` class, so a native client needs an implementation of it: Expo's, or a polyfill.
3. A link only fills in the pairing screen. A client never pairs from a link by itself: the operator still presses Pair. The web client reads a page at `/pair` as it loads, before the router sees the address, and replaces it at once with the app's root, given as a whole URL, so the code leaves the address bar and the tab's back and forward history, and an address copied from it (**Verified** in headless Chromium 151 with a built client: each of two links opened in turn in a tab already at `/` loads the page, fills in its code and leaves the address at `/`, and Back and Forward bring no code back). It also drops a link's code when the page is put aside (`pagehide`), as when the operator leaves for another page before pressing Pair: a page the back/forward cache restores keeps what it held, and without that Back would bring the unused code back into the form. The pairing screen then starts over, its device name with it. **Assumed** until tried in a browser with the cache: that the restored page shows the form empty; the drop is tested on what holds the code, not in a browser. When the browser turns out to be paired with that server, which it knows only once it is connected, it drops the code without asking; a browser whose stored credential the server refuses, as after a reinstall or a revocation, keeps the code for the pairing screen it then shows. Every client's pairing screen shows, prominently, the origin of the server it pairs with. A native client that is already paired with a different server when it reads a link to another one must say that pairing replaces that server. The mobile app scans only on its pairing screen, while it is not paired, so this cannot happen there. An address a client takes from a scanned link follows the rules of one typed in ([Reaching the server](#reaching-the-server)): plain HTTP only at a loopback or private IP literal, HTTPS everywhere else.
4. The new client sends the code to `POST /api/pair` with a name for the device and receives a device token. The web client guesses the name from the browser and the system, in the operator's language ("Chrome on Linux", "Chrome no Linux"); a native client offers its platform's name for the device, such as the phone's. The operator can change it before pairing. The server stores only a hash of the token. A code works once.
5. Devices are listed in settings with their last activity, and can be revoked. Revoking closes that device's connections immediately. A client waits ten seconds at most for the server to confirm a revocation; without that answer it says the revocation is not confirmed, offers to try again, and reads the list again once connected, which shows whether the device is still there.

A device token grants everything the operator can do in J3 Bots. There are no narrower roles in the first versions.

Signing out a device ends its access. It is offered in settings and, while there is no roster yet (connecting, or before the first bot), as a quiet button on that screen. It takes four steps, each attempted whatever the others did, and each failure is logged on its own:

1. It stops sending the outbox.
2. If it is connected, it revokes its own credential on the server and waits up to ten seconds for the server's word, described below. No later step asks the server anything, so this is all the time sign-out spends on the server.
3. It deletes its pairing's drafts and unsent messages, which hold conversation text.
4. It deletes the credential, unless the device stores another one by then, and only then returns to pairing.

Every step acts on the pairing the tab follows when the operator confirms, read before anything waits. Stopping the outbox waits for an answer being recorded, and while it does, or while the server answers, another tab may learn of the revocation first, pair again and write. That pairing stays whole, with its credential and its text; the tab that signed out follows it, even before word of it reached that tab, since deleting the credential reads what the device stores. A notice says that another tab paired this browser again, so it stays signed in, and either that the old access ended or, when the server never confirmed it, that the old access may still show under Devices. The notice belongs to the page, not to the shell, which the pairing screen replaces meanwhile. If deleting the credential fails, the device stays signed in, and settings say that sign-out did not finish.

Only the server's word counts as the revocation confirmed: its answer, or its refusal of the credential on a ticket request. Revoking closes the device's sockets before the answer can arrive, so the refusal is usually what tells. Every tab of the device loses its socket at that moment and asks for a ticket after its own wait, so any of them may hear the refusal first. The tab that hears it deletes the credential and, in the same storage transaction, leaves in its place a record naming the pairing the server ended. The record holds no secret, says only that one pairing ended, which never returns, and the next pairing saved replaces it. A tab that is signing out and finds the credential gone counts the revocation confirmed only when that record names its pairing, or when it heard the refusal itself. When the server cannot be reached, or another tab only signed out here first, nothing confirms it: the device still signs out here, and the pairing screen says the server did not confirm it, so the other devices may list it until one of them revokes it.

A tab only ever shows, keeps or sends the drafts and unsent messages of the pairing it follows. Every record names the pairing that wrote it, and the rule holds by construction, not by erasing:

- The drafts and the outbox each hold the pairing they follow. It changes only under their own lock, in the same step as they drop everything they held. Every read projects only that pairing's records: another pairing's record reads as no record.
- Every write is that pairing's, and the storage transaction that writes it also reads the stored credential, and writes nothing unless it is still that pairing's. In a browser and in the desktop app the credential and the records are in one IndexedDB database, so the check and the write are one transaction. A platform that keeps the credential in a system keychain keeps a copy of the paired device id beside the records for this check: the mobile app does, in its SQLite database ([Mobile](#mobile)). A pairing never returns once it ended, so a write refused while the credential is still the tab's pairing was refused for another tab's change, and one refused otherwise means the pairing ended: the tab writes nothing more and follows the next.
- The same holds for presence: what the operator has in view is reported only on a socket of the pairing it was set under; a socket of another pairing hears that nothing is in view until the window says what it shows. A notification that arrives on a socket of a pairing the window no longer follows is dropped. An entry counts as seen only while its window shows it and has focus, as for what the window reports in view, so a reply that arrives in a background window both notifies and stays unread.
- A message goes only on a socket opened with its own pairing's credential. Any other command belongs to the pairing it started under: a socket of another pairing never runs it, and it fails as not paired.
- A file transfer carries the token of the pairing it started under, read once, and stops as soon as the tab follows another pairing or none: an upload under way never goes again under the next pairing.
- The pairing a tab follows changes in the same step as the credential it holds.

Erasing is cleanup. Whenever the pairing a tab follows changes (from none, to none, or to another), it drops what it held, erases the device's records of the pairing that ended, and only those, then reads the records of the pairing it follows now; its composer is read-only until it has, so nothing typed meanwhile is lost under them. Nothing of the pairing that ended shows from the moment the pairing changes, though dropping it may wait for an answer or a draft still being saved under it. When the drafts cannot be read, the composer stays read-only and says it couldn't load the draft, with a way to try again: an empty composer would look like no draft at all. A tab on the pairing screen that hears of a pairing another tab made reads that pairing's saved drafts the same way. A tab can close before it erased a pairing's records, so at launch the client erases every record whose pairing is not the one the device stores, read after the records: a record is written after its pairing is saved, so one that names another pairing names one that ended. When erasing fails, the records stay on the device, and no tab shows or sends them.

Ending a pairing never touches another: the stored credential is deleted only if it is still the one that ended, compared and deleted in one storage transaction, and a tab that finds a newer one follows it instead of returning to pairing. In a browser, every change to the stored credential is announced to the origin's other tabs with `BroadcastChannel`, and each loads it again, so pairing or signing out in one tab takes effect in all of them.

## Connecting

Every connection is one device's. The server accepts the device token as an `Authorization: Bearer` header on the upgrade, or a single-use ticket bought with it at `POST /api/socket-ticket` and passed as `/ws?ticket=…` within a minute. Either way the server checks the credential once, at the upgrade, and the socket is that device's until it closes.

All three clients use the ticket. A browser cannot set a header on a WebSocket, and cannot read the status of a refused upgrade, which reaches it as a plain connection failure. The ticket route is plain HTTP, whose status every platform reads the same way, so one path serves all three:

- Before its first ticket, the client checks `GET /api/server`. A server that speaks another protocol version is shown as incompatible and not retried until the operator asks.
- Every socket is opened with a fresh ticket, since a ticket works once.
- A 401 from the ticket route whose body is the server's own `NotAuthenticated` means the device is not paired or was revoked: the client forgets its credential, stops reconnecting and asks to pair again. Any other 401 comes from something in between, such as a reverse proxy whose own login expired, and counts as the server being out of reach: the client keeps its credential, drafts and unsent messages, and tries again.
- Anything else (no answer, a refused upgrade, a socket that closes after it opened) means try again, after a pause that doubles from half a second up to thirty seconds, jittered so clients do not return together. When the platform reports the network gone, the client closes its socket at once rather than wait for it to fail, which can take a long time; it then waits, and tries at once when the network returns.

A request in flight when its socket closes is sent again on the next socket. That is safe because every command carries its command id, and the rest are reads. Files go over HTTP with the same bearer: `POST /attachments` before sending a message that carries them, and `GET /attachments/:id` to open one. The ticket's rule holds for files too: only the server's own `NotAuthenticated` in a 401 means the device is not paired, and an answer that comes from another address, as when a proxy redirects the request to its own login page, did not come from the server. Either is a failure to try again, not a refusal.

No HTTP request waits forever, since a server or a proxy can take one and never answer. The server check, pairing and the ticket get ten seconds each, after which the server counts as out of reach and the pause above follows. A file transfer gets the same ten seconds plus time for its bytes over a slow link (32 KiB a second), fifteen minutes at most, counted until its last byte is read: an upload then starts again after the same pause, and a download says the file could not be opened. The installed web app's service worker sends a page load to the network first and opens the copy of the app it keeps when the network fails, when the server answers with an error of its own (a 5xx), or when the whole page, headers and body, has not arrived after four seconds. The page that loads is the network's answer itself, its headers, status and address untouched; the worker only reads a copy of it to the end. After the four seconds, a page still arriving is cancelled, and so is the body of one whose headers come later. A request with no answer yet is left to end on its own while the kept page shows: sent with an abort signal, it would no longer be a page load to the server or a proxy.

## Protocol compatibility

`PROTOCOL_VERSION` (`packages/contracts/src/http.ts`) is the first thing a client checks, and a server that speaks another version is shown as incompatible ([Connecting](#connecting)). Raising it locks out every client built before, the installed Android app included, which does not update itself. A client compares versions for equality, so raising it also keeps a newer client away from an older server. So it is raised only for a change an older client cannot survive, or one a newer client cannot make against an older server, and a server may add, without raising it, what a client is built to pass over.

**What a client passes over.** Five sets stay open, because each is in data a client cannot avoid reading and each grows whenever J3 Bots learns something new to say:

- **Kinds of entry.** `entries.subscribe` and `entries.history` carry `ReceivedEntry`. An entry whose `_tag` the client does not know decodes as `UnknownEntry`: its kind, id, order and time, and nothing else. Entries stay in history, so one a client refused would keep the whole conversation from opening, for good.
- **Kinds of notice.** A notice whose `_tag` the client does not know decodes as `UnknownNotice`. Notices are the kind added most often: each new way for something to stop gets one.
- **Kinds in a roster preview.** `EntryPreview.kind` decodes a kind the client does not know as `unknown`. The roster carries every conversation's latest entry, so one new kind there would stop the whole roster.
- **Failure classes.** In a `turn-failed` notice and in a blocked bot's state, a failure class the client does not know decodes as `unknown` (`ReceivedFailureClass`), worded as a failure it cannot name. A new class is added as a provider fails in a new way, and the roster carries every bot's state. Whether the notice offers Try again is still the server's `retryable`.
- **Avatar tokens.** A bot's `Avatar` is two tokens, a shape and a color, each of which a client that does not know it draws with its fallback, apart from the other (`resolveAvatar`: a dome for a shape and slate for a color now, a circle and gray in 0.1.x). Only what a client sends is closed (`AvatarChoice`), since the server refuses a name it does not have. So a server may draw on new silhouettes and colors without a bump, but a client that sends a new one needs it: a server built before refuses the name, and creating or editing the bot fails instead of saying the app and the server don't match.

An unknown entry or notice shows in its place as one quiet line, "This needs a newer version of the app.", and a roster row as "Something this version of the app can't show". The read mark passes it like any other entry. An unknown notice offers no Try again: the operator could not tell what it would run again. Only a value the client does not know is unknown: an entry or notice of a known kind that does not decode is refused as before, so a broken server is never mistaken for a newer one. The server itself writes and stores only the closed `Entry`, `Notice` and `FailureClass`, and its handlers for `entries.subscribe` and `entries.history` are typed to answer only `Entry`, so it never sends `unknown`.

A field a client does not know is dropped as the client decodes, so a server may add a field that older clients can do without, and a client may read an optional field a server of the same version does not send yet, decoding it as null and doing without it: a work fold's `turnStartedAt` and a waiting bot's `since` are two, with which a turn's clock counts from the turn's start, and without which a fold counts from its first step and a waiting bot shows no clock; a finished fold's `waitedBeforeMs` (0 without it), a stalled bot's `quietSince` (without it, the line says "No recent activity" with no duration) and a roster preview's `ending` (without it, a fold of no steps reads "Did some work") are others. A protocol-7 client from before these fields, which only unreleased development builds are, shows a fold of no steps as "Stopped after 0s", with nothing in its panel (**Read** in Effect 4.1.3: `effect/rpc/RpcClient` decodes with the RPC's parse options, which J3 Bots leaves at the default, and `onExcessProperty` defaults to `ignore`).

**What a client calls without relying on it.** A client may call an RPC an older server of the same version lacks when it only tells the server something the server can do without, and passes over any failure of that call. `settings.deviceTimeZone` is one: an older server answers it with a defect for an unknown request, and the operator's time zone stays as it was.

**What needs a bump.** Everything else is closed, because a client acts on it: whether a card can still be answered, what Try again runs, which Android channel a push goes to. A value it misread would make it do the wrong thing, which is worse than saying the app needs updating. These need `PROTOCOL_VERSION` raised:

- a new value in any other set the contract lists: authors, a message's delivery and mentions, a card's status, an approval's kind, a work step's kind or status, a turn's ending, bot states, routine triggers and runs, roster items, subscription frames, errors, and `NotificationKind`, so a new kind of entry that notifies needs a bump where one that does not, does not;
- a field removed, renamed, made required, or given a new type or a narrower range, in anything a client decodes;
- a field a client must understand to act correctly, even when it is new;
- a new RPC or route a client relies on, and a change to what an existing one takes or answers: a client compares versions for equality, so it also refuses an older server, and a newer client of the same version would call what that server lacks.

Protocol 6 is the first whose clients pass over the open sets: from protocol 6 on, adding a kind of entry or notice, or a failure class, needs no bump. Clients of protocol 5 and before, J3 Bots 0.1.0 among them, refuse a conversation or a roster that holds one, so 6 shows them the incompatible screen instead.

Protocol 7 came with the twelve silhouettes and twelve colors (migration 20). Its clients send them whenever a bot is created or its look is edited, the look the picker starts on included. A server of protocol 6, J3 Bots 0.1.1 among them, refuses a token it does not have. Teal is the only one it shares, a color, so every look a new client sends carries a shape it refuses. A client of protocol 6 against a newer server draws every bot as a circle, gray unless its color is teal. Either way the client shows the server as incompatible instead, which asks the operator to update the app or the server so they match.

## Behavior every client must get right

- **Offline and reconnect.** A message typed while disconnected is kept and sent on reconnect, exactly once, and the messages of one conversation reach the server in the order they were written. Sending moves the message from its draft to the outbox in one storage transaction, so a crash leaves it in exactly one of them; if the device cannot keep it, it stays in the draft and the operator is told. A draft is kept whatever its length; the limits of a message apply when it is sent, checked against the same schemas and limits the server applies (its text, its number of files, an empty file, the size of each inline image and of all of them together), both where the composer sends a draft and where any message enters the outbox: a message over one is not sent, the draft stays as it is, and the composer says why. While that transaction runs, a few milliseconds, the composer is read-only and takes no files, so nothing typed meanwhile is lost.
- **Several windows.** Each draft is stored with a revision. Every write of it, as the operator types and when Send moves it to the outbox, claims the revision this window last read or wrote; if another window sent or changed the draft since, it writes nothing, and this window shows the draft as stored, with its own files still uploading or refused on top, as far as one message can carry them (a file still uploading that no longer fits stops, and says why), and tells the operator, saying it sent nothing when it was sending. A draft emptied or sent stays stored, empty, with a revision of its own, so a window that read it before still finds it changed; it reads as no draft, and there is at most one such record per conversation. One rule keeps this whole: every operation on a draft (autosave, deletion, Send, Restore) runs under this window's draft lock (one for all of its drafts) and reads its inputs, both the in-memory draft and the expected stored revision, only after acquiring the lock. Send commits exactly the text and files the operator pressed Send on, captured at the press, or nothing. Only what is persisted is ever written: upload progress and failed files live in memory only. The lock is the window's own; between windows, the revision decides. When this window held text the device never kept, the composer offers it back, saying the operator's earlier text was replaced in another tab, with Restore and Dismiss, and announces it to assistive technology each time newer text is offered; the toast says the draft changed when the change offered nothing new, or when Send sent nothing. Restore writes the text as a new change over the stored draft: nothing is written back unless the operator asks. When the device cannot write a draft, or cannot read the one another window changed, the window keeps the draft as it holds it and tries again, under the same revision claim, after a pause that grows with each failure, until the device keeps it or shows what another window kept; meanwhile the composer says quietly that it is not saved yet, and Send sends nothing and says the device couldn't keep the message. Text the device kept, the other window had in front of it, so there is nothing to restore. The offer, one text per draft, stays beside the composer until the operator restores it, dismisses it or sends the draft, through any later change: a change that displaces no new text keeps it. A change that displaces newer text the device never kept replaces it: that text is the last the operator wrote, and the older one, which the newer was typed after, goes. Unsent messages follow one rule: the stored outbox records are the only truth about them. Every window's list of outgoing messages is a projection of storage, read again whenever another window changes the outbox, after each read a delivery makes, on every connection, and every five seconds while connected, which bounds how long a message waits when the window that kept it closed before telling the others. Delivery, Retry and Discard act on the stored record, claimed with the state the window expects in one storage transaction, so a window that missed a change does nothing rather than undo it; when the device cannot write the claim, nothing changes and a notice says the change wasn't saved. Every attempt to deliver a message has its own persisted revision. A claim (Retry, Discard, recording an answer) names the revision it expects. A caller waiting on an attempt is answered from storage with what became of that attempt: a record keeps the failure of each earlier attempt, so a caller of an attempt another window has since replaced learns how its own ended, not how a later one did. The command id stays the same across attempts, so the server applies the message once. Recording the server's answer is part of the attempt: the window keeps the conversation's lock until the device holds the answer, trying a failed write again a few times within a fraction of a second, and never sends the attempt again meanwhile. When the device still cannot record it, the message says so at once, and the window tries again to record the answer every five seconds, connected or not, since recording needs no socket, instead of sending it again, each answer on its own so a conversation another window is sending holds up no other; a failed read of the outbox is tried again the same way, so what the window shows catches up with what the device keeps; another window, which does not have the answer, may send the same attempt, which the server answers from its receipt. An accepted message leaves the conversation when its entry arrives, or when a read of the conversation started after the window knew the server had it holds no such entry: the entry is then older than the history loaded, where scrolling back finds it. A delivered or discarded message leaves a record of its outcome for ten minutes, so a window still showing it can tell one from the other. A window's memory holds a message only when the device could not keep it. One window at a time sends a conversation's messages, holding a lock named for that conversation, and only while its connection lives: a window whose socket closes lets go of the lock, and a connected window sends what it was sending. The window that holds the lock sends everything the device keeps for the conversation in the order it was kept, given by a sequence number the outbox assigns in the transaction that keeps the message. A browser announces each change to the outbox to the origin's other tabs with `BroadcastChannel`. A page served over plain HTTP on a local network has no Web Locks API, so there each tab sends on its own: no message is recorded twice, but two tabs can interleave their messages to one conversation.
- **A message sent again after a reload** leaves the conversation once the server accepts it; its entry may be older than the history loaded, and shows where it belongs when the history is read.
- **One conversation everywhere.** An entry sent or answered on one device appears on the others without a reload.
- **Cards resolve once.** Answering a question or an approval on any device resolves it on all.
- **State is the server's.** A client never infers "the bot is working" from its own timers. It shows what the server reports and marks its view as stale when disconnected.
- **Notifications are the server's call.** A client reports what the operator has in view (a conversation or room in a window that shows and has focus, with no details sheet or dialog over it, or nothing; a modal hides everything under it from assistive technology except live regions and what holds them, so the conversation holds none, and the header's announcements are spoken by a region outside it, which drops the last one when another conversation is chosen) on every socket, and shows each notification the server sends, except one about what it has in view, which the server can send before it hears the view on a new socket. It never decides by itself what deserves one.
- **Every action has a name.** A command's label, its shortcut hint, its menu entry and its accessible name describe the same action on the same object.
- **Languages from the first screen.** Interface text goes through the translation layer from day one, as whole sentences. English is the source language.
