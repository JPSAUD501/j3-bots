# Clients

J3 Bots has three clients: a web app, a desktop app and a mobile app. All three show the same conversations and none of them runs a bot. A bot keeps working with every client closed.

## What clients share

**`packages/contracts`** defines every request, subscription, entity and error that crosses the wire. Clients and the server decode with the same schemas.

**`packages/client-runtime`** holds everything a client does that is not drawing:

- the connection: pairing, authentication, reconnect with backoff, resuming the subscriptions that resume and re-reading the ones that start with a snapshot; no socket while the app is in the background, on a platform that says when it is (the `Lifecycle` port: a phone; a browser tab and the desktop app never are, since no push reaches them), and a new one when it returns;
- state: the roster, the open conversation, pending cards, routines and each one's recent runs, read again as the routine changes or is deleted, engine status, and the turns bots spent recently, for the usage view: the contract does not push those, so they are read when the view opens and on every reconnect while it stays open;
- presence: reporting what the operator has in view on every socket, and receiving the server's notifications;
- commands: sending a message, answering a card, stopping a bot or a room's work, each with its own idempotency key and optimistic entry;
- the roster's order (`orderRoster`, the server's own: pinned rows, then what needs the operator, then the latest activity, then the longest there) and its arrangement (`arrangeRoster`, `filterRoster`): a hidden bot or room (`isHidden`, [decision 0050](../decisions/0050-bots-and-rooms-are-visible-or-hidden-and-the-operators-choice-wins.md)) leaves the rows and the pinned band and is listed among the hidden conversations, while a search finds it; the bot and room forms (`botEdit`, `roomForm`) carry "Hide from the list" and send it only when it changed;
- drafts and unsent messages. A draft's text holds U+FFFC (`FILE_MARK`, the object replacement character) where each of its files stands, one per file, in the order of its files; Send sends the text without them and the offset of each in `message.send`'s `attachmentOffsets`. Whatever writes the text, the draft holds exactly one mark per file (`fittedMarks`): marks past its files are dropped, and a file with none gets one after the text, as for a draft kept before files were placed, or files attached with no place, as a share's. A file that never uploaded is not kept across a restart, and neither is its mark;
- what opening a notification does, the same for a click in the browser and a tap on a push (`notificationOpening`, `pushOpening`): the conversation or room it is about, only while the client follows the pairing that received it (a push names it as the `deviceId` of its data, `PushData` in the contract) and the roster lists what it is about, hidden bots and rooms included; a tap before the roster loaded waits for it; anything else, data that does not decode included, opens nothing;
- templates ([decision 0023](../decisions/0023-a-bot-template-is-a-file.md)): opening a file as one (`openTemplateFile`, refusing a file over the limit before it is read; `openTemplateChunks`, which also reads it in chunks and stops once it passes the limit, whatever size it was said to be; and `readTemplateFile`, which decodes it whole with the contract's schema, refusing a field the schema does not name, or tells a later version's from a file that is not one), the file's name (`templateFileName`; its text is the contract's `templateFileText`, which the server measures before it shares one), whether a share is one template file and nothing else (`sharedTemplate`), and what a bot made from one starts with here (`templateStart`): the template's model if the engine offers it, else the first ready provider's first, and the permission mode capped by the default, with the mode the template asked for when that lowered it. A client sends that model with Create, and a permission mode only when the operator picked one (`templateSubmission`): left as it was, the server settles it by the same rule when it makes the bot. Asking for a bot's template answers `BotTemplateResult`, which tells a bot too large to share (`TemplateTooLarge`, with its largest part) from a failure to try again;
- a turn's plan and its little ones as every client draws them ([decision 0070](../decisions/0070-a-turns-plan-and-its-little-ones-are-its-work.md)): a plan of two steps or more, and how far it got (`shownPlan`, `planProgress`; a step of a status the client does not know is still to do); the little ones still working, in the order they started, at most four and how many more (`shownLittleOnes`; one of a status the client does not know has ended); the roster's dots for a working bot's count (`littleOneDots`); and a room member's (`memberWorkOf`);
- how that work is drawn ([decision 0071](../decisions/0071-a-bot-splits-into-little-ones-under-its-face-and-its-plan-is-a-quiet-card.md)): the lines of the plan's card, the window of a long plan and which line carries its live mark (`planLines`, `planWindow`, `liveLine`); the members of a room with work to show (`roomMemberWork`); and the model the bot's little ones move from, pure and stepped by each renderer as the avatar's is (`presentation/littleOnes.ts`: `syncLitter` is told who works, `stepLitter` moves them, `littleFace` and `littleSpot` say what to draw, `litterPokes` what the bot's own avatar answers), with the hook that keeps the ones on their way home drawn until the model reports them there (`useLittleRows`);
- a routine in steps as every client draws it, the Track ([decision 0080](../decisions/0080-a-routines-steps-are-each-bots-own-turns-driven-by-j3-bots.md)): its stations, one for the trigger and one per step, each standing as the run's copy of the step says (`trackStations`), the run's status as the card's tag and frame (`trackStatus`, `trackAttention`), the station the light stops at and how far the rail is inked (`currentStation`, `inkTo`), the few stations a quick look shows (`trackWindow`), the dots of a run's mini rail (`miniRail`), and the bots that take part (`trackCast`). Its words are the runtime's too (`wording/routine.ts`): the routine's sentence, composed from its trigger, its steps and the bots' names, never written by a model (`routineSentence`), each station's title and line, the yes's question and its ending, a failure's plain words and its one main action (`failureHelp`), and the line a finished run folds to (`foldLine`). A one-step routine is drawn as before.
- what sharing from another app puts in a draft (`sharedDraft`): the shared text, with its URL on a line of its own unless the text holds it, after what the draft already holds, whose mentions stay where they are; the text whole, whatever its length, so Send says when it is too long as for typed text; and the shared files admitted against those the draft holds by the rule `attach` applies, each to upload or left out with the reason the composer gives. Nothing is sent until the operator presses Send.
- a bot's browser (`Browser`): its tabs, kept current by `browser.subscribe`, and a view of one on the media socket. A view asks for the picture size the client gives, read again for each socket; holds the newest picture and acknowledges it only once the client says it is drawn, so the server sends the next only then; answers the server's pings, and takes 45 s without a frame for a dropped socket. Its socket closes while the app is in the background and opens again in the foreground, and opens again with backoff after a drop, keeping the page's size and who holds it meanwhile, so a tab the operator holds comes back held within the server's 60 s. A socket closed because another view on this device took the tab, because the tab closed, or because the host cannot start the browser ends the view. What the operator types while the socket is down is dropped, since it is about a page they no longer see; taking or giving back the tab waits for the socket. Closing a view never gives the tab back: only the operator does that;

**`packages/design-tokens`** holds colors, the bot palette (`botPalette.ts`), the avatar silhouettes (their names alone in `@j3-bots/design-tokens/names`, which the contract takes the avatar choices it accepts from, with the cast new bots take their avatars from), type sizes, spacing, radii, motion timings and layout sizes as data, so the web stylesheet and the mobile theme are generated from one source. One script writes both: `@j3-bots/design-tokens/web.css` for Tailwind on the web and `@j3-bots/design-tokens/uniwind.css` for Uniwind on mobile. Both name their utilities from the same tokens (`bg-background`, `text-sm`, `rounded-bubble`, `tablet:`), except fonts, which the mobile app sets itself. On mobile the colors are converted to 8-bit sRGB, so a color outside sRGB renders clipped there. A test fails when either file is stale. How an avatar's face is laid out at a size (`avatarFrame`: the eye, the antenna, the light and the signal, with the small-size proportions) is data there too, which each client draws with its own renderer (SVG on the web and on Android); its rasterizer, imported from `@j3-bots/design-tokens/raster` so a client that only draws SVG never loads the PNG encoder, draws avatars into PNG images with no image library, in Node, a browser or the mobile app. A notification's icon is drawn with it (`renderStillAvatar` for a bot, `renderStillRoomAvatar` for a room), and so is a mention's face in Android's composer, at the screen's pixels with the proportions of its 16 px, and so are the tray's (`renderTrayIcon`) and every platform's app icon (`renderAppIcon`, [App icons](../design/design-language.md#app-icons)), each the brand mark drawn from `appIconArt.ts`, its plate's shading and its light's glow as the rasterizer's gradients: the web's as the web client builds, the desktop window's as the app starts, and the files the native builds read, which the same script writes to `@j3-bots/design-tokens/icons/*` with their colors in `colors.json`, under the same staleness test. The avatar's model stays in `client-runtime` (`presentation/avatar.ts`): which state a bot shows, each state's pose and still form, the seeded life each bot has, how it answers the pointer, a press and a tap, its entrance, and the state a notification gives its bot (`notificationState`). It is the one place an avatar moves from: every part has one channel there, and a renderer only draws what it says ([decision 0052](../decisions/0052-motion-follows-palco.md)). It is pure, and the functions a frame runs are worklets, so Android runs them on the UI thread. The springs it rides are the tokens' own, solved exactly by `springStep` beside them, which the web's frame loop uses too. The first run's steps and their order, who stands on its stage (`stageCast`), which set the stage has at each step (`stageScene`), how each bot is lit in it (`stageLight`), whose turn in the light it is while the cast says what it does (`workTurn`), what the first run's one line says the server is still getting ready (`gettingReady`, which folds `preparation`'s items: under way while any starts, downloads or installs, with one share of all of them while something downloads), where a first run left off starts again (`resumedStep`, `FirstRunProgress`) and who is new to the roster and gets an entrance (`rosterArrivals`) are decided there as well, so both clients agree.

**`packages/i18n`** is the translation catalog: every interface sentence in each language the contract lists (English and Brazilian Portuguese), where a sentence missing from a language, or a placeholder dropped from one, fails the typecheck. It also words notifications, so the server can write a push as the clients show one.

`client-runtime` imports nothing from a platform. Each app provides it, as services: the server's origin; a credential store (IndexedDB in the browser, the keychain or keystore on mobile, IndexedDB holding the token encrypted with the system's key on desktop); a small local store that keeps drafts and unsent messages across restarts; locks shared by the app's windows (the Web Locks API in a browser); a file uploader, which reports progress where the platform can; a source of network status; the device's time zone (`Intl` in a browser and the desktop app, the system's calendar on a phone), which the runtime gives the server on every socket; an HTTP client and a WebSocket constructor (`fetch` and the global `WebSocket`); and a secure random source. The runtime's HTTP client refuses every redirect: it asks `fetch` for `redirect: "error"`, so an answer that redirects fails the request and nothing is sent where it points. The server never redirects its own routes, and following a redirect from something in between would send a pairing code or a device token to another address, plain HTTP included. React Native's own `fetch` ignores that option and follows every redirect, so the mobile app gives the runtime `expo/fetch`, which honors it on Android and iOS (**Read** in Expo 58.0.23, `expo/src/winter/fetch` and its native modules). File uploads go through the platform's uploader. A browser's is `XMLHttpRequest`, for its progress, which cannot refuse a redirect, so the runtime takes an answer from another address as not the server's. The phone's is `expo/fetch` with `redirect: "error"`, like its other requests, and reports no progress: React Native's `XMLHttpRequest` has no way to refuse a redirect, and iOS's handler follows every one (**Read** in React Native 0.88.1, `Libraries/Network/XMLHttpRequest.js` and `Libraries/Network/RCTHTTPRequestHandler.mm`), and neither does Expo's upload task, whose options name none and whose Android client is React Native's OkHttp builder (**Read** in `expo-file-system` 58.0.14, `src/NetworkTasks.types.ts` and `FileSystemUploadTask.kt`). A file the phone uploads shows as uploading, without a percentage. The runtime exposes state as values a UI reads synchronously and watches with a listener, so any renderer can use it; React hooks over them live in `@j3-bots/client-runtime/react`.

The rule from T3 Code that J3 Bots adopts as is: **the UI stays dumb.** A component receives state and emits intent. If two clients need the same decision, the decision lives in `client-runtime`. The decisions a client makes before it draws (roster order, arrangement and search, which pairs of bots the roster and a bot's details list, timeline grouping and the runs of teammate messages it makes one line, message text, mentions (whom a draft addresses, the picks its field draws as chips, whose bot each mention in a message is), form edits, usage grouping, how a moment is formatted, how a cron expression reads) live in `@j3-bots/client-runtime/presentation`, free of any UI library. The sentences built from them that every client says the same way (a roster row's line, a notice, a delivery line, why a file cannot go, a time in words, who a room message goes to) are worded in `@j3-bots/client-runtime/wording`, from the catalog's sentences; the rest (schedules in words, the usage view) are still worded in the web app.

## Web

The reference client. It is served by the J3 Bots server itself, so pointing a browser at the server is enough to use J3 Bots.

- React with the React Compiler, TanStack Router, Tailwind CSS v4 with tokens as CSS variables.
- Component primitives on Base UI, in a local `components/ui` layer whose components own their look: callers pick a variant, they do not restyle.
- A virtualized conversation list that keeps the scroll position stable while messages stream in.
- **One frame loop** (`components/avatar/ticker.ts`) for everything that moves frame by frame: every avatar, and whatever travels on a spring it can be interrupted on (`lib/sprung.ts`), which is the first run's camera and the roster's rows. It runs only while something moves, reads layout before it writes, and writes transforms, `translate`, `scale` and SVG attributes, never a property that lays the page out. Fades, lights and text that arrives once are CSS, on the compositor. No component renders per frame: a frame writes to elements, not to React.
- **The first run** (`onboarding/`) is one stage (`Stage.tsx`) that stays mounted from the welcome to the arrival, over the steps' words, which swap under it. It is drawn in the dark appearance whatever the app's. The stage only says how each bot is lit (`data-light`, from the runtime's `stageLight`); the lights themselves are layers the stylesheet draws, a conic gradient for each cone, masks for its fall and its dust, a filter for the bot's rim, which cross over as opacities and filters ([decision 0065](../decisions/0065-the-first-run-tells-what-j3-bots-is-before-it-asks.md)). The component renders once a step, and once a turn while the light goes round, never per frame. One line under the steps says what the server is getting ready (`Preparing`), from the engine's status and, in the desktop app, from whether its own server has answered yet. What the operator typed and picked, and the step, are kept in the browser's `localStorage` (`progress.ts`, decoded with the runtime's schema) and dropped once the bot exists; nothing of it goes to the server. The gallery's first-run frames start at a given step and keep nothing. The gallery shows one section alone, or one frame of it, when its address asks (`/gallery?section=first-run&frame=…`, the frame by its label, and `&lang=pt-BR` for the language it starts in), so a state can be looked at, measured or captured with nothing else moving on the page.
- **The composer's field** is a `contenteditable` element in `plaintext-only` mode, so the browser never writes markup into it, holding the draft's text and, where each file stands, a chip that the browser treats as one uneditable character (`contenteditable="false"`), and over each pick of a member that counts, a chip for the whole of its text, uneditable too, so Backspace deletes it whole; React draws each chip into its place through a portal. Reading the field walks its nodes into the draft's text, a file's chip giving its mark and a mention's its text. The field is rebuilt only when the draft changed elsewhere, or when a pick starts or stops counting, so typing never moves the caret; while the keyboard composes text, a pick's change waits for the composition to end, which a rebuild would break. Paste, drop and the picker attach at the caret, a drop where it lands (`caretPositionFromPoint`), and the caret then follows the new chips. T3 Code's composer does the same with a Tiptap (ProseMirror) editor whose inline nodes are its file and terminal chips (**Read** at `c1464d67`, `apps/web/src/components/ComposerPromptEditor.tsx`); J3 Bots needs only text and chips, so it does without the editor.
- **Images** a file card, a chip or the viewer shows are fetched once with the device token and kept as object URLs, the 64 most recently shown, so a conversation scrolled back and forth fetches nothing twice.
- **Documents** (`components/documents`): a PDF, text, Markdown, CSV, Excel, Word or PowerPoint file in a message shows a preview in its card once the card comes into view, when it is at most 8 MiB, and opens in the document viewer, a Base UI dialog over everything with the image viewer's look, Save and Close. The bytes come through the runtime with the device's credential. Every format but PDF is read by `client-runtime/documents` in a worker of its own (`reader.worker.ts`), ended after its answer or 30 seconds, into the shared document model, which the page decodes and draws with its own components; long ones draw 200 blocks or rows at a time as the end nears. PDFs open in pdf.js, loaded only then, and each page is drawn to a canvas as it comes near the view and freed as it leaves it. The page keeps the last 8 documents read that nothing shows; one in a card in view or in the viewer stays. Each PDF opens in a worker of its own that the page starts for pdf.js, and that ends when the page lets go of the PDF or when it has not opened in 30 seconds. Limits and the safety of each step: [Security: documents](security.md#documents).
- **Routines in steps** (`components/RoutineTrack.tsx`): the Track, as the routine's change card, as its run card in the owner's conversation with the yes and a failure's one action, which answer with `routine.answer`, `routine.retry` and `routine.stopRun`, and at rest above a routine's runs, each run with its mini rail; the details show a routine's cast and sentence. The rail is SVG measured against the stations' rows; the light moves along it on `slide`, through the frame loop, and a finished run folds to one line a few seconds after it ends, at once with reduced motion ([decision 0052](../decisions/0052-motion-follows-palco.md)). The gallery (`gallery/`) shows every moment of a run.
- **Hidden conversations.** The roster's last row opens the hidden bots and rooms in its place, each with Show; a room's menu hides or shows it as a bot's does (`placeRoom`, which also pins), and a hidden bot's or room's details say so after Stop, with Show. New bot, a template's New bot, Edit bot and the room form carry the "Hide from the list" switch.
- Installable as a PWA, which gives phone users a working client before the native app exists.
- Bot templates. Share as template, in a bot's details and under More in its roster menu, opens a sheet with everything the file holds, then downloads it (`<name>.j3bot`, of the template's media type) or copies its text. New bot from a template, in the roster's new menu, opens the browser's file picker; a single `.j3bot` file dropped anywhere on the window opens the same preview, and a drop of anything else is let go rather than opened by the browser. The desktop app, which renders this client, does the same.
- **Secrets**, in Settings: the operator's secrets, each with its name, the reference bots use it by (`secret:<name>`), whether it is a login with its sites or a single value, the bots that may use it and where one last did; Add a secret; and, on a secret, its values hidden until Show, its code now, Edit and Delete. A value shown goes after 30 seconds, when Settings closes, or when the page is hidden. Copy in the desktop app goes through its main process, which takes the value off the clipboard 30 seconds later if the clipboard still holds it; whatever the operator copied since stays. Electron reads the clipboard only asynchronously, so an app that quits before then leaves the value there. The desktop app and the Android app share that logic (`client-runtime`'s `secretClipboard`). A browser does not let the page read the clipboard back without asking, so there a copied value stays until something else is copied. With no bot yet, the bots that may use a secret say that no bot can use it, under the switch for every bot. While the secrets cannot be used the section says why instead, from the server's state: an old vault offers its password once, in place, with what a forgotten one means; a missing or other key file, or a newer server's secrets, says what to do. A bot's ask for a secret is a card in its conversation (`SecretAskCard`): a login's site, as the bot gave it, then its masked fields, or one masked value; a switch to let every bot use it, the bot that asked always may; Save and Decline; and, once it closes, what became of it (saved under its reference, declined, or expired). A login's fill shows in the turn's work fold: the login and the field, then the page's origin where it was filled, or in the blocked tone why it was not (the reason the server gives, the page's origin as the server checked it, a lookalike as its punycode) or that the secrets could not be used. Its wording is `client-runtime`'s (`stepText`, `fillDetail`), which the Android app shows the same way.
- **MCP and skills**, in Settings (the connectors home, named for what people search for): what the bots added, the connectors and then the skills, with no form to add either and no gallery to browse ([decision 0068](../decisions/0068-settings-lists-what-the-bots-added.md)). Each connector's row has its status and, once its server answered, what it said of itself on one line, the revision it speaks and how many tools, resources and prompts it lists (`serverText` in `client-runtime`). The skills leave out J3 Bots' own (`skillGroups` in `client-runtime`). With none of either, one line says to ask a bot. A connector's page lists its tools as its server lists them; there is nothing to accept. A command connector's page changes its command line after the confirmation (`commandEdit` and `commandConsent` in `client-runtime`).
- **The `/` menu.** In a bot's conversation, a draft that is `/` and a word opens a list of the prompts the bot's connectors offer that match it, read with `connector.prompts` each time the `/` is typed, since a server can change them. Up, Down, Enter and Escape move, pick and close it, as the mention menu does (`usePromptPicker` in `components/PromptPicker.tsx`). A prompt with arguments opens a short form above the field; Use prompt has its server write it (`connector.renderPrompt`) and the text replaces the draft, to read and send as the operator's own, with a line when it was cut to the draft's length. Rooms have none. Matching and the arguments' check are `client-runtime`'s (`promptOptions`, `promptArguments`), which the Android app shares.
- **A bot's ask to add a connector** (`connector-ask`) is a card in the bot's conversation (`ConnectorAskCard`). For an address in the operator's own network, one sentence names the bot and the address's host, with Allow and Decline. For a gallery entry that needs the operator's own app, it reads the entry's setup with `connectors.get`, in the interface's language: its steps, a button to the page they start at, and the address its sign-ins return to, the server's own when the browser returns there and this device's loopback otherwise, to copy; then the client ID and the masked client secret, checked before Allow (`ownAppClient` in `client-runtime`), and a line that the bot never sees them. The client is sent redacted with `card.answer`, and kept nowhere on the device. Closed, it says how: added, declined, failed (the bot was told why), or closed with no answer. The Android app shows the same card.
- **A service's question** (`connector-input`) is a card in the bot's conversation: a form with its server's fields, checked before Send, or a page named by its host with Open, which opens it and accepts, since the server waits on the page; Decline and Not now beside them. It says the answer goes to the service only. Answered or expired, it says which.
- Browser notifications, through the service worker where one is active and from the page otherwise. The browser's permission is asked for only when the operator presses "Allow notifications in this browser" in Settings, never on load. A notification carries the pairing that received it. A click focuses a window of the app, the focused one first, or opens one at the app's root when none is open, and that window opens the conversation or room the notification is about only if it follows that pairing and the roster lists it, hidden bots included; a click that arrives before the roster loaded waits for it. Settings, the details and any dialog over it close, a save under way carries on, and the profile in Settings keeps what the operator typed. New bot holding a name, and the bot editor or the memory viewer holding an edit not saved yet, stay open, with the conversation opened under them and focus kept in them, so the click never throws typing away or sends it to the conversation, and closing the dialog lands on what the notification was about; one holding nothing closes like any dialog. When a pairing a window followed ends, here or in another tab, the window closes every notification that pairing received, and only those, so signing out or a revocation takes the bots' names and words off the screen while a newer pairing keeps what it showed; a notification whose pairing ends while the browser is still showing it is closed once shown. The first pairing a window knows also closes every notification another pairing received, so a window closed before it finished closing them leaves them only until the app next starts. A notification shows only while the browser's permission, read again as it arrives, allows it, and Settings reads the permission again when the operator comes back to the page, since not every browser reports a change made in its site settings. Every window shows the server's notifications, tagged by entry, so the browser keeps one per entry. Its icon is the still avatar of what it is about, a 192 px PNG in the theme the system is in as it shows, drawn by the rasterizer, which is not part of the app's start: a paired page with notifications allowed fetches it once it has started, so a page left open across a server upgrade already holds it; the app's icon stands in when there is no avatar to draw or the fetch failed. Chrome shows the icon in an 80 px square (**Read**: `kNotificationIconSize` in Chromium's `ui/message_center/public/cpp/message_center_constants.h`), and the systems that show it themselves give it about as much or less (**Assumed**), never as little as the 28 px below which an avatar draws its mark larger, so the image is drawn with the proportions of its own size. Drawing one takes about 20 ms in Chromium, once per notification, so nothing is cached. Browsers offer notifications only in a secure context, so a page served over plain HTTP on the local network gets none, and Settings says so; Safari on iPhone and iPad offers them only to the app added to the Home Screen, and Settings says that too. Some mobile browsers (Android's) show a notification only through a service worker (**Assumed**: not yet observed on a device).

## Desktop

An Electron shell around the web client ([decision 0012](../decisions/0012-desktop-reaches-the-server-directly.md)).

- **Its own build of the web client.** The window loads the built client from a privileged custom scheme, `j3bots://app` (`j3bots-dev://app` in development; both names are placeholders until the app's name and ids are settled), never from a dev server, a `file://` path or the server. The scheme serves only that build's files: a path outside it, or one of the server's routes, is refused, and a route without a file gets `index.html` for the client's own routing. The page is a secure context, so Web Locks, WebCrypto and notifications work as on an HTTPS origin, whatever the server is served over.
- **Where the bots live.** Where the app can run J3 Bots itself, its first screen asks where the bots live ([this computer or a server](../product/concepts.md#where-the-bots-live)). "Use this computer" goes straight into the first run: the page signs the computer in by itself, the first time only, and the first run goes on while J3 Bots starts, only the first bot waiting for it to run. "Connect to a server" goes on to the server's address, with a way back. Elsewhere the server's address is the first screen. Settings changes it both ways.
- **A server the operator names.** For a server, the app asks for its address before pairing. The main process checks it (an answer from `/api/server` that decodes as a J3 Bots server; a redirect is refused, not followed) and keeps it in the app's settings. An address without a scheme is HTTP for a loopback or private IP literal or `localhost`, and HTTPS otherwise; plain HTTP to any other host is refused, and a saved server is held to the same rule when the app starts, or dropped. The rule is `parseServerAddress` in `client-runtime`, which the mobile app uses too.
- **Changing server.** The pairing screen and Settings show the server with a way to change it, and so do the screens before the first roster (connecting, no bots yet), where a server that moved leaves the app, and the screen for a server of another protocol version, which tells the operator to update the app or the server so they match: the app carries its own page, so reloading only helps once one of them is updated. Under that screen, and under the pairing form when pairing fails for the same reason, the app shows its update whenever it checks for one, so an app installed older than its server reaches a newer version without opening Settings. Changing server forgets this device's pairing here: the page's IndexedDB (credential, drafts, unsent messages) is emptied, its preferences stay, and the app opens its first page, the server address screen. The device stays listed on the old server until it is removed from another device. A device token never reaches another server by construction: the credential is stored with the origin of the server that issued it and is absent for any other, the app empties that storage again right before it keeps a new server, and it keeps one only once it is written to its settings, one choice at a time.
- **The server at its own origin.** The custom scheme serves the app's own files and forwards nothing. The page calls the server with ordinary HTTP (`fetch`), `XMLHttpRequest` for uploads and WebSockets exactly as a browser does, and the server answers CORS for the app's origins.
- **The bots on this computer ("local mode").** On Linux x64 and Windows x64 the operator can have the app run the server itself instead of naming one; Apple silicon only with `J3_EXPERIMENTAL_LOCAL_MODE=1` until a Mac has run it. The server is a supervised child of the app ([decision 0024](../decisions/0024-the-local-server-is-a-supervised-child-of-the-app.md)), in `apps/desktop/src/localServer/`:
  - **Its runtime.** The package carries the release's own Node and server bundle in `resources/server-runtime` (a development build takes the one `node scripts/build-release.ts --server-runtime` writes to `dist/release/server-runtime/<platform>-<arch>`). It never runs from there: each version is copied to `<userData>/server-runtime/<version>/`, through a temporary folder renamed into place once whole. On Windows the server runs from `<userData>/server-runtime/current/`, swapped by rename when the version changes, so the firewall, which remembers an executable by its path, asks once.
  - **Its version.** Each start asks the home's record which release may start (`decideStart`, [decision 0016](../decisions/0016-an-update-keeps-a-snapshot-to-roll-back-to.md)), and the app is that core's second host, beside `j3-bots update`. Its main process runs the core (`@j3-bots/server/transition`) inside the supervisor's start, so Quit waits for it. A new release in the package starts through a transition: a snapshot, the old server stopped, the new one started from its runtime and awaited, and a rollback to the old one, from the runtime it kept, if the new one never gets ready. Only once the new one runs are the runtimes of other releases removed, keeping the two it moved between. The release it rolled back from is not started again until the person asks (`retryServerUpdate`), and the release the data was handed to runs while the app is older. The page learns of each through the local server's state (`update`: `updating`, `rolled-back`, `older-app`), and its connection line says so, with Try again and the details of a rollback the app saw.
  - **Its home and ports.** `J3_HOME` is `<userData>/server/home`, the app's own, apart from a server installed from the command line. Before it starts the server, the app checks that the home is a folder only this user can open, and so are the folders in it where the harnesses keep their sign-ins (`providers` and each provider's home in it), as the server checks them at its own start, so the app never starts a server that then refuses its home: owner and mode bits on Unix, and on Windows its access list, read and judged by the server's own code ([Security](security.md#j3-bots-own-surface)). A home that fails is refused with why and what repairs it: a `chmod` or `chown` command on Unix, and on Windows an `icacls` command to run in PowerShell, which also removes any rule that denies the user, with the path in single quotes so that nothing in it is expanded. A list that cannot be read is refused too, with how to take the folder as the user should Windows have denied access to it, and so is a home the system would not show, which is never taken for missing. When "Use this computer" finds the home refused, nothing changes: the first screen shows that the bots could not start, with the reason, the fix and Try again, which checks the home again, and Settings shows the reason and the fix under its button. A refusal at a later start shows as any refused start does. A missing home is created private: mode 0700 on Unix, and on Windows with its list in place from the first moment, as the server creates its own. One another process made after the app looked is left as that process made it, and checked before anything is written into it. (**Verified** on Windows 11 x64, packaged: a fresh install started its server and a bot answered, the server came back on the same home after Quit, and a home opened to the Users group was refused with its repair until the repair ran.) When the operator chooses this computer, it writes the home's `config.json`: loopback, and three ports, the lowest free on `127.0.0.1` from 3747 on. It tries each port on loopback only, where the server will listen: a trial listen on every address would make Windows Firewall ask about the app (**Assumed**: Windows 11 asked once about the app while it tried every address. **Verified** on Windows 11 x64, packaged, with a new profile and no firewall rule for the app: trying loopback only, no prompt showed and no rule was added). The file is never rewritten, so the origin the page signed in to stays, and one the app cannot read is refused, never replaced. Every start reads it first: one that went missing is written again with the port the page is kept on, rather than left to the server's defaults (3737), and one that sets another port is refused with how to repair it, since the page would not find the server there.
  - **How it starts.** The main process spawns `node server/bin.mjs serve --admin-fd 3 --exit-with-stdin` with its stdin a pipe (the lifeline), its stdout and stderr the log file, fd 3 an overlapped pipe (the admin channel), `J3_HOST` (`127.0.0.1`, or `lan` while phones may reach it, below), `J3_WEB_CLIENT` (the app's own build of the web client, which the package carries outside its asar in `resources/web/dist`: the runtime has none, and a phone that opens the pairing link is served this one. A packaged app gives the server a copy of it, `<userData>/server/web`, made again only for another release, beside the one there and renamed over it, never the package's own folder: an AppImage's mount goes as the app exits, and a later run may take over the server it started), and an environment without the app's own (`ELECTRON_*`, `NODE_*` but `NODE_EXTRA_CA_CERTS`, the certificates the operator trusts for a proxy, `J3_*`, `npm_*`, an AppImage's variables). Its `PATH` is the one a new terminal of the operator's would have, so it finds `claude` and `codex`, and `provider.harnesses` reports where, for the app's sign-in buttons: an interactive login shell prints it between two markers, or on Windows PowerShell with the operator's profile and without it, then the folders where the harnesses' installers put them, then the app's own (re-implemented from T3 Code's `apps/desktop/src/shell/DesktopShellEnvironment.ts`, **Read** at `bc0f04d`, MIT). Nothing in it needs a `node` on the operator's `PATH`.
  - **How it is kept running.** The app reads the server's `/status` on the inherited pipe, which answers once it serves, and counts it ready when the status names the child's own pid. A server that stops on its own is started again after 1 s, then 2, 4 and so on up to 30 s; a minute of running counts the next stop as the first again. A start the server refused (exit status 78: a home others can open, a configuration this release refuses or cannot read, a database a newer release migrated, a port in its configuration that another program holds) is never started again by itself: the tray and the page show its message until the operator tries again. A home another server still holds is no refusal: that server may be the one a crashed run left, still stopping, so the start is tried again after the pause, and passes once it has stopped. A server an earlier run left behind is taken over when it is the release a start would run as it is, with no update due (Unix, through the home's `admin.sock`, trusted because only this user can open the home) and stopped otherwise. Its pid comes from its status, and the app signals it only while that pid is still the process that started then, by its start time (`/proc/<pid>/stat` on Linux, `ps -o lstart=` on macOS), so a pid the system gave to another program is never signalled; on Windows, where no `admin.sock` is bound, the app records the pid of each server it starts with that process's start time, as Windows records it, and ends the process by its tree only while the process with that pid started then, checked in one PowerShell command that holds a handle to it. A server whose start Windows did not say is not recorded, and is left to stop by itself.
  - **How it stops.** Quit, from the tray, the menu or the system, is held while the server stops: the app asks it on the pipe (`/shutdown`), or sends SIGTERM where that fails, and kills it 30 s after the stop began, however long the asking took. A server still starting on Windows, which the app cannot ask (its pipe is read only once it serves) and has no signal for, is killed at once. The short commands the app runs to read the system (the login shell's `PATH`, a process's executable or start) are ended by their deadline, SIGTERM then SIGKILL 2 s later, so none can hold Quit up. An update stops it before it installs, and starts it again if the install fails. If the app dies, the server's stdin ends and it stops itself. Waking from sleep reads its status, and a server that does not answer is killed and started again.
  - **Its output.** Everything the server writes goes to `<userData>/server/server.log`, moved to `server.log.1` past 10 MB, and the last 8 KB it wrote travel with its state to the page and the tray. The server writes to the file itself, never through the app, so a server whose app died still logs, and stops its engine, as it stops.
  - **Signing in.** The page signs in with no pairing code: the main process asks the server on the pipe for a device (`/local-device`, named after the computer), once `/status` names the child's pid and the port the settings name, and hands the page its id, token and the server's origin, through a bridge call only the top frame may make. The page seals and keeps the token as after pairing; the app keeps only the device's id. The server signs this computer in as one device at a time: each device it mints on the admin channel revokes, in the same transaction, those it minted there before and the one the app names, so a device whose id the app could not keep is not left signed in. A device revoked from another device is never signed in again silently: the page says to sign in again on this computer, and only the operator's click mints a new one.
  - **Moving the bots to another server.** Settings → Where your bots live → "Move to another server" exports them for `j3-bots import` on a server ([decision 0062](../decisions/0062-a-home-moves-as-an-export.md)). The page asks for the export's passphrase, twice, at least eight characters, and says it cannot be recovered; the main process asks where to save the file, with the system's save dialog, offering a name with the minute in it, and refuses, before anything stops, a file that is already there and one in the bots' home, which deleting their data would delete too, a folder reached through a link or a junction included (`exportLocal`, `serverChoice.ts`'s `moveAway`). It stops the server, then runs the export of the release that would start next, from its runtime, as the server's own command (`apps/desktop/src/localServer/exportProcess.ts`): `export --output <file> --passphrase-stdin --report <report>` on the home, the passphrase the first line of its stdin, under the transition lock an update takes, so neither runs while the other does (`VersionTransition.forExport`). An update that was cut off is not exported from: the operator opens the bots here once, which finishes it. The passphrase never reaches the command line, the environment, a file or a log. Quit, and an update's restart, wait for a move under way to end, its export kept or undone, as they wait for the server to stop: an export never outlives the app that keeps that it was written. An export that fails, or whose report cannot be read, starts the server again and the page says why, in the export's own words when it gave them; an archive with no report is removed. Once the file is written, the app keeps that the bots moved in its settings (`moved`: the file, when, and what the report says it left out: the secrets and why, links, files whose name an import would refuse, the first twenty of them by path, attachments already missing), and the page opens on a screen that says so, with what was left out and what to do on the new server. From then on the server does not start, not even as the app starts, and nothing that would start it (Try again, an update's retry or a failed install, phone access, choosing this computer again on the first screen, which opens this screen instead) does, and closing the window quits the app, with nothing left to keep running in the tray, until the operator chooses one of:
    - **Connect to the new server**, which turns "Start with the system" off and goes on to the server address screen. The data stays, and Settings, on that server, says the bots moved from this computer left it here, with a way to delete it.
    - **Run the bots here again**, which asks first, then forgets the move and starts the server on the data it kept.
    - **Delete the data on this computer**, which asks first, saying the export is the only copy until the new server runs them and, when the export left the secrets out, that deleting loses them. It deletes the home, the server's log and its pid file, and forgets this computer's device and the move, and, while the bots lived here, the choice of where they live, so the app opens on its first screen.
  - **Phones on the same network.** Settings → "Use from your phone" lets phones on this computer's network reach the server ([decision 0036](../decisions/0036-phone-access-restarts-the-local-server-on-the-network.md)). The choice is kept in the app's settings (`phoneAccess`, off unless the operator turns it on, and off again when they connect to a server instead), and `apps/desktop/src/localServer/phoneAccess.ts` decides, at each start the supervisor makes, where the server listens: `127.0.0.1` while it is off; `lan`, the server's own setting, while it is on. Changing it starts the server again through the supervisor's one start path, with an update's transition if one is due; when the admin channel's `/running-work` counts bots with work running, or cannot be asked, the page asks first ("Restart your bots?", saying the bots may be working when the count is unknown) and only the operator's yes stops that work. The count is asked again right before the stop, in one step with the changes of where the bots live: work that started after the operator was asked is not stopped, and once the bots live elsewhere the choice is not kept. Each time the server answers, where it listens is compared with where the choice puts it now; a server that listens elsewhere, as one an earlier run of the app left running or one started while the choice changed, is started again where it should, once `/running-work` counts no bot working there: no one chose to stop that work, so the restart waits for it, asking again every 15 seconds, while the server keeps serving where it is. Devices paired over the network stay paired while it is off, and reach the server again, without pairing, once it is back on.
    - **What holds.** While a non-internal interface has a public IPv4 address, `lan` would listen there too and the server would refuse it, so the app starts the server on `127.0.0.1` and says why. A start on `lan` that ends without the server answering (a port the network side cannot have, a refusal) is followed at once by one on `127.0.0.1`, so the app is never left without its server, and the page shows what the server said until the operator tries again; when a public address appeared meanwhile, it says that instead. Once the server answers on `lan`, its `/status` names the origins another device reaches it at (`origins`, as `j3-bots pair` lists them). A phone is given only the server's own private interface origins among them, never its `publicOrigin`, which names a way in set up for elsewhere, and Settings shows the first. With none (no Wi-Fi, no cable), it says so. While the server failed, and nothing starts it until the operator tries it again, it says the bots stopped rather than that it is turning on; the server's own failure shows its reason and Try again.
    - **The network is not watched.** It is read at each start, each change of the choice, each Try again, as the page shows Settings or asks for a code, and as the system wakes; the addresses shown follow then. A public address that appears in between is refused by the server itself: its listener stays bound on every interface, and it checks each new connection's destination address, closing one that reached an address outside the private ranges ([Security](security.md#j3-bots-own-surface)).
    - **Pairing a phone.** "Pair a phone" asks the server on the admin channel for a code (`/pairing`) and shows it as a QR code of the pairing link at the first private origin, `<origin>/pair#<code>`, with the address and the code typed out, how long it still works and a way to pick another address when the server has several. A phone's camera opens the link in its browser, where the server serves the app's web client, and the Android app's scanner reads it too. The page is never given a device token for it: the phone pairs over the network as any device does. While wrong codes lock pairing, the page says until when and offers to lift the lock (`/pairing/unlock`) and show a code at once, as `j3-bots pair --unlock` does. With phone access off, or the server on `127.0.0.1`, no code is made.
    - **The firewall.** While phones reach it, Settings says what the system's firewall may need: Windows asks whether to allow public and private networks to access "Node.js JavaScript Runtime", the server's `node.exe`, which it blocks until the operator chooses Allow, and macOS whether it may accept incoming connections; on Linux, ufw drops a phone's connections without asking, so Settings gives `sudo ufw allow <port>/tcp` to copy ([Reaching J3 Bots from elsewhere](../operations/exposing.md#from-the-desktop-app)). The tray says "Phone access on" while phones reach the server. **Verified** on Linux x64 (a boat VM, the packaged AppImage, X11 with an XEmbed tray): turned on, the server listened on `0.0.0.0` and Settings showed the VM's private address; the Android emulator's Chrome opened the pairing link, paired, and got a bot's answer; a request for another `Host` got `403`; turned off, the server listened on `127.0.0.1` only, the phone could not reach it and the desktop kept working; turned on again, the phone sent and got an answer without pairing again; with a bot working, the switch asked first; and the app started again on `lan` after a restart. **Verified** on Windows 11 x64 (a VM, the packaged NSIS install): turned on, the server listened on `0.0.0.0`, Windows Defender Firewall asked about "Node.js JavaScript Runtime" and, on Allow, let it in on the Private profile only; Settings showed "On at" the VM's private address and "Pair a phone" its QR code, and another machine on that network paired with the code and was refused for another `Host`. **Assumed**: macOS, where local mode is not offered yet.
  - **The window and the tray.** In local mode closing the window hides it to the tray, which says how the server stands, so the bots keep running; Quit ends both. Connecting to a server instead stops the local one. **Verified** packaged on Linux x64 (X11, an XEmbed tray host) and Windows 11 x64: with the server ended again as it came back, the tray's menu said "Bots stopped · restarting in 4 s" (Linux) and "… in 30 s" (Windows), and "Nothing needs you" once it ran again.
- **A narrow bridge.** The page reaches the main process only through a preload script that exposes the current server, connecting to a server and forgetting it, sealing and opening the device token, the network status and the system's wake from sleep, restarting the app, showing a notification and closing a pairing's notifications, the clicks on them, the links to the app the operator follows, and, for updates, the update's status and its changes, a check, the restart into an update, the choice of channel and a report of whether a save is under way, and, for the menus and the tray, the page's language, what needs the operator, the commands the menus and the tray give the page, the global shortcut's status and a change to it, and, for quick access, whether its page has a bot to show, the cue to come in or go out and what it read of the window in front, hiding its window, opening the main window at a bot's conversation and a picture of that window, what quick access reads (the window's title, a picture on every message) and a change to it, and the ask for macOS's Screen Recording, and, for the bots on this computer, whether phones reach them, its changes, turning it on or off and a pairing code for a phone, and moving them to another server, running them here again and deleting their data. Both sides decode every message with the schemas in `packages/desktop-bridge`, and the main process acts only on calls from the app's own top frame.
- **The device credential.** It is kept in the page's IndexedDB, in the same database as the drafts and the outbox, so a write's pairing check reads it in the same transaction, as in a browser. The device id and the issuing server's origin are stored in the clear for that check; the token only as the main process sealed it with Electron's `safeStorage` (the Keychain on macOS, DPAPI on Windows, a secret service on Linux), in a payload of its own that is read back only if it decodes, with how it was sealed. The sealed token is held to base64's canonical form, never empty, by the page as it reads the record and by the main process as it is asked to open one: a lenient decoder reads a value such as `A` as no bytes, which the system opens without an error. A stored value that is not a record of this server (no record, one of another server, one whose device id or server is not readable) reads as not paired. A record of this server whose sealed token is missing or not in that form is damaged storage, never a missing pairing. Otherwise opening it ends one of three ways. It opens. It decrypts to something the app did not seal (a damaged ciphertext, another profile's): that reads as not paired, like a record of another server, and the app shows the pairing screen. Or it is not opened: the system's encryption is not available, the system refuses (as while a keyring is locked, or for a key it no longer has), or the main process gives no answer within 60 seconds, long enough for the system to ask the operator to unlock a keyring, and for Chromium to give up on one that does not answer (**Verified** on Linux, Electron 44.10.1, under `xvfb-run` on a desktop session whose GNOME Keyring was locked: the first seal took 24 s before Chromium fell back to its built-in key). Of a record of this server, only a payload the system opened that is not the app's reads as not paired; a damaged record, or one not opened, is not taken for a missing pairing, which would lead the operator to pair again and leave the old pairing's drafts and unsent messages to be deleted. The app says it cannot read this device's sign-in, keeps the pairing and what is kept for it, and offers to restart the app or to change server. Trying again in the same process would not help: Chromium sets up the system's encryption once per process and keeps it (**Read** in Chromium 152.0.7977.169, the one Electron 44.10.1 ships, `components/os_crypt/async/browser/os_crypt_async.cc`), so a keyring unlocked later is seen only by a new process. For the same reason the page asks the main process to open a stored value once for as long as it stays the stored value, and every later read shares that answer: the client's start reads the credential more than once, and waits for the main process once, 60 seconds at most. The restart quits as closing the window does, so its place is saved, and keeps IndexedDB (**Verified** on Linux, Electron 44.10.1, under `xvfb-run`: the app exits with 0, its window's place is in its settings, and a new instance starts with the same arguments). An AppImage restarts as it does into an update (see Updates below), because Electron's relaunch does not restart one. Signing out deletes the stored record if its device id, read in the clear, is still the pairing being signed out, in the transaction that deletes it; it opens nothing, so it works with a keyring locked since. As in a browser, the record can also be the word that the server refused a pairing, left in the credential's place by the tab that heard it ([Clients: pairing](#pairing)): it holds the pairing's device id and nothing secret, and reads as not paired. **Verified** on Linux, Electron 44.10.1, under `xvfb-run` with no unlocked keyring (the smoke): pairing survives a restart, the stored record holds only the sealed token, the sealed form is found in the profile's files and the token in none of them, a record the system refuses (not sealed by it) shows the screen that says the sign-in cannot be read, and one with a byte changed in the first block of its ciphertext shows the pairing screen.
- **Linux with no keyring.** The app seals and opens only while `safeStorage.isAsyncEncryptionAvailable()` says it can; where it cannot, a save fails rather than store the token as it is. A save that fails as the device pairs comes after the server spent the code and listed the device, so the pairing form says to unlock the system's keychain or keyring, offers to restart the app, and asks for a new code. On Linux with no secret service the app can use, `safeStorage` still seals, with a key built into Chromium, which only obscures the token; what it seals that way begins with Chromium's version `v10`. The app counts a token as `encrypted` on Linux only when it begins with a keyring's version, `v11` (the Secret Service: GNOME Keyring, KWallet) or `v12` (the Secret Portal), and as `unencrypted` otherwise, `v10` and any version it does not know included, so the notice errs on the side of showing (**Read** in Chromium 152.0.7977.169, `components/os_crypt/async/browser/`: `posix_key_provider.cc`, `freedesktop_secret_key_provider.cc`, `secret_portal_key_provider.h`). The app pairs anyway rather than refuse, and Settings → Devices, under This device, says that the sign-in is stored without encryption, with the dot on Devices in Settings' list, as long as the record on disk says so, and that pairing the device again once a keychain or keyring is unlocked stores it encrypted. The app never seals a stored token again: IndexedDB's LevelDB files can keep the earlier, obscured copy of the same token in their log and tables after the record is replaced, so a token once stored obscured stays readable from the profile until it stops working. Only a new pairing, which issues a new token, ends that, and only then does the notice go. **Verified** on Ubuntu with Electron 44.10.1, with no unlocked keyring, whether Electron picks `basic_text` or `gnome_libsecret`: `isAsyncEncryptionAvailable()` is true while `isEncryptionAvailable()` is false, so the first cannot tell how a token is kept; what `encryptStringAsync` seals begins with `v10`; `decryptStringAsync` opens it; a ciphertext without Chromium's prefix rejects; the notice shows (the smoke). **Assumed**: with an unlocked keyring, `safeStorage` seals with the keyring's key under another version; that macOS and Windows always encrypt (not measured).
- **Network status** comes from the main process (`net.isOnline`), asked again on each of the page's `online` and `offline` events, and is sent to the page as the system wakes from sleep (`powerMonitor` `resume`), so the client tries the server at once instead of when its backoff ends.
- **Locked down as T3 Code's shell is, and further** (**Read** at `bc0f04d`, `apps/desktop/src/window/DesktopWindow.ts`): context isolation, the renderer sandbox and no Node integration, as T3 Code's window has, and no `<webview>`, which T3 Code's window allows for its preview pane. The window never navigates away from the app; an `http:`, `https:` or `mailto:` link opens in the system's handler, anything else nowhere. A Content Security Policy allows scripts from the app only (its inline scripts by hash) and connections only to the app and the named server. Only notifications and clipboard writes are granted. One instance runs per profile; a second launch brings the first window forward, or focuses it as it first shows when the app is still starting, and hands over the link it was started with, if any. The window's size, place and maximized state are kept and restored onto the display it overlaps most, moved and shrunk to that display's work area so its title bar is always in reach.
- **Files.** An upload goes as in a browser: `XMLHttpRequest` from the page to the server's attachments route, with the device token, reporting progress as the body goes; the composer removing a file aborts it. Nothing of it passes through the main process. The Content Security Policy's `connect-src` holds it, as every request of the page, to the named server (a redirect included, **Assumed** from the CSP specification, which checks each one), and the client takes an answer only from the server's attachments route. **Verified** on Linux, Electron 44.10.1, under `xvfb-run`, with the page on `j3bots-dev://app` and the server's testing layer on a plain-HTTP loopback origin, upload throttled to 4 MiB/s with the DevTools protocol: the server answered the preflight from `Origin: j3bots-dev://app` with 204; a 25 MiB file, the largest a message carries, showed its progress rise from 0 to 100 % in the composer over about 7 s and arrived whole (26,214,400 bytes, identical); a second one, removed at 25 %, was cancelled (`net::ERR_ABORTED`) and never answered. An attachment the operator opens is saved, not shown in a window: the app opens no window but its own. Electron's default download handling asks where to save it (**Assumed**).
- **Notifications are the system's own.** The page decides what to show exactly as the web does (the runtime's pairing check, the permission and what is in view), and hands each notification to the main process instead of showing it, so that a click can restore a minimized window and bring it forward: the entry it is about, the title and body worded by `packages/i18n`, the still avatar as a 192 px PNG in the theme the system is in, the conversation or room it is about, and the pairing that received it. The main process decodes it (an icon must begin with PNG's signature and its header, declare at most 192 px each way, and stay under 1 MiB, so a small file cannot make the main process, which has no sandbox, decode an image of gigabytes), takes it only from the app's top frame, and shows it with Electron's `Notification`, one per entry, a newer one replacing it; an icon that does not decode leaves the app's. A click closes it, restores, shows and focuses the window, and hands the page what it was about and its pairing, and the page opens it under the web's rules (`notificationOpening`), only while it still follows that pairing and the roster lists what it is about. A notification has no actions: only a click opens it, since approving from one would grant without the exact command in view, which the approval card exists to show. When a pairing ends, the page tells the main process, which closes everything that pairing received; a notification sent just before is closed too, since the two requests travel in order, and the page sends none after it. Every notification also closes when another page loads in the window (a reload, or the server forgotten; a navigation the window refuses changes nothing) and when the app quits, since only that page knows when its pairing ends and a click could open nothing once it is gone; with no service worker, none outlives the app. **Verified** on Linux, Electron 44.10.1, with the development build under a headless GNOME Shell 50.1 through Xwayland, against a server on loopback with the scripted agent: a bot's message with its conversation on screen in the focused window showed nothing; with the window minimized, another window focused and another conversation open in the app, GNOME showed a banner with the bot's name and its still avatar; activating it, as a click does, restored and focused the window on that bot's conversation; and a notification still showing closed as the device signed out. Under the test driver the page kept reporting focus and visibility after the window was minimized, so the conversation was out of view through the other conversation being open, not through the window's state alone. **Assumed**: the same on macOS and Windows, and on a native Wayland session (Ubuntu's default GNOME), where Electron may run without Xwayland and GNOME can refuse focus to a window that asks without an activation token, showing that the app is ready instead; none of these run yet.
- **A connector's sign-in comes back to the app.** When the page starts a sign-in, the main process listens on a free port of `127.0.0.1` for that one sign-in, and the server sends the browser back to `http://127.0.0.1:<port>/oauth/callback/<issuer>`, a path of each authorization server's own: its host, then its path, as `/oauth/callback/accounts.google.com`. Once the server answers, and before the browser opens the sign-in, the page tells the listener the `state` in the address it is about to open. The listener takes only a `GET` to a path under `/oauth/callback/` whose next segment is a host and that a URL parser reads as written (no `..`, `.` or backslash), that names the listener by that address (so a page that reached the port under another name, by DNS rebinding, is turned away) and carries that `state`, compared in a time that depends only on its length. Anything else, a return with another `state` or one that came before the page told it, gets an error and changes nothing: the listener waits on, the page hears nothing and the window stays where it was, so a process or a page that reaches the port first cannot spend the sign-in. The browser is shown a page without script that says the app takes it from here, the app comes forward, and the address the browser came back to goes to the page, which hands it to the server with `connector.completeSignIn` as a redacted value and keeps none of it. The listener closes once it has the address, when the page cancels or goes away (a page that goes away while the app opens the listener, or while the server starts the sign-in, closes it as soon as it opens and opens no browser), or after ten minutes, when the sign-in expires. The page names the listener by its port to tell it the `state` or to close it, so an earlier sign-in never closes a later one's.
- **Links to the app.** `j3bots://bot/<id>` opens that bot's conversation, `j3bots://room/<id>` that room, and `j3bots://pair?server=<origin>&code=<code>` fills in pairing. A development build takes `j3bots-dev:` links instead, so the two never take each other's. The main process decodes a link with `AppLinkUrl` in `packages/desktop-bridge`: an id is one percent-encoded path segment (a final `/` allowed), a server is an `http:` or `https:` origin, and a code is read as a typed one is (`normalizePairingCode`). Anything else opens nothing: another host, a path beyond the id, a query on a bot or room link, a fragment, a missing, repeated or unknown parameter. - **Updates.** electron-updater 6.8.9 checks the newest published release on the app's channel at launch and every six hours ([Security: desktop updates](security.md#desktop-updates)). A check that could not reach the release, as one at a launch before the network is up, is tried again a minute later, then five and thirty minutes after that, and at once when the system wakes from sleep (`RETRY_AFTER` in `updater.ts`); a download that did not match or an install that failed is not, since it would fail the same way. Settings → About and updates shows the app's version, where its update stands, its channel and, where the build installs updates, "Update automatically". How a build updates depends on what it can replace as the operator's user:
  - **The channel.** Stable or Nightly, kept in the app's settings (`updateChannel`, stable at first) and changed only while nothing is downloading, being checked or installing. Before each check the app picks the release itself, by the policy the server's feed follows (`newestOn` in `@j3-bots/release`): Stable takes GitHub's `releases/latest`, Nightly the newest of the stable releases and the nightly builds among the newest 30 (`releases?per_page=30`), a release candidate on neither. It then points electron-updater at that release's own folder, where it reads its default feed file, `latest*.yml` (`releaseChoice.ts`): a build for GitHub writes that name for a nightly too, since electron-builder names the feed after the version's pre-release identifier only for a generic server (**Read** in app-builder-lib 26.16.1, `out/publish/PublishManager.js:413-436` and `out/publish/updateInfoBuilder.js:36-41`; **Verified**: `v0.1.0-rc.1`'s release has `latest-linux.yml`, `latest-mac.yml` and `latest.yml`). electron-updater reads that file without downloading, and the app downloads only once the file names the chosen release's version and every file it would download lies directly in that release's folder, resolved as electron-updater resolves it: a feed file pointing at another release, path or host, or naming another version, fails the check before any download is asked for. electron-updater's GitHub feed is not used: given a channel, it takes only releases of that channel, so a nightly build would never be offered a newer stable release (**Read** in electron-updater 6.8.9, `providers/GitHubProvider.js`). A choice applies at once, and what was found or downloaded on the other channel is dropped before the app checks again. Neither ever offers an older version than the one running: electron-updater installs only a version that sorts after it (`AppUpdater.js`, `isUpdateAvailable`, with `allowDowngrade` false), and the app never sets electron-updater's channel, whose setter turns `allowDowngrade` on. An app on a nightly build that moves to Stable keeps it until a stable release is newer, and Settings says so.
  - **An AppImage and a Windows install update themselves.** They download a newer version in the background, check its SHA-512 against the release's feed, then check it against the release's signed `SHA256SUMS` (`apps/desktop/src/downloadCheck.ts`, [Security: desktop updates](security.md#desktop-updates)), and install it or offer "Restart to update" only once both match. A download that does not match is neither installed nor offered: Settings says it didn't match the release's signature, and the version that runs stays. When a verified version installs is the operator's setting, "Update automatically" (`automaticUpdates` in the app's settings, on at first; [decision 0041](../decisions/0041-the-apps-update-themselves-when-they-start.md)):
    - **On, at launch.** The first check is the launch's, and the page waits for it before it shows anything else: up to five seconds (`LAUNCH_WAIT` in `updater.ts`) for a newer version to be found. While it checks, the page says only "Checking for updates…". A version found in time is downloaded, checked and installed, and the app restarts into it with no click, while the page shows only that it is updating to that version and how far the download has come (`LaunchUpdate.tsx`); a download that goes 30 seconds without progress, or takes more than five minutes in all (`LAUNCH_STALL`, `LAUNCH_DOWNLOAD_LIMIT`), opens the page and goes on in the background, since electron-updater sets no timeout that Electron's requests honour (**Read** in builder-util-runtime 9.7.0, `httpExecutor.js`, `addTimeOutHandler`, which waits for a `socket` event, not among those Electron documents for `ClientRequest`), and it reports progress about once a second (`ProgressCallbackTransform.js`). A check that finds nothing, fails, or takes longer opens the page as usual, as does a download that fails or does not match; a version a late check finds is then one found while the app runs. In local mode the server starts once the launch's update is over, so it never starts only to be stopped by the restart; where the launch installs nothing first, it starts at once, as before. The page knows the launch is updating from the status the app answers as the page starts (`launch` in `UpdateStatus`), and shows nothing until that answer, which comes at once.
    - **On, while it runs.** A version found by the six-hourly check or by Check for updates downloads and is checked in the background, then waits: [the update prompt](#the-update-prompt) offers it, and its "Update now" restarts into it after the server's update; Settings says it is ready and installs when the operator quits J3 Bots, and "Restart to update" stays there to install it sooner. As the app quits for good, after the quit gate has stopped the server, its `quit` handler installs it without starting it (electron-updater's `install(true, false)`, as its own install on quit does): the Windows installer runs silently once the app has exited, and an AppImage is replaced in place. electron-updater's own `autoInstallOnAppQuit` stays off, since it would install a download before the app checked it. An app that does not quit cleanly installs at its next launch: electron-updater finds the download in its cache, checks its SHA-512 again, and the launch's update installs it. A restart the page asks for, as after a keyring is unlocked, restarts into a version that waits rather than beside its installer; a version verified while such a restart is under way waits for the next launch.
    - **Off.** The app never restarts by itself, nor installs as it quits: the operator restarts into a verified version with the prompt's "Update now" or with "Restart to update".
    - **Either way**, a restart while a save is under way waits for it to end: a setting, a bot's profile or memory, an action, or a draft that is sending, uploading, or changed here and not yet kept on the device, a file that just finished uploading included. While it waits, as when an upload stalls offline, Settings and the prompt offer "Cancel restart", which offers the restart again and leaves the version to install as the app quits where it would have. At the launch, the page shows only the update, so no save is under way.
    - **Restarting into it.** Windows runs the installer silently, and the installer starts the new version. An AppImage is replaced in place by electron-updater, then started again by `restartApp` (`apps/desktop/src/restart.ts`), which also serves the plain restart: a detached Bash closes the descriptors it inherited, waits for the old process to exit and starts the AppImage, so the old runtime and its mount go. It starts the file electron-updater installed to: when the operator renamed the AppImage with a version in its name, electron-updater deletes that file and installs the new version under the release's file name, `J3-Bots-x86_64.AppImage` (**Read** in electron-updater 6.8.9, `AppImageUpdater.js:72-115`). The app counts itself an AppImage only when its own executable lies inside the AppImage's mount (`APPDIR`), not because it inherited `APPIMAGE` from a process an AppImage started. Where FUSE is missing and the AppImage was unpacked rather than mounted, the restart and electron-updater's run of the new AppImage are told to unpack it too (`APPIMAGE_EXTRACT_AND_RUN`), and nothing else the app starts is: the server and what bots run do not inherit it. An AppImage in a folder the operator's user cannot write to, as `/opt`, never installs: electron-updater deletes the file and moves the new one into that folder, so the app only says a newer version is out and links to it, as a deb does. An install that fails anyway leaves the app running on its version and says that version could not be installed, with a Download link to its release page, apart from a check that failed; the next check tries again. At launch it then opens the page as usual. What electron-updater's install step itself leaves undone is listed in [Releasing: what electron-updater's install leaves](../operations/releasing.md#what-electron-updaters-install-leaves). **Read** in electron-updater 6.8.9: `install(isSilent, isForceRunAfter)` runs the platform's install synchronously without quitting (`BaseUpdater.js:42-68`), the Windows installer is spawned detached (`NsisUpdater.js`, `doInstall`), and an AppImage is moved into place and run once to finish its install (`AppImageUpdater.js`, `doInstall`). The launch's update and the install as the app quits have not been run on a packaged build (**Assumed**: the release's desktop jobs build them, and the model's steps are tested in `updates.test.ts`).
  - **A deb and a Mac build only say a newer version is out**, in the prompt and in Settings, with a link to its release, and the operator installs it as they installed the first. They show no "Update automatically". A deb would need root to install, and the app never asks for it; Squirrel.Mac installs only a signed app, and builds are unsigned for now. In the composer, `Escape` closes it before a suggested reply would take the key to be set aside, which it otherwise would nearly every time; a list open on the composer still takes its own. A page left with nothing to draw while it shows, as once the primary bot is deleted or this device's pairing ends, hides the window at once, and so does a page that is loaded again: a window is never left up with nothing in it, taking the clicks meant for what is behind. What was open over the card, as an image, is put away with it.

Pressed over another app, the global shortcut reads that app's window (`apps/desktop/src/lookingAt`), and the page shows it above the composer as chips: one for the app and its window's title (`Example Browser · Invoice 2026-031`), one for a picture of the window, off until tapped. The picture is taken only when the page asks for it, which it does once the operator turns it on, or as the chips appear when Settings asks for one on every message (`windowPicture`, off by default); the main process takes the ask only for the showing it read, while it shows, and answers a JPEG of at most 1,600 px on its longest side (`MAX_PICTURE_SIDE`). ## Mobile

An Expo app for iOS and Android, in `apps/mobile`, on the Expo SDK and React Native versions T3 Code's mobile app runs (**Read** at `c1464d67`, `apps/mobile/package.json`). The native projects are generated by `expo prebuild` and never committed. `APP_VARIANT` picks one of three variants, development, preview and production, each with its own name, link scheme (`j3bots-dev`, `j3bots-preview`, `j3bots`) and app id (`dev.j3bots.mobile.dev`, `dev.j3bots.mobile.preview`, `dev.j3bots.mobile`), so they install side by side. Production is the one each release publishes, as a signed APK, which fixes its id ([decision 0017](../decisions/0017-the-android-app-is-a-signed-apk-on-the-release.md)). `eas.json` names the same three builds and holds no account.

- **A server the operator names, and pairing.** The first screen asks for the server's address, the pairing code and a name for the phone, prefilled with the device's own. Its scanner reads the QR code a paired device or `j3-bots pair` shows with `expo-camera`, decodes it as a `PairingLink` and fills in the address and the code; it never pairs by itself. The camera is asked for once, as the scanner opens; refused, the scanner offers to ask again, or the phone's settings once the system no longer lets the app ask, as Android 11 and later do after a second refusal (**Read**: Android's permissions documentation). The permission is read again whenever the app comes back to the foreground, so a camera allowed in the phone's settings opens on return. **Verified** on the Pixel 8 emulator (Android 16): the system asks as the scanner opens; refused once, "Allow the camera" asks again; refused twice, "Open the phone's settings" opens the app's page there; allowed there, the camera shows on return. On Android, `false` for a permission in any one config plugin removes it for the whole app, so every plugin that names the camera or the microphone gets the same sentence for it: `expo-image-picker` and `expo-camera` name the scanner's camera, and both of them and `expo-speech-recognition` name dictation's microphone. The scanner records nothing, so `expo-camera` takes no audio (**Verified** with `expo config --type introspect`: the manifest keeps `CAMERA` and `RECORD_AUDIO`, and iOS gets one camera sentence and one microphone sentence; and on the Pixel 8 emulator the installed app declares both, granted only once asked). Reading a code has not been run on a device: the emulator's camera shows its own moving test pattern. The address follows the same rule as the desktop app's (`parseServerAddress` in `client-runtime`), and pairing checks the server's `/api/server` before it sends the code. A paired phone opens its server's roster on the next start, if the saved server still passes that rule. One that does not is forgotten with its pairing (the credential, the device-id copy, and the drafts and unsent messages), so pairing again leaves nothing of it behind, and the pairing screen shows; if that cannot be deleted, the app says it cannot read this device's sign-in. Pairing with another server replaces the client of the first; its credential is stored with the origin of the server that issued it, so it never reaches another.
- **Changing server.** A server whose address changed (a new router, a new DHCP lease) is never reached again, so the line that says the server cannot be reached, and the screen for a server of another protocol version, offer to change server. After the operator confirms, the app signs the phone out the way sign-out does: it revokes nothing, since it is not connected, deletes that pairing's drafts and unsent messages, then its credential and the device-id copy, and shows the pairing screen with an empty address. The old entry may still show under Devices on the server, and another device can revoke it there.
- **The first run** is the web's, step for step, with the same words from `client-runtime` (`presentation/onboarding.ts`, `wording/onboarding.ts`). It is the web's stage in the phone's idiom ([First run](../design/design-language.md#motion)): the cast comes down into lights of the bots' own colors, in the app's own appearance, and stays up over the three steps that say what J3 Bots is while its lights change (`Cast` and `Light` in `onboarding/parts.tsx`, drawn with `react-native-svg`); the bot being made is carried on `slide` from the cast to its place above the steps, each step's lines rise in under it, and what the operator does it answers through the avatar's own model, on the UI thread. Its moves are the design tokens' springs (`reanimatedSpring(springs.pop)` and the others) and the `stage` values beside them, the ones the web uses, so both clients move alike; its buttons press with `PressScale`, and the command that connects a provider copies with `expo-clipboard`. Where it left off is kept in `expo-sqlite`'s key-value store, beside the appearance and the language, and dropped once the bot exists. **Assumed**, not run on a device: the stage, the entrances, the finger leading the avatars' eyes, and the resume, written with [decision 0052](../decisions/0052-motion-follows-palco.md); and the three steps of the story, the lights as cones, the light going round and gathering, the arrival's swell and the line that says what the server prepares, written with [decision 0065](../decisions/0065-the-first-run-tells-what-j3-bots-is-before-it-asks.md). - **Its ports.** The credential is in the system's secure storage (the keychain on iOS, the keystore on Android), readable after the first unlock and on this device only. A read that fails, or a stored value that does not decode, is not taken for a missing pairing, which would lead the operator to pair again over the unreadable credential and leave the old device listed: the app says it cannot read this device's sign-in and offers to try again or to forget the sign-in. Forgetting, after the operator confirms as for changing server, deletes the device-id copy and every draft and unsent message in one transaction, then the credential, and shows the pairing screen. Drafts and unsent messages are in SQLite, beside a copy of the paired device id that the check before every write reads in the same transaction (see [Pairing](#pairing)). The app keeps one connection to the database, and every operation on the device's storage, whichever client makes it, runs one at a time, so a client being replaced never runs a statement inside the new one's transaction. The copy follows the credential: saving one writes the copy first and, if the secure write fails, sets the copy back to what the secure storage holds; clearing one clears the copy first; reading one sets the copy to what it finds, which mends a copy left behind by a crash, or a keychain item that outlived the app's data. Locks are in process, as the app has one window. Network status comes from `expo-network`, random bytes from `expo-crypto`, HTTP from `expo/fetch`, and the socket from React Native's `WebSocket`.
- **What outlives the app.** On iOS the keychain item outlives uninstalling the app (**Assumed**: Apple documents no removal on uninstall, and nothing was run on iOS), so a reinstall goes straight to the roster of the same pairing. Changing server, or revoking the phone from another device, ends it. On Android the credential is kept out of the system's backups by `expo-secure-store`'s config plugin; the backups include the SQLite database, with drafts and unsent messages and never the credential. That is intended: they are the operator's own text and give no access to the server, and a restored phone pairs anew.

A memory file opens read-only and is edited in place; a file that changed on the server meanwhile is never overwritten. **Verified** on the Pixel 9 Pro Fold emulator: New room said what was missing only once Create was pressed; editing a room added a member and removed one; a bot's profile saved its title, job and permission mode; the system's back on an edited form asked first; a memory file's edit reached the disk, and one made while the file changed on the server kept the server's text and offered to load it. A failed save and the toast after a form closed were not seen, nor the swipe, which is iOS's.

- **Visuals.** A bot's message that carries a visual shows it above its words, at the height the page reports, clamped to 80–2000 px, and starts at the bot's own height, or 240 px when neither has said. Inline, it is only drawn: the press goes to the card, and a screen reader reads its title. A press opens it full screen, where it can be scrolled and pinch-zoomed; the close button and Back close it. Until it has painted, its title holds its place. If it cannot be drawn, or its page holds what the document's guard could not watch (another document or a declarative shadow root: `visualEscapesGuard`), the card says so under its title ("Couldn't show this visual."). It is drawn in the app's own view, `modules/visual-view` (a WebView; [Security](security.md#visuals-on-android) says how it is shut). The view is Android's only: on iOS, a visual shows the failure line. The WebView loads `client-runtime`'s `visualShell` around its `visualDocument`, in the app's current theme, built again when the theme changes. The app reads only a height from what the page sends, and the shell's word that the frame shows something else, which the visual navigated it to, with `readVisualReport`; the card then says it could not show the visual.
  - **In the list.** LegendList draws only rows near the screen. A visual loads its page only once its row has been drawn for 150 ms with the list still, and stays loaded while its row does. A fling passes placeholders and starts no WebView. The height each visual reports is kept while the conversation is open, so a row that scrolls back comes back at its own height. **Verified** on the Pixel 8 emulator with 17 visuals in one conversation: at most 6 WebViews were alive at once. Six flings each way gave a 53 ms median frame and 56% janky frames, against 38 ms and 36% for a text-only conversation of the same length. Loading pages during the fling, before the list had to be still, gave 65–101 ms and 84–92%. The emulator draws with SwiftShader, a software GPU, so these numbers show the difference, not what a phone does.
  - **One renderer.** Android runs every WebView of an app in one renderer process, so a page that crashes it or runs it out of memory fails every visual drawn at that moment, and Android does not say which page it was. Each shows the failure line, and the app goes on. The visuals that were on screen stay failed while the conversation is open: a row that comes back does not load the page that did it again, which would take the others down once more. Opened again, the conversation tries them all. A renderer the system reclaims while the app is out of sight fails its visuals the same way, but each tries again when its row comes back. **Verified** with a page that allocates until it is killed, in dark mode and pt-BR.
  - **No WebView.** On a device whose WebView is missing or being updated, every visual shows the failure line and the conversation works as before. Each tries again when its row comes back. **Verified** with the emulator's WebView provider removed for its user (`pm uninstall -k --user 0`; disabling it is not enough on Android 16, which loads it anyway).
  - **No react-native-webview.** That library has no setting that blocks the network. It allows a navigation when the app does not answer within 250 ms. It opens a URL outside its allowed list in the system browser (**Read** in react-native-webview 14.0.1, `RNCWebViewClient.java` and `WebViewShared.tsx`). The app's own view decides every one of these natively.

- **The composer** keeps a draft per bot and room, with mentions in rooms, and sends through the runtime's outbox. A message sent offline waits as "Sending…" and goes once the phone is back: **Verified** on the Pixel 8 emulator (Android 16) in airplane mode, where it landed once, with one row and one command id on the server. Android's field is the app's own, an `EditText` in a local Expo module (`modules/chip-field`), because React Native's `TextInput` cannot draw anything but text inside the text: each file is a `ReplacementSpan` over its mark, which draws the chip with its image or a page, its name and its ×, and which the text treats as one character, so Backspace takes the whole chip. A tap on a chip opens its file; one on its × removes it. The field tells the app each edit with a count, and the app passes back with each value the count of the newest edit the draft has taken, as React Native's own field does, so a value that arrives after the operator typed on is not shown over what they typed; and a caret the app places in text the field does not hold yet, as after an attach, whose command can arrive before the value, waits for that value. The field changes what makes it take edits (its key listener, the cursor, the keyboard on focus) only when it starts or stops taking them, never when React only sends its props again: Android's `setKeyListener` restarts the keyboard's input (**Read** in AOSP's `TextView.setKeyListener`), and doing it on every render, as the app once did, lost the keys Gboard was delivering while the restart ran (**Verified** on the Pixel 8 emulator with Gboard and a busy JS thread: a few letters of 60 typed fast went missing in each try before, none after). Each pick of a member that counts is a `ReplacementSpan` over its text too, sent with the value it answers: the bot's face, a PNG the app draws with the avatar rasterizer, and the text on its tint; the text stays the field's, so an edit inside it takes the span away at once, before the app answers (**Assumed**: built and run on no device yet). It reports its content's height, which the composer clamps. On iOS, where the app has no such field, the composer is React Native's field, without marks, and the files follow the text (**Assumed**: the iOS app has not run). The photo picker hides a file's own name, so a photo goes as its media id with its extension (**Verified** on the Pixel 9 Pro Fold emulator: a picked PNG arrived with identical bytes; and on the Pixel 8 emulator with the plugins above, the photo picker opened with no permission asked). - **Dictation.** While the draft has no words, the composer's trailing button dictates, with Send beside it when files wait to go; while it listens it stops, and once there are words it sends again. The first press asks for the microphone (and, on iOS, for speech recognition). What the recognizer hears becomes the draft's words as it is heard, through `setDraftText` like typing, where the caret was, between the draft's files and a space apart from them, and waits there: dictation never sends. Typing stops it, and so do the draft taking no change, the conversation leaving the screen (another screen over it, on a phone) and the app leaving the foreground; a press still being prepared is not cancelled by the last two, since Android reports the app in the background while its permission dialog is open. Recognition is the platform's (`SpeechRecognizer` on Android, `SFSpeechRecognizer` on iOS) through `expo-speech-recognition`, a community module with a config plugin for continuous native generation and releases that follow the Expo SDK's major version; Expo maintains no speech recognition module (`expo-speech` speaks text). T3 Code's app transcribes a recording itself instead, on the device with ML Kit's alpha GenAI speech recognition on Android or Apple's speech framework on iOS 26 and later, or with a transcription model in the engine's environment or a cloud provider, none of which J3 Bots has (**Read** at `bc0f04d`, `apps/mobile/modules/t3-voice-transcription`). On Android the app prefers recognition on the device: when the system has an on-device recognizer (13 and later) and lists the device's language among those installed, it asks for it with `createOnDeviceSpeechRecognizer` and `EXTRA_PREFER_OFFLINE` (**Read** in `expo-speech-recognition` 58.0.1, `ExpoSpeechService.kt`); a language whose model is not installed is recognized online rather than downloaded first. On iOS the module's on-device check asks about the recognizer of the system's language, not of the language dictation listens for (**Read**, `ExpoSpeechRecognitionModule.swift`), so the app takes iOS to recognize online until it is shown otherwise on a device. Online, the device's speech service may send the audio to its provider, and the line under the pill says so while it listens. On an Android 16 emulator with Google's speech services and only the en-US on-device model installed (**Verified**): the first press asked for the microphone; refusing it left "Dictation needs the microphone." and the next press asked again; with it allowed, speech played into the emulator's microphone reached the draft as it was heard, recognized on the device, and stayed there after Stop with nothing sent, in the light theme and the dark. Going back to the bots, opening the bot's details over the conversation and sending the app home each ended the recording at once, and later speech did not reach the draft. The on-device recognizer answers Stop of a continuous session with a client error instead of its end, which the app takes as the end the operator asked for. With the app in Portuguese, whose model was not installed, the line said recognition may run online, but the online recognizer heard nothing of the played speech there: the online path is shown only as far as that line. Without a recognizer, as on an Android device with no speech service, the composer has no dictation. While it listens, the field says "Listening…" where the text goes, in the placeholder's color, after any text and chips on their last line, and, when recognition runs online, a quieter, smaller "may be recognized online" after it; the field draws both itself, so its height never changes as dictation starts and stops, and the whole sentence is announced instead. Why dictation stopped by itself is said under the composer.

- **Opening a file.** Any other file: the runtime downloads it with the device's credential and hands the app its bytes, not a `Blob`: React Native's `Blob` cannot be made from bytes (**Read** in React Native 0.88.1, `Libraries/Blob/BlobManager.js`). The app writes them to its cache, in a folder of each open's own, under the file's own name, with path separators and control characters replaced and shortened to the file system's 255 bytes. Once written, the files of opens that started earlier are deleted, and one that started later is never touched, so two opens at once never meet. `expo-file-system` then shows it in the system's viewer for its type, an app that takes `ACTION_VIEW` for it on Android, through the library's file provider, or Quick Look on iOS (**Read** in `expo-file-system` 58.0.14, `FileSystemModule.kt` and `FileSystemPreview.swift`); with no viewer for the type, the share sheet (`expo-sharing`) offers to save it or send it to an app. On Android a PDF opened in the system's PDF viewer and a PNG in Photos, through the file provider, and a file of an unknown type in the share sheet; after a second open the cache held only its folder (**Verified** on the Pixel 8 and Pixel 9 Pro Fold emulators, Android 16). Quick Look on iOS has not run on a device (**Assumed**). Nothing of the file runs in the app. The last file opened stays in the app's cache until another is opened, the app starts again, or its server is forgotten or changed, which deletes every one with the drafts and unsent messages; an open still under way then keeps nothing. The system may clear the cache sooner, and a file it cannot delete is left to it.
- **A bot's browser.** The viewer (`apps/mobile/src/browser`) is a screen of its own over the conversation, opened from a help card. It asks for pictures as wide and as tall as the screen in pixels, at quality 55 on a cellular network (`expo-network`) and at the server's default otherwise. Each picture is decoded from a data URI into an `Image` laid over the last, shown once it is drawn (`onLoad`) and only then acknowledged, so the page never blanks between two pictures and the phone is never sent more than it draws. Touches go through the responder system on the page's view: a touch that moves less than 8 points is a tap, mapped from the drawn picture to the page's CSS pixels; one that moves further is a drag, sent as wheel events of the distance it covers on the page; a finger held still for 500 ms is a right-click; two fingers are a pinch, which only zooms the picture. A tap sends a `probe` before its click, and the probe's answer decides the keyboard: a field raises it, anything else lowers it. The keyboard types into a hidden `TextInput`, and each change to what it holds is sent as Backspaces for what went and text for what came, so a keyboard that composes a word, swaps in a suggestion or deletes a selection reaches the page as a desktop's would; Backspace on the empty field and the return key are sent as keys. The field asks for no autocorrection, autofill or suggestions and has Android's visible-password type, which keyboards treat as a password and do not learn from (**Assumed**), because what the operator types into a page is often a password, and a tap cannot tell the viewer which fields are; a keyboard that composes only outside password fields, as some do for languages that need it, types Latin letters there. On the Pixel 8 emulator (Android 16), against a development server running the pinned engine with the scripted agent, a bot's tab was watched, taken, scrolled by dragging, zoomed with two fingers, typed into (an address, then a password with a Backspace, sent with the return key, which submitted the form) and given back, in light and dark and in English and Portuguese; the engine refused the bot's actions while the phone held the tab and took them again once it was given back (**Verified**). That run opened the viewer by a link of its own, not from a help card.

- **Sharing from another app.** On Android, other apps' share sheets list J3 Bots for text, links and files of any type, one or several, through `expo-sharing`'s intent filters for `ACTION_SEND` and `ACTION_SEND_MULTIPLE`, as T3 Code's app does (**Read** at `c1464d67`, `apps/mobile/app.config.ts:209-230`). The composer of a bot's conversation has the same `/` menu, its list and form above the field, and a service's question is the same card, its page opened in the system's browser.
  - **A sign-in's return.** The service opens in a Custom Tab (`androidx.browser`). From a server the phone reaches over `https:`, the app asks for the server's own callback (`server`), so nothing of the sign-in passes through the phone; the server can only give it when it knows the address a browser reaches it at, [`publicOrigin`](../operations/exposing.md#publicorigin), and without it the panel asks for the address the browser lands on, as the web does (`paste`) (**Read**: `ConnectorAuth`'s `serverOrigin` and `client-runtime`'s `startSignIn`, at this branch's head). From one on plain HTTP, the app's module (`modules/sign-in-relay`) listens on the phone's `127.0.0.1` for that one sign-in, and the server sends the browser to `http://127.0.0.1:<port>/oauth/callback/<issuer>` (`relay`). The module only reads each request's line and Host header and asks the app what to answer; which request is the sign-in's own is decided by the same code as the desktop app's (`signInCatch`, in `client-runtime`), and the address goes to the server with `connector.completeSignIn`. The app then asks Android to bring it back over the tab; where Android keeps it behind (it limits starts from the background), the page the browser lands on says to come back to the app.
  - **Kept awake while it waits.** An app behind a Custom Tab is cached, and Android freezes cached apps: on the Pixel 8 emulator (Android 16) the app was frozen while the tab was in front, the browser's return waited unaccepted in the listener's queue, and the sign-in finished only once the operator came back to the app (**Verified**, against a fake authorization server). So while the listener is open, a short foreground service (`SignInWaitService`, type `shortService` from Android 14) keeps the app running, under a notification in the app's language; it started as a foreground service of that type on Android 16 (**Verified**). That the return is then taken while the tab is still in front is **Assumed**: the device check stopped before it. Android ends a short service after about three minutes; a return that arrives later is taken once the app is opened again. Below Android 14 the service starts with no type (**Assumed** to be allowed).
- **Push notifications**, through Expo's push service ([decision 0014](../decisions/0014-push-goes-through-a-push-sender.md)), with `expo-notifications` 58.1.8, the version T3 Code's app ran at `db51b67`; at `bc0f04d` it asks for `~58.1.9` (**Read**, `apps/mobile/package.json`). No push has reached a device, and none can for now: there is no Expo or Firebase project, by the owner's decision, so no build has the values below (What a build needs). Everything about receiving a push on a device is **Assumed**, not run, except where it says what was read. What is tested runs without a device: the runtime's tests (in the background the server has no socket for the device and counts it as one to push to, and once the app returns, one it tells on the socket; the background from offline and from waiting to reconnect; signing out in the background), and the server's tests for sending (`PushWorker`, and `ExpoPushSender` against a stand-in for Expo's API, with the Android channel and the iOS collapse id).
  - **Permission.** Only "Allow notifications on this phone", on Settings' Notifications page, asks for it: the section's `thisPhone` (`usePhoneNotifications`) passes the phone's access and `allow`, which calls `allowNotifications`. Not asked yet, or refused once on Android, where the system can ask again, the section shows the button; refused for good, it says the phone's settings decide, and a press that comes then opens the app's page in the system's settings, since the system would show no dialog. An answer just given in the dialog stays as it was. The access is read again whenever the app returns to the foreground, so one changed in the system's settings shows on return. A build that cannot receive pushes shows no line for this phone. Nothing asks at start, and creating the channels at start does not ask either, on Android 13 and later, for an app that targets them. On Android 12 and lower there is no permission to ask for: Android has it from Android 13, API level 33 (**Read**: Android's notification permission documentation), and before that an app's notifications are allowed from its install, so the app registers at start and the section says the phone shows them.
  - **Registration.** While notifications are allowed, the app registers this phone's Expo push token for the pairing with the server, with the language the app shows (the one chosen in Settings, or the phone's): for each pairing as it starts; when the operator chooses another language; whenever the app returns to the foreground, sent again in full, so a permission given or withdrawn in the system's settings, a new language, or a registration the server dropped reaches the server then; and when the push service gives the app a new token. Once the operator refuses notifications, it ends the registration. Between two returns to the foreground, what the app already told the server is not sent again.
  - **A token for each pairing.** Expo keeps a token for each device id an app gives it, the app's installation id by default, and when the device's own token (Firebase's or Apple's) changes, `expo-notifications` posts the new one to Expo under the installation id by itself (**Read** at 58.1.8, `src/getExpoPushTokenAsync.ts` and `src/utils/updateDevicePushTokenAsync.ts`). With that one token, a server the phone left could be reached again through the next. So the app asks for each pairing's token under its own device id, a UUID shaped from a SHA-256 hash of the pairing's id, with nothing stored. The installation id's token, which no server holds, is the only one Expo moves by itself.
  - **The socket.** In the background the app keeps no socket open (`Lifecycle`, from React Native's `AppState`; iOS's `inactive`, under the notification center or the app switcher, keeps it), so the server pushes to the phone; it connects again when the app returns. The server pushes to any device with no socket open, so a push also reaches the app in the foreground while it cannot reach the server, offline or between attempts: it shows then as in the background. Only while the app is connected does a push show nothing: it raced the socket's opening, and the roster shows its entry unread. Whether Android puts the app in the background while the system's photo or document picker is open, which would close the socket until the app returns, is not known: it was not run.
  - **Channels.** On Android each kind of notification shows in a channel of its own, named in the language the app shows, and renamed when it changes, whose id is the kind the server sends as the push's `channelId` (`NotificationKind`), so the operator can silence messages and keep approvals. A push that names none, from a server older than the channels, shows with the messages.
  - **A tap** opens the conversation or room as the runtime's `pushOpening` decides, from the roster's screen, which is under every other, with the opener a roster row uses (`useOpenConversation`): its own screen on a phone, unless it is the one shown, or beside the roster from the tablet width up. Another pairing's push, or one about a bot or room that is gone, opens nothing; a tap before the roster loaded waits for it.
  - **Previews off.** The push shows the bot's or room's name and a fixed sentence, never what the bot wrote: the server words it so ([Security](security.md#push-notifications)), and the app shows the push as it came.
  - **Leaving a pairing.** Signing out, changing server and forgetting an unreadable sign-in clear the notifications shown and have the push service forget the device's token (`unregisterForNotificationsAsync`: Firebase's `deleteToken` on Android, `unregisterForRemoteNotifications` on iOS; **Read** at 58.1.8). The app does not wait for that before the pairing screen accepts a new pairing; the new pairing's registration waits for it. Revoking a device deletes its registration on the server, and on the phone revoked from another device, the notifications it shows are cleared too. A server that still lists a pairing, after a sign-out it never confirmed, holds that pairing's token, and on Android, once the device's token is deleted, Expo answers it `DeviceNotRegistered`. Two cases still let that server reach the phone (**Assumed**, both). On Android, a `deleteToken` that fails, as offline, is logged and not tried again, and the old device token stays valid. On iOS, Apple usually gives the same device token after the app unregisters and registers again, so the old pairing's token keeps reaching the phone. Its pushes show, and a tap opens nothing. Revoking the phone from that server's Devices ends them.
  - **What a build needs.** Two values from the environment it is built in, neither in the repository: `EAS_PROJECT_ID`, the EAS project whose push credentials Expo holds, and, for Android, `GOOGLE_SERVICES_JSON`, the path to that project's Firebase config file. A build without them runs, and Settings simply cannot turn this phone's notifications on: it shows no line for this phone, and the app registers nothing with the server and makes no notification channels. No plugin needs the Firebase file: `googleServicesFile` and the project id are set only when given, and `expo config --type introspect` without them resolves the config, with the notification icon and no Firebase file (**Verified**). Nothing calls Firebase at start: `expo-notifications` reaches it only to get or delete a token or change a topic (**Read** at 58.1.8, `PushTokenModule.kt`, `TopicSubscriptionModule.kt`), and the app gets or deletes one only with a project and uses no topics. Such a build was not run on a device either.

### Installing the Android app

Each release has the app as `j3-bots-<version>-android-arm64.apk`, for arm64 phones, which nearly every Android phone of the last years is ([Releasing](../operations/releasing.md#what-a-release-contains)). On the phone:

1. Open the release on GitHub (Releases, on the repository's page) and download the APK under Assets.
2. Open the download. Android asks to allow the browser, or the files app, to install apps; allow it, go back, and install. Play Protect may say it does not know the app; it lets the install go on.
3. Open J3 Bots and pair it with the server: scan the QR code that Settings → Devices on a paired device, or `j3-bots pair` on the server's machine, shows.

Every later release is checked by the phone itself: it installs over the app only when it is signed with the same key. The first install has nothing to compare with, so whoever wants to check it compares the APK's signing certificate with the project's, before installing, on a computer with the Android SDK's build tools:

```sh
apksigner verify --print-certs j3-bots-<version>-android-arm64.apk
```

The command must succeed first: if it prints `DOES NOT VERIFY` or exits with an error, the APK is damaged or was changed after signing, whatever digest it shows, and must not be installed. Then every line `certificate SHA-256 digest` must read `bfd3b598e6bd1c1ccdc969076a4254fd5a3696bddd5092df44b2bb51581431ff`, the release certificate's, which each release's notes repeat. Any other value means the APK was not signed by the project.

A newer release installs over the one installed and keeps its pairing, drafts and settings. From 0.3.1 the app installs it itself ([Updating the Android app](#updating-the-android-app)); an APK opened from the browser installs the same way. **Verified** on the Pixel 8 emulator (Android 16) with x86_64 builds of the release variant, built unsigned and signed with `apksigner` and a test key as the release workflow does: the APK started with no Metro, paired with a server and showed the roster, and the next version, built and signed the same way, installed over it and opened on the same roster. The release APK cannot show push notifications: it is built without the Expo and Firebase projects they need. It installs beside a development build, which has another app id.

### Updating the Android app

The app updates itself from the release's APK ([decision 0035](../decisions/0035-the-android-app-installs-its-update-through-a-session.md)), with `apps/mobile/src/update` and a native module of its own, `apps/mobile/modules/app-update`.

- **Its own channel.** Stable, the default, or nightly, chosen on the phone in Settings → About and updates, apart from the server's. The app reads `/releases/latest` for stable and `/releases?per_page=30` for nightly from GitHub's API, without a token, when it starts and when it comes back to the foreground, at most every hour with "Update automatically" on and every six hours with it off, and whenever the operator asks. It takes the newest release of its channel only when it is newer than the version it runs (`@j3-bots/release`'s `newestOn` and `offer`, the server's own rules), so moving from nightly to stable waits for a stable release newer than the nightly, and says so. A check that was reading the other channel when the operator changed it is dropped, and the new channel is read. So is an update waiting for the operator, with its file.
- **Only a verified release is offered.** Before it offers one, the app downloads the release's `SHA256SUMS` and `SHA256SUMS.sig` from the release's own tag, checks the signature with the release key it carries, and finds the APK's digest in the list. A release that fails any check is not offered; the app says a newer version is out but did not check out against the project's signature. Ed25519 comes from `@noble/curves`, since Android has it only from 13 on (**Read**: Android's `KeyFactory` reference, Ed25519 from API level 33) and Hermes has no `crypto`; the shared test vectors of `@j3-bots/release` run against it.
- **The download** goes to the app's cache (`<cache>/app-updates`, which no backup copies: **Read**, Android's Auto Backup leaves out the cache directory), with its progress. React Native's requests have no deadline of their own, so a request that goes 30 seconds without its answer, or a download 30 seconds without a byte, counts as unreachable. Then the app checks the file's SHA-256, computed natively, against the verified list, and reads the APK (`PackageManager.getPackageArchiveInfo`): it must be this app's package, with the release's version name, a version newer than the installed app's and a higher version code. A file that fails is deleted, and nothing is installed.
- **"Update automatically"**, beside the channel, is on by default and kept on the phone (`j3:appUpdateAutomatic`, written only when off). On, a check that finds a verified release goes straight on to download, check and install it, with no tap, once per check. Without "Install unknown apps" it asks for that before it downloads, since the file would otherwise wait and go at the next start, and downloads when the operator comes back with it allowed. An install that fails or is refused says so and is tried again at the next opening the bound lets check, or when the operator taps. A cancelled confirmation waits for the operator until the app restarts. While the update prompt updates the server first, nothing installs the app by itself (`waitForServer`): the checks it makes as it opens or comes back wait, a check already under way only offers what it finds, and an install waiting for "Install unknown apps" waits on, so it never installs ahead of its server. The line over the roster shows the download, the check and the install as they go, and how it ended when it did not go through, and opens Settings from there. Off, [the update prompt](#the-update-prompt) offers the release, and its "Update now" installs it after the server's update; Settings keeps the same tap ([decision 0035](../decisions/0035-the-android-app-installs-its-update-through-a-session.md)).
- **"Install unknown apps."** The manifest asks for `REQUEST_INSTALL_PACKAGES`. The first time, the app explains the permission before it opens Android's page for it (`ACTION_MANAGE_UNKNOWN_APP_SOURCES`), and goes on with the install when the operator comes back with it allowed.
- **The install** is a `PackageInstaller` session. The module copies the checked file into it, hashing it again as it writes, and commits only when that digest is the release's; otherwise it abandons the session. With "Update automatically" on, it commits the session with `setRequireUserAction(USER_ACTION_NOT_REQUIRED)` on Android 12 and later, and the manifest declares `UPDATE_PACKAGES_WITHOUT_USER_ACTION`: Android then installs without asking an app that updates itself and targets a recent enough SDK (the exact conditions are in decision 0035; **Read**, Android's reference, not yet run on a phone). Otherwise, and wherever Android does not grant it, Android asks the operator to confirm. It does not let an app in the background open its dialog, so when the operator went to another app during the download, the module keeps the confirmation and shows it once when they come back. Android refuses an APK signed with another key or with a lower version code. The session reports how it ended: installed (which ends the app's process, so the app learns it at its next start), cancelled (the checked file is kept for another try), or refused, with why, in words. The file is deleted after an install or a refusal, and the update folder is emptied at every start. The module reads, hashes and installs only files in that folder.
- **An app from Google Play** would be updated by Play. The app reads which package installed it (`getInstallSourceInfo` from Android 11, `getInstallerPackageName` before), and for `com.android.vending` it opens its page on Play instead (`updateRoute`). J3 Bots is not on Play ([decision 0017](../decisions/0017-the-android-app-is-a-signed-apk-on-the-release.md)), so this branch has unit tests but has never run on a phone.
- **Builds.** The production build trusts only `RELEASE_KEYS` and the project's GitHub releases. A preview or development build updates itself only when it is built with `J3_APP_UPDATE_FEED`, a release server of its own that answers as GitHub does, and `J3_APP_UPDATE_KEY`, the PEM public key its releases are signed with. The production build refuses to be built with either, and the app installed as J3 Bots (`dev.j3bots.mobile`) ignores a test feed at run time too, since Expo reads the config again when the native project is assembled. Without them, a preview or development build does not update itself.

**Verified** on the Pixel 8 emulator (Android 16), with x86_64 preview builds signed with a test keystore, against a local release server that answers as GitHub does, with `SHA256SUMS` signed by a test key, before "Update automatically" existed, so with the operator's tap and Android's confirmation. The unattended install has not run on a phone or an emulator yet:

- 0.3.1 offered 0.3.2, explained "Install unknown apps", opened Android's page for it, and went on with the install once it was allowed. Android asked to confirm, installed 0.3.2 and recorded the app itself as its installer. The update folder was empty afterwards.
- An APK changed after its `SHA256SUMS` was signed was refused as not the file the release signed, deleted, and nothing was installed.
- An APK listed in a correctly signed `SHA256SUMS` but signed with another keystore passed the app's checks. Android refused it at the install, and the app said it is not signed like the installed app.
- After an install ended the app's process, the next start emptied the update folder.
- Cancelling Android's install dialog: the app said the install was cancelled and the checked release ready, kept the file, and installed it from there at the next tap.
- Leaving the app during the download: nothing opened over the other app. Android's confirmation was there when the operator came back, and cancelling it ended the update as cancelled.
- Changing from nightly to stable with a cancelled nightly install waiting: the nightly and its file went, and the stable release was offered.
- The server's update from the phone, against a server that `install.sh` installed as a systemd user service: the roster's notice opened Settings at the server's offer, one tap took it, the roster said the bots were restarting on the new version, and the app reconnected to it. A release that never became ready rolled back, and the roster said so, with the reason, until it was closed.

Mobile uses its own components. Web and mobile share logic, tokens and vocabulary, not React components. See [decision 0007](../decisions/0007-client-and-server-stack.md) for why, and for the alternative of a single universal codebase.

## Reaching the server

The server listens on an address the operator chooses. J3 Bots does not run a relay.

| Where the client is | How it reaches the server |
| --- | --- |
| Same machine | Loopback |
| Same network | The server's LAN address |
| Anywhere else | The operator's own private network (Tailscale, WireGuard) or their own reverse proxy with TLS |

Plain HTTP is accepted only on loopback and private address ranges. Everything else requires TLS.

## Pairing

A new client is paired with a one-time code.

1. The operator runs `j3-bots pair` on the host, which prints the code and the addresses the server listens on (while pairing is locked after failed attempts it makes no code, says until when, and `--unlock` lifts the lock: [Security](security.md#j3-bots-own-surface)), or opens Devices in an already paired client, which shows the code as text with the time it expires. A code expires in five minutes. Making one in Devices needs a connection to the server; offline, Devices says so. The code is ten characters of Crockford base32 (no `I`, `L`, `O` or `U`); clients accept it in lower case and with spaces or dashes.
2. Both also show a QR code of a pairing link, for a phone's camera: the server's own address at the path `/pair`, with the code as the fragment, `<origin>/pair#<code>`, so neither is typed. A camera opens it in the browser, where the server serves the web client at `/pair` as at any path it routes; the native app's scanner reads the same link. The path is the link's own because a browser loads the page again for a new path, while a tab already showing the app at `/` would take a new fragment alone without loading, leave the pairing screen empty and let Back and Forward bring the code back (**Verified** in Chromium). `pairing.start` answers the code with the origins another device reaches the server at, the ones `j3-bots pair` lists: its `publicOrigin` first, when one is set ([Server: configuration](server.md#configuration)), then where it listens; a server from before that field answers without it, which a client reads as none. Devices puts the origin it reaches the server at first when that is `https`, as a domain a proxy serves, or one the server offers; a plain-HTTP origin the server does not offer, such as a forwarded port, is left out. The others follow, each once, and an origin that names the reading device itself (loopback, also IPv4-mapped, or the unspecified address) never reaches a QR code. The operator can pick which one the QR code carries when there is more than one; the pick holds across Get a new code while the new code lists it (`qrOrigin` in `client-runtime`). Under the QR code, one line says that behind a sign-in page the operator signs in on the phone first, or types the code ([Security: J3 Bots' own surface](security.md#j3-bots-own-surface)). `j3-bots pair` draws it for the first address it lists that is not `localhost` or another loopback address (the `publicOrigin`, else the first in the order the machine lists its interfaces), or for the one `--address` names, and says which address it carries. `--address` takes only a bare `http` or `https` origin (a trailing `/` at most; no path, query, fragment or user name, not even an empty one, and no other scheme), checked as typed, before the URL parser resolves a path such as `/x/..` or drops an empty `@`; it must be one the command lists or an `https` origin, and anything else is refused before a code is made. The lines that say where the link goes come first and the QR code last, so the prompt after it scrolls the text, not the code, away. Where its standard output is not a terminal, or the terminal is smaller than those lines, the QR code with its quiet zone and the prompt's row, it prints the link as text and says how large the terminal must be. With no address another device reaches, as on a server that listens on loopback only, there is no QR code, only the code. The link's schema is in `packages/contracts` (`PairingLink`), for every client to decode: the base must be a bare `http` or `https` origin as a browser writes it, the path `/pair`, no query or user name, and the fragment exactly one code, read as a typed code is (in either case, with dashes between groups) and then with the pairing code's form; anything else is refused. `parseUrl` there is built on the WHATWG `URL` class, so a native client needs an implementation of it: Expo's, or a polyfill.
3. A link only fills in the pairing screen. A client never pairs from a link by itself: the operator still presses Pair. The web client reads a page at `/pair` as it loads, before the router sees the address, and replaces it at once with the app's root, given as a whole URL, so the code leaves the address bar and the tab's back and forward history, and an address copied from it (**Verified** in headless Chromium 151 with a built client: each of two links opened in turn in a tab already at `/` loads the page, fills in its code and leaves the address at `/`, and Back and Forward bring no code back). It also drops a link's code when the page is put aside (`pagehide`), as when the operator leaves for another page before pressing Pair: a page the back/forward cache restores keeps what it held, and without that Back would bring the unused code back into the form. The pairing screen then starts over, its device name with it. **Assumed** until tried in a browser with the cache: that the restored page shows the form empty; the drop is tested on what holds the code, not in a browser. When the browser turns out to be paired with that server, which it knows only once it is connected, it drops the code without asking; a browser whose stored credential the server refuses, as after a reinstall or a revocation, keeps the code for the pairing screen it then shows. Every client's pairing screen shows, prominently, the origin of the server it pairs with. A native client that is already paired with a different server when it reads a link to another one must say that pairing replaces that server. The mobile app scans only on its pairing screen, while it is not paired, so this cannot happen there. An address a client takes from a scanned link follows the rules of one typed in ([Reaching the server](#reaching-the-server)): plain HTTP only at a loopback or private IP literal, HTTPS everywhere else.
4. The new client sends the code to `POST /api/pair` with a name for the device and receives a device token. The web client guesses the name from the browser and the system, in the operator's language ("Chrome on Linux", "Chrome no Linux"); a native client offers its platform's name for the device, such as the phone's. The operator can change it before pairing. The server stores only a hash of the token. A code works once.
5. Devices are listed in settings with their last activity, and can be revoked. Revoking closes that device's connections immediately. A client waits ten seconds at most for the server to confirm a revocation; without that answer it says the revocation is not confirmed, offers to try again, and reads the list again once connected, which shows whether the device is still there.

A device token grants everything the operator can do in J3 Bots. There are no narrower roles in the first versions.

Signing out a device ends its access. It is offered in settings and, while there is no roster yet (connecting, or before the first bot), as a quiet button on that screen. It takes four steps, each attempted whatever the others did, and each failure is logged on its own:

1. It stops sending the outbox.
2. If it is connected, it revokes its own credential on the server and waits up to ten seconds for the server's word, described below. If it is not, it asks the server nothing, but reads whether another tab recorded the server's refusal of its pairing meanwhile, as while it reconnected. No later step asks the server anything, so this is all the time sign-out spends on the server.
3. It deletes its pairing's drafts and unsent messages, which hold conversation text.
4. It deletes the credential, unless the device stores another one by then, and only then returns to pairing.

Every step acts on the pairing the tab follows when the operator confirms, read before anything waits. Stopping the outbox waits for an answer being recorded, and while it does, or while the server answers, another tab may learn of the revocation first, pair again and write. That pairing stays whole, with its credential and its text; the tab that signed out follows it, even before word of it reached that tab, since deleting the credential reads what the device stores. A notice says that another tab paired this browser again, so it stays signed in, and either that the old access ended or, when the server never confirmed it, that the old access may still show under Devices. The notice belongs to the page, not to the shell, which the pairing screen replaces meanwhile. If deleting the credential fails, the device stays signed in, and settings say that sign-out did not finish.

Only the server's word counts as the revocation confirmed: its answer, or its refusal of the credential on a ticket request. Revoking closes the device's sockets before the answer can arrive, so the refusal is usually what tells. Every tab of the device loses its socket at that moment and asks for a ticket after its own wait, so any of them may hear the refusal first. The tab that hears it deletes the credential and, in the same storage transaction, leaves in its place a record naming the pairing the server ended. The record holds no secret, says only that one pairing ended, which never returns, and the next pairing saved replaces it. A tab that is signing out and finds the credential gone counts the revocation confirmed only when that record names its pairing, or when it heard the refusal itself. One record is the price of keeping the credential and the word about it in the same cell, so a pairing saved in the second between another tab hearing the refusal and the signing-out tab reading it replaces that word: the notice then says the old access may still show under Devices, though the server ended it. Devices, read from the new pairing, shows the truth. When the server cannot be reached, or another tab only signed out here first, nothing confirms it: the device still signs out here, and the pairing screen says the server did not confirm it, so the other devices may list it until one of them revokes it.

A tab only ever shows, keeps or sends the drafts and unsent messages of the pairing it follows. Every record names the pairing that wrote it, and the rule holds by construction, not by erasing:

- The drafts and the outbox each hold the pairing they follow. It changes only under their own lock, in the same step as they drop everything they held. Every read projects only that pairing's records: another pairing's record reads as no record.
- Every write is that pairing's, and the storage transaction that writes it also reads the stored credential, and writes nothing unless it is still that pairing's. In a browser and in the desktop app the credential and the records are in one IndexedDB database, so the check and the write are one transaction. A platform that keeps the credential in a system keychain keeps a copy of the paired device id beside the records for this check: the mobile app does, in its SQLite database ([Mobile](#mobile)). A pairing never returns once it ended, so a write refused while the credential is still the tab's pairing was refused for another tab's change, and one refused otherwise means the pairing ended: the tab writes nothing more and follows the next.
- The same holds for presence: what the operator has in view is reported only on a socket of the pairing it was set under; a socket of another pairing hears that nothing is in view until the window says what it shows. A notification that arrives on a socket of a pairing the window no longer follows is dropped. An entry counts as seen only while its window shows it and has focus, as for what the window reports in view, so a reply that arrives in a background window both notifies and stays unread.
- A message goes only on a socket opened with its own pairing's credential. Any other command belongs to the pairing it started under: a socket of another pairing never runs it, and it fails as not paired.
- A file transfer carries the token of the pairing it started under, read once, and stops as soon as the tab follows another pairing or none: an upload under way never goes again under the next pairing.
- The pairing a tab follows changes in the same step as the credential it holds.

Erasing is cleanup. Whenever the pairing a tab follows changes (from none, to none, or to another), it drops what it held, erases the device's records of the pairing that ended, and only those, then reads the records of the pairing it follows now; its composer is read-only until it has, so nothing typed meanwhile is lost under them. Nothing of the pairing that ended shows from the moment the pairing changes, though dropping it may wait for an answer or a draft still being saved under it. When the drafts cannot be read, the composer stays read-only and says it couldn't load the draft, with a way to try again: an empty composer would look like no draft at all. A tab on the pairing screen that hears of a pairing another tab made reads that pairing's saved drafts the same way. A tab can close before it erased a pairing's records, so at launch the client erases every record whose pairing is not the one the device stores, read after the records: a record is written after its pairing is saved, so one that names another pairing names one that ended. When erasing fails, the records stay on the device, and no tab shows or sends them.

Ending a pairing never touches another: the stored credential is deleted only if it is still the one that ended, compared and deleted in one storage transaction, and a tab that finds a newer one follows it instead of returning to pairing. In a browser, every change to the stored credential is announced to the origin's other tabs with `BroadcastChannel`, and each loads it again, so pairing or signing out in one tab takes effect in all of them.

## Connecting

Every connection is one device's. The server accepts the device token as an `Authorization: Bearer` header on the upgrade, or a single-use ticket bought with it at `POST /api/socket-ticket` and passed as `/ws?ticket=…` within a minute. Either way the server checks the credential once, at the upgrade, and the socket is that device's until it closes.

All three clients use the ticket. A browser cannot set a header on a WebSocket, and cannot read the status of a refused upgrade, which reaches it as a plain connection failure. The ticket route is plain HTTP, whose status every platform reads the same way, so one path serves all three:

- Before its first ticket, the client checks `GET /api/server`. A server that speaks another protocol version is shown as incompatible and not retried until the operator asks.
- Every socket is opened with a fresh ticket, since a ticket works once.
- A 401 from the ticket route whose body is the server's own `NotAuthenticated` means the device is not paired or was revoked: the client forgets its credential, stops reconnecting and asks to pair again. Any other 401 comes from something in between, such as a reverse proxy whose own login expired, and counts as the server being out of reach: the client keeps its credential, drafts and unsent messages, and tries again.
- Anything else (no answer, a refused upgrade, a socket that closes after it opened) means try again, after a pause that doubles from half a second up to thirty seconds, jittered so clients do not return together. When the platform reports the network gone, the client closes its socket at once rather than wait for it to fail, which can take a long time; it then waits, and tries at once when the network returns.

A request in flight when its socket closes is sent again on the next socket. That is safe because every command carries its command id, and the rest are reads. Files go over HTTP with the same bearer: `POST /attachments` before sending a message that carries them, and `GET /attachments/:id` to open one. The ticket's rule holds for files too: only the server's own `NotAuthenticated` in a 401 means the device is not paired, and an answer that comes from another address, as when a proxy redirects the request to its own login page, did not come from the server. Either is a failure to try again, not a refusal.

No HTTP request waits forever, since a server or a proxy can take one and never answer. The server check, pairing and the ticket get ten seconds each, after which the server counts as out of reach and the pause above follows. A file transfer gets the same ten seconds plus time for its bytes over a slow link (32 KiB a second), fifteen minutes at most, counted until its last byte is read: an upload then starts again after the same pause, and a download says the file could not be opened. The installed web app's service worker sends a page load to the network first and opens the copy of the app it keeps when the network fails, when the server answers with an error of its own (a 5xx), or when the whole page, headers and body, has not arrived after four seconds. The page that loads is the network's answer itself, its headers, status and address untouched; the worker only reads a copy of it to the end. After the four seconds, a page still arriving is cancelled, and so is the body of one whose headers come later. A request with no answer yet is left to end on its own while the kept page shows: sent with an abort signal, it would no longer be a page load to the server or a proxy.

## Visuals

A bot's message can carry a **visual** ([decision 0030](../decisions/0030-a-visual-is-part-of-say.md)): a page the bot built, a chart, a table, a diagram or a mockup, as `MessageEntry.visual` (`{title, html, height}`, at most `MAX_VISUAL_BYTES`, 512 KB). Every client draws it the same way, from `@j3-bots/client-runtime`'s `visualDocument` and `@j3-bots/contracts`' policies; why the frame is shut as it is is in [Security: visuals](security.md#visuals), and how it sits in a conversation in the [design language](../design/design-language.md#visuals).

- **The frame.** A client never writes the page into its own document, and never into a `srcdoc` frame. The web and desktop clients load their own visual page (`VISUAL_FRAME_PATH`, `/visual-frame.html`, a few lines of script and no content) in an `<iframe sandbox="allow-scripts">` titled with the visual's title, and post it the document `visualDocument(html, theme)` builds: the bot's page under the visual's Content Security Policy, the theme's variables, a guard that shuts WebRTC and every nested document out of the page, and a script that reports the page's height once it has loaded. A page whose markup embeds another document or holds a declarative shadow root (`visualEscapesGuard`) gets no document at all, and shows as failed. The visual page writes that document over itself once, which also removes its own listener, so nothing posted later is read.
- **Height.** The client takes the height from a message only when it comes from that frame's own window (`ownFrameHeight`: `event.source` is the frame's `contentWindow`), and only as a number, clamped to 80 to 2000 pixels (`readVisualHeight`). A message from any other window, another visual's included, is ignored. Until the first report the frame holds the height the bot measured, or 240, invisible under a placeholder. The document's root keeps room for a scrollbar on both sides, so where scrollbars take space a page's width, and the height of a chart scaled to it, stays the same whether one shows or not; without it, a page first shown too short could keep a scrollbar it no longer needs.
- **Failure.** A frame that has not reported a height ten seconds after it is drawn shows "Couldn't show this visual." in its place: the visual page did not load, the page is stuck in a script that never ends, or it navigated its frame before it had loaded. So does a frame that loads a third time, after its visual page and the document written over it: the page navigated it, and the frame shows something else. Offline, the web app's service worker answers the visual page with the app's own page, which refuses to be framed, so a visual shows as failed until the client is back online (not yet observed).
- **Theme.** The document is built in the app's theme, light or dark, and built again when the theme changes. The page colors itself with the variables the theme sets on its `:root` (`visualVariables`, from `@j3-bots/design-tokens`), the names the `say` tool's description lists to the bot.
- **Full screen.** The visual's caption opens it in a dialog named by its title, with the page drawn again to fill it. Escape or Close returns focus to the caption's button.
- **Android** loads `visualShell(document)` in a WebView: a page under the visual's policy that frames the same document in an `<iframe sandbox="allow-scripts">`, as the web does, since a WebView itself loads a page unsandboxed. The document reports its height to that page, which passes it, from its frame's window alone, to an object the app puts on the WebView (`VISUAL_BRIDGE`, `J3Visual`); the app reads it with `readVisualReport` and sizes the WebView to it. The shell's frame loads once, with the visual; at a later load the shell tells the app the frame shows something else, and the card says it could not show the visual.

## Connector apps

A connector's tool can open an **app** ([decision 0048](../decisions/0048-a-servers-interface-runs-isolated-in-j3-bots-clients.md), [Server: connector apps](server.md#connectors)): an interface its server wrote, drawn under the work of the turn whose call opened it, below the fold's line, so it shows whether the fold is open or not. A fold names its apps (`WorkFoldEntry.apps`); a client opens each as it draws it (`connectorApp.open`). Every client runs the host's side of the MCP Apps protocol the same way, from `@j3-bots/client-runtime`'s `connectorAppHost`; why the frame is shut as it is is in [Security: connector apps](security.md#connector-apps).

- **The card.** A line naming the tool and its connector ("Stock · Wheelhouse"), then the app's frame, then whatever the app asks of the operator. The line and what follows the frame are the client's own, outside the frame, so the app cannot draw over them. It is the card's width, and starts 360 pixels tall.
- **The frame.** As a visual's: never the client's document, never a `srcdoc` frame. The web and desktop clients load their app page (`CONNECTOR_APP_FRAME_PATH`, `/connector-app-frame.html`, a few lines of script) in an `<iframe sandbox="allow-scripts allow-forms" allow="">` titled with the tool and connector, and post it the document `connectorAppDocument` builds: the app's own policy (`connectorAppContentPolicy`), the guard every visual runs first, then the app's document as its server wrote it. A document that embeds another gets no frame: the card says "Couldn't show this app."
- **Messages.** The client takes a message only from that frame's own window (`fromOwnFrame`), as JSON-RPC 2.0, and drops anything else unread. It answers `ui/initialize` with J3 Bots' capabilities and where the app is drawn (`hostContext`: the tool, the theme, the theme's colors, fonts and radii under the extension's standard variable names (`appStyleVariables`, `@j3-bots/design-tokens`), the language, the time zone, the platform, touch and hover, `inline` as the one display mode, and the frame's width with a 1,600-pixel height at most), and sends nothing else until the app says it is initialized; then the call's arguments (`ui/notifications/tool-input`) and its answer (`tool-result`), or `tool-cancelled` when the server kept none. A change of theme, language or width reaches the app as `host-context-changed`. When the card goes, the app is told (`ui/resource-teardown`) and nothing it sends is read after.
- **What the app asks.** `tools/call` and `resources/read` go to the server (`connectorApp.callTool`, `readResource`). A call the server refuses `needs-allow`, which it does while the bot is not in full access, waits on the operator, once for each tool while the card is drawn, and goes again once they allow it; the client keeps no copy of the bot's mode, so a bot that goes back to full access runs the next call without asking: "This app wants to run hold on Wheelhouse, as the bot." with **Allow** and **Don't allow**; one declined fails at the app. `ui/message` shows the text it would send with **Send** and **Not now**: only Send sends it, as the operator's own message to the bot. `ui/open-link` shows the address with **Open** and **Not now**: only an `http:` or `https:` address with no user name or password, opened in the system's browser. `ui/request-display-mode` answers `inline`; `ui/update-model-context` is refused, since J3 Bots gives a bot nothing an app says; any other request is unknown. `ui/notifications/size-changed` sets the frame's height, clamped to 80 to 1,600 pixels.
- **Android** loads `connectorAppShell(document)` in its own view (`apps/mobile/modules/connector-app-view`): a page under the widest policy an app may have that frames the document in the same sandbox, and relays what the frame sends, from its window alone, to an object the app puts on the WebView (`CONNECTOR_APP_BRIDGE`, `J3App`), in order; the app hands the shell the host's messages through a function of the view (`deliver`). The card, its line and what the app asks are the app's own, as on the web.

## Protocol compatibility

`PROTOCOL_VERSION` (`packages/contracts/src/http.ts`) is the first thing a client checks, and a server that speaks another version is shown as incompatible ([Connecting](#connecting)). Raising it locks out every client built before until it is updated, and the client says which side is behind and brings it forward over the update routes ([Updates, outside the protocol](#updates-outside-the-protocol)). A client compares versions for equality, so raising it also keeps a newer client away from an older server. So it is raised only for a change an older client cannot survive, or one a newer client cannot make against an older server, and a server may add, without raising it, what a client is built to pass over.

**What a client passes over.** Five sets stay open, because each is in data a client cannot avoid reading and each grows whenever J3 Bots learns something new to say:

- **Kinds of entry.** `entries.subscribe` and `entries.history` carry `ReceivedEntry`. An entry whose `_tag` the client does not know decodes as `UnknownEntry`: its kind, id, order and time, and nothing else. Entries stay in history, so one a client refused would keep the whole conversation from opening, for good.
- **Kinds of notice.** A notice whose `_tag` the client does not know decodes as `UnknownNotice`. Notices are the kind added most often: each new way for something to stop gets one, and so does a change a bot makes that the operator should see, such as `operator-named`.
- **Kinds in a roster preview.** `EntryPreview.kind` decodes a kind the client does not know as `unknown`. The roster carries every conversation's latest entry, so one new kind there would stop the whole roster.
- **Failure classes.** In a `turn-failed` notice and in a blocked bot's state, a failure class the client does not know decodes as `unknown` (`ReceivedFailureClass`), worded as a failure it cannot name. A new class is added as a provider fails in a new way, and the roster carries every bot's state. Whether the notice offers Try again is still the server's `retryable`.
- **Avatar tokens.** A bot's `Avatar` is two tokens, a shape and a color, each of which a client that does not know it draws with its fallback, apart from the other (`resolveAvatar`: a dome for a shape and slate for a color now, a circle and gray in 0.1.x). Only what a client sends is closed (`AvatarChoice`), since the server refuses a name it does not have. So a server may draw on new silhouettes and colors without a bump, but a client that sends a new one needs it: a server built before refuses the name, and creating or editing the bot fails instead of saying the app and the server don't match.

An unknown entry or notice shows in its place as one quiet line, "This needs a newer version of the app.", and a roster row as "Something this version of the app can't show". The read mark passes it like any other entry. An unknown notice offers no Try again: the operator could not tell what it would run again. Only a value the client does not know is unknown: an entry or notice of a known kind that does not decode is refused as before, so a broken server is never mistaken for a newer one. The server itself writes and stores only the closed `Entry`, `Notice` and `FailureClass`, and its handlers for `entries.subscribe` and `entries.history` are typed to answer only `Entry`, so it never sends `unknown`.

A field a client does not know is dropped as the client decodes, so a server may add a field that older clients can do without, and a client may read an optional field a server of the same version does not send yet, decoding it as null and doing without it: a work fold's `turnStartedAt` is one, with which a client ties the fold to its turn, and without which to its first step; a waiting bot's `since` (without it, a client takes the wait as one between turns); a roster preview's `ending` (without it, a fold of no steps reads "Did some work"), a roster preview's `order` (without it, the roster offers no Mark as read: the conversation is read by opening it), a starting engine's `install` (without it, the engine is only starting, and no download shows), a routine run's `dueAt` (without it, a run that started late reads as one on time) and a routine's `missed` (without it, the routine says nothing of the runs it missed while J3 Bots wasn't running, [Server: routines](server.md#routines)) are others. The 0.2 clients, the Android app among them, are from before `install`, `dueAt` and `missed`, so against a 0.3 server they do without those three as above. A protocol-7 client from before the others, which only unreleased development builds are, shows a fold of no steps as "Stopped after 0s", with nothing in its panel (**Read** in Effect 4.1.3: `effect/rpc/RpcClient` decodes with the RPC's parse options, which J3 Bots leaves at the default, and `onExcessProperty` defaults to `ignore`).

A turn's work is another ([Server: a turn's plan and its little ones](server.md#a-turns-plan-and-its-little-ones)): a work fold's `work`, a room's `memberWork` and a working bot's `littleOnes` are read as none from a server that does not send them, and a client that predates them shows a turn's other steps, without its plan or its little ones, since the server no longer writes the steps they replace. A plan step's status and a little one's are open: one the client does not know decodes as `unknown`.

0.11.0 added within protocol 11 what an older client can pass over ([decision 0072](../decisions/0072-errors-say-what-to-do-force-stop-and-whole-questions.md)). A turn's `retrying` decodes as false without it, and a client from before it shows the bot's step while the engine tries its AI again. A failed turn's `details` is dropped, so an older client shows the notice without Details. The `unreachable` failure class is in the open set, which an older client shows as an unexpected error. A question's `header` and an option's `preview` are dropped, and the question shows without them. A question card's `whole` carries an engine question larger than four questions of six options. Beside it, `questions` holds one placeholder that asks for an update, so an older client shows that placeholder rather than part of a question, and its answer never reaches the bot. `Bot.forceStop` and `Room.forceStop` decode as false without them. A client offers Force stop, which sends `bot.forceStop` or `room.forceStop`, only when the server says so: a server that sends either field as true has those RPCs. Against an older server, Stop stays Stop.

0.12.0 adds the `asks-before-acting` notice within protocol 11 ([decision 0083](../decisions/0083-only-the-engine-notices-a-person-can-act-on-show.md)). An older client decodes it as a notice of an unknown kind, and shows its one line that asks for a newer version of the app. It also adds a working bot's `activityKind`, the kind of the step it is on, from which a client words its line; it decodes as null without it, and a kind the client does not know as `unknown`, both read as work it does not name ("Working"). An older client drops it and shows the step's label as before.

0.13.0 drops, within protocol 11, what only measured a turn's time: a finished work fold's `waitedMs`, `waitedBeforeMs` and `background`, and a stalled bot's `quietSince`. Each decodes with a default in the clients that read it (0, false and null), so an older client still works against a newer server: it counts a finished fold's time without leaving out the waits, never says work goes on after the turn, and says a stall as "No recent activity".

**What a client calls without relying on it.** A client may call an RPC an older server of the same version lacks when it only tells the server something the server can do without, or asks for something the client can do without, and passes over any failure of that call. `settings.deviceTimeZone` is one: an older server answers it with a defect for an unknown request, and the operator's time zone stays as it was. `settings.subscribe` is another: a client reads the settings once with `settings.get` and then follows the stream, and against an older server, which answers with a defect, it keeps the copy it read, which changes only when this device saves, as before. The provider RPCs (`provider.harnesses`, `provider.signIn`, `provider.cancelSignIn`, `provider.connect`) are called on the same terms: only the desktop app calls them, and only in local mode, on the server it runs on its own computer, which comes with the app. That is a convention of the clients, not a rule the server keeps: any paired device may call them, since a paired device holds the operator's authority ([Security](security.md)), and gains nothing it did not have. A server without them answers with a defect, which the app reads as a server that cannot set the providers up from it, and it shows the command instead. A sign-in's failure reason is an open set, as the failure classes are: one the client does not know reads as a sign-in that did not work. It may also call one that serves a feature of its own and nothing else, when that call's failure shows as the feature's: `bot.template` and `bot.createFromTemplate` are two, and against an older server sharing says the template couldn't be prepared and creating says the bot wasn't created, while the rest of the client works as before.

**What a client offers only when the server says it has it.** A feature an older server of the same version lacks may be added without a bump when the server says it has it in data every client reads first, and a client offers the feature only then. The roster's organization is one ([decision 0022](../decisions/0022-the-operator-arranges-the-roster-in-sections.md)): a roster snapshot that carries `sections` comes from a server that has sections, a bot's `sectionId` and `entries.markUnread`. Against a snapshot without it, a client shows no sections and offers neither Mark as unread nor moving a bot into a section, and so never sends `section.*`, `entries.markUnread` or a `bot.update` with `sectionId`, which an older server would answer with a defect, or would take while dropping the field. `NotFound("section")` answers only those requests, so no older client receives it. Why a provider cannot run is another ([Engine: the adapter's interface](engine.md#the-adapters-interface)): a provider `unavailable` with a `reason` comes from a server that has `engine.recheckProvider`, and a client offers Try again or Look again only under such a provider. A provider without one, from an older server, reads "Unavailable now" with no action, as before. The reason is an open set: one the client does not know reads the same way. `NotFound("provider")` answers only that request, so no older client receives it. A harness's version is a fourth: a provider with a `version` comes from a server that has `engine.updateProvider`, and a client shows a version line and offers Update only under such a provider; `Conflict("provider-not-updatable")` answers only that request. An update's state is an open set too. J3 Bots' own copy of a harness is a fifth ([Server: J3 Bots' own harnesses](server.md#j3-bots-own-harnesses)): a Claude Code or Codex provider with a `copy` comes from a server that has `provider.installHarness` and `provider.cancelHarnessInstall`, and a client offers Install, its progress and Cancel under a harness that is not installed, the copy's version with Update in Settings, and the switch that turns its updates off, only then. Without `copy`, a harness that is not installed links to its maker's page with Look again, as before. Each provider line offers one Update: for J3 Bots' own copy it asks `provider.installHarness`, for the operator's own the engine (`engine.updateProvider`); a provider on J3 Bots' copy carries no engine `version`. A failure reason is an open set: one the client does not know reads as an install that could not finish. `Conflict("harness-not-installable")` answers only those requests.

**What needs a bump.** Everything else is closed, because a client acts on it: whether a card can still be answered, what Try again runs, which Android channel a push goes to. A value it misread would make it do the wrong thing, which is worse than saying the app needs updating. These need `PROTOCOL_VERSION` raised:

- a new value in any other set the contract lists: authors, a message's delivery and mentions, a card's status, an approval's kind, a work step's kind or status, a turn's ending, bot states, routine triggers and runs, roster items, subscription frames, errors, and `NotificationKind`, so a new kind of entry that notifies needs a bump where one that does not, does not;
- a field removed, renamed, made required, or given a new type or a narrower range, in anything a client decodes;
- a field a client must understand to act correctly, even when it is new;
- a new RPC or route a client relies on, and a change to what an existing one takes or answers: a client compares versions for equality, so it also refuses an older server, and a newer client of the same version would call what that server lacks.

Protocol 6 is the first whose clients pass over the open sets: from protocol 6 on, adding a kind of entry or notice, or a failure class, needs no bump. Clients of protocol 5 and before, J3 Bots 0.1.0 among them, refuse a conversation or a roster that holds one, so 6 shows them the incompatible screen instead.

Protocol 7 came with the twelve silhouettes and twelve colors (migration 20). Its clients send them whenever a bot is created or its look is edited, the look the picker starts on included. A server of protocol 6, J3 Bots 0.1.1 among them, refuses a token it does not have. Teal is the only one it shares, a color, so every look a new client sends carries a shape it refuses. A client of protocol 6 against a newer server draws every bot as a circle, gray unless its color is teal. Either way the client shows the server as incompatible instead, which asks the operator to update the app or the server so they match.

Protocol 8 comes with the 0.4 release, once for all its changes. One is a message's visual: a client that predates it would drop the field as it decodes and show the bot's text without the page it explains, so an older client shows the server as incompatible instead, never a message without its visual and never the page's source.

Protocol 9 comes with the 0.5 release, once for all its changes. One is the teammate conversations (`pairs.subscribe`, `pairs.messages.subscribe`, `pairs.history`): a client of 0.5 lists the pairs of bots beside the roster and opens their conversations, which a server of protocol 8 cannot answer. An older client against a newer server would still show every teammate message as a card in each bot's conversation, but no longer marked unread nor notified, so it shows the server as incompatible instead.

The bot's browser brought the `browser.subscribe` RPC, which lists a bot's tabs and who holds each, and the media socket at `HTTP_PATHS.browser`, which shows one tab and passes on what the operator does in it ([Server: the bot's browser](server.md#the-bots-browser)). A client of protocol 8 relies on both, and a server of protocol 7 has neither. It also added the browser help card: a `browser-help` entry, answered with `card.answer`'s `browser-help` answer, and its `browser-help` notification kind, which an Android client shows in a channel of its own. A server of protocol 7 refuses that answer, and a client of protocol 7 would decode the notification as nothing it knows. The media socket's frames are closed sets the client acts on: who holds a tab, a dialog that waits for an answer, why a tab cannot be shown. So a client of either version shows a server of the other as incompatible.

Connectors brought ([Server: connectors](server.md#connectors)) the `ConnectorRpcs` (`connectors.list`, `connectors.search`, `connectors.get`, `connectors.subscribe`, `connector.add`, `connector.update`, `connector.remove`, `connector.setBots`, `connector.beginSignIn`, `connector.completeSignIn`, `connector.acceptToolChanges`), which the Connectors screen relied on (since 0.10.0 no client sends `connectors.list`, `connectors.search` or `connector.add`, which the server keeps for clients on protocol 11, and `connectors.get` only for the card that asks for the operator's own app, [decision 0068](../decisions/0068-settings-lists-what-the-bots-added.md)), and the `connector` notification kind, a value of a closed set that names an Android channel, with the notification's `connector` field saying which card made it, which decodes as null when it is missing. Its sign-in card, `connector-auth`, and the `connector` step tool are in open sets, which a client of protocol 7 reads as an entry or a tool it cannot name; they needed no bump of their own.

Protocol 11 comes with the 0.9 release, once for all its changes. One is the skills ([Server: skills](server.md#skills)): `skills.subscribe`, `skill.read`, `skill.save`, `skill.install` and `skill.remove`, which the skills screens rely on (all but `skill.install`, since 0.10.0), and `lastChange` on a connector and a skill, which says who changed it last. The connector suggestion card is gone, with its answers: the bots add servers themselves, and a server of 0.9 deletes the old cards, so no conversation keeps one it cannot show. The steps of a bot's management tools (`mcp-server-added` and the others) are in the open set of step tools. The review of a connector's changed tools is gone too ([decision 0047](../decisions/0047-j3-bots-is-a-complete-mcp-host-at-the-current-specification.md)): `Connector` has no `review`, and `connector.acceptToolChanges`, which an older client would call and show, is gone. Its new RPCs are `connector.prompts` and `connector.renderPrompt`, which the `/` menu relies on; `Connector` says what its server said of itself (`server`); and the `connector-input` card is answered with `card.answer`'s `connector-input` answer, which a server of protocol 10 refuses.


### Updates, outside the protocol

A client that cannot open the socket, because the server speaks another protocol, still has to see both versions and bring the one behind up to date. So the update routes are plain HTTP beside the protocol, not part of it ([decision 0032](../decisions/0032-updates-are-served-outside-the-protocol.md)):

- **Their own version, in the path.** `UPDATE_HTTP_PATHS` are `/api/update/v1/status`, `/check`, `/channel` and `/start`, with `UPDATE_API_VERSION` 1. `PROTOCOL_VERSION` does not cover them and a bump of it does not touch them. Their shapes are frozen: a later version adds paths and leaves these as they are, so a client of any protocol reads any server's status.
- **Found from `GET /api/server`.** `ServerInfo.updateApi` names the version the server serves, and is null from a server without them (a client decodes it as null when it is missing). A client offers to update the server, or to change its channel, only when it is set.
- **The device token, and JSON.** Each route takes the device token as a bearer and answers 401 without one, so any paired device may use them. A `POST` body is JSON, and any other content type is refused before it is read, so a page elsewhere cannot send one without a preflight the server never grants.
- **Open sets.** A client decodes the answers with `ReceivedUpdateStatus` and `ReceivedUpdateRefused`, in which a state, a reason, an outcome or a channel it does not know reads as `unknown`. It shows an unknown state as an update under way, and an unknown reason as one it cannot name. The server writes only the closed `UpdateStatus`.
- **One exact version.** `start` takes exactly the status' `available.version`, never a tag: the newest release on the server's channel, newer than the one it runs, whose signature verified ([Security: updates](security.md#updates)). Anything else is refused with `not-available`, before anything is downloaded.
- **Following it.** `start` answers 202 once the update runs. Its progress is read by polling `status`, whose `state` is the stage and `run` the versions and the device that asked. The server stops in the middle, so a client keeps polling through refused connections until a status says the run ended ([Server: updating from a client](server.md#updating-from-a-client)).
- **How it ended** is `lastResult`, the same on every client, whichever asked: `done`, `rolled-back` with its reason, or `failed`, after a rollback that did not finish. A server that cannot update itself says why in `canUpdate`, with the command that updates it by hand; the desktop app's own server says `desktop-managed`, and the app reports that update itself. A client on another device reads the same word for one more thing (`runByDesktopApp`): that computer has no `j3-bots` command, so an empty conversation whose hello waits for a model sends the operator to Settings → Providers in the app there, not to `j3-bots provider connect`.
- **The channel** is also `Settings.updateChannel`, which `settings.update` changes, and a client sends it there only to a server whose `updateApi` is set: an older server would take the rest of the change and drop it.

What every client does with them is in `packages/client-runtime/src/update/`: it reads the status when it connects, when the server turns out to speak another protocol, when a screen that shows it opens, and every hour while it stays connected, so a release the server finds meanwhile reaches it; a read sent before this client's latest start is dropped when it answers, since it shows the server as it was before; it follows an update it saw start every two seconds, counts a server that stops answering meanwhile as restarting, and after ten minutes without an answer says the update has not finished, with `j3-bots doctor` to run on the server's machine. It reports how an update it followed ended once, then reconnects. A route that answers 404 is a server from before them, read as one to update on its machine with `j3-bots update`. The one tap sends `start` without `stopWork`; only a `work-running` refusal makes the client ask, naming how many bots have work running, and then it sends again with `stopWork`. Any other refusal reads the status again, so the reason shows at once. Its words are shared too (`serverUpdateLine`, `updateResultLine`, in `client-runtime/wording`), so the web, the desktop and the phone say the same thing. On the web and the desktop:

- **Settings → About and updates** shows the server's version, how its update stands, its channel, and "Update now", which opens [the update prompt](#the-update-prompt); a rollback the server still runs after stays there with why and the server's own detail. In local mode the server has no row: the app carries it, so the app's update is the server's ([Its version](#desktop)), and the app's row says where the bots on this computer stand after the app moved them, with Try again (`retryServerUpdate`) after a rollback.
- **Versions that do not match.** The connection's `incompatible` state carries the server's version, and the protocol says which side is behind. A server behind the desktop app is offered its update on that screen. The screen first has the server check its release feed once (`POST check`), since a server looks only every few hours and may not have seen the release the app came from, and says there is no newer release only once that check has ended (`serverBehindLine` in `client-runtime/wording`, which every client shares); an app behind the server updates itself there; a browser reloads, since the server serves the page. Retry and changing server stay on both.
- **The restart in the middle.** While a server this device updates does not answer, the connection line says the bots are updating to the new version, not that the connection was lost.

### The update prompt

When a newer release is ready for the server or for the app, one dialog opens in front of the app, on every client, and its "Update now" updates the server first and this client after it ([decision 0051](../decisions/0051-an-update-asks-in-front-and-goes-server-first.md)). Every client runs the same model and runner, `prompt.ts` and `UpdatePrompt.ts` in `packages/client-runtime/src/update/`; the web, the desktop and the phone draw it (`apps/web/src/components/UpdatePrompt.tsx`, `apps/mobile/src/update/UpdatePrompt.tsx`) and say how their own app updates (`clientSideOf` and the runner's `update` in each `updatePrompt.ts`).

- **When it opens.** Only on a paired device. The server's release counts when this client can start its update (`serverOffer`: a verified, newer release, `canUpdate` able, no update running). The app's counts once it is ready, and only while the server is known to be current: its status read, no update running, nothing to offer (a server from before the update routes counts as current). While the status is not read, the server does not answer or an update runs, the app's version waits. The app's is ready: the desktop app's download verified, or a deb or Mac build's release found; the Android app's release found with "Update automatically" off. In local mode the server is the app's own, so only the app's part is offered. It does not open over the screen for a server this client cannot talk to, which already offers the side behind; a sequence under way goes on there.
- **What it says.** The version, one sentence on what "Update now" does, up to five highlights, which the server reads from the release notes and sends as `highlights` in the update status, and a link to the notes. A desktop app's own version has no highlights, since the app does not read notes from its feed.
- **The sequence.** "Update now" sends `start` for the status' `available.version`. A `work-running` refusal asks, naming the bots, with "Stop and update", which sends it again with `stopWork`. The prompt then shows the server's progress with the shared words. The server's part ends with the first status that shows no update running, the follower's or the one a reconnect reads, and the client's part starts only when that status says the update ended `done` on the version asked for and the server runs it. Then the desktop app checks its feed, downloads, verifies and restarts; the Android app checks, downloads, verifies and installs through its session; a browser reloads. In local mode, the app's restart stops the bots on this computer, so the prompt first asks when the roster shows a bot with a turn under way, or while the roster is not read yet, as work that may be running. With the server current, the app's part runs alone; a deb or Mac build opens its release page.
- **A failure stops it.** A refusal, a server that cannot be reached, an update that rolls back or fails, one that goes ten minutes without an answer, and one whose status does not say the server runs the version leave the client as it is. The prompt says why, with the command to run when there is one, and offers "Try again". "Try again" reads the server's status first when it is not known: a server that reached the version after all goes on to the client, one that still offers the release starts it again, and anything else stays where it failed. An app that does not update after its server did offers "Try again" for its part alone, and counts the bots at work again before a restart that stops them.
- **Later and the way back.** "Later" closes it for 24 hours for the versions on offer, kept on the device (`j3:updatePromptSnooze`); a newer version on either side opens it sooner. A part that runs can be hidden, and the prompt comes back when it needs the operator. The way back is one line: in the roster's footer, above Settings, on the web and the desktop, and over the roster on the phone.

## Suggested replies

A bot's conversation can offer the message the AI guessed the operator will send next ([Server: Suggested replies](server.md#suggested-replies), [decision 0073](../decisions/0073-a-suggested-reply-follows-what-the-operator-saw.md)). The server puts it on the bot (`Bot.suggestedReply`), with the entry it follows, and a client shows it only while that entry is still the newest one it shows, a finished work fold after it aside (`offeredReply` in `client-runtime`): a message the operator just sent, still in the outbox, or one that just arrived takes it away before the server says so. A room never has one.

The composer shows it as T3 Code's does: in place of its placeholder, faint, while the draft is empty and nothing is offered above the composer (a mention or prompt list, a prompt's form), with **Use** beside it. Use, or Tab on the web, puts it in the draft with the caret after it, for the operator to send or change; it is never sent by itself. Typing hides it, and Escape on the web sets it aside until a later answer brings another. The field keeps its own name for assistive technology, and the suggestion is its description (the web) or Use's hint (Android). Use arrives as anything new in place does: `appear` on the web, its counterpart on Android, and neither moves under reduced motion.

Settings → Providers has the switch, under the AI accounts, with what it costs in plain words. A server that predates it sends no `suggestReplies` in Settings, and the switch does not show.

## Behavior every client must get right

- **Offline and reconnect.** A message typed while disconnected is kept and sent on reconnect, exactly once, and the messages of one conversation reach the server in the order they were written. Sending moves the message from its draft to the outbox in one storage transaction, so a crash leaves it in exactly one of them; if the device cannot keep it, it stays in the draft and the operator is told. A draft is kept whatever its length; the limits of a message apply when it is sent, checked against the same schemas and limits the server applies (its text, its number of files, an empty file, the size of each inline image and of all of them together), both where the composer sends a draft and where any message enters the outbox: a message over one is not sent, the draft stays as it is, and the composer says why. While that transaction runs, a few milliseconds, the composer is read-only and takes no files, so nothing typed meanwhile is lost.
- **Several windows.** Every window of a device holds the same drafts: a window is told when another keeps, empties or sends one (a browser announces each change to the origin's other tabs with `BroadcastChannel`, and the desktop app's two windows are two such tabs), reads it, and shows it as the device now keeps it, so what is typed in one shows in the other and the next write there starts from it. A window that is not told, or is told late, finds the change as it writes, by the rule that follows. Each draft is stored with a revision. Every write of it, as the operator types and when Send moves it to the outbox, claims the revision this window last read or wrote; if another window sent or changed the draft since, it writes nothing, and this window shows the draft as stored, with its own files still uploading or refused on top, as far as one message can carry them (a file still uploading that no longer fits stops, and says why), and, when it was sending, tells the operator it sent nothing. A draft emptied or sent stays stored, empty, with a revision of its own, so a window that read it before still finds it changed; it reads as no draft, and there is at most one such record per conversation. One rule keeps this whole: every operation on a draft (autosave, deletion, Send, Restore) runs under this window's draft lock (one for all of its drafts) and reads its inputs, both the in-memory draft and the expected stored revision, only after acquiring the lock. Send commits exactly the text and files the operator pressed Send on, captured at the press, or nothing. Only what is persisted is ever written: upload progress and failed files live in memory only. The lock is the window's own; between windows, the revision decides. When this window held text the device never kept, the composer offers it back, saying the operator's earlier text was replaced in another tab, with Restore and Dismiss, and announces it to assistive technology each time newer text is offered; a toast speaks only when Send sent nothing. Restore writes the text as a new change over the stored draft: nothing is written back unless the operator asks. When the device cannot write a draft, or cannot read the one another window changed, the window keeps the draft as it holds it and tries again, under the same revision claim, after a pause that grows with each failure, until the device keeps it or shows what another window kept; meanwhile the composer says quietly that it is not saved yet, and Send sends nothing and says the device couldn't keep the message. Text the device kept, the other window had in front of it, so there is nothing to restore. The offer, one text per draft, stays beside the composer until the operator restores it, dismisses it or sends the draft, through any later change: a change that displaces no new text keeps it. A change that displaces newer text the device never kept replaces it: that text is the last the operator wrote, and the older one, which the newer was typed after, goes. Unsent messages follow one rule: the stored outbox records are the only truth about them. Every window's list of outgoing messages is a projection of storage, read again whenever another window changes the outbox, after each read a delivery makes, on every connection, and every five seconds while connected, which bounds how long a message waits when the window that kept it closed before telling the others. Delivery, Retry and Discard act on the stored record, claimed with the state the window expects in one storage transaction, so a window that missed a change does nothing rather than undo it; when the device cannot write the claim, nothing changes and a notice says the change wasn't saved. Every attempt to deliver a message has its own persisted revision. A claim (Retry, Discard, recording an answer) names the revision it expects. A caller waiting on an attempt is answered from storage with what became of that attempt: a record keeps the failure of each earlier attempt, so a caller of an attempt another window has since replaced learns how its own ended, not how a later one did. The command id stays the same across attempts, so the server applies the message once. Recording the server's answer is part of the attempt: the window keeps the conversation's lock until the device holds the answer, trying a failed write again a few times within a fraction of a second, and never sends the attempt again meanwhile. When the device still cannot record it, the message says so at once, and the window tries again to record the answer every five seconds, connected or not, since recording needs no socket, instead of sending it again, each answer on its own so a conversation another window is sending holds up no other; a failed read of the outbox is tried again the same way, so what the window shows catches up with what the device keeps; another window, which does not have the answer, may send the same attempt, which the server answers from its receipt. An accepted message leaves the conversation when its entry arrives, or when a read of the conversation started after the window knew the server had it holds no such entry: the entry is then older than the history loaded, where scrolling back finds it. A delivered or discarded message leaves a record of its outcome for ten minutes, so a window still showing it can tell one from the other. A window's memory holds a message only when the device could not keep it. One window at a time sends a conversation's messages, holding a lock named for that conversation, and only while its connection lives: a window whose socket closes lets go of the lock, and a connected window sends what it was sending. The window that holds the lock sends everything the device keeps for the conversation in the order it was kept, given by a sequence number the outbox assigns in the transaction that keeps the message. A browser announces each change to the outbox to the origin's other tabs with `BroadcastChannel`. A page served over plain HTTP on a local network has no Web Locks API, so there each tab sends on its own: no message is recorded twice, but two tabs can interleave their messages to one conversation.
- **A message sent again after a reload** leaves the conversation once the server accepts it; its entry may be older than the history loaded, and shows where it belongs when the history is read.
- **One conversation everywhere.** An entry sent or answered on one device appears on the others without a reload.
- **Cards resolve once.** Answering a question or an approval on any device resolves it on all.
- **State is the server's.** A client never infers "the bot is working" from its own timers. It shows what the server reports and marks its view as stale when disconnected.
- **The engine's first download shows.** While the server downloads the engine (its status `starting` with `install`, [Engine](engine.md)), every step of the first run says so in its one quiet line, with the share downloaded (`gettingReady` in `client-runtime`, which counts the harnesses the server downloads beside it), an AI account open on the first run's connect step says how far its own download is in place of that line, and Settings → Providers says it as its first line: "Downloading the engine… 42 of 180 MB", or the megabytes alone when the size is not known (`engineDownload` in `client-runtime`). Starting and downloading are drawn as on their way, not blocked. The web gallery shows both.
- **Connecting an AI is one model on every client** ([decision 0066](../decisions/0066-connecting-an-ai-is-picking-the-account-you-have.md), [decision 0085](../decisions/0085-signing-in-is-one-row-and-the-browser-opens-by-itself.md)). `presentation/aiAccount.ts` in `client-runtime` turns the engine's status, the server's own install of each harness (`providerFix` once the engine reports the provider, `EngineStatus.harnesses` before it does, so an account shows its download while J3 Bots still starts), the server's harness locations and this client's own sign-ins into one state per account (`AiAccountState`: connected, finishing, signing in, downloading, signed out, missing, being checked, a problem, or J3 Bots still starting), says what the account's one button does there (`aiAction`), and whether it is on its way with nothing left to press (`aiOnItsWay`), which the first run's Create follows. `wording/aiAccount.ts` puts each state in the operator's words and keeps what the engine or a sign-in said for a folded "Details"; `react/aiConnect.ts` holds what the app remembers of it while it runs (`AiSession`, shared under `J3ClientProvider`): a sign-in asked for before it could start, which it carries through the download, asking for one nothing started, to its start, once, from whichever screen shows the account (`useAiConnect`). The web's and the Android app's `AiConnect` components only draw that, one row per account (`AiAccountRow`) whose status line carries its action, in the first run's step, Settings → Providers and a conversation whose bot waits for its AI. The page a sign-in waits on is opened by `ProviderSetup` in `client-runtime` as soon as the server reports it, once per sign-in. Where an account signs in (`AiPlace`) is the one thing that differs by client: `here` in the desktop app on the server's own computer, which runs the sign-in; `desktop-app` from a device that reaches that app's server (`runByDesktopApp`); `server` elsewhere, with the account's command from the contract (`signInCommands`).
- **Notifications are the server's call.** A client reports what the operator has in view (a conversation or room in a window that shows and has focus, with no details sheet or dialog over it, or nothing; a modal hides everything under it from assistive technology except live regions and what holds them, so the conversation holds none, and the header's announcements are spoken by a region outside it, which drops the last one when another conversation is chosen) on every socket, and shows each notification the server sends, except one about what it has in view, which the server can send before it hears the view on a new socket. It never decides by itself what deserves one.
- **Every action has a name.** A command's label, its shortcut hint, its menu entry and its accessible name describe the same action on the same object.
- **Languages from the first screen.** Interface text goes through the translation layer from day one, as whole sentences. English is the source language.
