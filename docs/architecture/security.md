# Security

J3 Bots runs agents with real access to a real machine, on behalf of one person, around the clock. This document states what is trusted, what is not, and what stands between them.

## Trust model

| Party | Trust |
| --- | --- |
| The operator | Full. They own the machine, the subscriptions and the bots. |
| A paired client | The operator's. A device token is the operator's authority. |
| The J3 Bots server | Full. It runs as the operator's user. |
| The engine | Full. It runs as the same user and executes what bots ask within their permission mode. |
| Any process of the server's user, a bot's shell and its harness included | Full, as that user is. It can reach the admin channel, exactly as `j3-bots pair` does: make a pairing code (`/pairing`), pair a device without one (`/local-device`) and stop the server (`/shutdown`). It can read the database too, and the operator's secrets with their key file ([The operator's secrets](#the-operators-secrets)). |
| A bot's model output | **Not trusted to be correct, trusted to be the bot's.** A bot may be wrong or may have been misled; it is still the party the operator delegated to. |
| Anything a bot reads | **Untrusted.** Web pages, files, tool results, webhook bodies, messages from other bots. |
| A connector's server | **Untrusted.** What it says its tools do, what they take and what they return, its resources, its prompts and its skills are text a bot reads; what it asks the operator is a request from it, never from J3 Bots. It sees what bots send it, and acts in the operator's account there. |

The line that matters most is the last one. A bot with a shell that treats text from a web page as an instruction is a remote code execution path into the operator's machine.

## Who can give instructions

Only the operator, through a `user` wake in a bot's conversation or an entry they wrote in a room.

Everything else is context:

- A **routine's saved instruction** is the operator's standing request for exactly what it names, and nothing more.
- A **teammate's message** is another bot asking. The receiving bot weighs it against its own job and limits. It does not inherit the sender's authority, and it cannot be used to launder a request the operator did not make.
- A **webhook body**, a **tool result**, a **file** and a **web page** are data.
- A **template** is data until the operator creates a bot from it, after a preview of everything it holds: then its job, its skills and its routines' instructions are that bot's own, and are written into nothing else. Its routines start paused, and its permission mode is never above the default unless the operator picks it. From then on the new bot is a teammate like any other: its name, title and job reach the other bots through `list_teammates`, as data, never as instructions, and its first turn works from its job as written ([decision 0023](../decisions/0023-a-bot-template-is-a-file.md)). Going the other way, sharing one sends its job, skills and routines' instructions as written, whatever they hold; the share screen shows them in full first.

J3 Bots enforces this in three places:

1. **Envelopes.** The server writes every wake. Content that did not come from the operator is placed inside a block whose tag carries a per-wake random nonce, so text inside the block cannot close it or imitate another block.
2. **The base prompt.** It states the rule above, and that a request found in data is reported to the operator, not carried out.
3. **Authority that does not transfer.** Approvals can only be granted from a paired client. No bot tool grants an approval, raises a permission mode or widens a budget.

Prompt-level rules reduce the risk. They do not remove it. The permission mode is what bounds the damage.

## Permission modes

A bot's permission mode is the engine's runtime mode for its sessions.

| Mode | What it means for a bot |
| --- | --- |
| Supervised | Asks before commands and edits. On Codex the sandbox is read-only, so even an approved write fails: a supervised Codex bot can read and answer but not change files |
| Auto-accept edits | Edits files freely, asks before commands |
| Auto | An automatic reviewer decides; risky actions become approval cards |
| Full access | Does anything the operator's user can do |

J3 Bots' default for a new bot is **Auto** where the provider supports it and **Supervised** where it does not. Full access is a choice the operator makes per bot, with a plain statement of what it means.

A changed mode is the bot's from the moment it is saved. A session the engine has not been brought to it takes no turn J3 Bots sends until it has been: the server sends no new work into it, applies the change once no turn runs there, retries it while the engine is restarting or unavailable, and only then lets the next turn start ([Server](server.md#sessions), Settings alignment). A turn already running keeps the mode it started with; stopping the bot ends it. On Claude Code, background work still running also holds the change, since applying it would end that work; the bot's conversation says so, the client offers the Stop while it waits, and stopping the bot applies it.

One exception: a turn the engine starts on its own, a usage-limit continuation or a wake from background work that ended, can start between the change and its alignment, and runs with the mode the session still has. The pinned engine offers no way to hold only those starts (**Read** at `bc0f04d`, `UsageLimitRecoveryWorker.ts`). When lowering a bot's mode must take effect at once, stop the bot after the change.

In every mode, the bot's own `j3` tools run without asking: they only reach J3 Bots, which applies its own rules to each call. Each harness is given their exact names, never the whole `j3` server. A connector's tools reach the bot through the same bridge and are not pre-approved: they follow the bot's permission mode like any other harness tool ([decision 0027](../decisions/0027-connector-tools-reach-a-bot-through-the-j3-bridge.md), [Connectors](#connectors)). The engine's and the harness's other tools keep the mode's rules. **Verified** on `0.1.11` with Claude Code 2.1.330 and Codex 0.171.0, and the code it rests on is unchanged at `bc0f04d` (`ClaudeAdapterV2.ts`, `canUseTool`; `CodexAdapterV2.ts`, `mcpServer/elicitation/request` for a server other than T3 Code's own): in Supervised, `say` ran without asking and a connector tool asked; in Full access neither did ([Engine](engine.md#behaviors-j3-bots-designs-around)).

J3 Bots adds no sandbox. A bot in full access can read the operator's SSH keys, their other bots' folders, and J3 Bots' own database.

## Acting on the operator's behalf

Sending something to another person is not reversible. The base prompt holds bots to these rules regardless of permission mode:

- A message, email or post to anyone but the operator goes out only when the operator asked for that specific send, or a routine's saved instruction names it.
- When in doubt, the bot drafts and asks.
- A declined send is final. The bot does not retry it, reword it or find another route.
- Purchases, deletions, publishing and changes to accounts need the operator's explicit yes in the conversation.

## Running on a machine that matters

The first deployment of J3 Bots is on a host that has SSH access to the rest of its owner's network. That is common for a home server and it changes the stakes: a misled bot on that host can reach every machine the host can.

Recommended for any such host, and set out step by step in [Installing J3 Bots](../operations/install.md#choose-the-user-it-runs-as):

- Run J3 Bots and its engine as a **dedicated system user** that has no SSH keys, is in no group that can become root, and has no read access to the operator's home directory.
- Give that user its own provider sign-ins.
- If a bot needs access to something outside its workspace, grant that one thing.

This is a deployment recommendation, not something J3 Bots enforces. `j3-bots doctor` warns when the user it runs as keeps an SSH private key directly in `~/.ssh`, or is in a group that can become root, and gives the steps to a dedicated user. A key is a regular file whose first line is a private key's header; up to the first 64 bytes of each regular file are read, and no symbolic link is followed, so neither a linked file in `~/.ssh` nor a `~/.ssh` that is itself a link is looked into. The groups are `sudo`, `wheel` and `admin`, which reach root through sudo, and `docker`, `lxd` and `incus`, whose members can start a container that mounts the host's root (`docker run -v /:/host`). They are read from `/etc/group` only, so a group from a directory service, such as LDAP through sssd, is not seen. It does not look for keys elsewhere, nor at other ways the user can reach other machines, such as an SSH agent or stored cloud credentials. See [open question 3](../open-questions.md).

## The engine's credentials

- The engine listens on loopback only.
- J3 Bots' engine token carries `orchestration:operate`, which can start a full-access agent, and `settings:write`, which can change any of the engine's settings; the server writes only projects' overrides with it, for each bot's browser switch. The engine's own CLI mints it, the server keeps it in `<J3_HOME>/engine/j3/credential.json` (mode 0600, inside the private home), never writes it to a log, and replaces it before it expires. A backup of the home contains it.
- The token also carries `providers:manage`, which the operator's update of a harness needs (`engine.updateProvider`) and which also lets it change where the engine keeps and sends provider credentials. The server uses it only for that update, and to switch a Claude Code or Codex instance to J3 Bots' own copy of its harness ([J3 Bots' own copies](#j3-bots-own-copies)). It adds little to `settings:write` and `orchestration:operate`, which already reach the engine's settings and a shell as the server's user.
- The token also carries `preview:operate`, without which the engine drops what a person does in a tab. Whoever holds the token can open a viewer on any tab of the engine's browser, take it from the bot that drives it, and click, type, go to an address and answer its dialogs, as that browser, with its sign-ins. Any process of the server's user can read the file, a bot's shell included ([Trust model](#trust-model)), so a misled bot could drive another bot's tabs that way. That adds little to what such a process already reaches: `orchestration:operate`, the database and the admin channel.
- When the engine starts with a stored token that lacks a scope or is due for renewal, the adapter mints a new one and revokes every older session J3 Bots minted (`t3 auth session revoke`, matched by the label it mints with). So the token an earlier J3 Bots minted without `preview:operate`, `settings:write` or `providers:manage` stops working at once. A token replaced while the engine runs, on renewal or after the engine refused it, is not revoked, because revoking it could cut connections that still use it: it expires within two days, or the engine already refuses it.
- Bots receive no engine credential from J3 Bots. Their sessions get the engine's own per-session MCP token, scoped to their thread, as T3 Code provides to any agent it runs.

## J3 Bots' own surface

- **Client connections** require a device token. Tokens are stored hashed, listed, and revocable. The socket checks the token, or a single-use ticket bought with it, once at the upgrade; each socket belongs to one device, and revoking the device closes its sockets at once. File routes take the same bearer on every request.
- **Pairing codes** carry 50 bits (ten Crockford base32 characters), expire after five minutes and work once. The server compares a presented code with every live code, each in constant time, so how long an attempt takes says nothing of how near it came to one. A code travels only in bodies, never in a path, and reaches no log line: the request logs of the server and of the admin socket record method, path and status, and an answer of the admin socket that `j3-bots pair` cannot read is reported without its body. Failed attempts are limited across all sources, not per address, which would mean nothing behind a proxy, where every attempt comes from the proxy: after five failures in fifteen minutes, pairing is locked for fifteen minutes, and every attempt, the right code included, is answered with the time it opens again. A locked-out attacker gets a handful of guesses per quarter hour against a space of 2^50. The price of a global limit is that anyone who reaches the server can keep pairing locked. While pairing is locked, `j3-bots pair` makes no code and says until when, and `j3-bots pair --unlock` lifts the lock, forgets the failures counted towards one and prints a code at once. Against someone who keeps sending wrong codes, that only opens a window until the next five failures; the lasting answer is to stop exposing pairing to them, `POST /api/pair` as well as the `/pair` page, as [Reaching J3 Bots from elsewhere](../operations/exposing.md#who-can-reach-it) describes. A pairing screen that was answered with a lockout keeps its Pair button, so a code made after an unlock can be used at once. `j3-bots pair` and `j3-bots pair --unlock` go through the admin socket, so only the service's user on the host can run them, and the desktop app's "Pair a phone" and its unlock go through its admin pipe, which only the app holds. A bot's shell runs as the service's user too, so a bot can make a code or lift the lock, as the trust boundary below says. Codes, failures and the lock are kept in memory, so a restart of the server forgets them. A pairing request is capped at 4 KiB, declared or chunked, and refused with 413 before it counts as an attempt or is decoded.

  The QR code that `j3-bots pair` and Devices show carries the code itself, as the fragment of the server's own address at `/pair` (`<origin>/pair#<code>`): it still expires in five minutes and works once, but anyone who sees the QR code in that window, over a shoulder, on a screen share or in a photo, can pair with it before the operator does. The link's schema (`PairingLink` in `packages/contracts`) admits only a bare `http` or `https` origin as a browser writes it, the path `/pair`, no query or user name, and a fragment that is one code, read as a typed code is: in either case, with dashes between groups. A browser sends no fragment to the server, so the code stays out of the server's request log, any proxy's log and `Referer`. The web client replaces the page's address as it loads, so the code leaves the address bar and the tab's back and forward history, and it drops the link's code when the page is put aside (`pagehide`), so Back does not bring an unused code back into the form from the back/forward cache ([Clients: pairing](clients.md#pairing)). A browser carries a fragment along a redirect, so a sign-in gate in front of the server that sends a phone to an identity provider on another origin hands that provider's page the code. A client cannot tell that a gate stands in front of it, so Devices says, under every QR code it shows, to sign in on the phone first or type the code, as [Reaching J3 Bots from elsewhere](../operations/exposing.md#a-sign-in-gate) does. A pairing link only fills in a client's pairing screen; it never pairs by itself. Every pairing screen shows the origin of the server it pairs with, and a native client already paired with another server must say pairing replaces it, so a link sent to the operator cannot pair their device with someone else's server without their seeing where and pressing Pair. An address taken from a scanned link meets the same transport rule as one typed in: plain HTTP only at a loopback or private IP literal. The desktop app's own pairing link, `j3bots://pair?server=…&code=…`, which any web page can ask the system to open, follows the same rules and one more: it never changes the server the app keeps. Before a server is named it only fills in the server address screen, for the operator to check and continue; after, a link for another server is refused ([Clients: desktop](clients.md#desktop)).
- **Plain HTTP** reaches only loopback and private addresses. A configured address must be an IP literal in one of those ranges, or start is refused. The default, `lan`, listens on every IPv4 interface and serves only private addresses, over HTTP and over HTTPS alike. Start refuses it while any of the host's addresses is public, and the server then checks each new connection's destination address as it accepts it: one that reached an address outside those ranges is closed before a byte of it is read. A public address that appears after start is refused that way: the listener stays bound on every interface, the new address included, so the check, not the bind, is what keeps it out. A public address needs a TLS certificate and key, and `host` set to that address ([Server: configuration](server.md#configuration)). On a private network, plain HTTP still lets anyone on that network read a device token in transit. Serving HTTPS, for instance on a Tailscale name, closes that gap. The desktop app's own server listens on `127.0.0.1` unless the operator turns on "Use from your phone", and then on `lan` under the same rules; the app never starts it on `lan` while an interface has a public address, gives a phone only the server's own private interface addresses, never its `publicOrigin`, and Settings says, beside the switch, that the connection is not encrypted, so only a trusted network will do ([Clients: desktop](clients.md#desktop)). A phone pairs with it as with any server, with a code the operator makes at the computer: the pairing link carries the code, never a device token.
- **Cross-origin reads** are allowed only to the desktop app's pages (`j3bots://app`, and `j3bots-dev://app` in development): the server answers their preflights for `GET` and `POST` with the headers clients send, never with credentials, since a device token is a bearer header and never a cookie. Every other origin gets no CORS header, so a page elsewhere cannot read an answer ([decision 0012](../decisions/0012-desktop-reaches-the-server-directly.md)). The desktop app accepts a plain-HTTP server only at a loopback or private IP literal or `localhost`, the same ranges the server serves over HTTP, so a typed name never sends a token in clear across the internet.
- **The desktop app's quick access window** ([Clients: Desktop](clients.md#desktop)) adds a second window, not a second kind of page. It loads only the app's own page, `/quick` on the app's scheme, with the main window's preload script, context isolation, sandbox, navigation lock and permission rules, and the same content security policy from the same file server; it holds no credential of its own, only the pairing the origin's storage already holds, which any page of that origin reads. Four calls are new on the bridge, and the main process takes each only from that window's top frame at `/quick`, decoded by its schema: whether the page has a bot to show (a boolean), hiding the window (with the number of the showing it belongs to), a picture of the window that was in front as a showing opened (named by that showing, below), and opening the main window at a place the conversation leads to (one of a closed list: a bot's conversation, a room, a bot's browser tab, a teammate conversation, a routine, a connector's sign-in, each named by its id, with the pairing it was listed under; the main window's page opens it only while it still follows that pairing, as for a bot chosen in the tray, and by its own routes, never by an address the request carries). None reads or writes anything on disk, and none moves or resizes the window: the system drags it by the region the page marks. A pairing link's code, which the app hands to the page that loads after the server address screen, is given to the main window's page only. Because both pages share the origin's storage, the main process takes quick access's page off its window before it clears that storage for a change of server, so nothing of the server left behind is written back. The window stands above other apps' windows only while the operator has it open, and what it shows is what the main window would: a notification preview's rule does not apply to it, since it is the conversation itself.
- **The window the operator was in is the operator's data** ([0079](../decisions/0079-quick-access-brings-the-window-the-operator-was-in.md)). A window's title can name a document, a person, a site or an account, and quick access reads it only as the global shortcut opens it over another app: never in the background, never from the tray's menu, never over one of J3 Bots' own windows, and not at all on Wayland. The main process holds what it read for that one showing and forgets it as the window hides; the page shows it as chips, and only what the chips show at Send leaves the computer, with that one message, to the server and, in the envelope, to the bot's AI provider, as the operator's words do. The entry keeps the app and the title so the conversation can show them; nothing else of the window is stored. Settings turns the title off, after which only the app's name is read. A picture of the window is taken only when the page asks for one, which it does only once the operator turns the picture on, for that message or for every message in Settings (off by default), and the main process takes the ask only for the showing it read and while that showing is on screen; it goes as an attachment, kept as the message's other files are. On macOS the title and the picture need the operator's Screen Recording permission, which the app asks for only when the operator turns the picture on, in a card that says why. On Windows the app runs a helper in Windows PowerShell, from `System32`, without the operator's PowerShell modules or profile, which answers only the app's own asks over its standard streams. A title reaches the bot as data, after a line of J3 Bots' own saying whose words it is ([Prompts](../prompts/architecture.md#wake-envelopes)), so a page that titles itself with an instruction gives the bot information, not an order.
- **Web pages in a browser** can send requests to any address the browser reaches, loopback included, even where they cannot read the answers. Two rules keep them from doing harm with requests that need no token:
  - `POST /api/pair` takes `Content-Type: application/json` only. Any other content type is answered `415` before the body is read, and the request does not count towards the pairing lock. A page may send `text/plain`, a form or no type at all to another origin without asking first, but JSON needs a preflight, which the server answers for no web page, so a page cannot lock pairing by posting wrong codes. Every client sends JSON.
  - On a plain-HTTP listener, a request's `Host` must be `localhost`, an IP address, or the name in `publicOrigin`, at any port. Anything else is answered `403` before routing, the socket's upgrade included, with one plain-text line saying which addresses the server answers. A page on the refused name can read that line, so it names no address of the server's own; the server's log does, once for each refused name and for at most 16 names, with what would serve that name (`publicOrigin` for a proxy or tunnel in front, an address for anyone else). This stops DNS rebinding: a page on a name its owner points at this machine's address is same-origin with the server under that name, so it could read what the server answers without a token (`/api/server`, the web client) and try pairing codes and webhook addresses at will, and its browser sends that name as `Host`. Nobody can rebind an IP address, nor `localhost`, which browsers resolve to loopback themselves. The port is not compared: the name is what a rebinding page cannot change, and a proxy on another port, Docker's published ports and the Android emulator's alias `10.0.2.2` all reach the server other than at the address and port it bound. So over plain HTTP the server answers a browser only at an address, at `localhost` or at its `publicOrigin`, never at another name such as `<machine>.local`. The desktop's server on `lan` is held to the same rule: a phone opens it at the private address Settings shows. Over HTTPS `Host` is not checked: the browser refuses a name the certificate does not cover, and a proxy in front may send any name.
- **A device token at rest.** A browser keeps it in IndexedDB in the clear: only pages of the server's origin can read it, and anyone who can read the browser's profile. The desktop app keeps it in IndexedDB too, sealed by its main process with the system's key (Electron's `safeStorage`), so the profile's files alone do not give it away. Opening it is a call the app's own page makes, as it uses the token anyway: the protection is against reading the disk, not against code running as the operator's user, which can ask the system's keyring as the app does. On Linux with no keyring the app can use, the token is only obscured, and Settings → Devices, under This device, says so from the stored record until the device is paired again, which issues a new token: sealing the same token again would not help, as the profile's database files can keep the obscured copy after the record is replaced ([Clients: desktop](clients.md#desktop)). A token the system does not open, as while a keyring is locked, and a record of the server whose sealed token is damaged, do not read as a missing pairing, so nothing kept for that pairing is deleted. Uploads from the desktop app go like every other request of its page, held by its Content Security Policy to the named server.
- **The data directory is private, or the server does not start.** Before it opens the database or binds anything, the server checks that the home is a folder owned by its user, which that user can read, write and search (0700) and which no group and no other user can open (no bit of mode 077 set), and that each folder in it where the harnesses keep their sign-ins (`providers`, `providers/claude-code`, `providers/codex`) that exists is one too. A home the system will not show, as when this user cannot open a folder it is in, is refused too, never taken for missing, and so is one of those folders that exists but cannot be looked at. A missing home is created private (mode 0700, on Windows with its access list in place from the first moment), and checked again once created, before anything is written into it: one another process made since the server looked is left as that process made it, and refused unless private. `j3-bots doctor` reports a folder that fails this as a problem, with the `chmod` or `chown` command that fixes it, or, for one it cannot look at, that this user must be able to open it and every folder it is in. The home holds the database, the engine's credential and the admin socket. A home that is a symbolic link, or on Windows a junction, is judged by the folder it leads to, where its files are.

  On Windows a mode means nothing: who may open a folder is its access control list and its owner. There the home is private when it is owned by the user, SYSTEM or the Administrators group, no rule lets any other account open it, a rule naming the user gives it Modify on the folder, and no rule denies that to the user or one of its groups. SYSTEM and the Administrators are let in because Windows gives them the user's profile, where the home lives, and an administrator can take any file whatever its list says: shutting them out keeps no one out and breaks the profile's backups. The server creates a missing home with its list in place (inheritance off; full control for the user, SYSTEM and the Administrators, passed on to everything inside), so nothing can be put in it before it is private, and checks an existing one at every start, with those folders in it: a rule on a folder reaches it whatever the folders it is in allow, as Windows lets every user pass through a folder to what is inside (the "bypass traverse checking" right), so a private home does not keep a provider's home opened to others private, and a provider's home made later takes the rules `providers` passes on. It reads every list in one Windows PowerShell run with `Get-Acl`, by security identifier, never by account name, which `icacls` prints in the system's language. The user's groups are the ones its token holds, those enabled and those for deny only: Windows checks a rule that denies against both, and .NET's `WindowsIdentity.Groups` leaves the deny-only ones out, so they are read from the identity's claims (**Read** in .NET Framework's reference source at `ec9fa9a`, `windowsidentity.cs` `AddGroupSidClaims`; the CI runner's token holds no deny-only group, so this part is not **Verified**). A home that fails is refused with the `icacls` command that repairs it, for PowerShell: it turns inheritance off, removes the rules that deny the user, SYSTEM or the Administrators, which granting does not replace, grants the three full control and removes every other account, with each argument in single quotes, so a path holding `$` or `%` is taken as it is written. One whose list cannot be read is refused too. The desktop app judges its own server's home with the same code before it starts a server there, and creates a missing one the same way, so it never starts a server that then refuses its home (**Verified** on Windows Server 2025 in CI: a home created this way is judged private, and one opened to the Users group is refused until the repair command runs. **Verified** on Windows 11 x64 with the packaged app: "Use this computer" created the home with inheritance off and full control for the user, SYSTEM and the Administrators only; once the Users group was given read access, the app refused to start the server, saying other users could open the home and giving the `icacls` command, and once the list was repaired, "Try again" started it. **Verified** on Windows Server 2025 in CI: the repair command, run in PowerShell, makes private a folder whose name holds a quote, `%TEMP%`, `$HOME`, `&` and `^`, and one that denies the user writing).
- **Private state stays in the home.** Every location the server or its engine adapter writes must resolve, symbolic links followed, inside the home and outside the web client's folder: at start, and again before each write ([Server: data](server.md#data)).

  This rule protects against misconfiguration and against a link inside the home that would publish private state. It does not defend against a hostile process running as the same user, and that includes a bot's own shell tools: such a process can already write anywhere the user can. The rule therefore stays a cheap, uniform check and does not grow into a sandbox. A refused write affects only the scope that was tampered with (one bot's workspace or memory, the attachments, the engine's folder), never the server or the other bots.
- **What a bot attaches comes from its workspace.** A file a `say` names is read only inside the bot's workspace, against the folder's real path kept from its first provisioning, before the bot's first turn, never resolved again: a link the bot puts in the folder's place leads nowhere inside it. On Linux the check is made on the opened file, so a folder swapped for a link while it is read is refused too. Elsewhere it compares the opened file with what the path resolves to again, which a folder swapped out and back in between could pass. Either way this containment is a guardrail against a bot attaching the wrong file, not a security boundary: the bot runs commands as the same user as the server, can read any file that user can, and could copy one into its workspace first ([Server: attachments](server.md#attachments)).
- **An image a bot looked at is served by an id, from its workspace.** A device never names a path: it asks for an image by the opaque id (100 random bits) the server gave the step that looked at it, and only with a paired device's token. The server ties an id to a path only inside the bot's workspace, which also holds what the operator gave the bot (their files are copied there), and reads the file again on each request under the same containment as an attachment. It serves at most 10 MiB, and only a GIF, JPEG, PNG or WebP by its first bytes, never by its name, so a file named `.png` that holds a page or an SVG is refused; the response is typed from those bytes, with `nosniff` and a policy that runs nothing (`default-src 'none'; sandbox`). The image shows only in the fold of the turn that looked at it, which is in the bot's own conversation, a room turn's too: a room shows no fold, so nothing a bot looked at reaches a room. The server decodes no image: the client bounds it in a frame. As with attachments, the bot could copy any file its user can read into its workspace and read it there ([Server: images a bot looked at](server.md#images-a-bot-looked-at)).
- **One server per home.** The server holds an exclusive lock on `<J3_HOME>/server.lock` for as long as it runs. The kernel releases it when the process ends, so a crash never leaves the home held, and two servers that start at once cannot both get it.
- **The admin channel** gives commands on the host a pairing code, a way to lift a lock on pairing, the server's status and a provider connection, and gives the desktop app that runs its own server a device and a way to stop it. It takes no token, because only the server's own user reaches it, two ways ([Server: the admin channel](server.md#the-admin-channel)). The admin socket is a Unix socket inside the private home, created with no access for group or others: the server narrows its umask for the call that binds it, so the socket never has a looser mode, not even until a `chmod`. A test holds that another user of the machine is refused it (`EACCES`), and one that the socket is closed to others even under a umask of 0. Just before the bind the server checks that the home is private and notes which folder it is, and checks again once the socket is served: a home moved, replaced or opened in between stops the start. The server removes a socket a stopped server left behind only while it holds the lock, and only once it has seen that the file is a socket and that nothing listens on it. On Windows there is no admin socket, since Node would make its path a named pipe that other users could open (**Assumed**). With `--admin-fd`, the same routes are served on a pipe the server inherited from the process that started it. Only that process holds the other end, and the server's end can never be opened by name: it is a socket pair on Linux and macOS, and on Windows a named pipe of a single instance, which the parent opens itself before the child starts (**Read** in libuv). The server's own children do not inherit it (**Verified** on Linux and on Windows, in CI: on Windows by comparing a stand-in engine's files with the server's and its parent's, since there the engine ends with the server). The start fails on a TCP socket, listening or connected, so the channel never travels over TCP, and, on Linux and macOS, on anything that is not a socket, such as a FIFO. Anyone who can act as the server's user can reach the channel, and can already read the database: every bot's shell can make a pairing code or a device this way, or stop the server, as the trust model above says.
- **The local desktop gets its device through the admin channel, never over TCP.** When the desktop app runs its own server, it asks that server for a device on the admin channel (`POST /local-device`) instead of pairing with a code: an ordinary device, listed and revocable like any other, which replaces, revoked in the same transaction, every device the admin channel made before it and the one the app names. A process of the server's user that asks for one therefore signs the desktop out, which is no more than that user can already do: it can stop the server. No code is made, none crosses the network, and the pairing lockout neither applies to it nor is lifted for it. The route exists on the admin channel only; the client listener answers 404 to it, which a test holds. The app never asks for a new device by itself after its device was revoked: a revoked desktop shows that it was signed out, and only the operator's choice to sign in again asks for one ([decision 0020](../decisions/0020-the-local-desktop-gets-its-device-through-the-admin-channel.md)).
- **A failing request** fails alone, with a generic error; the cause stays in the server log, and the socket's other subscriptions carry on.
- **A failed turn's details are scrubbed before they are kept.** What the engine says of a failure (its error's class, code and message) can quote what the AI was sent, credentials included. Before the server stores it, shows it behind the notice's Details, or logs it, the adapter takes out every secret J3 Bots gives the engine, whatever its shape (the connection's key, and each provider instance's and the tool bridge's variables), and then removes what has the shape of a secret: `Bearer`, `Basic` and `Token` credentials, JWTs, keys in the `sk-` style, `key=value` fields named for a token, secret, password, cookie or authorization, the user and password in a URL, and any long run of mixed letters and digits. It then cuts the text to 2,000 characters. A secret J3 Bots was not given, with no recognizable shape, is not caught. Details reach only the operator's own devices, as the conversation does ([decision 0072](../decisions/0072-errors-say-what-to-do-force-stop-and-whole-questions.md)). The engine's notices go through the same scrub before the adapter logs them or puts their words in a notice's Details: a hook's or an MCP server's message can quote a secret too. The log takes only a notice's title, or its message when it has none, since a message can quote what the operator wrote ([decision 0083](../decisions/0083-only-the-engine-notices-a-person-can-act-on-show.md)).
- **Webhook endpoints** authenticate with a 256-bit secret in the path. Before it reads the body or a header it acts on (`Idempotency-Key`, `Content-Length`), the webhook route looks the routine up and compares SHA-256 digests of the given and the stored secret with Node's `timingSafeEqual`: an unknown routine, a wrong secret and a routine with another trigger all get `404`, and the server closes the connection after answering. The route never reads the body of such a call, whatever it declares; bytes the caller already sent are discarded as the connection closes, and a caller that waits for `100 Continue` is never sent one, so it sends no body. That holds for the route on J3 Bots' own listener: a proxy in front of it, such as the container's Caddy, may wait for or buffer the body before it forwards the request. Only for a call that named its webhook are the headers and the body read: up to 64 KiB, and at most ten runs a minute for each routine ([Server: webhooks](server.md#webhooks)). An HMAC signature over the body is not checked: it needs a field in the routine contract that requires one.

  The constant time covers the comparison of the digests, not the whole check: a routine that exists is read from the database and decoded, and an unknown id is not, so timing can tell whether a routine id exists. The `404` already answers that the same way for a wrong secret and an unknown routine, and the id is not the credential. Refused calls are not limited: one costs a lookup and two short digests, and no rate of guessing finds a 256-bit secret, while a limit shared by every caller would let anyone who reaches the server, or a sender still posting to an address an operator replaced, close every webhook.

  The secret travels in the URL, so anything that logs requests can hold it. The server's request log records any path under `/hooks/` as `/hooks/…`, and no trace span is made of such a request. The container proxy this repository ships ([`deploy/container-proxy`](../../deploy/container-proxy/compose.yaml)) keeps no access log and leaves the whole request out of every line it logs: Caddy logs the request with each error it answers, such as a `502` while the server restarts, and a filter on the URI alone still left the path in headers such as `X-Original-URL` and `Referer` (**Verified** on Caddy 2.10.2). Its admin API is off. A platform's own router in front of it, or a tunnel, logs what its own settings say; many keep access logs with paths. A routine's secret changes only when its trigger does: to replace a secret that may have leaked, change the routine to a schedule and back to a webhook, which gives it a new address and makes the old one answer `404`.
- **The bot tool endpoint** listens on `127.0.0.1` only, and takes a request only as the `j3` bridge makes it: with an authority (its `Host`, or the authority of an absolute request target) of `127.0.0.1` and the port the request arrived on, as a URL writes them, declared exactly `application/json`, and with no `Origin`. Any other request to the route gets 403 before its body is read. This keeps out web pages in a browser on the host, which can reach loopback too: a browser sends a page's `POST` with an `Origin`, a page on a name rebound to `127.0.0.1` sends that name as `Host`, and a page may send a JSON body to another origin only after a preflight, which the endpoint never grants. The bridge sends that `Host`, that content type and no `Origin`, with Node's own `http` client on the server's own Node executable (**Verified** with that client on Node 24.22.1, the bridge started by Claude Code and Codex; with `fetch` before it, on Node 26.13.1, the version the server pins), and its tests send its requests through the check with that client. Any program on the host can still reach the port, so a body is capped at 4 MiB before it is decoded.

  A request names its caller's session, never an argument the model supplies, and the server refuses a session it did not create. A session's engine id is derived from a random 100-bit id, so it cannot be guessed. The tools that act for a turn (`say`, `ask`, `request_browser_help`, `message_bot`, `read_room`, `set_routine`, `set_operator_name`, `ask_for_secret`, `fill_credential`, `create_bot` and `start_room`) act only on an open call, which no other request has claimed, that the engine recorded with the same input in that session's running turn ([Server: bot tools](server.md#bot-tools)). So a request that names a session whose turn has no such call open, one that reuses a request id another session's call already stored a result under, and a replay of a request id whose result is stored, for the same session and tool, whatever arguments it now carries, record nothing and wake no one; a replay whose arguments the tool accepts, for a session the server still has, gets the stored result back. A test holds each case.

  Every request is signed, and so is every answer. The server makes a new HMAC-SHA256 key each time it starts and holds it in memory only. The engine starts each bridge with it: in the bridge's entry of Claude Code's `.claude.json` and of Codex's `config.toml`, in the instance's own home, or, for an ACP agent, in the instance's environment, which the engine keeps in its secret store, not in its settings file ([Engine: provisioning](engine.md#provisioning)). A request is tagged over its path and its body as sent, and an answer over the request's tag and its own body. The endpoint refuses a request with no tag, or a wrong one, with 403 before its body is decoded, and the bridge takes no answer that was not signed for its own request. So a session's id alone does nothing: the server's log can name one, and the engine's is computed from J3 Bots', yet another user who reads either has nothing to call with. A program that binds the tool port in the moment the server stops, before the engine stops the harnesses, receives what a bridge forwards then, but cannot answer it, and a request it keeps is refused by the next server, whose key is another. The key reaches no log, client, entry or prompt: the engine's log lines and its account of a provider are cleared of it as of every other secret J3 Bots gives the harnesses ([The harnesses](#the-harnesses)), and Claude Code and Codex get it in the bridge's entry, not in their own environment, so their shell commands do not inherit it. An ACP agent gets it in its own environment, which a command it runs inherits. **Verified** with Claude Code 2.1.332: a server in an entry's `env` got that variable. **Read** for Codex, in its configuration reference (`mcp_servers.<id>.env`). **Assumed**: the engine and the harnesses write the configuration they read nowhere else, such as a log.

  What still holds the key is the server's user's: the harnesses' configuration files, which a bot's shell can read ([What a bot's shell can still reach](#what-a-bots-shell-can-still-reach)). The tools that act for no turn (memory, `list_routines`, `list_teammates`, `update_bot`, `update_profile` and `set_visibility`) are not matched to a call, so a process of that user that reads the key and a session's id can use them as that session's bot, as far as that bot may (`update_bot` only for the primary bot; `set_visibility` only on what the operator never chose, and for a bot other than the primary only on what it made, [decision 0050](../decisions/0050-bots-and-rooms-are-visible-or-hidden-and-the-operators-choice-wins.md)). Every bot's shell runs as that user, so one bot can use those tools as another. That gives it nothing it lacks already: such a process can change the memory files and the database directly.
- **Bot scope.** A bot's tools reach its own conversation, memory and routines, the shared memory, and the rooms it belongs to. Two things reach past its rooms, and neither reads one: the primary bot's `list_teammates` also names the rooms it is not in, with their names, members and whether they are hidden; and `set_visibility` shows or hides a room the caller is not in, any the operator never chose for the primary bot, and for another bot one it made, also after it left it. Reading a room and posting in it stay for its members. Nothing in the tool surface returns another bot's conversation or memory. This is isolation of the product surface, not of the filesystem.

## Visuals

A visual is a page a bot wrote ([decision 0030](../decisions/0030-a-visual-is-part-of-say.md)), and a bot writes what its prompts and the pages it reads lead it to, so a visual is untrusted content. The server stores it as text and never runs, parses or logs it; a notification, a push and the roster say the message's text, never the page. A client draws it where it can run its own scripts and nothing else ([Clients: visuals](clients.md#visuals)):

- **A sandbox with scripts only.** The frame is `sandbox="allow-scripts"`, never with `allow-same-origin`, so its origin is opaque: it reads no cookie, storage or IndexedDB of the client's, and cannot reach the client's document. Without `allow-top-navigation`, `allow-popups`, `allow-forms` or `allow-modals` it cannot take the window elsewhere, open one, submit a form or block the page with a dialog. Every document the page makes inherits the sandbox, so it too has an opaque origin of its own, cross-origin to the page from the moment it exists. Every client draws a visual in such a frame: a WebView loads its page unsandboxed (a `sandbox` in a `<meta>` policy does nothing), so Android loads `visualShell`, which frames the document as the web does.
- **No network.** The document the frame is given carries the visual's Content Security Policy (`VISUAL_CONTENT_SECURITY_POLICY`, `@j3-bots/contracts`): inline scripts and styles, images and fonts from `data:` and `blob:` only, and nothing else: no `fetch` or socket (`connect-src 'none'`), no remote image, font or stylesheet, no frame, no form target, no `<base>`. So a page cannot send what it holds anywhere by loading a URL. Two ways past a policy remain: WebRTC, which the next point shuts, and resource hints, which are a [known gap](#known-gaps).
- **No WebRTC.** A policy does not reach a peer connection: `connect-src` does not govern WebRTC in Chromium, and Chrome 151 does not know a `webrtc` directive ("Unrecognized Content-Security-Policy directive 'webrtc'", **Verified**). Without more, a visual's script could open a data channel through a STUN or TURN server of its choosing, reveal the client's address and send what it holds (**Verified**: packets left for the chosen port). So the document's first script, before any of the page's, deletes every `RTC…` interface from the page's realm (`RTCPeerConnection`, `webkitRTCPeerConnection`, `RTCDataChannel` and the rest), and the page cannot make one. A nested document would be a realm with its own again, so a visual holds none:
  - its markup may have no `<iframe>`, `<frame>`, `<object>` or `<embed>` start tag, the only way markup makes one, and no declarative shadow root (a `shadowrootmode` or `shadowroot` attribute), which the parser attaches without `attachShadow`, so the guard would never see a frame a script later added inside it: `say` refuses such a page, and `visualDocument` builds no document for it, so a client shows it as failed (`visualEscapesGuard`, `@j3-bots/contracts`);
  - the same first script removes every frame a script adds, to the document or to a shadow root it attaches, at the next microtask, before the frame's document can load (a `srcdoc` document loads only in a later task). It attaches every shadow root unclonable, so `cloneNode` or `importNode` never copies one it does not watch;
  - it deletes the ways to parse a declarative shadow root, whose inside it could not see (`setHTMLUnsafe`, `Document.parseHTMLUnsafe`, and the Sanitizer API's `setHTML` and `Document.parseHTML`, which keep one when the page's own configuration allows it), and `document.open`, `write` and `writeln`;
  - it keeps the built-ins it relies on before the page runs, so a page that replaces `Element.prototype.remove` or `MutationRecord.prototype.addedNodes` does not turn it off.

  The rest cannot make a realm the page reaches: a nested document is cross-origin to the page whatever it holds, even the empty one a frame has the moment it is added, before the guard removes it (the sandbox gives each its own opaque origin: `SecurityError` on reading its globals through `contentWindow` or `window[i]`, and no `contentDocument`), so the page cannot borrow an `attachShadow` or a parser the guard never touched; a worker cannot start (`script-src` allows no `blob:` or `data:` script), `window.open` returns `null`, and a `javascript:` URL the frame navigates itself to does nothing (**Verified**, Chrome 151). A frame cannot get a fresh realm by navigating elsewhere either, as the next point says.
- **Not `srcdoc`.** A `srcdoc` frame inherits the policy of the page that made it (**Verified**, Chrome 151), which on the desktop allows no inline script, so a chart's own script would not run. The client instead loads its visual page, a static file of its own build, and posts it the document. The server and the desktop app serve that page with `VISUAL_FRAME_POLICY`: the visual's policy, the `sandbox allow-scripts` directive, so the page is sandboxed even when opened on its own, and `frame-ancestors 'self'`, so only the client frames it. It writes over itself once, only with a string from the window that framed it, and only while its origin is opaque.
- **No way out of the frame.** Every page of the client is served with `frame-src 'self'`, so a frame that navigates itself, by script or by a refresh, can reach only the client's own pages, which refuse to be framed (`frame-ancestors 'none'`). The desktop app also refuses any frame navigation but to its visual page (`will-frame-navigate`), grants a permission only to its own window's main frame, so a visual is denied notifications and the clipboard, and runs its preload in the main frame only. What a frame shows once it has navigated is not the visual, so the client shows "Couldn't show this visual" in its place: the frame loads twice as the client means it to, its visual page and then the document written over it, and a later load is the frame showing something else. A visual reports its height only once its document has loaded, so one that navigates while it loads never reports, and fails when its ten seconds run out (**Verified**, Chrome 151 headless, the visual page under its policy in a page under `frame-src 'self'`: navigating by `location` while it loads, from its load event and later, by a link and by a refresh each showed as failed, and a visual that stayed was shown and resized).
- **Height alone comes back.** The client reads one thing from a frame: a number, from that frame's own window, clamped to 2000 pixels. A message from another window, another visual included, changes nothing.

**Proof** (**Verified**, the server's own headers, in Chrome 151 headless and in the desktop app on Electron 44): a visual that tries each way out got a `SecurityError` reading `document.cookie`, `localStorage`, `sessionStorage`, `indexedDB` and `parent.document` and setting `top.location`; `window.open` returned `null`; `fetch` to the server's API and to a remote address failed under the policy; a remote image was refused without a request; a form submit was blocked; messages posted to the client and to its other frames changed no height; navigating itself away, by script and by a refresh, left the frame on an error page with no request answered. In the desktop app the visual was also denied notifications and the clipboard while the app held notifications, and a frame navigation to the app's own settings page was refused. Against WebRTC (**Verified**, Chrome 151, the visual page and policies as served, the document as `visualDocument` builds it, a STUN and TURN address on the test machine, every packet to its port captured): a page that opens a data channel from its own realm and from a nested document made each of fifteen ways (a `srcdoc` frame in its markup, one in a closed declarative shadow root, one added by script, one given its `srcdoc` once in the page, one added by `innerHTML`, `insertAdjacentHTML`, `setHTMLUnsafe`, `Document.parseHTMLUnsafe`, `document.write`, a template's clone, into a closed shadow root, after replacing `Element.prototype.remove` or `MutationRecord.prototype.addedNodes`, while busy right after adding it, and later from a timer) sent 187 packets without the guard and none with it: its markup frames refused, `RTCPeerConnection` not defined, the parsing APIs gone, no frame left in the page, while its script still drew its chart and its height reached the client. A frame put in the copy of a clonable shadow root, made by `cloneNode` or `importNode`, opened a peer connection without the guard; with it, no root was copied. A frame a script added to a declarative shadow root of the page's own markup, open or closed (through `attachInternals`), sent 22 packets until such a page was refused. A page that borrowed `attachShadow` and `RTCPeerConnection` from the empty document of a frame it had just added, through `contentWindow`, `window[i]` and `contentDocument`, sent 33 packets when its document was loaded unsandboxed, as a WebView would load it, and none in the sandboxed frame, where each way was refused.

## Visuals on Android

The Android app draws a bot's visual in its own native view (`apps/mobile/modules/visual-view`), a WebView configured for an untrusted page. The WebView loads `visualShell`'s page, which holds the visual's document in an `<iframe sandbox="allow-scripts">`, as the web does ([Visuals](#visuals)). The sandbox is the frame's: a WebView loads its own page unsandboxed, and a policy's `sandbox` in a `<meta>` does nothing.

- **Opaque origins.** The shell is loaded as a `data:` URL, so its origin is `null`, and the visual's sandboxed frame has an opaque origin of its own. Neither has a cookie, `localStorage` or IndexedDB; each throws `SecurityError`. A frame the visual adds gets yet another origin, so the visual cannot borrow its globals, which the guard never touched.
- **No network, twice.** The shell and the visual's document each carry the visual's policy, which allows no network, and the WebView blocks network loads and network images as well (`blockNetworkLoads`, `blockNetworkImage`).
- **No way out.** The WebView refuses every navigation of its own page on its own thread, with no timeout, and opens no second window (multiple windows are off, and `onCreateWindow` refuses). The visual's frame cannot reach the shell or navigate it (`SecurityError`). It can navigate itself, by a link, `location`, a refresh or a form. The shell's policy refuses that, and the frame then shows the WebView's error page. Nothing loads, and nothing reaches the system browser. The shell's frame loads once, with the visual, so the shell counts its loads and tells the app of a later one (`{type: "j3-visual-gone"}`), and the card shows "Couldn't show this visual" instead (**Verified** with the shell in Chrome 151 headless and a stand-in for the app's bridge; on a WebView, **Assumed**). A visual that navigates while it is still loading never reports its height and the frame never loads again, but the app has no time limit for a report, so it keeps the error page ([known gaps](#known-gaps)).
- **Nothing else of the device.** Off: file access, content URIs, DOM storage, the database, the cache, third-party cookies, saved form data and geolocation. Permission requests (camera, microphone) are denied, the file chooser does not open, and `alert`, `confirm`, `prompt` and `beforeunload` are cancelled, so no dialog draws over the app. Nothing a page logs reaches the device's log.
- **One string in.** The app is reached only through `postMessage(string)` on `J3Visual` (`VISUAL_BRIDGE`). The shell passes on the visual's height through it, and that its frame left the visual. The WebView puts that object in every frame, the visual's sandboxed frame included, so the visual can also call it directly: it is the same channel. A string over 256 characters is dropped, and only the latest message waits for the app's main thread. The app reads only `{type: "j3-visual-height", height}`, clamped, and `{type: "j3-visual-gone"}` from it (`readVisualReport`). A visual that sends either itself changes only its own view.
- **WebRTC.** Android's WebView has no setting that turns WebRTC off, and blocking network loads does not cover a peer connection's sockets. What shuts it is the document's guard, which deletes the RTC interfaces and removes the frames a script adds, together with the sandbox, which keeps the visual out of any realm that still has them.
- **A dead renderer, or no WebView,** shows "Couldn't show this visual" instead of taking the app down (`onRenderProcessGone`; the `AndroidRuntimeException` a WebView throws as it is made when the device has none, or is updating it).

**Verified** on the Pixel 8 emulator (Android 16, WebView 133), with the shell, inline and full screen:
- the visual's origin was `null`;
- cookies, `localStorage` and IndexedDB threw `SecurityError`, and so did reading `parent.document` and setting `top.location`;
- `eval` threw `EvalError`;
- `fetch` failed, `sendBeacon` sent nothing, and the remote image fired `onerror`;
- `window.open` returned `null`;
- `alert` and `confirm` showed nothing;
- the page recorded policy violations for `script-src`, `connect-src` and `img-src`;
- a scripted `location` change and a real tap on a link were refused by the policy (`ERR_BLOCKED_BY_CSP`), and the app stayed in front;
- messages with another `type`, with an extra field, and of 5,000 characters changed nothing;
- a page with a frame or a declarative shadow root in its markup never reached the WebView: its card showed the failure line;
- the `J3Visual` object was present in the shell, in a child frame and in a sandboxed child frame.

**Verified** for WebRTC on the same emulator, with a capture on the device (`tcpdump`) and a STUN listener on the host:
- with no guard, a visual's data channel sent 257 STUN and TURN packets to an address it chose, the binding requests carrying a username it chose;
- with the guard but without the shell, a page took `attachShadow` from a new frame's `about:blank` window, which shared the page's origin, hid a `srcdoc` frame from the guard in a shadow root and sent 14 STUN requests from it;
- with the shell, none left, over two minutes:
  - from the visual's own realm, which has no RTC interface;
  - from a `srcdoc` frame a script added, to the document or to a closed shadow root, or just before a 1.5-second busy loop;
  - by borrowing a new frame's realm through `contentWindow`, `window[i]` or `contentDocument`, which threw `SecurityError` or found no document;
  - by copying a shadow root asked for as clonable, with `cloneNode` or `importNode`: the root came back unclonable, and neither copy had one;
- heights still arrived, a scripted chart in the same conversation still drew, and full screen still scrolled and pinch-zoomed.

That a screen reader skips the inline page is **Assumed**. The view sets `IMPORTANT_FOR_ACCESSIBILITY_NO_HIDE_DESCENDANTS` on the WebView, and its React parent does the same, but the test driver's accessibility tree still lists the page's nodes, and TalkBack was not run.

## Documents

A document in a conversation (a PDF, a text, Markdown or CSV file, an Excel workbook, a Word document or a PowerPoint deck) is read and drawn on the client ([decision 0078](../decisions/0078-documents-open-in-a-viewer-of-the-apps-own.md)). Whoever made it, a bot or someone who sent it to the operator, may have made it to attack the viewer, so nothing in it is trusted:

- **Nothing of the file becomes markup, a script, a style or an address.** Every format but PDF is read by J3 Bots' own readers (`client-runtime/documents`) into a typed model of text runs, blocks, sheets and slides, which the app draws with its own components. A link is its text, a Markdown image its description, raw HTML its characters. A picture becomes a picture only when its first bytes are a GIF, JPEG, PNG or WebP and its header says how large it is: at most 10 MiB and 25 megapixels each, and 40 MiB and 100 megapixels a document, a picture counted again each time it shows, so a small file that claims to be enormous, or one picture shown a thousand times, stays out. It is drawn from those bytes (an object URL on the web, a `data:` URI on Android), never from a path or address the file names. Nothing in the viewer fetches anything.
- **Office files are opened with limits.** The zip reader reads the central directory itself and refuses an encrypted, ZIP64 or split archive. Each part inflates in 1 KiB steps (fflate) and stops past 48 MiB, and the parts read for a document stop past 128 MiB together, so a zip bomb ends as "too big". The XML reader refuses any `DOCTYPE`, so no entity is ever defined or expanded, and stops after a million elements; it reads each tag in one pass, and a tag it cannot read makes the file unreadable. The Markdown reader reads each line in time in proportion to its length, however it is built: it finds the end of each link, code span and emphasis in one pass, and takes a line's blank ends off by hand rather than with a pattern that would go back over them. A part's relationships are followed only inside the archive: an external target, or one that climbs out of it, is skipped. Macros, embedded objects, OLE and ActiveX parts are never read. A legacy binary file, or anything else that is no zip, is unreadable.
- **Readers stop at a document's size.** Text at a million characters, 5,000 blocks, 2,000 rows and 100 columns a sheet (a row number in the file never moves a sheet back past a row it has read), 2,000 characters a cell, 50 sheets, 300 slides, 60 pictures, 500 PDF pages; past them the viewer says it shows only the start. A file over the attachment limit, or empty, is not read at all.
- **On the web, off the page's thread.** Every format but PDF is read in a dedicated worker of its own, which the page ends when it answers or after 30 seconds; the page decodes the answer with the model's schema before using it. PDFs are parsed by pdf.js (Apache-2.0) in a worker the app starts for each PDF and hands to it, so pdf.js never falls back to parsing on the page; a PDF that takes more than 30 seconds to open is unreadable, and its worker ends with it, as it does once nothing shows the PDF, at most five seconds after even if pdf.js never answers. It is drawn to a canvas without its text or annotation layers, with XFA off, its scripting never loaded, at most 50 megapixels for an image in the file and 9 for a drawn page. It is given no font, character map or color profile to fetch; the only data it may ask for are the app's own JBIG2 and JPEG 2000 decoders, which the app hands it by name (`BundledDecoders`), and an unknown name is refused. The pdf.js build used has no `eval` or `new Function` (**Verified** in `pdfjs-dist` 6.5.438, `build/`). The desktop app's Content Security Policy allows `'wasm-unsafe-eval'` for those decoders: it lets the page compile WebAssembly, not run text as script.
- **On Android, PDFs in an isolated process.** The app writes the PDF to its cache and has a service draw it with Android's own renderer (`PdfRenderer`, on PDFium) in a process declared `isolatedProcess` (`apps/mobile/modules/document-pages`). Android runs such a process under an identity of its own, with no permission and no access to the app's files or the network (**Read**, Android's `<service>` documentation). It gets the PDF read-only and the drawing's file write-only as descriptors through its binder, and reads nothing else; the app's side hands over only files in its document folder, and takes a drawing only once it is written whole. A call that takes longer than 20 seconds ends the service's process, a crash ends only that process, and either way the page shows blank or the PDF unreadable. A page is drawn whole: at most 2,400 pixels wide, 8,192 tall and about 11.5 megapixels, a tall page drawn narrower to fit. Drawings are kept in the cache up to 64 MiB, the ones shown longest ago deleted first, and a PDF the app no longer keeps read, or that does not read, is deleted from it. That the renderer works in an isolated process on every Android version the app supports is **Assumed**: the module was compiled, not run on a device. Other formats are read on the JavaScript thread, with the same readers and limits as the web.
- **What it costs if a reader is wrong.** A bug in J3 Bots' readers can at worst make a document show wrongly or not at all, or, past the limits, slow the worker or (on Android) the JavaScript thread: they build plain data and never run or fetch anything. A bug in pdf.js or PDFium is that library's; it runs in pdf.js's worker on the web and in the isolated process on Android.

## Connector apps

A connector's app is a document a connector's server wrote ([decision 0048](../decisions/0048-a-servers-interface-runs-isolated-in-j3-bots-clients.md)), untrusted as anything that server sends. Unlike a visual it is meant to be used: it runs scripts, may reach the network its server declared, and asks J3 Bots to call its server's tools. So a client draws it where it reaches nothing of J3 Bots' and of the operator's but what each request asks for, and the operator answers what matters ([Clients: connector apps](clients.md#connector-apps)). The server stores its document as text, never runs it, and logs none of it.

The MCP Apps extension's reference host draws an app on an origin of its own, through a proxy page served from a second origin. J3 Bots has one origin, its server's address (or the desktop app's scheme), and the operator's server has no second one to give. It shuts the app in the same way a visual is shut instead, and gives it no origin at all:

- **An opaque origin.** The frame is `sandbox="allow-scripts allow-forms"`, never `allow-same-origin`: the app reads no cookie, storage or IndexedDB, and cannot reach the client's document, where the device's token is. Nothing ambient rides with what it sends: J3 Bots authenticates with that token, never a cookie. Without `allow-top-navigation`, `allow-popups` or `allow-modals` it cannot take the window elsewhere, open one or block the page with a dialog; a form's submission is sent nowhere (`form-action 'none'`), so a form only runs its own script. `allow=""` gives it no device feature: no camera, microphone, geolocation or clipboard. An app that needs an origin of its own (`_meta.ui.domain`) does not get one: what it fetches goes with `Origin: null`, which its server's CORS must allow.
- **Only what its server declared.** The app page is served with `CONNECTOR_APP_FRAME_POLICY`: the widest an app may have, `https:` and `wss:` only, never `'self'`; `sandbox allow-scripts allow-forms`, so the page is sandboxed even when opened on its own; and `frame-ancestors 'self'`. The document the page writes over itself carries the narrower policy its server declared (`connectorAppContentPolicy`): its own inline scripts and styles, images, fonts and media from `data:` (and `blob:`), and of the network only the origins it named, by kind: `connectDomains` for `fetch` and sockets, `resourceDomains` for scripts, styles, images, fonts and media, `baseUriDomains` for a `<base>`. Declared nothing, it reaches nothing. An origin is kept only as `ConnectorAppOrigin` allows it, so no app reaches the operator's own network by an IP address, `localhost` or a single-label name, and no list names `'self'`, a scheme alone or `*`. The client drops any origin that reaches the host of the J3 Bots server it speaks to, at any port or through a wildcard, so an app sends nothing there, even a request whose answer it could not read. A script can add a policy of its own, which only narrows; none takes one back.
- **No nested frame, no WebRTC.** `frameDomains` is never granted (`frame-src 'none'`), and the guard every visual runs first runs first in an app too: no RTC interface, no frame a script adds, no `document.write`, and a document whose markup embeds another is not drawn ([Visuals](#visuals)).
- **No way out of the frame.** As for a visual: every other page of the client refuses to be framed, and the desktop app lets a frame go only to its visual page or its app page (`will-frame-navigate`), and grants a permission only to its own window's main frame.
- **Its own frame's messages alone.** The client reads a message only from the app's frame's window, as JSON-RPC, and acts on each method as [Clients: connector apps](clients.md#connector-apps) lists. A height is clamped to 1,600 pixels.
- **What it can make J3 Bots do.** Call a tool of its own connector, as the bot whose call opened it, only a tool its server lists and lets apps call, only while that bot has the connector and the connector is connected, the grant checked on each request as for the bot's own calls ([Connectors](#connectors)). Unless the bot is in full access, each tool waits on the operator's **Allow** once while the app is drawn, in a line the app cannot draw over or press. The server checks the bot's mode at each call, not when the app was opened: a call the operator did not allow is refused once the bot leaves full access, and the client asks. Read a resource of its own connector the same way. Propose a message, which goes to the bot only when the operator presses **Send**, as their own. Ask to open an `http:` or `https:` address, which opens only when the operator presses **Open**. Nothing else: no other connector, no J3 Bots request of its own, nothing into the bot's context, no other app or visual.
- **What it is given.** The call that opened it, its arguments and its answer, and each answer to its own requests, all with the connector's secrets taken out, from text and from any base64 `blob` that is text ([Server: connector apps](server.md#connectors)), each at most 2 MiB. The theme, the language, the time zone, whether the device has touch and hover, and the frame's width. Never the bot's name, the operator's, the conversation, or anything of another connector.

**On Android** the app's view (`modules/connector-app-view`) is configured as a visual's ([Visuals on Android](#visuals-on-android)), with two differences: network loads are allowed, under the policy, and the shell passes on every message, in order, up to 64 waiting and 3 MiB each, rather than the latest height. The `J3App` object is in every frame, the app's included, so the app can call it directly: it is the same channel its messages take.

**What remains.** The app draws whatever it likes in its frame: it can imitate J3 Bots' own lines or ask for what it should not, and the operator sees whose it is only from the card's line above it. It runs, as the bot, every tool its server lists and opened to apps, and in full access without asking: that is the bot's permission mode, which is the operator's choice ([Permission modes](#permission-modes)). It sends what it was given to the origins its server declared, which need not be that server's. Resource hints reach past its policy as a visual's do ([Known gaps](#known-gaps)).

**Proof.** The policies, the sandbox and the message filter are covered by tests (`connectorApp.test.ts` in `@j3-bots/client-runtime`, `ConnectorApps.test.ts` in the server). That an app's frame behaves in Chrome and in the desktop app as a visual's does, with the network its policy allows, is **Assumed** from the visual's proof, since it is shut the same way; it was not run against a browser for this release. Android's view was not built or run (**Assumed**).

## Push notifications

A phone in the background is reached through a push service: Expo's, for now, which hands each notification to Apple's or Google's ([decision 0014](../decisions/0014-push-goes-through-a-push-sender.md)).

- **What a client's update may do.** It installs only the feed's verified release, verified again as it downloads. It runs as the service's user, in a transient unit with `NoNewPrivileges`, and gains nothing that user does not have ([Server: updating from a client](server.md#updating-from-a-client)). The server logs the versions, the device that asked and how it ended, never a token.
- **What leaves the server.** For each push: the device's push token, a title (the bot's name, or the room's), a body, and the data the app opens (the device's id, the bot's or the room's id, the entry's id), with the delivery's id as its key; to Android, also the channel it shows in, which names the kind of entry (a message, a question, an approval, a credential request or an urgent handoff), as the fixed sentence already does. With previews off, the default, the body is a fixed sentence such as "Sent you a message", and no text of the entry leaves the server; with previews on, it is the entry's first line, at most 200 characters. Expo also sees the server's address and when it sent. The server sends Expo no credential, with the project's "enhanced security" off: a token a self-hosted server holds would ship to every operator, and protect nothing.
- **A setting changed later only holds a push back.** A push is worded in the transaction that adds its entry, with its preview only if previews were on then, and also without it. Each send reads the settings again, in the transaction that claims it, so a change committed before the claim holds for that send: with previews off by then, it carries the fixed sentence, never the stored preview; with notifications off, the push is dropped unsent. Turning previews on later never sends an earlier entry's text.
- **Push tokens.** A push token is the address a push service gives one installed app: whoever holds it can send that app a notification through the service, so it is stored with the operator's data and never shown to a client, the Devices list included, which shows only whether a device has push on. A device registers only itself, from its own authenticated socket; the token is bounded (printable ASCII, at most 256 characters) and the platform and language must be ones the server knows. A token moves to the device that registers it last. That is no escalation: tokens leave the server only for the push service, so a device can only take a token it already holds, as an app that paired again does. Revoking a device, which signing out does, deletes its registration in the same transaction, and a push command the device sent before is refused from then on rather than answered from its receipt. A send is begun only while the device still has the registration the worker read, so a revocation that lands while the worker is sending other pushes stops that device's push too. Any paired device can revoke another, and so end its pushes; that is no more than revocation already allows.
- **A phone that leaves a server unconfirmed.** A sign-out the server never confirmed, as offline, leaves the device listed there with its registration, so that server goes on pushing to its token. The phone holds an Expo token of its own for each pairing, under a device id made from the pairing's, so the token a new pairing registers is never one an earlier server holds, and the token Expo moves to a new device token by itself is one no server holds ([Clients](clients.md#mobile)). Leaving a pairing also has the push service forget the device's token, after which Expo answers the old pairing's token `DeviceNotRegistered`. That still does not hold in two cases (**Assumed**, both): on Android, when deleting the token fails, as offline, the old device token stays valid; on iOS, Apple usually gives the same device token again after the app unregisters and registers, so the old token keeps reaching the phone. That server's pushes then show the name of a bot or room and, with its previews on, their first line; a tap on one opens nothing, since it names a pairing the phone no longer follows. Revoking the phone from that server's Devices ends them.
- **A repeat replaces, not adds.** A send repeated after a crash or a lost reply carries the delivery's id as its key, Expo's `tag` on Android and `collapseId` on iOS, which replace a notification with the same key still shown. One the operator already dismissed is gone, so a repeat can show again. Expo documents that, rarely, a notification reaches Apple or Google more than once or not at all. How a device shows a repeat is **Assumed** until the mobile app is tried on one.
- **What is kept.** A push's words are stored only until the push service takes it; what is left until its receipt is read is the delivery's ids, the generation of the registration it went to and the service's receipt. Of the service itself, the server keeps only when it may next be tried after a request it did not answer. The logs name deliveries and devices, Expo's error codes only when Expo documents them, and a failure only by its tag: never a token, a message Expo sent (which can quote one), a failure's text, or what a push says.

## Release signing

Every file a release publishes is listed in its `SHA256SUMS`, and `SHA256SUMS.sig` is an Ed25519 signature over it ([decision 0031](../decisions/0031-a-release-is-signed-and-a-nightly-is-a-pre-release-of-the-next-patch.md), [Releasing: what verifies a release](../operations/releasing.md#what-verifies-a-release)).

- **What it proves.** A file whose digest is in a `SHA256SUMS` that a committed key signed is a file the release workflow built and listed. It ties a download to the project's key, not only to the place it came from. So whoever can change a file on a release, or sit between GitHub and the machine, can't make it pass. Unlike the feed's checksum, this holds even for someone who can publish a release.
- **Who checks.** `install.sh` checks with OpenSSL 3 and refuses without it, never falling back to the digest alone. It checks the signature before it reads a digest. A mirror's release is checked the same way ([Updates: a mirror](#updates)). The server and the apps check the same file before they install an update ([Updates](#updates)).
- **Where the key is.** The private key is one secret of the `release-signing` environment, read only by the `sign` job, which runs nothing from the repository or the build. The environment admits `v*` tags, which only admins may create, move or delete (a ruleset that gives GitHub Actions no bypass), and the branch `main`, from which the nightly is built. A nightly's tag is its version with no `v`, so it matches neither rule. Nightly tags are unprotected: the workflow token, any workflow on any branch, or anyone with write access can create or delete one. That opens no key, and a nightly's integrity rests on its signature alone, since a nightly or release someone fakes isn't signed by a committed key and every verifier refuses it. The owner keeps an offline backup. The public keys are committed in `release-keys/`, and `install.sh` and `RELEASE_KEYS` in `packages/release/src/keys.ts` carry copies that a test holds equal to them ([Releasing: the signing key](../operations/releasing.md#the-signing-key)).
- **Which keys `sign` accepts.** Before it hands a signature on, `sign` checks it with the public keys of the commit it builds. So a commit that adds a key to `release-keys/` passes that check: it catches a wrong secret, not a wrong commit, and the review of changes to `main` is what keeps a key out. A leaked key is replaced by one release signed with it that carries only a new key; anyone holding the leaked key can make the same kind of release with a key of their own, so that is a race ([Releasing: if the key leaks](../operations/releasing.md#if-the-key-leaks)).
- **What it does not prove.** The key signs whatever the build made. A compromised build dependency, or a malicious change merged to `main`, is signed like any other. A stable release has the maintainer's review of the draft before it's published; a nightly has none, and is published once built. Only servers and apps set to the nightly channel take one.

## Updates

A paired device can ask the server to update itself, since every paired device holds the operator's authority. What keeps that safe is not who asks but what may be installed: only a release the project signed, newer than the one running, on the server's channel ([Server: release feed](server.md#release-feed), [decision 0032](../decisions/0032-updates-are-served-outside-the-protocol.md)).

- **What is signed.** A release's `SHA256SUMS` and its signature, `SHA256SUMS.sig` ([Release signing](#release-signing)). The server and the apps verify with `RELEASE_KEYS` in `packages/release/src/keys.ts`, the keys in `release-keys/`; a release verifies when any of them signed it, so a new key is added a release before the old one stops signing.
- **What is checked, in order** (`verifySums` in `@j3-bots/release`): the signature over `SHA256SUMS`, against the release keys; that the signed list is the release's own, by naming that version's server archives, so a replayed older release, signed as genuinely, cannot pass for a newer one whose desktop package names no version; then a file's digest from that list, against the SHA-256 of the file as downloaded. A digest is never read from a list whose signature did not verify. Each refusal has its own reason (`VerificationFailure`): no `SHA256SUMS`, no signature, a signature that does not verify, a list not exactly as the release writes it, another release's list, a file it does not name, or a digest that differs. A list is exactly as the release writes it when every line, the last included, is 64 lowercase hex digits, two spaces, a name and a line feed; a blank line, a carriage return, a space after the name, binary mode's `*`, a name in a folder, `.` or `..`, a name given twice, or no line is refused. The signature file is the 88 base64 characters and at most one line feed.
- **Where.** The server's release feed verifies a release before it offers it. It keeps the `SHA256SUMS` and signature it verified, and verifies them again at each start against the keys trusted then, before a kept verdict counts. `j3-bots update` verifies again what it downloads, before it installs it, whatever the feed says. The desktop app and the Android app verify their own downloads with the same code, the Android app with its platform's Ed25519 and SHA-256 in place of Node's.
- **No downgrade.** A release is offered only when it sorts after the running version. A move from the nightly channel to stable waits for a stable release newer than the nightly that runs.
- **A mirror.** `J3_RELEASE_BASE_URL` points the server, `j3-bots update` and `install.sh` at a mirror of the releases page. A mirror's own releases verify with the key `J3_RELEASE_PUBLIC_KEY` gives, as PEM, as well as the release keys, and only while `J3_RELEASE_BASE_URL` is set, which is how the tests and the upgrade check sign theirs. Whoever can set the server's environment can already run anything as its user, so the variable opens nothing new; the server logs a warning when it trusts it. A value that is not an Ed25519 public key stops the server from starting, rather than being passed over, so a mistyped key is seen at once.
- **What leaves the server.** The feed's requests go to GitHub's API and releases without a token, carrying the user agent `j3-bots/<version>`, so GitHub sees the server's address and the release it runs. They go nowhere else: a redirect to a host other than the API's, the releases page's or GitHub's host for release files is refused before a request is sent, so no answer can point the server at another host, one on its own network included.

## The harnesses

What a harness runs is the operator's to choose, and J3 Bots' requests about one are the operator's too: only a paired device asks the engine to check a provider again (`engine.recheckProvider`), and no bot tool reaches it. A check runs the harness the engine already found, as the engine's own periodic check does, so asking for one gains a device nothing. The engine's account of a provider it cannot run (its `detail`) is shown and logged, never acted on, and is cut to 500 characters. It can hold what a harness printed, so the adapter first replaces every secret J3 Bots gives the harnesses, the provider connection's key and each instance's variables, with `[redacted]`; a secret the harness holds on its own, such as a sign-in token it printed, is not known to J3 Bots and is not taken out. J3 Bots installs and updates the harnesses on the same terms: only the operator, through a paired device (`engine.updateProvider`, which the server refuses unless the engine says it can update that harness), and no bot tool reaches it. An update runs the harness maker's own update command as the server's user, as the operator would. The engine runs it, and its lookup of the latest version, with the harness's own environment, so the provider connection's key reaches the package manager and, for a harness npm installed, the install scripts of the harness's own package, which npm allows for that package alone: the maker's code, which runs with the key as the harness anyway ([decision 0044](../decisions/0044-j3-bots-installs-and-updates-the-harnesses.md)).

### J3 Bots' own copies

Where the server finds neither a copy of its own nor the operator's harness, it can install Claude Code or Codex itself, and it keeps the copies it installed up to date ([decision 0045](../decisions/0045-j3-bots-keeps-its-own-copies-of-the-harnesses.md), [Server: J3 Bots' own harnesses](server.md#j3-bots-own-harnesses)). What keeps that safe:

- **Only the makers' own distributions.** Claude Code from `https://downloads.claude.ai/claude-code-releases`, Codex from `https://releases.openai.com/codex`: the addresses each maker's own install script reads. Every request goes to one of those two origins, over HTTPS, and a redirect is refused rather than followed, so no answer can send the server elsewhere, one on its own network included. No mirror is configurable, no install script runs, and nothing is installed with npm.
- **A checksum before anything runs.** The whole download is hashed (SHA-256) and compared with the digest the maker publishes, and with its size where the maker gives one, before anything is unpacked or made executable. A listing that gives no digest for the file fails the install, as a digest that differs does; a download larger than the size listed, or than 1 GiB when none is, is stopped. For Codex the package's digest must be the same in the release listing and in its `codex-package_SHA256SUMS`, and that file's own digest must be the listing's. The listing, the checksum and the file all come from the maker's origin over HTTPS, so the check guards against a download damaged or cut short and a file changed after the listing, not against the maker's origin itself: no signature is checked, since neither maker publishes one J3 Bots verifies (Codex's `.sigstore` bundles are **Assumed** verifiable, and not checked).
- **Then a run, as the engine would.** The unpacked copy runs once, `--version`, with the environment the engine gives a harness and J3 Bots' own harness home as its configuration folder, never the operator's, and Claude Code's self-update turned off (`DISABLE_AUTOUPDATER`); it must say the version listed, or it is removed. Codex's package is unpacked by the system's `tar` (on Windows, `System32\tar.exe`), which by default writes no entry outside the folder it unpacks into, an absolute name or one with `..` (**Assumed** for every system J3 Bots installs on: so GNU tar and bsdtar behave without `-P`, and the archive is the maker's, checked first); the executable is the one its `codex-package.json` names, inside the version's folder.
- **Inside the home.** A copy lives in `<J3_HOME>/harnesses/<provider>/`, written under the private-state rule ([Server: data](server.md#data)); the download, written in place so that it resumes, is opened so that a link at its name is refused, except on Windows. `current.json` names its executable by a path inside the version's folder, with no `..`, and one that does not read is no copy: the server then runs the operator's harness, if any.
- **The operator's own harness is not touched.** A harness found on the server's `PATH` is never replaced, moved or updated by J3 Bots, and while it runs a provider the server installs nothing for it. The operator's `PATH` is not changed: the engine is told the copy's path (`binaryPath`).
- **What leaves the server.** The checks and downloads go to those two origins with no credential, so each maker sees the server's address and which version it fetches, as with its own installer.
- **What it does not defend against.** The copy is the server user's, as a harness the operator installs would be, so a bot's own shell, which runs as that user, could change it, as it could change the operator's.

## Desktop updates

The desktop app updates itself from the repository's GitHub releases with electron-updater 6.8.9, unmodified ([Clients: desktop](clients.md#desktop), [Releasing](../operations/releasing.md)). Builds are unsigned for now. The citations below are **Read** in electron-updater 6.8.9 and builder-util-runtime 9.7.0, which it uses, unless marked otherwise.

- **Where an update comes from.** A packaged app asks GitHub's API over HTTPS for the releases its channel offers and picks the newest by the server's policy: the stable channel reads only `releases/latest`, which is never a pre-release; the nightly channel takes the newest of the stable releases and the nightly builds; a draft or a release candidate is never offered. It reads its platform's feed file from that release's folder (`latest-linux.yml` on Linux, `latest.yml` on Windows, a nightly build's included), and, where it installs updates, downloads the file the feed names from the same folder, and only once the feed names that release's version and only files directly in its folder: whoever can change a release's files can change its feed file, and could otherwise send the download to another release or host ([Clients: desktop](clients.md#desktop)).
- **What is checked.** The download is hashed as it streams and refused unless its SHA-512 is the one the feed gives (builder-util-runtime `httpExecutor.js:457-470`, the refusal at `:431`). A differential download is held to the same check (`differentialDownloader/DifferentialDownloader.js:121`), and so is a file downloaded in an earlier run, before it is reused (`DownloadedUpdateHelper.js:113-125`). **Verified** on Linux: an AppImage at 0.0.1-test, offered 0.0.2-test by a loopback feed whose SHA-512 had been altered, downloaded the file, logged `sha512 checksum mismatch`, kept nothing in its update cache and stayed at 0.0.1-test.
- **What ties it to the project.** The feed and the file come from the same release, so the SHA-512 catches a damaged download, not a malicious release. So once a download is complete, and before it is installed or "Restart to update" is offered, the app checks it as the server checks a release ([Updates](#updates), [decision 0034](../decisions/0034-the-desktop-app-installs-only-a-signed-download.md)), with the same code (`verifyDownload` in `apps/desktop/src/downloadCheck.ts`, `verifySums` in `@j3-bots/release`): it fetches `SHA256SUMS` and `SHA256SUMS.sig` of the version electron-updater downloaded, from that version's own release in the repository, and requires the signature by a release key, a list that names that version's server archives, a file this platform installs (an AppImage on Linux, an installer on Windows), so a feed pointed at another file the release signs, such as `install.sh`, is refused, and the file's SHA-256 as the one the list gives its name. Anything short of that, a release with no `SHA256SUMS` or one that cannot be fetched included, leaves the download neither installed nor offered, and Settings says it didn't match the release's signature. So whoever can publish a release in the repository can no longer ship code to installed apps without the release key. What that does not cover:
  - The file is checked where electron-updater keeps it, in the operator's update cache, and installed from there: a process running as the operator could replace it between the check and the install. Such a process can already change the installed app itself.
  - On Windows, electron-updater checks an update's Authenticode signature against the build's `publisherName` before running it, and skips the check when no `publisherName` is set, as now (`NsisUpdater.js:84-99`).
  - On macOS, the app does not update itself while it is unsigned: it says a newer version is out and links to its release, and the operator downloads it.
  - On Linux, packages carry no signature of their own; the signed `SHA256SUMS` is the whole check for an AppImage. A deb does not update itself: like a Mac build, it links to the release.
- **Installing never cuts work short, and never takes root.** With "Update automatically" on, as it is unless the operator turns it off, a verified update installs by itself: what the launch's check finds before the page opens, what a later check finds as the app quits ([decision 0041](../decisions/0041-the-apps-update-themselves-when-they-start.md)). Off, it installs only when the operator presses "Restart to update". Either way never while the page reports a save under way, and never a download the signed checksums have not matched: electron-updater's own install on quit, which would take any completed download, stays off, and the app's own `quit` handler installs only a verified one. Only an AppImage and a Windows install install one, each as the operator's user: an AppImage is replaced in place, and the Windows installer runs silently. An AppImage in a folder that user cannot write to only says a newer version is out, as a deb does. A deb is never installed by the app. electron-updater would install it with `dpkg -i` as root, through `pkexec` or `sudo` (`LinuxUpdater.js:43-50`, `DebUpdater.js:53-56`), from a file in the operator's own update cache, which any process running as the operator could replace before that step. The app neither downloads nor installs a deb: it says a newer version is out and where to get it.
- **No downgrade.** Only a version newer than the running one is offered (`allowDowngrade` is false, `AppUpdater.js`, `isUpdateAvailable`). The app never sets electron-updater's channel, whose setter turns `allowDowngrade` on; a move from Nightly to Stable keeps the nightly build until a stable release is newer. A broken release is fixed by a newer one, and withdrawing it only stops apps that have not downloaded it yet.
- **What leaves the device.** Each check is a request to GitHub, which sees the device's address. Every update request carries an `x-user-staging-id` header: a random UUID made once and kept in the app's profile (`.updaterId`), so GitHub could tell one installation's checks apart over time (`AppUpdater.js:386-387`, `:502`). The user agent is Electron's default, which names the app and its version (**Assumed**). Nothing about the J3 Bots server, the device's pairing or its conversations goes with them.
- **The page's part.** The page can read the update's status, ask for a check, ask for the restart or call off one that waits for a save, choose the channel (stable or nightly, which the main process keeps in its settings), turn updating by itself on or off (kept there too) and report whether a save is under way, through the bridge, decoded with its schemas on both sides and heard only from the app's top frame. It cannot choose the feed, the file or the version.

## Dictation

- **What leaves the device.** The mobile app's dictation uses the platform's speech recognizer ([Clients: mobile](clients.md#mobile)), and the microphone only from the press of Dictate until Stop, or until the conversation leaves the screen or the app leaves the foreground. Recognition on the device sends nothing; online, the operator's audio goes to the device's speech service (usually Google's on Android, Apple's on iOS) for as long as dictation is on. The app asks Android for the on-device recognizer where it has the device's language installed (**Read** in `expo-speech-recognition` 58.0.1, `ExpoSpeechService.kt`), and takes iOS to recognize online; that the on-device recognizer then sends nothing is **Assumed** from Android's own description of it. While it listens, the line under the composer says whether recognition may run online. Nothing goes to the J3 Bots server but the text, once the operator sends it.

## Secrets

- J3 Bots never asks the operator to paste a secret into a conversation, and the base prompt tells bots not to either.
- When a bot needs a credential, it uses the engine's secret request, which shows the operator an input for each value it asks for, at once, and hands them on without placing them in the conversation. Where they go is the request's, and the card says it: a request for one value without `delivery: "file"` goes to the engine's store, behind a one-use reference the tool that asked reads, so the model never sees it; a request with `fields`, which the engine always delivers as files, and any other with `delivery: "file"`, goes to owner-only files, one per value, that the bot's commands read for 24 hours. A bot can read such a file, so the card does not promise that it cannot ([Engine: secret requests](engine.md#the-adapters-interface)).
- J3 Bots carries the values from the client to the engine and keeps nothing of them: not in the card, the change log, a notification, a command receipt or a log line. The card records only that the values were provided, and a notification carries only the request's label. In code each value travels as a redacted type, from the input to the socket and on to the engine's own call, so printing one shows nothing; an answer that does not fit the card is refused by its shape, never with a value in the error. Each value goes only under the name the bot asked for it with, and only all together: the engine takes every field or none.
- A value the bot marked not secret, such as an email, shows as typed. Every other value is masked, and showing it is the operator's choice on that device only. Only a sign-in's user name and password, a shown value followed by a masked one, are offered to the operator's password manager; any other value is marked not to be filled (`autocomplete="off"`, and on Android not for autofill). On Android a masked value shown on request is still a password to the keyboard (`visible-password`), so the keyboard offers no suggestions for it; that it learns nothing from it is **Assumed** of the keyboards that honour that type.
- Memory files are not a place for secrets. The `remember` tool refuses text that looks like a credential.
- **A secret the operator wants kept**, a website login or a single value, goes to their secrets, from a card the bot raises with `ask_for_secret` or from Settings, never through the conversation. What the operator types on the card goes from the client to the server; the bot is given only the reference, `secret:<name>` ([The operator's secrets](#the-operators-secrets)).
- **The provider connection's key** is typed on the host into `j3-bots provider connect`, without echo, or piped on standard input, never on the command line; or, in the desktop app running the bots on its own computer, into its endpoint form, which sends it to that server once, over the `provider.connect` RPC with no command ID, so no receipt keeps it, and clears the field once the server took it. The command hands it to the running server over the admin socket, and the server to the engine's secret store, as one file holding the base URL and the key together (mode 0600, inside the private home), so a change cut short never pairs one connection's base URL with another's key. Only before the engine starts is it written out to the harnesses: one secret file per instance for the variable each harness's configuration names next to the base URL; `provider connect` restarts the engine for that ([Engine: reaching the models](engine.md#reaching-the-models)). The server keeps no copy and logs nothing of it. Its request types the key as a redacted value, decoded as one at the admin socket and at the RPC, and checked for length only then, so neither a refused key nor a log of the request prints it; a test holds that a key refused for its length and one stored reach no answer and no log. It travels only to the endpoint, so the base URL must be `https`, or `http` to this machine only; the command refuses plain `http` to another host. The engine gives the key to the harness process, in its environment; Claude Code reads it from there through its key helper, `printenv` of that variable. That environment reaches the commands a bot runs in its shell, so a bot can read the key: a Codex command's live environment holding it is **Verified** with Codex 0.171.0, through `exec_command`; a Claude Code command's is **Assumed**, since no run looked. Codex's shell snapshot is turned off ([decision 0019](../decisions/0019-codex-runs-with-a-home-of-its-own.md)), so no file under its home captures the key any more, but the snapshots Codex wrote before that change, which held it (**Verified** on release `4969`, in `providers/codex/shell_snapshots/`, inside the private home), are not removed and can still be there on a home that was upgraded. Keeping the key out of the bots' shells is an open problem.
- **A harness's sign-in from the app** runs on the server, for J3 Bots' home for that harness, with no terminal ([Engine: sign-in from the app](engine.md#sign-in-from-the-app)). Of what the harness prints, only the `https` page it waits on leaves the server, to the client that follows the sign-in; the rest, which may hold a code, stays in memory and is never logged or returned. The page returns to the harness on `localhost`, so only a browser on that computer can finish it. The sign-in refuses a provider home that is a symbolic link, or that other users can open, by its mode or, on Windows, its access list, and Claude Code's credential file when it is a link, as `provider login` does, and never touches the operator's own sign-in.
- **The operator's own provider setup stays out, and stays as it is.** The harnesses run with homes of their own, and the engine starts with an allowlist of the server's environment (the system's basics, locale, proxy and certificate variables), so a server started from the operator's shell does not hand bots the operator's harness configuration, sign-ins or keys. No harness the engine runs uses the operator's `~/.claude` or `~/.codex`: the engine's own default Claude Code and Codex instances are turned off, and any other harness run gets empty folders of J3 Bots' own. On Linux and macOS, Codex runs with a home folder of J3 Bots' own too, so a Codex bot is not offered the operator's `~/.agents/skills`, while its commands keep the operator's `HOME` and profile ([Engine: isolation](engine.md#isolation), [decision 0019](../decisions/0019-codex-runs-with-a-home-of-its-own.md)); on Windows it still is (known gaps, below). This matters most where J3 Bots runs as the operator on their own computer, next to the Claude Code and Codex they use themselves.
- **An export carries the secrets sealed again under a passphrase of its own**, never the key file. It leaves out the engine's credential, the provider key, the providers' sign-ins and the paired devices with their tokens' hashes ([Server: moving to another server](server.md#moving-to-another-server)). The file still holds every conversation, memory and file, so it is written private to the operator (mode 0600, or on Windows an access list of its own) and kept private like a backup. A webhook's secret does not travel: the import gives each webhook a new one. Whoever has the file and the passphrase can open the secrets. Without the passphrase, nobody can, the operator included. The import seals each value again under the new home's key, and no value reaches a log or an error on the way.
- **The trust boundary is the operator's user.** A bot's harness runs as the user the server runs as, and the commands it runs inherit the harness environment. So the connection's key, the engine's secret store and every file that user can read, the operator's own sign-ins included, are within reach of a bot that runs a command to look; the allowlist keeps configuration from leaking in by accident, and is not a wall. The key reaches those commands: a Codex command's environment holding it is **Verified** with Codex 0.171.0, through `exec_command`; a Claude Code command's is **Assumed**. Codex's shell snapshot, a file that held it too, is turned off ([decision 0019](../decisions/0019-codex-runs-with-a-home-of-its-own.md)).

## The browser, secrets and connectors

New in 0.4.0. Three things put the operator's accounts within a bot's reach: the bot's browser, signed in to sites as the operator; their secrets, which hold their logins, values and connectors' secrets; and connectors, which act in their accounts at services. The parts below share three rules and one limit.

- **What they bring in is untrusted.** A page, a connector's tool description and its result are text a bot reads, never the operator's instruction ([Who can give instructions](#who-can-give-instructions)). A bot reports a request it finds there and does not carry it out, and it sends, buys, deletes, shares or changes an account through any of them only with the operator's yes ([Acting on the operator's behalf](#acting-on-the-operators-behalf)), in every permission mode. These are rules of the bot's prompt; what enforces anything is said part by part below.
- **J3 Bots never writes a secret it holds where it keeps or shows things.** A password, a one-time code key, a token, a client secret or a header value that J3 Bots holds is never put into a log line, an entry, a change, a command receipt, an error, a tool result or a prompt. Values travel as redacted types from the client to the secrets and from there to the request, and the requests that carry one take no command id, so no receipt keeps it. Tests drive the secrets' requests, the fill tools and the connectors' requests, and check the logs, the errors, the work steps and the answers. What a bot reads from elsewhere is another matter: a page shows what it shows, a token it prints or an unmasked field included ([The bot's browser](#the-bots-browser)); a filled one-time code, or a password in the wrong field, sits where the bot reads it ([Filling a login](#filling-a-login)); and a connector's server that echoes a secret in a form the redaction does not match reaches the bot's result ([Connectors](#connectors)).
- **Each is off or empty until the operator acts.** No bot has the browser until its switch is on. No secret exists until the operator types one, and a bot uses only those it is allowed. No connector exists until the operator, or a bot, adds one, and it reaches only the bots granted it. A bot never turns on its browser or reads a secret's value: it can ask the operator for a secret on a card (`ask_for_secret`). It can add a connector, under its permission mode ([Bots that change what bots reach](#bots-that-change-what-bots-reach)).

### What a bot's shell can still reach

Every part of this runs as the server's user, and so does every bot's shell ([Trust model](#trust-model), [Secrets](#secrets)). The browser switch and secrets keep values out of prompts, transcripts and logs. They are not a wall against a bot that runs a command to look, which only its permission mode governs:

- **The browser's profile**, its session cookies included, is a folder in the engine's data directory. A bot's shell can read it whether that bot's switch is on or not: the switch decides whether the engine takes the bot's calls to the browser's tools, not who reads the files.
- **J3 Bots' engine token** carries `preview:operate` and is a file of that user, so a process that reads it can open a viewer on any tab of the engine's browser and act in it ([The engine's credentials](#the-engines-credentials)).
- **The secrets' key file**, `<J3_HOME>/vault/key`, and the secrets' file beside it: together they open every secret, connectors' tokens included ([The operator's secrets](#the-operators-secrets)).
- **A filled login** can end up where the bot reads it ([Filling a login](#filling-a-login)).
- **The key the bridges sign with**, in the harnesses' configuration files: with it and a session's id, a process can call the bot tools as that session's bot ([J3 Bots' own surface](#j3-bots-own-surface)). It is a new one each time the server starts.

A [dedicated user](#running-on-a-machine-that-matters) limits what else is in reach. Inside it, the protections here keep secrets from being exposed by accident, and from a model that only reads.

### The bot's browser

A bot whose browser switch is on opens pages in the engine's browser on the host and acts in them ([Server: the bot's browser](server.md#the-bots-browser), [Engine: the bot's browser](engine.md#the-bots-browser)).

- **Shared logins.** The browser keeps one profile, the engine's `default`, shared by every bot whose switch is on, and the operator signs in to sites in it. Each of those bots acts on those sites with the operator's sessions: what it can do there is what the operator's account can do, and the site cannot tell the bot from the operator. So the switch is off for every bot until the operator turns it on, and the engine's browser access is off engine-wide besides it. Turning the switch off takes the browser from the bot at once: its work is stopped, and every thread of its project, a delegated task's or another agent's included, loses it before it runs again. **Sign out of all sites**, in Settings, deletes the `default` profile: every session in it ends, for every bot.
- **The profile holds live session cookies**, so a copy of it lets whoever has it act on those sites as the operator. The documented backup leaves it out ([Back up](../operations/operating.md#back-up)).
- **Help, not a way around.** A bot that meets a check that a person is there, a sign-in, a second factor, a QR code or a passkey asks the operator with a help card instead of getting around it, and the server stops the turn that asked, so the bot cannot go on using the browser while the card waits. Asking is the prompt's rule; stopping the turn is the server's.
- **The stream shows secrets.** A picture of a page is the page: an account's details, a token a settings page prints, a one-time code, what the operator types into a field that does not mask it. J3 Bots does not try to tell a secret on a page from the rest, so every rule about who may see a picture is a rule about who may see those.
- **A paired device is a remote control.** Any paired device can watch every bot's tabs and take one over: click, type, go to an address, answer the page's dialogs, as the bot's browser, with its sign-ins. This is the operator's authority, which a paired device already holds ([Trust model](#trust-model)). A device that is lost is revoked: its viewers close at once, a tab it held included, without the 60 s a dropped connection keeps.
- **The media socket is authenticated as the RPC socket is**, with the device token or a one-use ticket, behind the same `Host` check, and the ticket is not logged.
- **Pictures stay in memory.** The server keeps at most three pictures per viewer: the one in flight, the newest waiting and the last one drawn. It holds them only while the viewer is open. It never writes one to disk or to the database, logs one, caches one or sends one in a push. What the operator types goes to the engine and is not logged.
- **What a page can reach on a device.** The media socket carries pictures and the frames the contract lists, and nothing a page could use to reach the device. The engine's clipboard, downloads, uploads and file pickers are dropped. An address a device sends is `http` or `https` only. A dialog's text is the page's: a client shows it as plain text, as it does any text a page or a bot wrote.
- **The bot can still read a tab the operator holds.** While a person holds a tab, the bot's actions on it fail, but its reads (status, snapshot, waiting for something on the page) still work ([Engine: the bot's browser](engine.md#the-bots-browser)). So the bot can read what the page shows meanwhile, what the operator typed into a field that does not mask it included. A password field is masked in a snapshot as it is on screen: **Assumed**. Every bot with the browser also has the engine's `preview_evaluate`, on Claude Code and on Codex, and a script it runs reads any field's value, masked or not; for a filled login, the owner accepted that ([Filling a login](#filling-a-login)). To keep a value from the bot, the operator uses a card, not the browser.

### The operator's secrets

Secrets seal the operator's logins and single values, and connectors' secrets, under a data key the server keeps in a key file of its home, `<J3_HOME>/vault/key` ([Server: secrets](server.md#secrets), [decision 0046](../decisions/0046-secrets-the-operator-types-a-bot-uses-a-reference.md)). Nothing unlocks them, so they work from the server's start.

What they keep a value out of: prompts, transcripts, conversation entries, work steps, the harnesses' configuration, logs, errors, tool results, update snapshots and backups. What they do not keep it from: **the key file is readable by any process of the server's user, a bot's shell included**, and so is the secrets' file beside it. A bot deliberately misled into reading `<J3_HOME>` with its shell, by a page, a connector's result or a file it opened, can open every secret. Its permission mode decides whether that command runs without the operator's yes, as for any command ([Permission modes](#permission-modes)). Before 0.9.0, the same bot could reach the key in the memory of the unlocked server; the master password guarded only a copy of the file. The wall that would hold is a harness sandbox that denies a bot's shell any read of `<J3_HOME>`, which neither harness gives J3 Bots yet; it is a later item ([Known gaps](#known-gaps)).

| Threat | What stands in its way | What does not |
| --- | --- | --- |
| A copy of the secrets' file leaves the machine: a disk, a synced folder | Every value is sealed with AES-256-GCM under the data key, bound to its record and field. Updates never copy the file or the key into a snapshot. | A copy that has the key file with it opens everything: keep the key file out of such copies, or apart from them ([Operating: secrets](../operations/operating.md#secrets)). What the file keeps in the clear: each secret's name, kind, times, which bots may use it, and where and when it was last used and shown. |
| A bot, or anything running as the server's user | No tool returns a value: a bot gets a reference, and the server puts the value where it is used, for the bots the secret allows. | The key file and the secrets' file are that user's files ([What a bot's shell can still reach](#what-a-bots-shell-can-still-reach)). |
| A bot uses a secret it should not | A secret is used only for the bots it allows: the one that asked for it, or more as the operator sets. A reference to any other fails, saying which secret and why. | Every secret the operator lets every bot use is within reach of every bot, those made later included. |
| A page a bot reads talks it into asking for a secret | The card shows the operator the bot, the name, a login's site and the bot's note, says the bot will not see what they type, and notifies them. The operator chooses whether to save anything; declining wakes the bot to say so. | A login saved for the wrong site, if the operator does not check it: the server then fills it wherever that site's page asks, for every bot the login allows ([Filling a login](#filling-a-login)). |
| A paired device falls into other hands | Revoking the device closes its sockets at once. | Any paired client can read any value: a device token carries the operator's authority. |
| A value leaks into what J3 Bots keeps or shows | Values are redacted types from the client to the secrets, and from there to the page a fill types into, the request a connector makes or the command it starts, whose server's answers are scrubbed of every value it was sent, an argument's included. No request that carries one takes a command id, so no receipt keeps one, and no value reaches an entry, a change, a work step, a log line, an error or a tool result. Tests drive the secrets' requests over the socket, the ask and fill tools through the bot tools, and check the logs, the errors, the steps and the answers. | What a client does with a value it was asked to show. The web and Android hide a shown value after 30 seconds. Copy puts it on the system clipboard, which other apps can read and which J3 Bots does not clear. |
| A value the operator copies stays on the clipboard for other apps to read | The desktop app and the Android app take it off 30 seconds after Copy, or, on Android, as the app comes back to the foreground once that time is up, only if the clipboard still holds it, so nothing copied since is lost. Android marks it sensitive, which keeps it out of the clipboard's preview. | Any app that reads the clipboard before then, a clipboard manager or history that keeps what was copied, and a value the desktop app quits on before its time is up. In a browser, and on iOS, the client cannot read the clipboard back without asking the operator, so a copied value stays until something else is copied. |
| The key file is lost | The server changes nothing: the secrets are `unreadable` until the file is put back. | Without it, nothing recovers them. |

### Filling a login

A bot whose browser is on can have the server type a login it may use into its browser tab, unattended: there is no confirmation for each fill ([Server: filling a login](server.md#filling-a-login), [decision 0037](../decisions/0037-the-server-types-a-saved-login-into-the-bots-tab.md)). The bot is never handed the value: no tool result, work step, entry or log line carries it. It can still read it from the page, which the owner accepted (the row on reading the value back). What keeps a page from taking it, and what does not:

| Threat | What stands in its way | What does not |
| --- | --- | --- |
| A page asks the bot to fill a login on another site, or a lookalike | The server reads the tab's committed address from the engine after it took the tab, so the bot cannot move it meanwhile, and the bot's word counts for nothing. The page's origin must equal one of the login's exactly: scheme, ASCII host and port, so a lookalike name is compared in punycode and never matches the real one, and a subdomain is another origin. Plain `http:` is refused except on this computer, and so is any page whose own address is not `http:` or `https:`, a `blob:` page included. The address is read again right before typing, and a page that moved types nothing. | A login saved for the wrong origin. A page of the login's own origin that sends itself elsewhere between the server's last read and the typing: the engine types into whatever page is there when it runs the input. Only a page of that origin can time this, and such a page can already take the value where it is typed (next row). |
| A page asks the bot to fill the login into a field that is not the login's: a comment box, a search field, a field that sends what it gets elsewhere | The fill types where the bot focused, on the login's own origin only, so what a page can do there is what that site can do. After a password the server always presses Enter, and clears the field when the page stays. A refused fill closes that tab to fills for the rest of the turn. The tool's description and the base prompt tell the bot to fill only a site's sign-in form, and to tell the operator when a page asks otherwise. | J3 Bots cannot tell a password field from a text field: the engine's viewer channel does not say which element has focus. A page on the login's origin, a compromised or hostile one, can get the bot to focus a field it reads, and receive the value there. |
| A frame inside the page reads the value | The origin checked is the top page's. | J3 Bots cannot tell the top frame from a cross-origin frame either: if the bot clicked into an embedded frame, the value goes to that frame's page. |
| The bot reads the value back from the page | The bot cannot act on the tab while the server types: it holds the tab. The bot does not get the tab back on a page with a filled password field: the server submits and, if the page stays, empties the field first. A password field shows dots in a snapshot, as on screen (**Assumed**). | **Accepted by the owner:** a bot a login allows can read a value it just filled back out of the page with a script, through the engine's `preview_evaluate`, which every bot keeps, on Claude Code and Codex. A script it runs before the fill can also catch the value as it is typed. Its result reaches the model, so the model and its provider may see the value. The owner accepted this to keep page scripts for every bot. The guards above still stand: the exact origin, the server holding the tab while it types, logins allowed per bot, and the field cleared after a submit that stays. The real fix is a field the bot cannot read, which only the engine can give ([Proposal: a typed secret in the engine's browser](../proposals/engine-browser-secret-input.md)). A user name and a one-time code are typed in fields that show them, so the bot can read them on the page, as the operator would. A page that copies the value elsewhere in itself, where the bot reads it, gives it away. A bot's shell can read the browser's profile, saved form data included, as for every bot ([Known gaps](#known-gaps)). Clearing a password types Backspaces where the focus is: a page that moves the focus when Enter is pressed, as a form with an empty required field does, gets them in that field, and the password stays where it was typed. The server reads the page every 100 ms for a sign-in that leaves it: a page that loads another and has finished between two reads, or one still loading after 6 s, counts as staying, and the Backspaces go to the new page. When the engine does not confirm the typing within 5 s, the fill answers `unavailable` and gives the tab back without clearing it, so a password may be left in the field. |
| A bot fills when the operator did not want it to | A login is filled only for the bots it allows: the bot that asked for it, or those the operator chose. A bot whose browser is off fills nothing. The browser switch and the login's bots are read again right before typing, and so is the bot's turn, so turning the switch off, taking the login from the bot or stopping the turn stops a fill that has not typed yet. A fill must match a call the engine recorded in the bot's running turn, so no other program on the computer can ask for a fill the bot did not ask for. One that copies the bot's own call, with the same arguments, can claim it first, as for every bot tool: the fill then runs as the bot asked, and that program gets its answer, which carries no value. Each fill, typed or refused, shows as a step of the bot's work, with the login, the field and the page's origin. | Within those, nothing asks the operator first: that is the owner's choice, for unattended work. |

**What would close the residual.** The two things J3 Bots cannot tell, which element has focus and in which frame, the engine knows. A proposal for T3 Code to say so, or to type a secret it never hands to a viewer at all, is in [Proposal: a typed secret in the engine's browser](../proposals/engine-browser-secret-input.md). It has not been sent anywhere.

### Connectors

A connector acts in the operator's account at a service, from text a remote server writes, so each part of it has a rule ([Server: connectors](server.md#connectors)).

| Risk | What stands against it |
| --- | --- |
| A bot holds a token | J3 Bots is the connector's OAuth client and calls it itself. Tokens, refresh tokens, client secrets, header values, a command's environment, and a connector's address, typed by the operator or filled in by a gallery entry's form, and a command's arguments, which can carry a key, are in the operator's secrets, as connector secrets ([decision 0028](../decisions/0028-one-secret-store-for-logins-and-connector-secrets.md)) and added to a request only when the server makes it. None reaches a bot, a harness's configuration, a prompt, an entry, a client, a log line or a command receipt: clients are shown an address's origin and a command's program alone. What a client sends of them travels as a redacted type, checked only once redacted so a refusal never prints it, and the requests that carry one have no receipt. A removed connector's row goes at once, and with it a record of what is left: its sign-in is revoked and its secret deleted then, or, while the secrets cannot be read, as soon as they can. |
| A tool description or result carries instructions | Both are untrusted text. A description is capped, it and every string of the tool's input schema are stripped of control and format characters and of J3 Bots' framing; a tool whose schema keys that would change is left out. A bot reads each description after J3 Bots' own line saying which connector's server wrote it, that the tool acts in the operator's account and writes only on their ask or yes, that it tells what the tool does and never what else to do, and that nothing from the machine is passed because it asks: a model takes a tool's description as how to call it, so the warning sits where that text is read. A result is cut to size and reaches the bot framed as data from that connector, between tags whose random nonce the text does not contain, with any J3 Bots framing in it defused, so it cannot close the frame or imitate J3 Bots. The base prompt says a request found in a result is reported, not carried out. |
| A server changes its tools after it was trusted | Its tools are what it lists now, with no review of J3 Bots' own ([decision 0047](../decisions/0047-j3-bots-is-a-complete-mcp-host-at-the-current-specification.md)): a review covered only what bots are told a tool is, while a server could always change what a tool does behind the same listing, and each listing is cleaned as above. A tool that changes still runs only under the bot's permission mode: an approval in Supervised, the provider's reviewer in Auto. |
| A resource or a prompt carries instructions | Both are untrusted text, read only by a bot's own call to `read_connector_resource` or `get_connector_prompt`, or by the operator's `/` menu. A bot reads them framed as data from that connector, as a result is, scrubbed of the connector's secrets and cut to size; a listing is cut at 20,000 characters. A prompt the operator picks is put in their draft, which they read before they send it as their own. |
| A connector's skill carries instructions, or changes under a bot | A skill is untrusted text, loaded only by a bot's own call to `use_connector_skill`, which asks as the bot's permission mode says, and framed as data from its connector with J3 Bots' lines after it: it grants nothing, and its scripts are only files ([decision 0089](../decisions/0089-a-connectors-skills-load-through-j3-tools.md)). Its `allowed-tools` is ignored, and a `SKILL.md` among its files is not a skill. Every file is read only if the skill's entry lists it, and checked against it: size, SHA-256 and the frontmatter field by field; on a mismatch the server asks for the entry again once, then refuses the skill and says so. A skill its server generates is checked by its frontmatter only, and read up to 16 MiB a load. A bot reads only files of a skill it loaded from that connector, by a path inside the skill's folder, so a skill of the same name at another connector, or an address the bot writes, reaches nothing. Instructions that changed since the bot loaded them are refused until it loads them again. A listing a server marks private is kept with the sign-in that read it, and never served under another. |
| A server asks the operator for something | A request for input (elicitation) is a card in the conversation of the bot whose call caused it, naming the service, and its answer goes to the server only, never to the bot. A form whose field's key, label or description names a password, a key, a token, a PIN, a one-time or verification code or an authenticator is declined unseen, as MCP asks of a server; a page opens only at an `https:` address with no credentials in it, shown by its host, on the operator's device, never on the server. A request with no bot's call behind it is declined. Nothing answers for the operator: a card left open expires with the call. J3 Bots never lets a server sample a model through it. |
| A connector sends, deletes or shares without the operator | Its tools are not pre-approved: they follow the bot's permission mode. The base prompt's rules on [acting on the operator's behalf](#acting-on-the-operators-behalf) hold in every mode. The mode binds the harness, which forwards a call only once it is allowed. The server's match does not see the approval: the engine's Claude Code adapter and Codex itself record a call before they ask for it (**Read** at `bc0f04d`, `ClaudeAdapterV2.ts`, `canUseTool`; in Codex `rust-v0.171.0`, `core/src/mcp_tool_call.rs`), and a connector's call can be claimed after its record closed. So a request that names the session and carries the call's input could claim a call while its approval waits. On Claude Code, once the operator declines it, no request can: the engine's adapter files the approval under the call's tool-use id (**Read** at `bc0f04d`, `ClaudeAdapterV2.ts`), so the server knows which call it holds back, and the decline, written before the engine hears it, ends the call for every claim. Codex's approval of an MCP tool is filed under the server's name alone, as an elicitation (**Read** at `bc0f04d`, `CodexAdapterV2.ts`, `mcpServer/elicitation/request`), so the engine does not say which call it holds, and a call the operator declined on Codex can still be claimed until its turn ends. It takes the key the bridges sign with, the session's id, and the input the model wrote, which is not logged but is known in advance for a tool that takes none. Only the operator's user has the key, and it is already past the mode, as a bot's shell allowed to run commands is ([J3 Bots' own surface](#j3-bots-own-surface)). An approval card names the connector's tool and shows its input as the engine recorded it, never only an argument the tool calls `command`. |
| A bot reaches a connector it was not given | The server checks the connector's grant for the session's bot on every call, and again right before each request of that bot's session is signed, so a grant taken away while a call waits goes out unsigned, if at all; the bot's session closes with it. It matches the call to the bot's running turn as it does every `j3` tool, with no weaker path. A bot that adds a connector gets it alone, and only the primary bot grants one to other bots ([below](#bots-that-change-what-bots-reach)). A teammate's request does not lend its connectors. |
| A sign-in is forged or misdirected | PKCE with S256, required of the service. `state` is random, used once, expires after ten minutes and is bound to the connector and the device that began the sign-in; only that device can finish it, and the server's own callback finishes only a sign-in that returns there. Another device's attempt does not use the sign-in up. The parameters of the address the device opens are J3 Bots' own: a curated entry may add one a service needs (Google's `access_type`), never one J3 Bots sets or a request object (`request`, `request_uri`) that could set them, nor where the code returns (`response_mode`), and the server refuses at start a list that tries. The resource a sign-in names never holds a key a gallery entry's form put in its address, and such an entry never signs in with OAuth. The returned address must be the registered redirect exactly, and each authorization server has a redirect path of its own, from its issuer exactly as written, so an answer one of them sent cannot finish a sign-in at another (mix-up, RFC 9700 §4.4), and it must name the issuer when the service promised to (RFC 9207). Every OAuth endpoint must be `https:`, and a client opens a sign-in only at an `https:` address. |
| J3 Bots' OAuth client is impersonated | Its client id is the address of a metadata document the server serves at its public `https:` origin, one per authorization server, which lists only J3 Bots' own callbacks and holds no secret ([Server: the OAuth client](server.md#connectors)). Whoever names that id gets codes sent only to those callbacks, which finish only a sign-in the server began, with its PKCE verifier and `state`. The server reads the document itself, through the client that reaches public addresses only, before it names it, so a sign-in never leaves the operator at a provider that cannot read it; otherwise it registers, as before. |
| A token reaches a server it was not issued for | The `resource` (RFC 8707) is asked for on the authorization and on the token request, and the resource the metadata names must cover the connector's address. The token is sent only to that connector's server, never to an address a metadata document or an answer names later, and never to another connector. J3 Bots never takes a token from a bot or a client to pass on. |
| J3 Bots is used as a confused deputy | J3 Bots is a client, not an MCP server that signs others in, so no third party's consent rides on its client. Each server registers its own client per service, for its own redirects, and uses it again only for a redirect it registered, loopback on any port included; the operator's own client is the operator's. Metadata from a connector's server only points to where to sign in: the issuer it names must match its metadata exactly, which must offer PKCE S256 and `https:` endpoints, and a saved client is never used with another issuer. The operator's own client is given with the issuer it was registered at, and refused for a connector that names another, so a connector's server cannot point J3 Bots at one of its own to collect that client's secret. A sign-in that is still being prepared, or finishes, after the connector was signed out, signed in again or removed is dropped rather than undoing it, and never writes a removed connector's secrets back. |
| A sign-in's code or `state` leaks | The verifier never leaves the server, so a code is useless to whoever catches it. The code, `state`, verifier, tokens and client secret are redacted values; none is logged, returned in an error or written to an entry or a receipt, and the callback's query is left out of the request log and of traces, however the request names its path. Requests to authorization servers, and the discovery request to the connector, record no trace span, since the connector's address can hold a key. The callback page loads nothing and sends no `Referer`. A test signs in and refreshes with every value in view and finds none in the logs or the errors. |
| The server is made to reach into the operator's network | A connector's address is `https:`, with no user name or password. Every address its name resolves to is checked as each connection opens, not once when it is added, so a name that resolves elsewhere later (DNS rebinding) gains nothing: loopback, link-local, unique-local, private and reserved addresses are refused. An address in the operator's own network is refused until they confirm it for that connector, on the card a bot's ask shows or, for a client of protocol 11 from before 0.10.0, in its form, and loopback, link-local and reserved ones are refused even then, as are the cloud metadata services' addresses that sit in a private network's ranges or in public space (Alibaba Cloud's, Azure's platform endpoint, and the IPv6 ones of AWS, Google Cloud, Oracle Cloud and Akamai; **Read** in Google Cloud's documentation for its own, and in cloud-init's Oracle data source for Oracle's). A redirect is never followed by the transport: each is a new request, checked as the first. Addresses a remote server names (metadata, registration) are checked the same way. A sign-in's requests never reach the operator's network, even for a connector they confirmed there, follow no redirect, and have 15 seconds, answer included, and 64 KiB at most. |
| A connector's server is slow, huge or hangs | Opening a session or listing all of its tools may take 30 seconds, and a call 10 minutes, or an hour for one its server answers with a task. A call that is stopped or out of time has its request aborted, its connection closed, whether or not the server heeds the cancellation it is also sent. Once connected, a server has 11 minutes to begin any answer. An answer is read up to 8 MiB, a listing up to 64 pages and 8 MiB of tools once cleaned, and a bot reads at most 100,000 characters of a result. However often a server says its tools changed, a connector is listed once at a time, and once more after. Its progress reaches the bot's step at most once a second, and its log messages the server's log at most 30 a minute, 500 characters each. At most 32 sessions are open at once: a new one past that closes the idle one unused the longest, a call finds the server busy only while every one is in use, and each closes after ten idle minutes. |
| A gallery entry misleads the operator | The curated list's text, glyphs and addresses are J3 Bots' own, reviewed for each release; the registry never changes a curated entry's address. A registry entry's text is its publisher's: shown as plain text, cut short, without control or direction-changing characters, and with who published it, as the domain that owns its host or as the namespace that published it, never as "verified". Only the server reaches the registry, and it sends it only the words searched for ([Server: connectors](server.md#connectors)). |
| A connector started by command runs code | It is code execution, on the server's computer, as the server's user, with everything that user can reach: its files, its network, its other credentials, the secrets' key file. A bot adds one under its permission mode, as it runs any other command ([decision 0049](../decisions/0049-the-bots-manage-mcp-servers-and-skills.md)); the clients add none ([decision 0068](../decisions/0068-settings-lists-what-the-bots-added.md)). When the operator changes one's command line, the server makes sure the choice is the one they saw: a paired client sends it only after a confirmation that shows the whole command line and the name of every environment variable, and again whenever either changes. A variable that decides which code runs (`NODE_OPTIONS`, `PYTHONPATH`, `LD_PRELOAD`, `DOTNET_STARTUP_HOOKS` and the like, `codeVariable` in `packages/contracts`) is part of the command line, value included: the confirmation shows its value above the program, its value may not be a reference to a secret, whose value changes with no new confirmation (a command saved with one before the server refused it does not start until its line is confirmed again with the value itself), and a new value is a new command line, confirmed again, which the server takes only whole (`values` naming one is refused); the Android app changes none, a convention of the apps rather than a wall the server keeps. A package fetched as it starts (`npx`, `uvx` and the like) must be named at an exact version, or the command is refused, so a registry cannot swap the code between the confirmation and a start; a launcher option the server does not know is refused rather than guessed at, and so is one that names a configuration file (npm's `--userconfig`, uv's `--config-file`). The server starts such a launcher with no configuration file of the user's or of a project's, where a registry, a package or a script shell set there would run code the line does not name: npm's user file is the system's empty device (`npm_config_userconfig`), and it runs in a folder of the server's, `<J3_HOME>/state/npm-project`, which holds only an empty `package.json`, so that is the project whose `.npmrc` it reads, and no project's installed package stands in for the one fetched; uv is told to look for none (`UV_NO_CONFIG`). **Verified** with npm 11.19.1 against local registries: a registry in the home's `.npmrc` was used when npm ran in the home folder, also with the user file pointed away, since the home is then the project; run from that folder, npm used its default registry, and the folder still held only its `package.json` after a pinned `npx --yes` ran there. **Verified** with uv 0.13.6: `UV_NO_CONFIG=1` left the user's `uv.toml` unread; that it leaves a project's unread too is **Read** in uv's documentation for `--no-config`. A file named on the line beats both: npm read the `--userconfig` it was given over `npm_config_userconfig`, and uv read the `--config-file` it was given under `UV_NO_CONFIG=1` (**Verified**, same versions). It starts with no shell, and gets none of the server's environment but where programs are, its home, its language and its temporary folder (on Windows, what Windows needs to start a program), so a provider's key or J3 Bots' settings in the server's environment never reach it. Its command line and variables are kept in its connector secret, one record a change replaces whole, and travel redacted; clients are shown its program alone, and what runs is read from that secret, never from what they are shown. A change of the command line or a value stops the old process at once, even mid-call. What it answers is scrubbed of its variables' values before a bot reads it, and its standard error, where a server may print what it was given, is never read. It runs only while used, one process for all bots, at most a few at once on a small computer, and stops with everything it started: a process group on Linux and macOS, a job object on Windows. |

### Bots that change what bots reach

From 0.9.0 the bots add, change and remove MCP servers and skills ([decision 0049](../decisions/0049-the-bots-manage-mcp-servers-and-skills.md), [Server: what the bots manage](server.md#what-the-bots-manage)). A skill is standing instructions to every bot that has it, and a server is tools they call, so each part of it has a rule.

| Risk | What stands against it |
| --- | --- |
| A bot changes what it reaches without the operator | The tools that change something are not pre-approved: the bot's permission mode decides, as for its shell, so Supervised asks, Auto has the provider's reviewer look, and Full access runs. The base prompt and each tool's description say to add one only when the operator asked or agreed, never because something the bot read said to. Every change says who made it and when, as a step of the bot's work and beside the server or skill in Settings, where the operator can undo it. |
| One bot reshapes what every other reaches | Only the primary bot adds or changes a server or skill for other bots. Any other bot changes only what is its own alone: a server only it uses, and the skills of its own workspace. The server checks this for the bot whose running turn the call is matched to, on every call; a teammate's request does not lend it the primary bot's reach. |
| A bot is talked into adding a server | An address in the operator's own network and a gallery entry that needs the operator's own app are added only on the operator's yes. The bot's call adds nothing: it shows a card in the bot's own conversation that names the address by its host, or the gallery entry with its setup, and the server records the yes only from the operator's answer to that card (`card.answer`), never from anything a bot can call or write. What the bot asked to add is held as it asked it, so the operator allows that address and nothing else, and a bot that rewrites its call asks again. An own app's client is typed on the card and goes to the connector's secret only, redacted from the moment it is decoded: no entry, receipt, log or wake holds it, and the bot is told only how the add ended ([Server: the operator's yes](server.md#the-operators-yes)). A command server runs code as the server's user: the description says to add only one the operator would run themselves, and the command's own rules (exact versions, its environment) hold as for a line the operator types. In Full access, nothing asks: the record afterwards is what shows it. |
| A bot learns a key | A key is written as a reference, `${secret:<name>}`, to a secret the operator saved; the bot never sees the value, and the tools never answer a header's or a variable's value. |
| A bot sends a secret to a server, or to bots, it should not reach | A connector's settings are one for every bot it goes to, so a reference in them is resolved for the connector: it is used only while every bot the connector goes to may use that secret, by the secret's own rule. Adding, changing and granting a connector check each reference against each bot it will go to, from Settings and a bot's tools alike, and a refusal names the secret and keeps nothing. A bot may write a reference only to a secret it may use itself, so it cannot point another bot's key at a server of its choosing, and a reference in an address is refused. Once a connector's settings reference a secret, no bot changes where they send it: its address, its headers, its command's program and arguments, and its variables stay as they were, its references aside, whatever the bot's permission mode, so a connector the operator saw added keeps sending its secrets where they saw; the operator changes them, or the bot adds a new connector and asks for the secret again. A new connector a bot adds may still reference any secret the bot may use ([decision 0046](../decisions/0046-secrets-the-operator-types-a-bot-uses-a-reference.md)), under its permission mode, so a secret is shared only with bots trusted with it. A key the operator typed into a command's variable as a plain value, not a reference, is not held there: a bot that may change that connector can change its other variables, and the key goes with the process. A secret deleted, emptied or narrowed later stops the connector, which then says which secret it needs and sends nothing: a reference never reaches a server as text ([Server: secrets in a connector's settings](server.md#secrets-in-a-connectors-settings)). |
| A skill from a repository runs code | Nothing in a repository is run: J3 Bots reads one commit from git's own objects, with nothing checked out and git's hooks, filters, submodules, credential helpers, prompts and redirects off, and none of the operator's git configuration. The address is `https:` and checked as a connector's is, so none in the operator's network. A link or a submodule in the folder refuses it. The commit installed is recorded, so the operator sees what was read. A script it ships runs only if a bot runs it, as any file. |
| A skill writes where it should not | A skill's name is one lowercase segment; its folder and every link to it go through the private-location check, so a link at a skill's place, or a skill folder that leads out of J3 Bots' data, is refused. J3 Bots' own skills (`j3-…`) take no change. |

**Logged:** a connector's id and host, the tool's name, the outcome, the HTTP status and how long a call took; for a connector's app, the bot, the view, each request's method and tool and its outcome. **Never:** a secret, a sign-in's code, `state` or PKCE verifier, the address a sign-in returned to, a call's arguments or its result, an app's document or what it sends, which are the operator's data. A result stays in the engine's transcript as any tool's output does. Before a bot reads it, any value of the connector's own secrets in it is replaced with `[redacted]`, so a server that echoes what it was sent does not put it there: the header values and token that request was signed with, a refused one included, the path and query of the address, whole and each query value, and each secret value of a gallery entry's form, as given and URL-encoded, which the address and headers carry only inside another value. A listing is treated the same before it is kept, shown or offered, in tools' names, descriptions and schemas, and a tool whose name or schema keys hold one is left out. This finds exact values only: one of 8 characters or more wherever it stands, and one known to be a secret (a secret field's of a form, or what a secret reference resolved to, but a login's user name, which is ordinary text and is taken out only from 8 characters) of 4 to 7 characters where it stands as a word of its own, a structured answer value by value. A shorter one would match ordinary text, so it is not taken out, and a short value that is not known to be a secret, such as a plain header's, is taken out only from 8 characters. A server that encodes, splits or changes a value is not caught. A secret the server returns of its own is the operator's data, as any result is. The headers and the token are read from the store as each request is made, and no session keeps a copy. Tests cover each case: the headers and token on the request, a refused token, a header value with a line break, an echoed secret in a result and in a listing, a token renewed while a call ran, and the errors, which carry no URL, secret or text of the remote server.

## What is logged

- Conversations, rooms and memory are the operator's data, stored on their disk, in the clear.
- Server logs record wakes, dispatches and outcomes with identifiers, not message text, and, for each provider the engine cannot run, the engine's account of why, with J3 Bots' secrets taken out ([The harnesses](#the-harnesses)).
- No telemetry leaves the machine by default.

## Known gaps

- No isolation between bots at the filesystem level, and none between a bot and the operator's user.
- A bot can send a message to another bot's session through the engine's own `t3_thread_send`, which reaches any thread of the engine that runs in no broader a mode than the sender's (**Read** at `bc0f04d`, `mcp/toolkits/orchestrator/tools.ts`). That message goes around J3 Bots' teammate messages and their limits, and the turn it starts shows as background work the server did not dispatch. So a bot without the browser can ask one with it to use it. This predates the browser switch.
- No protection against a compromised paired device beyond revocation.
- The browser, secrets and connectors keep secrets out of what J3 Bots keeps and shows, not out of reach of the server's user: a bot's shell can read the browser's profile, the engine token, the key the bridges sign with, and the secrets with their key file ([What a bot's shell can still reach](#what-a-bots-shell-can-still-reach)). The wall that would hold is a harness sandbox that denies a bot's shell any read of `<J3_HOME>`, a later item. A login filled into the wrong field on the right site can reach the bot ([Filling a login](#filling-a-login)).
- A bot a login allows can read a value it filled back out of the page with a script (the engine's `preview_evaluate`, which every bot keeps), so the model may see it. The owner accepted this to keep page scripts ([Filling a login](#filling-a-login)).
- On Linux without a keyring the desktop app can use, its device token is stored obscured, not encrypted. The app says so rather than refuse to pair, and the token stays obscured until the device is paired again.
- Desktop builds carry no code signature: an update is checked against the release key's signature over `SHA256SUMS`, but the first install is trusted as far as the page it was downloaded from, and Windows and macOS do not check who published it ([Desktop updates](#desktop-updates)).
- A nightly is signed with the release key with no review: whatever reaches `main` reaches every server and app on the nightly channel the next day ([Release signing](#release-signing)).
- Push notifications pass through Expo's push service and Apple's or Google's, which see what a push says; previews are opt-in for that reason. A push cannot be withdrawn: it stays on the phone after the operator answers elsewhere. A browser notification never leaves the device, but it can show on a screen others see, so the same setting holds for it.
- A visual that never yields, a script stuck in a loop, stalls the other visuals that share its renderer process; each shows as failed after ten seconds, and the client's own page stays responsive (**Verified**, Chrome 151 and Electron 44). A reload does not reliably bring them back, since the new frames can land in the same stuck process: Chrome drew them all again in one run and none in the next, and the desktop app none through two reloads half a minute apart (**Verified**, Chrome 151 and Electron 44). Closing the tab or restarting the app starts a new process (**Assumed**). Firefox and Safari have not been tried.
- A visual can name another host in a resource hint, `<link rel="preconnect">` or `rel="dns-prefetch"`, from its markup or a script. Chromium hands such a hint to the browser when the element is added, with no check of the Content Security Policy, the sandbox or an opaque origin (**Read**, `PreloadHelper::PreconnectIfNeeded` and `DnsPrefetchIfNeeded`, Chromium `third_party/blink/renderer/core/loader/preload_helper.cc`), before the guard could remove it. The browser may then look the host up and open a connection to it, so a visual could tell a host it was shown, and what a host name can carry, though it reads nothing back. On the test machine no hint from a visual reached the network in seven runs, but in those runs neither did a hint of the framing page's own, so this does not show that Chrome ignores a visual's; that it acts on one is **Assumed**. Closing it would take visuals without scripts, whose markup could then be refused a `<link>`; a script can add one however its tag is spelled.
- On Android, a visual that navigates its own frame while it is still loading shows the WebView's error page in place of the visual: it never reports its height, and the app, unlike the web and desktop clients, gives a visual no time limit to report one ([Visuals on Android](#visuals-on-android)). A visual that reloads itself (`location.reload()`) comes back whole in its frame there, but the shell counts that load as the frame leaving the visual, so it shows as failed. A visual that navigates once it has loaded shows as failed on every client. That the web and desktop clients count a frame's loads right is **Verified** in Chromium only; in Firefox or Safari, a load fired more or fewer times around the document written into the frame would fail every visual, or miss one that navigated.
- A visual can navigate its own frame to another address of the server it was loaded from: `frame-src 'self'` lets the request go, and the answer is refused only after it arrives (`frame-ancestors 'none'`); the desktop app stops it before it leaves. The visual learns nothing from it, and gains nothing a page on any other site could not do with the same request.
- The automatic reviewer in Auto mode is the provider's, and its judgment is not J3 Bots' to guarantee.
- A sign-in returns to an address the device controls only as far as its system does. A relay's loopback port, or the page a pasted address names, can be taken by another program of the operator's user on that device, which then sees the code; without the verifier it cannot use it, but it can keep the sign-in from finishing. Signing in through a browser of another user on the same computer is no different.
- A connector started by command runs as the server's user, and nothing keeps it from what that user can reach: not the bots' workspaces, the server's database or the operator's other files, and not the secrets' key file. J3 Bots checks that what runs is what the operator confirmed, not what it does. Running the server as a dedicated user ([Running on a machine that matters](#running-on-a-machine-that-matters)) is what limits it.
- A command connector's arguments are on its process's command line, which other users of the computer can read in the process list on most systems; on Windows, the launcher's too. A secret belongs in its environment, as a reference to one of the operator's secrets, which the process list does not show to other users. A server that writes a value it was given to a file or the network is not stopped.
- npm still reads its global configuration, the `npmrc` of the Node installation it runs from, which belongs to whoever installed Node, and whether `UV_NO_CONFIG` also leaves uv's system file (`/etc/uv/uv.toml`) unread is **Assumed**. The variables that decide which code runs are a list of J3 Bots' own (`codeVariable`): a program that loads code named by another variable is not covered, and that variable's value still changes with no new confirmation, and may be a reference to a secret. An argument may be one too, as a key on the line is (`--token=${secret:<name>}`): it is confirmed as the reference, and the secret's value is the operator's to change. npm takes a folder above its own for the project when that folder's `package.json` lists it among its workspaces, and then reads that folder's `.npmrc`: a home put inside such a project, with a workspace pattern that takes in `state/npm-project`, gives npm that project's configuration (**Verified** with npm 11.19.1: run from such a folder, `npm exec` took the registry of the `.npmrc` above it, and the default one once the pattern was gone). With `npm_config_workspaces=false` there, `npm exec` failed rather than leave the workspace out, so the server sets nothing for it: where the home is, is the operator's choice.
- The version check reads `npx`, `npm exec`, `uvx` and `uv tool run` only. A command that fetches code another way (another launcher, `uv run --with`, a script that downloads, a package manager's own `dlx`, a link to `npx` by another name, or `npx` reached through `cmd /c` or a shell) runs as given. On Windows a program that is a batch file, as `npx.cmd` is, runs through the command interpreter, which reads its own syntax in the arguments: the server refuses to start one whose arguments hold a character the interpreter treats as more than text, but what the batch file itself does with them is its own.
- A server killed before it can stop its command connectors' processes leaves them to end by themselves. Most do, since its end closes their input; on Windows the launcher then ends too, and the job with it. On Linux and macOS a process that ignores its input, and whatever it started, runs on until the computer restarts or someone ends it.
- What a connector's server does with what bots send it is that server's to answer for.
- A connector's app draws what its server wrote, which can imitate J3 Bots' own lines, and runs, as its bot, the tools its server opened to apps: without asking when the bot is in full access ([Connector apps](#connector-apps)). An app gets no origin of its own, so one that needs its own storage or an origin its server's CORS names does not work in J3 Bots.
- On Windows, a Codex bot is offered the operator's `~/.agents/skills`, so on a Windows computer that runs the bots itself, every skill the operator keeps there for their own coding reaches every Codex bot. Codex finds that folder through the system's profile folder and reads no variable for it (**Read**, Codex 0.171.0 `ext/skills/src/host_roots.rs`, `dirs-sys` 0.5.0). **Verified** on Windows 11 with Codex 0.171.0: its app server listed a skill there as enabled with `HOME`, `USERPROFILE`, `HOMEDRIVE` and `HOMEPATH` all moved to an empty folder. No Codex release has a setting that turns only that folder off (**Read** in 0.172.0, `3d86e43`, the newest stable, and 0.174.0-alpha.7, `380fb87`, the newest prerelease), and J3 Bots does not turn the operator's skills off one by one ([decision 0019](../decisions/0019-codex-runs-with-a-home-of-its-own.md), [#168](https://github.com/JPSAUD501/j3-bots/issues/168)). Claude Code bots are not affected. Until Codex offers a way, an operator on Windows who wants their skills kept from bots keeps them out of `%USERPROFILE%\.agents\skills` or uses Claude Code for those bots.
- A built-in provider that a later engine adds, enabled by default, would run as an instance of the engine's own on the operator's setup until the adapter turns it off too. Each engine upgrade checks for one ([Engine: upgrading](engine.md#upgrading-the-engine)).
