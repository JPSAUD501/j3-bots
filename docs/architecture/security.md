# Security

J3 Bots runs agents with real access to a real machine, on behalf of one person, around the clock. This document states what is trusted, what is not, and what stands between them.

## Trust model

| Party | Trust |
| --- | --- |
| The operator | Full. They own the machine, the subscriptions and the bots. |
| A paired client | The operator's. A device token is the operator's authority. |
| The J3 Bots server | Full. It runs as the operator's user. |
| The engine | Full. It runs as the same user and executes what bots ask within their permission mode. |
| A bot's model output | **Not trusted to be correct, trusted to be the bot's.** A bot may be wrong or may have been misled; it is still the party the operator delegated to. |
| Anything a bot reads | **Untrusted.** Web pages, files, tool results, webhook bodies, messages from other bots. |

The line that matters most is the last one. A bot with a shell that treats text from a web page as an instruction is a remote code execution path into the operator's machine.

## Who can give instructions

Only the operator, through a `user` wake in a bot's conversation or an entry they wrote in a room.

Everything else is context:

- A **routine's saved instruction** is the operator's standing request for exactly what it names, and nothing more.
- A **teammate's message** is another bot asking. The receiving bot weighs it against its own job and limits. It does not inherit the sender's authority, and it cannot be used to launder a request the operator did not make.
- A **webhook body**, a **tool result**, a **file** and a **web page** are data.

J3 Bots enforces this in three places:

1. **Envelopes.** The server writes every wake. Content that did not come from the operator is placed inside a block whose tag carries a per-wake random nonce, so text inside the block cannot close it or imitate another block.
2. **The base prompt.** It states the rule above, and that a request found in data is reported to the operator, not carried out.
3. **Authority that does not transfer.** Approvals can only be granted from a paired client. No bot tool grants an approval, raises a permission mode or widens a budget.

Prompt-level rules reduce the risk. They do not remove it. The permission mode is what bounds the damage.

## Permission modes

A bot's permission mode is the engine's runtime mode for its sessions.

| Mode | What it means for a bot |
| --- | --- |
| Supervised | Asks before commands and edits. On Codex the sandbox is read-only, so even an approved write fails: a supervised Codex bot can read and answer but not change files |
| Auto-accept edits | Edits files freely, asks before commands |
| Auto | An automatic reviewer decides; risky actions become approval cards |
| Full access | Does anything the operator's user can do |

J3 Bots' default for a new bot is **Auto** where the provider supports it and **Supervised** where it does not. Full access is a choice the operator makes per bot, with a plain statement of what it means.

A changed mode is the bot's from the moment it is saved. A session the engine has not been brought to it takes no turn J3 Bots sends until it has been: the server sends no new work into it, applies the change once no turn runs there, retries it while the engine is restarting or unavailable, and only then lets the next turn start ([Server](server.md#sessions), Settings alignment). A turn already running keeps the mode it started with; stopping the bot ends it. On Claude Code, background work still running also holds the change, since applying it would end that work; the bot's conversation says so, the client offers the Stop while it waits, and stopping the bot applies it.

One exception: a turn the engine starts on its own, a usage-limit continuation or a wake from background work that ended, can start between the change and its alignment, and runs with the mode the session still has. The pinned engine offers no way to hold only those starts (**Read** at `db51b67`, `UsageLimitRecoveryWorker.ts`). When lowering a bot's mode must take effect at once, stop the bot after the change.

In every mode, the bot's own `j3` tools run without asking: they only reach J3 Bots, which applies its own rules to each call. The engine's and the harness's other tools keep the mode's rules. The Codex behavior is **Verified** on release `4969`; see [Engine](engine.md#behaviors-j3-bots-designs-around).

J3 Bots adds no sandbox. A bot in full access can read the operator's SSH keys, their other bots' folders, and J3 Bots' own database.

## Acting on the operator's behalf

Sending something to another person is not reversible. The base prompt holds bots to these rules regardless of permission mode:

- A message, email or post to anyone but the operator goes out only when the operator asked for that specific send, or a routine's saved instruction names it.
- When in doubt, the bot drafts and asks.
- A declined send is final. The bot does not retry it, reword it or find another route.
- Purchases, deletions, publishing and changes to accounts need the operator's explicit yes in the conversation.

## Running on a machine that matters

The first deployment of J3 Bots is on a host that has SSH access to the rest of its owner's network. That is common for a home server and it changes the stakes: a misled bot on that host can reach every machine the host can.

Recommended for any such host, and set out step by step in [Running on a Raspberry Pi](../operations/running-on-a-pi.md#choose-the-user-it-runs-as):

- Run J3 Bots and its engine as a **dedicated system user** that has no SSH keys, no sudo, and no read access to the operator's home directory.
- Give that user its own provider sign-ins.
- If a bot needs access to something outside its workspace, grant that one thing.

This is a deployment recommendation, not something J3 Bots enforces. See [open question 3](../open-questions.md).

## The engine's credentials

- The engine listens on loopback only.
- J3 Bots' engine token carries `orchestration:operate`, which can start a full-access agent. The engine's own CLI mints it, the server keeps it in `<J3_HOME>/engine/j3/credential.json` (mode 0600, inside the private home), never writes it to a log, and replaces it before it expires. A backup of the home contains it.
- Bots receive no engine credential from J3 Bots. Their sessions get the engine's own per-session MCP token, scoped to their thread, as T3 Code provides to any agent it runs.

## J3 Bots' own surface

- **Client connections** require a device token. Tokens are stored hashed, listed, and revocable. The socket checks the token, or a single-use ticket bought with it, once at the upgrade; each socket belongs to one device, and revoking the device closes its sockets at once. File routes take the same bearer on every request.
- **Pairing codes** carry 50 bits (ten Crockford base32 characters), expire after five minutes and work once. The server compares a presented code with every live code, each in constant time, so how long an attempt takes says nothing of how near it came to one. A code travels only in bodies, never in a path, and reaches no log line: the request logs of the server and of the admin socket record method, path and status, and an answer of the admin socket that `j3-bots pair` cannot read is reported without its body. Failed attempts are limited across all sources, not per address, which would mean nothing behind a proxy, where every attempt comes from the proxy: after five failures in fifteen minutes, pairing is locked for fifteen minutes, and every attempt, the right code included, is answered with the time it opens again. A locked-out attacker gets a handful of guesses per quarter hour against a space of 2^50. The price of a global limit is that anyone who reaches the server can keep pairing locked; the way out is on the host. While pairing is locked, `j3-bots pair` makes no code and says until when, and `j3-bots pair --unlock` lifts the lock, forgets the failures counted towards one and prints a code at once. Both go through the admin socket, so only the service's user on the host can. Codes, failures and the lock are kept in memory, so a restart of the server forgets them. A pairing request is capped at 4 KiB, declared or chunked, and refused with 413 before it counts as an attempt or is decoded.

  The QR code that `j3-bots pair` and Devices show carries the code itself, as the fragment of the server's own address at `/pair` (`<origin>/pair#<code>`): it still expires in five minutes and works once, but anyone who sees the QR code in that window, over a shoulder, on a screen share or in a photo, can pair with it before the operator does. The link's schema (`PairingLink` in `packages/contracts`) admits only a bare `http` or `https` origin as a browser writes it, the path `/pair`, no query or user name, and a fragment that is one code, read as a typed code is: in either case, with dashes between groups. A browser sends no fragment to the server, so the code stays out of the server's request log, any proxy's log and `Referer`. The web client replaces the page's address as it loads, so the code leaves the address bar and the tab's back and forward history, and it drops the link's code when the page is put aside (`pagehide`), so Back does not bring an unused code back into the form from the back/forward cache ([Clients: pairing](clients.md#pairing)). A browser carries a fragment along a redirect, so a sign-in gate in front of the server that sends a phone to an identity provider on another origin hands that provider's page the code; the [Pi guide](../operations/running-on-a-pi.md#serve-it-through-a-container) tells operators to sign in on the phone first or type the code. A pairing link only fills in a client's pairing screen; it never pairs by itself. Every pairing screen shows the origin of the server it pairs with, and a native client already paired with another server must say pairing replaces it, so a link sent to the operator cannot pair their device with someone else's server without their seeing where and pressing Pair. An address taken from a scanned link meets the same transport rule as one typed in: plain HTTP only at a loopback or private IP literal.
- **Plain HTTP** reaches only loopback and private addresses. A configured address must be an IP literal in one of those ranges, or start is refused. The default, `lan`, listens on every IPv4 interface and serves only private addresses, over HTTP and over HTTPS alike. Start refuses it while any of the host's addresses is public, and the server then checks each connection as it accepts it: one that reached an address outside those ranges, such as one that appeared after start, is closed before a byte of it is read. A public address needs a TLS certificate and key, and `host` set to that address ([Server: configuration](server.md#configuration)). On a private network, plain HTTP still lets anyone on that network read a device token in transit. Serving HTTPS, for instance on a Tailscale name, closes that gap.
- **Cross-origin reads** are allowed only to the desktop app's pages (`j3bots://app`, and `j3bots-dev://app` in development): the server answers their preflights for `GET` and `POST` with the headers clients send, never with credentials, since a device token is a bearer header and never a cookie. Every other origin gets no CORS header, so a page elsewhere cannot read an answer ([decision 0012](../decisions/0012-desktop-reaches-the-server-directly.md)). The desktop app accepts a plain-HTTP server only at a loopback or private IP literal or `localhost`, the same ranges the server serves over HTTP, so a typed name never sends a token in clear across the internet.
- **A device token at rest.** A browser keeps it in IndexedDB in the clear: only pages of the server's origin can read it, and anyone who can read the browser's profile. The desktop app keeps it in IndexedDB too, sealed by its main process with the system's key (Electron's `safeStorage`), so the profile's files alone do not give it away. Opening it is a call the app's own page makes, as it uses the token anyway: the protection is against reading the disk, not against code running as the operator's user, which can ask the system's keyring as the app does. On Linux with no keyring the app can use, the token is only obscured, and Settings → This device says so from the stored record until the device is paired again, which issues a new token: sealing the same token again would not help, as the profile's database files can keep the obscured copy after the record is replaced ([Clients: desktop](clients.md#desktop)). A token the system does not open, as while a keyring is locked, and a record of the server whose sealed token is damaged, do not read as a missing pairing, so nothing kept for that pairing is deleted. Uploads from the desktop app go like every other request of its page, held by its Content Security Policy to the named server.
- **The data directory is private, or the server does not start.** Before it opens the database or binds anything, the server checks that the home is a folder owned by its user, which that user can read, write and search (0700) and which no group and no other user can open (no bit of mode 077 set). `j3-bots doctor` reports a home that fails this as a problem, with the `chmod` or `chown` command that fixes it. The home holds the database, the engine's credential and the admin socket.
- **Private state stays in the home.** Every location the server or its engine adapter writes must resolve, symbolic links followed, inside the home and outside the web client's folder: at start, and again before each write ([Server: data](server.md#data)).

  This rule protects against misconfiguration and against a link inside the home that would publish private state. It does not defend against a hostile process running as the same user, and that includes a bot's own shell tools: such a process can already write anywhere the user can. The rule therefore stays a cheap, uniform check and does not grow into a sandbox. A refused write affects only the scope that was tampered with (one bot's workspace or memory, the attachments, the engine's folder), never the server or the other bots.
- **What a bot attaches comes from its workspace.** A file a `say` names is read only inside the bot's workspace, against the folder's real path kept from its first provisioning, before the bot's first turn, never resolved again: a link the bot puts in the folder's place leads nowhere inside it. On Linux the check is made on the opened file, so a folder swapped for a link while it is read is refused too. Elsewhere it compares the opened file with what the path resolves to again, which a folder swapped out and back in between could pass. Either way this containment is a guardrail against a bot attaching the wrong file, not a security boundary: the bot runs commands as the same user as the server, can read any file that user can, and could copy one into its workspace first ([Server: attachments](server.md#attachments)).
- **One server per home.** The server holds an exclusive lock on `<J3_HOME>/server.lock` for as long as it runs. The kernel releases it when the process ends, so a crash never leaves the home held, and two servers that start at once cannot both get it.
- **The admin socket** gives commands on the host a pairing code, a way to lift a lock on pairing, and the server's status. It takes no token: it is a Unix socket (mode 0600) inside the private home, so only the operator's user can open it. Anyone who can act as that user can already read the database. The server removes a socket a stopped server left behind only while it holds the lock, and only once it has seen that the file is a socket and that nothing listens on it.
- **A failing request** fails alone, with a generic error; the cause stays in the server log, and the socket's other subscriptions carry on.
- **Webhook endpoints** authenticate with a 256-bit secret in the path. Before it reads the body or a header it acts on (`Idempotency-Key`, `Content-Length`), the webhook route looks the routine up and compares SHA-256 digests of the given and the stored secret with Node's `timingSafeEqual`: an unknown routine, a wrong secret and a routine with another trigger all get `404`, and the server closes the connection after answering. The route never reads the body of such a call, whatever it declares; bytes the caller already sent are discarded as the connection closes, and a caller that waits for `100 Continue` is never sent one, so it sends no body. That holds for the route on J3 Bots' own listener: a proxy in front of it, such as the container's Caddy, may wait for or buffer the body before it forwards the request. Only for a call that named its webhook are the headers and the body read: up to 64 KiB, and at most ten runs a minute for each routine ([Server: webhooks](server.md#webhooks)). An HMAC signature over the body is not checked: it needs a field in the routine contract that requires one.

  The constant time covers the comparison of the digests, not the whole check: a routine that exists is read from the database and decoded, and an unknown id is not, so timing can tell whether a routine id exists. The `404` already answers that the same way for a wrong secret and an unknown routine, and the id is not the credential. Refused calls are not limited: one costs a lookup and two short digests, and no rate of guessing finds a 256-bit secret, while a limit shared by every caller would let anyone who reaches the server, or a sender still posting to an address an operator replaced, close every webhook.

  The secret travels in the URL, so anything that logs requests can hold it. The server's request log records any path under `/hooks/` as `/hooks/…`, and no trace span is made of such a request. The container proxy this repository ships ([`deploy/container-proxy`](../../deploy/container-proxy/compose.yaml)) keeps no access log and leaves the whole request out of every line it logs: Caddy logs the request with each error it answers, such as a `502` while the server restarts, and a filter on the URI alone still left the path in headers such as `X-Original-URL` and `Referer` (**Verified** on Caddy 2.10.2). Its admin API is off. A platform's own router in front of it, or a tunnel, logs what its own settings say; many keep access logs with paths. A routine's secret changes only when its trigger does: to replace a secret that may have leaked, change the routine to a schedule and back to a webhook, which gives it a new address and makes the old one answer `404`.
- **The bot tool endpoint** listens on `127.0.0.1` only, and takes a request only as the `j3` bridge makes it: with an authority (its `Host`, or the authority of an absolute request target) of `127.0.0.1` and the port the request arrived on, as a URL writes them, declared exactly `application/json`, and with no `Origin`. Any other request to the route gets 403 before its body is read. This keeps out web pages in a browser on the host, which can reach loopback too: a browser sends a page's `POST` with an `Origin`, a page on a name rebound to `127.0.0.1` sends that name as `Host`, and a page may send a JSON body to another origin only after a preflight, which the endpoint never grants. The bridge sends that `Host`, that content type and no `Origin` (**Verified** by running it against the endpoint on Node 26.13.1, the version the server pins; the bridge runs on the server's own Node executable), and its tests go through the check. Any program on the host can still reach the port, so a body is capped at 4 MiB before it is decoded.

  A request names its caller's session, never an argument the model supplies, and the server refuses a session it did not create. A session's engine id is derived from a random 100-bit id, so it cannot be guessed. The tools that act for a turn (`say`, `ask`, `message_bot`, `set_routine`) act only on an open call, which no other request has claimed, that the engine recorded with the same input in that session's running turn ([Server: bot tools](server.md#bot-tools)). So a request that names a session whose turn has no such call open, one that reuses a request id another session's call already stored a result under, and a replay of a request id whose result is stored, for the same session and tool, whatever arguments it now carries, record nothing and wake no one; a replay whose arguments the tool accepts, for a session the server still has, gets the stored result back. A test holds each case.

  The rest is within the operator's trust boundary. The other tools (memory, `list_routines`, `list_teammates`, `create_bot`, `update_bot` and `update_profile`) are not matched to a call, so whoever knows a session's id can use them as that session's bot, as far as that bot may (`create_bot` and `update_bot` only for the primary bot). The id is in the database inside the private home and in the environment the engine gives the harness and the bridge, which only the operator's user can read. Every bot's shell runs as that user, so one bot can use those tools as another. That gives it nothing it lacks already: such a process can change the memory files and the database directly. Two places reach past that user. The server's log can name a session, by J3 Bots' id or by the engine's, and the engine's is computed from J3 Bots'; the installed Linux service normally logs to the systemd journal, which on many distributions the host's administrators and members of groups such as `adm` or `systemd-journal` can read. And when the server stops, its tool port closes before the engine stops the harnesses, so another user who binds the port in that moment receives, and can answer, what a bridge forwards then, its session id included ([Known gaps](#known-gaps)). **Assumed**: the engine and the harnesses show the id nowhere else that other users can read, such as a process's command line.
- **Bot scope.** A bot's tools reach its own conversation, memory and routines, the shared memory, and the rooms it belongs to. Nothing in the tool surface returns another bot's conversation or memory. This is isolation of the product surface, not of the filesystem.

## Push notifications

A phone in the background is reached through a push service: Expo's, for now, which hands each notification to Apple's or Google's ([decision 0014](../decisions/0014-push-goes-through-a-push-sender.md)).

- **What leaves the server.** For each push: the device's push token, a title (the bot's name, or the room's), a body, and the data the app opens (the device's id, the bot's or the room's id, the entry's id), with the delivery's id as its key. With previews off, the default, the body is a fixed sentence such as "Sent you a message", and no text of the entry leaves the server; with previews on, it is the entry's first line, at most 200 characters. Expo also sees the server's address and when it sent. The server sends Expo no credential, with the project's "enhanced security" off: a token a self-hosted server holds would ship to every operator, and protect nothing.
- **A setting changed later only holds a push back.** A push is worded in the transaction that adds its entry, with its preview only if previews were on then, and also without it. Each send reads the settings again, in the transaction that claims it, so a change committed before the claim holds for that send: with previews off by then, it carries the fixed sentence, never the stored preview; with notifications off, the push is dropped unsent. Turning previews on later never sends an earlier entry's text.
- **Push tokens.** A push token is the address a push service gives one installed app: whoever holds it can send that app a notification through the service, so it is stored with the operator's data and never shown to a client, the Devices list included, which shows only whether a device has push on. A device registers only itself, from its own authenticated socket; the token is bounded (printable ASCII, at most 256 characters) and the platform and language must be ones the server knows. A token moves to the device that registers it last. That is no escalation: tokens leave the server only for the push service, so a device can only take a token it already holds, as an app that paired again does. Revoking a device, which signing out does, deletes its registration in the same transaction, and a push command the device sent before is refused from then on rather than answered from its receipt. A send is begun only while the device still has the registration the worker read, so a revocation that lands while the worker is sending other pushes stops that device's push too. Any paired device can revoke another, and so end its pushes; that is no more than revocation already allows.
- **A repeat replaces, not adds.** A send repeated after a crash or a lost reply carries the delivery's id as its key, Expo's `tag` on Android and `collapseId` on iOS, which replace a notification with the same key still shown. One the operator already dismissed is gone, so a repeat can show again. Expo documents that, rarely, a notification reaches Apple or Google more than once or not at all. How a device shows a repeat is **Assumed** until the mobile app is tried on one.
- **What is kept.** A push's words are stored only until the push service takes it; what is left until its receipt is read is the delivery's ids, the generation of the registration it went to and the service's receipt. Of the service itself, the server keeps only when it may next be tried after a request it did not answer. The logs name deliveries and devices, Expo's error codes only when Expo documents them, and a failure only by its tag: never a token, a message Expo sent (which can quote one), a failure's text, or what a push says.

## Desktop updates

The desktop app updates itself from the repository's GitHub releases with electron-updater 6.8.9, unmodified ([Clients: desktop](clients.md#desktop), [Releasing](../operations/releasing.md)). Builds are unsigned for now. The citations below are **Read** in electron-updater 6.8.9 and builder-util-runtime 9.7.0, which it uses, unless marked otherwise.

- **Where an update comes from.** A packaged app asks GitHub over HTTPS for the latest published release, reads its platform's feed file from that release (`latest-linux.yml` on Linux, `latest-mac.yml` on macOS, `latest.yml` on Windows), and, where it installs updates, downloads the file the feed names from the same release (`providers/GitHubProvider.js:158-175`). A draft is never offered; a maintainer publishes each release by hand. An app running a pre-release also takes pre-releases, and one running a release never does (`AppUpdater.js:218`).
- **What is checked.** The download is hashed as it streams and refused unless its SHA-512 is the one the feed gives (builder-util-runtime `httpExecutor.js:457-470`, the refusal at `:431`). A differential download is held to the same check (`differentialDownloader/DifferentialDownloader.js:121`), and so is a file downloaded in an earlier run, before it is reused (`DownloadedUpdateHelper.js:113-125`). **Verified** on Linux: an AppImage at 0.0.1-test, offered 0.0.2-test by a loopback feed whose SHA-512 had been altered, downloaded the file, logged `sha512 checksum mismatch`, kept nothing in its update cache and stayed at 0.0.1-test.
- **What that does not prove.** The feed and the file come from the same release, so the checksum catches a damaged or substituted download, not a malicious release. Whoever can publish a release in the repository (a maintainer, the release workflow, a token with `contents: write`) can ship code to every installed app. A signature is what would tie an update to its publisher, and for now there is none:
  - On Windows, electron-updater checks an update's Authenticode signature against the build's `publisherName` before running it, and skips the check when no `publisherName` is set, as now (`NsisUpdater.js:84-99`).
  - On macOS, the app does not update itself while it is unsigned: it says a newer version is out and links to its release, and the operator downloads it.
  - On Linux, packages carry no signature; the checksum is the whole check for an AppImage. A deb does not update itself: like a Mac build, it links to the release.
- **Installing waits for the operator, and never takes root.** An update installs only when the operator presses "Restart to update", never as the app quits, and never while the page reports a save under way. Only an AppImage and a Windows install install one, each as the operator's user: an AppImage is replaced in place, and the Windows installer runs silently. A deb is never installed by the app. electron-updater would install it with `dpkg -i` as root, through `pkexec` or `sudo` (`LinuxUpdater.js:43-50`, `DebUpdater.js:53-56`), from a file in the operator's own update cache, which any process running as the operator could replace before that step. The app neither downloads nor installs a deb: it says a newer version is out and where to get it.
- **No downgrade.** Only a version newer than the running one is offered (`allowDowngrade` is false, `AppUpdater.js:138`). A broken release is fixed by a newer one, and withdrawing it only stops apps that have not downloaded it yet.
- **What leaves the device.** Each check is a request to GitHub, which sees the device's address. Every update request carries an `x-user-staging-id` header: a random UUID made once and kept in the app's profile (`.updaterId`), so GitHub could tell one installation's checks apart over time (`AppUpdater.js:386-387`, `:502`). The user agent is Electron's default, which names the app and its version (**Assumed**). Nothing about the J3 Bots server, the device's pairing or its conversations goes with them.
- **The page's part.** The page can read the update's status, ask for a check, ask for the restart and report whether a save is under way, through the bridge, decoded with its schemas on both sides and heard only from the app's top frame. It cannot choose the feed, the file or the version.

## Secrets

- J3 Bots never asks the operator to paste a secret into a conversation, and the base prompt tells bots not to either.
- When a bot needs a credential, it uses the engine's secret request, which shows the operator a masked input and gives the value to the command that needs it without placing it in the model's context.
- J3 Bots carries the value from the client to the engine and keeps nothing of it: not in the card, the change log, a command receipt or a log line. The card records only that a value was provided. In code the value travels as a redacted type, so printing it shows nothing.
- Memory files are not a place for secrets. The `remember` tool refuses text that looks like a credential.
- **The provider connection's key** is typed on the host into `j3-bots provider connect`, without echo, or piped on standard input, never on the command line. The command hands it to the running server over the admin socket, and the server to the engine's secret store, as one file holding the base URL and the key together (mode 0600, inside the private home), so a change cut short never pairs one connection's base URL with another's key. Only before the engine starts is it written out to the harnesses: one secret file per instance for the variable each harness's configuration names next to the base URL; `provider connect` restarts the engine for that ([Engine: reaching the models](engine.md#reaching-the-models)). The server keeps no copy and logs nothing of it. It travels only to the endpoint, so the base URL must be `https`, or `http` to this machine only; the command refuses plain `http` to another host. The engine gives the key to the harness process, in its environment; Claude Code reads it from there through its key helper, `printenv` of that variable. That environment reaches the commands a bot runs in its shell, so a bot can read the key. **Verified** for Codex on release `4969`: the shell snapshot Codex wrote under its home (`providers/codex/shell_snapshots/`, inside the private home) held the key after a bot's turn. **Assumed**: that the live environment of a command a bot runs holds it, under Codex, whose shells start from that snapshot, and under Claude Code, where no run looked. Keeping it out of the bots' shells is an open problem.
- **The operator's own provider setup stays out.** The harnesses run with homes of their own, and the engine starts with an allowlist of the server's environment (the system's basics, locale, proxy and certificate variables), so a server started from the operator's shell does not hand bots the operator's harness configuration, sign-ins or keys ([Engine: isolation](engine.md#isolation)).
- **The trust boundary is the operator's user.** A bot's harness runs as the user the server runs as, and the commands it runs inherit the harness environment. So the connection's key, the engine's secret store and every file that user can read, the operator's own sign-ins included, are within reach of a bot that runs a command to look; the allowlist keeps configuration from leaking in by accident, and is not a wall. What is established of the key reaching those commands is in [Secrets](#secrets): Codex's shell snapshot holding it is **Verified**, a command's live environment holding it, under either harness, is **Assumed**.

## What is logged

- Conversations, rooms and memory are the operator's data, stored on their disk, in the clear.
- Server logs record wakes, dispatches and outcomes with identifiers, not message text.
- No telemetry leaves the machine by default.

## Known gaps

- No isolation between bots at the filesystem level, and none between a bot and the operator's user.
- Whoever can read the service's log, or binds the tool port in the moment the server stops while a bridge forwards a call, can learn a session's id and, until the server retires that session, use the bot tools that do not act for a turn as that session's bot; the one who binds the port can also answer that call ([J3 Bots' own surface](#j3-bots-own-surface)).
- No protection against a compromised paired device beyond revocation.
- On Linux without a keyring the desktop app can use, its device token is stored obscured, not encrypted. The app says so rather than refuse to pair, and the token stays obscured until the device is paired again.
- Desktop builds are unsigned: an update is trusted as far as the GitHub release it comes from, and Windows does not check who published it ([Desktop updates](#desktop-updates)).
- Push notifications pass through Expo's push service and Apple's or Google's, which see what a push says; previews are opt-in for that reason. A push cannot be withdrawn: it stays on the phone after the operator answers elsewhere. A browser notification never leaves the device, but it can show on a screen others see, so the same setting holds for it.
- The automatic reviewer in Auto mode is the provider's, and its judgment is not J3 Bots' to guarantee.
