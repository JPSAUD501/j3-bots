# Security

J3 Bots runs agents with real access to a real machine, on behalf of one person, around the clock. This document states what is trusted, what is not, and what stands between them.

## Trust model

| Party | Trust |
| --- | --- |
| The operator | Full. They own the machine, the subscriptions and the bots. |
| A paired client | The operator's. A device token is the operator's authority. |
| The J3 Bots server | Full. It runs as the operator's user. |
| The engine | Full. It runs as the same user and executes what bots ask within their permission mode. |
| Any process of the server's user, a bot's shell and its harness included | Full, as that user is. It can reach the admin channel, exactly as `j3-bots pair` does: make a pairing code (`/pairing`), pair a device without one (`/local-device`) and stop the server (`/shutdown`). It can read the database too, and the vault's file, though not what the file seals ([The vault](#the-vault)). |
| A bot's model output | **Not trusted to be correct, trusted to be the bot's.** A bot may be wrong or may have been misled; it is still the party the operator delegated to. |
| Anything a bot reads | **Untrusted.** Web pages, files, tool results, webhook bodies, messages from other bots. |
| A connector's server | **Untrusted.** What it says its tools do, what they take and what they return is text a bot reads. It sees what bots send it, and acts in the operator's account there. |

The line that matters most is the last one. A bot with a shell that treats text from a web page as an instruction is a remote code execution path into the operator's machine.

## Who can give instructions

Only the operator, through a `user` wake in a bot's conversation or an entry they wrote in a room.

Everything else is context:

- A **routine's saved instruction** is the operator's standing request for exactly what it names, and nothing more.
- A **teammate's message** is another bot asking. The receiving bot weighs it against its own job and limits. It does not inherit the sender's authority, and it cannot be used to launder a request the operator did not make.
- A **webhook body**, a **tool result**, a **file** and a **web page** are data.
- A **template** is data until the operator creates a bot from it, after a preview of everything it holds: then its job, its skills and its routines' instructions are that bot's own, and are written into nothing else. Its routines start paused, and its permission mode is never above the default unless the operator picks it. From then on the new bot is a teammate like any other: its name, title and job reach the other bots through `list_teammates`, as data, never as instructions, and its first turn works from its job as written ([decision 0023](../decisions/0023-a-bot-template-is-a-file.md)). Going the other way, sharing one sends its job, skills and routines' instructions as written, whatever they hold; the share screen shows them in full first.

J3 Bots enforces this in three places:

1. **Envelopes.** The server writes every wake. Content that did not come from the operator is placed inside a block whose tag carries a per-wake random nonce, so text inside the block cannot close it or imitate another block.
2. **The base prompt.** It states the rule above, and that a request found in data is reported to the operator, not carried out.
3. **Authority that does not transfer.** Approvals can only be granted from a paired client. No bot tool grants an approval, raises a permission mode or widens a budget.

Prompt-level rules reduce the risk. They do not remove it. The permission mode is what bounds the damage.

## Permission modes

A bot's permission mode is the engine's runtime mode for its sessions.

| Mode | What it means for a bot |
| --- | --- |
| Supervised | Asks before commands and edits. On Codex the sandbox is read-only, so even an approved write fails: a supervised Codex bot can read and answer but not change files |
| Auto-accept edits | Edits files freely, asks before commands |
| Auto | An automatic reviewer decides; risky actions become approval cards |
| Full access | Does anything the operator's user can do |

J3 Bots' default for a new bot is **Auto** where the provider supports it and **Supervised** where it does not. Full access is a choice the operator makes per bot, with a plain statement of what it means.

A changed mode is the bot's from the moment it is saved. A session the engine has not been brought to it takes no turn J3 Bots sends until it has been: the server sends no new work into it, applies the change once no turn runs there, retries it while the engine is restarting or unavailable, and only then lets the next turn start ([Server](server.md#sessions), Settings alignment). A turn already running keeps the mode it started with; stopping the bot ends it. On Claude Code, background work still running also holds the change, since applying it would end that work; the bot's conversation says so, the client offers the Stop while it waits, and stopping the bot applies it.

One exception: a turn the engine starts on its own, a usage-limit continuation or a wake from background work that ended, can start between the change and its alignment, and runs with the mode the session still has. The pinned engine offers no way to hold only those starts (**Read** at `db51b67`, `UsageLimitRecoveryWorker.ts`). When lowering a bot's mode must take effect at once, stop the bot after the change.

In every mode, the bot's own `j3` tools run without asking: they only reach J3 Bots, which applies its own rules to each call. A connector's tools reach the bot through the same bridge and are not pre-approved: they follow the bot's permission mode like any other harness tool ([decision 0027](../decisions/0027-connector-tools-reach-a-bot-through-the-j3-bridge.md), [Connectors](#connectors)). The engine's and the harness's other tools keep the mode's rules. The Codex behavior is **Verified** on release `4969`; see [Engine](engine.md#behaviors-j3-bots-designs-around).

J3 Bots adds no sandbox. A bot in full access can read the operator's SSH keys, their other bots' folders, and J3 Bots' own database.

## Acting on the operator's behalf

Sending something to another person is not reversible. The base prompt holds bots to these rules regardless of permission mode:

- A message, email or post to anyone but the operator goes out only when the operator asked for that specific send, or a routine's saved instruction names it.
- When in doubt, the bot drafts and asks.
- A declined send is final. The bot does not retry it, reword it or find another route.
- Purchases, deletions, publishing and changes to accounts need the operator's explicit yes in the conversation.

## The browser

A bot whose browser switch is on can open pages in the engine's browser on the host and act in them ([Concepts](../product/concepts.md#controls)). That browser keeps one profile, shared by every bot with the switch on, and the operator signs in to sites in it. So each of those bots acts on those sites with the operator's sessions: what it can do there is what the operator's account can do, and the site cannot tell the bot from the operator. The rules in [Acting on the operator's behalf](#acting-on-the-operators-behalf) apply to what a bot does in a page as to any other send.

- The switch is off for every bot until the operator turns it on, and the engine's browser access is off engine-wide besides it ([Engine: the browser](engine.md#the-browser)).
- Turning it off takes the browser from the bot at once: its work is stopped, and every thread of its project, a delegated task's or another agent's included, loses it before it runs again.
- A page is untrusted content, like any tool output: what a page says is never the operator's instruction.
- **Sign out of all sites**, in Settings, deletes the engine's `default` profile, the one bots use: every session in it ends, for every bot.
- The profile holds live session cookies, and a backup of the data directory holds them with it ([Back up](../operations/operating.md#back-up)).

## Running on a machine that matters

The first deployment of J3 Bots is on a host that has SSH access to the rest of its owner's network. That is common for a home server and it changes the stakes: a misled bot on that host can reach every machine the host can.

Recommended for any such host, and set out step by step in [Installing J3 Bots](../operations/install.md#choose-the-user-it-runs-as):

- Run J3 Bots and its engine as a **dedicated system user** that has no SSH keys, is in no group that can become root, and has no read access to the operator's home directory.
- Give that user its own provider sign-ins.
- If a bot needs access to something outside its workspace, grant that one thing.

This is a deployment recommendation, not something J3 Bots enforces. `j3-bots doctor` warns when the user it runs as keeps an SSH private key directly in `~/.ssh`, or is in a group that can become root, and gives the steps to a dedicated user. A key is a regular file whose first line is a private key's header; up to the first 64 bytes of each regular file are read, and no symbolic link is followed, so neither a linked file in `~/.ssh` nor a `~/.ssh` that is itself a link is looked into. The groups are `sudo`, `wheel` and `admin`, which reach root through sudo, and `docker`, `lxd` and `incus`, whose members can start a container that mounts the host's root (`docker run -v /:/host`). They are read from `/etc/group` only, so a group from a directory service, such as LDAP through sssd, is not seen. It does not look for keys elsewhere, nor at other ways the user can reach other machines, such as an SSH agent or stored cloud credentials. See [open question 3](../open-questions.md).

## The engine's credentials

- The engine listens on loopback only.
- J3 Bots' engine token carries `orchestration:operate`, which can start a full-access agent, and `settings:write`, which can change any of the engine's settings; the server writes only projects' overrides with it, for each bot's browser switch. The engine's own CLI mints it, the server keeps it in `<J3_HOME>/engine/j3/credential.json` (mode 0600, inside the private home), never writes it to a log, and replaces it before it expires. A backup of the home contains it.
- The token also carries `preview:operate`, without which the engine drops what a person does in a tab. Whoever holds the token can open a viewer on any tab of the engine's browser, take it from the bot that drives it, and click, type, go to an address and answer its dialogs, as that browser, with its sign-ins. Any process of the server's user can read the file, a bot's shell included ([Trust model](#trust-model)), so a misled bot could drive another bot's tabs that way. That adds little to what such a process already reaches: `orchestration:operate`, the database and the admin channel.
- When the engine starts with a stored token that lacks a scope or is due for renewal, the adapter mints a new one and revokes every older session J3 Bots minted (`t3 auth session revoke`, matched by the label it mints with). So the token an earlier J3 Bots minted without `preview:operate` or `settings:write` stops working at once. A token replaced while the engine runs, on renewal or after the engine refused it, is not revoked, because revoking it could cut connections that still use it: it expires within two days, or the engine already refuses it.
- Bots receive no engine credential from J3 Bots. Their sessions get the engine's own per-session MCP token, scoped to their thread, as T3 Code provides to any agent it runs.

## J3 Bots' own surface

- **Client connections** require a device token. Tokens are stored hashed, listed, and revocable. The socket checks the token, or a single-use ticket bought with it, once at the upgrade; each socket belongs to one device, and revoking the device closes its sockets at once. File routes take the same bearer on every request.
- **Pairing codes** carry 50 bits (ten Crockford base32 characters), expire after five minutes and work once. The server compares a presented code with every live code, each in constant time, so how long an attempt takes says nothing of how near it came to one. A code travels only in bodies, never in a path, and reaches no log line: the request logs of the server and of the admin socket record method, path and status, and an answer of the admin socket that `j3-bots pair` cannot read is reported without its body. Failed attempts are limited across all sources, not per address, which would mean nothing behind a proxy, where every attempt comes from the proxy: after five failures in fifteen minutes, pairing is locked for fifteen minutes, and every attempt, the right code included, is answered with the time it opens again. A locked-out attacker gets a handful of guesses per quarter hour against a space of 2^50. The price of a global limit is that anyone who reaches the server can keep pairing locked. While pairing is locked, `j3-bots pair` makes no code and says until when, and `j3-bots pair --unlock` lifts the lock, forgets the failures counted towards one and prints a code at once. Against someone who keeps sending wrong codes, that only opens a window until the next five failures; the lasting answer is to stop exposing pairing to them, `POST /api/pair` as well as the `/pair` page, as [Reaching J3 Bots from elsewhere](../operations/exposing.md#who-can-reach-it) describes. A pairing screen that was answered with a lockout keeps its Pair button, so a code made after an unlock can be used at once. `j3-bots pair` and `j3-bots pair --unlock` go through the admin socket, so only the service's user on the host can run them, and the desktop app's "Pair a phone" and its unlock go through its admin pipe, which only the app holds. A bot's shell runs as the service's user too, so a bot can make a code or lift the lock, as the trust boundary below says. Codes, failures and the lock are kept in memory, so a restart of the server forgets them. A pairing request is capped at 4 KiB, declared or chunked, and refused with 413 before it counts as an attempt or is decoded.

  The QR code that `j3-bots pair` and Devices show carries the code itself, as the fragment of the server's own address at `/pair` (`<origin>/pair#<code>`): it still expires in five minutes and works once, but anyone who sees the QR code in that window, over a shoulder, on a screen share or in a photo, can pair with it before the operator does. The link's schema (`PairingLink` in `packages/contracts`) admits only a bare `http` or `https` origin as a browser writes it, the path `/pair`, no query or user name, and a fragment that is one code, read as a typed code is: in either case, with dashes between groups. A browser sends no fragment to the server, so the code stays out of the server's request log, any proxy's log and `Referer`. The web client replaces the page's address as it loads, so the code leaves the address bar and the tab's back and forward history, and it drops the link's code when the page is put aside (`pagehide`), so Back does not bring an unused code back into the form from the back/forward cache ([Clients: pairing](clients.md#pairing)). A browser carries a fragment along a redirect, so a sign-in gate in front of the server that sends a phone to an identity provider on another origin hands that provider's page the code; [Reaching J3 Bots from elsewhere](../operations/exposing.md#a-sign-in-gate) tells operators to sign in on the phone first or type the code. A pairing link only fills in a client's pairing screen; it never pairs by itself. Every pairing screen shows the origin of the server it pairs with, and a native client already paired with another server must say pairing replaces it, so a link sent to the operator cannot pair their device with someone else's server without their seeing where and pressing Pair. An address taken from a scanned link meets the same transport rule as one typed in: plain HTTP only at a loopback or private IP literal. The desktop app's own pairing link, `j3bots://pair?server=…&code=…`, which any web page can ask the system to open, follows the same rules and one more: it never changes the server the app keeps. Before a server is named it only fills in the server address screen, for the operator to check and continue; after, a link for another server is refused ([Clients: desktop](clients.md#desktop)).
- **Plain HTTP** reaches only loopback and private addresses. A configured address must be an IP literal in one of those ranges, or start is refused. The default, `lan`, listens on every IPv4 interface and serves only private addresses, over HTTP and over HTTPS alike. Start refuses it while any of the host's addresses is public, and the server then checks each new connection's destination address as it accepts it: one that reached an address outside those ranges is closed before a byte of it is read. A public address that appears after start is refused that way: the listener stays bound on every interface, the new address included, so the check, not the bind, is what keeps it out. A public address needs a TLS certificate and key, and `host` set to that address ([Server: configuration](server.md#configuration)). On a private network, plain HTTP still lets anyone on that network read a device token in transit. Serving HTTPS, for instance on a Tailscale name, closes that gap. The desktop app's own server listens on `127.0.0.1` unless the operator turns on "Use from your phone", and then on `lan` under the same rules; the app never starts it on `lan` while an interface has a public address, gives a phone only the server's own private interface addresses, never its `publicOrigin`, and Settings says, beside the switch, that the connection is not encrypted, so only a trusted network will do ([Clients: desktop](clients.md#desktop)). A phone pairs with it as with any server, with a code the operator makes at the computer: the pairing link carries the code, never a device token.
- **Cross-origin reads** are allowed only to the desktop app's pages (`j3bots://app`, and `j3bots-dev://app` in development): the server answers their preflights for `GET` and `POST` with the headers clients send, never with credentials, since a device token is a bearer header and never a cookie. Every other origin gets no CORS header, so a page elsewhere cannot read an answer ([decision 0012](../decisions/0012-desktop-reaches-the-server-directly.md)). The desktop app accepts a plain-HTTP server only at a loopback or private IP literal or `localhost`, the same ranges the server serves over HTTP, so a typed name never sends a token in clear across the internet.
- **Web pages in a browser** can send requests to any address the browser reaches, loopback included, even where they cannot read the answers. Two rules keep them from doing harm with requests that need no token:
  - `POST /api/pair` takes `Content-Type: application/json` only. Any other content type is answered `415` before the body is read, and the request does not count towards the pairing lock. A page may send `text/plain`, a form or no type at all to another origin without asking first, but JSON needs a preflight, which the server answers for no web page, so a page cannot lock pairing by posting wrong codes. Every client sends JSON.
  - On a plain-HTTP listener, a request's `Host` must be `localhost`, an IP address, or the name in `publicOrigin`, at any port. Anything else is answered `403` before routing, the socket's upgrade included, with one plain-text line saying which addresses the server answers. A page on the refused name can read that line, so it names no address of the server's own; the server's log does, once for each refused name and for at most 16 names, with what would serve that name (`publicOrigin` for a proxy or tunnel in front, an address for anyone else). This stops DNS rebinding: a page on a name its owner points at this machine's address is same-origin with the server under that name, so it could read what the server answers without a token (`/api/server`, the web client) and try pairing codes and webhook addresses at will, and its browser sends that name as `Host`. Nobody can rebind an IP address, nor `localhost`, which browsers resolve to loopback themselves. The port is not compared: the name is what a rebinding page cannot change, and a proxy on another port, Docker's published ports and the Android emulator's alias `10.0.2.2` all reach the server other than at the address and port it bound. So over plain HTTP the server answers a browser only at an address, at `localhost` or at its `publicOrigin`, never at another name such as `<machine>.local`. The desktop's server on `lan` is held to the same rule: a phone opens it at the private address Settings shows. Over HTTPS `Host` is not checked: the browser refuses a name the certificate does not cover, and a proxy in front may send any name.
- **A device token at rest.** A browser keeps it in IndexedDB in the clear: only pages of the server's origin can read it, and anyone who can read the browser's profile. The desktop app keeps it in IndexedDB too, sealed by its main process with the system's key (Electron's `safeStorage`), so the profile's files alone do not give it away. Opening it is a call the app's own page makes, as it uses the token anyway: the protection is against reading the disk, not against code running as the operator's user, which can ask the system's keyring as the app does. On Linux with no keyring the app can use, the token is only obscured, and Settings → This device says so from the stored record until the device is paired again, which issues a new token: sealing the same token again would not help, as the profile's database files can keep the obscured copy after the record is replaced ([Clients: desktop](clients.md#desktop)). A token the system does not open, as while a keyring is locked, and a record of the server whose sealed token is damaged, do not read as a missing pairing, so nothing kept for that pairing is deleted. Uploads from the desktop app go like every other request of its page, held by its Content Security Policy to the named server.
- **The data directory is private, or the server does not start.** Before it opens the database or binds anything, the server checks that the home is a folder owned by its user, which that user can read, write and search (0700) and which no group and no other user can open (no bit of mode 077 set). `j3-bots doctor` reports a home that fails this as a problem, with the `chmod` or `chown` command that fixes it. The home holds the database, the engine's credential and the admin socket.

  On Windows a mode means nothing: who may open a folder is its access control list and its owner. There the home is private when it is owned by the user, SYSTEM or the Administrators group, no rule lets any other account open it, a rule naming the user gives it Modify on the folder, and no rule denies that to the user or one of its groups. SYSTEM and the Administrators are let in because Windows gives them the user's profile, where the home lives, and an administrator can take any file whatever its list says: shutting them out keeps no one out and breaks the profile's backups. The server creates a missing home with its list in place (inheritance off; full control for the user, SYSTEM and the Administrators, passed on to everything inside), so nothing can be put in it before it is private, and checks an existing one at every start. It reads the list with Windows PowerShell's `Get-Acl`, by security identifier, never by account name, which `icacls` prints in the system's language. A home that fails is refused with the `icacls` command that repairs it, for PowerShell: it turns inheritance off, removes the rules that deny the user, SYSTEM or the Administrators, which granting does not replace, grants the three full control and removes every other account, with each argument in single quotes, so a path holding `$` or `%` is taken as it is written. One whose list cannot be read is refused too. The desktop app judges its own server's home with the same code before it starts a server there, and creates a missing one the same way, so it never starts a server that then refuses its home (**Verified** on Windows Server 2025 in CI: a home created this way is judged private, and one opened to the Users group is refused until the repair command runs. **Verified** on Windows 11 x64 with the packaged app: "Use this computer" created the home with inheritance off and full control for the user, SYSTEM and the Administrators only; once the Users group was given read access, the app refused to start the server, saying other users could open the home and giving the `icacls` command, and once the list was repaired, "Try again" started it. **Verified** on Windows Server 2025 in CI: the repair command, run in PowerShell, makes private a folder whose name holds a quote, `%TEMP%`, `$HOME`, `&` and `^`, and one that denies the user writing).
- **Private state stays in the home.** Every location the server or its engine adapter writes must resolve, symbolic links followed, inside the home and outside the web client's folder: at start, and again before each write ([Server: data](server.md#data)).

  This rule protects against misconfiguration and against a link inside the home that would publish private state. It does not defend against a hostile process running as the same user, and that includes a bot's own shell tools: such a process can already write anywhere the user can. The rule therefore stays a cheap, uniform check and does not grow into a sandbox. A refused write affects only the scope that was tampered with (one bot's workspace or memory, the attachments, the engine's folder), never the server or the other bots.
- **What a bot attaches comes from its workspace.** A file a `say` names is read only inside the bot's workspace, against the folder's real path kept from its first provisioning, before the bot's first turn, never resolved again: a link the bot puts in the folder's place leads nowhere inside it. On Linux the check is made on the opened file, so a folder swapped for a link while it is read is refused too. Elsewhere it compares the opened file with what the path resolves to again, which a folder swapped out and back in between could pass. Either way this containment is a guardrail against a bot attaching the wrong file, not a security boundary: the bot runs commands as the same user as the server, can read any file that user can, and could copy one into its workspace first ([Server: attachments](server.md#attachments)).
- **One server per home.** The server holds an exclusive lock on `<J3_HOME>/server.lock` for as long as it runs. The kernel releases it when the process ends, so a crash never leaves the home held, and two servers that start at once cannot both get it.
- **The admin channel** gives commands on the host a pairing code, a way to lift a lock on pairing, the server's status and a provider connection, and gives the desktop app that runs its own server a device and a way to stop it. It takes no token, because only the server's own user reaches it, two ways ([Server: the admin channel](server.md#the-admin-channel)). The admin socket is a Unix socket inside the private home, created with no access for group or others: the server narrows its umask for the call that binds it, so the socket never has a looser mode, not even until a `chmod`. A test holds that another user of the machine is refused it (`EACCES`), and one that the socket is closed to others even under a umask of 0. Just before the bind the server checks that the home is private and notes which folder it is, and checks again once the socket is served: a home moved, replaced or opened in between stops the start. The server removes a socket a stopped server left behind only while it holds the lock, and only once it has seen that the file is a socket and that nothing listens on it. On Windows there is no admin socket, since Node would make its path a named pipe that other users could open (**Assumed**). With `--admin-fd`, the same routes are served on a pipe the server inherited from the process that started it. Only that process holds the other end, and the server's end can never be opened by name: it is a socket pair on Linux and macOS, and on Windows a named pipe of a single instance, which the parent opens itself before the child starts (**Read** in libuv). The server's own children do not inherit it (**Verified** on Linux). The start fails on a TCP socket, listening or connected, so the channel never travels over TCP, and, on Linux and macOS, on anything that is not a socket, such as a FIFO. Anyone who can act as the server's user can reach the channel, and can already read the database: every bot's shell can make a pairing code or a device this way, or stop the server, as the trust model above says.
- **The local desktop gets its device through the admin channel, never over TCP.** When the desktop app runs its own server, it asks that server for a device on the admin channel (`POST /local-device`) instead of pairing with a code: an ordinary device, listed and revocable like any other, which can name the device it replaces, revoked in the same transaction. No code is made, none crosses the network, and the pairing lockout neither applies to it nor is lifted for it. The route exists on the admin channel only; the client listener answers 404 to it, which a test holds. The app never asks for a new device by itself after its device was revoked: a revoked desktop shows that it was signed out, and only the operator's choice to sign in again asks for one ([decision 0020](../decisions/0020-the-local-desktop-gets-its-device-through-the-admin-channel.md)).
- **A failing request** fails alone, with a generic error; the cause stays in the server log, and the socket's other subscriptions carry on.
- **Webhook endpoints** authenticate with a 256-bit secret in the path. Before it reads the body or a header it acts on (`Idempotency-Key`, `Content-Length`), the webhook route looks the routine up and compares SHA-256 digests of the given and the stored secret with Node's `timingSafeEqual`: an unknown routine, a wrong secret and a routine with another trigger all get `404`, and the server closes the connection after answering. The route never reads the body of such a call, whatever it declares; bytes the caller already sent are discarded as the connection closes, and a caller that waits for `100 Continue` is never sent one, so it sends no body. That holds for the route on J3 Bots' own listener: a proxy in front of it, such as the container's Caddy, may wait for or buffer the body before it forwards the request. Only for a call that named its webhook are the headers and the body read: up to 64 KiB, and at most ten runs a minute for each routine ([Server: webhooks](server.md#webhooks)). An HMAC signature over the body is not checked: it needs a field in the routine contract that requires one.

  The constant time covers the comparison of the digests, not the whole check: a routine that exists is read from the database and decoded, and an unknown id is not, so timing can tell whether a routine id exists. The `404` already answers that the same way for a wrong secret and an unknown routine, and the id is not the credential. Refused calls are not limited: one costs a lookup and two short digests, and no rate of guessing finds a 256-bit secret, while a limit shared by every caller would let anyone who reaches the server, or a sender still posting to an address an operator replaced, close every webhook.

  The secret travels in the URL, so anything that logs requests can hold it. The server's request log records any path under `/hooks/` as `/hooks/…`, and no trace span is made of such a request. The container proxy this repository ships ([`deploy/container-proxy`](../../deploy/container-proxy/compose.yaml)) keeps no access log and leaves the whole request out of every line it logs: Caddy logs the request with each error it answers, such as a `502` while the server restarts, and a filter on the URI alone still left the path in headers such as `X-Original-URL` and `Referer` (**Verified** on Caddy 2.10.2). Its admin API is off. A platform's own router in front of it, or a tunnel, logs what its own settings say; many keep access logs with paths. A routine's secret changes only when its trigger does: to replace a secret that may have leaked, change the routine to a schedule and back to a webhook, which gives it a new address and makes the old one answer `404`.
- **The bot tool endpoint** listens on `127.0.0.1` only, and takes a request only as the `j3` bridge makes it: with an authority (its `Host`, or the authority of an absolute request target) of `127.0.0.1` and the port the request arrived on, as a URL writes them, declared exactly `application/json`, and with no `Origin`. Any other request to the route gets 403 before its body is read. This keeps out web pages in a browser on the host, which can reach loopback too: a browser sends a page's `POST` with an `Origin`, a page on a name rebound to `127.0.0.1` sends that name as `Host`, and a page may send a JSON body to another origin only after a preflight, which the endpoint never grants. The bridge sends that `Host`, that content type and no `Origin` (**Verified** by running it against the endpoint on Node 26.13.1, the version the server pins; the bridge runs on the server's own Node executable), and its tests go through the check. Any program on the host can still reach the port, so a body is capped at 4 MiB before it is decoded.

  A request names its caller's session, never an argument the model supplies, and the server refuses a session it did not create. A session's engine id is derived from a random 100-bit id, so it cannot be guessed. The tools that act for a turn (`say`, `ask`, `message_bot`, `set_routine`) act only on an open call, which no other request has claimed, that the engine recorded with the same input in that session's running turn ([Server: bot tools](server.md#bot-tools)). So a request that names a session whose turn has no such call open, one that reuses a request id another session's call already stored a result under, and a replay of a request id whose result is stored, for the same session and tool, whatever arguments it now carries, record nothing and wake no one; a replay whose arguments the tool accepts, for a session the server still has, gets the stored result back. A test holds each case.

  The rest is within the operator's trust boundary. The other tools (memory, `list_routines`, `list_teammates`, `create_bot`, `update_bot` and `update_profile`) are not matched to a call, so whoever knows a session's id can use them as that session's bot, as far as that bot may (`create_bot` and `update_bot` only for the primary bot). The id is in the database inside the private home and in the environment the engine gives the harness and the bridge, which only the operator's user can read. Every bot's shell runs as that user, so one bot can use those tools as another. That gives it nothing it lacks already: such a process can change the memory files and the database directly. Two places reach past that user. The server's log can name a session, by J3 Bots' id or by the engine's, and the engine's is computed from J3 Bots'; the installed Linux service normally logs to the systemd journal, which on many distributions the host's administrators and members of groups such as `adm` or `systemd-journal` can read. And when the server stops, its tool port closes before the engine stops the harnesses, so another user who binds the port in that moment receives, and can answer, what a bridge forwards then, its session id included ([Known gaps](#known-gaps)). **Assumed**: the engine and the harnesses show the id nowhere else that other users can read, such as a process's command line.
- **Bot scope.** A bot's tools reach its own conversation, memory and routines, the shared memory, and the rooms it belongs to. Nothing in the tool surface returns another bot's conversation or memory. This is isolation of the product surface, not of the filesystem.

## Push notifications

A phone in the background is reached through a push service: Expo's, for now, which hands each notification to Apple's or Google's ([decision 0014](../decisions/0014-push-goes-through-a-push-sender.md)).

- **What a client's update may do.** It installs only the feed's verified release, verified again as it downloads. It runs as the service's user, in a transient unit with `NoNewPrivileges`, and gains nothing that user does not have ([Server: updating from a client](server.md#updating-from-a-client)). The server logs the versions, the device that asked and how it ended, never a token.
- **What leaves the server.** For each push: the device's push token, a title (the bot's name, or the room's), a body, and the data the app opens (the device's id, the bot's or the room's id, the entry's id), with the delivery's id as its key; to Android, also the channel it shows in, which names the kind of entry (a message, a question, an approval, a credential request or an urgent handoff), as the fixed sentence already does. With previews off, the default, the body is a fixed sentence such as "Sent you a message", and no text of the entry leaves the server; with previews on, it is the entry's first line, at most 200 characters. Expo also sees the server's address and when it sent. The server sends Expo no credential, with the project's "enhanced security" off: a token a self-hosted server holds would ship to every operator, and protect nothing.
- **A setting changed later only holds a push back.** A push is worded in the transaction that adds its entry, with its preview only if previews were on then, and also without it. Each send reads the settings again, in the transaction that claims it, so a change committed before the claim holds for that send: with previews off by then, it carries the fixed sentence, never the stored preview; with notifications off, the push is dropped unsent. Turning previews on later never sends an earlier entry's text.
- **Push tokens.** A push token is the address a push service gives one installed app: whoever holds it can send that app a notification through the service, so it is stored with the operator's data and never shown to a client, the Devices list included, which shows only whether a device has push on. A device registers only itself, from its own authenticated socket; the token is bounded (printable ASCII, at most 256 characters) and the platform and language must be ones the server knows. A token moves to the device that registers it last. That is no escalation: tokens leave the server only for the push service, so a device can only take a token it already holds, as an app that paired again does. Revoking a device, which signing out does, deletes its registration in the same transaction, and a push command the device sent before is refused from then on rather than answered from its receipt. A send is begun only while the device still has the registration the worker read, so a revocation that lands while the worker is sending other pushes stops that device's push too. Any paired device can revoke another, and so end its pushes; that is no more than revocation already allows.
- **A phone that leaves a server unconfirmed.** A sign-out the server never confirmed, as offline, leaves the device listed there with its registration, so that server goes on pushing to its token. The phone holds an Expo token of its own for each pairing, under a device id made from the pairing's, so the token a new pairing registers is never one an earlier server holds, and the token Expo moves to a new device token by itself is one no server holds ([Clients](clients.md#mobile)). Leaving a pairing also has the push service forget the device's token, after which Expo answers the old pairing's token `DeviceNotRegistered`. That still does not hold in two cases (**Assumed**, both): on Android, when deleting the token fails, as offline, the old device token stays valid; on iOS, Apple usually gives the same device token again after the app unregisters and registers, so the old token keeps reaching the phone. That server's pushes then show the name of a bot or room and, with its previews on, their first line; a tap on one opens nothing, since it names a pairing the phone no longer follows. Revoking the phone from that server's Devices ends them.
- **A repeat replaces, not adds.** A send repeated after a crash or a lost reply carries the delivery's id as its key, Expo's `tag` on Android and `collapseId` on iOS, which replace a notification with the same key still shown. One the operator already dismissed is gone, so a repeat can show again. Expo documents that, rarely, a notification reaches Apple or Google more than once or not at all. How a device shows a repeat is **Assumed** until the mobile app is tried on one.
- **What is kept.** A push's words are stored only until the push service takes it; what is left until its receipt is read is the delivery's ids, the generation of the registration it went to and the service's receipt. Of the service itself, the server keeps only when it may next be tried after a request it did not answer. The logs name deliveries and devices, Expo's error codes only when Expo documents them, and a failure only by its tag: never a token, a message Expo sent (which can quote one), a failure's text, or what a push says.

## Release signing

Every file a release publishes is listed in its `SHA256SUMS`, and `SHA256SUMS.sig` is an Ed25519 signature over it ([decision 0031](../decisions/0031-a-release-is-signed-and-a-nightly-is-a-pre-release-of-the-next-patch.md), [Releasing: what verifies a release](../operations/releasing.md#what-verifies-a-release)).

- **What it proves.** A file whose digest is in a `SHA256SUMS` that a committed key signed is a file the release workflow built and listed. It ties a download to the project's key, not only to the place it came from. So whoever can change a file on a release, or sit between GitHub and the machine, can't make it pass. Unlike the feed's checksum, this holds even for someone who can publish a release.
- **Who checks.** `install.sh` checks with OpenSSL 3 and refuses without it, never falling back to the digest alone. It checks the signature before it reads a digest. A mirror's release is checked the same way ([Updates: a mirror](#updates)). The server and the apps check the same file before they install an update ([Updates](#updates)).
- **Where the key is.** The private key is one secret of the `release-signing` environment, read only by the `sign` job, which runs nothing from the repository or the build. The environment admits `v*` tags, which only admins may create, move or delete (a ruleset that gives GitHub Actions no bypass), and the branch `main`, from which the nightly is built. A nightly's tag is its version with no `v`, so it matches neither rule. Nightly tags are unprotected: the workflow token, any workflow on any branch, or anyone with write access can create or delete one. That opens no key, and a nightly's integrity rests on its signature alone, since a nightly or release someone fakes isn't signed by a committed key and every verifier refuses it. The owner keeps an offline backup. The public keys are committed in `release-keys/`, and `install.sh` and `RELEASE_KEYS` in `packages/release/src/keys.ts` carry copies that a test holds equal to them ([Releasing: the signing key](../operations/releasing.md#the-signing-key)).
- **Which keys `sign` accepts.** Before it hands a signature on, `sign` checks it with the public keys of the commit it builds. So a commit that adds a key to `release-keys/` passes that check: it catches a wrong secret, not a wrong commit, and the review of changes to `main` is what keeps a key out. A leaked key is replaced by one release signed with it that carries only a new key; anyone holding the leaked key can make the same kind of release with a key of their own, so that is a race ([Releasing: if the key leaks](../operations/releasing.md#if-the-key-leaks)).
- **What it does not prove.** The key signs whatever the build made. A compromised build dependency, or a malicious change merged to `main`, is signed like any other. A stable release has the maintainer's review of the draft before it's published; a nightly has none, and is published once built. Only servers and apps set to the nightly channel take one.

## Updates

A paired device can ask the server to update itself, since every paired device holds the operator's authority. What keeps that safe is not who asks but what may be installed: only a release the project signed, newer than the one running, on the server's channel ([Server: release feed](server.md#release-feed), [decision 0032](../decisions/0032-updates-are-served-outside-the-protocol.md)).

- **What is signed.** A release's `SHA256SUMS` and its signature, `SHA256SUMS.sig` ([Release signing](#release-signing)). The server and the apps verify with `RELEASE_KEYS` in `packages/release/src/keys.ts`, the keys in `release-keys/`; a release verifies when any of them signed it, so a new key is added a release before the old one stops signing.
- **What is checked, in order** (`verifySums` in `@j3-bots/release`): the signature over `SHA256SUMS`, against the release keys; that the signed list is the release's own, by naming that version's server archives, so a replayed older release, signed as genuinely, cannot pass for a newer one whose desktop package names no version; then a file's digest from that list, against the SHA-256 of the file as downloaded. A digest is never read from a list whose signature did not verify. Each refusal has its own reason (`VerificationFailure`): no `SHA256SUMS`, no signature, a signature that does not verify, a list not exactly as the release writes it, another release's list, a file it does not name, or a digest that differs. A list is exactly as the release writes it when every line, the last included, is 64 lowercase hex digits, two spaces, a name and a line feed; a blank line, a carriage return, a space after the name, binary mode's `*`, a name in a folder, `.` or `..`, a name given twice, or no line is refused. The signature file is the 88 base64 characters and at most one line feed.
- **Where.** The server's release feed verifies a release before it offers it. It keeps the `SHA256SUMS` and signature it verified, and verifies them again at each start against the keys trusted then, before a kept verdict counts. `j3-bots update` verifies again what it downloads, before it installs it, whatever the feed says. The desktop app and the Android app verify their own downloads with the same code, the Android app with its platform's Ed25519 and SHA-256 in place of Node's.
- **No downgrade.** A release is offered only when it sorts after the running version. A move from the nightly channel to stable waits for a stable release newer than the nightly that runs.
- **A mirror.** `J3_RELEASE_BASE_URL` points the server, `j3-bots update` and `install.sh` at a mirror of the releases page. A mirror's own releases verify with the key `J3_RELEASE_PUBLIC_KEY` gives, as PEM, as well as the release keys, and only while `J3_RELEASE_BASE_URL` is set, which is how the tests and the upgrade check sign theirs. Whoever can set the server's environment can already run anything as its user, so the variable opens nothing new; the server logs a warning when it trusts it. A value that is not an Ed25519 public key stops the server from starting, rather than being passed over, so a mistyped key is seen at once.
- **What leaves the server.** The feed's requests go to GitHub's API and releases without a token, carrying the user agent `j3-bots/<version>`, so GitHub sees the server's address and the release it runs. They go nowhere else: a redirect to a host other than the API's, the releases page's or GitHub's host for release files is refused before a request is sent, so no answer can point the server at another host, one on its own network included.

## Desktop updates

The desktop app updates itself from the repository's GitHub releases with electron-updater 6.8.9, unmodified ([Clients: desktop](clients.md#desktop), [Releasing](../operations/releasing.md)). Builds are unsigned for now. The citations below are **Read** in electron-updater 6.8.9 and builder-util-runtime 9.7.0, which it uses, unless marked otherwise.

- **Where an update comes from.** A packaged app asks GitHub's API over HTTPS for the releases its channel offers and picks the newest by the server's policy: the stable channel reads only `releases/latest`, which is never a pre-release; the nightly channel takes the newest of the stable releases and the nightly builds; a draft or a release candidate is never offered. It reads its platform's feed file from that release's folder (`latest-linux.yml` on Linux, `latest.yml` on Windows; `nightly*.yml` for a nightly build), and, where it installs updates, downloads the file the feed names from the same folder, and only once the feed names that release's version and only files directly in its folder: whoever can change a release's files can change its feed file, and could otherwise send the download to another release or host ([Clients: desktop](clients.md#desktop)).
- **What is checked.** The download is hashed as it streams and refused unless its SHA-512 is the one the feed gives (builder-util-runtime `httpExecutor.js:457-470`, the refusal at `:431`). A differential download is held to the same check (`differentialDownloader/DifferentialDownloader.js:121`), and so is a file downloaded in an earlier run, before it is reused (`DownloadedUpdateHelper.js:113-125`). **Verified** on Linux: an AppImage at 0.0.1-test, offered 0.0.2-test by a loopback feed whose SHA-512 had been altered, downloaded the file, logged `sha512 checksum mismatch`, kept nothing in its update cache and stayed at 0.0.1-test.
- **What ties it to the project.** The feed and the file come from the same release, so the SHA-512 catches a damaged download, not a malicious release. So once a download is complete, and before "Restart to update" is offered, the app checks it as the server checks a release ([Updates](#updates), [decision 0034](../decisions/0034-the-desktop-app-installs-only-a-signed-download.md)), with the same code (`verifyDownload` in `apps/desktop/src/downloadCheck.ts`, `verifySums` in `@j3-bots/release`): it fetches `SHA256SUMS` and `SHA256SUMS.sig` of the version electron-updater downloaded, from that version's own release in the repository, and requires the signature by a release key, a list that names that version's server archives, a file this platform installs (an AppImage on Linux, an installer on Windows), so a feed pointed at another file the release signs, such as `install.sh`, is refused, and the file's SHA-256 as the one the list gives its name. Anything short of that, a release with no `SHA256SUMS` or one that cannot be fetched included, leaves the download unoffered, and Settings says it didn't match the release's signature. So whoever can publish a release in the repository can no longer ship code to installed apps without the release key. What that does not cover:
  - The file is checked where electron-updater keeps it, in the operator's update cache, and installed from there: a process running as the operator could replace it between the check and the install. Such a process can already change the installed app itself.
  - On Windows, electron-updater checks an update's Authenticode signature against the build's `publisherName` before running it, and skips the check when no `publisherName` is set, as now (`NsisUpdater.js:84-99`).
  - On macOS, the app does not update itself while it is unsigned: it says a newer version is out and links to its release, and the operator downloads it.
  - On Linux, packages carry no signature of their own; the signed `SHA256SUMS` is the whole check for an AppImage. A deb does not update itself: like a Mac build, it links to the release.
- **Installing waits for the operator, and never takes root.** An update installs only when the operator presses "Restart to update", never as the app quits, and never while the page reports a save under way. Only an AppImage and a Windows install install one, each as the operator's user: an AppImage is replaced in place, and the Windows installer runs silently. A deb is never installed by the app. electron-updater would install it with `dpkg -i` as root, through `pkexec` or `sudo` (`LinuxUpdater.js:43-50`, `DebUpdater.js:53-56`), from a file in the operator's own update cache, which any process running as the operator could replace before that step. The app neither downloads nor installs a deb: it says a newer version is out and where to get it.
- **No downgrade.** Only a version newer than the running one is offered (`allowDowngrade` is false, `AppUpdater.js`, `isUpdateAvailable`). The app never sets electron-updater's channel, whose setter turns `allowDowngrade` on; a move from Nightly to Stable keeps the nightly build until a stable release is newer. A broken release is fixed by a newer one, and withdrawing it only stops apps that have not downloaded it yet.
- **What leaves the device.** Each check is a request to GitHub, which sees the device's address. Every update request carries an `x-user-staging-id` header: a random UUID made once and kept in the app's profile (`.updaterId`), so GitHub could tell one installation's checks apart over time (`AppUpdater.js:386-387`, `:502`). The user agent is Electron's default, which names the app and its version (**Assumed**). Nothing about the J3 Bots server, the device's pairing or its conversations goes with them.
- **The page's part.** The page can read the update's status, ask for a check, ask for the restart, choose the channel (stable or nightly, which the main process keeps in its settings) and report whether a save is under way, through the bridge, decoded with its schemas on both sides and heard only from the app's top frame. It cannot choose the feed, the file or the version.

## Dictation

- **What leaves the device.** The mobile app's dictation uses the platform's speech recognizer ([Clients: mobile](clients.md#mobile)), and the microphone only from the press of Dictate until Stop, or until the conversation leaves the screen or the app leaves the foreground. Recognition on the device sends nothing; online, the operator's audio goes to the device's speech service (usually Google's on Android, Apple's on iOS) for as long as dictation is on. The app asks Android for the on-device recognizer where it has the device's language installed (**Read** in `expo-speech-recognition` 58.0.1, `ExpoSpeechService.kt`), and takes iOS to recognize online; that the on-device recognizer then sends nothing is **Assumed** from Android's own description of it. While it listens, the line under the composer says whether recognition may run online. Nothing goes to the J3 Bots server but the text, once the operator sends it.

## Secrets

- J3 Bots never asks the operator to paste a secret into a conversation, and the base prompt tells bots not to either.
- When a bot needs a credential, it uses the engine's secret request, which shows the operator a masked input and gives the value to the command that needs it without placing it in the model's context.
- J3 Bots carries the value from the client to the engine and keeps nothing of it: not in the card, the change log, a command receipt or a log line. The card records only that a value was provided. In code the value travels as a redacted type, so printing it shows nothing.
- Memory files are not a place for secrets. The `remember` tool refuses text that looks like a credential.
- **A website login the operator wants kept** goes to the vault, from a save-login card the bot raises with `request_credential` or from Settings, never through the conversation. What the operator types on the card goes from the client to the vault; the bot is told only that the card is shown ([The vault](#the-vault)).
- **The provider connection's key** is typed on the host into `j3-bots provider connect`, without echo, or piped on standard input, never on the command line; or, in the desktop app running the bots on its own computer, into its endpoint form, which sends it to that server once, over the `provider.connect` RPC with no command ID, so no receipt keeps it, and clears the field once the server took it. The command hands it to the running server over the admin socket, and the server to the engine's secret store, as one file holding the base URL and the key together (mode 0600, inside the private home), so a change cut short never pairs one connection's base URL with another's key. Only before the engine starts is it written out to the harnesses: one secret file per instance for the variable each harness's configuration names next to the base URL; `provider connect` restarts the engine for that ([Engine: reaching the models](engine.md#reaching-the-models)). The server keeps no copy and logs nothing of it. Its request types the key as a redacted value, decoded as one at the admin socket and at the RPC, and checked for length only then, so neither a refused key nor a log of the request prints it; a test holds that a key refused for its length and one stored reach no answer and no log. It travels only to the endpoint, so the base URL must be `https`, or `http` to this machine only; the command refuses plain `http` to another host. The engine gives the key to the harness process, in its environment; Claude Code reads it from there through its key helper, `printenv` of that variable. That environment reaches the commands a bot runs in its shell, so a bot can read the key: a Codex command's live environment holding it is **Verified** with Codex 0.171.0, through `exec_command`; a Claude Code command's is **Assumed**, since no run looked. Codex's shell snapshot is turned off ([decision 0019](../decisions/0019-codex-runs-with-a-home-of-its-own.md)), so no file under its home captures the key any more, but the snapshots Codex wrote before that change, which held it (**Verified** on release `4969`, in `providers/codex/shell_snapshots/`, inside the private home), are not removed and can still be there on a home that was upgraded. Keeping the key out of the bots' shells is an open problem.
- **A harness's sign-in from the app** runs on the server, for J3 Bots' home for that harness, with no terminal ([Engine: sign-in from the app](engine.md#sign-in-from-the-app)). Of what the harness prints, only the `https` page it waits on leaves the server, to the client that follows the sign-in; the rest, which may hold a code, stays in memory and is never logged or returned. The page returns to the harness on `localhost`, so only a browser on that computer can finish it. The sign-in refuses a provider home that is a symbolic link, or that other users can open, by its mode or, on Windows, its access list, and Claude Code's credential file when it is a link, as `provider login` does, and never touches the operator's own sign-in.
- **The operator's own provider setup stays out, and stays as it is.** The harnesses run with homes of their own, and the engine starts with an allowlist of the server's environment (the system's basics, locale, proxy and certificate variables), so a server started from the operator's shell does not hand bots the operator's harness configuration, sign-ins or keys. No harness the engine runs uses the operator's `~/.claude` or `~/.codex`: the engine's own default Claude Code and Codex instances are turned off, and any other harness run gets empty folders of J3 Bots' own. On Linux and macOS, Codex runs with a home folder of J3 Bots' own too, so a Codex bot is not offered the operator's `~/.agents/skills`, while its commands keep the operator's `HOME` and profile ([Engine: isolation](engine.md#isolation), [decision 0019](../decisions/0019-codex-runs-with-a-home-of-its-own.md)); on Windows it still is (known gaps, below). This matters most where J3 Bots runs as the operator on their own computer, next to the Claude Code and Codex they use themselves.
- **The trust boundary is the operator's user.** A bot's harness runs as the user the server runs as, and the commands it runs inherit the harness environment. So the connection's key, the engine's secret store and every file that user can read, the operator's own sign-ins included, are within reach of a bot that runs a command to look; the allowlist keeps configuration from leaking in by accident, and is not a wall. The key reaches those commands: a Codex command's environment holding it is **Verified** with Codex 0.171.0, through `exec_command`; a Claude Code command's is **Assumed**. Codex's shell snapshot, a file that held it too, is turned off ([decision 0019](../decisions/0019-codex-runs-with-a-home-of-its-own.md)).

## The bot's browser

A bot's browser is signed in wherever the bot or the operator signed it in, and it shows whatever its pages show ([Server: the bot's browser](server.md#the-bots-browser)).

- **The stream shows secrets.** A picture of a page is the page: an account's details, a token a settings page prints, a one-time code, what the operator types into a field that does not mask it. J3 Bots does not try to tell a secret on a page from the rest, so every rule about who may see a picture is a rule about who may see those.
- **A paired device is a remote control.** Any paired device can watch every bot's tabs and take one over: click, type, go to an address, answer the page's dialogs, as the bot's browser, with its sign-ins. This is the operator's authority, which a paired device already holds ([Trust model](#trust-model)). A device that is lost is revoked: its viewers close at once, a tab it held included, without the 60 s a dropped connection keeps.
- **The media socket is authenticated as the RPC socket is**, with the device token or a one-use ticket, behind the same `Host` check, and the ticket is not logged.
- **Pictures stay in memory.** The server keeps at most three pictures per viewer: the one in flight, the newest waiting and the last one drawn. It holds them only while the viewer is open. It never writes one to disk or to the database, logs one, caches one or sends one in a push. What the operator types goes to the engine and is not logged.
- **What a page can reach on a device.** The media socket carries pictures and the frames the contract lists, and nothing a page could use to reach the device. The engine's clipboard, downloads, uploads and file pickers are dropped. An address a device sends is `http` or `https` only. A dialog's text is the page's: a client shows it as plain text, as it does any text a page or a bot wrote.
- **The bot can still read a tab the operator holds.** While a person holds a tab, the bot's actions on it fail, but its reads (status, snapshot, waiting for something on the page) still work ([Engine: the bot's browser](engine.md#the-bots-browser)). So the bot can read what the page shows meanwhile, what the operator typed into a field that does not mask it included. A password field is masked in a snapshot as it is on screen: **Assumed**. To keep a value from the bot, the operator uses the engine's secret request, not the browser.

## The vault

The vault seals the operator's saved logins and connectors' secrets under a key that comes only from the master password ([Server: the vault](server.md#the-vault), [decision 0029](../decisions/0029-the-vault-key-comes-from-a-master-password-held-in-memory.md)). It protects what is on disk. It does not protect against the server's own user while the vault is unlocked: that user, a bot's shell included, is inside the trust boundary, as for everything else here.

| Threat | What stands in its way | What does not |
| --- | --- | --- |
| A copy of the vault's file leaves the machine: a backup, a disk, a synced folder | Every value is sealed with AES-256-GCM under a data key that only the master password unwraps, and every guess at the password costs scrypt's 64 MiB and about 0.7 s on a Raspberry Pi 4. Updates never copy the file into a snapshot. | A weak password: offline, nothing but scrypt slows the guessing. What the file keeps in the clear: record ids, times, which bots each login allows, and when and on which device each value was last shown. |
| Someone guesses the password through a paired client | Five wrong passwords in a row, then waits that double from 30 seconds up to an hour, across every client. A wrong password and a refusal say nothing of how close the guess came. | The count starts over only after a day with no wrong password, so guessing without a pause is held to one try an hour, and a day's pause buys five quick ones. The vault's file keeps the count and the wait, so a restart does not reset them; the server's user can still edit that file, but that user is inside the boundary anyway. |
| A paired device falls into other hands | Each unlock needs the password. Revoking the device closes its sockets at once. | While the vault is unlocked, any paired client can read any value: a device token carries the operator's authority. Nothing locks the vault on a timer; the operator locks it with Lock now. |
| A bot, or anything running as the server's user | While the vault is locked, the key is nowhere on disk, and the file alone gives nothing. No tool returns a value, and the card tells the bot only that it is shown. | While it is unlocked, the key is in the server's memory. Whether another process of that user can read that memory depends on the system's debugging policy, such as Linux's `ptrace_scope` (**Assumed**). That user can also replace the server's own files, so that a later unlock gives away the password. |
| A page a bot reads talks it into asking for a login | The card shows the operator the site's origin and the bot's note. The operator chooses whether to save anything, and the bot never sees what they type. | A login saved for the wrong site, if the operator does not check the origin: the server then fills it wherever that origin's page asks, for every bot the login allows ([Filling a login](#filling-a-login)). |
| A value leaks into what J3 Bots keeps or shows | Values are redacted types from the client to the vault, and from the vault to the page a fill types into. No vault request takes a command id, so no receipt keeps one, and no value reaches an entry, a change, a work step, a log line, an error or a tool result. Tests drive every vault request over the socket, and the fill tools through the bot tools, and check the logs, the errors, the steps and the answers. | What a client does with a value it was asked to show. The web hides a shown value after 30 seconds. Copy puts it on the system clipboard, which other apps can read and which J3 Bots does not clear. |
| The master password is forgotten | — | Nothing recovers the logins or the connectors' secrets: no reset and no recovery key. Setup and every password change say so. |

## Filling a login

A bot whose vault access is on can have the server type a saved login into its browser tab, unattended: there is no confirmation for each fill ([Server: filling a login](server.md#filling-a-login), [decision 0037](../decisions/0037-the-server-types-a-saved-login-into-the-bots-tab.md)). The bot is never handed the value: no tool result, work step, entry or log line carries it. It can still read it from the page, which the owner accepted (the row on reading the value back). What keeps a page from taking it, and what does not:

| Threat | What stands in its way | What does not |
| --- | --- | --- |
| A page asks the bot to fill a login on another site, or a lookalike | The server reads the tab's committed address from the engine after it took the tab, so the bot cannot move it meanwhile, and the bot's word counts for nothing. The page's origin must equal one of the login's exactly: scheme, ASCII host and port, so a lookalike name is compared in punycode and never matches the real one, and a subdomain is another origin. Plain `http:` is refused except on this computer, and so is any page whose own address is not `http:` or `https:`, a `blob:` page included. The address is read again right before typing, and a page that moved types nothing. | A login saved for the wrong origin. A page of the login's own origin that sends itself elsewhere between the server's last read and the typing: the engine types into whatever page is there when it runs the input. Only a page of that origin can time this, and such a page can already take the value where it is typed (next row). |
| A page asks the bot to fill the login into a field that is not the login's: a comment box, a search field, a field that sends what it gets elsewhere | The fill types where the bot focused, on the login's own origin only, so what a page can do there is what that site can do. After a password the server always presses Enter, and clears the field when the page stays. A refused fill closes that tab to fills for the rest of the turn. The tool's description and the base prompt tell the bot to fill only a site's sign-in form, and to tell the operator when a page asks otherwise. | J3 Bots cannot tell a password field from a text field: the engine's viewer channel does not say which element has focus. A page on the login's origin, a compromised or hostile one, can get the bot to focus a field it reads, and receive the value there. |
| A frame inside the page reads the value | The origin checked is the top page's. | J3 Bots cannot tell the top frame from a cross-origin frame either: if the bot clicked into an embedded frame, the value goes to that frame's page. |
| The bot reads the value back from the page | The bot cannot act on the tab while the server types: it holds the tab. The bot does not get the tab back on a page with a filled password field: the server submits and, if the page stays, empties the field first. A password field shows dots in a snapshot, as on screen (**Assumed**). | **Accepted by the owner:** a bot with vault access can read a value it just filled back out of the page with a script, through the engine's `preview_evaluate`, which every bot keeps, on Claude Code and Codex. A script it runs before the fill can also catch the value as it is typed. Its result reaches the model, so the model and its provider may see the value. The owner accepted this to keep page scripts for every bot. The guards above still stand: the exact origin, the server holding the tab while it types, vault access per bot and off by default, and the field cleared after a submit that stays. The real fix is a field the bot cannot read, which only the engine can give ([Proposal: a typed secret in the engine's browser](../proposals/engine-browser-secret-input.md)). A user name and a one-time code are typed in fields that show them, so the bot can read them on the page, as the operator would. A page that copies the value elsewhere in itself, where the bot reads it, gives it away. A bot's shell can read the browser's profile, saved form data included, as for every bot ([Known gaps](#known-gaps)). Clearing a password types Backspaces where the focus is: a page that moves the focus when Enter is pressed, as a form with an empty required field does, gets them in that field, and the password stays where it was typed. The server reads the page every 100 ms for a sign-in that leaves it: a page that loads another and has finished between two reads, or one still loading after 6 s, counts as staying, and the Backspaces go to the new page. When the engine does not confirm the typing within 5 s, the fill answers `unavailable` and gives the tab back without clearing it, so a password may be left in the field. |
| A bot fills when the operator did not want it to | Vault access is per bot and off by default, a switch on the bot's details next to the browser's, and a bot whose browser is off fills nothing either. Both switches and the login's bots are read again right before typing, and so is the bot's turn, so turning a switch off or stopping the turn stops a fill that has not typed yet. A login is filled only for the bots it allows, none by default. A fill must match a call the engine recorded in the bot's running turn, so no other program on the computer can ask for a fill the bot did not ask for. One that copies the bot's own call, with the same arguments, can claim it first, as for every bot tool: the fill then runs as the bot asked, and that program gets its answer, which carries no value. Each fill, typed or refused, shows as a step of the bot's work, with the login, the field and the page's origin. Locking the vault stops every fill. | Within those, nothing asks the operator first: that is the owner's choice, for unattended work. |

**What would close the residual.** The two things J3 Bots cannot tell, which element has focus and in which frame, the engine knows. A proposal for T3 Code to say so, or to type a secret it never hands to a viewer at all, is in [Proposal: a typed secret in the engine's browser](../proposals/engine-browser-secret-input.md). It has not been sent anywhere.

## Connectors

New in 0.4.0, and being built ([Server: connectors](server.md#connectors)). A connector acts in the operator's account at a service, from text a remote server writes, so each part of it has a rule.

| Risk | What stands against it |
| --- | --- |
| A bot holds a token | J3 Bots is the connector's OAuth client and calls it itself. Tokens, refresh tokens, client secrets, header values, a command's environment, and an address or command arguments the operator typed, which can carry a key, are in the vault ([decision 0028](../decisions/0028-one-secret-store-for-logins-and-connector-secrets.md)) and added to a request only when the server makes it. None reaches a bot, a harness's configuration, a prompt, an entry, a client, a log line or a command receipt: clients are shown an address's origin and a command's program alone. What a client sends of them travels as a redacted type, checked only once redacted so a refusal never prints it, and the requests that carry one have no receipt. |
| A tool description or result carries instructions | Both are untrusted text. A description is capped and stripped of control and format characters, and shown to the operator before bots get the tool. A result reaches the bot framed as data from that connector, which it cannot close or imitate. The base prompt says a request found in a result is reported, not carried out. |
| A server changes its tools after it was trusted | The tools are recorded when the connector is connected. A tool added later, or one whose description or input changes, is held from every bot until the operator accepts it, at the revision they saw. Declining keeps it held: a changed tool is not served at its old version, which the connector no longer offers, so bots get none of the held tools until it is accepted. |
| A connector sends, deletes or shares without the operator | Its tools are not pre-approved: they follow the bot's permission mode. The base prompt's rules on [acting on the operator's behalf](#acting-on-the-operators-behalf) hold in every mode. |
| A bot reaches a connector it was not given | The server checks the connector's grant for the session's bot on every call, and matches the call to the bot's running turn as it does every `j3` tool, with no weaker path. A bot can suggest a connector, never add one or grant one. A teammate's request does not lend its connectors. |
| A sign-in is forged or misdirected | PKCE with S256, required of the service. `state` is random, used once, expires after ten minutes and is bound to the connector and the device that began the sign-in; only that device can finish it. A token is sent only to the server it was issued for (the resource indicator), never to an address a metadata document names later. Every OAuth endpoint must be `https:`, and a client opens a sign-in only at an `https:` address. |
| The server is made to reach into the operator's network | A connector's address is `https:`, with no user name. An address the operator types that leads into their own network is refused until they confirm it. Addresses a remote server names (metadata, registration, redirects) are checked after DNS resolution, when connecting, and refused when they lead to loopback, private, link-local or unique local addresses. |
| A connector started by command | It runs on the server as its user, with everything that user can reach: code the operator chose to run. Only a paired client adds one, after a confirmation that shows the whole command line, whose secrets belong in its environment; the Android app adds none in this release, a convention of the apps rather than a wall the server keeps. |

**Logged:** a connector's id and host, the tool's name, the outcome, the HTTP status and how long a call took. **Never:** a secret, a sign-in's code, `state` or PKCE verifier, the address a sign-in returned to, a call's arguments or its result, which are the operator's data. A result stays in the engine's transcript as any tool's output does; a server that echoes a secret it was sent puts it there, which J3 Bots cannot scrub from arbitrary text.

## What is logged

- Conversations, rooms and memory are the operator's data, stored on their disk, in the clear.
- Server logs record wakes, dispatches and outcomes with identifiers, not message text.
- No telemetry leaves the machine by default.

## Known gaps

- No isolation between bots at the filesystem level, and none between a bot and the operator's user.
- Whoever can read the service's log, or binds the tool port in the moment the server stops while a bridge forwards a call, can learn a session's id and, until the server retires that session, use the bot tools that do not act for a turn as that session's bot; the one who binds the port can also answer that call ([J3 Bots' own surface](#j3-bots-own-surface)).
- A bot's shell can read the browser's profile, its session cookies included, whether that bot's browser switch is on or not: the profile is a folder in the engine's data directory, and every bot runs as the same user. The switch controls whether the engine takes the bot's calls to the browser's tools, not the files.
- A bot can send a message to another bot's session through the engine's own `t3_thread_send`, which reaches any thread of the engine that runs in no broader a mode than the sender's (**Read** at `59651c1`, `mcp/toolkits/orchestrator/tools.ts`). That message goes around J3 Bots' teammate messages and their limits, and the turn it starts shows as background work the server did not dispatch. So a bot without the browser can ask one with it to use it. This predates the browser switch.
- No protection against a compromised paired device beyond revocation.
- A fill types where the bot's focus is: J3 Bots cannot tell a password field from a text field, nor the top frame from a cross-origin frame, so a page on the login's own origin can receive the value in a field of its choosing ([Filling a login](#filling-a-login)).
- A bot with vault access can read a value it filled back out of the page with a script (the engine's `preview_evaluate`, which every bot keeps), so the model may see it. The owner accepted this to keep page scripts ([Filling a login](#filling-a-login)).
- The vault protects its file, not a running server. While it is unlocked, its key is in the server's memory, within reach of anything that can act as the server's user ([The vault](#the-vault)).
- On Linux without a keyring the desktop app can use, its device token is stored obscured, not encrypted. The app says so rather than refuse to pair, and the token stays obscured until the device is paired again.
- Desktop builds carry no code signature: an update is checked against the release key's signature over `SHA256SUMS`, but the first install is trusted as far as the page it was downloaded from, and Windows and macOS do not check who published it ([Desktop updates](#desktop-updates)).
- A nightly is signed with the release key with no review: whatever reaches `main` reaches every server and app on the nightly channel the next day ([Release signing](#release-signing)).
- Push notifications pass through Expo's push service and Apple's or Google's, which see what a push says; previews are opt-in for that reason. A push cannot be withdrawn: it stays on the phone after the operator answers elsewhere. A browser notification never leaves the device, but it can show on a screen others see, so the same setting holds for it.
- The automatic reviewer in Auto mode is the provider's, and its judgment is not J3 Bots' to guarantee.
- A connector's secrets are as safe as the vault while it is unlocked: its key is in the server's memory, which any process of the server's user can reach, a bot's shell in full access included ([decision 0028](../decisions/0028-one-secret-store-for-logins-and-connector-secrets.md)). And what a connector's server does with what bots send it is that server's to answer for.
- On Windows, a Codex bot is offered the operator's `~/.agents/skills`, so on a Windows computer that runs the bots itself, every skill the operator keeps there for their own coding reaches every Codex bot. Codex finds that folder through the system's profile folder and reads no variable for it (**Read**, Codex 0.171.0 `ext/skills/src/host_roots.rs`, `dirs-sys` 0.5.0). **Verified** on Windows 11 with Codex 0.171.0: its app server listed a skill there as enabled with `HOME`, `USERPROFILE`, `HOMEDRIVE` and `HOMEPATH` all moved to an empty folder. No Codex release up to 0.173.0-alpha.4 has a setting that turns only that folder off, and J3 Bots does not turn the operator's skills off one by one ([decision 0019](../decisions/0019-codex-runs-with-a-home-of-its-own.md), [#168](https://github.com/JPSAUD501/j3-bots/issues/168)). Claude Code bots are not affected. Until Codex offers a way, an operator on Windows who wants their skills kept from bots keeps them out of `%USERPROFILE%\.agents\skills` or uses Claude Code for those bots.
- A built-in provider that a later engine adds, enabled by default, would run as an instance of the engine's own on the operator's setup until the adapter turns it off too. Each engine upgrade checks for one ([Engine: upgrading](engine.md#upgrading-the-engine)).
