# Server

The J3 Bots server is the product. It owns what the operator sees and decides what every bot does next. This document describes its data, its one central mechanism (the wake pipeline) and the features built on it.

## Data

J3 Bots keeps two kinds of state, in two places, for two different readers.

**The database** (`<J3_HOME>/j3.sqlite`) holds what the server needs to query and what clients render:

| Entity | What it holds |
| --- | --- |
| Settings | One row: the operator's name, their time zone and whether it was set, the budgets, notification preferences, the update channel |
| Bot | Profile, model, permission mode, whether it may use the browser, whether it may fill saved logins ([Filling a login](#filling-a-login)) and how many times it lost it that are not yet withdrawn from its project, how many times its model, permission mode or browser switch changed, workspace path and the real path it had when first provisioned, engine project id, whether its conversation was told that its main session is not ready, the count of model or permission mode changes at which the engine refused its permission mode, and the refusal of it its conversation was told of |
| Conversation | One per bot. A sequence of entries, and how far the operator has read |
| Section | A named group of bots in the roster: its name and its place among the others. A bot names the one it is in, or none |
| Room | Name, members, host, status (active or archived) and when it was archived. A sequence of entries |
| Entry | A message or a card, with its author, its time, its delivery state and its fixed place (`order`) in its conversation or room |
| Session | J3 Bots' own id, its bot, its purpose (main or side), the engine thread id once the engine has one, how many times the engine refused to open it, the prompt version it was created with, the provider it runs on, how many changes of its bot's settings it has not been brought to (a main session) or how many its bot had when it was written (a side session), the browser switch its tools were last brought to, the rotation it is due for and why, when it was retired and when the engine took it out of use after that, the cursor of the engine events applied so far, the turn it has admitted with that turn's audience, the engine queue's current hold and the hold it last resumed, when the engine answered that it has no such session and, for a side session, the routine wake it runs |
| Wake | Kind, priority, target bot, audience, payload, hop count, status (pending, dispatched, finished, cancelled or failed), the dispatch that delivered it, and, for a room wake, whether its bot left the room before it ran |
| Dispatch | One delivery to the engine: its sequence number, the order it was written in, the target session, the audience, start or steer, the rendered envelope and its files, how many times it was sent, how many times staging its files failed, the disposition the engine reported first if it reported one, for a room dispatch the room's newest entry when its envelope was written, the turn that delivers it, its status and, when it failed, why, a pending continuation of its turn, the Stop that fenced it, the outcome. Several coalesced wakes share one |
| Stop | The operator's Stop of one bot (scope `bot`), or of a room's work when the room is archived (scope `room`): its command id, the highest dispatch sequence number when it was recorded, and per target session and round the engine key, when the engine acknowledged it or refused it, when the events were observed past that acknowledgment, and whether they confirmed it stopped |
| Ask card | For an `ask` question: the wake it came from and the audience of the turn that asked |
| Tool call | A bot tool call pinned to the turn and audience it came from and to the engine's record of the call, with its result and, for a teammate message, the teammate it reached |
| Engine request | For an approval, an engine question or a secret request: the session, the engine's request id and the turn it belongs to; for a secret request, whether a submission may be in flight, never its value |
| Catch-up note | What a bot's main session has not seen yet, consumed by its next main-session dispatch, and for a routine run's message, that message's place in the conversation |
| Held message | A non-urgent teammate message waiting for the recipient's next envelope: its sender, its text, its hop count and the handoff card it put in the recipient's conversation |
| Teammate message | Where a teammate message stands in its pair's teammate conversation: the pair (its two bot ids, sorted), the sender and recipient, its two handoff cards while their bots exist, and its place among all teammate messages ([Teammate conversations](#teammate-conversations)) |
| Blob | File bytes, stored once per digest: size and where they are stored |
| Attachment | A file the operator sent or a bot produced: a name and a media type over a blob |
| Routine | Bot, name, instruction, trigger, enabled, next run, run count, webhook secret, and the runs it missed since its last run started (how many, the first and the last). Its runs: status, when a scheduled run was due, start and end, the wake of its latest attempt, how many attempts started and when the next may start, trigger data, the webhook request's idempotency key, and why its last attempt failed when J3 Bots can name it |
| Device | A paired client: its token hash, when it was revoked |
| Push registration | Where to push to one device: the push service, the token, the platform, the language to write in, when it was registered, its generation (new at each registration, also one made again with the same token) and how many sends failed since. One per device at most, deleted with the device's revocation |
| Push service | When the next send to the push service may begin, after a request it did not answer. One row |
| Push delivery | One notification to push to one device about one entry: its words until the push service takes it, with and without a preview, how many sends began, the generation of the registration the last went to, the service's receipt, when it is next due and the deadline of its stage. Deleted once it settles |

A column that holds one of a fixed set of values carries a `CHECK` listing them, as a push registration's provider and platform do. SQLite cannot change a `CHECK` in place, so a new push provider means rebuilding that table, in the migration that comes with its sender ([decision 0014](../decisions/0014-push-goes-through-a-push-sender.md)).

Migrations are numbered and applied in order, each once. The migrator applies only those numbered past the last one the database recorded, so the server refuses to start on a database that recorded a later migration than one it lacks, naming the one missing, rather than run without it. It also refuses a database that records a migration it does not know, naming it: a newer release migrated it, and `j3-bots update --rollback` puts back the database from before ([decision 0016](../decisions/0016-an-update-keeps-a-snapshot-to-roll-back-to.md)).

Entries are ordered by `order`, set when the entry is created and never changed. The change sequence that clients resume subscriptions with is separate: it records when an entry changed, not where it sits.

**The filesystem** (`<J3_HOME>/bots/<bot>/`) holds what a bot reads and writes with its own tools, and what the operator may want to open in an editor:

```
bots/scout/
  .j3/
    system.md        generated: base prompt + profile + pinned memory
  AGENTS.md          generated: the same identity for harnesses that read it
  memory/
    profile.md       small, always in front of the bot
    log/2026-11.md   dated history
  skills/            procedures, one folder each
  files/             what the bot produces
shared/
  memory/
    user.md          facts about the operator every bot can read
    log/2026-11.md   shared dated history
  skills/            skills available to every bot, the shipped `j3-` ones among them
providers/
  claude-code/       Claude Code's home for every bot (`CLAUDE_CONFIG_DIR`)
    skills/          a link to each shared skill, made at every engine start
  codex/             Codex's home for every bot (`CODEX_HOME`)
    skills/          the same
state/
  shipped-skills.json  the SHA-256 of each shipped skill text the server wrote
  runtime.json       the release this home's data was last handed to, whether by a rollback, and a transition under way
  release-feed.json  the newest release each channel last offered, whether it verified, and when the feed checks next
vault/
  vault.sqlite       the vault's sealed logins and connector secrets; in no snapshot
backups/
  <snapshot>/        the databases and settings a version transition copied before it changed release, the vault's never
  update.lock        held by the one version transition or rollback running
```

Generated files are written by the server from the database and the memory files. A bot never edits them by hand, and the server rewrites them whenever their inputs change.

**Private state stays in the home.** Every location the server writes (each entry of the home but `web`, the shared memory and skills, each bot's workspace with its memory and generated files, the attachments, and the engine's folder with the folders the engine adapter declares it writes there, `j3/` among them) must resolve, symbolic links followed, inside the home's real path and outside the web client's folder. A bot's `skills/` and `files/` are its own: the server creates them once, and writes there only the operator's files it copies into `files/inbox/`, each through the check below, so a link there is the bot's business and refuses nothing at start. Start refuses a home where a written location does not resolve as it should, naming it. Every write of private state, the adapter's included, checks its folder the same way first, then writes a new file (mode 0600) of a random name there that must not exist yet and renames it into place, so a link made while the server runs (by a bot's own tools, say) is never followed and cannot publish memory or a generated file through the web client. The engine download is the one file written in place, so that an interrupted one resumes: it must be a regular file, its folder and itself are checked the same way, and it is opened so that a link at its name is refused, even one made after the check. Windows has no such way to open a file, so there a link made after the check is followed; making a symbolic link there takes a privilege an ordinary user does not hold unless Developer Mode is on. A removal (a deleted bot's memory and generated files, an attachment's bytes once nothing refers to them) checks the folder above what it removes the same way, and removes a link there rather than following it. A refused write or removal is logged, and only that bot's workspace or memory, the attachments, or the engine's folder is affected: a memory write or an upload fails with `Conflict("private-location")`, also when a folder inside the memory, such as `log/`, is the link; a file copied into `files/inbox/` fails its staging; a generated file or a removal is skipped; the engine is not installed; and every other bot carries on. What this rule does and does not defend against is in [Security](security.md). To keep state on another disk, put the whole home there.

Memory lives in files and not in the database because the bot's own tools can read, search and quote files, and because the operator can read, edit, diff and back them up without J3 Bots. See [decision 0006](../decisions/0006-memory-is-files.md).

## The wake pipeline

Everything a bot does starts as a **wake**. There is one pipeline for all five kinds, and it is the only path to the engine.

```
 operator message ─┐
 room message ─────┤
 teammate message ─┼──> wake (persisted) ──> held by the server ──> dispatch (persisted) ──> engine session ──> turn
 routine trigger ──┤                              │
 system event ─────┘                              └── priority, coalescing, concurrency
```

### 1. A wake is recorded before anything happens

Creating a wake and the entry that caused it (the operator's message, the room message, the answered card) is one transaction. A wake that exists will be dispatched or visibly cancelled; one that does not exist never was requested. If the server stops between recording and dispatching, it picks the wake up again at start.

A bot created without a model gets the first model of the first provider that can run it now; with none ready, of the first that is at its limit, then signed out, then still in the engine's first check since it started, among those that list a model. A provider the engine checked and cannot run is never the default: the engine lists Claude Code's catalog also when Claude Code is not installed or its check failed (**Read** at `59651c1`, `checkClaudeProviderStatus` in `ClaudeProvider.ts`), and a bot put there would wait for a provider that never comes. So a first bot is not refused for want of a connected provider: its opening waits for one, as below. An engine with no such provider refuses it with `Invalid("model")`. A bot created without a permission mode gets Auto on a provider whose harness has the engine's reviewer (Claude Code and Codex; **Assumed** for any other harness), Supervised otherwise.

The bot records whether the server chose its model and its permission mode, or the operator did (`bots.model_by_server`, `bots.permission_mode_by_server`); a bot created before that was recorded counts as the operator's on both. A bot whose model the server chose moves to the default model while the engine does not have its opening yet (its wake pending, or in a dispatch never sent), its provider is not ready and the default model's provider is. The server looks for such bots in one pass at a time, each bot in the order it was created: whenever a provider's state changes or it lists its first model or its last one goes (a ready provider whose catalog fills in has not changed state), and, for the new bot alone, after each creation. Each bot's move is decided and saved in one transaction, inside the gate of its main session, from the engine's state as it is then: a bot the operator gave a model meanwhile, one deleted meanwhile, or one whose new provider stopped being ready meanwhile is left as it is, so the operator's own choice always wins. The change is applied as the operator's change of provider is applied (below) and recorded as the server's choice; when the server also chose the permission mode, the bot takes the new provider's default mode, recorded the same way. A bot that cannot move is logged, and neither stops the pass nor fails a creation. So a Codex-only operator whose first bot landed on Claude Code while both were still being checked gets the hello once Codex is ready. A model the operator chose, at creation or since, is never moved.

Creating a bot writes its first wake with it, in the same transaction: a `first-run` system wake for its conversation, so the bot's first turn opens the conversation ([Experience](../product/experience.md#first-run)). Its envelope says that none of the operator's bots knows what to call them while the operator has no name and no other bot's `first-run` wake has been dispatched; this is read in the transaction that writes the dispatch, from the wakes, so the operator is asked by the first bot to say hello, and again only when that same opening is retried. A bot deleted with its wakes leaves no trace of having asked, so a bot created after it may ask once more. That is the only place one is written: a retried `bot.create` finds its receipt, and a restart, a replaced session, a fresh start or a change of model write none. A bot the primary bot creates with `create_bot` gets one too; its cause is the operator's, as the creation is. The wake waits like any pending wake until the bot's main session is opened and can take it, and an operator wake goes first. It also waits while the engine reports the bot's provider as anything but ready (signed out, at its limit, unavailable), or does not report it at all, as while the engine is down or just after it started: a turn that fails before the provider starts helps nobody, and the dispatcher looks again as soon as a provider's state changes. An opening already written into a dispatch never sent waits at its first send the same way, as one a restart finds, or one written just before its provider stopped being ready: the send reads the provider's state again, in its claim's transaction too, and releases the dispatch, so the hello waits as a pending wake and the bot can still move. The wait has no deadline: the provider turning ready, a move, the operator's change of model or their Stop ends it. What ends it before it runs:

- **The operator writes first.** Whether the opening gives way depends on whether it waits for its provider:
  - **Withdrawn.** Ordinarily, `message.send` to the bot's conversation cancels the opening in its own transaction while it is pending, and also once it is written into a dispatch never sent: that dispatch is released, which the send's claim cannot race, since a claim needs it still `intended` with no attempt. Otherwise the envelope would say the operator has not written. A dispatch sent at least once may be in the engine, so it runs, and the operator's message reaches the same turn as a steer or the next one; the base prompt tells the bot to answer a message that reaches it in that turn instead of greeting.
  - **Held.** While the opening is not with the engine and its provider is not ready, or while it already holds a message, it is not cancelled: the message's wake records the opening it waits behind (`wakes.behind_opening_id`) in the transaction that writes it, and so does every message after it until the opening has ended, so neither a later message nor the provider turning ready withdraws the hello. A held wake is not dispatchable while its opening has not ended: it never joins the opening's envelope or steers its turn. Once the opening has ended (finished, failed, refused or cancelled), the held wakes are ordinary `user` wakes in the order they were written, which go as the bot's next turn: the bot greets, then answers. Until the opening goes to the engine, each such message's `pending` delivery says it waits behind the hello (`behindOpening`), so clients can say what it waits for ([Experience](../product/experience.md#first-run)); once the hello has gone, the message shows as any queued one.
- **The operator's Stop and a fresh start** cancel it like any pending wake, with the messages held behind it.
- **A provider change does not.** Its Stop spares the opening, and the operator's messages held behind it while it has not ended: a pending one stays pending, and one written into a dispatch never sent is released back to pending, so the hello runs on the new provider, the messages after it. Once the opening has ended, a message that was held behind it is ordinary work, and the Stop cancels it like any other. A bot with no live main session gets no Stop at all, so it is the same either way. An opening the engine may already have is stopped with the rest of the work.

If the opening's dispatch fails before its turn starts, the wake has no message to show it, so the conversation shows a retryable `turn-failed` notice, as for an `ask` answer ([3. A dispatch is written](#3-a-dispatch-is-written-before-the-engine-is-called)). If its turn fails, or its session is lost while the turn runs, the notice offers a retry like an operator's turn. Either retry records the `first-run` wake again. Once the operator has written in the conversation, no opening is offered again: `message.send` takes the retry off every notice for it, a notice written later has none, and `notice.retry` refuses one a client still shows. An opening that ends without a word is only a quiet bot: no `undelivered` follow-up and no notice.

### 2. The server holds waiting wakes

J3 Bots owns waiting and priority. A pending wake stays in the server's database until its session can take it; J3 Bots never asks the engine to queue a message. The engine still queues a start that meets a turn it began itself, and the server follows that (`queued`, below). Each wake has a priority from its kind: `user` first, then `room`, `bot`, `system`, and `routine`, and within a priority they go in the order they were written, which also orders the messages in one envelope. The operator's message in a room is a `room` wake with the priority of a `user` one: it goes before a bot's room wakes, and it may steer as a `user` wake does. Wakes written in one transaction share a time, so the order is the database's own insertion order, never the time or the id.

For each pending wake the dispatcher applies, in order:

- **Readiness.** A session the engine no longer has is skipped ([Sessions](#sessions)). A wake is dispatched only into an idle session: no admitted turn, no dispatch that may be in the engine and is not yet finished (sent but unanswered, accepted, or delivered), and no turn the engine started on its own; a pending continuation holds back every wake but the operator's. The one exception is below: a wake at `user` priority for a running turn with the same audience. Nothing at all is dispatched into a session while a Stop of it is unsettled ([Stop](#stop)). Nothing is planned into a session whose events are not known yet ([Observation](#4-the-turn-is-observed-and-admitted)), since they decide how it can take the wake, nor into one whose first send was refused as busy, before its busy deadline passes or its next event is applied ([Refusals](#3-a-dispatch-is-written-before-the-engine-is-called)). Each of these holds back only that session's wakes: the dispatcher goes on with every other bot.
- **One turn per room.** A room runs one turn at a time ([decision 0011](../decisions/0011-a-room-runs-one-turn-at-a-time.md)). A room wake may start a turn only when no turn of the room runs and no dispatch of it may be in the engine or is about to be sent (`intended`, `accepted`, or `delivered` with no continuation pending), and only when it is the room's next wake: the members' pending wakes for the room go by priority, then in the order they were written, whichever member each wakes. A member whose permission mode the engine refuses has no place in that order while the refusal stands, since nothing can be planned into its main session until the operator acts ([Sessions](#sessions), Every bot has a main session): its wakes wait out of the way, the rest of the room goes on, and they take their place again, as written, once the refusal is gone. One exception keeps the operator's word from waiting behind a member that cannot start: while the next wake's member cannot get a turn slot (**Concurrency**), the operator's room wake to a member whose session can start a turn now, as one whose continuation is pending holds a slot already, goes first instead. Whenever the next wake's member can start, the order stands. A dispatch whose turn waits for a usage limit's reset holds the room no more: its continuation is its own bot's, whose automated wakes wait for the reset anyway, and the operator's wake to that bot is dispatched and drops it (**Readiness**). Nothing records that a room is busy; the dispatcher derives it from those rows, and the transaction that writes the dispatch reads it again, with the room still active, the bot still a member, and its wake still the room's next (an archived room's wakes, and a former member's, are cancelled there instead). The transaction that claims a room start's first send reads the same rule again, not counting the start itself, with the bot still a member: another member's turn may have started since, as one the engine resumed after a usage limit's reset. A start that finds the room live, or its bot gone from it, is released unsent, and its wakes are planned again with the room as it is then. So is a room start that cannot be sent when it is due, for want of a turn slot or because a usage limit holds it (**Blocked providers**), before anything of it is staged: unsent, it would hold the room for nothing, and the operator's word to a member that holds a slot could not go first. Its wakes wait as pending wakes, which hold nothing, and are planned again in the room's order once what held them is gone. So a member busy elsewhere holds the room until it can take its turn, while its other wakes go on as usual. The operator's room wake is the one exception: it may steer the running turn of its member for the same room.
- **Coalescing.** Pending wakes of a bot with the same kind and the same audience that are ready for the same session become one dispatch: three messages in one room that arrived while the bot was busy are delivered together. Wakes for different audiences never share a dispatch, so one turn always speaks to one place. A room envelope is cut differently, and never fails for its size ([Rooms](#rooms)). Coalescing stops at the engine's limits for one message: its files together (`attachmentLimitViolation`) and the length of the rendered envelope (`engineInputLength` against `ENGINE_INPUT_LIMIT`, 120,000 characters, measured as the engine measures it, after expanding any assistant-quote link). The envelope holds the head wake, then as much of what the session has not seen as fits, oldest first, then as many of the other wakes as fit, in order. What is left out waits for the next dispatch in the same order, so a batch that does not fit becomes consecutive dispatches. A single wake always fits: every path that writes the operator's text into a wake checks that wake alone before it commits, with the same margin of 1,000 characters under the limit, which covers what renders longer at dispatch, such as the date, the zone and a room's name. `message.send` checks each message's files and its envelope (`Invalid("message-length")`, nothing written), a room message's as long as it can render: in the room at its widest (the longest name, as many members as a room can have, and the longest names, titles and ids), since the room may be renamed or given members before the wake goes, with the longest closing line and a line counting entries left out; `card.answer` checks an `ask` answer's envelope (`Invalid("answer-length")`, the card left open for another answer), a room card's with the longest room name. A retry sends again a wake that passed that check, and a system event is far below the limit. The dispatcher still never lets a wake hold the queue: a head wake that does not fit alone gets a dispatch of its own that fails as `rejected` without being sent, so it shows where it came from as a refused dispatch does ([Refusals](#3-a-dispatch-is-written-before-the-engine-is-called)), and the wakes behind it go on. Something the session has not seen that would not fit even beside the smallest wake, a system event, is left out for good, in order, with a `too-long` notice in the bot's conversation; both cards of a teammate's message left out so show `not-delivered`, and keep showing it whatever becomes of the urgent wake it was held from.
- **Concurrency.** At most N turns run at once across all bots. A slot is held by every session with a turn running or a dispatch the engine may have (sent and unanswered, accepted or delivered, a pending continuation included). A dispatch never sent holds none: it takes a slot when it is sent, and the slots are counted again before that send, so a session that cannot take its work yet never keeps a slot another bot could use. Every start is admitted by the same rule, whether it is planned now or sent again after its files failed to stage: a slot is free, or its session already holds one, as an operator's message beside a pending continuation does. The rule is read when the start is planned, and again in the transaction that claims its first send, since the budget or the sessions holding it may change while its files stage: a start refused then stays unsent, for the dispatcher's next pass, except a room start, which is released (**One turn per room**). Higher-priority wakes take a free slot first, and only work that can take a slot now competes for it: a routine's start, which the routine runner writes ([Routines](#routines)), is sent only after every bot's waiting wakes were planned in the same pass, and not while its session's provider is at its usage limit (**Blocked providers**, below).
- **Blocked providers.** If the bot's provider is at its usage limit, every wake but the operator's waits for the reset: a routine's, a teammate's message, and a room wake a bot's `say` caused alike. The engine's status may say so; when it does not, the turns the server saw end on that provider, in any session, each on its session's provider, do: the newest one that completed or failed at the usage limit, when it failed with a reset still ahead. An index over exactly those turns, newest first, keeps that read short. A wake held so is looked at again at the reset, when the limit says when that is, and as soon as the engine reports the provider's status changed. A start of such work written before the limit was reached, and not sent yet, is released instead, and the transaction that claims its first send checks the limit again, since it may have been reached while the files staged: unsent, it would keep its session busy, and the operator's word to the bot would wait behind it until the reset. Its wakes go back to pending, where they are held as above. A routine's start, in a side session that takes nothing else, is held unsent until the reset instead. An operator wake is dispatched anyway so the operator gets the engine's own limit message. A `first-run` wake waits while the engine reports the bot's provider as anything but ready (1. A wake is recorded).

| Wake | The session is idle | The session is in a turn |
| --- | --- | --- |
| `user`, and the operator's `room` wake | Start a turn (for a room, when it is the room's turn) | If the running turn has the same audience (the conversation, or the room the operator wrote in), steer it, so they can redirect work in progress. Otherwise wait, first in line, so a private message never lands in a room turn; the operator's later word for the running turn's audience still steers it. A wake carrying an `ask` answer always waits ([Questions](#questions-approvals-and-secrets)) |
| A bot's `room` wake | Start a turn, when it is the room's turn | Wait |
| `bot`, `system` | Start a turn | Wait |
| `routine` | Start a turn in a new side session | Not applicable: side sessions run alongside the main one |

### 3. A dispatch is written before the engine is called

Before anything is written, a message's files are checked against the engine's limits (`attachmentLimitViolation`: no empty file, inline images at most 10 MiB each and 80 MiB together). A message that breaks one is refused with nothing written.

In one transaction the dispatcher renders the envelope, writes a **dispatch** with the target session, the audience, the delivery (start, or steer with the turn), that envelope and its files in order, links the coalesced wakes to it, and consumes the bot's catch-up note and held messages into the envelope. A dispatch never changes its session, its audience or its envelope afterwards; the database refuses it.

Then, inside the session's gate ([One gate per session](#one-gate-per-session)), it reads the dispatch again and goes on only if it is still due: still `intended`, its deadline passed, and, for a first send, its session's events known and unfenced in a session with no unsettled Stop. A resend waits for no observation: its key makes the engine apply it once whatever the server knows yet, and a Stop may be waiting on its answer. A steer goes only into the turn it was planned for: if that turn is no longer the session's admitted turn when its first send comes, the dispatch is released and its wakes wait for the next dispatch. Before a first send, it copies each file into the bot's workspace, at `files/inbox/<attachment id>/<name>`, where the envelope names it beside the name the operator gave: the folder of its own keeps two files apart, and the name is made one path segment (a name made only of dots becomes `_`) of at most 200 bytes in UTF-8, shortened if need be with its extension kept, so the bot can open it with its own tools, replacing whatever is there. Before each copy it reads the dispatch again: one settled meanwhile, or a room start whose bot left the room while an earlier file staged, gets nothing more, and is released if it is still `intended`. A resend copies nothing, since the engine applies the envelope at most once and the inbox is the bot's since. It stages each file in the engine (`stageAttachment`) and stores the id the engine minted; **claims** the attempt, and calls `dispatch` with the dispatch id as the key. The claim is one conditional update, right before the call, that raises the attempt count only if the dispatch is still `intended` and at the attempt count read before staging, and, for a first send, unfenced, in a session with no unsettled Stop that is neither retired nor lost, and, for a first start, admitted by the turn budget as it stands then ([Concurrency](#2-the-server-holds-waiting-wakes)). A first steer is checked again in the same transaction: if the turn it was planned for ended while its files were staging, the engine would make it a turn of its own, outside the budget, so the dispatch is released instead and its wakes go through a start's admission. When the claim changes nothing, the dispatch was settled meanwhile (a Stop fenced it while its files were staging, say) and the engine is not called. A resend claims whatever the fence or the Stop: the key may already be in the engine, and only the recovery can learn its answer. A staging the engine did not answer, or a file the store no longer has, is tried again with the recovery's backoff, by whichever worker owns the send: the dispatcher for a first send, under the turn budget like any other, and the recovery for a resend. Each worker hands the sender its own claim to the send, and the sender checks it again inside the gate before anything else: a first attempt given back because the engine was unreachable makes the dispatch the dispatcher's again, so a recovery that read it while it was claimed leaves it alone; after five failures the dispatch fails, as `rejected` when it was never sent and as `unresolved` when it was. A staging refused because the engine is unreachable counts no failure: the dispatch waits for the engine. A send that fails unexpectedly counts against the same bounds and is never tried again at once: before the claim, as a staging failure, since nothing was sent; after it, as an indeterminate answer for the recovery ([Recovery](#3-a-dispatch-is-written-before-the-engine-is-called)), since the call may have reached the engine. A defect that repeats so ends visibly within its bound, and a Stop that waits on the dispatch is not held for a day. The dispatcher and the recovery read their candidate rows one by one, so a row that cannot be read is the only one held back. When counting the defect fails too, or the defect comes before the gate (a dispatch that cannot be read, say), one write that touches nothing but the deadline of a dispatch still `intended` puts it thirty seconds ahead, so even then it is never retried at once, and a broken dispatch stays deferred while the others go on. A send into a session that is gone settles at once, without waiting out a backoff. The adapter derives the engine's command id and message id from that key ([Engine: the adapter's interface](engine.md#the-adapters-interface)), so sending the same dispatch again is the same command. The staged ids are the one input that may change between sends: a file is staged again whenever its `usableUntil` has passed before a send, including a recovery, because the engine claims the files before it looks at the key; a copy a recovery does not use is removed by the engine. A retried staging after a lost reply leaves an unused copy the same way.

The engine's answer records **acceptance**. Its first disposition is stored and never changes:

| Disposition | Meaning | What the server does |
| --- | --- | --- |
| `started` | A new turn started | The turn is admitted when its `turn-started` arrives |
| `queued` | A turn the engine began while the start was on its way runs first; this message's turn waits behind it | The turn is admitted when its `turn-started` arrives, with this dispatch's audience, whatever the turn ahead of it was for |
| `steered` | The message was given to that turn | The dispatch waits for the steer to settle (see below) |
| `new-turn` | A steer arrived too late, or the provider can take no steer: the message became its own turn, possibly after the running one | The turn is admitted when its `turn-started` arrives |

A dispatch accepted through a recovery has no disposition: the engine does not say how a key it already had was applied. The events say where it went, as for any other.

**Delivery** is what the events say, not the disposition: a dispatch is delivered when `turn-started` arrives with the cause `dispatch` and its key, or, for a steer, when it settles as taken. A steer settles only after the turn it steered has ended, with one event right after that turn's `turn-finished`, decided by the engine's own state: `steer-requeued` (the engine queued it as a follow-up turn: the dispatch and its wakes move to that turn, which is admitted when it starts), `steer-dropped` (Stop ended the turn first: the dispatch is dropped, and the engine shows its own notice) or otherwise `steered` (taken: the dispatch finishes with that turn's outcome). `steered` is the engine's claim; on some provider paths it cannot prove the model read the message ([Engine](engine.md#the-adapters-interface)). Until it settles the dispatch is accepted and undecided, and no `undelivered` wake fires for it. A steer rides a turn it does not own: it finishes with that turn and never follows its continuation, which belongs to the dispatch that owns the turn.

Events about a key can arrive before the engine's answer does, after a lost reply. They prove it applied: the server records the dispatch as accepted, with no disposition, and applies them. `turn-finished` names its turn's cause as `turn-started` does, so a turn that ends without starting (cancelled from the engine's queue, or failed before its provider took it) still settles its dispatch by key, including a dispatch the server knows only through a recovery, which names no turn.

**Refusals.** Only two answers prove that the engine applied nothing, and only on a dispatch's first send, which they refuse before anything is sent:

- `SessionBusy`: the adapter already saw a turn in the session. It is a best-effort check; a turn that begins just after it gives `queued` instead. The adapter saw a turn the server has not applied yet, so the session gets a **busy deadline**: nothing is planned into it before the deadline passes, two seconds doubling with each refusal in a row up to thirty, or before its next event is applied, which clears the deadline and nudges the dispatcher. A deadline rather than a mark, so a turn whose last event committed before the refusal was recorded never strands the session.
- `SessionNotFound`: the adapter has no such session. The session is recorded **lost** ([Sessions](#sessions)).

Either one **releases** the dispatch: its wakes wait again, and its catch-up notes and held messages go back for the next envelope. `EngineUnavailable` proves the same and gives the attempt back.

`PermissionModeRefused` proves it too, on a first send or a recovery alike: the engine refuses to run a turn in the permission mode its session has, as the ceiling of an administrator's policy installed after the session was opened in that mode does, and keeps no receipt for the key, so neither this send nor an earlier one of the key was applied ([Engine: the adapter's interface](engine.md#the-adapters-interface)). In the bot's main session the dispatch is released, and in the same transaction the bot records the refusal as for a refused opening (**Every bot has a main session**, below): nothing is planned into the session until the bot's settings change or the engine is ready again, its conversation is told once, and the message waits as `pending`. Its wakes then go in a new dispatch, under a key of its own, so it is delivered once. In a side session, the routine's attempt fails as for a side session the engine refused to open ([Routines](#routines)).

`DispatchRejected` means the engine's reply named a refusal, so it applied nothing and the key is spent. The dispatch **fails** as `rejected`, and its wakes fail visibly: each shows, where it came from, that it did not reach the bot. They never return to pending on their own, because the same wakes would be refused the same way; `message.retry` sends an operator message again as new wakes, under a new key. An `ask` answer, like a new bot's `first-run` wake, has no message of its own, so its failure shows as a retryable `turn-failed` notice where it was for, written in the same transaction as the failure, whether the dispatch failed or the engine dropped the turn it was to start. Its class says why: `stopped` when a room's Stop dropped it, `engine-unavailable` when its send was never resolved, `unknown` otherwise. Whether such a notice offers a retry is one rule, read again from durable state after every change to its dispatch or that dispatch's wakes, and again when the retry is pressed: the dispatch failed or the engine dropped it, so the engine cannot still have the answer and never delivered it, and the answer's (or the opening's) wake failed and was not sent again. A key the engine accepts after all takes the retry away whichever arrives first, its reply or its events; the engine dropping it before its turn started gives the retry back; a delivery ends it. A notice for a turn that ran and failed is retried on its own terms ([The outcome](#5-the-outcome-closes-the-dispatch)).

**Catch-up notes and held messages** go back only when the engine certainly never applied the dispatch that consumed them: it was released, proved never sent, failed as `rejected`, or dropped by the engine. An `unresolved` dispatch keeps them: it may still land and deliver its envelope, and a note handed to the next envelope as well would be told twice. A routine run's note from before the bot's latest fresh start does not go back: it is dropped ([Sessions](#sessions)).

**Recovery.** When the server cannot tell whether a dispatch reached the engine (it crashed during the call, or the call failed with `EngineIndeterminate`), it recovers the dispatch with `redispatch`: the same key, envelope, delivery and files, with none of `dispatch`'s local checks, because the key may itself have started the turn that makes the session busy. A lost reply is never taken as "not applied", and a dispatch with no recorded attempt was never sent, which is the only other proof of that. A recovery that succeeds means accepted, with no disposition. One that answers `DispatchRejected` fails the dispatch as `rejected`, and one that answers `PermissionModeRefused` releases it as above. Anything else is tried again with backoff, doubling from two seconds to ten minutes; while the engine is unreachable the server waits until it is ready again, or 30 seconds, since the engine's status can trail it, and the wait counts no attempt. Three things end the recovery without an answer: ten indeterminate answers, the session being retired, lost or removed (a rotation, a fresh start, a deleted bot, a session the engine no longer has), or the dispatch being older than a day. A session lost after the engine accepted the dispatch, and before its turn ran, ends it the same way: no event will ever report the turn, so it fails as `unresolved` and keeps the engine's first answer. A recovery that fails unexpectedly counts as an indeterminate answer. The engine keeps its receipts for good, so the day is J3 Bots' own bound, matching how long the engine keeps a session's events. The dispatch then fails as `unresolved` and its wakes fail visibly, never re-queued.

**Late delivery is legal.** If a turn later names a failed dispatch's key, the engine had applied it after all: the dispatch moves on to `delivered` and its turn goes to the dispatch's audience, and its wakes and messages show as delivered. If the events show the engine holding it before its turn starts (a `turn-queued`, or a replacement that lists its turn waiting), it is `accepted` again, and its messages show as pending with no retry: a failed wake counts as failed only while its dispatch is `failed` or `dropped`, and a message's retry sends only such wakes, so nothing the engine may still deliver is sent twice. A message the operator retried meanwhile went again under a new key, by their choice. A Stop recorded over such a dispatch's work still covers it: the Stop fences it, so its landing reopens the Stop and the turn is stopped on sight ([Stop](#stop)), while the dispatch stays failed and is the recovery's no more. A dispatch moves to a replacement session only through retried wakes. The server never guesses, so a wake is never delivered twice by J3 Bots' own doing, and never silently lost.

### One gate per session

Every step that sends a session something runs through that session's **gate**: one serial lock per session in the server process. A dispatch, a recovery, a held-queue resume, a Stop round and a room archival's Stop each take the gate, read the state they need inside it, make their engine call and record the result in one transaction, and release it. They never hold it while they wait for events or back off. So a Stop recorded while a dispatch waits for the gate fences that dispatch before it is sent, a resume never runs between a Stop's commands, and two recoveries of one key never overlap. Different sessions do not share a gate. A Stop round records durably, inside the gate and before its call, that it was issued.

### The workers

Seven workers act on durable state: the **dispatcher** (pending wakes and every first send, also one whose files wait to be staged again), the **recovery** (every claimed send: dispatches sent at least once whose answer was lost), the **Stop runner**, the **responder** (the operator's answers to engine requests), the **resumer** of held queues, the **rotator** (main sessions to open, align or replace, and every retired session's archive, [Sessions](#sessions)) and the **routine runner** (routine runs and their side sessions, [Routines](#routines)). Each is a reconciler. A pass reads what is due from the database and does it; nothing it needs lives only in memory. A signal from whoever changed that state only shortens the wait before the next pass: a pass also runs at the earliest durable deadline it knows of (a recovery's backoff, a resume's or an answer's retry, a busy deadline, a routine run's next attempt), five seconds after a pass that left due work undone (a session not ready, a call that timed out), and once a minute otherwise. So a timeout, a readiness change or a lost signal never leaves work waiting for good, and a pass that changed nothing schedules nothing extra: signals are fired only when state changed. Passes of one worker run one at a time, also those the startup sequence runs. Outside the turn machinery, the **push worker** ([Notifications](#notifications)) is a reconciler in the same way; it sends nothing to the engine, so it never waits for the engine to be ready.

**Sessions are isolated.** A session that is lost, not yet known from its events, within a busy deadline, held by a Stop or not observable (its events cannot be applied, or a marker did not come in time) holds back only its own work: the pass skips it and goes on. Only the engine refusing a command (`EngineUnavailable`) ends a pass, since nothing else can be sent either; that worker then waits until the engine is ready again, or thirty seconds, since the engine's status can trail it. A catch-up (`synchronize`) that fails the same way is that session's alone: the adapter's catch-up of one stream failed or timed out, so the Stop runner and the resumer defer that session and go on.

**Each worker is supervised.** A defect in one item (a send, one session's Stop round, one answer, one resume) is logged and the pass goes on with the rest, and the item waits for a durable deadline. A send's defect counts against the dispatch's bounds, so it ends visibly; one the sender could not count is caught at the send itself, in the dispatcher and the recovery alike, and the pass looks again in thirty seconds. An answer or a resume, whose key makes every send of it one command, is sent again on the backoff of a lost reply, as long as its request is open or its hold is current. A session's Stop work waits thirty seconds, a deadline stored on its targets. A defect that escapes a pass is logged and the worker waits thirty seconds before its next pass. Every loop of the machinery (each of the five workers, the stall watcher, the engine status loop) is supervised on its own, the same way. A failure is never retried at once, and one loop's failure never stops another.

**Idempotent work retries for as long as it is due.** An answer to an engine request and a held queue's resume carry a key the engine applies once, so a lost reply is never final: each is sent again with the recovery's backoff, doubling up to ten minutes, its deadline stored with it, for as long as its request is open or its hold is the session's current one. A refusal is final, as for every keyed command: the engine keeps it for the key, so an answer it refused is never sent again ([Questions, approvals and secrets](#questions-approvals-and-secrets)). A dispatch is different: an unresolved one fails visibly at its bounds, because the operator must know that it may never arrive.

### 4. The turn is observed, and admitted

The adapter streams each session's events, and the server derives the bot's state from them: thinking, working, waiting on a request, blocked, idle. A working bot shows its newest step still running, since steps run in parallel. A running turn with no step, tool call, request or speech for ten minutes is shown as stalled, with when it last showed activity (`quietSince`), which a client counts the quiet from. Every state of a running turn carries the time the turn started, as the server recorded it, so a client's clock for it is the same after a reload or on another device: thinking and working always, and waiting while the request it waits on holds a running turn, from the start of that request's own turn, whatever runs beside it; an `ask` card the bot waits on after its turn ended carries none. A bot can run a turn in its main session and a routine's in a side session at once: its state is the main session's turn while one runs, since that is the one its conversation shows, else the newest routine's. Clients see that state live. The server opens a session's stream before it relies on it: the engine answers `synchronize` only on the streams open when it is called, and a stream counts as open from when it is subscribed ([Engine](engine.md#the-adapters-interface)), so a stream is started before anything waits for its marker. Nothing is planned or sent into a session before its state is known from a committed cursor, or from the first replacement once it is applied: until then the planner leaves its wakes pending, taking no slot, a send into it is skipped, and the event that makes it known nudges the dispatcher. Asking whether a session is known never opens its stream; the workers open it (`watch`) where they need it. Each event is applied and its cursor stored in one transaction, so a restart neither skips nor repeats one; once it commits the session is marked known before the change is published, so whoever sees the change finds the session ready. A wait for a marker is tied to its stream: it fails, to be retried, when the stream closes, and every `synchronize` has a deadline of ten seconds, shorter than the adapter's own ([Engine](engine.md#the-adapters-interface)), so a stalled stream defers only its session's work. A stream that ends is opened again with backoff, doubling up to a minute; until then the session is not known, and nothing opens it sooner. So is a stream that could not be opened, and one whose end could not be handled: what was subscribed is closed, and nothing is left looking open. Waiters on a stream fail only once its end was handled, so one that retries finds the session as that end left it. Once a session is recorded lost, or its archive by the engine is recorded, checked inside each event's transaction, its stream is no longer read: what it had buffered is never applied. An applied event nudges the dispatcher only when it can change whether the session is idle (a turn starting or finishing, a dispatch or steer settling, a replacement, a request opening or closing), when it ends a busy deadline, or when it makes the session known; it nudges the Stop runner only in the first case. An event the server cannot apply is not skipped: it is logged with its cause, shown once in the conversation as an `observation-failed` notice, and read again on each reopening. The notice is written in its own transaction and counts as shown only once it commits: one that cannot be written is logged, tried again the next time, and never keeps the stream from being opened again. Until an event of the session applies again, nothing is sent into it, because what the server knows of it is behind. A stream that ends with `SessionNotFound` records the session lost. A stream that resumes too late to replay starts with one replacement of the session's state, and the server reconciles against it by stable ids (turn, request, speech and dispatch key), so a turn, a speech or a resolution it already applied changes nothing when it comes again ([Engine](engine.md#the-adapters-interface)).

A session has at most one **admitted turn**: its running turn, once the provider took it, with its **audience**, where its speech goes (the bot's conversation, or one room). A turn caused by a dispatch is admitted when it starts, with the dispatch's audience; a `queued` start keeps its own audience even when the turn ahead of it was a room's. A turn the engine started to continue another after a usage limit reset is admitted with the audience of the turn it continues ([Continuations](#5-the-outcome-closes-the-dispatch)). A turn the engine started for background work that finished is admitted with the bot's own conversation as its audience.

What the bot *says* does not come from the event stream. It comes from the bot calling J3 Bots' `say` tool, which appends an entry to the audience of the turn the call came from and returns ([Bot tools](#bot-tools)). A `say` or `ask` that cannot be matched to a call of the session's running turn fails with a typed `TurnEnded` result, and nothing is published or recorded. A call to the engine's own `send_to_user` tool arrives as host speech and is delivered once per speech id, like a `say` without `done`, so a slip is not lost.

A `say` with `done: true` **closes the delivery**: the delivered dispatch that owns the turn has its wakes finished, and the operator sees the bot's reply as delivered. A steer riding the turn is not closed by it: it settles as the engine reports. It does not interrupt the run. The bot is expected to end its turn; if it keeps working, what it says next still reaches the same audience. The server never interrupts a run to end it, because an interrupt may drop the delivery of a delegated task's completion ([Engine](engine.md#behaviors-j3-bots-designs-around)).

The turn's final reply text is never published: the base prompt tells the bot it reaches nobody, and the bot may have used it for notes. If a `user` wake's turn ends without a `say` carrying `done: true`, a pending question or a background handoff, the server wakes the bot once more with an `undelivered` system wake. If that turn also delivers nothing, the conversation shows a notice with a retry action. Neither comes for work a Stop covers ([Stop](#stop)).

### 5. The outcome closes the dispatch

When the turn ends, the dispatch records how: completed, failed (with the engine's error class), interrupted, or waiting on the operator, and its wakes are finished. A failed routine wake is retried according to its routine's policy. An operator's turn that failed, or that something other than the operator's Stop interrupted (a provider, an engine restart), shows a `turn-failed` notice in the conversation with a retry action, and so does a new bot's opening turn; an interruption carries the class `unknown`. A turn that fails before it starts never delivered its dispatch, so its wakes fail as `rejected` and its messages show that they did not reach the bot. The dispatch keeps the outcome: a routine run's attempt that failed so, a provider's passing error say, is tried again, unlike one whose envelope the engine refused.

The adapter knows which turn delivers a dispatch because every engine run names the message that started it, and that message's id comes from the dispatch key; a steer's follow-up turn keeps the same message, and a run the engine restarted to take a steer keeps the message of its first attempt. A turn the engine started on its own closes no dispatch.

**Continuations.** A turn that fails at a usage limit may end with a pending continuation: the engine will resume it at the reset ([Engine](engine.md#the-adapters-interface)). Only the dispatch that owns the turn follows it. Its `turn-finished` then leaves the dispatch delivered rather than finished, with the outcome so far and the reset time recorded, and no `undelivered` wake fires. When the continuation turn starts, its cause names the turn it continues; the server follows that one link, moving the dispatch's turn and its audience to the new turn, so a chain of continuations is followed a link at a time. A continuation turn that ends before it started (it failed, or a Stop cancelled it while it waited) follows the link the same way, by its cause, as its end is applied: once the engine has a turn continuing another it sends no `continuation-dropped`, so nothing else would end that work. The dispatch finishes when a turn ends with no continuation pending, or when `continuation-dropped` arrives, with the last outcome; only then does an `undelivered` wake fire if nothing was delivered. A last turn that did not complete (it failed, was interrupted, or was cancelled before it started) gives a `turn-failed` notice instead, unless a Stop covers the work. A continuation cancelled before it started ran nothing, so its notice shows the outcome of the turn it was to continue, as when one is dropped. A pending continuation keeps the session busy for automated wakes, which wait for the reset anyway. An operator wake is still dispatched; the engine then drops the continuation, because it resumes only the session's latest turn. A Stop disarms it too. J3 Bots never snoozes a session: snoozing would only delay the continuation. The engine's continuation after its own restart is turned off, so a turn a restart cut short ends `interrupted` like any other.

### Stop

A Stop is a separate path, never a side effect of `done`, and a durable one: it is written down before the engine is called, and finished after a crash. It has a **scope**: `bot`, the operator's Stop of one bot, which ends all of its work; or `room`, recorded when the operator stops a room's work (`room.stop`), archives or deletes the room, or removes a member, which ends only work whose audience is that room. The server also records a Stop of its own that ends one turn, the one that asked for help in the bot's browser ([A Stop of one turn](#stop)).

1. **Record.** In one transaction the server writes the Stop under its command id with its **targets**: every session of the bot with a turn running, or a dispatch that may have been sent (`intended` with an attempt, `accepted`, `delivered`, or failed `unresolved`, whose key may still land, a turn waiting in the engine included), in the Stop's scope. A `bot` Stop also targets every live session of the bot that the engine has, for background work the server does not see, except one whose engine thread the server has already archived, which runs nothing more. A `room` Stop targets the room's turns and dispatches, and every session where background work one of the room's turns started may still be pending ([Rooms](#rooms)). Each target's first round gets an engine key derived from the Stop's command id, the session id and the round. The same transaction **fences** every dispatch in scope that has not been accepted yet, so it is never sent for delivery again, and cancels every wake in scope the server still holds; each shows as cancelled where it came from, except a teammate's urgent message, which waits on as a held one ([A Stop of the recipient](#teammate-messages)). A fenced dispatch that was never sent is released, its wakes cancelled. It marks every turn in scope still running as stopped, which covers that turn's work also when no dispatch began it ([What a Stop covers](#stop)). And it covers what those turns sent their teammates, and nothing else the bot sent: each such message no earlier Stop marked is marked with this one, an urgent one's wake still pending is cancelled unless it is the operator's Retry, and a held one not yet in an envelope is removed ([A Stop of the sender](#teammate-messages)).
2. **Settle the dispatches in flight.** A dispatch of the target session whose call may still be in flight is waited for, and so is every one whose reply was lost, fenced or not: confirmation needs the engine's answer for each. They belong to the recovery, which tries a fenced one at once and every one with its usual backoff and bounds, recovering it with its key to learn the answer: if the engine had applied it, the recovery applies nothing; if it had not, the recovery applies it, and the stop that follows ends it. The Stop waits for them in that session, and meanwhile the session's running turn keeps running: no round is sent before the recovery settles them. Either way nothing the bot was sent lands behind the Stop. A fenced dispatch that may have been sent never waits again: if it fails, refused or unresolved, its wakes are settled by the one rule below ([What a Stop covers](#stop)). Only a dispatch proved never sent gives its wakes back. A dispatch that failed `unresolved`, whose key may still land, is fenced too, without returning to the recovery: it waits for nothing, and its landing reopens the Stop (step 4).
3. **Stop each target.** A `room` round waits, unsent, while its session has work for another audience: a turn running, or a dispatch the engine took whose turn the events do not show ended: one starting, or running unseen. A dispatch the engine answered as `started` holds it from that answer, before any `turn-started` shows its turn. The operator's steer into a turn holds it until the engine settles the steer, which it does after that turn's end: taken, dropped or requeued. A dispatch whose turn the events have not shown start, and that the engine did not answer as started, does not count while that turn cannot start as far as the server sees: the room's own turn runs ahead of it, or the engine holds the queue; the room's Stop cancels it, and it fails as `stopped`, retryable. That view is brought up to the engine's report first (below), so it trails the engine only from that report to the engine's stop: a private turn queued behind the room's that starts then, when the room's turn ends meanwhile, is ended with the room's work, and its dispatch fails as `stopped`, retryable, the same outcome as the cancel. A steer the engine makes a `new-turn` while it holds the queue is **Assumed** not to start until the queue is resumed. While the round waits, the only send the dispatcher can make into the session is the operator's steer into the admitted turn ([A session with an unsettled Stop takes nothing](#stop)), and the engine can make that steer a turn of its own two ways. If the turn it was for already ended in the engine, the steer becomes a new turn (`new-turn`); if that turn ends without taking it, the engine requeues it as a follow-up turn (`steer-requeued`). Either turn can start while the round waits, and the round waits for it too, unless the engine holds the queue: a turn that fails holds it, so a steer requeued behind a failed turn cannot start, and the round goes and cancels it. The engine's stop ends the whole session, and a room's Stop does not end the operator's private turn or another room's while the server can see it. It does disarm a usage-limit continuation pending for private work in the session: that dispatch finishes with its last outcome and shows a `turn-failed` notice, retryable. That work's end nudges the runner. A `room` round is judged again inside the session's gate, right before it is issued, since every send into the session is claimed there: work that started meanwhile holds it. **Bound.** A turn of another audience the events show running holds the round for as long as it runs: it ends on its own. Work the server cannot see run holds it for at most two minutes (`ROOM_ROUND_HOLD_BOUND`): a dispatch the engine took whose turn no event shows, or a runnable turn the engine's report lists that no event told of. Such a run starts in seconds; one stuck in startup would otherwise hold the room's Stop for good. The bound counts from when such work alone first held the round, recorded on the round so it holds across a restart, and again from the next time once a turn of another audience was admitted, recorded in the transaction that admits it, so a turn that starts and ends between two passes of the runner counts too. A round past its bound goes as a bot Stop's would, logged, while the room still has work running or flagged there, and what it ends fails as `stopped`, retryable; with nothing of the room left, it settles with no round. Unless a turn of another audience the events show running holds it, a `room` round is judged in the gate on a report of the session's pending work and runnable turns that the runner asks the engine for in that pass, outside the gate, which also brings the events up to it; without one, also from an engine that cannot be reached, the round waits for a later pass, and only that session waits. Each runnable turn the report lists is attributed by the server's turns and the dispatches that name it (`engine_turn_id`), a dispatch for the room not admitted yet included: one that is not the room's holds the round, within the bound, as it may start or run with no event telling of it, unless a dispatch of another audience names it whose turn cannot start as above, which the round cancels, so an engine-queued run no dispatch names, such as a background command's wake, whose work may be the room's, holds it also behind a held queue; otherwise the round goes while the room's work runs or the report lists a runnable turn of the room's, which may be active, or the background work its turns started (the engine lists no background work while a run is active), and settles the target with no round when it lists neither. A session the engine no longer has is lost meanwhile. Its fences stay, so a fenced key that lands after all reopens it. The engine can still start a turn on its own, a harness's wake or a continuation, between that check and the engine's stop, and the stop ends it too ([0013](../decisions/0013-background-work-belongs-to-the-turn-that-started-it.md)). The round is **issued** first: recorded, inside the session's gate, before its commands are sent. Then `stop` with the round's key ends the running turn and the delegated work the engine can reach, including background work a turn left running after it ended, cancels every turn waiting in the engine, drops untaken steers and disarms a pending continuation. The adapter sends the engine's own stop to every target, also one with no running turn. The adapter derives each engine command from the key, so a retried round, or one resumed after a crash, sends the same commands. Its success only acknowledges the commands, and is recorded as the round's acknowledgment. Each command is resolved by its key, as a dispatch is: a call that gets no answer, or an error reply that proves nothing, leaves the round issued and unacknowledged, and the runner sends it again with the same key on a later pass, with no other signal needed; the engine's receipt for the key answers it. When the receipt shows the engine refused the round while something it targets can still run, the round's key is spent: the round is marked refused and the target gets a fresh round, with a new key, due after the recovery's backoff, doubling with each round the engine refused since it last acknowledged one, up to ten minutes. No fresh round follows a target that settled meanwhile: every writer of a round checks, in the transaction that writes it, that the target is unsettled and its session not lost, so a refusal the runner hears after the session's loss committed is recorded on its round and opens nothing. Each round waits only on its own deadline: another target's round that is due, such as the operator's new Stop, goes out meanwhile. A refusal while nothing it targets can still run is moot, and counts as acknowledged. A refusal while a tool whose persistence the adapter could not decide is live is not: a refused stop interrupted nothing, so the tool may still run ([Engine](engine.md#the-adapters-interface)).
4. **Confirm from the events.** One rule governs every target: it settles only when the engine's own state shows nothing the Stop targeted can still run, no run waiting, preparing, starting or running and no background work pending that the engine's stop ends (`stoppable`); and as long as it is unsettled, something keeps acting on it. Its latest round is always in a state a durable deadline or an event moves on: not yet sent, and sent once due (step 3); being sent, and resolved by its key; refused, and followed by a fresh round after a backoff; acknowledged, and watched until the target settles, with a fresh round once the round's grace passes while the engine still shows work it targets. Waiting on a round the engine refused or ignored is never an option. The acknowledgment of step 3 only says the engine took the commands; their effects can lag it, and the engine can lose them without saying so (an interrupt it could not plan, a run whose provider never starts). After it, the server synchronizes the session, which **observes** the round: every event the engine had by then is applied. A marker that reports what no event has told of leaves the round unobserved, and the runner synchronizes again a few seconds later ([Engine](engine.md#the-adapters-interface)): background work the engine still counts as pending, which in a session whose last turn already ended the engine's stop interrupts only after it answered, and which an interrupt the engine failed to plan leaves running though the stop was acknowledged (a tool whose persistence the adapter could not read from the stream counts as the engine's own projection of its pending work shows it, and as pending while that cannot say); and a run the engine can still run: one it is starting, created after the round's commands or held by a provider that never starts it, or one it queued on its own after the round's cancels, such as a scheduled message, which no dispatch of the server's names and no event will start while the Stop holds the queue. **Grace.** An acknowledged round gives the engine 30 seconds to show its effect, doubling with each round of the target the engine acknowledged, up to ten minutes. When a synchronization after that still shows work the Stop targets (a run waiting, preparing, starting or running, a dispatch waiting in the engine's queue, a continuation pending, background work pending), the target gets one fresh round, due at once, whatever the events did or did not announce. The deadline is the round's own, so it holds across a restart. A Stop the engine can never end therefore costs a bounded amount: one round per grace, at most one every ten minutes once the grace has reached its cap, and a synchronization of the session every five seconds. A target is stopped when its latest round is observed and the session's events then show nothing left: no running turn, no dispatch the engine may still start, no continuation pending. Background work the engine's stop does not reach, which a provider session the engine kept from before a fresh-context start still runs, is not waited on: no round would end it, and the session's retirement does ([Engine](engine.md#the-adapters-interface)). This holds for a `room` Stop too: the engine's stop ends the whole session, its background work included, so a session a `room` Stop targets confirms only once the engine shows no background work pending there that its stop ends, whoever started it.

    Such a Stop settles by no deadline of its own: it stays unsettled for as long as the engine counts the work as pending, and the session takes nothing meanwhile, while the server keeps sending a round after each grace. That is the engine's own account, and the engine keeps acting on it: an interrupt the provider does not confirm leaves the turn open for the operator to force-stop it in the engine's console, and a command queued behind it waits for the turn to end (**Read** at `db51b67`: `ClaudeAdapterV2.ts`, L13831-13845; `Orchestrator.ts`, L14122-14130). The operator can also stop the bot again, which records a fresh round for every live session of the bot ([Record](#stop)) and goes out at once, whatever the backoff of earlier rounds. The Stop runner confirms only from such an observation, never from one event as it is applied, because the next event may start a turn the engine had waiting; each event that is not itself a marker makes it observe again. A turn whose start is applied once the latest round was issued, also one that started while the round's commands were on their way, opens a new round, since the commands may have missed it; so does a fenced dispatch the engine applies after its target was confirmed, which shows as a turn with its key: it is stopped on sight. A dispatch the events first show waiting in the engine's queue (a `turn-queued`, or a replacement that lists its turn waiting) opens one too, as it is accepted: its key may have landed after the round's cancels, held in the queue the Stop left, where no turn would start to reopen the Stop. Only that first sight does; a replacement that lists the turn again finds the dispatch already accepted. The Stop is finished when every target is stopped.

**A session with an unsettled Stop takes nothing.** From the moment its target is recorded until it is confirmed stopped, the server sends that session no first send (only the recoveries of step 2) and resumes no held queue in it. One send is let through: the operator's steer into the admitted turn while every unsettled target of the session is a `room` Stop for another room that has issued no round there yet. That Stop waits for the turn anyway (step 3), and the steer keeps it waiting, so the operator's word reaches the turn they are talking to; the planner, the send and its claim read the rule alike. No first send of a new turn goes: what that steer becomes when its turn does not take it (step 3) is the only new turn the server's sends can give the session meanwhile. The engine's Stop is several commands, and a message arriving between them could restart a turn the Stop is ending ([Engine](engine.md#behaviors-j3-bots-designs-around)). The rule is the database's, so it holds across a restart: each round records when it was issued, acknowledged and observed, and the Stop runner's first pass at start, once every session's events are followed again, sends the rounds that were never acknowledged and confirms only from an observation made after an acknowledgment. Once a target is confirmed, what it held back is nudged: the dispatcher, the recovery and the resumer.

**What a Stop covers.** One rule decides whether work is the operator's to have stopped: a Stop of the bot, or of the room the work was for, recorded after the dispatch that began the work was written. The order is exact, not a time: every dispatch has a sequence number, higher than any written before it and never reused, and a Stop records the highest one when it is recorded. Work is covered when its dispatch's number is at or below that mark. SQLite serializes writes, so a dispatch committed after the Stop is always above it, even in the same millisecond or after the clock stepped back. Whether that Stop has settled does not matter: nothing is planned into its sessions while it is unsettled, so work that began after it was planned after it, as new intent. Work it covers starts nothing new of its own accord: a turn that ends, even on its own before the interrupt lands, gets no `undelivered` wake and no notice. A turn the engine started on its own has no such dispatch. One that continues an earlier turn of its session (a usage limit's continuation, or a delegated task's completion that names the turn that delegated it) is that turn's work: a Stop that covers any turn of its chain, or marked one stopped, covers it. One that names none, such as a harness's own wake, is covered by a Stop recorded while it ran, and not by one recorded before it began. The rule applies wherever work, not the operator, would create a wake, also a teammate's: a message to a teammate is its sender's work, so none is sent from work a Stop covers. Once sent, it is that work's result: only a Stop that reaches its sending turn while the turn runs ends what it has not delivered ([A Stop of the sender](#teammate-messages)). Such a wake also needs a place to go, so a room archived or deleted meanwhile gets none. An operator's own wake after a Stop is never covered: it is new intent.

The same rule settles every dispatch that will not run to its end, read in the transaction that settles it, so a Stop recorded or a room archived meanwhile counts:

| The dispatch | Covered by a Stop | Not covered |
| --- | --- | --- |
| Never sent (released) | Wakes cancelled | Wakes pending again |
| Dropped by the engine (a waiting turn cancelled, a starting turn interrupted, a steer dropped) | Wakes cancelled | Wakes failed as `stopped` |
| Failed (`rejected`, `unresolved`, its session lost) | Wakes cancelled | Wakes failed with that reason |

A notice follows from the outcome: cancelled wakes get none, and failed ones show where they came from, retryable. The events close the rest: the running turn ends interrupted, a waiting turn ends cancelled and its dispatch is dropped, a dropped steer drops its dispatch. The engine's Stop ends a whole session. A `room` Stop waits for another audience's turn to end (step 3), but still reaches private work waiting in the engine behind the room's turn, and private background work pending in the session, which it does not cover: a private dispatch it fenced before sending is released, its wakes pending again, and one the Stop drops fails as `stopped`, visibly and retryable, because the operator did not stop it, also one whose recovery had given up and that the engine took late: its wakes fail again, as `stopped`, and an answer keeps the notice it already shows, which now says so. So does work a Stop sent from the engine's own console drops: the server recorded no Stop. Work for the room, and all of a bot's work under a later `bot` Stop, is covered. A room's dispatch that was never sent is fenced and cancelled even when no session needs the engine's Stop. Background work the engine could not reach may still wake the bot later, as a background turn.

**A Stop of one turn.** Once a bot's request for help in its browser is in ([Help in the browser](#help-in-the-browser)), the server records a Stop that names the turn that asked (`stops.engine_turn_id`), in the same transaction as the card, so the bot can do nothing more in the browser until the answer wakes it in a turn of its own. Its `scope` and `room_id` are the turn's audience, and it targets only that turn's session. Its round is judged as a `room` round is (step 3), with the turn and the dispatch that names it as its own work in place of the room's: it waits while other work runs in the session, within the same bound, and settles unsent when the turn already ended. The same transaction fences the session's dispatches not yet accepted, as any Stop does. It is not the operator's: it covers no work, so a wake an expiry of the card records, which continues that work, still goes; it cancels no wake, and marks no turn stopped; the turn's interrupted end shows no `turn-failed` notice and gets no `undelivered` wake, since the card ended its delivery; and an operator's steer is held by it, as a `room` Stop that issued a round holds one. It holds the session like any unsettled Stop, so the answer's wake waits for the stop to be confirmed and starts a fresh turn.

**Held queues.** The adapter reports each hold of a session's engine queue as a `queue-held` event, with the turns waiting behind it. Applying it only stores the hold's cursor on the session; the resumer, a worker like the others, resumes it with `resumeQueue` naming that cursor, once: it stores the cursor of the hold it last resumed, and a hold equal to it is not resumed again. Before a resume it synchronizes the session, so a replacement that shows the queue no longer held, or a hold replayed from before, is applied first, and it then reads the hold again inside the session's gate. A replacement that shows the queue not held clears a hold recorded before. A resume whose reply was lost, or that failed unexpectedly, is sent again for the same hold with backoff, doubling up to ten minutes, for as long as that hold is the session's current one ([The workers](#the-workers)); a resume's result is recorded only if the hold it answered is still current, so a newer hold is never taken as resumed. Each session's resume runs on its own: one that fails never holds up another's. It never resumes while a Stop of the session is unsettled; the hold is resumed once the Stop is confirmed, if turns still wait. Nor does it resume a hold of a retired or lost session, whose queue holds nothing the bot waits for, or of one not yet brought to its bot's settings (**Settings alignment**, in [Sessions](#sessions)), whose alignment nudges it; it reads that again in the gate, so a session retired or changed meanwhile is left alone. The engine refuses a resume on an archived session or at a usage limit, which leaves the queue to the engine's own rules.

## Questions, approvals and secrets

Two kinds of card wait on the operator, with separate lifecycles. A third, a bot's request for help in its browser, has its own ([Help in the browser](#help-in-the-browser)).

**A bot's `ask`** is a J3 Bots question. The card stores the wake it came from and the audience of the turn that asked: the conversation, or the room. The bot ends its turn after asking. The card does not expire. Answering or dismissing it closes the card and creates a `user` wake carrying the answer in the same transaction, with the stored audience; that wake's turn delivers there. An answer is never steered into a running turn and never shares an envelope with a steer: one that arrives before the turn that asked has ended waits for it, and then starts the next turn. The answer's envelope is defined in [Prompt architecture](../prompts/architecture.md#wake-envelopes).

**The engine's requests** belong to a running turn: an approval, a question asked through the harness's own tool, or a secret request. The card stores the session, the engine's request id and the turn. Its card goes to the bot's conversation, also during a room turn, because the operator answers for their bot there. While the request is open, the engine can report a fuller record of it (`request-updated`, such as an approval that becomes exact once its file change is fetched), and a replacement lists it as it then shows: the card shows that record in place and keeps its status, so an answer already recorded is the one sent. "Allow for session" is taken only while the card offers a grant (`sessionGrant`). An engine question takes a choice or a typed answer, not both: the engine receives a typed answer alone, so an answer with both is refused (`Invalid("answer")`) rather than shown with a choice the turn never got. An `ask` question takes both. An engine question takes no dismissal: the engine refuses one for every question a harness asks while its turn waits ([Engine](engine.md#the-adapters-interface)), so `dismiss` is refused (`Invalid("not-dismissible")`), nothing is recorded, and the card stays open. The clients offer Dismiss only on an `ask` question. The turn goes on once the question is answered, or is stopped. Answering it records the answer durably and then sends it to the engine for that turn, keyed by the card, so the answer is applied once however often it is sent, and the turn continues. A card takes one answer: a second command finds it closed. The responder sends each answer the engine has not taken; one whose reply was lost, or whose send failed unexpectedly, is sent again with backoff, doubling up to ten minutes, for as long as its request is open ([The workers](#the-workers)). An answer the engine refuses while its request stays open (`AnswerRejected`) is final: the engine keeps the refusal for the answer's key, so the answer is never sent again. The server logs it, closes the request on its side, and closes the card as `refused`, which tells the operator that the bot could not take the answer and to stop the bot and ask again in a message. The turn waits until it is stopped or ends. Each answer is sent on its own: one that fails never holds up the next. When the turn ends, every request still open on it expires, and its card shows that it expired. An engine question too large for a card (`unsupported-question`: more than four questions, or more than six options to one) is shown as a question card that says so, with no options and no answer: the operator stops the turn, and can ask the bot to put the question in a message. The server never shows part of a question.

**A secret request** comes from a bot calling the engine's `request_secret` tool. Its card shows the label, the reason, an optional link and a placeholder, never a value. The operator's answer travels in its own request (`secret.provide`), which hands the value straight to the engine. The value never enters an entry, a change, a log or a command receipt. The card records only that a value was provided, or declined, or that the request expired, from the request's resolution. `secret.provide` succeeds only when this call's own answer was the one the engine took. It has no receipt, so after a lost reply a retry may find the request closed: the server synchronizes the session and fails with `Conflict("card-closed")`, because the closing answer may have been another device's, or the request expired. A closed card is never reported as success; the card itself shows how it closed. The server takes one submission per card at a time, and so does the adapter per request, so a second device's submission waits for the first and then finds the card closed. Before calling the engine, the server writes a durable marker on the card that a submission is in flight, naming that submission and holding no value, and clears it on a definite answer; a cleanup removes only the marker of its own submission, so it never erases a newer one. A marker left by `EngineIndeterminate`, or found at start after a crash, means the outcome is unknown: the server synchronizes the session at start, and before it sends the next submission for that card. A request that is closed then shows how it closed; one still open takes a value again, and a submission that lands late only makes the next one find the card closed.

## The vault

The vault keeps what the operator wants kept secret on the server: the website logins they save (**credentials**), and what a connector needs to reach its service (**connector secrets**). It is a SQLite database of its own, `<J3_HOME>/vault/vault.sqlite`, apart from `j3.sqlite`. The key that opens it comes only from the operator's master password and lives only in the server's memory ([decision 0029](../decisions/0029-the-vault-key-comes-from-a-master-password-held-in-memory.md)).

**Keys.** The master password is 8 to 1,024 characters, normalized to NFC. scrypt (N = 2^16, r = 8, p = 1, with a random 16-byte salt) derives a key-encryption key from it. That key wraps a random 256-bit data key with AES-256-GCM. The data key seals every value with AES-256-GCM and a random 96-bit nonce. The value's record id and field name are its associated data, so a sealed value copied to another record or field does not open. The keyring row holds the scrypt parameters, the salt and the wrapped data key. Nothing else derived from the password is stored: a wrong password is detected because the wrapped key fails GCM's check. Changing the password wraps the same data key again under a new salt and rewrites no record. At these parameters scrypt takes 64 MiB and about 0.7 s on a Raspberry Pi 4 (**Verified**, Node 24, against 1.25 s for N = 2^17). That cost is paid once per unlock, and again by every guess. The parameters are read back from the file, so they are checked before scrypt runs: N must be a power of two from 2^14 to 2^20, r from 1 to 32 and p from 1 to 16, using at most 256 MiB. Parameters outside that range are logged with their values and refused with `Conflict("vault-damaged")`, without counting a wrong password. Every buffer that holds a key or an opened value is zeroed once it is used, also when the request fails or is interrupted. An interrupted unlock waits for scrypt to finish, then zeroes the key it gave.

**States.** The vault has four states:

- `uninitialized`: no password exists yet.
- `locked`.
- `unlocked`.
- `newer`: the file records a migration this release does not know, because a newer release wrote it. The server leaves the file as it is, starts anyway, and refuses every vault request with `Conflict("vault-newer")`.

A value that does not open under the data key, or opens but does not decode as what its field holds, means the file was changed or damaged. The request fails with `Conflict("vault-damaged")`, and the server logs an error naming the record and the field, never the value or the decoder's message, which could quote it. Clients show it as damage to restore from a backup, never as a server without a vault.

The vault's migrations are forward only and numbered apart from the database's. The vault starts locked after every server start, including one after an update. Any paired client can unlock it, and the key then stays in memory until a client presses Lock now or the server stops; it is zeroed at either. Nothing locks the vault on a timer. `vault.status` streams the state to every client, with a revision that changes with the saved logins and, while unlocking waits, the time it waits until.

**Unlocking waits.** Five wrong passwords in a row cost nothing more than scrypt's time. Each one after that makes unlocking wait: 30 seconds after the sixth, doubling with each further wrong password, up to an hour. A refused attempt is checked before scrypt runs. The vault's file keeps the count, the last wrong password's time and the time unlocking waits until, so a restart neither resets the count nor ends a wait. The right password resets the count, and so does a day with no wrong one. Each wrong password is logged as a warning with the count, never with the text.

**Credentials.** A credential holds:

- a name;
- the sites it is for: up to 10 origins;
- a user name;
- a password;
- optionally, a one-time-code key. This is TOTP (RFC 6238) over HOTP (RFC 4226), read from a base32 key or an `otpauth://` address, with SHA-1, SHA-256 or SHA-512, 6 to 8 digits and a period of 15 to 120 seconds. It is computed with `node:crypto` and adds no dependency.

Every one of these values is sealed, the name and the sites included. In the clear, the file holds only:

- record ids and kinds;
- creation and change times;
- the ids of the bots allowed to use each login;
- when each value was last shown, which field it was, and on which device.

`vault.list` returns the logins with none of their values. `vault.reveal` returns one value to the client that asked, and in the same step records the time, the device and the field; the login shows this as when it was last shown. `vault.totpPreview` returns the current code and until when it holds. `allowedBots` records which bots may use a login, none by default. A bot never reads one: the server types it into the bot's tab for it ([Filling a login](#filling-a-login)).

**The save-login card.** A bot that meets a website login its operator wants kept calls `request_credential`, with the page's origin and a note in its own words. The call puts a save-login card (`credential-request`) in the bot's own conversation, also during a room turn, since only the operator types into it. The bot gets back only that the card is shown. The operator types the login into the card. The client sends it to `vault.save` with the card's id. The server saves the login in the vault, then marks the card as saved, with the login's id and name. The vault is a separate database, so the two steps are not one transaction. The login is saved first, so a retry after a crash between them finds the login saved and still marks the card. `vault.save` carries the id the client chose for the login, so a retry after a lost reply adds nothing. A card that was closed in another way stays closed, and the login is saved anyway, since the operator typed it. A dismissal (`card.answer` with `dismiss`) closes the card. Neither a save nor a dismissal wakes the bot. While the vault is locked or has no password, the card offers unlock or setup in place. A card with any other answer is refused with `Invalid("answer")`.

**Connector secrets.** A connector's secret is one record, `connector:<id>`, with six sealed fields:

- `address`: the full URL of a remote connector, as the operator typed it or a gallery entry's form filled it in, which may carry a key in its path or query; empty for a command;
- `oauth`: the OAuth client (issuer, whether it was registered dynamically or by the operator, client id, optional client secret, how it authenticates, redirect URIs) and its tokens (access token, optional refresh token, expiry, scopes, resource);
- `headers`: header values;
- `command`: a started server's program and its arguments, which can carry a key; empty for a remote connector. What runs is read from here, never from the program the connector's row shows;
- `env`: environment values;
- `formSecrets`: the value of each secret field of a gallery entry's form, by the field's key. The address and headers hold them rendered (the key in `Bearer {key}`, or in a segment of the path); these are never sent as they are, only taken out of what the connector's server says and kept out of a sign-in's address.

In the server these are typed records: every token, secret and value is a redacted type. Connectors read and write them through `Vault.connectorSecrets` (`get`, `put` of the whole secret, `remove`). That service is not reachable over RPC, and nothing it does changes the revision clients list logins by. **The master password locks connectors too.** While the vault is locked, every one of these calls fails with `Conflict("vault-locked")`. A connector reports that as its own state, "vault locked", and makes no call to its service until a client unlocks the vault; the status stream says when that happens. After a server restart, every connector waits for that unlock.

**What carries a value.** Values travel as redacted types from the client to the vault and back, both in the contract and in the server, and are decoded as redacted types at the RPC boundary. The client gets a value only from `vault.reveal` and `vault.totpPreview`. No value reaches an entry, a change, a command receipt, a log line, an error or a tool result. None of the vault's requests takes a command id, so no receipt keeps one: `vault.save` is made safe to repeat by the login id it carries instead. A test drives every vault request over the socket and checks that no value appears in any log, error or answer except the one that reveals it.

**Backups.** No update snapshot copies the vault, and no rollback puts an older one back ([decision 0016](../decisions/0016-an-update-keeps-a-snapshot-to-roll-back-to.md)). A rollback to a release that predates the vault leaves the file in place, and a later update finds it as it was. A release that finds the vault `newer` leaves it alone. A copy of the file is useless without the master password, and so is the operator's data if the password is lost. Exporting the vault re-encrypted under a password of the export's own is planned with the operator's export ([#154](https://github.com/JPSAUD501/j3-bots/issues/154)).

## Filling a login

A bot signs in to a site with a saved login without being handed its values: it asks, and the server types them into the bot's browser tab while it holds the tab ([decision 0037](../decisions/0037-the-server-types-a-saved-login-into-the-bots-tab.md)). There is no confirmation for each fill: the operator decides ahead of time, per bot and per login.

**Who may.** A bot may fill a login only when all of these hold:

- its **vault access** is on (`bots.vault`, the `vault` of `bot.update`, off by default). It is a server switch, not a session setting: it is read at each call, so a change takes effect at once and moves no session's settings count;
- its **browser** is on (`bots.browser`), since the fill uses the bot's tab ([The bot's browser](#the-bots-browser));
- the login allows the bot (`allowedBots`).

Either switch off gives `no-access`, for `list_credentials` too.

**What the bot sees.** Two `j3` tools, whose answers are fixed shapes that carry no value:

- `list_credentials` answers with the name and origins of every login that allows the bot, while its vault access is on and the vault unlocked. A vault with no password lists none. Otherwise it answers `locked`, or `refused` with `no-access` or `unavailable`.
- `fill_credential` takes the login's name, the field (`username`, `password` or `totp`) and, optionally, `submit`. It answers `filled` with whether Enter was pressed, `refused` with a reason, or `locked`. The reasons are `FillRefusal` in the contract.

**The fill.** The bot first clicks the field, with the engine's browser tools, so that the page's focus is in it. Then:

1. **The call.** The request is matched to the engine's record of a `fill_credential` call, open in the caller's running turn with the same arguments, and pinned to it in `tool_calls`, as a turn tool's call is ([Bot tools](#bot-tools), "Matching a call to its turn"), but in a transaction of its own: the fill holds a tab for seconds and runs after it. A request no call of the turn matches, from a client that is not the bot's harness or after the turn ended, is refused by the bridge before anything is read, as for a turn tool. The pin carries the turn the refusals below count in, and later the fill's outcome, which a forward retried under the same request id gets back. Past this point, one fill runs at a time on the whole server.
2. **The bot and the login.** The bot's switches and the logins that allow it under that name are read. None gives `unknown-login`.
3. **The tab.** The fill acts on the bot's front tab: the tab of the calling session that most recently opened or navigated ([The bot's browser](#the-bots-browser)). A session with no tab gives `no-tab`, and a tab a paired device holds gives `held`.
4. **Take it.** The server opens an engine viewer of its own on the tab and takes it, as a device would. From then until it closes the viewer, the bot's browser actions on the tab fail with the engine's `humanControl` ([Engine: the bot's browser](engine.md#the-bots-browser)). The engine must say the server holds it within 5 s; when another viewer holds it, `held`.
5. **Read where the tab is.** Only now, so the bot can no longer move it, the server reads the tab's committed address from the engine (`BrowserBridge.readTab`), not from anything the bot said. A page still loading gives `loading`; a blank or failed one, or an address that is not `http:` or `https:` gives `origin`. That includes a `blob:` page, whose origin is the address inside it but whose content is whatever made it. Plain `http:` on a host other than `localhost`, `127.0.0.0/8` or `[::1]` gives `insecure`.
6. **Match the origin.** The bot's switches and its logins are read again, as they are now: the operator may have turned one off while the take waited. The page's origin, as the URL parser writes it (scheme, ASCII host, so a lookalike name stays in punycode, and a port other than the default), must equal one of the origins of an allowed login of that name exactly. No domain or suffix match: `https://example.com` does not cover `https://accounts.example.com`. No match gives `origin`; two logins of that name matching gives `ambiguous`.
7. **Open the value.** `Vault.fillValue` opens the user name or password, or computes the current one-time code from the login's TOTP key (RFC 6238), and answers it with the login as it was when it opened it, both read under the vault's lock. The fill refuses unless that login still allows the bot and is for the page's origin, so a change to the login made meanwhile cannot pair a new value with the origins it had before. It records no reveal, since no device saw it. A login without that value gives `no-value`.
8. **Read again, then type.** The server reads the tab once more and refuses with `navigated` unless it is still loaded at the same address. It reads the bot's switches and the login's bots once more, and checks that the pinned call is still open in the session's running admitted turn: a turn the operator stopped while this fill waited for another gives `stopped`. It refuses unless the server still holds the tab. Then it types the value with the engine's `text` input (Chromium's `Input.insertText`), where the page's focus is.
9. **Submit.** With `submit`, it presses Enter. After a password it always does, `submit` or not, so the bot does not get the tab back with a filled password field on the page (step 11 says when it still can).
10. **Wait for the engine to type.** The engine runs a holder's input one action at a time, in order, and a release drops what is still waiting ([Engine: the bot's browser](engine.md#the-bots-browser)). So the server sends a `probe` after its input and waits up to 5 s for the answer, which the engine gives from the same line once the input before it ran. No answer gives `unavailable`, with a warning in the log: the value may then be in the field.
11. **Clear a password on a page that stays.** After a password, the server reads the tab every 100 ms for up to 6 s. The page counts as gone only when the tab closes, goes blank or fails, or loads another address after it was seen loading. Anything else counts as staying: an address that changes while the page stays loaded (a page that shows an error with `history.pushState`), loading the same address again (a sign-in that failed and shows the form again, or a submission answered with no new document), and a sign-in still loading when the wait ends. If it stays, the server deletes what it typed with one Backspace per character where the focus is, then waits for the engine again as in step 10.
12. **Give it back.** Closing the viewer gives the tab back to the bot, whose call then returns.

The viewer is released when the fill ends however it ends, refused, failed or interrupted, so a tab is never left held. A fill runs in the server's scope, not the call's: a bridge that gives up on a forward does not cut it short between typing and giving the tab back, and the forward's retry under the same request id gets the same answer.

**A refusal is final for the turn.** Once a fill was refused on a tab, every other fill the same session asks for on that tab in the same turn, the one its call was pinned to, is refused with `refused-before`, without taking the tab. This keeps a bot that a page talked into the wrong fill from trying again until something works. A locked vault, a browser that did not answer, a person holding the tab and a stopped turn are not refusals of the page, and do not count.

**What is kept.** Each fill, typed or not, is a step of the bot's running turn in its work fold: tool `login`, the login's name and id, the field, the page's origin as checked, and the outcome (`CredentialFill` in the contract). A fill outside a running turn is not recorded there. The server's log gets one line per fill with the bot, the login's id, the field and the outcome. No value reaches a step, an entry, a log line, a tool result or an error. A test drives `list_credentials` and three fills through the bot tools and checks every step, answer, conversation entry and captured log line for the values and the one-time code.

**Reading the value back.** The fill keeps the value from the bot's tools; it does not keep it from the page, and every bot keeps the engine's `preview_evaluate`, so a bot can read a value it filled back with a script. The owner accepted that to keep page scripts. What the server cannot rule out, and what stands against it, is in [Security: filling a login](security.md#filling-a-login).

## Attachments

Files cross the server in both directions as attachments. Bytes and names are stored apart: a **blob** is the bytes, stored once under `<J3_HOME>/attachments` by their SHA-256; an **attachment** is a name and a media type over a blob. The same bytes sent twice, or under two names, are one blob and two attachments.

- A client uploads a file with `POST /attachments` before sending the message that carries it, and gets its id. The server puts its name and media type in the form the engine's upload takes (`normalizeAttachmentMetadata`: the name trimmed, the media type lowercased without parameters, at most 100 characters) and stores that, so a staging never fails on metadata. An empty file, a blank name or an unusable media type is refused; each file is limited to 25 MiB. `message.send` names up to ten, and the server checks them against the engine's limits before it writes anything: inline images (GIF, JPEG, PNG, WebP) at most 10 MiB each and 80 MiB together. It checks the message's length as the bot would read it the same way. `message.send` may also say where the operator placed each file in the text (`attachmentOffsets`: one UTF-16 offset per file, never decreasing, none inside a character); offsets that do not fit the text and the files are refused with `Invalid("attachment")`, and the message entry keeps them for every client to draw. The wake envelope writes each file there ([Wake envelopes](../prompts/architecture.md#wake-envelopes)). Coalesced wakes are checked again together ([coalescing](#2-the-server-holds-waiting-wakes)).
- The dispatch lists its files in order. Before its first send, each is staged in the engine, which mints its own id for it; the server keeps that id with the dispatch, so a retry sends the same staged file. A file is staged again whenever its `usableUntil` has passed before a send, including a recovery, because the engine claims the files before it looks at the key; a copy a recovery does not use is removed by the engine.
- A file a bot attaches to `say` is copied from its workspace into the same store, so the operator's devices can open it after the bot has changed or removed its copy. Paths outside the workspace, links that lead outside it and URLs are refused: the server never fetches a file for a bot. The workspace is its real path as the server recorded it when it first provisioned the folder, before the bot's first turn (`workspace_root`), never resolved again, so a link the bot puts in the folder's place leads outside it. The path is resolved and checked, then opened without following a link at its name and without waiting on a FIFO, and the check that counts is made on the open descriptor, since the bot can swap a folder on the way for a link between the check and the open: on Linux by the name the kernel gives the descriptor's file (`/proc/self/fd`), elsewhere by matching the descriptor's file to what the path resolves to again, which narrows the swap to one made and undone between two reads. This containment is a guardrail, not a security boundary: the bot runs as the same user ([Security](security.md)). Only a regular file is read, and at most `MAX_ATTACHMENT_SIZE` bytes of it, the limit of an upload: a larger file is refused once the read passes the limit. The files of one `say` together take at most 25 MiB (`MAX_SAY_ATTACHMENTS_SIZE`): the operator's upload path has no total per message, so a `say` takes one upload's worth, and each file is read only up to what is left of it, so a `say` past the total is refused while it is read and never buffers more. Every file is checked, its name included, before any is stored. The files are stored in the transaction that admits the `say` and publishes its message, so a refused `say` stores none of them; bytes written for a transaction that rolled back are removed before the store's lock is released. Writing a blob's file and counting it for that removal are one step an interruption waits out, so a write the file system finishes after an admission's deadline is still removed.
- The store has one lock over its files, so writing a blob and removing one never interleave. It is always taken before a transaction and never inside one: an upload, a `say` with files and a blob's removal take them in that order, so they never wait on each other in turn.
- `GET /attachments/:id` serves a file to a paired device only, with the device token as a bearer.
- `bot.files` lists the files a bot has produced, newest first, for the bot's details view.

## Visuals

A `say` may show a page above its text ([decision 0030](../decisions/0030-a-visual-is-part-of-say.md)): `visual: {path, title, height?}` names an HTML file in the bot's workspace, which the server reads as it reads an attachment, by the same containment, and stores with the message as `MessageEntry.visual`, `{title, html, height}`. The page itself is never sent to the bridge inline, since the engine summarizes a tool input past 16 KB and J3 Bots matches a `say` to the engine's call by its input ([Bot tools](#bot-tools)).

- **What is refused.** A blank title or one over 200 characters, a URL, a path that does not end in `.html` or `.htm`, a path outside the workspace or that is not a regular file, a file past `MAX_VISUAL_BYTES` (512 KB, of which no more is read), one that is not UTF-8 text, an empty one, and one that embeds another page or holds a declarative shadow root: an `<iframe>`, `<frame>`, `<object>` or `<embed>` start tag, or a `shadowrootmode` attribute, anywhere in its text, which a client would not show ([Security: visuals](security.md#visuals)). Each refusal sends nothing, and says what to change. A `height` outside 80 to 2000 is refused by the tool's schema; without one, the client measures the page.
- **What is done with it.** Nothing: the server neither runs nor parses the page, which only a client's sandboxed frame renders ([Security: visuals](security.md#visuals)). It is stored as text in the entry and never written to a log, a trace, a notification or a push, which say the message's text. The roster's preview of the message is its text.
- **How it is served.** The web client's visual page, `VISUAL_FRAME_PATH`, is served with `VISUAL_FRAME_POLICY` and no `X-Frame-Options`, so the client can frame it; every other page of the client is served with `frame-ancestors 'none'; frame-src 'self'`.

## Sessions

Each bot has one **main session**: an engine thread in the bot's project, where operator turns, room turns and teammate messages all land. One working context means a bot in a room can use what the operator told it privately, which is what makes it the same teammate everywhere.

**Side sessions** are short-lived engine threads in the same project, used for routine runs: each attempt of a run gets one of its own, never reused by another. They start with fresh context, see the same system prompt and memory files, and can deliver messages with `say` like the main session; what they say goes to the bot's conversation. They cannot use `ask`: its answer would wake the main session, which never saw the question, so a routine's turn puts its question in what it says. Of `set_routine` they may only pause the routine they run ([Bot tools](#bot-tools)). Their work is out of the operator's sight: a side session's turn shows no work fold, and a failed attempt no notice. A side session counts toward the concurrency budget like any other, and its turns count in the bot's usage (`usage.turns`), each naming its routine, or saying it was deleted since: deleting a routine unlinks its wakes but not its side sessions.

A side session is never aligned (**Settings alignment**, below): it is replaced. Its row names the bot's provider, read in the transaction that writes it, and it is opened on that provider with the bot's model, permission mode and browser switch as they stand then, its project's browser access written first. Every write of a project's browser access, for an opening, an alignment or a side session, reads the bot's switch just before it, one write at a time and outside every session's gate: the last one written has the latest switch, and a write never waits for a turn to end. While the bot counts a browser it lost and not yet withdrawn (`bots.browser_withdrawals`, one more in the transaction that turns the switch off), a write that finds the switch still off withdraws it from the whole project instead, and clears the count it read only if no other was added since ([Engine: the bot's browser](engine.md#the-bots-browser)). The bot counts the changes of any of them (`settings_revision`), one more in the transaction that saves each, and a side session's row records the bot's count when it is written, before it is opened. The sender's claim refuses every first send into a side session whose bot has moved past its count, also one claimed before the change and given back unsent because the engine was unreachable. The routine runner then releases the attempt's dispatch, if one waits unsent, retires the session and opens a fresh one for the same attempt with the new settings, which does not count as another attempt; a send given back so nudges it. So no routine turn starts with a permission mode the operator lowered, also when its session opened before the change and waited for a turn slot. A side session whose first send was claimed and not given back keeps the settings it opened with, as a running turn does: the claim is where its turn starts. A retried opening returns the thread with the settings of its first attempt, which are never newer than the count its row records, so a change committed after the row was written has it replaced as well. One not opened yet whose bot moved to another provider is retired unopened and a fresh one written for the same attempt, as for a main session. The rotator never rotates, aligns or opens a side session: each of those reads main sessions only.

Once its attempt has ended, and the engine shows no turn it can still run and no background work in it, the routine runner retires it, checking again in that transaction that the server knows of no turn, dispatch, continuation or unsettled Stop there. Background work the run left running keeps it until that work ends, unless a newer attempt supersedes it: a retry of its failed attempt is due, or a newer run of the routine has started. The retry waits for the failed attempt's session to be out of use, so once the retry's delay has passed, the session is retired as soon as no turn can still run there. A newer run has a session of its own, so a run that succeeded and left work running keeps its session only until the routine runs again. Either way the archive ends that work, as it does for a main session replaced on recovered context. The rotator then archives its engine thread and stops following its events, by the same path as a replaced main session (**Rotation**, below). A side session the engine answers it no longer has, archived from the engine's console say, is recorded lost, without a notice, and then retired. A side session lost before its attempt reached the engine is replaced by a fresh one for the same attempt.

A session's id is J3 Bots' own, written before the engine is asked for a thread and used as the key of that request, so a retried creation cannot make a second thread. The engine keeps a refusal for the key it was sent under, so a key it refused is never sent again: a main session the engine refused to open is opened later under its id with the count of refusals, a key that names a thread of its own (**Every bot has a main session**, below), and a side session it refused to open fails its attempt ([Routines](#routines)). A refusal of the bot's permission mode is the exception: the engine keeps no receipt for it, so it spends no key. A main session it refused for its mode is opened later under the same key, and a side session's attempt still fails, its retry opening a fresh side session under a key of its own, as every new attempt does. The engine's thread id is stored next to it once known, unique across sessions. The prompt version the session was created with is recorded too, so a session started on an older prompt can be found and rotated.

Because the main session does not see what a side session did, the server keeps a **catch-up note** per bot, in the database. When the bot next wakes in its main session, the envelope begins with what happened since: "Routine 'Morning repo check' ran at 08:03 and told the user: …". Each message a routine run says adds one note, in the transaction that publishes the message, with the message's place in the conversation: everything said in a side session is its attempt's, also in a turn the engine started there itself, as when background work the run started wakes it. A silent run adds none. A fresh start drops every such note from before it, and one an unsent dispatch carried is dropped when that dispatch gives it back, so nothing said before a fresh start reaches the bot's working context; the conversation itself still shows it. A routine's own run history is not the bot's working context: it stays, and a routine's next run still reads what its recent runs said, also those before the fresh start, to tell what is new ([Routines](#routines)). The note is consumed in the same transaction that writes that dispatch, so it is neither lost nor shown twice.

**Rotation.** The server replaces a bot's main session when any of these is true:

- it ran 200 turns, a provisional threshold ([open question 6](../open-questions.md#6-when-should-a-main-session-rotate-and-what-does-the-digest-contain));
- the engine ran a turn on recovered context because the provider could not resume its own conversation (the turn ends with `contextRecovered`, [Engine](engine.md#the-adapters-interface));
- the operator moved the bot to another provider (another model on the same provider stays in the session, aligned as **Settings alignment** below describes);
- the operator asked for a fresh start (`bot.freshStart`).

Each records the reason on the session in the transaction of what caused it. A stronger reason replaces a weaker one (the run limit, then recovered context, then a provider change, then a fresh start); a weaker one never replaces a stronger. How the rotator waits depends on the reason, and quiet is the engine's word: before it retires a session it takes a synchronization marker ([Engine](engine.md#the-adapters-interface)) once the session's events are known, and then checks again, in the transaction that retires the session, what the server itself knows: no admitted or open turn, no continuation pending, no dispatch on its way and no Stop unsettled.

- **The run limit** waits for the session to be quiet: no turn the engine can still run, also one whose provider has not started, and no background work pending, counting work the adapter could not judge yet and work the engine's stop does not reach ([Engine](engine.md#the-adapters-interface)). Meanwhile the session still takes new work, so long background work, a dev server or a watcher, never holds the bot's wakes. Background work that may end with no event is looked at again every 30 seconds.
- **Recovered context** waits only until no turn runs or can run. Nothing new is planned into the session. Background work it still has is ended by the retirement, as for a lost session, and the server logs that it was when the engine showed background work pending.
- **A provider change and a fresh start** are the operator's own actions. Each first stops the bot's work through the Stop machinery ([Stop](#stop)), in the transaction that records it, and the session is replaced once that Stop settles and the engine shows no turn it can still run and no background work pending that its stop ends. Background work it does not reach, which a provider session the engine kept from before a fresh-context start still runs, does not hold the session: the retirement ends it, as for recovered context; a client says so wherever it offers the action ("Stops any work {name} has running."). Nothing new is planned into the session, and wakes written after the action wait for the new one. A fresh start clears the bot's context, not its inbox: a teammate's message the bot has not read is new work, so a held one waits for the new session, and an urgent one the fresh start's Stop cancels waits on as held ([Teammate messages](#teammate-messages)). A provider change's Stop leaves a new bot's unsent opening waiting (1. A wake is recorded). A bot moved back to its session's provider before the session was replaced keeps it: the reason is cleared and the held wakes go to it. A weaker reason the move replaced is not restored; the rotator asks for the run limit again on its next pass. A fresh start also takes effect when the bot has no opened main session: the one written and not yet opened is retired at once.

In one transaction the rotator retires the session and writes a catch-up note with a digest of the conversation, unless the operator asked for a fresh start, which carries none; memory files stay either way. The bot has at most one digest waiting: a later one replaces one no envelope carried yet, and a fresh start drops it. A fresh start also records where the conversation stood, and no later digest reaches back past that point, so a session lost after a fresh start brings only what was said since. A digest belongs to the session it was written for: when a dispatch that carried it is returned unsent because its session was retired or lost, the digest goes with it, and the session that replaces that one gets a digest of its own. The bot's new main session is then opened as any is, and its first envelope brings the note in `since-last-turn`, ahead of whatever woke it, so a rotation costs no turn of its own. A digest is far below the engine's input limit; only a message that alone comes near the limit leaves it no room, and it then comes with the next envelope (**Coalescing**, above). The old engine thread is archived (`retireSession`) and never deleted. Each retirement sends its Stop round and its archive under keys of its own. An archive whose answer was lost is asked again on the next pass. One the engine refused is tried again from 5 seconds, doubling up to 5 minutes: the engine refuses an archive while delegated tasks run in the thread, and the retirement's Stop only queues their end, so an archive sent right after it can be refused once (**Verified** on `0.1.11`, in the conformance suite). Either way only that session waits, and the pass goes on with the others; a retired session holds no turn slot meanwhile. The server closes its event stream and never follows it again. Since no event of it is applied once the archive is recorded, also one the stream had already delivered, the transaction that records the archive settles what is still open there as a loss does (**A lost session**, below), without a notice: a turn the engine started there meanwhile, as finished background work can, ends interrupted. The conversation itself is untouched.

A dispatch planned into a session is written only if, in the writing transaction, the session is still live and still takes new work; otherwise the bot's wakes are planned again, into whichever session now takes them. So no envelope reaches a session the rotator has retired or reserved for its replacement.

**Every bot has a main session.** On each pass the rotator opens the main session of any live bot that has none opened: under the key of the one already written, so a retried creation makes no second thread, or a new one. A failed opening is tried again from 5 seconds, doubling up to 5 minutes, with no engine restart needed, and one the engine refused under a fresh key ([Sessions](#sessions)); an engine that takes no commands waits until it is ready. Once three openings or alignments in a row failed, about 15 seconds in, the bot's conversation shows a `session-not-ready` notice, once until an alignment succeeds: the bot keeps trying, new messages wait, and if it does not clear the operator checks the bot's model, since a model the engine no longer offers fails every attempt. A permission mode the engine refuses to open the session in, as the ceiling of an administrator's policy on its machine does until the mode is lowered or the engine starts again under another policy ([Engine: protocol facts](engine.md#protocol-facts-the-adapter-depends-on)), is no failure and is not tried on the backoff: in one transaction the bot records the count of its settings changes it was refused at, read with the settings it sent, and its conversation shows a `permission-mode-refused` notice naming the mode and the highest one the policy allows, when the engine reports it, and the two ways out: choose a lower permission mode, or raise the policy's limit and restart J3 Bots, which restarts the engine. Each active room it is a member of shows a `member-mode-refused` notice naming it, once for each refusal its conversation is told of: a room is told unless it already has such a line newer than the conversation's last `permission-mode-refused` notice. So a room that takes the bot in while the refusal stands is told then, and one that took it in while no refusal stood, as after an engine restart, is told at its next refusal, even one its conversation was told of before. The line says what happened at its time: the bot took no part there until the operator acted, and the rest of the room went on without it ([One turn per room](#2-the-server-holds-waiting-wakes)). A turn the engine refuses to run in a session already in such a mode, as one opened before the policy was installed is, puts the bot in the same state ([The wake pipeline](#3-a-dispatch-is-written-before-the-engine-is-called), Refusals). The rotator then neither opens nor aligns its main session while that count stands, the dispatcher plans nothing into it, and new messages wait. Any change of the bot's model or permission mode moves the count past it and nudges the rotator, which opens the session under the same key, since the engine kept nothing for it, or aligns it, which nudges the dispatcher. Each time the engine becomes ready, J3 Bots' own start included, every bot's recorded refusal is cleared before the workers are nudged, since the engine may have started under another policy, so each is asked once more. A refusal is stamped with the engine's start generation, read before the call that met it: how many times the engine became ready and the server took it in. One that arrives after the engine became ready again, from an engine that has stopped since, is not recorded, so it can never block the bot under an engine that would allow its mode; the generation is read in the transaction that records it, and the clearing runs after the generation moves, so a refusal is either cleared or never written. The bot also records the refusal its conversation was told of, its count of changes and the mode the engine allowed: a refusal the engine repeats after a restart is not told again, and one at a later count, or naming another allowed mode, is told once. An opening or alignment that succeeds, or a turn the engine takes in the main session, forgets it, so a later refusal is told again. The provider of a session is chosen in the transaction that writes its row, from the bot's provider then, and a session is opened only on that provider: a bot moved to another provider before its session opened gets a new session on the new one, never one on the provider it left. Once the engine answers an opening, the server records the session's engine id and aligns it before it takes any work, since a retried opening returns the thread with the settings of its first attempt. A crash between the engine creating the thread and the server recording its id leaves that thread on the engine; if the session is then retired before it is opened again, nothing knows the thread's id to archive it, so it stays on the engine un-archived, idle and unused.

**Settings alignment.** The bot's saved model, permission mode and browser switch are what its session runs with, and a session takes no work until the engine has them. Each session row counts the changes of its bot's settings it has not been brought to (`settings_pending`): a new row starts at one, and `bot.update` adds one in the transaction that saves a new model, permission mode or browser switch, then answers with success. That transaction runs in the gate of the bot's main session, and checks that the session is still the bot's main one, or runs again in the gate of the one that is: a send claimed before the change reaches the engine before the change commits, and a send after it is refused. So `bot.update` waits behind a send in flight on that session; its receipt makes a client's retry safe. Nothing is planned into a session above zero, the transaction that writes a dispatch checks it again, the sender's claim refuses every send into it, a resend included, since the engine starts a turn for a key it never had, and a held engine queue there is not resumed.

The rotator aligns such a session on its next pass, which the change nudges and an engine coming back to ready starts: in the session's gate, so no send and no other alignment crosses it, it sends the bot's settings as they stand (`configureSession`), with a browser switch that differs from the one the row records as a reload of the session's tools after its project's browser access is written ([Engine: the bot's browser](engine.md#the-bots-browser)), and sets the count back to zero, and the row's browser to the one it sent, only if no change committed meanwhile, which wakes the dispatcher; otherwise it aligns again. A session already opened is only aligned; its workspace and project are not provisioned again. A failed alignment is tried again with the same backoff as an opening. One whose permission mode the engine refuses waits for the bot's settings to change, or the engine to be ready again, as an opening does (**Every bot has a main session**, above): the session keeps the settings it had and takes no work meanwhile. A session on a provider the bot left, or one lost, is replaced instead. An alignment the engine answers with `SessionNotFound`, as for a thread archived from the engine's console, whose event stream stays open, records the session lost (**A lost session**, below) and stops following its events, which nothing else would end, and the next pass replaces it.

- **Turning the browser off does not wait.** Its transaction also records the bot's Stop, as a change of provider does, keeping the bot's opening; and its alignment withdraws the browser from every thread of the bot's project before it checks for a running turn. So a turn running with the browser is stopped, and nothing the engine starts there afterwards has it.
- **A running turn keeps the other settings it started with.** On Claude Code a new permission mode replaces the provider session, which would end a turn running there, and close a request it waits on (**Read** at `db51b67`, `Orchestrator.ts` L4715-4757, `ClaudeAdapterV2.ts` L577). So the rotator aligns only while the server knows of no admitted or open turn in the session, and the adapter refuses the change with `SessionBusy`, sending nothing, when it sees a turn the engine is preparing, starting or running. The turn's end nudges the rotator, which aligns then, with no backoff. The operator stops the turn to end it sooner.
- **Background work holds it.** The engine refuses a change that would replace a provider session still running background work, a delegated agent or a command left running (**Read** at `db51b67`, `Orchestrator.ts` L4744-4757); the adapter reports `BackgroundWorkRunning`. The rotator looks again every 30 seconds, as for a rotation held by background work, which may end with no event. Meanwhile the bot takes no work, and its conversation shows a `settings-held` notice once per change: the new settings apply once the background work ends, and a Stop, which ends it, applies them now. The bot's `settingsHeld` says so to clients, which offer the Stop while it is true, also with no turn running; it clears once the alignment succeeds, or with the next change, until the engine refuses that one too, and once the session is replaced, since the next one opens with the bot's settings. A bot Stop reaches every live session of the bot, and the engine's stop, seeing the background work pending, interrupts the latest run with a restart of the provider's runtime, which ends a Claude Code process and the commands and agents it runs (**Read** at `db51b67`, `dispatchThreadStop`, `ProviderTurnControlService.ts` L312-317, `ClaudeAdapterV2.interruptTurn`). Its settling nudges the rotator, which aligns then. A wakeup Claude Code scheduled for itself is not work the stop reaches, and holds the change until it fires (**Read**, `ClaudeAdapterV2.ts`, `hasPendingBackgroundWork`).
- **What the engine starts on its own is not held.** The engine can start a turn without J3 Bots: a usage-limit continuation at its reset (`autoResumeLimitedThreads`, `UsageLimitRecoveryWorker.ts`), or a wake from background work that ended. Between a change and its alignment such a turn runs with the settings the session still has, and the alignment waits for its end. The pinned engine has no fence that holds those starts and nothing else: a settled thread loses usage-limit resume altogether, and a snooze holds only that resume (**Read** at `db51b67`, `UsageLimitRecoveryWorker.ts`, `limitRecoveryCommand`). The window is short unless the engine is unreachable to J3 Bots while it runs, or background work holds the change.

The digest is the delivered messages of the bot's conversation, the operator's and the bot's own, newest kept: at most the last 60 such messages, each cut to 1,000 characters, 6,000 characters in all with the names of their files, oldest first. Each message is kept apart with its author, so the envelope renders it as its own block ([Prompts](../prompts/architecture.md)). Notices and messages that never reached the bot neither appear nor count toward the 60. Memory, not the digest, is what a bot relies on across rotations ([decision 0003](../decisions/0003-conversation-is-not-session.md)).

**A lost session.** When the engine answers that it has no such session (`SessionNotFound`), to a send, a Stop round, a resume, an answer or the event stream, the session is recorded **lost**, once, and everything open in it is settled in the same transaction, since nothing runs there any more: its Stop targets settle, each round keeping what the engine answered for it, a refusal included; a dispatch the engine had accepted, also one it queued, fails as `unresolved` and keeps the engine's first answer, its wakes failed and retryable, or cancelled when a Stop covers them ([What a Stop covers](#stop)); a delivered one, every open turn and its work fold end interrupted; its open requests close as expired. A dispatch whose answer is not known is due at once and the sender settles it in the gate, as `unresolved` when it was sent. Nothing is planned into the session or watched in it again, and it counts toward no budget. Its loss only holds back its own work: every other bot goes on. A lost main session shows a `session-lost` notice in the bot's conversation, unless the server had already retired it, so its disappearing was intended; when the loss cut short a new bot's opening turn that no Stop covers, a retryable `turn-failed` notice follows it ([1. A wake is recorded](#1-a-wake-is-recorded-before-anything-happens)); the bot's wakes wait until it has a new main session, which the rotator opens at once, with the same digest a rotation brings ([Rotation](#sessions)).

## Bot tools

Bots act on J3 Bots through a small MCP server named `j3`. The harness starts it as a local stdio process, one per loaded session; that process forwards each call to the J3 Bots server's tool endpoint, an HTTP listener of its own on `127.0.0.1:J3_TOOL_PORT`, which stays on loopback whatever `host` is and takes a request only as the bridge makes it ([Security](security.md#j3-bots-own-surface)). It holds no state and does no work of its own, because a host with many recently active bots runs many of them (see [Engine](engine.md#footprint)).

The bridge identifies its caller from `T3CODE_THREAD_ID`, an environment variable the engine sets for each stdio MCP server the harness starts, with the session's thread id. The bridge reads it with `sessionOfToolCaller` from `packages/engine-t3` and never names the variable itself. The server maps that id to a session and a bot. A call from an unknown thread is refused. **Verified** on Claude Code on releases `4941` and `4969`, and on Codex from `4969`, the pinned release ([Engine](engine.md#version-pinning)).

**Matching a call to its turn.** A request carries a session, not a turn, and the server's view of the session can trail the engine by a few events: a call made at the end of one turn could otherwise act for the next. So the server matches each request to the engine's own record of the call. The engine reports every `j3` tool call as a `tool-call` event in its turn, with the bare tool name and a digest of its input ([Engine](engine.md#the-adapters-interface)).

1. It picks a token, starts waiting for it, and calls `synchronize` for the session. When its event applier has applied the `synchronized` event with that token, every event the engine had when the request arrived has been applied.
2. It looks, in the session's running admitted turn, for an open call to the same tool whose input digest equals `toolInputDigest` of the request's arguments and that no other request has claimed. It takes the oldest.
3. The engine records the call apart from the request, so the call may not be there yet. Without a match the server synchronizes again, up to five times within two seconds.
4. With a match, the request is **pinned**: stored under the bridge's id for the request with the turn, the turn's audience and the engine's id for the call, which no other request can claim. The pin is written in the transaction that applies the request, publishing what it says, messaging the teammate or changing the routine, and that transaction checks again, from what is committed, that the call is still open and unclaimed in the session's admitted turn, with the input digest it was matched by (the engine records an open, unclaimed call again when an ACP agent reports its arguments late, so a request matched against the earlier input does not claim the call as recorded since), that the turn has not finished, and that the room the turn speaks for is still live, also for a `say` to the operator from a room turn. A retry of a request that already committed returns its stored result there; a result is stored for the request's id, session and tool together, so the same id from another session or for another tool gets none and is refused. The files a `say` attaches are read before and stored only once the pin holds. Everything the request does acts for that turn and audience, even if the session admits another turn meanwhile.
5. Without one, unless a forward of the same request committed meanwhile and claimed the call, whose stored result it then returns, the request fails with a typed `TurnEnded` result whose text the bot reads (`NO_TURN_REFUSAL` in `packages/prompts`), and nothing is published or recorded: the call belongs to a turn that has ended, or to no turn of this session.

**Subagents cannot speak.** A Claude Code subagent's tool call is recorded on the subagent's own thread, outside the bot's turn (**Read** at `db51b67`, `ClaudeAdapterV2.ts`, `startSubagentToolCall`; Codex is **Assumed** to do the same), so it never matches and is refused by step 5. The tool descriptions and the base prompt tell a subagent to report in its final reply instead.

**Duplicates.** Several requests may match one call: the bridge forwarding the same request twice under different ids, or a harness repeating an identical call. The oldest unclaimed request claims the call, and every other one is refused at step 5, so one call acts once. A later identical call is a call of its own, with its own engine record: the model made it twice, so it is accepted and acted on once more. That fails safe, because each call still acts exactly once: a repeated `say` shows twice, visibly, and a repeated `remember` is deduplicated.

**Size.** The engine shows a tool input over 16,384 bytes only as a summary, which no digest can match, so the tool schemas refuse arguments over 12,288 bytes with a message telling the bot to split them ([Engine](engine.md#behaviors-j3-bots-designs-around)).

A call whose audience is a room that is now archived fails with `Conflict("room-archived")`, and nothing is published.

The bridge gives each request one id and reuses it when it retries the forward, so a retry finds the stored request, acts for the same turn, and returns the stored result instead of acting twice. If the engine cannot be reached, the server retries the match until the request's deadline and then fails it as retryable. A request has fifteen seconds end to end; past that nothing was committed and it fails as retryable.

J3 Bots' own `j3` tools are pre-approved by name in every permission mode, so they never raise an approval card; a connector's tools are not, and follow the bot's permission mode. How each harness is told so is in [Engine](engine.md#provisioning).

**Connector tools.** The bridge lists, after J3 Bots' own tools, the connector tools its session's bot is offered ([Connectors](#connectors)), each named `<connector>__<tool>`; none of J3 Bots' own tools has a `__` in its name. The bridge asks the server for the list (`/tools/list`) each time the harness lists, and falls back to J3 Bots' own tools when the server cannot be reached or the session is no bot's. Each bot's list has a version, which changes whenever the connectors say its offered tools may have, and which a server process never gives twice across restarts. Once the harness has listed, the bridge waits on the server for a version other than the one it listed (`/tools/changes`, answered at a change or after four minutes, and refused at once for a session that is no bot's, so only a session's own bridge can hold such a wait open) and then sends `notifications/tools/list_changed`, so a grant reaches a bot without a new session: a Codex bot in the same turn, a Claude Code bot from its next turn ([Engine](engine.md#behaviors-j3-bots-designs-around)). It sends each wait once, and stops waiting at the first the server does not answer: the server is stopping, and its harnesses with it, or the session is no bot's. So a bridge with nothing to forward never sends its session's id to a port the server has let go ([Security](security.md#known-gaps)).

A call to a connector tool:

1. is refused when its arguments are not an object or are over the same 12,288 bytes as J3 Bots' own tools take;
2. is matched to the engine's record of the call in the session's running admitted turn, as above, and claimed for its request in a transaction of its own, which commits before the connector is called, so the call is made once, and only for a running turn. Unlike J3 Bots' own tools, the record may have closed already: Codex starts a call before it asks for its approval (**Read** in Codex `rust-v0.171.0`, `core/src/mcp_tool_call.rs`), and the engine closes the record when Codex's code-mode `exec` yields, about 30 seconds in (**Verified** for a call that runs; **Assumed** for one that waits on its approval), so an approval that takes longer reaches the server with the record closed. The call must still be the running turn's and no other request's, and not one the operator declined: the server keeps which call an approval holds back when the engine names it beside the request, which it does on Claude Code and not on Codex ([Security: connectors](security.md#connectors)), so a decline ends the call for every claim from the moment it is written, before the engine hears it;
3. goes to the connector's client, which refuses a tool the bot is not offered and answers the rest as text the bot reads as untrusted, or J3 Bots' own line when the connector could not answer. The answer goes back to the bot and is not stored: the operator's data stays at the connector. So a forward of a request claimed before, after a lost reply or a server restart, is answered that the call may or may not have taken effect, and that the bot should check before making it again.

A connector call may take up to eleven minutes at the bridge, past the connector client's own deadline, and each harness's timeout for `j3` is twelve. A harness that gives up on a call sends `notifications/cancelled`; the bridge then abandons its forward without an answer, which interrupts the call at the server and, through the connector's client, at the connector's server. A harness that closes the bridge's input, as it does when it ends, has every call still running abandoned the same way. When the bridge gets no answer from the server for a connector call, it tells the bot that the call may or may not have taken effect and to check before making it again, never to try again: the server may have made the call before its answer was lost, and a new call is a new request. No progress is relayed: neither harness extends its timeout for it ([Engine](engine.md#behaviors-j3-bots-designs-around)). A connector call shows in the bot's work fold as a `connector` step, named by the connector and the tool, never by its arguments.

## Rooms

A room is J3 Bots data: members, host, entries, and a status. An active room has two to six members and a host among them. An archived room is read-only: it takes no messages and no changes but `pinned` and unarchiving, and it may have fewer than two members and no host. There is no engine object behind it.

**Archiving** a room, by the operator (`room.update` with `archived: true`) or because deleting bots left it too small, is one transaction that cancels every pending wake addressed to the room, expires the room's open `ask` cards (an answer can no longer reach it), and records a Stop for every member session whose turn, waiting turn or dispatch has the room as its audience, selected as every room Stop selects its targets ([Record](#stop)). That Stop has the `room` scope and then runs as any other ([Stop](#stop)). A bot tool call whose audience is the archived room fails with `Conflict("room-archived")`, and host speech from a turn whose audience is the archived room is not published there, including speech a replacement replays after the archival. Unarchiving needs two to six members and a host, which the same update may give. **Removing a member** records, in the same transaction, a `room` Stop of its work for the room, so its running room turn ends; it cancels its wakes still held for the room, releases its room dispatches never sent with their wakes cancelled, expires the `ask` cards it raised there, and takes the Retry off the room's notices of its failed turns, so it reads nothing said there after it left. A `say` its turn makes for the room after that is refused with a tool error telling it its work there is over; the dispatcher cancels any wake it meets later the same way, and a room start's send refuses a bot that is no longer a member, also between two of its files. The operator's room messages it never received count it no more, as for a deleted bot ([Deleting a bot](#deleting-a-bot)): every wake of its for the room that did not finish, pending, in a dispatch never sent, or failed, stops counting, so each message shows its delivery to the other members it addressed, and `cancelled` only when it had no other. When the removal cancelled or released anything, the dispatcher is nudged once it commits: the room's next member may have waited behind the one that left. **Stopping** the room's work (`room.stop`) records the same Stop for an active room and cancels its waiting wakes without archiving it: its cards stay open and it takes messages as before. In an archived room it fails with `Conflict("room-archived")`: the archival stopped its work. **Deleting** a room records the same Stop before the room's row goes. The Stop, the dispatches and the turns keep the room's id as plain text, with no reference to the row, so once the room is gone the one rule of [What a Stop covers](#stop) still tells its work from another room's: a dispatch of the deleted room that settles later, also one whose key the engine applies after the deletion, is covered by the room's Stop, and its wakes are cancelled.

**Background work belongs to the turn that started it** ([0013](../decisions/0013-background-work-belongs-to-the-turn-that-started-it.md)). A turn records the turn of its session whose work it continues: the one a usage limit's continuation resumes, or the one whose delegated task woke the session, when the engine names it ([Engine](engine.md#behaviors-j3-bots-designs-around)). It speaks to that turn's audience, so a room turn's background work reports in the room, and nowhere once the room is archived or the bot left it; its hops and its Stops count with that turn ([Budgets](#budgets), [What a Stop covers](#stop)). Each turn also records whether background work it started may still be pending: set when it ends handing off to such work, then kept or cleared by each report of the session's pending work taken while nothing runs. While turns of a session have it set, each turn's end makes a report due, which the Stop runner asks the engine for once nothing runs there, so a flag lasts little longer than its work. It waits while a Stop of the session is unsettled, whose rounds ask for reports of their own, and while the engine holds the session's queue, whose waiting turns keep any report from being the check. A report taken while nothing runs or waits makes it due no more, and the end of a turn that ran or waited makes it due again. A room's Stop targets a session while one of the room's turns there has it set. It never uses a flag kept for the whole session: the engine's rule for pending work does not ask which run started it, so such a flag would reach private work, or outlive the room's.

**An active room says whether its work is under way** (`Room.work`), so a client offers its Stop without guessing from its members' states, which do not say whom a bot works for. It is derived when the room is read, from what the turn machinery records: `stopping` while a room Stop of it has a target not settled; else `running` while a wake for the room is pending, a dispatch for it is not settled, a session has a turn for it admitted, or one of its turns runs or still has background work flagged in a session neither lost nor retired by the engine; else `none`. A member's work for another audience never counts. The roster pushes the room again through its usual path: with every change of one of its members, when the room's work as the subscriber last received it differs (a turn's start and end, a background report, a Stop settling), and with the room itself when a wake for it is written or cancelled, a dispatch for it settles without a turn, a Stop of it settles without a round, or the operator's `room.stop` is recorded. A client of a server that does not send it reads `none`, and offers no Stop of the room.

**The room is checked wherever its wakes are written.** `Wakes.record` writes no room wake, whatever caused it, for a room that is not active or a bot that is not its member, nor a wake that work for such a room causes, so no new wake carries a deleted room's id. A path that returns a room's wake to `pending` asks `covers` first (`wakesAfter`). In an archived room, retrying a message or notice fails with `Conflict("room-archived")`, and answering a card with `Conflict("card-closed")`, since the archival expired it; a failed wake survives the archival, so the Retry works again once the room is unarchived. Deleting a room deletes its entries, so each of these then fails with `NotFound` ([Client API](#client-api)).

When an entry is added to a room, the server decides who wakes:

| The entry | Who wakes |
| --- | --- |
| From the operator, mentions bots | Each mentioned bot, one at a time in the order mentioned |
| From the operator, mentions `@everyone` | Every member, one at a time in member order; each sees the replies before it |
| From the operator, mentions nobody | The host |
| From a bot, its `say` lists members in `mention` | Each listed member, one at a time in the order listed, within the room's hop limit |
| From a bot, mentions nobody | Nobody. The room waits |

Every one of these is a `room` wake for the room's audience, written in the transaction that adds the entry, with what addressed the bot (`mentioned`, `everyone`, or `host` when nobody was). The operator's carry 0 hops and the operator's priority ([2. The server holds waiting wakes](#2-the-server-holds-waiting-wakes)); a bot's carry the hops of the turn that spoke ([Budgets](#budgets)) and are held to that turn's Stops like any wake work causes ([1. A wake is recorded](#1-a-wake-is-recorded-before-anything-happens)). A Stop of the speaker after it spoke does not take them back: what it said was said.

**Mentions are structured.** The operator's message carries the bots it mentions, up to six, or `everyone`. A bot's `say` carries `mention`, a list of member ids, which the server honours only in a room turn. It refuses, with a tool error that says why and nothing written, a `mention` outside a room turn (also with `to: "dm"`), one that lists the bot itself or a bot that is not a member, and one that lists more members than the fan-out limit allows ([Budgets](#budgets)). The server never parses mentions out of the text. The entry records the members a bot mentioned, so every envelope that shows it names them.

**A room runs one turn at a time.** A room wake starts a turn only when nothing of its room runs or is about to, and the room's oldest wake goes first, by priority and then in the order written, whatever member it wakes ([One turn per room](#2-the-server-holds-waiting-wakes)). So `@everyone` runs member by member, each envelope carrying the replies before it, and a bot's handoff runs after the turn that made it. A member whose permission mode the engine refuses is passed over until the operator lowers it or raises the policy's limit, and the room shows one `member-mode-refused` line naming it; what was said to it then reaches it once, in its place. While the room's next member cannot get a turn slot, the operator's message to a member that holds one already goes first, so a pending continuation never keeps their word waiting. A bot's waiting room wakes for the same room share one envelope; wakes for two rooms never do. When the operator's room message wakes a member whose turn for that room is running, it steers that turn, so they can redirect it. It never steers another member's turn: a message for Bo while Hal's room turn runs reaches Bo as the room's next turn, as it does a member whose turn is elsewhere.

**The envelope carries what the member has not seen.** A room wake is delivered into the bot's **main session**, in an envelope that names the room, its members and its host, and that ends with a line chosen by what addressed the bot ([Prompt architecture](../prompts/architecture.md#wake-envelopes)). Each room dispatch records the room's newest entry when its envelope was written, and a member has seen the room through the newest such entry among its dispatches the engine may have applied: one released, dropped or refused leaves its entries unseen for the next envelope. The envelope holds the entries the bot's wakes are for, then the newest of the other unseen messages that fit the engine's limits for one message, in room order, never the bot's own. Earlier ones are left out for good, and one line says how many. The entry that woke the bot always fits alone, so a room wake never fails for its size: the operator's room message is accepted only if it fits beside the room at its widest, with the longest name a room can have, as many members as it can have, and the longest names, titles and ids they can have, since the room may change before the wake goes; another wake whose entry does not fit beside it waits for the next envelope. Its audience is the room: during that turn `say` delivers to the room, and `say` with `to: "dm"` delivers privately to the operator.

A bot that has nothing to add ends its turn without calling `say`. That is the normal way a room goes quiet.

**Waiting on the operator.** Approvals, engine questions and credential requests raised during a room turn appear as cards in the bot's own conversation, and the room shows one `waiting-in-conversation` notice per turn naming the bot, so the operator knows where to look. A room turn that fails shows `turn-failed` in the room, with a Retry that sends the member's wakes again while the room is active and the bot its member. So does a member's room turn that never started because its dispatch failed, when no message of the operator's woke it: a bot's message, also once the operator retried it, has no delivery state of the operator's to show the failure on. When the dispatch carried the operator's message, that message shows the failure, with its Retry, and the room shows nothing. What decides is the entry that woke the member, never the wake's priority. A `say` whose files the engine would refuse in one message, such as an image above the inline limit, is refused with nothing written, as the operator's message is.

## Deleting a bot

Deleting a bot removes its engine project first, so nothing keeps running for a bot that no longer exists, and waits for a session opening in progress to finish, so the rotator opens no session for a bot being deleted; while the engine cannot take that, the deletion fails with `Conflict("engine-unavailable")` and changes nothing. Then one transaction removes its conversation, sessions, wakes, routines and memory. What it said elsewhere stays:

- Entries it wrote in rooms keep their author id. Nothing refers to the bot row, so the entries outlive it, and clients render the author as a deleted bot.
- If it hosted a room, the room passes to the member who joined first among the rest, in the same transaction. The database refuses to leave an active room without a host.
- A room left with fewer than two members is archived, in the same transaction, as [Rooms](#rooms) describes: it stays readable, takes no new messages, and keeps no host if its host was the deleted bot.
- Files it produced stay in the attachment store while an entry refers to them.
- Messages it sent teammates stay theirs: a held one still reaches its recipient, and one a Stop of it ended stays ended ([Teammate messages](#teammate-messages)).
- Messages teammates sent it that it never read go with its conversation and inbox; each sender's card that still showed `sent` shows `not-delivered`.
- The operator's room messages to it show their delivery to the other members it addressed; one that only it was to receive, and never did, shows `cancelled`.

## Teammate messages

`message_bot` sends one teammate a message. Its `to` is a bot id; a room is reached only by `say` in a room turn. The call is pinned to its turn as `say` is ([Bot tools](#bot-tools)), and the transaction that pins it does the rest:

1. **Refuse what is not a teammate's to get.** A recipient that is the sender itself, or no bot (never created, or deleted), is refused, and so is work a Stop covers: a Stop of the sender, or of the room its turn speaks for, recorded while the turn ran or after the dispatch that began its work was written ([What a Stop covers](#stop)). A turn the engine started on its own has no such dispatch, so only a Stop recorded while it ran covers it. Nothing is written.
2. **Apply the budgets** ([Budgets](#budgets)). Past the fan-out limit the call is refused with nothing written. Past the hop limit it is refused, and the sender's conversation shows one `chain-stopped` notice for the turn, however often the turn tries.
3. **Show it in both conversations.** A handoff card goes into each: `sent` in the sender's conversation and `received` in the recipient's, each with the text and whether it is urgent. The message's row (`handoffs`) records the call that sent it, the recipient and both cards, and lives as long as the recipient's card: deleting the sender takes its call, never the row or the mark a Stop left on it. Clients name the other bot on each card, "To Wren" or "From Scout", and link the name to that bot's conversation, or show it as plain text once that bot was deleted; the text opens in full where it is. Both cards show where the message stands, the same on each: `sent` (on its way or read, which they do not tell apart), `not-delivered`, `stopped` or `unconfirmed`. The same transaction lists the message in its pair's teammate conversation ([Teammate conversations](#teammate-conversations)). Neither card calls for the operator: it never notifies, urgent or not ([Notifications](#notifications)), never makes its conversation unread, and is never the bot's roster preview or its latest activity ([Client API](#client-api)). A bot that needs the operator says so with `say`.
4. **Urgent:** a `bot` wake for the recipient's conversation, carrying its hop count and the recipient's card, and caused by the sender's work, so it is held to the sender's Stops like any wake work causes ([1. A wake is recorded](#1-a-wake-is-recorded-before-anything-happens)). The dispatcher takes it as any `bot` wake: a turn once the recipient's main session is idle, after the operator's and the rooms' wakes, and wakes that wait together share one envelope, one data block per message.
5. **Not urgent:** a held message, which wakes nobody. The recipient's next main-session dispatch, of any kind, carries it at the top of its envelope (`since-last-turn`), held messages in the order they were sent, and consumes it in the transaction that writes that dispatch. It goes back for the next envelope only when the engine certainly never applied that one ([Catch-up notes and held messages](#3-a-dispatch-is-written-before-the-engine-is-called)), so it reaches one envelope the bot may have read, never two. When that envelope's dispatch ends with nothing to tell whether the engine took it (its recovery gave up, or its session was lost before its turn started), the message stays with it, and both cards show `unconfirmed`; they show `sent` once the engine turns out to have taken it. A routine's side session never takes it.

**A failed urgent message never looks delivered.** When the dispatch carrying its wake fails (the engine refused it, or whether it took it could not be learned) or the engine dropped it before its turn started, the wake fails as an answer's does ([What a Stop covers](#stop)): both cards show it `not-delivered`, and the recipient's conversation shows one retryable `handoff-failed` notice per dispatch, naming each sender whose message it carried. `notice.retry` sends again the wakes that failed, never one a Stop cancelled, as they were: a `bot` wake with its hop count, so a retry does not start the chain again. The Retry itself is the operator's action, so no Stop of the sender cancels it, whenever that Stop is recorded, nor removes the held copy a Stop of the recipient makes of it; if its dispatch fails too, the cards and a new notice show that again. The cards show `sent` again once it goes; so does a late delivery, when the engine had taken it after all. A message that reached the recipient once, by whichever wake or held copy, stays `sent` and goes no more: the delivery that shows it read cancels a Retry still waiting and removes a held copy no envelope took, the dispatcher checks again before it writes either into an envelope and once more when it claims the first send of an envelope written before (which it releases, so whatever else it carried is planned again without the message), and no notice of it, the original's or a Retry's, offers a Retry. A Retry already sent when the original lands cannot be called back; a failure of it shows nothing and offers no Retry. The sender's tool call keeps the result it was given: the failure is the operator's to see and retry, not the bot's.

**A Stop of the sender.** A message belongs to the turn that sent it. A Stop covers it only when it reaches that turn while the turn runs: recording the Stop marks the running turns in its scope ([Record](#stop)), and with them each message they sent that no earlier Stop marked. A message from a turn that had already ended is that work's finished result: a later Stop of the sender leaves it as it is, an urgent one waiting for its turn and a held one for an envelope, also when the engine started that turn on its own. For a message it covers, recording the Stop cancels the urgent message's wake while it waits and removes a held message no envelope has taken, in the Stop's own transaction, and both cards show `stopped`. One already in a dispatch is left to it: if that dispatch does not run to its end, the wake is cancelled, or the held message removed, instead of waiting for the next one, and the cards show `stopped`; if the engine turns out to have started its turn after all, also after its recovery gave up, the cards show `sent`. Whether its wakes then count as delivered depends on the dispatch: one no Stop fenced runs its turn to the end, so wakes cancelled meanwhile count as delivered again; one a Stop fenced has its turn ended by that Stop, and its wakes stay cancelled, though a teammate's message among them was read all the same. The operator's Retry of an urgent message is the operator's own word: no Stop of the sender cancels it, also when the Retry is already in a dispatch that then fails or is released, or held after a Stop of the recipient.

**A Stop of the recipient.** The operator stopping the recipient stops the recipient's work, not what its teammates told it. An urgent message whose wake that Stop cancels before the engine had it (while it waits, in a dispatch the Stop releases, or in one the engine drops before its turn started) becomes a held message: the recipient's next envelope carries it, once, where it was sent among the held messages, and both cards stay `sent`. So does the operator's Retry of one, also after a Stop of the sender. One in a dispatch whose recovery gave up may have been read, so it is not carried again, and both cards show `unconfirmed`. A held message stays held, as any does. A fresh start, which stops the bot's work first, does the same: it clears the bot's context, not its inbox.

The sender gets an acknowledgement (`sent` or `held`), never a reply. A reply is a separate `message_bot` call from the other side and arrives as its own wake or held message. A refusal reaches the bot as the tool's error, with what to do instead. One that wrote its notice is stored as the request's result, so a retried forward refuses the same way and adds no second notice.

The prompt tells bots not to answer an acknowledgement, a thanks or an FYI. The budgets only bound how far an exchange goes when one answers anyway; they do not keep a bot silent.

## Teammate conversations

The messages two bots sent each other make their **teammate conversation**, which the operator reads and never writes into ([decision 0038](../decisions/0038-a-teammate-conversation-is-a-view-of-teammate-messages.md)). It is a view: a message stays its two handoff cards and its `handoffs` row, which delivery works from, and nothing about it moves.

- **One per pair of bots**, addressed by the two bot ids, sorted. It has no id of its own, and no read mark, pin or section. A pair with no messages is not one.
- **Its messages** are listed from `pair_messages`, one row per message, which `message_bot` writes with the cards (migration 31 filled it from every message sent before). A message is read from the recipient's card, or from the sender's once the recipient is deleted: they say the same, its state included. Each has `seq`, its place among all teammate messages, given in the order they were sent and never given again, which a client sorts and upserts by and pages back with. It also names both cards (`sentEntryId`, `receivedEntryId`), so a client maps a handoff card in a bot's conversation to the message.
- **A deleted bot.** Deleting a bot takes its conversation, so its cards: the row names the other card only, and the pair stays readable from the other bot's side, its messages that will never reach the deleted bot marked `not-delivered` by the deletion ([Deleting a bot](#deleting-a-bot)). Once neither card is left, which takes deleting both bots, the row goes (a trigger on the cards' deletion) and the pair with it. Hiding a bot changes nothing here: clients decide where a pair with a hidden or deleted bot shows.
- **`pairs.subscribe`** sends every pair, latest message first, each with its latest message (its text cut to `PREVIEW_LENGTH`) and how many messages it holds, then each pair whose row changes (a new message, a change of its latest one's state, a card gone with its bot) and each pair that is gone. It follows the two bots' conversations' changes and reads a pair again only when a changed entry is one of its cards, or when a bot itself changed (its deletion). It does not resume.
- **`pairs.messages.subscribe`** sends one pair's latest messages, then each message whose card changed, as whole messages. A frame is bounded as a conversation's is (8 MB of text, at least one message); a change too large to replay, or a gap in the change history, sends a fresh snapshot, and so does the deletion of either bot, whose cards go without a change being recorded. **`pairs.history`** pages back by `seq`. It does not resume either.

## Routines

A routine is a row with an instruction and a trigger. The server's scheduler owns it; the engine's scheduled tasks are not used ([decision 0005](../decisions/0005-j3-bots-owns-wakes.md)).

**Triggers.**

- **Schedule triggers** are five-field cron expressions read as wall-clock time in the time zone saved with the trigger. A bot's `set_routine` saves the operator's zone as set at the call, also when it gives a new schedule to a routine whose schedule kept another zone; a schedule nobody changes keeps its zone. A time the clocks repeat when they go back runs once, at its first occurrence. A time the clocks skip runs once that day, as much later as the clocks moved: 02:30 on the night the clocks skip 02:00 to 03:00 runs at 03:30. Two times that land on one instant run once. A schedule is refused with `Invalid("schedule")` when it does not parse, has a seconds field, names no date that exists (`0 0 31 2 *`), or runs twice within five minutes anywhere in the next eight days, and with `Invalid("time-zone")` when it names a zone the server does not know.
- **One-time triggers** run once at a set instant, in UTC, and then pause the routine. They are how "remind me tomorrow at nine" is kept. A one-time trigger must lie ahead when it is saved.

A new trigger is checked when it is saved, also on a paused routine, so a resume never meets one that could not have been saved. An update that sends the saved trigger again, as a form sending the whole draft does, gives no new trigger: it is not checked again, the next run does not move, and nothing starts. A one-time routine whose time has passed, whether it ran or was paused before its time, starts again when given a new trigger, from the operator or the bot, unless the same update pauses it. Any other paused routine keeps its pause through an update.
- **Webhook triggers** are an HTTP endpoint on the J3 Bots server; see [Webhooks](#webhooks). The request body reaches the bot as data inside a nonce-tagged block.

**The scheduler.** Each routine stores its next run. The scheduler wakes at the earliest of them, at least once a minute, and when a command changes a routine. For each routine that came due it records the run and the next run in one transaction, so a run is never recorded twice, also across a restart. Each routine is read again in that transaction, so an edit committed meanwhile wins. A routine whose run cannot be recorded is logged and tried again 30 seconds later, unless it was edited meanwhile; the other routines carry on. A schedule that no longer has a next run, such as one in a zone the server no longer knows, runs that once and pauses its routine, with a warning in the log. A routine whose stored trigger the server cannot read, such as one written by another version, runs nothing and is paused, with one warning. Either pause also shows a `routine-paused` notice in the bot's conversation, which names the routine and says to edit it to turn it back on. Anything else that goes wrong in the scheduler is logged, and it looks again 30 seconds later.

- **Runs missed while the server was not running** (shut down, crashed or asleep, which the server cannot tell apart) are not replayed. Of the runs that came due, only the latest can run: it runs once the server is back if the server is at least as near to it as to the schedule's next run, and the routine goes on from there. Past that half of the gap, the routine runs nothing now, waits for its next run, and counts every run that came due as **missed** ([decision 0021](../decisions/0021-a-missed-routine-runs-only-while-it-is-nearer-than-the-next.md)). So a daily 08:00 routine back at 10:00 runs, and one back at 07:00 the next day waits an hour for 08:00; an hourly one back at :40 waits for the hour; a weekly one runs up to three and a half days late; and a weekday 09:00 one that missed Friday's run still runs it on Saturday up to 21:00, halfway to Monday's. After a downtime of several runs, only the latest runs, and the earlier ones are not counted as missed. The rule has no constant of its own: half of the gap is at least two and a half minutes, since runs are at least five minutes apart, so a run a few seconds late always runs, and a night the clocks shorten or lengthen moves its half. A one-time trigger always runs, however late. The count of a routine's missed runs, with the first and the last, is kept on the routine until its next run starts, and is cleared when the routine gets a new trigger; a routine that misses runs again before that adds them up. It counts up to 1,000: a routine at that count missed at least as many. The cost lies in the transaction that records a run. Finding the latest run and the next one each walks about two days of the schedule's runs, since a run's wall-clock time can lie up to a day from its instant: some 580 steps each for a schedule every five minutes, a handful for a daily one. Counting the missed runs, only when the routine skips, reads at most 1,000 more, so a long stretch of a frequent schedule costs no more than that. Runs, and missed ones, are told by the schedule's own times: a run postponed 30 seconds after it could not be recorded is still the 08:00 run.
- A clock set forward makes the runs it jumps over come due, and the rule above limits what runs. A clock set back moves nothing: the next run is still ahead, and nothing runs twice. A schedule keeps the zone it was saved with ([Triggers](#routines)) when the computer moves to another zone, so an 08:00 routine saved in São Paulo still runs at 08:00 there.
- A scheduled run keeps when it was due. Clients are told that time for a run that started more than a minute after it (`dueAt`), and the routine envelope gives it to the bot, so it reads the dates in the instruction against the day the run was due ([Prompt architecture](../prompts/architecture.md#wake-envelopes)). An attempt tried again more than a minute after its run started gives that time too. The envelope also gives it when the run was due on another day in the operator's zone, however little before: a run due at 23:59:45 that starts at 00:00:15 is not late for clients, but its "today" is the day before.
- A run that comes due while the previous run of the same routine is still going is recorded as `skipped` and does not count as a run.
- `routine.run` runs a routine on demand, paused or not, without resuming it or moving its next run. A retried command is the same run.

**Running.** A run records a `routine` wake for the routine's bot through the wake pipeline, and the run keeps that wake. The main session's dispatcher never takes a routine wake, and the main session is never woken for one. The **routine runner**, a worker like the others ([The workers](#the-workers)), takes it instead:

1. Once the run's next attempt may start, the attempt it retries has its side session archived in the engine or lost (a send of it whose answer was lost may land there yet), and the bot's provider is not at its usage limit, it writes a side session for the attempt's wake, on the bot's provider, which starts the attempt. Then it asks the engine for the thread with the session's id as the key, so a retried request cannot make a second one. An engine that does not offer the bot's model, or that refuses the opening or the bot's permission mode, fails the attempt unsent, as an `unresolved` dispatch that was never sent, and the run tries again after its delay ([Retries](#routines)), in a side session of its own, under a fresh key: the engine keeps a refusal for its key. A refused permission mode is recorded on the run, with the mode the policy allows when the engine reports it, in the transaction that fails the attempt; its retry clears it, so a run that fails for good keeps why its last attempt failed, and its history says so. The same holds for a side session opened before a policy was installed whose turn the engine then refuses to run in its mode: the dispatcher fails that attempt `unresolved`, naming the refusal on the run, rather than as refused, which would fail the run at once.
2. Once the session's events are known and a turn slot is free, it writes the attempt's dispatch into that session as a start, in one transaction that finds the wake still pending, and the dispatcher sends it as it sends every start, unless the provider of the side session reached its usage limit meanwhile, which holds it until the reset. The envelope names the routine, its trigger and instruction, the trigger data, and the routine's five newest settled runs with what each said, as many of them as fit the engine's input limit. Runs from before the bot's latest fresh start count too: a fresh start clears the bot's working context and its catch-up notes, while each routine keeps what its recent runs said, so a run can tell what is new and not report the same thing again. An envelope that does not fit with none of them fails as refused, unsent.
3. A message the bot says in the side session is tagged with the attempt's wake, and adds a catch-up note ([Sessions](#sessions)).
4. Once the attempt's turn has ended, the run settles, and the side session is retired, then archived by the rotator.

A Stop of the bot reaches side sessions too: a wake still pending is cancelled, which settles its run, and a running attempt is stopped, which fails its run without another attempt. A provider change and a fresh start stop the bot's work first ([Rotation](#sessions)), so a run in progress ends this way, and its side session is retired once that Stop settles; the routine's next run opens on the bot's provider and settings then. Deleting the routine cancels a wake still pending, and one whose dispatch was written and not sent yet, held by a provider's usage limit say: that dispatch is released in the same transaction, so nothing of the routine starts after it is gone, and its side session is retired.

**Run history.** Each run has its start, its end, a status and, when it started more than a minute after its schedule's time, when it was due (`dueAt`):

| Status | Meaning |
| --- | --- |
| `running` | Its latest attempt has not ended, or the next one waits |
| `delivered` | The bot said something with `say` in one of its attempts |
| `silent` | Its attempt's turn completed without a message from the bot. It becomes `delivered` if the bot speaks later in the same side session |
| `failed` | Its last attempt failed, the engine refused its envelope, or a Stop of the bot or the routine's deletion ended it |
| `skipped` | It came due while the previous run was still going |

`skipped` keeps that one meaning: a run missed while the server was not running leaves no row, since a new status would change the protocol. It is counted on the routine instead (`missed`, above). A client of an earlier release ignores both fields.

**Retries.** An attempt that fails before the bot says anything (the engine could not open its session or lost it, its turn failed, also before it started, or was interrupted by something other than a Stop) is tried again with a new wake, in a fresh side session: two minutes after the first attempt failed, four after the second, three attempts in all. One whose envelope the engine refused, or that could never fit its input limit, fails the run at once: the next would be refused too. A failed attempt's leftover background work ends when its retry is due ([Sessions](#sessions)). The run's history shows how many attempts started, none for a skipped run. A provider at its usage limit holds the next attempt until the reset, as it holds every automated wake. The last attempt's failure fails the run. Nothing about a failed attempt shows in the conversation; the run's history is where it shows. What the operator stopped is not tried again.

A run settles from its latest attempt, when the runner, the scheduler or the routine next looks. A run whose row cannot be read is logged and left running; the others settle. A silent run keeps no `note` yet: the engine adapter does not surface a turn's final words outside `say`, so there is nothing to keep. A routine keeps its 100 newest settled runs and the run going, counted again as each run settles; its run count counts the runs that started.

### Webhooks

A webhook routine's address is `/hooks/<routine id>/<secret>` on the server's HTTP listener, given to the operator as the routine's `webhookUrl`, built when it is given: a repeated create or update names the listener as bound now. The secret is 32 random bytes, base64url-encoded, drawn when the routine gets its webhook trigger; an update that keeps the trigger keeps it. With `publicOrigin` set ([Configuration](#configuration)), the `webhookUrl` names that origin, for a server reached through a proxy or a tunnel. Without it, the `webhookUrl` names the first address `j3-bots pair` would offer, at the port the listener bound (the one the system chose, when the port set is `0`), written as a browser writes an origin, so `https` on port 443 names no port: with TLS, the first DNS name on the certificate; with `lan`, the first private address of a real interface (not loopback, a container or a virtual network), read when the URL is built; otherwise the address set. With none, it says what `pair` says: with TLS, `<a name the server's certificate covers>` in place of the host; with `lan`, `127.0.0.1`.

- **Authentication.** The secret in the path is the credential, checked before the body or a header the route acts on (`Idempotency-Key`, `Content-Length`) is read. The server compares SHA-256 digests of the given and the stored secret with Node's `timingSafeEqual`, also when there is no such routine, and answers a wrong secret, an unknown routine and a routine with another trigger alike: `404`, and it closes the connection after answering. The route never reads the body of such a call; bytes the caller already sent are discarded as the connection closes, and a caller that waits for `100 Continue` is never sent one, so it sends no body. A proxy in front of the server may wait for or buffer the body before it forwards the request. Refused calls are not limited ([Security](security.md#j3-bots-own-surface)). The server keeps the secret out of its logs: the request log records any path under `/hooks/` as `/hooks/…`, with the method and the status and nothing else, whether or not a webhook answers it, and no trace span is made of such a request. A call that fails answers `500`, and what went wrong is logged on its own line, without the request. An HMAC signature over the body is not checked: the routine contract has no field to require one, and a signature that is optional adds nothing.
- **The body** of a call that named its webhook is read up to 64 KiB (`413` past that) and must be UTF-8 text (`400` otherwise). It is stored with a `running` run as its trigger data. A `skipped` run keeps its `Idempotency-Key` but not the body.
- **Replay.** A request with an `Idempotency-Key` header (at most 200 characters) is recorded once: the same key again answers the run it recorded, with `200`, for as long as that run is kept in the history. Without the header, every request is a new call.
- **Rate.** A webhook call is refused while the routine has recorded ten runs in the last minute, skipped ones included: it answers `429` with `Retry-After`, the time until fewer than ten remain, and records nothing. A run the operator asks for is not limited, so it can take the count past ten.
- A paused routine answers `409` and records nothing.
- An accepted call answers `202` with the run's id and status, `running` or `skipped`.

## Templates

A template is a bot as a file to share, what makes it do its job and nothing it learned ([decision 0023](../decisions/0023-a-bot-template-is-a-file.md)); its schema is `BotTemplate` in `packages/contracts`.

**`bot.template`** builds one from named fields, never from a copy of anything larger: the profile, the model and the permission mode from the bot's row; each routine's name, instruction and trigger, a schedule as its cron alone and a webhook as the fact that it is one, with no one-time routine; and the skills from the bot's workspace as it was first provisioned. A skill is a folder of `skills/` whose name is a skill's name (one lowercase segment), that is a real folder holding a `SKILL.md` that is a regular file within the limit; a link is never followed, and a folder that breaks any of this is passed over. Folders are taken in name order, and skills and routines past the limits (16 each) stay out. Memory, the conversation, files, the routines' time zones and webhook addresses never reach it; the job, the skills and the routines' instructions go as written. The template is then measured as its file is written (`templateFileText` in `packages/contracts`, the same text the clients save), and one over 1 MiB of UTF-8 is refused with `TemplateTooLarge`, which names its largest part: the limits count characters, so text of several bytes a character can fit them and still make a file no client would read.

**`bot.createFromTemplate`** makes a bot from one, as `bot.create` does, in the same transaction and under the same command receipt, then, before the transaction commits:

- each routine, paused, with no next run, authored by the operator, who approved it in the preview; a schedule takes the operator's time zone, and one that cannot run refuses the whole command with `Invalid("schedule")`;
- each skill's `SKILL.md` under the new workspace's `skills/<name>/`, written through the workspace layout, which refuses a location that would expose a private one (`Conflict("private-location")`).

A creation that fails at any step, before or after the skills were written, rolls the transaction back and removes the workspace it started, so no bot is left half made. That holds for `bot.create` too, which writes nothing there before it commits.

The model is the command's, else the template's when the engine offers it, else the server's default. The permission mode is the command's, which a client sends only when the operator picked one, else the less permissive of the template's and the default for the model as it stands then (supervised for a mode this build does not know). The avatar is the template's when the server has its tokens, else one no other bot wears, as for any new bot. The bot is never made primary, and its opening wake is any new bot's: its first turn works from its job as written. A field the template's schema does not name is dropped as the payload is decoded, so it never reaches the bot; a client refuses such a file before this. The command is not decoded strictly, since the RPC's parse options also govern how a client decodes the reply, which would make an older client refuse a newer server's added fields of `Bot`.

## Connectors

New in 0.4.0. The contract is in `packages/contracts` (`connector.ts`, `ConnectorRpcs`). The server serves all of it: a connector added by address, from the gallery or by command. A connector is a service a bot uses through J3 Bots: an MCP server reached over Streamable HTTP, or one the server starts by command. The server is its MCP client and its OAuth client, and holds every secret it needs ([decision 0026](../decisions/0026-a-bot-uses-connected-services-through-j3-bots.md)). Bots call its tools through the `j3` bridge, under their permission mode ([decision 0027](../decisions/0027-connector-tools-reach-a-bot-through-the-j3-bridge.md)).

**What the server keeps.** For each connector, in the `connectors` table: its id (`conn_…`, chosen by the client that adds it, so adding again after a lost reply finds it), its name and glyph, a slug that names its tools, the gallery entry it came from, how it is reached as clients are shown it, how it signs in, the fields its form took without their values, whether the operator confirmed an address in their own network, its grant (`connector_bots`, or every bot), when its form was last given, the tools the operator accepted and the review they kept. The secrets are in the vault, a record per connector ([decision 0028](../decisions/0028-one-secret-store-for-logins-and-connector-secrets.md)): its OAuth client, tokens, header values and environment, and the address the operator typed or the command's arguments, either of which can carry a key in a path, a query or a flag. Nothing in J3 Bots' database holds a value of them. A client is shown how a connector is reached only as the address's origin or the command's program (`displayTransport`), in what `connector.add` answers as on `connectors.subscribe`; a secret a command needs belongs in its environment, which its form masks. What the server saw of a connector since it started (its last listing, a failure, a refused key) is kept in memory, not in the table. A removed connector's row goes at once; `connector_removals` keeps, in the same transaction, what is left to do outside the database (revoking an OAuth sign-in, deleting the vault record) until it is done.

**The gallery.** `connectors.list` gives J3 Bots' curated list, in the client's language; `connectors.search` adds the MCP Registry's matches after it, and says when the registry did not answer; `connectors.get` gives one entry's page and the form Connect shows. The server answers them from `apps/server/src/connectors/sources`.

**The curated list** is a file shipped with the server (`curated.json`), reviewed for each release. Its text is J3 Bots' own, in every language the interface has; a service's name is a trademark it only names. Each entry has one of J3 Bots' own glyphs, line drawings of what the service does that the clients ship (`CONNECTOR_GLYPHS` in `packages/design-tokens`), never a vendor's logo or an image fetched at run time. Each also carries its address, so the gallery works when the registry does not answer, and its address is never taken from the registry: a change there cannot move a curated connector. An entry connects one of three ways:

- **One tap** (`sign-in`): Notion, Linear, Atlassian, Stripe, Figma, Vercel and Supabase let any client register itself, so the operator only signs in.
- **A token in a header** (`token`): GitHub, with a fine-grained personal access token, and Linear, with an API key instead of a sign-in. The entry links to the page that makes the token and says which permissions to give it.
- **Bring your own app** (`own-app`): Google (Gmail, Calendar, Drive, Docs, Sheets, Slides, Chat and Contacts) and Slack accept only an OAuth client the operator registers. The entry's setup steps say how; every Google connector uses the same client. Google's servers are a Developer Preview that answers only accounts in Google's Workspace Developer Preview Program, which the entry says before anything else (**Read**, Google's documentation, 2026-11-23). Slack lets only its directory's apps and a workspace's own internal apps use its server, so the operator creates one in a workspace they administer (**Read**, Slack's documentation).

The file is decoded at start like any other input, and refused, with the server, when an entry lacks a language, an address is not `https:`, a glyph is not one J3 Bots draws, a key is listed twice, or an entry cannot be connected.

**The MCP Registry** (`registry.modelcontextprotocol.io`, API `v0.1`) is searched through the server; clients never reach it, and nothing mirrors it. It holds tens of thousands of entries, most mass-published, and its search matches names only (**Verified**, 2026-11-23). So the server budgets each search:

- at most three pages of 100, each answer read up to 1 MiB, each request given 5 seconds and the whole search 8; when a later page fails or the time is spent, what was read is used;
- two requests to the registry at once, across every search;
- results ranked and cut to 40 per query, then cached for an hour (32 queries), and an entry read by name for a day (128 entries). A search the registry did not answer is remembered for a minute, so each keystroke does not wait on it again. The caches are memory only: they are rebuilt after a restart and never reach a snapshot.

Within those, entries the registry marks deleted or deprecated are dropped, and so are the registry's copies of curated entries, by name or by address. The ranking puts first the entries whose namespace's domain owns their remote's host (`com.notion/mcp` at `mcp.notion.com`): the registry verifies a namespace when it is published, so such an entry was published by whoever runs the service. It shows as "from notion.com", never as verified: the registry reviews nothing else. Then come names closest to the query. Mass publishers and wrappers of other companies' services, which fill most searches, fall behind. Without `all`, only entries J3 Bots can connect are listed: a server reached only over the legacy SSE transport, or only by installing a package, shows as `unsupported`.

**The connect form** comes from the remote's `server.json`: its first Streamable HTTP remote at an `https:` address. Each URL variable becomes a plain field, masked when the publisher marks it secret; each header with no fixed value becomes a field, masked when the header is secret; a header whose fixed value names variables (`Bearer {api_key}`) asks for each of them, masked when the header or the variable is secret. A variable the publisher named but did not declare is still asked for, with the header's description and secrecy: sending its braces as written, which the schema allows, would make a request that cannot work. A field with a default is optional and shows the default as its placeholder; one with choices takes one of them. The values the operator gives are redacted from the moment they are decoded. Filling the form refuses a value with a control character, which could start another header, and a field the form does not have; a URL variable is percent-encoded, so it cannot leave the part of the address it fills; and a secret part of the address stays out of the address shown. A remote is not offered when it asks to set a header the transport owns (`Host`, `Content-Length`, `Mcp-Session-Id` and the like), declares a malformed header, or asks for more than 16 fields. Publisher text is shown as plain text: control and direction-changing characters taken out, cut to the contract's lengths.

**Not a source: `cursor/community-plugins`** (the directory behind cursor.directory). Its repository has no licence, so all rights are reserved, and its data lives in a hosted database outside it. J3 Bots neither imports nor fetches it, at build time or at run time.

**Adding.** `connector.add` takes a gallery entry with its form's values, an address with headers and an optional OAuth client, or a command. Without a grant it goes to the bot whose suggestion card it answers, else the primary bot, else no bot; the card closes as `connected` when that bot gets the connector. An address in the operator's own network is refused with `Conflict("private-network")` until the client sends it again saying the operator confirmed it. Without an OAuth client, the server lists the address's tools first, signed with the headers given, and that listing becomes the tools the operator accepted. A connector its server refuses becomes one that signs in with OAuth when it was given no headers, and one whose form needs new values when it was; one that does not answer is added as `failing`, and its tools are listed once it answers. With an OAuth client, the sign-in follows. A gallery entry is added from its form: the server builds the form again from the entry, in the language the client names, which the connector keeps its name and its fields' labels in, fills it with the values given, and adds the address and headers that gives as it adds one typed, checked by the same rules, never as one in the operator's own network. An entry whose form cannot be filled is `Invalid("connector-fields")`. How an entry signs in is its own, and a client cannot change it: an `own-app` entry needs the operator's client and is the only one that takes one; a `token` entry signs in with its form; a `sign-in` entry signs in with OAuth unless its server answers without one. An entry that would sign in with OAuth while its form put a key in its address is `Invalid("connector-unsupported")`, since a sign-in sends that address to the authorization server and through the browser. The connector shows the address's origin only when it is the entry's, so no value the form put in the host is shown. Its slug is chosen in the transaction that stores it, so two connectors added at once with one name get two. A connector that needs a secret needs the vault set up and unlocked to add it; if it cannot be stored, its vault record is deleted again.

**New values.** `connector.update` replaces the values a connector's form took. For a gallery entry, the server builds its form again, from the curated list or from the registry's entry (`Conflict("registry-unavailable")` while the registry does not answer and has no copy cached), and renders again each header a value is given for, from every value that header takes, an optional header left out when the connector was added included; a header no value names keeps what it had, and a value for a field of the address is `Invalid("connector-fields")`, since another address is another connector. For a connector added by address, a value names its header. The values go to the vault only, a secret field's own value with them.

**Connectors started by command.** The operator adds one from the web or desktop app; the Android app shows them and adds none, a convention of the apps, since every paired device holds the operator's authority. It is an MCP server the server starts on its own computer, as its own user, and speaks to over its standard input and output (`packages/connectors`, `command/`):

- **Consent.** Before the server first runs a command, the client shows the operator the whole command line, the program and every argument, and the name of each environment variable, without its value; `connector.add` with a command is sent only once they confirm. A new command line is shown and confirmed the same way, and sent whole with `connector.update` (`command`): the server stops the running process, forgets what it saw of the old one, and starts the new one to list its tools, where a tool that is new or changed waits on the operator's review as for any connector. The form takes new values only for the variables the command already names (`values`); adding, removing or renaming one is a new command line. A changed value stops the process too, and starts it again with the new one. One change of a connector runs at a time, so two clients changing it at once cannot lose either's values.
- **Exact versions.** A command that fetches a package as it starts, through `npx`, `npm exec`, `uvx` or `uv tool run`, must name every package it fetches at an exact version, such as `@scope/server@1.2.3` or `server==1.2.3`, so the code that runs is the version the operator saw. A version is exact as semver writes it, since npm takes anything else, such as `1.2.3-..`, for a tag. A tag such as `latest`, a range, no version, a URL or a path is refused as `Invalid("command-unpinned")`, when it is added and when it changes, and so is an option of the launcher's the server does not know, since it could name another package, and `npx -c`, which runs a shell line. `npm exec` reads its own options after the package too, so through it the package must follow `--`. npm takes any prefix only one of its commands has for that command, so a word that could be `exec`, `init` or `create` (which run a package too) is refused, as is an option before npm's command, which may take the next word as its value; uv's own options are read wherever they come before its command. The program is named by the file its path leads to, `.` and `..` read and Windows' trailing dots and spaces dropped, and checked again on the file found at each start. A launcher's settings in the environment can choose another package or registry, so a variable of the operator's named `npm_config_*` for npm, or `UV_*` for uv, is refused too. Any other program runs as given. The check is `pinRefusal` in `packages/contracts`, with `reservedVariable` for the names below, so a client's form says what the server would refuse before it sends a command line; the server checks again.
- **Its environment.** Only the server's `PATH`, `HOME`, `LANG`, `LC_ALL`, `LC_CTYPE` and `TMPDIR` reach it on Linux and macOS, and on Windows what Windows' own programs need to start (`PATH`, `PATHEXT`, `SystemRoot`, `ComSpec`, the profile and program folders, `TEMP` and `TMP`, and the like), then the operator's variables, which replace any of the same name; nothing else of the server's environment, such as a provider's key or J3 Bots' settings. Windows reads names without case, so a command may not name a variable twice in any case (`Invalid("connector-fields")`). Nor may it name one the server reads to find and start the program, in any case: `PATH`, `PATHEXT`, `SystemRoot`, `windir`, `ComSpec` and `PSModulePath`, since a value changes without a new confirmation and these would choose which program runs. A command has at most 32 variables, each one of the connector's fields. Node gives its children a `NODE_V8_COVERAGE` of its own unless told otherwise, so the server leaves it out of the process's environment unless the operator gave it. The command line, program and arguments together, and the variables' values are kept in the connector's vault record, redacted from the request that carries them to the process's start, and read from the vault at each start: the program the connector's row shows is never what runs, and a new command line replaces the old one in one write, so no start runs half of each.
- **How it starts.** With no shell. A program named without a folder is looked up on the command's own `PATH` (with `PATHEXT` on Windows), skipping a folder of it that is not absolute; a path is taken from the folder the command runs in, the home folder of the server's user. One that is not found is `failing` (`command-not-found`). While the server's own `NODE_DEBUG` names `child_process`, Node writes what it starts a child with, values included, to the server's standard error, so no command starts, and the connector is `failing` (`command-exited`). On Windows, a batch file such as the `npx.cmd` npm installs runs through the command interpreter, which reads its own syntax in the arguments however they are quoted: one with a quote, `%`, `!`, `^`, `&`, `|`, `<`, `>`, a parenthesis or a control character is not started, and the connector is `failing` (`command-exited`).
- **Its life.** A process starts when the connector is first used, by a listing or a bot's call, never ahead: after a restart of the server, a connector whose tools the operator accepted waits for a bot to call one. One process serves every bot granted the connector; the grant is checked on each call before it reaches the process. It stops after ten minutes unused, when the vault locks, when its command or values change, when the connector is removed, and with the server. Each of these but the idle one stops it at once, even in the middle of a call, which then fails: a process started with a value or command line the operator replaced does not run on. A start still waiting out its pause, or under way, when a stop comes is dropped and runs nothing. A change is written to the vault and the old process stopped as one step that a client's disconnect does not interrupt. One that ends by itself, or fails to start, is `failing` (`command-exited`) and started again by itself after a pause of a second, then twice as long each time it ends or fails again, up to a minute, starting over after a run of a minute; after five in a row it is left stopped until a value or the command line changes, or the server restarts. Every start that fails counts, however long it took; only a process that opened its session and then ran a minute starts the count over. A bot that calls it during a pause waits for it. At most one process runs per gibibyte of the computer's memory, from 2 to 12, so a Raspberry Pi runs only a few: a start past it stops the one unused the longest, and when every one is in use, the call is answered as the server being busy.
- **How it stops.** Its input is closed, as MCP asks of a client, and it has two seconds to end. On Linux and macOS it leads a process group of its own, which then gets `SIGTERM` and, three seconds later, `SIGKILL`, so a process it started ends with it. On Windows, which has no process groups, it runs in a job object that ends every process in it once the launcher holding the job ends (`inJob` in `packages/processes`, as the engine's processes do, with its standard streams relayed); ending the launcher ends them all.
- **What it says.** A message is a line of JSON-RPC; a line that is not one, as a server that logs to its output writes, is skipped, and a message longer than 10 MiB ends the session, as does a process that would leave more than 10 MiB of what was sent it unread. Either way the process is stopped, whether or not a call was waiting, and started again after its pause. What it answers is scrubbed of the values of the variables the operator gave it, as given and as a JSON string holds them, as a remote server's answers are of its credentials; its arguments are not, since they are the command's own words, such as a folder it serves. Its standard error goes nowhere: a server may print what it was given there, so none of it is read, kept or logged.
- **Logs.** The connector's id when its process starts, stops or ends by itself. Never the command line, an argument or a variable.

**Removing.** `connector.remove` takes the connector out at once, whether or not the vault is open: bots lose its tools and its sessions close. Then its OAuth sign-in is revoked and its vault record deleted, both of which need the vault: while it is locked, they are done when it next opens, from the removal recorded with the row's deletion.

**Signing in.** `connector.beginSignIn` starts a sign-in bound to the device that asked, for ten minutes, and answers the address that device opens in the system browser. The browser returns to the server's own address when it is `https:` or the server runs on the device's computer (`server`), to a listener of the desktop or Android app on loopback, which relays the address it caught (`relay`), or, from the web client, to a page nobody answers, whose address the operator pastes (`paste`). Each returns under `/oauth/callback`, at a path of the authorization server's own: its issuer's host, then its path exactly as written, trailing slash included, as `/oauth/callback/accounts.google.com`. The relayed or pasted address comes back with `connector.completeSignIn`, which only that device may send; the browser's return to the server's own callback finishes only a sign-in begun as `server`. The `state` travels in the address the device opens and comes back with the code; the PKCE verifier never leaves the server, so a code caught by anyone else is of no use.

**Finding where to sign in.** The server follows the MCP authorization specification, revision 2025-11-25. It reads the connector's full address from its record in the vault, since it can carry a key. It sends the connector's server an `initialize` without a token and reads the `Bearer` challenge of its `401`. The protected resource metadata (RFC 9728) is where the challenge's `resource_metadata` says, else at the path-inserted well-known address, then at the root one. Its `resource` must cover the connector's address (the same origin, and a path that is the address's or one above it, segment by segment), and its first authorization server is the one used. It is refused, as `sign-in-unsupported`, when it holds a secret value of the connector's form, as given or URL-encoded, since it goes in the browser's address. That server's metadata is looked for at the RFC 8414 address, then OpenID Connect's inserted and appended ones, in the specification's order. For both documents, an address that answers `4xx`, something that is not a metadata document (a page a catch-all route serves), a `5xx` or nothing is passed over for the next; when none has the document, discovery failed as unreachable if an address did, else for want of metadata. The document's `issuer` must be the one asked for, character for character, every endpoint `https:`, and `S256` among its PKCE methods. A connector that fails any of this is `Conflict("sign-in-unsupported")`, and one whose server did not answer is `Conflict("sign-in-unreachable")`. The scopes asked for are the challenge's `scope`, else the resource's `scopes_supported`. Metadata is kept an hour.

**The OAuth client.** J3 Bots registers itself with the authorization server (dynamic client registration, RFC 7591) for the address the sign-in returns to, as a public client when the server allows that, else with a secret it keeps in the vault; a registration the server refuses is `Conflict("registration-refused")`. A client registered earlier is used again when the same issuer has the sign-in's address registered. A relayed sign-in returns to a new loopback port each time, so a loopback address registered with another port counts as the same: RFC 8252 §7.3 asks an authorization server to accept any port for one (**Assumed** that each service does: one that does not shows its error in the browser, and the sign-in never comes back). The new client is kept only once its sign-in finishes, so a sign-in abandoned halfway leaves nothing in the vault, and the next one registers again: a client is used again only once a sign-in with it has finished. For a service that registers nobody, such as Google or Slack, the operator registers an app of their own and gives its client id and secret when adding the connector, and its issuer when the gallery entry does not name it. The entry's page (`connectors.get`) gives the addresses to register, as the server would send them: back to the server itself, from `publicOrigin` or the loopback address it listens on, and to a device's loopback ([Google](../operations/connector-google.md), [Slack](../operations/connector-slack.md), drafts). The app is used only when discovery finds that issuer, so a connector that names another authorization server never gets its secret; it authenticates with `client_secret_basic` when the server offers it, else `client_secret_post`. That client is never replaced, a sign-in started with another ends when it is given, and the operator registers at the service the addresses their sign-ins return to. A curated `own-app` entry also names the scopes its sign-in asks for and any parameters the service needs to give a refresh token (Google's `access_type=offline` and `prompt=consent`); the list is refused at start if one of them is a parameter J3 Bots sets itself. Client ID metadata documents (CIMD) are not supported yet: one needs a document J3 Bots publishes at an `https:` address of its own.

**The sign-in.** The address the device opens carries `response_type=code`, the client, the exact redirect, the PKCE challenge (S256 of a 32-byte random verifier), a 16-byte random `state`, the `resource` (RFC 8707) and the scopes. The returned address must be the redirect itself, query and fragment aside, and name the sign-in's `state`; when the authorization server sends `iss` (RFC 9207), or says it will, it must be its issuer. Since no two authorization servers share a redirect, an answer one of them sent cannot finish a sign-in at another, `iss` or not (mix-up, RFC 9700 §4.4). A sign-in ends when it is used, after ten minutes, when another starts for the same connector, and with the server. A sign-in, another client or a sign-out for the connector that comes while a sign-in is prepared (discovery, registration) ends it before its address is given, and one that comes while a code is being exchanged wins: the tokens that exchange gets are dropped. A connector removed meanwhile is never written back to the vault. Its code is exchanged with the verifier, the redirect and the `resource` again, authenticated as the client's registration says (none, `client_secret_post` or `client_secret_basic`).

**Tokens.** Every request to an authorization server, and the discovery request to the connector, has 15 seconds from connecting to the last byte of its answer, reads 64 KiB at most, and records no trace span, since the connector's address can hold a key. Only `Bearer` tokens are accepted. They are kept in the vault with when they expire, the scopes granted, the resource and when the operator signed in, which a refresh keeps; the connector's page shows that date. OAuth does not say which account at the service signed in, so none is shown. A worker per connector refreshes the access token five minutes before it expires, or halfway through a shorter life. A refresh that fails for a reason that may pass (the service down, a malformed answer) is tried again after 30 seconds, then twice as long each time up to 15 minutes; once the token has expired with the refresh still failing, the connector is `failing`. A refresh token the service rotates replaces the old one, and the request and the save are one step that nothing interrupts. When the vault locks while the answer is on its way, the rotated tokens are held in memory and saved at the unlock, and before any later refresh, so the refresh token they replace is never sent again; until then a call may still be signed with the access token the vault holds, while it lasts. A server that stops first loses them, and the connector then needs a new sign-in. One refresh at a time runs per connector, and a call that finds the token within a minute of expiring waits for it. A token given without a refresh token is used until it expires, then the connector needs a sign-in; an `expires_in` of `0` is a token that has already expired. A refresh answered with such a token keeps the refresh token it may have rotated and counts as failed: it is tried again after the wait, and no call is signed with it. When the connector's server refuses a token, the refusal says which token the request carried: one a sign-in or a refresh has replaced since is left alone, and the request goes again with the current one. A refused refresh (`invalid_grant`) signs the connector out: it `needs-sign-in` (`expired`). A refused client (`invalid_client`) also drops a client J3 Bots registered, so the next sign-in registers again; the operator's own client stays. When the connector's server refuses a token with `insufficient_scope`, no refresh is tried, since a refresh cannot widen a grant: the call needs a new sign-in. A sign-in asks for the scopes the connector's server names, those already granted, and each scope a call was refused for that the grant still lacks, so no call loses its scope to another's. Locking the vault stops every worker; unlocking starts them again.

**Signing out.** Removing a connector revokes its refresh token, then its access token, each asked for whatever became of the other, where the authorization server offers revocation (RFC 7009), then deletes them, with a client J3 Bots registered. Tokens a refresh holds while the vault is locked are the latest, and the ones revoked. A revocation that fails is logged and not tried again: the tokens are gone from J3 Bots either way.

**The client.** `packages/connectors` is the server's MCP client, on the official TypeScript SDK's client package (`@modelcontextprotocol/client`, pinned at 2.4.0, Apache-2.0): it speaks the protocol's 2025-11-25 version over Streamable HTTP, including the session and its notification stream, and brings few dependencies. J3 Bots supplies the transport's `fetch`, so every request goes through its own connection code (below), never the SDK's.

- **Sessions.** A bot's calls to a connector go through that bot's own session, since a session can hold state at its server, such as a page or a cursor. A connector started by command has one session, its process's, for every bot ([above](#connectors)). The server keeps one more per connector to list its tools. A session opens on the first request that needs it and closes after ten minutes unused; at most 32 are open at once, idle ones included, and a call that would open a 33rd is answered as the server being busy, with nothing recorded against the connector. A session that fails to open is not kept, and one that ends in a network failure, a reply that is not MCP or an error from the server is closed: the next call opens another. A connector's sessions close when the vault opens or locks, when its sign-in changes, and a bot's when the bot loses the connector.
- **Signing.** Every request reads the connector's headers and, for OAuth, its access token at the moment it goes out, and adds them then; the session keeps no copy. A stored header the transport sets itself, or one that would change how the request is framed (`Host`, `Content-Length`, `Mcp-Session-Id` and the like), is refused, as is a value with a line break: no request is sent, and the connector needs its form again. A bot's session first checks that the bot is still granted the connector, and a request it no longer may make is not sent: the call is answered as no tool the bot is offered. A `401`, or a `403` whose `Bearer` challenge says the token lacks a scope (`insufficient_scope`), asks the sign-in for new credentials once, naming the token that was refused so one renewed meanwhile is not renewed again, such as an OAuth refresh or a sign-in with that scope, and sends the request again; a second refusal, or one for a connector with only headers, means it needs a new sign-in or new values.
- **Limits.** Opening a session, or listing every page of its tools, may take 30 seconds, and a call 10 minutes; the `j3` bridge waits 11 and a harness 12, so the server's own deadline answers first. A connection may take 10 seconds to open, and once open the server has 11 minutes to begin its answer, which bounds what the SDK sends on its own. An answer is read up to 8 MiB. A listing is read page by page, up to 64 pages and 8 MiB of tools once cleaned, which is all it holds: past either, it fails as too large. A bot reads at most 100,000 characters of a tool's text: past that the text is cut, and the bot is told so. A call interrupted, as stopping the bot does, or out of time is cancelled at the connector's server (`notifications/cancelled`), and its request is aborted, closing its connection: the SDK alone does not close it (**Verified** at 2.4.0 with a test server), so the fetch J3 Bots gives it knows which call each request belongs to and aborts it with that call.
- **Where it connects.** A connector's address is `https:` with no user name or password. The name is resolved when each connection opens, and every address it resolves to is checked then, so a name that resolves to another address later (DNS rebinding) is checked again: loopback, link-local, unique-local, private and reserved addresses are refused, apart from the operator's own network for a connector they confirmed it for. The cloud metadata services' addresses are refused even then ([Security: connectors](security.md#connectors)). A redirect is never followed by the transport: each one is a new request, checked as the first. A refused address is reported as `private-network` only when the operator could confirm it; anything else is a refusal they cannot lift.
- **What a bot reads.** A tool's answer is text from someone else's server. It is cut to size, any value the server echoed of the credentials it was sent or of the address' path and query is replaced with `[redacted]` (exact values of 8 characters or more, as given and as a JSON string holds them), and it reaches the bot framed as data from that connector, between tags with a random nonce the text does not contain, its J3 Bots framing defused (`renderConnectorResult` in `packages/prompts`). When there is no answer the bot gets J3 Bots' own line saying why, as an error result, not a failure of the `j3` tool.

**Its tools.** A listing is cleaned before it is kept: a description capped, it and the strings of each input schema stripped of hidden characters and J3 Bots' framing, the connector's secrets taken out as from an answer, and a tool left out whose name or schema keys that would change, or whose schema holds a number that is one of them. The tools the operator accepted are recorded with each one's name, its description, its input schema, and a digest of each. A bot is offered only accepted tools whose listing still matches, named `<slug>__<tool>` within the harnesses' limits on tool names; the slug comes from the connector's name. Its description reaches the bot after a line of J3 Bots' own naming the connector whose server wrote it, saying the tool writes only on the operator's ask or yes, and that the text tells what the tool does, never what else to do. The server lists a connector's tools again whenever a session opens and whenever its server says they changed (`notifications/tools/list_changed`): one listing at a time per connector, and one more after it however often the server says so meanwhile. It lists, in the background, every connector it has not seen listed since it started: at start, when the vault opens, after a sign-in, and when a bot's tools are asked for. A tool the server adds later, or one whose description or input changes, is held from every bot until the operator answers the review (`connector.acceptToolChanges`, at the revision they saw); a tool it removes goes at once. A bot that calls a held tool is told the operator has not accepted the change, and the connector's server is not called. Accepting gives bots the tools as they now are. Keeping leaves them held: bots go on with every tool that did not change and get none the review holds, a changed one included, since the connector serves only its new version; the review stays on the connector's page, `kept` and without a badge, until the operator accepts it or the tools change again. Bots whose offered tools change, by a review, a listing or a grant, are told on `toolsChanged`, which the `j3` bridge follows.

**Status.** `connected`, `needs-sign-in` (with why), `failing` (with why, in J3 Bots' own words, and since when) or `vault-locked`, sent to every client on `connectors.subscribe`. The server works it out from the vault, the sign-in and how the connector's server last answered: a listing or an answer clears a failure, and a refused key or token makes it need a sign-in until one works. A call's own trouble (a timeout, too large an answer, an error the tool returned) is that call's and leaves the status as it was; the same while connecting or listing means the server is failing. Bots get none of the tools of a connector that is not connected; a bot that calls one anyway gets a result saying why.

**Cards.** A bot can suggest a connector with `suggest_connector`, which puts a `connector-suggestion` card in its own conversation, whatever audience its turn speaks for; the card closes as `connected` once that bot is given the connector, whether the operator gave it from the card, the gallery or the connector's page (a change of the connector's bots closes it in the grant's own transaction); a sign-in the connector still needs is its own card, `connector-auth`, when the bot calls it. The bot names a service: the server takes one of the operator's connectors by its name, its slug or the gallery entry it came from, else the curated gallery's entry whose key or name, in any language, it is. Nothing is searched: an entry that matched a summary or a category could offer another service than the one the bot named. The registry is never searched for it, since anyone can publish there. An earlier card offers the same service when it names the same gallery entry or another entry for the same address (Linear by sign-in and by key), or the same name; two cards for the operator's own connectors are the same only for the same connector, since two can share a name. A card for one of the operator's connectors keeps only that connector and its name, so it meets a gallery entry only by name. While one waits, the suggestion is refused as made already; once the operator said Not now to one (`card.answer` with `dismiss`, which wakes nobody), it is refused for good in that conversation. The checks and the card are written in one transaction, and the answer, refusals included, is stored with the call, so two calls at once show one card and a forward retried answers the same. When a bot's call finds that a connector needs a new sign-in, that bot's conversation gets one `connector-auth` card for that sign-in's end: no second one while it is open, and every open one closes as `signed-in` when the operator completes a sign-in, or as `removed` with the connector. A sign-in that comes back by itself, as when the vault unlocks, closes none. Both notify, as `connector`, and the notification's `connector` says which card it is, so a push words a suggestion apart from a sign-in to give again. A sign-in that ends while no bot calls the connector shows only in its status.

**Cost.** A connector started by command costs what its server costs while it runs, which is why it runs only while used and how many may run depends on the memory. A session idles at a few kilobytes, and its notification stream is one idle HTTP request; at the 32-session bound, the server's memory for them is **Assumed** to stay well under 20 MB. This fits a Raspberry Pi with room to spare. A connector's tools add to the tool list every model call pays for, which is what deferred tool loading in the harness keeps small.

**Logs.** A connector's id and host, the tool's name, the outcome, the HTTP status and how long it took. Never a call's arguments or result, and never a secret ([Security: connectors](security.md#connectors)). A sign-in logs its connector and, when it fails, a reason in J3 Bots' words; the request log shows the callback as `/oauth/callback`, without its query, however its path is spelled.

## Budgets

Three limits keep bots from spending the operator's allowance on each other. All three have conservative defaults and are part of the operator's settings (`settings.get`, `settings.update`), with the time zone and the notification preferences. Only the operator changes them; nothing a bot or a message says raises one.

| Limit | Default | Applies to |
| --- | --- | --- |
| Hops | 4 | Consecutive bot-caused wakes in one chain since the operator last spoke |
| Fan-out | 1 | Teammates one bot turn may bring in, and bots one bot's room message may mention |
| Concurrent turns | 2 | Turns running at once across all bots |

**Hops.** Every wake carries a hop count. The operator's wakes, a routine's and J3 Bots' system events carry 0. A wake a bot's turn causes carries 1 when the turn carries the operator's word (their wake, or their steer the engine accepted into it), so a chain starts again whenever they speak; otherwise one more than the furthest wake or held message the turn delivers. The engine says whether a turn took a steer only once that turn has ended (`steered`, `steer-requeued`), so a steer counts from the moment the engine accepted it for the turn, also one it later runs as a turn of its own. A turn the engine started on its own never carries the operator's word: one that continues an earlier turn counts as that turn ([Rooms](#rooms)), and one that names none takes, when it is admitted, the furthest count of the session's other turns whose background work is flagged, a flagged turn no dispatch began counting by the count it took itself, and keeps that count for the turns that go on with its own work. A flag may outlive its work until the engine's next report, so the count can come out too high, never too low; with none to trace it to, it may message no teammate, and its room mentions wake nobody, as its tool result says. A teammate message whose count would pass the limit is not sent. In a room the limit is the room's own, set from this one when the room is created and changed with the room: a `say` whose mentions would pass it is still published in the room, but wakes nobody, and its tool result says so.

**Fan-out.** In a room it bounds the members one `say` may list in `mention`, the operator's word or not: past it the `say` is refused with nothing published, and its error names the limit. For teammate messages, it counts the distinct teammates one turn messages, with two exceptions. A turn the operator spoke in, by the wake that started it or a steer of theirs the engine took into it (`steered`), counts none: the operator asked for the work. A continuation, or a turn the engine started for a turn's background work, inherits no such word: it counts the teammates its whole chain brought in. So does the continuation of a steer the engine made a turn of its own (`new-turn`). And a teammate whose message the turn carries, as a `bot` wake or a held message in its envelope, is answered, not brought in. Past those, a turn may bring in at most the limit; messaging a teammate it already messaged is no wider.

**Refused at the source.** A budget is checked by the tool call that would pass it, in the transaction that pins the call, against what is committed for the pinned turn: its wakes, its held messages, the teammates its earlier calls reached. SQLite serializes writes, so two calls never both take the last hop or the last teammate. Nothing past a budget is ever written, so the dispatcher checks none. A refusal wakes nobody, not even to report it: a wake to report a budget stop would itself be a bot turn spent. The tool's refusal tells the bot, and the place where the chain stopped shows it in one quiet `chain-stopped` line, once per turn however often the turn tries: the sender's conversation for a teammate message, the room for a room message. Nothing is dropped silently.

The concurrent-turns budget counts one fact, read again before each first send: a session with work the engine may have, a turn its events show or a dispatch sent at least once and not settled. A dispatch never sent holds no slot, also while its files wait to be staged again. Every start, a staging retry included, needs a free slot or one its session already holds, checked again when its first send is claimed.

## Notifications

The server sends a notification when a bot adds an entry to a conversation or room and no connected client currently has it in view. A bot that starts waiting on the operator adds a card, so a question, an approval or a credential request notifies the same way.

**What notifies.** A bot's message and its question, approval, credential, browser help and connector cards. Nothing else does: the operator's own entries, a turn's work fold, notices (quiet lines by design; the roster shows a blocked bot), routine changes (the bot's own message about one notifies) and teammate messages, urgent or not ([Teammate messages](#teammate-messages)). A push an earlier release recorded for an urgent teammate message still goes out, in the channel it had (`handoff`). Every notification follows from an entry, so a routine run that ends silently, which adds none, never notifies, and one that speaks notifies like any message.

**What is in view.** Each socket reports what the operator is looking at through it (`client.view`): a conversation or room, or nothing. A client reports a target only while its window shows it uncovered (no details sheet or dialog, such as Settings, an editor or a confirmation, over it), is visible and has focus; otherwise it reports nothing. The server keeps each socket's report in memory, and forgets it with the socket, so a client reports it again on every connection. An entry is in view when a socket of a device paired and not revoked reports its target.

**Who is told.** The server knows which paired device each socket belongs to, and groups sockets by device. For an entry that notifies, it works out two sets of devices, both among those paired and not revoked, each device once: the **live recipients**, which have a socket open and are told on every one of them, on its `notifications.subscribe` stream; and the **devices to push**, which have none open and registered for push. Both sets are worked out once per entry, together with what is in view, so a device is told on its sockets or pushed to, never both; a device that connects in between is left to the push. The stream is live only: a notification sent while a device was disconnected is not replayed, since the roster shows the entry unread when it returns. An entry in view, or sent while the operator has notifications off, reaches neither set. A notification names the target, the entry, the bot and the kind of entry, and, when the operator allows previews, the entry's first line, at most 200 characters (`PREVIEW_LENGTH`): the message, the question or the action.

**The operator's time zone** is their device's until they choose one. The server starts at UTC, and every client gives its device's zone when its socket opens (`settings.deviceTimeZone`): the first that gives one the server knows, and that does not keep UTC's clock all year, sets the operator's, in a statement that changes the row only while no zone was set, and rewrites every bot's instructions. After that a device's zone changes nothing, so a second device in another zone, or a laptop on a trip, never moves the routines' clock; only the operator does, in Settings. A zone on UTC's clock all year (no offset in any month, so no daylight saving) is passed over by its clock, not by a list of names: it is what a browser that hides its zone, a machine whose zone was never set or an emulator reports, and it says no more than the UTC the server starts at, so the operator's real device still sets the zone after it. An operator who wants UTC chooses it in Settings, which sets it. A database from before this rule counts a zone other than UTC as set, and lets UTC give way to the first device. On a new server a browser in São Paulo set `America/Sao_Paulo`, and a phone in Lisbon paired after it left that zone, offering its own in Settings (**Verified** with Chrome and the Pixel 8 emulator, Android 16).

**The settings stream.** `settings.subscribe` sends the settings row and then every change to it, from the operator's edits, a device's time zone and a bot's `set_operator_name` alike, so Settings on every device shows the name a bot saved without being opened again. It does not resume: each subscription starts with the row as it is. Each publish, like each render of the base prompt, reads the row while it holds the stream's lock, so of two changes close together the later one is what stays.

**The operator's preferences** are in the settings row (`settings.get`, `settings.update`): whether the server notifies at all (on by default; a browser still shows nothing until the operator lets it) and whether a notification carries a preview (off by default, because a notification can show where others see it, such as on a locked screen). A change names only the switch it turns, and the server merges it field by field in the transaction that saves it, so a device holding a stale copy never turns the other one back. Each notification reads them as it is sent.

- **Web and desktop**: over the open connection, shown by the client.
- **Mobile**: a push through a push service, for a device with no socket open (Push delivery, below).

**Push registration.** A device that can receive pushes registers for them on its own socket (`push.register`): the push service (Expo's, for now), the token that service gave the app, the platform, and the language the device shows, which a push to it is written in. A device registers only itself, never another. A second registration replaces the first, and a token belongs to one device: registering a token another device holds takes it from that device, so an app that paired again is not pushed to twice. `push.unregister` ends the registration, and revoking the device, which signing out does, deletes it in the same transaction, so a revoked device is never pushed to. Both commands check that the device is still paired before they look for a receipt, so a command a revoked device sent before fails with `NotFound("device")` instead of being answered as it was. The Devices list shows which devices have push on.

**Push delivery.** For each device to push, the server writes a delivery in the transaction that adds the entry, worded then, in the language the device registered with, from the shared catalog (`packages/i18n`): the title is the bot's name, or the room's, and the body is the entry's first line when the operator allows previews, or else a fixed sentence saying what arrived, such as "Sent you a message"; the fixed sentence is kept as well. A bot or room with no name to show gets none, nor does a registration the server can no longer read, which is logged. Neither working out who hears of an entry nor writing its pushes ever fails the entry: a failure is logged by the entry and the failure's tag, and the entry and its change commit without its pushes; the devices with a socket open are still told once they were worked out. The **push worker** sends each through the push sender, Expo's service for now ([decision 0014](../decisions/0014-push-goes-through-a-push-sender.md)), with data naming the device, the conversation or room and the entry, the delivery's id as its key, and, to an Android device, the entry's kind (`NotificationKind`) as the notification channel it shows in, which the app creates one of for each kind. Each send is claimed before it is made: recorded as begun, with the time the next may begin, only while its deadline has not passed and the device still has the registration the pass read, generation included: a delivery whose device was revoked, unregistered or registered again before it went out, even during the pass sending it, is not sent to the registration it no longer has. The claim reads the settings in its own transaction and words the send by them: none while notifications are off, which drops the delivery, and the fixed sentence once previews are off, never the other way. A change to the settings commits before a claim, and holds for its send, or after it, once that send is under way. After a crash or a lost reply, the same delivery goes again at that time with the same key, which the service uses to replace a notification still shown rather than add a second. A pass reads at most fifty due receipts, then sends at most fifty due pushes for at most a minute, and runs again soon while more are due, so slow sends never keep a later pass from reading the receipts and ending what passed its deadline first. A send the service does not take is tried again, from 5 seconds doubling to 5 minutes: one the service did not answer in 30 seconds, could not be reached for, or answered with 429 or 5xx, and one it refused because too many went to the device (`MessageRateExceeded`). The first of the former also ends the pass's sends and records, durably, when the service may next be tried, as long as that send waits: no send begins before then, one for a delivery written since included, so a service that does not answer is not asked again early, the other sends wait without a send counted, and receipts, read first, never wait on it. A send is tried at most eight times and within an hour of the entry; past either bound the delivery is dropped, logged, and counted on the registration's failures, as is a message the service refuses for good. Once the service took a message, its words are deleted and its receipt is read fifteen minutes later, then every thirty minutes for up to a day; each request for receipts stands alone, so one that fails does not lose another's answers. A receipt that says it was handed on ends the delivery; one that says too many went to the device drops it, logged but not counted as a failure, since its words are gone. A device the service says it no longer reaches (`DeviceNotRegistered`, in the answer to a send or in a receipt) loses its registration, and gets no pushes until it registers again; that answer, like a failure counted, holds only for the registration the send went to, by its generation, so a device that registered again since, even with the same token in the same millisecond, keeps its new one. The logs name deliveries and devices, Expo's documented error codes and a failure's tag, never a token, a failure's text or what a push says.

## The bot's browser

A bot that browses does it in the engine's browser ([Engine: the bot's browser](engine.md#the-bots-browser)). The server shows the operator what the bot has open and lets a paired device take a tab over: to sign in, to answer what the bot cannot, to show it where to click. It never acts on a page itself.

**The tabs.** `BrowserTabs` follows the engine's tabs of every session still in use for as long as the server runs, and gives each the bot whose session opened it. A tab of no bot's session is left out. Clients name a tab by a `BrowserTabRef` the server mints the first time it sees it. A ref names nothing once the tab closes, nor after a restart, so a client never keeps one. `browser.subscribe` streams one bot's tabs, a snapshot and then the whole list on every change, as the device that asked sees them:
- `controller` is `you` when this device holds the tab, `another-device` when another one does, and `bot` otherwise;
- `front` is the tab that most recently opened or navigated.

**The media socket.** `GET /api/browser/ws` shows one tab. The upgrade is authenticated as the RPC socket's is, before it becomes a socket ([Client API](#client-api)):
- a device token as a bearer, or a one-use ticket;
- the client gate's `Host` check first, as on every route;
- without a credential, a 401.

A query that does not decode becomes a socket that closes at once with 1008. A ref the server does not know gets `gone` and a normal close. The contract's `BrowserServerFrame` and `BrowserClientFrame` are what it carries, besides the pictures. A client frame that does not decode is dropped unread.

**One viewer per device and tab.** `BrowserViewers` opens one engine viewer for a device's first socket on a tab. The device's next socket on the same tab takes that viewer over, control included, and the socket before it closes with 4409. Two devices on one tab have a viewer each, so each can tell who holds it.
- A device's sockets on one tab take their turns, in the order they came: each finds the device's viewer, or opens it when there is none, and attaches to it before the next socket does. So a socket that comes while the viewer is still opening waits for it, and the device never has two engine viewers of one tab. The last socket to come is the one left attached.
- A viewer that ends while a socket attaches, its tab closing or its device revoked, is opened again once, if the tab is still listed. Otherwise the socket closes with 1013.
- A client message over 4 MiB closes its socket with 1009. The limit is shared with the RPC socket, whose largest message is a bot template; the media socket's are a few kilobytes.

**Pacing.** One picture is in flight to a client at a time.
- A picture that arrives while one is in flight waits. A newer one takes its place, and the engine is acknowledged for the one dropped unsent.
- The engine is acknowledged for a picture only once the client acknowledged it, so a slow client slows the engine's capture rather than piling pictures up.
- A socket whose write buffer would pass 2 MiB is dropped: one picture in flight never comes near that, so only a client that stopped reading gets there.
- The first picture may never come for a page that does not repaint ([Engine: the bot's browser](engine.md#the-bots-browser)). A client shows that it waits for it.

**Dropped links, and the grace.**
- The server pings every 15 s, and a socket it has heard nothing from for 45 s counts as dropped.
- A device that does not hold the tab gives up its viewer when its socket leaves.
- A device that holds the tab keeps it, and its viewer, for 60 s. A socket of that device that comes back within that time gets the viewer as it was: control, the page's size and the last picture the client drew. After 60 s the viewer closes, which gives the tab back to the bot.

**Revocation.** Revoking a device closes its viewers at once, those in their grace included, and their sockets with 1008. A held tab goes back to the bot then, not after the grace.

**Ends.** When the engine's stream ends, the socket ends with it:
- the tab closed: `gone`, then a normal close;
- the host needs setting up before the browser can start: `setup-needed` with what it lacks;
- the browser restarted: 1012, and the client connects again;
- anything else: 1013.

**Nothing is kept.** A picture lives in memory only, for as long as its viewer: the one in flight, the newest waiting behind it, and the last one the client drew, for a socket that takes the viewer over. None is written to disk or to the database, logged, cached or sent in a push. What a client types goes to the engine and nowhere else. The request log records the socket's path without its query, so a ticket is not logged ([Security: the bot's browser](security.md#the-bots-browser)).

### Help in the browser

Some steps on a page are the operator's to take: a check that a person is there, a sign-in the bot has no credential for, a one-time code, a code to scan, a passkey. The bot asks for one with `request_browser_help`, giving a reason from that list (or `other`) and a note in its own words. It never names a tab: the server takes the bot's front tab, so the bot never sees, and cannot forge, a tab's id.

**The card.** The request adds a `browser-help` entry to the bot's own conversation, also during a room turn, as an engine request's card goes there; the room is told the bot waits in its conversation, as for a secret request. The entry shows the reason, the note, the page's host name (only for an `http` or `https` page, never its path or query) and the tab's `BrowserTabRef`, which a client opens the browser on. A row in `browser_help_cards` keeps what the entry does not show: the audience and the dispatch that began the turn's work, the engine's id for the tab, which never leaves the server, and when the card stops waiting. Like an `ask`, the request ends the turn's delivery. The tool's result tells the bot its turn ends there, and the server stops that turn itself ([A Stop of one turn](#stop)), so a bot that would carry on in the browser anyway cannot: the operator's answer wakes it in a fresh turn. It notifies as a card of its own kind, `browser-help`, which Android shows in a channel of its own.

The request is refused, with nothing written, in a routine's side session, where nobody waits to help; when the bot has no tab open; for work the operator stopped; while another of the bot's browser help cards waits; and for the tab of the bot's last card when the operator declined it or let it run out and has not written since, in the bot's conversation or the room the request is for. The refusal says the operator already answered, so the bot tells them what the step still blocks instead of asking again; their next message lifts it. "Since" is by the order of entries (the last entry when the card closed), not by time. A retried request, with the same call id, gets the answer the first one got, also once the tab is gone.

**How it closes.** Once, in one of three ways, each in the transaction that wakes the bot:

- **The operator answers** `done` ("Pronto") or `declined` ("Não consigo") through `card.answer`, with a receipt as for any card. The answer closes the card first, and only then does any device of theirs that holds one of the bot's tabs let go of it, with the server waiting up to 5 s for the engine to report the tabs released before it answers. In that order nothing that letting go sets off, the expiry below included, can close the card in between. The wake can start before the release is reported; its first call is a snapshot, which reads the page whoever holds it. The same answer from another of the operator's devices, to a card already closed with it, succeeds and changes nothing. A different answer to a closed card fails with `Conflict("card-closed")`.
- **The tab closes.** Once the card's tab has been missing from the engine's tabs for two minutes, the card expires (`tab-closed`). The grace keeps a short gap, while the server follows the engine's tabs again, from closing it.
- **Nobody answers.** An hour after the request, the card expires (`timed-out`), but only while no device holds one of the bot's tabs: an operator still at work in the browser keeps it open, and for two minutes after they give the tabs back (`HAND_BACK_GRACE`), so giving back in the viewer and then tapping "Pronto" closes it as done.

The server keeps three things about the bot's browser in memory only, from its start: since when a card's tab has been missing, when a device took the bot's tabs, and when it last gave them back. After a restart a missing tab's two minutes count again from then, a card past its hour has no hand-back grace, and a takeover that spanned the restart wakes nothing when it ends. Each errs towards waiting longer for the operator or waking the bot less, never towards closing a card they are still answering.

Each close records a `system` wake, `browser-help`, with the outcome and the host name, for the audience of the turn that asked, so the bot carries on where it was asked. On `done` the envelope tells it to take a fresh snapshot before it acts. An answer is the operator's word, which a Stop never cancels ahead of time. An expiry continues the work that asked, so a Stop that covers that work drops it, as it drops the work's other wakes.

**A takeover without a card.** The operator can take a tab the bot did not ask about. The bot's actions on it then fail with `humanControl`, while its reads still work ([Engine](engine.md#the-bots-browser)), and its browser rules tell it to stop and end its turn. When the operator gives the browser back (no device holds any of the bot's tabs any more), the server wakes the bot once (`handed-back`) if a turn of its main session ran while they held it and nothing else will wake it about the browser: no card was open or closed meanwhile, no browser help wake waits, and the operator did not stop that turn's work. The wake goes to that turn's audience. A takeover while the bot was idle wakes nothing.

## Client API

Clients use one WebSocket to the server, with typed requests and subscriptions defined in `packages/contracts`, plus a few HTTP routes for what a socket does badly (pairing, file transfer), and the media socket that shows the bot's browser ([The bot's browser](#the-bots-browser)).

Each of the server's listeners (this one, the tool endpoint and the admin channel) binds only once its routes are built, so a request that arrives the moment a port opens is answered, never dropped. Node accepts connections as soon as a server binds and answers a request only once a handler is attached; bound first, a listener would leave a request that arrived in between waiting forever. Between the bind and the attach, Effect resumes from Node's listen callback synchronously, with nothing that waits in between, so no request can arrive unhandled. A step a listener takes after binding that does wait, such as setting the admin socket's mode, runs once its handler is attached.

**Over plain HTTP, a request names the server by an address.** On a client listener without TLS, a request whose `Host` is not `localhost`, an IP address or the name in `publicOrigin` is answered `403` before it is routed, the socket's upgrade included; the port in it is not compared. A page on a name rebound to this machine's address would send that name ([Security: web pages](security.md#j3-bots-own-surface)). With TLS, the certificate settles which names a browser reaches the server at, and `Host` is not checked. `POST /api/pair` reads a body only when it is declared `application/json`, and answers any other type `415` without counting an attempt towards the pairing lock.

**The socket is authenticated once, at the upgrade.** A client sends its device token as an `Authorization: Bearer` header, or, where it cannot set a header on an upgrade (a browser), a ticket it got from `POST /api/socket-ticket` with that bearer. A ticket works once and only within a minute. An upgrade without a valid credential is answered 401 and never becomes a socket. A browser cannot read that status, so a failed upgrade sends it back to the ticket route, whose own 401 is the signal to pair again ([Clients](clients.md#connecting)). The socket belongs to that device for its whole life, and every request on it acts as that device. Revoking the device closes its sockets at once. This is how T3 Code's own socket works (**Read** at `db51b67`, `apps/server/src/ws.ts`).

**A failure stays with its request.** Each socket runs its own RPC server. A handler that fails unexpectedly fails its own request with a generic "Internal server error", and the cause is logged on the server; the socket and its other subscriptions carry on.

**Subscriptions** send the current state and then changes, as whole entities:

- The roster (every bot and room, with its state, a preview of its last entry and whether it is unread, and the operator's sections in their order) and the engine status are small, so they always start with a snapshot and do not resume. A change carries the sections only when they changed, all of them; a bot that moves into or out of one is sent as a changed bot, and deleting a section sends each bot it held.
- A conversation or room resumes. Its snapshot holds the latest entries and the change sequence it was read at, its watermark; every later change follows, and nothing at or before the watermark does. A client that reconnects passes the last sequence it applied and gets the changes since, or, when the server no longer has them or there are too many, a fresh snapshot that replaces what the client holds. A frame is bounded by size as well as by count, since a visual makes one entry up to half a megabyte: a snapshot or a page of history stops once its entries' stored bodies pass 8 MB (always holding at least one), and the rest comes as older history; a replay that would pass it is answered with the snapshot instead.
- Routines resume the same way.
- Teammate conversations travel beside the roster: `pairs.subscribe` lists the pairs, and `pairs.messages.subscribe` follows an open one. Neither resumes ([Teammate conversations](#teammate-conversations)).
- The steps of a work fold stream while the operator has the fold open: every step so far, then each step as it changes, until the fold's turn ends and the work it handed off with it (a background task it started), as long as the engine reports that work pending for the turn. A fold carries when its turn started, which can be before its first step (`turnStartedAt`), and its time counts from then, as the turn's clock did. The finished fold carries the time its turn waited on the operator, from each card's arrival until it closed, or until the turn ended for a card whose answer the engine refused, since the turn still waits on it; so a client counts only the time the bot worked. The wait after the fold was written is `waitedMs`, which a client that counts from the fold's writing subtracts alone, and the wait between the turn's start and the fold's writing is `waitedBeforeMs`, so such a client never subtracts a wait its count does not cover. It also says whether the handed-off work still runs. A turn stopped or failed before its first step still writes a fold, of no steps, as it ends, whether the engine reports the end or the server settles it for a session the engine lost, so its conversation says how it ended and when, also after a reload; one that completed leaves only its reply, and a routine's turn, whose steps are never shown, leaves none. An operator's answer to a card counts as its turn's activity when the card closes, so a turn that waited long on the operator is not stalled the moment it resumes.
- A step names a tool the operator can meet in J3 Bots' own words (`WorkTool`), which the engine adapter maps from the names the engine and the harnesses give their tools; a client words it in the operator's language. A harness's own file, search and subagent tools read as what they worked on, as the harness's other steps do. A tool it cannot name keeps the engine's title of the call, else its own name made readable, never an engine's id. A working bot's state and a roster preview of a work fold carry the step that says what the work does or did, and the preview how the fold's turn ended, which is all a fold of no steps has to say (a failed turn's notice, with its Try again, is written after its fold, so the roster previews the notice): one still running, else the newest that is not housekeeping (updating its plan, looking in on a background task), else the newest. A bot whose opening wake is still to come or under way says so (`Bot.opening`), since its state passes through idle before its first turn.

Unread has one source of truth: the conversation's read mark against its newest entry that a bot or J3 Bots wrote, other than a teammate message's card, which never calls for the operator; nor is such a card the roster's preview of the conversation, or its latest activity. A bot that finished its turn is idle, and its reply is unread until the operator reads it; there is no separate "done" state. A client moves the mark forward only through the latest entry, by order, of those the operator can see: on screen, in a window that is showing, with no dialog over the conversation. Marking a conversation or room unread (`entries.markUnread`) moves the mark back to just before the last entry a bot or J3 Bots wrote, other than a teammate message's card, never forward, and only from past it: that entry reads as new again, and the next read past it clears it, with nothing else stored. A target whose only entries are the operator's has nothing to read again, and stays as it is. It is a command, with a receipt that commits with the move: since it moves the mark back, a connection that sends it again after a read made since, on this device or another, must find it applied rather than undo that read. A client sends a read it already sent only once, until the roster says the target is unread again: then the next read goes out, so a conversation marked unread elsewhere is read again when the operator comes back to it.

**Commands** carry a client-generated id and are idempotent: send a message, answer a card, stop a bot or a room's work, create or change a bot, a room, a section or a routine, mark a conversation or room unread, edit memory, change settings, register this device for push or end that registration. `secret.provide` is the exception: it keeps no receipt, because a receipt would hold the value; a retry that finds the card closed fails with `Conflict("card-closed")` instead.

**A room's past entries after it ends.** Archiving a room expires its open `ask` cards, so a client's stale answer to one fails with `Conflict("card-closed")`; a Retry of its message or notice fails with `Conflict("room-archived")` until the room is restored. Deleting a room deletes its entries, so a stale answer, and a Retry of anything that was in it, fails with `NotFound`.

The server pages history by `order`; a client asks for older entries as the operator scrolls.

## Release feed

The server learns of newer releases on its own, so a client can offer to update it (`UPDATE_HTTP_PATHS`, [Clients: updates](clients.md#updates-outside-the-protocol)). `ReleaseFeed` (`apps/server/src/releases/`) does it:

- **The channel** is a setting of the server, `Settings.updateChannel`: `stable` or `nightly`. It starts as the channel of the release that first runs with the setting (migration 23), so a home installed from a nightly build follows nightly builds, and one installed or updated from any other release follows stable releases. Stable reads GitHub's REST API `releases/latest`, the newest published release that is not a pre-release. Nightly reads `releases?per_page=30` and takes the newest release that is either a nightly build, a pre-release tagged with its bare version `<X.Y.Z>-nightly.<YYYYMMDD>.<N>`, or a stable release, tagged `v<X.Y.Z>`. Nightly tags carry no `v`, so they stay outside the `v*` tags only a maintainer may push. A draft, a release candidate, any other tag, a pre-release flag that contradicts the tag, or a release page that is not `https:` is passed over. A release's files are downloaded from the folder its own tag names. Versions order as semantic versioning does (`@j3-bots/release`, `compareVersions`), so a nightly sorts after the stable release it follows and before the next one.
- **Only newer, only verified.** The newest release on the channel is offered only when it sorts after the running version, never when it is the same or older: no downgrade. Before it is offered, the feed downloads its `SHA256SUMS` and `SHA256SUMS.sig` from the releases page and verifies them ([Security: updates](security.md#updates)). A release that fails is reported as `refused`, with why, and is not offered; a release that verified is not verified again, and one that was refused is verified again at each check, since its files can be fixed in place. A server on stable that runs a nightly, after its operator moved it from nightly, is offered nothing until a stable release newer than that nightly exists, and says it is waiting for one (`waitingForStable`).
- **When.** A minute after the server starts when no check is due later, then every 6 hours, give or take 30 minutes so servers started together do not ask together, and when the channel changes. A client may ask for a check. No check starts within a minute of the last, whatever asked for either and whether or not it finished, nor before a rate limit's reset: a check asked for then answers what the last one found, and a new channel is checked once one may start. Checks run one at a time; a check asked for while one runs waits for it.
- **Asking little.** No token: the API allows an address 60 requests an hour without one, shared by every machine behind it. A check is one request (two downloads more, from the releases page, only for a release not verified yet), so a server makes one every 6 hours on its own (four an hour at most while checks fail), and the checks clients ask for add at most one a minute. Each request carries the ETag of the last answer, which GitHub answers 304 when nothing changed, with nothing to decode. A 304 still counts against the limit without a token (**Verified** against `api.github.com`, 2026-11-24: `x-ratelimit-remaining` fell by one for each 304). A 403 or 429 is a rate limit: no check starts, for any reason, before `retry-after`, or `x-ratelimit-reset` when no requests are left, never more than 6 hours away whatever the header says. After a check that does not finish, the next scheduled one waits at least 15 minutes, doubled after each scheduled check that does not finish, up to 6 hours; a check a client asked for that does not finish leaves the wait as it was. What the last check found still stands meanwhile.
- **Where it asks.** Requests go only to the API's origin, the releases page's, and `release-assets.githubusercontent.com`, where the releases page redirects each download (**Verified** 2026-11-24). A redirect to any other host is refused before a request is sent there, and the check ends unreadable (`onlyToReleaseHosts`). A release's file is read as it streams and given up past 1 MiB, whatever its length said.
- **Kept across a restart.** What the feed found, the ETags, the rate limit's reset and the verdicts are written to `state/release-feed.json`, so a restart, an update's included, asks nothing before the next check is due. A verified verdict keeps its evidence, the `SHA256SUMS` and `SHA256SUMS.sig` it verified, byte for byte. At start the evidence is verified again against the keys trusted then, and a verdict whose evidence does not verify is set aside, so a file that says a release verified offers nothing on its word, nor does one verified with a mirror key no longer trusted. A file that cannot be read is a cache lost: the feed starts again from nothing.

`J3_RELEASE_FEED_URL` replaces the API (default `https://api.github.com/repos/JPSAUD501/j3-bots`), for tests and mirrors: it must answer `<base>/releases/latest` and `<base>/releases`. Downloads come from `J3_RELEASE_BASE_URL`, as `j3-bots update` and `install.sh` take them.

## Updating from a client

A client asks the server to update itself through `POST /api/update/v1/start`, with the version the status offers ([Clients: updates](clients.md#updates-outside-the-protocol)). The update is the same transition `j3-bots update` makes from a shell ([decision 0016](../decisions/0016-an-update-keeps-a-snapshot-to-roll-back-to.md)): the server only starts it, and reports what it records ([decision 0033](../decisions/0033-a-client-update-runs-in-a-transient-unit.md)). `UpdateRuns` (`apps/server/src/update/`) does it.

**Where it can run.** The update stops the service, so it cannot run in the server's process or as its child, whose cgroup ends with the service. It runs as a transient unit of the same systemd user manager, `j3-bots-update-<run>.service`, which `systemd-run --user --collect` starts. Only a server `install.sh` installed and its service runs can do that, on a manager that outlives the operator's sessions. Anything else answers `canUpdate: unable`, with a reason and the command that updates it by hand, checked in this order each time the status is read:

| Reason | When | Command |
| --- | --- | --- |
| `desktop-managed` | The desktop app runs the server (`--admin-fd`). The app updates it with itself, and its own surface reports that update ([Operating: the desktop app](../operations/operating.md#the-server-the-desktop-app-runs)). | none |
| `checkout` | A checkout runs it. | `git pull && pnpm install --frozen-lockfile && pnpm build && j3-bots service install` |
| `unpacked` | A release unpacked by hand, not under `install.sh`'s folder, or one whose manifest cannot be read. | the `install.sh` line |
| `started-by-hand` | The service's main process is not this server: `j3-bots serve` in a shell. | `j3-bots update` |
| `no-systemd` | `systemd-run` is not on the service's `PATH`. | `j3-bots update` |
| `no-linger` | The user does not linger, so the manager, and the update with it, would end with the operator's last session. | `sudo loginctl enable-linger "$(id -un)"` |
| `rollback-unfinished` | A rollback was cut off ([Operating](../operations/operating.md#update-and-roll-back)). | `j3-bots update --rollback` |

**What starts it**, in this order, each refusal an `UpdateRefused` with nothing changed:

1. `unable`, as above.
2. `not-available` unless the version is exactly the feed's `available` one: verified, newer, on the channel. Right after a channel change, until the feed has heard of it, its offer is the old channel's and is not taken. A change of the channel, through this API or `settings.update`, and a start never interleave: a start reads the offer and records its run with the channel held steady, so a change commits before the offer is read or after the run is recorded. No request names a file or an address.
3. `busy` while a run has not ended, or while the home's update lock is held, as by `j3-bots update` or `--rollback` from a shell. Steps 3 to 5 run under one lock, so two clients cannot both start.
4. `work-running`, with the number of bots, while bots have work running and the client did not send `stopWork`. The update asks again when it is ready to stop the service, and takes the client's `stopWork` as the answer: work begun meanwhile is stopped only if the client sent it, and otherwise the run ends as `rolled-back`, having changed nothing. When that last count finds no work, none begins before the stop: the server holds every new first send from the count until it stops (`POST /running-work`).
5. Otherwise the server writes the run record and starts the unit. A unit that does not start ends the run as `rolled-back` with `other` and `systemd-run`'s output: nothing was changed.

**The unit.** It runs the release that runs now, `<install>/versions/<current>/bin/j3-bots update --version <V> --run <run>`, as the same user, with no privilege the user does not have (`NoNewPrivileges=yes`). Its environment is the service's: `J3_HOME`, `PATH`, and `J3_RELEASE_BASE_URL` and `J3_RELEASE_PUBLIC_KEY` when the service has them, so it downloads from where the feed found the release. It also unsets the variables a shell may set to override the configuration file, as the service's unit does. systemd expands `$NAME` in a transient unit's arguments, as in `ExecStart=`, but takes the program's path as it is, and expands no `%` specifier there (**Verified** with systemd 255 on a test machine: in a `systemd-run --user` command, an argument's `$HOME` was expanded and `$$` gave one `$`; a path with `$HOME` in it ran, and the same path with `$$` was not found; `%h` was not expanded). So the path is passed as it is, and the arguments, a version and a run id, have no `$`. The service's own unit doubles each `$` in its arguments and none in Node's path. The update downloads `SHA256SUMS` and its signature again and verifies them itself before it reads a digest, whatever the feed found ([Security: updates](security.md#updates)). A release already in `versions/` is taken only when it is proven to be the signed one: each release an update unpacks keeps the SHA-256 of its archive, which must be the verified list's; one without it, as from a mirror or an install that verified nothing, is downloaded again and replaces it. Once it holds the update lock, the update checks that the release it was asked from still runs; if another update ran first, it changes nothing and says so, so a delayed run never takes the server back to an older release. It is collected when it ends, failed or not; what it printed stays in `journalctl --user -u j3-bots-update-<run>`.

**The record.** `<home>/state/update.json`, readable by the user alone, holds the run: its id, the release it came from and goes to, the device that asked and whether it let the update stop bots' work, when, its stage, and once it ends, how. The server writes it before it starts the unit. From then on only the update writes it: `downloading`, with bytes so far and the total once known, at most once a second; `verifying`; `installing`; `restarting`; then the outcome. Each write replaces the file whole and flushes it, and an update writes only a run that has its id and has not ended. Since the record is in the home, it outlives the restart: whichever release runs afterwards reads it.

**How it ended**, as the status' `lastResult`, the one entry every client sees for it (an update belongs to no bot, so it is no conversation's entry):

- `done`: the new release runs.
- `rolled-back`, with a reason: either the new release did not get ready and the release before runs again on the data as it was (`health-check`), or the update stopped before it changed anything (`download`, `verification`, `engine`, `disk`, `other`). Either way the release before runs.
- `failed`: bringing the release before back failed too, and `j3-bots update --rollback` finishes it; or the unit ended without recording how, as when the machine restarted under it (`interrupted`). A run whose unit has ended while it has not is ended that way the next time the status is read. The detail of any ending but `done` names the unit's journal, where what the update printed is.

While a run has not ended, the status' `state` is its stage and `run` names it, so a client follows it by polling `status`. A stream would end with the restart, and a client already polls `GET /api/server` while the server is down. The server logs the run, the versions and the device when it starts one, and how it ended when it finds one cut off, never a token.

## Configuration

The server reads its settings from `<J3_HOME>/config.json`. On first start, once the configuration and the home pass their checks, it writes that file whole, with every setting at its default but `scriptedAgent`, which is for test installs; it never replaces one that exists. A setting in the environment overrides the file, and a default applies only when neither has the setting. A setting that is present but invalid stops the start, so a typo never becomes the default. The file refuses unknown keys for the same reason. A port another program holds stops the start with a message that names the port and its setting. Start also refuses two listeners on one port, port `0` for the tool endpoint or the engine (both are dialed at the number configured), and a certificate and key that Node cannot load as a pair. `j3-bots doctor` runs the same checks without starting anything. A service runs with the file alone: it does not get the variables of the shell that installed it.

| File | Variable | Default | |
| --- | --- | --- | --- |
| | `J3_HOME` | `~/.j3-bots` | Created readable by the operator only. The server does not start while it is owned by another user or open to a group or to other users. Refused inside a Git checkout, including a folder that does not exist yet whose parent is one |
| `host` | `J3_HOST` | `lan` | `lan` listens on every IPv4 interface and serves private addresses only, with or without TLS. Start refuses it while any of the machine's addresses is public, and each connection to an address that is not loopback or private is closed unread. Any other value is one address, which must exist when the server starts. Without TLS it must be an IP literal in loopback or a private range: the private IPv4 ranges, IPv4 link-local, carrier-grade NAT (100.64.0.0/10, where Tailscale puts its addresses), and IPv6 unique-local and link-local. `0.0.0.0`, `::` and host names, `localhost` included, are refused |
| `port` | `J3_PORT` | `3737` | `0` lets the system choose; `j3-bots pair` prints the port the server got |
| `tls` | `J3_TLS_CERT`, `J3_TLS_KEY` | none | A certificate and key (`{ "cert", "key" }` in the file), which serve HTTPS. With them, `host` may be any address, public ones included; `lan` still serves private addresses only. The two variables are set together and replace the file's pair |
| `enginePort` | `J3_ENGINE_PORT` | `3738` | The engine's loopback port |

| `webClient` | `J3_WEB_CLIENT` | the one that comes with J3 Bots: `web/` in a release, `apps/web/dist` in a checkout ([decision 0015](../decisions/0015-a-release-is-a-self-contained-archive.md)). The server runtime a desktop package carries has none: the app loads its own page and calls only the server's API, which is all that server serves | The built web client, served on the API's origin. A folder named here must hold an `index.html`. Never for real use: release archives do not carry the agent, which runs only beside a checkout's installed dependencies; start refuses a path that is not a file; and `j3-bots doctor` warns while it is set. A new `config.json` does not list it. The variable is for development, and a service never gets it |

Relative paths in the file resolve against `J3_HOME`.

**The web client** is served by the same listener as the API, so the two share an origin. The server looks for a built client when it starts and registers its routes then; a client built later is served after a restart. Paths under `/api/` and the server's own routes are never answered with the client. A request for a path without a file extension that accepts HTML, and that names no file, gets `index.html`, for the client's own routing; anything else that names no file is a 404. Files under `/assets/` carry content hashes in their names and are cached for a year as immutable; everything else is revalidated on each use. Each request is resolved once: the request target is parsed as a URL (which drops the query and the fragment and resolves dot segments), its path is decoded and resolved inside the folder, and the file's real path, symbolic links resolved, is checked to lie inside the folder and is the file sent. No second parser reads the target. Paths that leave the folder are refused, and so is a file whose real path lies outside it, a folder's `index.html` and the app's `index.html` included. A folder named without its trailing slash is redirected to it.

**One server per home.** Right after it loads its configuration, before it opens the database or starts the engine, the server checks that the home is private and takes an exclusive lock on `<J3_HOME>/server.lock`, which it holds until it exits. A second server for the same home stops there. The lock is SQLite's, which the kernel releases when the process ends, so a crashed server never leaves the home held.

## The admin channel

The admin channel is how `j3-bots` commands on the host reach the running server, and how the desktop app that runs its own server gets its device and stops it. It needs no token, because only the server's own user can reach it, and nothing on the network does. It serves the same routes two ways:

- **The admin socket**, `<J3_HOME>/admin.sock`: a Unix socket that only the operator's user can open. Two things keep others out: the home is private, and the socket is created with no access for group or others, since the server narrows the umask for the call that binds it, so there is no moment between the bind and a `chmod` in which it has the process's usual mode. Node binds the path within that call (**Read** in Node's `lib/net.js`, `createServerHandle`, v24.x at `221ffa5`). The umask is the whole process's, so a file Node's thread pool happens to create in that instant gets no access for group or others either, which in a private home changes nothing. Just before the bind the server checks that the home is private and notes which folder it is (device and inode), and once the socket is served it checks again: a home moved, replaced or opened to others in between stops the start. A server holding the lock removes a socket left by one that stopped without closing, once it has seen that the file is a socket and that nothing listens on it. Anything else at that path stops the start, and so does a home whose path is too long for a socket's address (103 bytes for `admin.sock`'s). The server binds no admin socket on Windows, where Node would serve the path as a named pipe, which other users of the machine could open (**Assumed** from Node's and Windows' documentation, not measured); there the path's length is not checked either.
- **An inherited pipe**, with `j3-bots serve --admin-fd <n>`: the descriptor `n` the server inherited from the process that started it, which the desktop app passes as 3. Only that process holds the other end, and the server's end cannot be opened by name: on Linux and macOS Node makes it a socket pair (**Read** in libuv's `src/unix/process.c`, v1.x at `f08538c`), which has no name. On Windows libuv makes it a named pipe of a single instance (`FILE_FLAG_FIRST_PIPE_INSTANCE`), which the parent opens itself right after creating it, before the child starts (**Read** in `src/win/pipe.c`, `uv__create_pipe_pair`, same commit). The processes the server starts, the engine and the harnesses, do not inherit it (**Verified** on Linux with Node 24.22.1, not yet with the 26.13.1 the server pins: a process started by a Node process that had opened its fd 3 with `net.Socket` had no fd 3). On Windows it is the only admin channel.

  The start fails on a descriptor below 3, on a TCP socket, listening or connected, and, on Linux and macOS, on anything that is not a socket: a FIFO, a one-way pipe, a file, a terminal. Windows has no such file types to tell apart, and Node's stream over the descriptor refuses a file or a console there. A Unix socket that listens is not told apart from a socket pair; it would fail at its first read, and only a parent can hand one over.

  It is one HTTP/1.1 connection for the life of the process, and only the parent writes to it. The server never closes it for being idle: it ends when the server stops, when the parent closes its end, after which the server goes on without it, or when a request on it is malformed: Node's HTTP server answers it 400 and destroys the connection (**Read** in `lib/_http_server.js`, `socketOnError`, v24.x at `221ffa5`), since nothing would tell where the next request starts, so the channel is gone for the rest of the process. A request sent before the server serves waits in the pipe and is answered once it does. Requests go one at a time, each read to its end. The client in `AdminClient` waits for an answer as long as on the socket (10 seconds, or what the call gives, such as a first `/status` that waits for the server to start) and no longer, so a parent never hangs on a server that stopped answering or a descriptor that is not the channel. A request that times out or is abandoned closes the pipe, for the same reason, and the parent then treats the server as lost: the desktop app kills it, as it does when `/shutdown` gets no answer. Node creates every `pipe` it passes to a child readable and writable on every platform (**Read** in Node's `src/process_wrap.cc` on its main branch, November 2026). On Windows the parent should pass this one as `overlapped`, which is the same as `pipe` elsewhere: without it the server's end is a synchronous handle, and Windows serialises reads and writes on such a handle, so an answer could wait behind the read that waits for the next request (**Assumed**, from Windows' I/O rules and libuv's `src/win/pipe.c`, not measured).

| Route | What it does |
| --- | --- |
| `GET /status` | The server's version, its process id (which tells the server that started from another process on the same socket), when it started, where it listens (scheme, address, port and, with TLS, the certificate's concrete names), its tool and engine ports, the engine's state, how many devices are paired, whether it serves the web client, and its `publicOrigin` |
| `POST /pairing` | A pairing code, or, while pairing is locked after failed attempts, until when |
| `POST /pairing/unlock` | Lifts that lock, for `pair --unlock`, then answers as `/pairing` |
| `POST /running-work` | How many bots have work running, which a stop would end, read with every new first send held. When none runs, they stay held until the server stops, or for two minutes if it is not stopped, so `j3-bots update` stops the service with no work begun since it counted. A stop does not wait for the hold to end |
| `POST /provider-connection` | Stores `provider connect`'s new provider connection and restarts the engine with it, unless bots have work running that the restart would stop and the request did not agree to that |
| `POST /local-device` | `{name, replaces}` → `{deviceId, token}`: pairs a device without a code, as a successful pairing does (a new row, a new token of which only the hash is stored), and in the same transaction revokes the device `replaces` names, as `device.revoke` does: its push registration goes, and once the transaction commits its tickets and sockets do too. A `replaces` that is unknown or already revoked is left as it is, and `null` replaces nothing. `name` is held to a pairing device's rules. It neither needs nor counts towards the pairing lockout. 400 when the body does not decode. This is how the desktop app gets the device it uses with the server it runs ([decision 0020](../decisions/0020-the-local-desktop-gets-its-device-through-the-admin-channel.md)); the client listener has no such route |
| `POST /shutdown` | Answers 202, then stops the server as SIGTERM does. How the desktop app stops the server it runs on Windows, which has no SIGTERM |

**Stopping.** SIGINT, SIGTERM, `POST /shutdown` and, with `--exit-with-stdin`, the end of stdin all stop the server the same way: it releases what it holds in the reverse of the order it took it: the admin channels and the tool endpoint first, the admin channels each answering the requests in progress for up to a second, then the client listener, the engine, which stops the harnesses, the database and last the home's lock. **Verified** on Linux with the pinned engine 0.1.11 ready: once stdin of a server run with `--exit-with-stdin` closed, it exited with 0, no process it had started was left, and the lock was free. A stop through `/shutdown` or stdin ends with exit code 0.

**`--exit-with-stdin`** stops the server once its stdin reaches its end: when the process that started it closes it, or exits, which closes it too. So a server the desktop app runs never outlives the app, even one that crashed. A process whose stdin is already at its end, such as a service's, stops at once with it, so the flag is only for a parent that holds stdin open. A stop asked for while the server starts ends the start there.

The protocol is J3 Bots' own: the CLI and the desktop app ship with the server they talk to, so it is not a client contract. Its status reply stays readable both ways between releases, since an update has one release's CLI wait for the other's server ([`protocol.test.ts`](../../apps/server/src/admin/protocol.test.ts)).

## Failure handling

| Failure | What the server does |
| --- | --- |
| The engine process exits | Restarts it and reconnects. Each time the engine becomes ready, the server opens each session's stream again from its stored cursor, by replay or replacement, then releases the workers and nudges each, and checks the secret submissions left undecided alongside them. While the engine is not ready the workers hold. The order within a session comes from its own state, not from the sequence: nothing is planned into a session before its events are known, and nothing new is sent into one with an unsettled Stop or a dispatch whose answer is not known, so the Stop runner sends the rounds never acknowledged, and the recovery settles those dispatches with their key, before anything new reaches that session; each worker's deadlines are stored, so none starts afresh. The engine cancels the turn that was running and its open requests expire; the turn's dispatch is recorded as interrupted and handled like a failed one (the engine's restart continuation is turned off). The server resumes each reported hold once, except in a session with an unsettled Stop |
| The engine socket drops | Reconnects with backoff, then runs the same sequence as after an engine restart |
| The engine has no such session | Records the session lost, shows it once, and plans nothing into it ([Sessions](#sessions)) |
| The engine refuses to open or align a bot's main session | Tries again with backoff, an opening under a fresh key, and shows a `session-not-ready` notice once three attempts in a row failed, until an alignment succeeds ([Sessions](#sessions), Every bot has a main session) |
| The engine refuses to archive a retired session | Tries again with backoff under fresh keys; the session holds no turn slot, and the rotator goes on with the others ([Sessions](#sessions), Rotation) |
| The engine refuses a bot's permission mode, to open or align its main session or to run a turn there | Neither opens, aligns nor plans into its main session until the bot's settings change or the engine becomes ready again, when it asks once more; shows a `permission-mode-refused` notice, naming the mode the policy allows when the engine reports it, once per refusal that differs from the last one told, and each of the bot's rooms a `member-mode-refused` notice; the rest of a room goes on without the bot. A message whose turn it refused waits with the new ones, in its place, and is delivered once after either; a refusal from an engine that has stopped since is not recorded ([Sessions](#sessions), Every bot has a main session) |
| The engine refuses a settings change over background work | Sends the bot no work, shows a `settings-held` notice once per change, offers the Stop, and tries again every 30 seconds; a Stop ends the work, and the change applies then ([Sessions](#sessions), Settings alignment) |
| An event cannot be applied | Logs it with its cause, shows an `observation-failed` notice once, sends nothing into the session meanwhile, and reads it again each time the stream reopens with backoff; one item's failure never stops the loop that met it |
| A worker fails unexpectedly | Logs it; the item that failed gets a later deadline and the pass goes on, and a worker whose pass failed waits thirty seconds before the next ([The workers](#the-workers)) |
| The push service cannot be reached | Sends the push again with backoff, within its bounds, then drops it and logs it; the roster still shows the entry unread ([Notifications](#notifications)) |
| A turn fails | Records the engine's error class on the dispatch and shows it. A routine run's attempt shows nothing and is tried again instead, up to three attempts ([Routines](#routines)). So is one whose side session the engine refuses to open, for the bot's model or otherwise |
| A provider hits its limit | Marks the provider's bots blocked with the reset time; holds automated wakes until then. The turn that hit it stays open as a pending continuation, and a dispatch already waiting in the engine starts at the reset |
| The server process exits | On start, runs the sequence above, which also sends a dispatch written and never sent, whether or not its bot has a wake pending, and recovers every dispatch that was sent but has no recorded answer. No turn starts twice, because a dispatch keeps its key and its envelope |
| A session cannot be resumed | The engine runs the turn on its own summary of the old conversation; the server then rotates the session once it is quiet, and the new one starts from memory and the digest ([Sessions](#sessions)) |
