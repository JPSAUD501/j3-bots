# Server

The J3 Bots server is the product. It owns what the operator sees and decides what every bot does next. This document describes its data, its one central mechanism (the wake pipeline) and the features built on it.

## Data

J3 Bots keeps two kinds of state, in two places, for two different readers.

**The database** (`<J3_HOME>/j3.sqlite`) holds what the server needs to query and what clients render:

| Entity | What it holds |
| --- | --- |
| Settings | One row: the operator's name, their time zone, the budgets, notification preferences |
| Bot | Profile, model, permission mode, workspace path and the real path it had when first provisioned, engine project id |
| Conversation | One per bot. A sequence of entries, and how far the operator has read |
| Room | Name, members, host, status (active or archived) and when it was archived. A sequence of entries |
| Entry | A message or a card, with its author, its time, its delivery state and its fixed place (`order`) in its conversation or room |
| Session | J3 Bots' own id, its bot, its purpose (main or side), the engine thread id once the engine has one, the prompt version it was created with, the provider it runs on, the rotation it is due for and why, when the engine took it out of use after it was retired, the cursor of the engine events applied so far, the turn it has admitted with that turn's audience, the engine queue's current hold and the hold it last resumed, and when the engine answered that it has no such session |
| Wake | Kind, priority, target bot, audience, payload, hop count, status (pending, dispatched, finished, cancelled or failed), and the dispatch that delivered it |
| Dispatch | One delivery to the engine: its sequence number, the order it was written in, the target session, the audience, start or steer, the rendered envelope and its files, how many times it was sent, how many times staging its files failed, the disposition the engine reported first if it reported one, the turn that delivers it, its status and, when it failed, why, a pending continuation of its turn, the Stop that fenced it, the outcome. Several coalesced wakes share one |
| Stop | The operator's Stop of one bot (scope `bot`), or of a room's work when the room is archived (scope `room`): its command id, the highest dispatch sequence number when it was recorded, and per target session and round the engine key, when the engine acknowledged it or refused it, when the events were observed past that acknowledgment, and whether they confirmed it stopped |
| Ask card | For an `ask` question: the wake it came from and the audience of the turn that asked |
| Tool call | A bot tool call pinned to the turn and audience it came from and to the engine's record of the call, with its result |
| Engine request | For an approval, an engine question or a secret request: the session, the engine's request id and the turn it belongs to; for a secret request, whether a submission may be in flight, never its value |
| Catch-up note | What a bot's main session has not seen yet, consumed by its next main-session dispatch |
| Held message | A non-urgent teammate message waiting for the recipient's next envelope |
| Blob | File bytes, stored once per digest: size and where they are stored |
| Attachment | A file the operator sent or a bot produced: a name and a media type over a blob |
| Routine | Bot, name, instruction, trigger, enabled, next run, run count, webhook secret. Its runs: status, start and end, the wake that runs it, trigger data and the webhook request's idempotency key |
| Device | A paired client: its token hash, its push token, when it was revoked |

Entries are ordered by `order`, set when the entry is created and never changed. The change sequence that clients resume subscriptions with is separate: it records when an entry changed, not where it sits.

**The filesystem** (`<J3_HOME>/bots/<bot>/`) holds what a bot reads and writes with its own tools, and what the operator may want to open in an editor:

```
bots/scout/
  .j3/
    system.md        generated: base prompt + profile + pinned memory
  AGENTS.md          generated: the same identity for harnesses that read it
  memory/
    profile.md       small, always in front of the bot
    log/2026-11.md   dated history
  skills/            procedures, one folder each
  files/             what the bot produces
shared/
  memory/
    user.md          facts about the operator every bot can read
    log/2026-11.md   shared dated history
  skills/            skills available to every bot
providers/
  claude-code/       Claude Code's home for every bot (`CLAUDE_CONFIG_DIR`)
  codex/             Codex's home for every bot (`CODEX_HOME`)
```

Generated files are written by the server from the database and the memory files. A bot never edits them by hand, and the server rewrites them whenever their inputs change.

**Private state stays in the home.** Every location the server writes (each entry of the home but `web`, the shared memory and skills, each bot's workspace with its memory and generated files, the attachments, and the engine's folder with the folders the engine adapter declares it writes there, `j3/` among them) must resolve, symbolic links followed, inside the home's real path and outside the web client's folder. A bot's `skills/` and `files/` are its own: the server creates them once, and writes there only the operator's files it copies into `files/inbox/`, each through the check below, so a link there is the bot's business and refuses nothing at start. Start refuses a home where a written location does not resolve as it should, naming it. Every write of private state, the adapter's included, checks its folder the same way first, then writes a new file (mode 0600) of a random name there that must not exist yet and renames it into place, so a link made while the server runs (by a bot's own tools, say) is never followed and cannot publish memory or a generated file through the web client. The engine download is the one file written in place, so that an interrupted one resumes: it must be a regular file, its folder and itself are checked the same way, and it is opened so that a link at its name is refused, even one made after the check. A removal (a deleted bot's memory and generated files, an attachment's bytes once nothing refers to them) checks the folder above what it removes the same way, and removes a link there rather than following it. A refused write or removal is logged, and only that bot's workspace or memory, the attachments, or the engine's folder is affected: a memory write or an upload fails with `Conflict("private-location")`, also when a folder inside the memory, such as `log/`, is the link; a file copied into `files/inbox/` fails its staging; a generated file or a removal is skipped; the engine is not installed; and every other bot carries on. What this rule does and does not defend against is in [Security](security.md). To keep state on another disk, put the whole home there.

Memory lives in files and not in the database because the bot's own tools can read, search and quote files, and because the operator can read, edit, diff and back them up without J3 Bots. See [decision 0006](../decisions/0006-memory-is-files.md).

## The wake pipeline

Everything a bot does starts as a **wake**. There is one pipeline for all five kinds, and it is the only path to the engine.

```
 operator message ─┐
 room message ─────┤
 teammate message ─┼──> wake (persisted) ──> held by the server ──> dispatch (persisted) ──> engine session ──> turn
 routine trigger ──┤                              │
 system event ─────┘                              └── priority, budgets, coalescing, concurrency
```

### 1. A wake is recorded before anything happens

Creating a wake and the entry that caused it (the operator's message, the room message, the answered card) is one transaction. A wake that exists will be dispatched or visibly cancelled; one that does not exist never was requested. If the server stops between recording and dispatching, it picks the wake up again at start.

### 2. The server holds waiting wakes

J3 Bots owns waiting and priority. A pending wake stays in the server's database until its session can take it; J3 Bots never asks the engine to queue a message. The engine still queues a start that meets a turn it began itself, and the server follows that (`queued`, below). Each wake has a priority from its kind: `user` first, then `room`, `bot`, `system`, and `routine`, and within a priority they go in the order they were written, which also orders the messages in one envelope. Wakes written in one transaction share a time, so the order is the database's own insertion order, never the time or the id.

For each pending wake the dispatcher applies, in order:

- **Budget.** A wake caused by a bot carries a hop count. If the chain that led here exceeds the limit, the wake is cancelled and the conversation or room shows that the chain stopped. See [Budgets](#budgets).
- **Readiness.** A session the engine no longer has is skipped ([Sessions](#sessions)). A wake is dispatched only into an idle session: no admitted turn, no dispatch that may be in the engine and is not yet finished (sent but unanswered, accepted, or delivered), and no turn the engine started on its own; a pending continuation holds back every wake but the operator's. The one exception is below: a `user` wake for a running turn with the same audience. Nothing at all is dispatched into a session while a Stop of it is unsettled ([Stop](#stop)). Nothing is planned into a session whose events are not known yet ([Observation](#4-the-turn-is-observed-and-admitted)), since they decide how it can take the wake, nor into one whose first send was refused as busy, before its busy deadline passes or its next event is applied ([Refusals](#3-a-dispatch-is-written-before-the-engine-is-called)). Each of these holds back only that session's wakes: the dispatcher goes on with every other bot.
- **Coalescing.** Pending wakes of a bot with the same kind and the same audience that are ready for the same session become one dispatch: three messages in one room that arrived while the bot was busy are delivered together. Wakes for different audiences never share a dispatch, so one turn always speaks to one place. Coalescing stops at the engine's limits for one message: its files together (`attachmentLimitViolation`) and the length of the rendered envelope (`engineInputLength` against `ENGINE_INPUT_LIMIT`, 120,000 characters, measured as the engine measures it, after expanding any assistant-quote link). The envelope holds the head wake, then as much of what the session has not seen as fits, oldest first, then as many of the other wakes as fit, in order. What is left out waits for the next dispatch in the same order, so a batch that does not fit becomes consecutive dispatches. A single wake always fits: every path that writes the operator's text into a wake checks that wake alone before it commits, with the same margin of 1,000 characters under the limit, which covers what renders longer at dispatch, such as the date, the zone and a room's name. `message.send` checks each message's files and its envelope (`Invalid("message-length")`, nothing written); `card.answer` checks an `ask` answer's envelope (`Invalid("answer-length")`, the card left open for another answer). A retry sends again a wake that passed that check, and a system event is far below the limit. The dispatcher still never lets a wake hold the queue: a head wake that does not fit alone gets a dispatch of its own that fails as `rejected` without being sent, so it shows where it came from as a refused dispatch does ([Refusals](#3-a-dispatch-is-written-before-the-engine-is-called)), and the wakes behind it go on. Something the session has not seen that would not fit even beside the smallest wake, a system event, is left out for good, in order, with a `too-long` notice in the bot's conversation.
- **Concurrency.** At most N turns run at once across all bots. A slot is held by every session with a turn running or a dispatch the engine may have (sent and unanswered, accepted or delivered, a pending continuation included). A dispatch never sent holds none: it takes a slot when it is sent, and the slots are counted again before that send, so a session that cannot take its work yet never keeps a slot another bot could use. Every start is admitted by the same rule, whether it is planned now or sent again after its files failed to stage: a slot is free, or its session already holds one, as an operator's message beside a pending continuation does. The rule is read when the start is planned, and again in the transaction that claims its first send, since the budget or the sessions holding it may change while its files stage: a start refused then stays unsent, for the dispatcher's next pass. Higher-priority wakes take a free slot first.
- **Blocked providers.** If the bot's provider is at its usage limit, routine and bot wakes wait for the reset. An operator wake is dispatched anyway so the operator gets the engine's own limit message.

| Wake | The session is idle | The session is in a turn |
| --- | --- | --- |
| `user` | Start a turn | If the running turn has the same audience (the conversation, or the room the operator wrote in), steer it, so they can redirect work in progress. Otherwise wait, first in line, so a private message never lands in a room turn. A wake carrying an `ask` answer always waits ([Questions](#questions-approvals-and-secrets)) |
| `room`, `bot`, `system` | Start a turn | Wait |
| `routine` | Start a turn in a new side session | Not applicable: side sessions run alongside the main one |

### 3. A dispatch is written before the engine is called

Before anything is written, a message's files are checked against the engine's limits (`attachmentLimitViolation`: no empty file, inline images at most 10 MiB each and 80 MiB together). A message that breaks one is refused with nothing written.

In one transaction the dispatcher renders the envelope, writes a **dispatch** with the target session, the audience, the delivery (start, or steer with the turn), that envelope and its files in order, links the coalesced wakes to it, and consumes the bot's catch-up note and held messages into the envelope. A dispatch never changes its session, its audience or its envelope afterwards; the database refuses it.

Then, inside the session's gate ([One gate per session](#one-gate-per-session)), it reads the dispatch again and goes on only if it is still due: still `intended`, its deadline passed, and, for a first send, its session's events known and unfenced in a session with no unsettled Stop. A resend waits for no observation: its key makes the engine apply it once whatever the server knows yet, and a Stop may be waiting on its answer. A steer goes only into the turn it was planned for: if that turn is no longer the session's admitted turn when its first send comes, the dispatch is released and its wakes wait for the next dispatch. Before a first send, it copies each file into the bot's workspace, at `files/inbox/<attachment id>/<name>`, where the envelope names it beside the name the operator gave: the folder of its own keeps two files apart, and the name is made one path segment (a name made only of dots becomes `_`) of at most 200 bytes in UTF-8, shortened if need be with its extension kept, so the bot can open it with its own tools, replacing whatever is there; a resend copies nothing, since the engine applies the envelope at most once and the inbox is the bot's since. It stages each file in the engine (`stageAttachment`) and stores the id the engine minted; **claims** the attempt, and calls `dispatch` with the dispatch id as the key. The claim is one conditional update, right before the call, that raises the attempt count only if the dispatch is still `intended` and at the attempt count read before staging, and, for a first send, unfenced, in a session with no unsettled Stop that is neither retired nor lost, and, for a first start, admitted by the turn budget as it stands then ([Concurrency](#2-the-server-holds-waiting-wakes)). A first steer is checked again in the same transaction: if the turn it was planned for ended while its files were staging, the engine would make it a turn of its own, outside the budget, so the dispatch is released instead and its wakes go through a start's admission. When the claim changes nothing, the dispatch was settled meanwhile (a Stop fenced it while its files were staging, say) and the engine is not called. A resend claims whatever the fence or the Stop: the key may already be in the engine, and only the recovery can learn its answer. A staging the engine did not answer, or a file the store no longer has, is tried again with the recovery's backoff, by whichever worker owns the send: the dispatcher for a first send, under the turn budget like any other, and the recovery for a resend. Each worker hands the sender its own claim to the send, and the sender checks it again inside the gate before anything else: a first attempt given back because the engine was unreachable makes the dispatch the dispatcher's again, so a recovery that read it while it was claimed leaves it alone; after five failures the dispatch fails, as `rejected` when it was never sent and as `unresolved` when it was. A staging refused because the engine is unreachable counts no failure: the dispatch waits for the engine. A send that fails unexpectedly counts against the same bounds and is never tried again at once: before the claim, as a staging failure, since nothing was sent; after it, as an indeterminate answer for the recovery ([Recovery](#3-a-dispatch-is-written-before-the-engine-is-called)), since the call may have reached the engine. A defect that repeats so ends visibly within its bound, and a Stop that waits on the dispatch is not held for a day. The dispatcher and the recovery read their candidate rows one by one, so a row that cannot be read is the only one held back. When counting the defect fails too, or the defect comes before the gate (a dispatch that cannot be read, say), one write that touches nothing but the deadline of a dispatch still `intended` puts it thirty seconds ahead, so even then it is never retried at once, and a broken dispatch stays deferred while the others go on. A send into a session that is gone settles at once, without waiting out a backoff. The adapter derives the engine's command id and message id from that key ([Engine: the adapter's interface](engine.md#the-adapters-interface)), so sending the same dispatch again is the same command. The staged ids are the one input that may change between sends: a file is staged again whenever its `usableUntil` has passed before a send, including a recovery, because the engine claims the files before it looks at the key; a copy a recovery does not use is removed by the engine. A retried staging after a lost reply leaves an unused copy the same way.

The engine's answer records **acceptance**. Its first disposition is stored and never changes:

| Disposition | Meaning | What the server does |
| --- | --- | --- |
| `started` | A new turn started | The turn is admitted when its `turn-started` arrives |
| `queued` | A turn the engine began while the start was on its way runs first; this message's turn waits behind it | The turn is admitted when its `turn-started` arrives, with this dispatch's audience, whatever the turn ahead of it was for |
| `steered` | The message was given to that turn | The dispatch waits for the steer to settle (see below) |
| `new-turn` | A steer arrived too late, or the provider can take no steer: the message became its own turn, possibly after the running one | The turn is admitted when its `turn-started` arrives |

A dispatch accepted through a recovery has no disposition: the engine does not say how a key it already had was applied. The events say where it went, as for any other.

**Delivery** is what the events say, not the disposition: a dispatch is delivered when `turn-started` arrives with the cause `dispatch` and its key, or, for a steer, when it settles as taken. A steer settles only after the turn it steered has ended, with one event right after that turn's `turn-finished`, decided by the engine's own state: `steer-requeued` (the engine queued it as a follow-up turn: the dispatch and its wakes move to that turn, which is admitted when it starts), `steer-dropped` (Stop ended the turn first: the dispatch is dropped, and the engine shows its own notice) or otherwise `steered` (taken: the dispatch finishes with that turn's outcome). `steered` is the engine's claim; on some provider paths it cannot prove the model read the message ([Engine](engine.md#the-adapters-interface)). Until it settles the dispatch is accepted and undecided, and no `undelivered` wake fires for it. A steer rides a turn it does not own: it finishes with that turn and never follows its continuation, which belongs to the dispatch that owns the turn.

Events about a key can arrive before the engine's answer does, after a lost reply. They prove it applied: the server records the dispatch as accepted, with no disposition, and applies them. `turn-finished` names its turn's cause as `turn-started` does, so a turn that ends without starting (cancelled from the engine's queue, or failed before its provider took it) still settles its dispatch by key, including a dispatch the server knows only through a recovery, which names no turn.

**Refusals.** Only two answers prove that the engine applied nothing, and only on a dispatch's first send, which they refuse before anything is sent:

- `SessionBusy`: the adapter already saw a turn in the session. It is a best-effort check; a turn that begins just after it gives `queued` instead. The adapter saw a turn the server has not applied yet, so the session gets a **busy deadline**: nothing is planned into it before the deadline passes, two seconds doubling with each refusal in a row up to thirty, or before its next event is applied, which clears the deadline and nudges the dispatcher. A deadline rather than a mark, so a turn whose last event committed before the refusal was recorded never strands the session.
- `SessionNotFound`: the adapter has no such session. The session is recorded **lost** ([Sessions](#sessions)).

Either one **releases** the dispatch: its wakes wait again, and its catch-up notes and held messages go back for the next envelope. `EngineUnavailable` proves the same and gives the attempt back.

`DispatchRejected` means the engine's reply named a refusal, so it applied nothing and the key is spent. The dispatch **fails** as `rejected`, and its wakes fail visibly: each shows, where it came from, that it did not reach the bot. They never return to pending on their own, because the same wakes would be refused the same way; `message.retry` sends an operator message again as new wakes, under a new key. An `ask` answer has no message of its own, so its failure shows as a retryable `turn-failed` notice where the answer was for, written in the same transaction as the failure, whether the dispatch failed or the engine dropped the turn it was to start. Its class says why: `stopped` when a room's Stop dropped it, `engine-unavailable` when its send was never resolved, `unknown` otherwise. Whether such a notice offers a retry is one rule, read again from durable state after every change to its dispatch or that dispatch's wakes, and again when the retry is pressed: the dispatch failed or the engine dropped it, so the engine cannot still have the answer and never delivered it, and the answer's wake failed and was not sent again. A key the engine accepts after all takes the retry away whichever arrives first, its reply or its events; the engine dropping it before its turn started gives the retry back; a delivery ends it. A notice for a turn that ran and failed is retried on its own terms ([The outcome](#5-the-outcome-closes-the-dispatch)).

**Catch-up notes and held messages** go back only when the dispatch that consumed them is released, proved never sent, or dropped by the engine. A failed dispatch keeps them, `rejected` or `unresolved` alike: an `unresolved` one may still land and deliver its envelope, and a note handed to the next envelope as well would be told twice.

**Recovery.** When the server cannot tell whether a dispatch reached the engine (it crashed during the call, or the call failed with `EngineIndeterminate`), it recovers the dispatch with `redispatch`: the same key, envelope, delivery and files, with none of `dispatch`'s local checks, because the key may itself have started the turn that makes the session busy. A lost reply is never taken as "not applied", and a dispatch with no recorded attempt was never sent, which is the only other proof of that. A recovery that succeeds means accepted, with no disposition. One that answers `DispatchRejected` fails the dispatch as `rejected`. Anything else is tried again with backoff, doubling from two seconds to ten minutes; while the engine is unreachable the server waits until it is ready again, or 30 seconds, since the engine's status can trail it, and the wait counts no attempt. Three things end the recovery without an answer: ten indeterminate answers, the session being retired, lost or removed (a rotation, a fresh start, a deleted bot, a session the engine no longer has), or the dispatch being older than a day. A session lost after the engine accepted the dispatch, and before its turn ran, ends it the same way: no event will ever report the turn, so it fails as `unresolved` and keeps the engine's first answer. A recovery that fails unexpectedly counts as an indeterminate answer. The engine keeps its receipts for good, so the day is J3 Bots' own bound, matching how long the engine keeps a session's events. The dispatch then fails as `unresolved` and its wakes fail visibly, never re-queued.

**Late delivery is legal.** If a turn later names a failed dispatch's key, the engine had applied it after all: the dispatch moves on to `delivered` and its turn goes to the dispatch's audience, and its wakes and messages show as delivered. If the events show the engine holding it before its turn starts (a `turn-queued`, or a replacement that lists its turn waiting), it is `accepted` again, and its messages show as pending with no retry: a failed wake counts as failed only while its dispatch is `failed` or `dropped`, and a message's retry sends only such wakes, so nothing the engine may still deliver is sent twice. A message the operator retried meanwhile went again under a new key, by their choice. A Stop recorded over such a dispatch's work still covers it: the Stop fences it, so its landing reopens the Stop and the turn is stopped on sight ([Stop](#stop)), while the dispatch stays failed and is the recovery's no more. A dispatch moves to a replacement session only through retried wakes. The server never guesses, so a wake is never delivered twice by J3 Bots' own doing, and never silently lost.

### One gate per session

Every step that sends a session something runs through that session's **gate**: one serial lock per session in the server process. A dispatch, a recovery, a held-queue resume, a Stop round and a room archival's Stop each take the gate, read the state they need inside it, make their engine call and record the result in one transaction, and release it. They never hold it while they wait for events or back off. So a Stop recorded while a dispatch waits for the gate fences that dispatch before it is sent, a resume never runs between a Stop's commands, and two recoveries of one key never overlap. Different sessions do not share a gate. A Stop round records durably, inside the gate and before its call, that it was issued.

### The workers

Five workers act on durable state: the **dispatcher** (pending wakes and every first send, also one whose files wait to be staged again), the **recovery** (every claimed send: dispatches sent at least once whose answer was lost), the **Stop runner**, the **responder** (the operator's answers to engine requests) and the **resumer** of held queues. Each is a reconciler. A pass reads what is due from the database and does it; nothing it needs lives only in memory. A signal from whoever changed that state only shortens the wait before the next pass: a pass also runs at the earliest durable deadline it knows of (a recovery's backoff, a resume's or an answer's retry, a busy deadline), five seconds after a pass that left due work undone (a session not ready, a call that timed out), and once a minute otherwise. So a timeout, a readiness change or a lost signal never leaves work waiting for good, and a pass that changed nothing schedules nothing extra: signals are fired only when state changed. Passes of one worker run one at a time, also those the startup sequence runs.

**Sessions are isolated.** A session that is lost, not yet known from its events, within a busy deadline, held by a Stop or not observable (its events cannot be applied, or a marker did not come in time) holds back only its own work: the pass skips it and goes on. Only the engine refusing a command (`EngineUnavailable`) ends a pass, since nothing else can be sent either; that worker then waits until the engine is ready again, or thirty seconds, since the engine's status can trail it. A catch-up (`synchronize`) that fails the same way is that session's alone: the adapter's catch-up of one stream failed or timed out, so the Stop runner and the resumer defer that session and go on.

**Each worker is supervised.** A defect in one item (a send, one session's Stop round, one answer, one resume) is logged and the pass goes on with the rest, and the item waits for a durable deadline. A send's defect counts against the dispatch's bounds, so it ends visibly; one the sender could not count is caught at the send itself, in the dispatcher and the recovery alike, and the pass looks again in thirty seconds. An answer or a resume, whose key makes every send of it one command, is sent again on the backoff of a lost reply, as long as its request is open or its hold is current. A session's Stop work waits thirty seconds, a deadline stored on its targets. A defect that escapes a pass is logged and the worker waits thirty seconds before its next pass. Every loop of the machinery (each of the five workers, the stall watcher, the engine status loop) is supervised on its own, the same way. A failure is never retried at once, and one loop's failure never stops another.

**Idempotent work retries for as long as it is due.** An answer to an engine request and a held queue's resume carry a key the engine applies once, so a lost reply is never final: each is sent again with the recovery's backoff, doubling up to ten minutes, its deadline stored with it, for as long as its request is open or its hold is the session's current one. A dispatch is different: an unresolved one fails visibly at its bounds, because the operator must know that it may never arrive.

### 4. The turn is observed, and admitted

The adapter streams each session's events, and the server derives the bot's state from them: thinking, working, waiting on a request, blocked, idle. A working bot shows its newest step still running, since steps run in parallel. A running turn with no step, tool call, request or speech for ten minutes is shown as stalled. Clients see that state live. The server opens a session's stream before it relies on it: the engine answers `synchronize` only on the streams open when it is called, and a stream counts as open from when it is subscribed ([Engine](engine.md#the-adapters-interface)), so a stream is started before anything waits for its marker. Nothing is planned or sent into a session before its state is known from a committed cursor, or from the first replacement once it is applied: until then the planner leaves its wakes pending, taking no slot, a send into it is skipped, and the event that makes it known nudges the dispatcher. Asking whether a session is known never opens its stream; the workers open it (`watch`) where they need it. Each event is applied and its cursor stored in one transaction, so a restart neither skips nor repeats one; once it commits the session is marked known before the change is published, so whoever sees the change finds the session ready. A wait for a marker is tied to its stream: it fails, to be retried, when the stream closes, and every `synchronize` has a deadline of ten seconds, shorter than the adapter's own ([Engine](engine.md#the-adapters-interface)), so a stalled stream defers only its session's work. A stream that ends is opened again with backoff, doubling up to a minute; until then the session is not known, and nothing opens it sooner. So is a stream that could not be opened, and one whose end could not be handled: what was subscribed is closed, and nothing is left looking open. Waiters on a stream fail only once its end was handled, so one that retries finds the session as that end left it. Once a session is recorded lost, checked inside each event's transaction, its stream is no longer read: what it had buffered is never applied. An applied event nudges the dispatcher only when it can change whether the session is idle (a turn starting or finishing, a dispatch or steer settling, a replacement, a request opening or closing), when it ends a busy deadline, or when it makes the session known; it nudges the Stop runner only in the first case. An event the server cannot apply is not skipped: it is logged with its cause, shown once in the conversation as an `observation-failed` notice, and read again on each reopening. The notice is written in its own transaction and counts as shown only once it commits: one that cannot be written is logged, tried again the next time, and never keeps the stream from being opened again. Until an event of the session applies again, nothing is sent into it, because what the server knows of it is behind. A stream that ends with `SessionNotFound` records the session lost. A stream that resumes too late to replay starts with one replacement of the session's state, and the server reconciles against it by stable ids (turn, request, speech and dispatch key), so a turn, a speech or a resolution it already applied changes nothing when it comes again ([Engine](engine.md#the-adapters-interface)).

A session has at most one **admitted turn**: its running turn, once the provider took it, with its **audience**, where its speech goes (the bot's conversation, or one room). A turn caused by a dispatch is admitted when it starts, with the dispatch's audience; a `queued` start keeps its own audience even when the turn ahead of it was a room's. A turn the engine started to continue another after a usage limit reset is admitted with the audience of the turn it continues ([Continuations](#5-the-outcome-closes-the-dispatch)). A turn the engine started for background work that finished is admitted with the bot's own conversation as its audience.

What the bot *says* does not come from the event stream. It comes from the bot calling J3 Bots' `say` tool, which appends an entry to the audience of the turn the call came from and returns ([Bot tools](#bot-tools)). A `say` or `ask` that cannot be matched to a call of the session's running turn fails with a typed `TurnEnded` result, and nothing is published or recorded. A call to the engine's own `send_to_user` tool arrives as host speech and is delivered once per speech id, like a `say` without `done`, so a slip is not lost.

A `say` with `done: true` **closes the delivery**: the delivered dispatch that owns the turn has its wakes finished, and the operator sees the bot's reply as delivered. A steer riding the turn is not closed by it: it settles as the engine reports. It does not interrupt the run. The bot is expected to end its turn; if it keeps working, what it says next still reaches the same audience. The server never interrupts a run to end it, because an interrupt may drop the delivery of a delegated task's completion ([Engine](engine.md#behaviors-j3-bots-designs-around)).

The turn's final reply text is never published: the base prompt tells the bot it reaches nobody, and the bot may have used it for notes. If a `user` wake's turn ends without a `say` carrying `done: true`, a pending question or a background handoff, the server wakes the bot once more with an `undelivered` system wake. If that turn also delivers nothing, the conversation shows a notice with a retry action. Neither comes for work a Stop covers ([Stop](#stop)).

### 5. The outcome closes the dispatch

When the turn ends, the dispatch records how: completed, failed (with the engine's error class), interrupted, or waiting on the operator, and its wakes are finished. A failed routine wake is retried according to its routine's policy. An operator's turn that failed, or that something other than the operator's Stop interrupted (a provider, an engine restart), shows a `turn-failed` notice in the conversation with a retry action; an interruption carries the class `unknown`. A turn that fails before it starts never delivered its dispatch, so the dispatch fails as `rejected` and its messages show that they did not reach the bot.

The adapter knows which turn delivers a dispatch because every engine run names the message that started it, and that message's id comes from the dispatch key; a steer's follow-up turn keeps the same message, and a run the engine restarted to take a steer keeps the message of its first attempt. A turn the engine started on its own closes no dispatch.

**Continuations.** A turn that fails at a usage limit may end with a pending continuation: the engine will resume it at the reset ([Engine](engine.md#the-adapters-interface)). Only the dispatch that owns the turn follows it. Its `turn-finished` then leaves the dispatch delivered rather than finished, with the outcome so far and the reset time recorded, and no `undelivered` wake fires. When the continuation turn starts, its cause names the turn it continues; the server follows that one link, moving the dispatch's turn and its audience to the new turn, so a chain of continuations is followed a link at a time. A continuation turn that ends before it started (it failed, or a Stop cancelled it while it waited) follows the link the same way, by its cause, as its end is applied: once the engine has a turn continuing another it sends no `continuation-dropped`, so nothing else would end that work. The dispatch finishes when a turn ends with no continuation pending, or when `continuation-dropped` arrives, with the last outcome; only then does an `undelivered` wake fire if nothing was delivered. A last turn that did not complete (it failed, was interrupted, or was cancelled before it started) gives a `turn-failed` notice instead, unless a Stop covers the work. A continuation cancelled before it started ran nothing, so its notice shows the outcome of the turn it was to continue, as when one is dropped. A pending continuation keeps the session busy for automated wakes, which wait for the reset anyway. An operator wake is still dispatched; the engine then drops the continuation, because it resumes only the session's latest turn. A Stop disarms it too. J3 Bots never snoozes a session: snoozing would only delay the continuation. The engine's continuation after its own restart is turned off, so a turn a restart cut short ends `interrupted` like any other.

### Stop

A Stop is a separate path, never a side effect of `done`, and a durable one: it is written down before the engine is called, and finished after a crash. It has a **scope**: `bot`, the operator's Stop of one bot, which ends all of its work; or `room`, recorded when a room is archived, which ends only work whose audience is that room.

1. **Record.** In one transaction the server writes the Stop under its command id with its **targets**: every session of the bot with a turn running, or a dispatch that may have been sent (`intended` with an attempt, `accepted`, `delivered`, or failed `unresolved`, whose key may still land, a turn waiting in the engine included), in the Stop's scope. A `bot` Stop also targets every live session of the bot that the engine has, for background work the server does not see. A `room` Stop targets only what the room owns on this release: its turns and dispatches; it reaches no background work a room turn left running once that turn ended ([Rooms](#rooms)). Each target's first round gets an engine key derived from the Stop's command id, the session id and the round. The same transaction **fences** every dispatch in scope that has not been accepted yet, so it is never sent for delivery again, and cancels every wake in scope the server still holds; each shows as cancelled where it came from. A fenced dispatch that was never sent is released, its wakes cancelled.
2. **Settle the dispatches in flight.** A dispatch of the target session whose call may still be in flight is waited for, and so is every one whose reply was lost, fenced or not: confirmation needs the engine's answer for each. They belong to the recovery, which tries a fenced one at once and every one with its usual backoff and bounds, recovering it with its key to learn the answer: if the engine had applied it, the recovery applies nothing; if it had not, the recovery applies it, and the stop that follows ends it. The Stop waits for them in that session, and meanwhile the session's running turn keeps running: no round is sent before the recovery settles them. Either way nothing the bot was sent lands behind the Stop. A fenced dispatch that may have been sent never waits again: if it fails, refused or unresolved, its wakes are settled by the one rule below ([What a Stop covers](#stop)). Only a dispatch proved never sent gives its wakes back. A dispatch that failed `unresolved`, whose key may still land, is fenced too, without returning to the recovery: it waits for nothing, and its landing reopens the Stop (step 4).
3. **Stop each target.** The round is **issued** first: recorded, inside the session's gate, before its commands are sent. Then `stop` with the round's key ends the running turn and the delegated work the engine can reach, including background work a turn left running after it ended, cancels every turn waiting in the engine, drops untaken steers and disarms a pending continuation. The adapter sends the engine's own stop to every target, also one with no running turn. The adapter derives each engine command from the key, so a retried round, or one resumed after a crash, sends the same commands. Its success only acknowledges the commands, and is recorded as the round's acknowledgment. Each command is resolved by its key, as a dispatch is: a call that gets no answer, or an error reply that proves nothing, leaves the round issued and unacknowledged, and the runner sends it again with the same key on a later pass, with no other signal needed; the engine's receipt for the key answers it. When the receipt shows the engine refused the round while something it targets can still run, the round's key is spent: the round is marked refused and the target gets a fresh round, with a new key, due after the recovery's backoff, doubling with each round the engine refused since it last acknowledged one, up to ten minutes. No fresh round follows a target that settled meanwhile: every writer of a round checks, in the transaction that writes it, that the target is unsettled and its session not lost, so a refusal the runner hears after the session's loss committed is recorded on its round and opens nothing. Each round waits only on its own deadline: another target's round that is due, such as the operator's new Stop, goes out meanwhile. A refusal while nothing it targets can still run is moot, and counts as acknowledged. A refusal while a tool whose persistence the adapter could not decide is live is not: a refused stop interrupted nothing, so the tool may still run ([Engine](engine.md#the-adapters-interface)).
4. **Confirm from the events.** One rule governs every target: it settles only when the engine's own state shows nothing the Stop targeted can still run, no run waiting, preparing, starting or running and no background work pending; and as long as it is unsettled, something keeps acting on it. Its latest round is always in a state a durable deadline or an event moves on: not yet sent, and sent once due (step 3); being sent, and resolved by its key; refused, and followed by a fresh round after a backoff; acknowledged, and watched until the target settles, with a fresh round once the round's grace passes while the engine still shows work it targets. Waiting on a round the engine refused or ignored is never an option. The acknowledgment of step 3 only says the engine took the commands; their effects can lag it, and the engine can lose them without saying so (an interrupt it could not plan, a run whose provider never starts). After it, the server synchronizes the session, which **observes** the round: every event the engine had by then is applied. A marker that reports what no event has told of leaves the round unobserved, and the runner synchronizes again a few seconds later ([Engine](engine.md#the-adapters-interface)): background work the engine still counts as pending, which in a session whose last turn already ended the engine's stop interrupts only after it answered, and which an interrupt the engine failed to plan leaves running though the stop was acknowledged (a tool whose persistence the adapter could not read from the stream counts as the engine's own projection of its pending work shows it, and as pending while that cannot say); and a run the engine can still run: one it is starting, created after the round's commands or held by a provider that never starts it, or one it queued on its own after the round's cancels, such as a scheduled message, which no dispatch of the server's names and no event will start while the Stop holds the queue. **Grace.** An acknowledged round gives the engine 30 seconds to show its effect, doubling with each round of the target the engine acknowledged, up to ten minutes. When a synchronization after that still shows work the Stop targets (a run waiting, preparing, starting or running, a dispatch waiting in the engine's queue, a continuation pending, background work pending), the target gets one fresh round, due at once, whatever the events did or did not announce. The deadline is the round's own, so it holds across a restart. A Stop the engine can never end therefore costs a bounded amount: one round per grace, at most one every ten minutes once the grace has reached its cap, and a synchronization of the session every five seconds. A target is stopped when its latest round is observed and the session's events then show nothing left: no running turn, no dispatch the engine may still start, no continuation pending. This holds for a `room` Stop too: the engine's stop ends the whole session, its background work included, so a session a `room` Stop targets confirms only once the engine shows no background work pending there, whoever started it. What a `room` Stop does not do is target a session only because a room turn left background work running: it has no record that ties such work to the room ([Rooms](#rooms)).

    Such a Stop settles by no deadline of its own: it stays unsettled for as long as the engine counts the work as pending, and the session takes nothing meanwhile, while the server keeps sending a round after each grace. That is the engine's own account, and the engine keeps acting on it: an interrupt the provider does not confirm leaves the turn open for the operator to force-stop it in the engine's console, and a command queued behind it waits for the turn to end (**Read** at `db51b67`: `ClaudeAdapterV2.ts`, L13831-13845; `Orchestrator.ts`, L14122-14130). The operator can also stop the bot again, which records a fresh round for every live session of the bot ([Record](#stop)) and goes out at once, whatever the backoff of earlier rounds. The Stop runner confirms only from such an observation, never from one event as it is applied, because the next event may start a turn the engine had waiting; each event that is not itself a marker makes it observe again. A turn whose start is applied once the latest round was issued, also one that started while the round's commands were on their way, opens a new round, since the commands may have missed it; so does a fenced dispatch the engine applies after its target was confirmed, which shows as a turn with its key: it is stopped on sight. A dispatch the events first show waiting in the engine's queue (a `turn-queued`, or a replacement that lists its turn waiting) opens one too, as it is accepted: its key may have landed after the round's cancels, held in the queue the Stop left, where no turn would start to reopen the Stop. Only that first sight does; a replacement that lists the turn again finds the dispatch already accepted. The Stop is finished when every target is stopped.

**A session with an unsettled Stop takes nothing.** From the moment its target is recorded until it is confirmed stopped, the server sends that session no first send (only the recoveries of step 2) and resumes no held queue in it. The engine's Stop is several commands, and a message arriving between them could restart a turn the Stop is ending ([Engine](engine.md#behaviors-j3-bots-designs-around)). The rule is the database's, so it holds across a restart: each round records when it was issued, acknowledged and observed, and the Stop runner's first pass at start, once every session's events are followed again, sends the rounds that were never acknowledged and confirms only from an observation made after an acknowledgment. Once a target is confirmed, what it held back is nudged: the dispatcher, the recovery and the resumer.

**What a Stop covers.** One rule decides whether work is the operator's to have stopped: a Stop of the bot, or of the room the work was for, recorded after the dispatch that began the work was written. The order is exact, not a time: every dispatch has a sequence number, higher than any written before it and never reused, and a Stop records the highest one when it is recorded. Work is covered when its dispatch's number is at or below that mark. SQLite serializes writes, so a dispatch committed after the Stop is always above it, even in the same millisecond or after the clock stepped back. Whether that Stop has settled does not matter: nothing is planned into its sessions while it is unsettled, so work that began after it was planned after it, as new intent. Work it covers starts nothing new of its own accord: a turn that ends, even on its own before the interrupt lands, gets no `undelivered` wake and no notice. The rule applies wherever work, not the operator, would create a wake; such a wake also needs a place to go, so a room archived or deleted meanwhile gets none. An operator's own wake after a Stop is never covered: it is new intent.

The same rule settles every dispatch that will not run to its end, read in the transaction that settles it, so a Stop recorded or a room archived meanwhile counts:

| The dispatch | Covered by a Stop | Not covered |
| --- | --- | --- |
| Never sent (released) | Wakes cancelled | Wakes pending again |
| Dropped by the engine (a waiting turn cancelled, a steer dropped) | Wakes cancelled | Wakes failed as `stopped` |
| Failed (`rejected`, `unresolved`, its session lost) | Wakes cancelled | Wakes failed with that reason |

A notice follows from the outcome: cancelled wakes get none, and failed ones show where they came from, retryable. The events close the rest: the running turn ends interrupted, a waiting turn ends cancelled and its dispatch is dropped, a dropped steer drops its dispatch. The engine's Stop ends a whole session, so a `room` Stop also reaches private work in a member's main session, which it does not cover: a private dispatch it fenced before sending is released, its wakes pending again, and one the Stop drops fails as `stopped`, visibly and retryable, because the operator did not stop it, also one whose recovery had given up and that the engine took late: its wakes fail again, as `stopped`, and an answer keeps the notice it already shows, which now says so. So does work a Stop sent from the engine's own console drops: the server recorded no Stop. Work for the room, and all of a bot's work under a later `bot` Stop, is covered. A room's dispatch that was never sent is fenced and cancelled even when no session needs the engine's Stop. Background work the engine could not reach may still wake the bot later, as a background turn.

**Held queues.** The adapter reports each hold of a session's engine queue as a `queue-held` event, with the turns waiting behind it. Applying it only stores the hold's cursor on the session; the resumer, a worker like the others, resumes it with `resumeQueue` naming that cursor, once: it stores the cursor of the hold it last resumed, and a hold equal to it is not resumed again. Before a resume it synchronizes the session, so a replacement that shows the queue no longer held, or a hold replayed from before, is applied first, and it then reads the hold again inside the session's gate. A replacement that shows the queue not held clears a hold recorded before. A resume whose reply was lost, or that failed unexpectedly, is sent again for the same hold with backoff, doubling up to ten minutes, for as long as that hold is the session's current one ([The workers](#the-workers)); a resume's result is recorded only if the hold it answered is still current, so a newer hold is never taken as resumed. Each session's resume runs on its own: one that fails never holds up another's. It never resumes while a Stop of the session is unsettled; the hold is resumed once the Stop is confirmed, if turns still wait. Nor does it resume a hold of a retired or lost session, whose queue holds nothing the bot waits for, and it reads that again in the gate, so a session retired meanwhile is left alone. The engine refuses a resume on an archived session or at a usage limit, which leaves the queue to the engine's own rules.

## Questions, approvals and secrets

Two kinds of card wait on the operator, with separate lifecycles.

**A bot's `ask`** is a J3 Bots question. The card stores the wake it came from and the audience of the turn that asked: the conversation, or the room. The bot ends its turn after asking. The card does not expire. Answering or dismissing it closes the card and creates a `user` wake carrying the answer in the same transaction, with the stored audience; that wake's turn delivers there. An answer is never steered into a running turn and never shares an envelope with a steer: one that arrives before the turn that asked has ended waits for it, and then starts the next turn. The answer's envelope is defined in [Prompt architecture](../prompts/architecture.md#wake-envelopes).

**The engine's requests** belong to a running turn: an approval, a question asked through the harness's own tool, or a secret request. The card stores the session, the engine's request id and the turn. Its card goes to the bot's conversation, also during a room turn, because the operator answers for their bot there. While the request is open, the engine can report a fuller record of it (`request-updated`, such as an approval that becomes exact once its file change is fetched), and a replacement lists it as it then shows: the card shows that record in place and keeps its status, so an answer already recorded is the one sent. "Allow for session" is taken only while the card offers a grant (`sessionGrant`). An engine question takes a choice or a typed answer, not both: the engine receives a typed answer alone, so an answer with both is refused (`Invalid("answer")`) rather than shown with a choice the turn never got. An `ask` question takes both. Answering it records the answer durably and then sends it to the engine for that turn, keyed by the card, so the answer is applied once however often it is sent, and the turn continues. A card takes one answer: a second command finds it closed. The responder sends each answer the engine has not taken; one whose reply was lost, or whose send failed unexpectedly, is sent again with backoff, doubling up to ten minutes, for as long as its request is open ([The workers](#the-workers)). Each answer is sent on its own: one that fails never holds up the next. When the turn ends, every request still open on it expires, and its card shows that it expired. An engine question too large for a card (`unsupported-question`: more than four questions, or more than six options to one) is shown as a question card that says so, with no options and only a dismiss, which the bot reads as "no"; the server never shows part of a question.

**A secret request** comes from a bot calling the engine's `request_secret` tool. Its card shows the label, the reason, an optional link and a placeholder, never a value. The operator's answer travels in its own request (`secret.provide`), which hands the value straight to the engine. The value never enters an entry, a change, a log or a command receipt. The card records only that a value was provided, or declined, or that the request expired, from the request's resolution. `secret.provide` succeeds only when this call's own answer was the one the engine took. It has no receipt, so after a lost reply a retry may find the request closed: the server synchronizes the session and fails with `Conflict("card-closed")`, because the closing answer may have been another device's, or the request expired. A closed card is never reported as success; the card itself shows how it closed. The server takes one submission per card at a time, and so does the adapter per request, so a second device's submission waits for the first and then finds the card closed. Before calling the engine, the server writes a durable marker on the card that a submission is in flight, naming that submission and holding no value, and clears it on a definite answer; a cleanup removes only the marker of its own submission, so it never erases a newer one. A marker left by `EngineIndeterminate`, or found at start after a crash, means the outcome is unknown: the server synchronizes the session at start, and before it sends the next submission for that card. A request that is closed then shows how it closed; one still open takes a value again, and a submission that lands late only makes the next one find the card closed.

## Attachments

Files cross the server in both directions as attachments. Bytes and names are stored apart: a **blob** is the bytes, stored once under `<J3_HOME>/attachments` by their SHA-256; an **attachment** is a name and a media type over a blob. The same bytes sent twice, or under two names, are one blob and two attachments.

- A client uploads a file with `POST /attachments` before sending the message that carries it, and gets its id. The server puts its name and media type in the form the engine's upload takes (`normalizeAttachmentMetadata`: the name trimmed, the media type lowercased without parameters, at most 100 characters) and stores that, so a staging never fails on metadata. An empty file, a blank name or an unusable media type is refused; each file is limited to 25 MiB. `message.send` names up to ten, and the server checks them against the engine's limits before it writes anything: inline images (GIF, JPEG, PNG, WebP) at most 10 MiB each and 80 MiB together. It checks the message's length as the bot would read it the same way. Coalesced wakes are checked again together ([coalescing](#2-the-server-holds-waiting-wakes)).
- The dispatch lists its files in order. Before its first send, each is staged in the engine, which mints its own id for it; the server keeps that id with the dispatch, so a retry sends the same staged file. A file is staged again whenever its `usableUntil` has passed before a send, including a recovery, because the engine claims the files before it looks at the key; a copy a recovery does not use is removed by the engine.
- A file a bot attaches to `say` is copied from its workspace into the same store, so the operator's devices can open it after the bot has changed or removed its copy. Paths outside the workspace, links that lead outside it and URLs are refused: the server never fetches a file for a bot. The workspace is its real path as the server recorded it when it first provisioned the folder, before the bot's first turn (`workspace_root`), never resolved again, so a link the bot puts in the folder's place leads outside it. The path is resolved and checked, then opened without following a link at its name and without waiting on a FIFO, and the check that counts is made on the open descriptor, since the bot can swap a folder on the way for a link between the check and the open: on Linux by the name the kernel gives the descriptor's file (`/proc/self/fd`), elsewhere by matching the descriptor's file to what the path resolves to again, which narrows the swap to one made and undone between two reads. This containment is a guardrail, not a security boundary: the bot runs as the same user ([Security](security.md)). Only a regular file is read, and at most `MAX_ATTACHMENT_SIZE` bytes of it, the limit of an upload: a larger file is refused once the read passes the limit. The files of one `say` together take at most 25 MiB (`MAX_SAY_ATTACHMENTS_SIZE`): the operator's upload path has no total per message, so a `say` takes one upload's worth, and each file is read only up to what is left of it, so a `say` past the total is refused while it is read and never buffers more. Every file is checked, its name included, before any is stored. The files are stored in the transaction that admits the `say` and publishes its message, so a refused `say` stores none of them; bytes written for a transaction that rolled back are removed before the store's lock is released. Writing a blob's file and counting it for that removal are one step an interruption waits out, so a write the file system finishes after an admission's deadline is still removed.
- The store has one lock over its files, so writing a blob and removing one never interleave. It is always taken before a transaction and never inside one: an upload, a `say` with files and a blob's removal take them in that order, so they never wait on each other in turn.
- `GET /attachments/:id` serves a file to a paired device only, with the device token as a bearer.
- `bot.files` lists the files a bot has produced, newest first, for the bot's details view.

## Sessions

Each bot has one **main session**: an engine thread in the bot's project, where operator turns, room turns and teammate messages all land. One working context means a bot in a room can use what the operator told it privately, which is what makes it the same teammate everywhere.

**Side sessions** are short-lived engine threads in the same project, used for routine runs. They start with fresh context, see the same system prompt and memory files, and can deliver messages with `say` like the main session.

A session's id is J3 Bots' own, written before the engine is asked for a thread and used as the key of that request, so a retried creation cannot make a second thread. The engine's thread id is stored next to it once known, unique across sessions. The prompt version the session was created with is recorded too, so a session started on an older prompt can be found and rotated.

Because the main session does not see what a side session did, the server keeps a **catch-up note** per bot, in the database. When the bot next wakes in its main session, the envelope begins with what happened since: "Routine 'Morning repo check' ran at 08:03 and told the user: …". The note is consumed in the same transaction that writes that dispatch, so it is neither lost nor shown twice.

**Rotation.** The server replaces a bot's main session when any of these is true:

- it ran 200 turns, a provisional threshold ([open question 8](../open-questions.md));
- the engine ran a turn on recovered context because the provider could not resume its own conversation (the turn ends with `contextRecovered`, [Engine](engine.md#the-adapters-interface));
- the operator moved the bot to another provider (another model on the same provider stays in the session, through `configureSession`);
- the operator asked for a fresh start (`bot.freshStart`).

Each records the reason on the session in the transaction of what caused it. A stronger reason replaces a weaker one (the run limit, then recovered context, then a provider change, then a fresh start); a weaker one never replaces a stronger. How the rotator waits depends on the reason, and quiet is the engine's word: before it retires a session it takes a synchronization marker ([Engine](engine.md#the-adapters-interface)) once the session's events are known, and then checks again, in the transaction that retires the session, what the server itself knows: no admitted or open turn, no continuation pending, no dispatch on its way and no Stop unsettled.

- **The run limit** waits for the session to be quiet by the engine's own stop rule: no turn it can still run, also one whose provider has not started, and no background work pending, counting work the adapter could not judge yet ([Engine](engine.md#the-adapters-interface)). Meanwhile the session still takes new work, so long background work, a dev server or a watcher, never holds the bot's wakes. Background work that may end with no event is looked at again every 30 seconds.
- **Recovered context** waits only until no turn runs or can run. Nothing new is planned into the session. Background work it still has is ended by the retirement, as for a lost session, and the server logs that it was when the engine showed background work pending.
- **A provider change and a fresh start** are the operator's own actions. Each first stops the bot's work through the Stop machinery ([Stop](#stop)), in the transaction that records it, so the session is quiet once that Stop settles; a client says so wherever it offers the action ("Stops any work {name} has running."). Nothing new is planned into the session, and wakes written after the action wait for the new one. A fresh start also takes effect when the bot has no opened main session: the one written and not yet opened is retired at once.

In one transaction the rotator retires the session and writes a catch-up note with a digest of the conversation, unless the operator asked for a fresh start, which carries none; memory files stay either way. The bot has at most one digest waiting: a later one replaces one no envelope carried yet, and a fresh start drops it. A fresh start also records where the conversation stood, and no later digest reaches back past that point, so a session lost after a fresh start brings only what was said since. A digest belongs to the session it was written for: when a dispatch that carried it is returned unsent because its session was retired or lost, the digest goes with it, and the session that replaces that one gets a digest of its own. The bot's new main session is then opened as any is, and its first envelope brings the note in `since-last-turn`, ahead of whatever woke it, so a rotation costs no turn of its own. The old engine thread is archived (`retireSession`), retried until the engine answers, and never deleted; an archive whose answer was lost waits for the next pass for that session alone, while the pass goes on with the others; the server closes its event stream and never follows it again. The conversation itself is untouched.

A dispatch planned into a session is written only if, in the writing transaction, the session is still live and still takes new work; otherwise the bot's wakes are planned again, into whichever session now takes them. So no envelope reaches a session the rotator has retired or reserved for its replacement.

**Every bot has a main session.** On each pass the rotator opens the main session of any live bot that has none opened: under the key of the one already written, so a retried creation makes no second thread, or a new one. A failed opening is tried again from 5 seconds, doubling up to 5 minutes, with no engine restart needed; an engine that takes no commands waits until it is ready. The provider of a session is chosen in the transaction that writes its row, from the bot's provider then, and a session is opened only on that provider: a bot moved to another provider before its session opened gets a new session on the new one, never one on the provider it left. Once the engine answers an opening, the rotator sets the session's model and permission mode to what the bot has then (`configureSession`), also when a retried opening returned a thread created with older ones, and again if the bot's settings changed while the session's engine id was being recorded; only then can the session take work. A crash between the engine creating the thread and the server recording its id leaves that thread on the engine; if the session is then retired before it is opened again, nothing knows the thread's id to archive it, so it stays on the engine un-archived, idle and unused.

The digest is the delivered messages of the bot's conversation, the operator's and the bot's own, newest kept: at most the last 60 such messages, each cut to 1,000 characters, 6,000 characters in all with the names of their files, oldest first. Each message is kept apart with its author, so the envelope renders it as its own block ([Prompts](../prompts/architecture.md)). Notices and messages that never reached the bot neither appear nor count toward the 60. Memory, not the digest, is what a bot relies on across rotations ([decision 0003](../decisions/0003-conversation-is-not-session.md)).

**A lost session.** When the engine answers that it has no such session (`SessionNotFound`), to a send, a Stop round, a resume, an answer or the event stream, the session is recorded **lost**, once, and everything open in it is settled in the same transaction, since nothing runs there any more: its Stop targets settle, each round keeping what the engine answered for it, a refusal included; a dispatch the engine had accepted, also one it queued, fails as `unresolved` and keeps the engine's first answer, its wakes failed and retryable, or cancelled when a Stop covers them ([What a Stop covers](#stop)); a delivered one, every open turn and its work fold end interrupted; its open requests close as expired. A dispatch whose answer is not known is due at once and the sender settles it in the gate, as `unresolved` when it was sent. Nothing is planned into the session or watched in it again, and it counts toward no budget. Its loss only holds back its own work: every other bot goes on. A lost main session shows a `session-lost` notice in the bot's conversation; the bot's wakes wait until it has a new main session, which the rotator opens at once, with the same digest a rotation brings ([Rotation](#sessions)).

## Bot tools

Bots act on J3 Bots through a small MCP server named `j3`. The harness starts it as a local stdio process, one per loaded session; that process forwards each call to the J3 Bots server's tool endpoint, an HTTP listener of its own on `127.0.0.1:J3_TOOL_PORT`, which stays on loopback whatever `host` is. It holds no state and does no work of its own, because a host with many recently active bots runs many of them (see [Engine](engine.md#footprint)).

The bridge identifies its caller from `T3CODE_THREAD_ID`, an environment variable the engine sets for each stdio MCP server the harness starts, with the session's thread id. The bridge reads it with `sessionOfToolCaller` from `packages/engine-t3` and never names the variable itself. The server maps that id to a session and a bot. A call from an unknown thread is refused. **Verified** on Claude Code on releases `4941` and `4969`, and on Codex from `4969`, the pinned release ([Engine](engine.md#version-pinning)).

**Matching a call to its turn.** A request carries a session, not a turn, and the server's view of the session can trail the engine by a few events: a call made at the end of one turn could otherwise act for the next. So the server matches each request to the engine's own record of the call. The engine reports every `j3` tool call as a `tool-call` event in its turn, with the bare tool name and a digest of its input ([Engine](engine.md#the-adapters-interface)).

1. It picks a token, starts waiting for it, and calls `synchronize` for the session. When its event applier has applied the `synchronized` event with that token, every event the engine had when the request arrived has been applied.
2. It looks, in the session's running admitted turn, for an open call to the same tool whose input digest equals `toolInputDigest` of the request's arguments and that no other request has claimed. It takes the oldest.
3. The engine records the call apart from the request, so the call may not be there yet. Without a match the server synchronizes again, up to five times within two seconds.
4. With a match, the request is **pinned**: stored under the bridge's id for the request with the turn, the turn's audience and the engine's id for the call, which no other request can claim. The pin is written in the transaction that publishes what the request says, and that transaction checks again, from what is committed, that the call is still open and unclaimed in the session's admitted turn, with the input digest it was matched by (the engine records an open, unclaimed call again when an ACP agent reports its arguments late, so a request matched against the earlier input does not claim the call as recorded since), that the turn has not finished, and that the room the turn speaks for is still live, also for a `say` to the operator from a room turn. A retry of a request that already committed returns its stored result there. The files a `say` attaches are read before and stored only once the pin holds. Everything the request does acts for that turn and audience, even if the session admits another turn meanwhile.
5. Without one, the request fails with a typed `TurnEnded` result whose text the bot reads (`NO_TURN_REFUSAL` in `packages/prompts`), and nothing is published or recorded: the call belongs to a turn that has ended, or to no turn of this session.

**Subagents cannot speak.** A Claude Code subagent's tool call is recorded on the subagent's own thread, outside the bot's turn (**Read** at `db51b67`, `ClaudeAdapterV2.ts`, `startSubagentToolCall`; Codex is **Assumed** to do the same), so it never matches and is refused by step 5. The tool descriptions and the base prompt tell a subagent to report in its final reply instead.

**Duplicates.** Several requests may match one call: the bridge forwarding the same request twice under different ids, or a harness repeating an identical call. The oldest unclaimed request claims the call, and every other one is refused at step 5, so one call acts once. A later identical call is a call of its own, with its own engine record: the model made it twice, so it is accepted and acted on once more. That fails safe, because each call still acts exactly once: a repeated `say` shows twice, visibly, and a repeated `remember` is deduplicated.

**Size.** The engine shows a tool input over 16,384 bytes only as a summary, which no digest can match, so the tool schemas refuse arguments over 12,288 bytes with a message telling the bot to split them ([Engine](engine.md#behaviors-j3-bots-designs-around)).

A call whose audience is a room that is now archived fails with `Conflict("room-archived")`, and nothing is published.

The bridge gives each request one id and reuses it when it retries the forward, so a retry finds the stored request, acts for the same turn, and returns the stored result instead of acting twice. If the engine cannot be reached, the server retries the match until the request's deadline and then fails it as retryable. A request has fifteen seconds end to end; past that nothing was committed and it fails as retryable.

The `j3` tools are pre-approved in every permission mode, so they never raise an approval card. How each harness is told so is in [Engine](engine.md#provisioning).

| Tool | Purpose |
| --- | --- |
| `say` | Deliver a message to the audience of the turn that made the call: the operator, or the room during a room turn. Optional attachments. `done` marks the delivery complete. |
| `ask` | Put one question to the operator as a card with options. Ends the turn. |
| `message_bot` | Send a message to a teammate. `urgent` wakes them now; otherwise it waits for their next turn. Returns only a delivery acknowledgement. |
| `remember`, `forget`, `recall` | Write, remove and search memory, in the bot's own scope or the shared one. |
| `set_routine` | Create, change, pause, resume or delete one of the bot's routines. |
| `list_teammates` | Names, titles and jobs of the operator's other bots and the rooms this bot is in. |
| `create_bot`, `update_bot` | Primary bot only by default: create a teammate with a name and a job, or refine one. |
| `update_profile` | Change this bot's own name, title or avatar when the operator asks. |

The complete parameter schemas and the wording of each description are part of the prompt package. See [Prompt architecture](../prompts/architecture.md#tools).

## Rooms

A room is J3 Bots data: members, host, entries, and a status. An active room has two to six members and a host among them. An archived room is read-only: it takes no messages and no changes but `pinned` and unarchiving, and it may have fewer than two members and no host. There is no engine object behind it.

**Archiving** a room, by the operator (`room.update` with `archived: true`) or because deleting bots left it too small, is one transaction that cancels every pending wake addressed to the room, expires the room's open `ask` cards (an answer can no longer reach it), and records a Stop for every member session whose turn, waiting turn or dispatch has the room as its audience, selected as every room Stop selects its targets ([Record](#stop)). That Stop has the `room` scope and then runs as any other ([Stop](#stop)). A bot tool call whose audience is the archived room fails with `Conflict("room-archived")`, and host speech from a turn whose audience is the archived room is not published there, including speech a replacement replays after the archival. Unarchiving needs two to six members and a host, which the same update may give. **Deleting** a room records the same Stop before the room's row goes. The Stop, the dispatches and the turns keep the room's id as plain text, with no reference to the row, so once the room is gone the one rule of [What a Stop covers](#stop) still tells its work from another room's: a dispatch of the deleted room that settles later, also one whose key the engine applies after the deletion, is covered by the room's Stop, and its wakes are cancelled.

**What a room's Stop does not end yet.** Room turns arrive with M3; until then no routing wakes a member for a room, so no room turn runs. A room's Stop therefore ends what a room can own on this release: its pending wakes, and its dispatches and turns, which [What a Stop covers](#stop) settles. It does not end background work a room turn left running after that turn ended. M3 must add that, with room turns, and track it by the run that started it: the engine attributes each item to the run it belongs to, and each task a provider reports to the run that was executing when the task first appeared (**Read** at `db51b67`, `contracts/orchestrationV2.ts`, L1107-1111, `runId`). A room's Stop then targets a session while work that a room turn's run started is still pending there. It must never use a flag kept for the whole session: the engine's own rule for pending background work is the session's and does not ask which run started the work, so such a flag either reaches private work the room never started or stays set after the room's work ended.

M3 must also keep three rules when room turns arrive:

- Retrying a room message, or answering a room card, revalidates the room's status. A wake that failed survives the room's archival, and an operator's retry records its wakes again without asking whether the room is still live (`Pipeline.ts`, `message.retry`; `Wakes.record` checks the room only for a wake caused by work).
- A path that returns a room's wake to `pending` asks `covers` first, as `wakesAfter` does, and no new `wakes` row carries the id of a room that was deleted.
- A background turn that follows a room's turn speaks to that turn's audience, not to the bot's conversation: it carries the audience of the turn whose work woke it.

When an entry is added to a room, the server decides who wakes:

| The entry | Who wakes |
| --- | --- |
| From the operator, mentions bots | Each mentioned bot, one at a time in the order mentioned |
| From the operator, mentions `@everyone` | Every member, one at a time in member order; each sees the replies before it |
| From the operator, mentions nobody | The host |
| From a bot, mentions another bot | The mentioned bot |
| From a bot, mentions nobody | Nobody. The room waits |

Mentions are structured: a message carries the bots it mentions, up to six, or `everyone`. The server never parses them out of the text.

A room wake is delivered into the bot's **main session**, wrapped in an envelope that names the room and carries only the entries the bot has not yet seen. Its audience is the room: during that turn `say` delivers to the room, and `say` with `to: "dm"` delivers privately to the operator.

A bot that has nothing to add ends its turn without calling `say`. That is the normal way a room goes quiet.

Approvals and questions raised during a room turn appear in the bot's own conversation. The room shows the bot as waiting.

## Deleting a bot

Deleting a bot removes its engine project first, so nothing keeps running for a bot that no longer exists, and waits for a session opening in progress to finish, so the rotator opens no session for a bot being deleted; while the engine cannot take that, the deletion fails with `Conflict("engine-unavailable")` and changes nothing. Then one transaction removes its conversation, sessions, wakes, routines and memory. What it said elsewhere stays:

- Entries it wrote in rooms keep their author id. Nothing refers to the bot row, so the entries outlive it, and clients render the author as a deleted bot.
- If it hosted a room, the room passes to the member who joined first among the rest, in the same transaction. The database refuses to leave an active room without a host.
- A room left with fewer than two members is archived, in the same transaction, as [Rooms](#rooms) describes: it stays readable, takes no new messages, and keeps no host if its host was the deleted bot.
- Files it produced stay in the attachment store while an entry refers to them.

## Teammate messages

`message_bot` appends a handoff card to the sender's conversation and creates a `bot` wake for the recipient.

- **Urgent** messages wake the recipient now.
- **Non-urgent** messages are held in the database and delivered at the top of the recipient's next envelope, whenever that is. They are consumed in the transaction that writes that dispatch.
- The sender gets an acknowledgement, never a reply. A reply is a separate `message_bot` call from the other side and arrives as a new wake.

The prompt tells bots not to acknowledge acknowledgements. The hop budget enforces it.

## Routines

A routine is a row with an instruction and a trigger. The server's scheduler owns it; the engine's scheduled tasks are not used ([decision 0005](../decisions/0005-j3-bots-owns-wakes.md)).

**Triggers.**

- **Schedule triggers** are five-field cron expressions read as wall-clock time in the time zone saved with the trigger. A bot's `set_routine` saves the operator's zone; a schedule kept in another zone keeps it. A time the clocks repeat when they go back runs once, at its first occurrence. A time the clocks skip runs once that day, as much later as the clocks moved: 02:30 on the night the clocks skip 02:00 to 03:00 runs at 03:30. Two times that land on one instant run once. A schedule is refused with `Invalid("schedule")` when it does not parse, has a seconds field, names no date that exists (`0 0 31 2 *`), or runs twice within five minutes anywhere in the next eight days, and with `Invalid("time-zone")` when it names a zone the server does not know.
- **One-time triggers** run once at a set instant, in UTC, and then pause the routine. They are how "remind me tomorrow at nine" is kept. An enabled routine's one-time trigger must lie ahead when it is saved.
- **Webhook triggers** are an HTTP endpoint on the J3 Bots server; see [Webhooks](#webhooks). The request body reaches the bot as data inside a nonce-tagged block.

**The scheduler.** Each routine stores its next run. The scheduler wakes at the earliest of them, at least once a minute, and when a command changes a routine. For each routine that came due it records the run and the next run in one transaction, so a run is never recorded twice, also across a restart. Each routine is read again in that transaction, so an edit committed meanwhile wins. A routine whose run cannot be recorded is logged and tried again 30 seconds later, unless it was edited meanwhile; the other routines carry on. A schedule that no longer has a next run, such as one in a zone the server no longer knows, runs that once and pauses its routine, with a warning in the log. A routine whose stored trigger the server cannot read, such as one written by another version, runs nothing and is paused, with one warning. Anything else that goes wrong in the scheduler is logged, and it looks again 30 seconds later.

- Runs missed while the server was down are not replayed: a routine that missed at least one runs once on return, then on its schedule from then on.
- A run that comes due while the previous run of the same routine is still going is recorded as `skipped` and does not count as a run.
- `routine.run` runs a routine on demand, paused or not, without resuming it or moving its next run. A retried command is the same run.

**Running.** A run records a `routine` wake for the routine's bot through the wake pipeline, and the run keeps that wake. The main session's dispatcher never takes a routine wake: it waits for a side session of its own ([Sessions](#sessions)). The side-session runner, which opens that session, dispatches the run's envelope, records the catch-up note and settles the run, arrives with routines part 2. Until then a run stays `running`: later runs come due as `skipped`, and a Stop of the bot or deleting the routine cancels its wake and ends it.

**Run history.** Each run has its start, its end and a status:

| Status | Meaning |
| --- | --- |
| `running` | Its wake has not ended |
| `delivered` | Its wake finished and the bot said something with `say` |
| `silent` | Its wake finished without a message from the bot |
| `failed` | Its wake failed, was cancelled, or is gone |
| `skipped` | It came due while the previous run was still going |

A run settles from its wake, when the scheduler next looks or the routine next runs. A routine keeps its 100 newest settled runs and the run going, counted again as each run settles; its run count counts the runs that started.

### Webhooks

A webhook routine's address is `/hooks/<routine id>/<secret>` on the server's HTTP listener, given to the operator as the routine's `webhookUrl`, built when it is given: a repeated create or update names the listener as bound now. The secret is 32 random bytes, base64url-encoded, drawn when the routine is created. The `webhookUrl` names the first address `j3-bots pair` would offer, at the port the listener bound (the one the system chose, when the port set is `0`): with TLS, the first DNS name on the certificate; with `lan`, the first private address of a real interface (not loopback, a container or a virtual network), read when the URL is built; otherwise the address set. With none, it says what `pair` says: with TLS, `<a name the server's certificate covers>` in place of the host; with `lan`, `127.0.0.1`.

- **Authentication.** The secret in the path is the credential, so the server keeps it out of its logs: the request log records any path under `/hooks/` as `/hooks/…`, with the method and the status and nothing else, whether or not a webhook answers it, and no trace span is made of such a request. A call that fails answers `500`, and what went wrong is logged on its own line, without the request. The server compares SHA-256 digests of the given and the stored secret in constant time, also when there is no such routine, and answers a wrong secret, an unknown routine and a routine with another trigger alike: `404`. An HMAC signature over the body is not checked: the routine contract has no field to require one, and a signature that is optional adds nothing.
- **The body** is read up to 64 KiB (`413` past that) and must be UTF-8 text (`400` otherwise). It is stored with a `running` run as its trigger data. A `skipped` run keeps its `Idempotency-Key` but not the body.
- **Replay.** A request with an `Idempotency-Key` header (at most 200 characters) is recorded once: the same key again answers the run it recorded, with `200`, for as long as that run is kept in the history. Without the header, every request is a new call.
- **Rate.** A webhook call is refused while the routine has recorded ten runs in the last minute, skipped ones included: it answers `429` with `Retry-After`, the time until fewer than ten remain, and records nothing. A run the operator asks for is not limited, so it can take the count past ten.
- A paused routine answers `409` and records nothing.
- An accepted call answers `202` with the run's id and status, `running` or `skipped`.

## Budgets

Three limits keep bots from spending the operator's allowance on each other. All three have conservative defaults and are part of the operator's settings (`settings.get`, `settings.update`), with the time zone and the notification preferences.

| Limit | Default | Applies to |
| --- | --- | --- |
| Hops | 4 | Consecutive bot-caused wakes in one chain since the operator last spoke |
| Fan-out | 1 | Bots a single bot message may wake, unless the operator asked for more |
| Concurrent turns | 2 | Turns running at once across all bots |

The concurrent-turns budget counts one fact, read again before each first send: a session with work the engine may have, a turn its events show or a dispatch sent at least once and not settled. A dispatch never sent holds no slot, also while its files wait to be staged again. Every start, a staging retry included, needs a free slot or one its session already holds, checked again when its first send is claimed.

When a limit stops something, the place where it stopped says so in one quiet line. Nothing is dropped silently.

## Notifications

The server sends a notification when an entry is added to a conversation or room and no connected client currently has it in view, and when a bot starts waiting on the operator.

- **Web and desktop**: over the open connection, shown by the client.
- **Mobile**: a push through the platform's service. The payload carries the bot's name and, if the operator allows it, the first line of the message. See [open question 4](../open-questions.md).

Routines that end silently and non-urgent teammate messages never notify.

## Client API

Clients use one WebSocket to the server, with typed requests and subscriptions defined in `packages/contracts`, plus a few HTTP routes for what a socket does badly (pairing, file transfer).

Each of the server's listeners (this one, the tool endpoint and the admin socket) binds only once its routes are built, so a request that arrives the moment a port opens is answered, never dropped. Node accepts connections as soon as a server binds and answers a request only once a handler is attached; bound first, a listener would leave a request that arrived in between waiting forever. Between the bind and the attach, Effect resumes from Node's listen callback synchronously, with nothing that waits in between, so no request can arrive unhandled. A step a listener takes after binding that does wait, such as setting the admin socket's mode, runs once its handler is attached.

**The socket is authenticated once, at the upgrade.** A client sends its device token as an `Authorization: Bearer` header, or, where it cannot set a header on an upgrade (a browser), a ticket it got from `POST /api/socket-ticket` with that bearer. A ticket works once and only within a minute. An upgrade without a valid credential is answered 401 and never becomes a socket. A browser cannot read that status, so a failed upgrade sends it back to the ticket route, whose own 401 is the signal to pair again ([Clients](clients.md#connecting)). The socket belongs to that device for its whole life, and every request on it acts as that device. Revoking the device closes its sockets at once. This is how T3 Code's own socket works (**Read** at `db51b67`, `apps/server/src/ws.ts`).

**A failure stays with its request.** Each socket runs its own RPC server. A handler that fails unexpectedly fails its own request with a generic "Internal server error", and the cause is logged on the server; the socket and its other subscriptions carry on.

**Subscriptions** send the current state and then changes, as whole entities:

- The roster (every bot and room, with its state, a preview of its last entry and whether it is unread) and the engine status are small, so they always start with a snapshot and do not resume.
- A conversation or room resumes. Its snapshot holds the latest entries and the change sequence it was read at, its watermark; every later change follows, and nothing at or before the watermark does. A client that reconnects passes the last sequence it applied and gets the changes since, or, when the server no longer has them or there are too many, a fresh snapshot that replaces what the client holds.
- Routines resume the same way.
- The steps of a work fold stream while the operator has the fold open: every step so far, then each step as it changes, until the fold's turn ends.

Unread has one source of truth: the conversation's read mark against its newest entry. A bot that finished its turn is idle, and its reply is unread until the operator reads it; there is no separate "done" state. A client moves the mark forward only through the newest entry the operator can see: on screen, in a window that is showing, with no dialog over the conversation.

**Commands** carry a client-generated id and are idempotent: send a message, answer a card, stop a bot, create or change a bot, a room or a routine, edit memory, change settings. `secret.provide` is the exception: it keeps no receipt, because a receipt would hold the value; a retry that finds the card closed fails with `Conflict("card-closed")` instead.

The server pages history by `order`; a client asks for older entries as the operator scrolls.

## Configuration

The server reads its settings from `<J3_HOME>/config.json`. On first start, once the configuration and the home pass their checks, it writes that file whole, with every setting at its default; it never replaces one that exists. A setting in the environment overrides the file, and a default applies only when neither has the setting. A setting that is present but invalid stops the start, so a typo never becomes the default. The file refuses unknown keys for the same reason. A port another program holds stops the start with a message that names the port and its setting. Start also refuses two listeners on one port, port `0` for the tool endpoint or the engine (both are dialed at the number configured), and a certificate and key that Node cannot load as a pair. `j3-bots doctor` runs the same checks without starting anything. A service runs with the file alone: it does not get the variables of the shell that installed it.

| File | Variable | Default | |
| --- | --- | --- | --- |
| | `J3_HOME` | `~/.j3-bots` | Created readable by the operator only. The server does not start while it is owned by another user or open to a group or to other users. Refused inside a Git checkout, including a folder that does not exist yet whose parent is one |
| `host` | `J3_HOST` | `lan` | `lan` listens on every IPv4 interface and serves private addresses only, with or without TLS. Start refuses it while any of the machine's addresses is public, and each connection to an address that is not loopback or private is closed unread. Any other value is one address, which must exist when the server starts. Without TLS it must be an IP literal in loopback or a private range: the private IPv4 ranges, IPv4 link-local, carrier-grade NAT (100.64.0.0/10, where Tailscale puts its addresses), and IPv6 unique-local and link-local. `0.0.0.0`, `::` and host names, `localhost` included, are refused |
| `port` | `J3_PORT` | `3737` | `0` lets the system choose; `j3-bots pair` prints the port the server got |
| `tls` | `J3_TLS_CERT`, `J3_TLS_KEY` | none | A certificate and key (`{ "cert", "key" }` in the file), which serve HTTPS. With them, `host` may be any address, public ones included; `lan` still serves private addresses only. The two variables are set together and replace the file's pair |
| `enginePort` | `J3_ENGINE_PORT` | `3738` | The engine's loopback port |
| | `J3_ENGINE_BINARY` | the pinned release | For testing an engine build. Not in the file, and a service never uses it |
| | `J3_SCRIPTED_AGENT` | none | The engine's scripted ACP agent, offered as a provider named `scripted` and listed first, so new bots run on it: an end-to-end run with no model. For development. Not in the file, and a service never uses it |
| `toolPort` | `J3_TOOL_PORT` | `3739` | The bot tool endpoint's loopback port, which the `j3` bridges call |
| `webClient` | `J3_WEB_CLIENT` | this checkout's `apps/web/dist` | The built web client, served on the API's origin. A folder named here must hold an `index.html`. Everything in it is public, so it may not overlap private state in either direction, symbolic links resolved: it may not hold the home, the TLS certificate or key, or anything the home keeps private, nor lie inside any of them. The one place inside the home it may be is `<J3_HOME>/web`. The default is served once it is built |

Relative paths in the file resolve against `J3_HOME`.

**The web client** is served by the same listener as the API, so the two share an origin. The server looks for a built client when it starts and registers its routes then; a client built later is served after a restart. Paths under `/api/` and the server's own routes are never answered with the client. A request for a path without a file extension that accepts HTML, and that names no file, gets `index.html`, for the client's own routing; anything else that names no file is a 404. Files under `/assets/` carry content hashes in their names and are cached for a year as immutable; everything else is revalidated on each use. Each request is resolved once: the request target is parsed as a URL (which drops the query and the fragment and resolves dot segments), its path is decoded and resolved inside the folder, and the file's real path, symbolic links resolved, is checked to lie inside the folder and is the file sent. No second parser reads the target. Paths that leave the folder are refused, and so is a file whose real path lies outside it, a folder's `index.html` and the app's `index.html` included. A folder named without its trailing slash is redirected to it.

**One server per home.** Right after it loads its configuration, before it opens the database or starts the engine, the server checks that the home is private and takes an exclusive lock on `<J3_HOME>/server.lock`, which it holds until it exits. A second server for the same home stops there. The lock is SQLite's, which the kernel releases when the process ends, so a crashed server never leaves the home held.

**The admin socket**, `<J3_HOME>/admin.sock`, is how `j3-bots` commands on the host reach the running server: its status and process id, where it listens (scheme, address, port and, with TLS, the certificate's concrete names), and a pairing code. It is a Unix socket that only the operator's user can open (the home is private, the socket 0600), so it needs no token. A server holding the lock removes a socket left by one that stopped without closing, once it has seen that the file is a socket and that nothing listens on it. Anything else at that path stops the start.

## Failure handling

| Failure | What the server does |
| --- | --- |
| The engine process exits | Restarts it and reconnects. Each time the engine becomes ready, the server opens each session's stream again from its stored cursor, by replay or replacement, then releases the workers and nudges each, and checks the secret submissions left undecided alongside them. While the engine is not ready the workers hold. The order within a session comes from its own state, not from the sequence: nothing is planned into a session before its events are known, and nothing new is sent into one with an unsettled Stop or a dispatch whose answer is not known, so the Stop runner sends the rounds never acknowledged, and the recovery settles those dispatches with their key, before anything new reaches that session; each worker's deadlines are stored, so none starts afresh. The engine cancels the turn that was running and its open requests expire; the turn's dispatch is recorded as interrupted and handled like a failed one (the engine's restart continuation is turned off). The server resumes each reported hold once, except in a session with an unsettled Stop |
| The engine socket drops | Reconnects with backoff, then runs the same sequence as after an engine restart |
| The engine has no such session | Records the session lost, shows it once, and plans nothing into it ([Sessions](#sessions)) |
| An event cannot be applied | Logs it with its cause, shows an `observation-failed` notice once, sends nothing into the session meanwhile, and reads it again each time the stream reopens with backoff; one item's failure never stops the loop that met it |
| A worker fails unexpectedly | Logs it; the item that failed gets a later deadline and the pass goes on, and a worker whose pass failed waits thirty seconds before the next ([The workers](#the-workers)) |
| A turn fails | Records the engine's error class on the dispatch and shows it; retries only routine wakes, with a cap |
| A provider hits its limit | Marks the provider's bots blocked with the reset time; holds automated wakes until then. The turn that hit it stays open as a pending continuation, and a dispatch already waiting in the engine starts at the reset |
| The server process exits | On start, runs the sequence above, which also sends a dispatch written and never sent, whether or not its bot has a wake pending, and recovers every dispatch that was sent but has no recorded answer. No turn starts twice, because a dispatch keeps its key and its envelope |
| A session cannot be resumed | The engine runs the turn on its own summary of the old conversation; the server then rotates the session once it is quiet, and the new one starts from memory and the digest ([Sessions](#sessions)) |
