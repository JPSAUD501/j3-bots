# Engine

J3 Bots runs a stock T3 Code server and drives it as a headless client. This document covers how the engine is installed, isolated, connected to, configured and upgraded, and which of its behaviors J3 Bots has to design around.

Labels **Verified**, **Read** and **Assumed** are defined in the [documentation index](../README.md). Sources for every claim are in [research/t3-code.md](../research/t3-code.md).

## Isolation

The engine is a separate T3 Code instance that belongs to J3 Bots. It shares nothing with a T3 Code the operator may already use for coding.

- **Own data directory.** The engine runs with `--base-dir <J3_HOME>/engine`. A fresh directory gets its own database, settings, secrets and environment identity. **Verified**: an instance started this way came up with a different environment id and no projects or threads from the main instance.
- **Loopback only.** `--host 127.0.0.1` and an explicit `--port`. Without an explicit port, a second instance picks any free one. **Read**.
- **Supervised by J3 Bots.** The J3 Bots server starts the engine as a child process (`t3 serve --no-browser`) and restarts it if it exits. T3 Code's own service installer allows one service per user and refuses a second data directory, so J3 Bots cannot use it. **Read**. After each start the adapter records the engine's pid and environment id in `<engine dir>/j3/engine-process.json`. A port that already answers at a start, with this data directory's environment id, holds an engine an earlier J3 Bots process lost: the adapter stops it (SIGTERM, then SIGKILL after ten seconds) only if the recorded pid still runs `serve` on this data directory. Anything else on the port is never touched, whether it answers as an engine or not: a port that does not answer as this home's engine, but that a trial listen on loopback finds in use, makes the engine `unavailable` (`port-in-use`), and it is not started until the port is free. A failed install is `unavailable` (`install-failed`) and retried, from once a minute up to every half hour; it never stops the server. On Windows the adapter installs the `win32-x64` archive, a zip it unpacks itself, without the system's `tar`, refusing an entry whose name leads out of the folder or that Windows would read as another name, a link, and a file whose bytes do not match their CRC-32; the engine is `t3.exe`.

  **Supervision on Windows.** T3 Code stops cleanly only on SIGTERM or SIGINT, which `NodeRuntime.runMain` listens for (**Read** at `59651c1`, `apps/server/src/binCli.ts:143`), and Windows sends neither to another process: Node's `kill` there ends a process at once. Nor does the engine stop when its parent goes away there (`launcherWatch.ts:24` waits forever on `win32`). And Windows has no process groups: a process's children keep running when it ends, and a tree kill (`taskkill /T`) finds them only through a parent that still runs, so a harness running when the engine crashed, or one whose own parent had ended, would outlive the engine, its restart and the server's stop, and hold files an update replaces. So on Windows the adapter starts the engine through a small launcher (`inJob` in `packages/processes`) that puts itself in a new job object marked kill-on-close, which allows no breakaway, then starts the engine and waits for it. Every process the engine starts, and every process those start, is a member of the job whatever becomes of its parent; when the launcher ends, after the engine or by the adapter's stop, it closes the job's only handle and Windows ends every process left in the job. The launcher is a C# program that the first start on a computer compiles with the compiler of .NET Framework 4, which every supported Windows ships (`csc.exe`), into `J3 Bots\launcher` in the user's local application data, under a name that is a hash of its source; every later start runs that file, and a release that changes the source compiles a new one. Compiling it on every start, as it once did through Windows PowerShell's `Add-Type`, took 0.4 s on an idle Windows 11 VM and 27 to 29 s on a busy GitHub runner (**Verified**), where it was almost all of a start. The file is the user's to change, as everything else the server runs is. So the adapter never looks for the engine's processes by command line or executable path, which for a harness name neither the data directory nor the J3 home: membership in the job is what ties a process to this J3 Bots instance. At the server's stop, whether by `/shutdown` or the end of its standard input, and at a restart, the adapter ends the launcher's tree (`taskkill /T /F`), and the stop returns only once the engine itself is gone too, which can be after its launcher, so what follows (a restart, the desktop's snapshot of the data at an update) finds the engine's files free; an engine that ended by itself has taken everything it started with it before the restart. Either way every bot's turn ends at once, as with SIGKILL on Linux: a turn in progress is reported `interrupted` when the engine is back. An engine an earlier J3 Bots process lost, which a killed server leaves running, is stopped at the next start by its recorded pid, checked first by the command line Windows gives for it (Windows PowerShell's `Get-CimInstance Win32_Process`) and by its start time. One script checks both and ends the tree while it holds a handle to the process, and Windows gives no new process the pid of one a handle is still open on, so the tree it ends is the one it checked, never a process that took the pid since. Its launcher then ends, and its job with it. **Verified** on Windows 11 and in CI on Windows Server 2025: with a stand-in engine whose harness keeps running and whose second harness has lost its parent, both end once only the engine is killed, and once only the launcher is; with the job turned off, both outlive it. With the real engine, the Windows smoke (`apps/server/smoke/windows.test.ts`) downloads, unpacks and starts the pinned `win32-x64` zip, runs a scripted turn whose harness starts a process of its own that keeps running, kills only the engine and checks that process is gone before the restart, runs a turn on the restarted engine, and stops the server, once by `/shutdown` and once by the end of its standard input, after which no process the server started is left. A process with the recorded pid but another start time, as one that took the pid would have, is left running, and so is what it started.
- **Provider processes are not the engine's children.** On Linux the engine launches each provider CLI through `systemd-run --user --scope`, so a process tree under the engine's pid misses them. Elsewhere, Windows included, it starts them as its own children, with no scope (**Read** at `59651c1`, `apps/server/src/process/agentScope.ts:103`), so they are in the engine's process tree, and on Windows in its job too, which ends a harness whose parent has ended (above). Stopping the engine stops them all. Memory accounting and leak checks go by the engine's systemd slice, not by parent pid. **Verified**.
- **Own environment.** The engine passes its environment on to every harness it starts. So the adapter starts it with an allowlist of the server's environment and nothing else: `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG` and every `LC_*`, `TZ`, `TMPDIR`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, the proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, upper and lower case), and the certificate variables (`NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`). Windows names these needs differently, and a program there cannot start without some of its own, so there the list is another, matched without case: `PATH`, `PATHEXT`, `SystemRoot`, `SystemDrive`, `windir`, `ComSpec`, `OS`, `PROCESSOR_ARCHITECTURE`, `NUMBER_OF_PROCESSORS`, the profile and its data folders (`USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`), `ProgramData`, the program folders (`ProgramFiles`, `CommonProgramFiles` and their `(x86)` and `W6432` forms), `PUBLIC`, `ALLUSERSPROFILE`, `TEMP`, `TMP`, `USERNAME`, `USERDOMAIN`, `LOGONSERVER`, `COMPUTERNAME`, `TZ`, and the same proxy and certificate variables. Node starts no Windows program without eleven of these: libuv copies the server's `HOMEDRIVE`, `HOMEPATH`, `LOGONSERVER`, `PATH`, `SYSTEMDRIVE`, `SYSTEMROOT`, `TEMP`, `USERDOMAIN`, `USERNAME`, `USERPROFILE` and `WINDIR` into any environment it is given that lacks them (**Read**, libuv `src/win/process.c`, `required_vars`; **Verified** with Node 26.13.1 on Windows 11: a child given only `SystemRoot` and `PATH` got all eleven). So the list holds them all, and is exactly what the engine gets. `LOGONSERVER` names the server that signed the user in, the machine itself or a domain controller, and is set only where a sign-in set it; it holds no credential. A variable that configures T3 Code or a harness, or holds a credential of the operator's, never reaches a bot: a bot's harness is configured only by what J3 Bots provisions. **Verified** before the allowlist, with the denylist it replaced: a server started from a shell that carried `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN` had its Claude Code instance report signed in with no connection; started without them, the same instance reported signed out. `T3CODE_HOME` would not have moved the engine's data, since `--base-dir` takes precedence (**Read** at `db51b67`, `cli/config.ts`). To that the adapter adds `CLAUDE_CONFIG_DIR` and `CODEX_HOME` of its own, two empty folders in `<engine dir>/j3/harness-defaults/`: each J3 Bots instance has its own folder, which the engine sets for it ([Provisioning](#provisioning)), and any other run of a harness gets these instead of the operator's `~/.claude` and `~/.codex`. The engine makes one such run: it checks the installed Codex with `codex --version` and `codex app-server --help` outside any instance (**Read** at `59651c1`, `CodexInstallation.ts`; **Verified** on `0.1.11`). A harness a bot runs in its own shell gets them too. This is a boundary against configuration leaking in, not against a bot: a harness runs as the server's user, so the files that user can read, the operator's own sign-ins and keys among them, are inside the operator's trust boundary ([Security](security.md)).
- **No harness runs on the operator's own folders.** The engine adds an instance of each of its built-in providers that its settings do not name, under the provider's own name, and the Claude Code and Codex ones start enabled, with no home of their own (**Read** at `59651c1`, `deriveProviderInstanceConfigMap` in `ProviderInstanceRegistryHydration.ts`, `isUnconfiguredDefaultInstanceEnabled` in `contracts/src/settings.ts`). The engine checks every enabled instance when it starts, so on any machine with Claude Code or Codex installed, those two ran on the operator's `~/.claude`, `~/.claude.json` and `~/.codex`, next to J3 Bots' own instances, and created or wrote them ([#86](https://github.com/JPSAUD501/j3-bots/issues/86)). So the adapter writes every built-in default instance into the engine's settings turned off (`codex`, `claudeAgent`, `cursor`, `grok`, `fx`, `opencode`, `antigravity`, `kiro`, `pi`, `muse`: every built-in provider at `59651c1` but the ACP registry, which has none). The engine also looks up each harness's latest release, which the operator's update needs ([Harness versions and updates](#the-adapters-interface)), for a harness whose version its check read (**Read** at `59651c1`, `enrichProviderSnapshotWithVersionAdvisory`, `resolveLatestProviderVersion` and `withConfiguredNpmVersionLookup` in `provider-core/src/server/maintenanceResolver.ts`; `ClaudeMaintenance.ts`; `CodexDriver.ts`). A native install asks its maker's release channel over HTTPS (`downloads.claude.ai`, `releases.openai.com`). One a package manager installed (pnpm, Bun, mise, Vite+, Homebrew, Chocolatey) asks that package manager. Whenever `npm` is on the engine's `PATH`, the engine also runs `npm view --global` for the harness's package, after a native channel that gave no answer and in place of the others, whatever installed the harness, with the server's own environment: npm then writes its cache and logs in the server user's `~/.npm`, a cost J3 Bots accepts for the update. Each lookup is bounded, 4 seconds over HTTPS and 10 for a command, and its answer cached. Until 0.8.0 the adapter turned that lookup off (`enableProviderUpdateChecks`). **Verified** on `0.1.11` with Claude Code 2.1.330 and Codex 0.171.0, through a release run on a fresh `HOME` for 75 seconds with no provider connected, with the lookup still turned off after the change: before, that `HOME` gained `.claude/`, `.claude.json`, `.codex/` (106 MB, Codex's databases and logs) and `.npm/` (21 MB), and the harness runs the engine made included `claude` and `codex app-server` with neither `CLAUDE_CONFIG_DIR` nor `CODEX_HOME`; after, every harness run had J3 Bots' folder, and none of those appeared. The release archive's smoke, which CI runs on every change (`apps/server/smoke/release.test.ts`), checks it: its stand-ins for `claude` and `codex` record what each run was given and write where the real ones write, and the user's home must stay empty. It does not cover the lookup: its stand-ins print no version, so the engine looks nothing up. A new built-in provider in a later engine is not in the adapter's list; [Upgrading the engine](#upgrading-the-engine) says to look.
- **Not inside a Git checkout.** `J3_HOME` must not sit under a repository: T3 Code treats any folder inside one as part of it, which would turn on checkpointing for bot workspaces. **Read**. It asks git itself (`rev-parse --show-toplevel`, **Read** at `59651c1`, `GitVcsDriverCore.ts`), so the server decides it by git's own rule: a `.git` folder holding `HEAD`, `objects` and `refs`, or a `.git` file that starts with `gitdir:`, as a linked worktree or a submodule has. Git also checks what such a file points at and what `HEAD` holds; the server does not, so where it differs from git it refuses a home git would not call a checkout, never the other way round. An empty `.git` folder, which Codex's sandbox can leave in `/tmp`, is not a checkout (**Verified** with Codex on `0.1.11`).

What is still shared with the machine:

- **Provider homes.** By default Claude Code uses `~/.claude` and Codex uses `~/.codex`. J3 Bots gives each engine provider instance its own home directory, `<J3_HOME>/providers/claude-code` and `<J3_HOME>/providers/codex`, so bots do not inherit the operator's coding instructions, hooks, MCP servers or sign-in, nor the skills in the operator's provider homes. See [Reaching the models](#reaching-the-models).
- **The home folder, which Codex does not get.** Codex lists the skills in `$HOME/.agents/skills` as user skills, beside those in its `CODEX_HOME`, and reads plugin marketplaces from `$HOME` too (**Read** in Codex 0.171.0, `ext/skills/src/host_roots.rs`, `core-plugins/src/marketplace.rs`). So Codex runs with a home folder of J3 Bots' own, empty, and the commands it runs get the server's `HOME` back ([decision 0019](../decisions/0019-codex-runs-with-a-home-of-its-own.md), [Provisioning](#provisioning)). **Verified** with Codex 0.171.0, through its app server's `skills/list` with a fresh `CODEX_HOME`: given the operator's `HOME`, it listed a skill in their `~/.agents/skills` with scope `user` ([#48](https://github.com/JPSAUD501/j3-bots/issues/48)); given the folder of its own, it did not. Claude Code needs none of this: with `CLAUDE_CONFIG_DIR` set, it lists neither `~/.claude/skills` nor `~/.agents/skills`. **Verified** with Claude Code 2.1.330, by the `skills` of its `init` message, with the operator's `HOME` holding a skill in each: neither was listed; without `CLAUDE_CONFIG_DIR`, the one in `~/.claude/skills` was. The rest of a bot's environment is the operator's on both harnesses: its commands run in a login shell with the operator's `HOME`, so they read the operator's profile, and `git` and `gh` read their configuration from the operator's home. For Codex that takes its shell snapshot turned off, since the snapshot reads the profile once with Codex's own `HOME` ([Provisioning](#provisioning)). On Windows, Codex finds its home folder from the system and reads no variable for it, so a Codex bot there is still offered the operator's `~/.agents/skills`, and Codex has no setting that turns that location off (**Read**, Codex 0.171.0 `ext/skills/src/host_roots.rs`, `dirs-sys` 0.5.0; **Verified** on Windows 11 with Codex 0.171.0, through `skills/list`, with `HOME`, `USERPROFILE`, `HOMEDRIVE` and `HOMEPATH` all moved to an empty folder; [Security: known gaps](security.md#known-gaps), [#168](https://github.com/JPSAUD501/j3-bots/issues/168)).
- **`gh`.** The engine's GitHub integration asks `gh` for its `http_unix_socket` setting once at start, in the operator's home, and `gh` keeps a device id in `~/.local/state/gh` whenever it runs (**Read** at `59651c1`, `GitHubHttpClient.ts`; **Verified** on `0.1.11`). J3 Bots leaves it so: `gh` is the operator's in a bot's shell too.
- **Managed policy.** `/etc/t3code/policy.json` on Linux applies to every T3 Code instance on the machine, including the engine. **Read**.

## Version pinning

J3 Bots names one exact T3 Code version, in `engine.json` at the repository root: the release version, the commit its tag points at, and the SHA-256 of the standalone server archive for each platform J3 Bots runs on (`linux-x64`, `linux-arm64`, `darwin-arm64`, `win32-x64`). The pin is `0.1.11`, commit `59651c1761f6c63e9b6056839067066968e6a406`. **Verified** on 2026-11-21: the tag `v0.1.11` points at that commit, and the digests in `engine.json` are the ones the release's `SHA256SUMS` lists. **Verified** on 2026-11-22, on T3 Code's GitHub releases: `v0.1.11` is still its newest stable release, the one GitHub shows as the latest, and every release published since is a `0.1.12` nightly, the newest `v0.1.12-nightly.20261122.5085`.

**A release of J3 Bots pins a stable T3 Code release, never a nightly.** T3 Code publishes a nightly from `main` most days, as a GitHub pre-release, and a stable release now and then, as a full release that GitHub shows as the latest (**Verified** on 2026-11-21: 86 of its last 100 releases are nightlies, and `v0.1.11` is the first stable release after `v0.1.10`). It also publishes the odd preview, another pre-release channel its installer accepts (6 of those 100). Pinning only stable releases does three things:

- **The engine is the one T3 Code installs by default.** A nightly is whatever `main` held that day, and T3 Code's own installer follows the stable channel unless told otherwise (**Read** at `59651c1`, `scripts/install.sh`: `T3CODE_CHANNEL` defaults to `stable`, the latest release). So the engine a J3 Bots operator runs is the version T3 Code's own users get.
- **Upgrades come at T3 Code's release pace, not daily.** Each pin bump costs the conformance suite, the cases checked by hand and the upgrade check below. Following stable releases keeps that cost to the releases that matter.
- **The engine carries nothing its nightlies did not.** So far a stable tag has pointed at a commit a nightly already shipped: `v0.1.11` is the commit of `v0.1.11-nightly.20261120.4979`, published an hour before it, and `v0.1.9` and `v0.1.10` each match a nightly's commit too (**Verified** for those three; T3 Code states no such rule). So a stable pin has not been newer or less tried than the nightlies before it.

Between J3 Bots releases, `main` may pin a nightly when J3 Bots needs an engine change that no stable release has yet; a J3 Bots release then waits for a stable release that contains it.

The pin must also be at or after the oldest release on which the engine gives a stdio MCP server that Codex starts the `T3CODE_THREAD_ID` variable, which the [bot tool bridge](server.md#bot-tools) needs to identify a Codex bot. Upstream pull request 39414 added it in nightly `4969`. **Verified**: absent on `4941`, present on `4969`, and on `0.1.11` a Codex bot's `j3` calls were matched to its turn.

`0.1.11` is the previous pin, nightly `4969` at `db51b67`, plus nine commits (**Verified**, upstream history). None of them changes `packages/contracts`, so the vendored source is the same, nor the Effect versions. One changes behavior J3 Bots meets: on Claude Code, the completion of an async task the engine delegated, or a delegated task's notice, that arrives while any run of the session has a running provider turn is now steered into that run, whichever turn delegated it, as Codex already did at `db51b67` (upstream pull request 39528, `activeSteeringInterruptsTools` set to `false` in `ClaudeAdapterV2.ts`; **Read** at `59651c1`, `Orchestrator.ts:7631-7673` and `ProviderContinuationService.ts`). Only when no run is running does it start a turn that names the turn that delegated it ([Behaviors](#behaviors-j3-bots-designs-around)). J3 Bots does not see such a steer yet, so a room turn's delegated work can report into a private turn, or a private task's into a room turn ([#98](https://github.com/JPSAUD501/j3-bots/issues/98)). The others change the Antigravity provider, GitLab, the engine's web client, Claude history import, and how a delegated task's launch survives its caller going away.

The source claims labelled **Read** were made at commit `9bb92a4`, unless the research notes name `db51b67`. `db51b67` is `9bb92a4` plus ten commits, and the pin is `db51b67` plus nine, so every Read claim is at or before the pin. Of the files those claims cite, only `ClaudeAdapterV2.ts` changed since, by the one line above. Each claim still holds only until it is checked at the pin, by the adapter's code or its conformance suite. A release's commit is in its title on GitHub, and it is often older than `main` on the same day: a fact read in source counts for a release only if that commit contains it.

The engine binary is the standalone release archive for the platform, downloaded once, checked against the digest `engine.json` pins for that platform, and stored under `<J3_HOME>/engine/j3/runtime/<version>/`, apart from the engine's own `runtime/` folder, which belongs to its service launcher. An interrupted download resumes from a `.partial` file, which must be a regular file and is never written through a link; it is checked before the download starts. The archive is unpacked into a `.staging` folder the install creates itself, so it never unpacks through a link left at that name ([Server: data](server.md#data)). One install of a version runs at a time: it holds an exclusive lock on `<version>.lock` beside it while it downloads and unpacks, and another, such as `j3-bots engine fetch` during an update while the server downloads its first engine, waits for it and then finds the version installed. A start that finds the version installed removes a `.partial` or `.staging` an interrupted install left beside it; a removal that fails is logged, and the engine runs. An archive with any other digest is deleted and not installed, so a release rebuilt under the same version, or replaced upstream, never runs; a platform the pin has no digest for is unsupported. `j3-bots engine fetch` runs the same install without starting the engine, so a new release's engine can be downloaded while the running server keeps its own.

While it downloads, the engine's status is `starting` with `install`: the bytes in hand, a resumed download counting what its `.partial` held, and the archive's size, from the `Content-Range` total of a resumed download or the `Content-Length` of a whole one (counted from 0 when the release server answers a range with the whole file), or null when the answer says neither or gives a size too large to count exactly. The download reports when it starts, and at most once a second while it runs, never the same count twice in a row, so a client follows it without being sent every chunk. `install` goes as soon as the last byte arrives, so the status is plain `starting` while the archive is checked and unpacked, and until the engine answers. While `j3-bots engine fetch` holds the install lock, the server waiting for it shows plain `starting` too: it reports only a download it runs itself. A failed install is `unavailable` with `install-failed` while it waits to try again, and the next attempt shows `install` again once bytes arrive. The server's log has the download as `Downloading the engine: 42 of 180 MB` when it starts and every ten seconds, and as `Downloaded the engine: 180 MB` when it ends, whether or not its size was known; each attempt logs from its own start. `j3-bots engine fetch` prints the same: in place on a terminal, and as those log lines when its output is not one, as when `j3-bots update` relays it (**Read** in this repository, `Install.ts`; covered by its tests, with a stand-in release server). A megabyte there is a million bytes, in whole ones. **Verified**: the first install took 21 seconds, and the engine answered as ready 3 to 5 seconds after each start. While the engine is not installed and no server answers, `j3-bots doctor` asks GitHub whether the download answers, with a `HEAD` request for the same archive through the same client as the server's download, Node's `fetch` (**Read** in this repository, `server.ts` and `cli/main.ts`). That client does not use `HTTPS_PROXY` or `HTTP_PROXY` unless Node is told to with `NODE_USE_ENV_PROXY=1` (**Assumed**, from Node's documentation), so a machine that reaches GitHub only through a proxy fails both alike.

At startup the adapter reads the engine's public descriptor and refuses to continue if the server version or the orchestration protocol version is not the pinned one. **Verified**: `GET /.well-known/t3/environment` returns `serverVersion` and `orchestrationProtocolVersion` without authentication.

### The engine's contracts

The adapter decodes the protocol with T3 Code's own schemas ([decision 0007](../decisions/0007-client-and-server-stack.md)). Their package, `@t3tools/contracts`, is not published to a registry, so J3 Bots vendors it.

- `packages/engine-t3/vendor/t3-contracts/` holds the package's source at the pinned commit, unmodified, with T3 Code's MIT license. It is a workspace package under its upstream name. Only `packages/engine-t3` may import it: a lint rule refuses an `@t3tools/*` import anywhere else.
- `pnpm vendor:t3-contracts` regenerates it from `engine.json`, and writes the archive digests into `engine.json` from the release's `SHA256SUMS`, so a moved pin shows them in its diff. The script refuses to run if the release tag no longer points at the pinned commit, and leaves out upstream's tests. A weekly CI job re-runs it and fails if the vendored package or the digests differ from what is committed.
- The package depends only on `effect`. J3 Bots' version catalog pins exactly the Effect versions T3 Code pins at the commit (`effect` 4.1.3, `@effect/platform-node` 4.1.2, unchanged from `4941` to `0.1.11`; **Read** in `pnpm-workspace.yaml` at `59651c1`), so the vendored schemas and J3 Bots' code share one copy of Effect. **Verified**: the vendored source typechecks in J3 Bots' build with T3 Code's compiler settings.

## Connecting

The engine exposes two interfaces. J3 Bots uses the one T3 Code's own clients use.

| Interface | What it is | J3 Bots' use |
| --- | --- | --- |
| `/ws` | Effect RPC over WebSocket, JSON frames. Commands, queries and live subscriptions. | Everything |
| `/mcp` | MCP over HTTP with OAuth. Request and response only; no push. | Not used by J3 Bots. Bots use it from inside their sessions, as T3 Code intends. |

The connection sequence:

1. **Mint a token.** `t3 auth session issue --base-dir <engine dir> --scope orchestration:read --scope orchestration:operate --scope preview:operate --scope settings:write --scope providers:manage --ttl 30d --label "J3 Bots" --json`, run with the pinned binary, which prints the token, its session's id and its expiry. This works without a sign-in because the CLI opens the engine's database directly. The token lasts 30 days and does not renew. The adapter keeps it in `<engine dir>/j3/credential.json` with the scopes it asked for, reuses it while it is valid and holds every scope the adapter asks for, and mints a new one before expiry or when it lacks one: a token kept before the bot's browser has no `preview:operate`, which the preview stream needs before it takes a viewer's input (**Read** at `59651c1`, `ServerBrowserStream.ts` L74-77), nor `settings:write`, which each bot's browser switch needs to write its project's override, and one kept before 0.8.0 has no `providers:manage`, which the operator's update of a harness needs. When it mints while the engine is stopped, before a start, it then lists the sessions (`t3 auth session list --base-dir <engine dir> --json`) and revokes each other one labelled `J3 Bots` (`t3 auth session revoke --base-dir <engine dir> <session id>`). The list shows no token, only each session's id and the label it was issued with (**Read** at `59651c1`, `cliAuthFormat.ts` `formatSessionList`). A mint while the engine runs, on renewal or after a refusal, revokes nothing ([Security: the engine's credentials](security.md#the-engines-credentials)). **Verified** (minting), **Read** (lifetime).
2. **Open the socket.** `ws://127.0.0.1:<port>/ws?orchestrationProtocol=2`, authenticated either with an `Authorization: Bearer` header on the upgrade or with a five-minute ticket from `POST /api/auth/websocket-ticket/rpc` passed as `&wsTicket=`. **Verified**, both, from a plain Node process with no T3 Code dependency.
3. **Subscribe.** `orchestration.subscribeShell` streams every thread's status, pending requests and last message. `orchestration.subscribeThread` with `{threadId, afterSequence?}` streams one thread: a `snapshot` item when no `afterSequence` is given, then `event` items. **Verified**.
4. **Keep checking access.** The engine is ready only while it accepts the token: every health check asks `GET /api/auth/session` with it, which answers whether the bearer is authenticated and with which scopes (**Read** at `db51b67`, `AuthSessionState`). A definitive refusal (401, 403, or a missing scope) gets one freshly minted token; if the engine refuses that one too, it is `unavailable` (`credential-refused`) until it grants access again.

A whole turn has been driven this way from outside: create a project and a thread, dispatch, stream, answer an approval, answer a question, interrupt, and resume after a dropped socket and after an engine restart. **Verified** on Claude Code and Codex. The command and event shapes the adapter needs are in [research/t3-code.md](../research/t3-code.md#the-turn-protocol).

Protocol facts the adapter depends on:

- Each WebSocket message is one JSON object: `Request`, `Ack`, `Interrupt`, `Ping` from the client; `Chunk`, `Exit`, `Defect`, `Pong` from the server. **Verified** for all but `Defect`.
- **Every stream chunk must be acknowledged.** A subscription whose chunks are not acked stops after a few chunks and continues once they are. **Verified**; the window of eight is **Read**.
- **Events replace whole entities.** A streaming assistant message arrives as its full text so far. The client upserts by id and never applies deltas. **Verified**.
- **Resume by sequence.** The client remembers the last sequence it applied and resubscribes with `afterSequence`. The stream continues from the next event, with nothing lost, across a dropped socket and across an engine restart. The engine sends a fresh snapshot instead of a replay when that point was pruned, lies beyond the thread's latest sequence, is followed by more than 128 stored events or more than 1 MiB of them, or comes before the thread was created again (**Read** at `db51b67`, `ws.ts` `subscribeThread`, `ThreadStream.ts` `decideThreadResume`). A replay coalesces the live updates of each entity, so it gives each entity's state after the point, not every change it went through (**Read**, `coalesceLiveUpdatedEvents`). Events may overlap; the client drops anything at or below what it has. **Verified**.
- **Sequences belong to the environment, not the thread.** One counter serves every thread and project, so a thread's stream has gaps. A gap is not loss. **Verified**.
- **Commands are idempotent by `commandId`.** A replayed `message.dispatch` returns the first one's sequence and starts no second run, even with a different message id. **Verified**. The engine reserves the command's receipt in the same transaction that commits its events, compares only the id, never the payload, and keeps receipts for good; only its events are pruned, after a day (**Read** at `db51b67`, `EventSink.ts`, `CommandReceiptStore.ts`, `ProjectionMaintenance.ts`). A command it refused while planning leaves a rejected receipt, whatever the cause, a projection read that failed included (**Read** at `59651c1`, `dispatchWithReceiptEffect`), and a replay of that id fails as previously rejected (`OrchestratorCommandPreviouslyRejectedError`), also once the cause has passed: an archive refused while a delegated task ran stayed refused under its id for fifteen seconds, where a fresh id passed a second later, and a `thread.create` refused because its thread id was taken was refused again (**Verified** on `0.1.11`, in the conformance suite). So a key the engine refused is never sent again; a command that may pass later goes again under a fresh key. A replay of an accepted id answers `{sequence}` and applies nothing (**Read**, `Orchestrator.ts`, `replayCommandReceipt`). Two refusals leave no receipt, because they depend on modes that can change: a runtime mode above the ceiling of an administrator's policy (`OrchestratorRuntimeModeAboveCeilingError`) and a thread above its dispatch-mode limit (`OrchestratorThreadAboveModeLimitError`), which a command over `/ws` never meets, since only the engine's agent and MCP callers set that limit (**Read** at `59651c1`, `dispatchWithReceiptEffect`, `DispatchModeLimit.ts`). The ceiling refuses a thread created in a mode above it and a change to such a mode (`refused: "mode"`), and, in a thread already above it, a turn that would run there, a first send (`run.created`) or a new attempt (`run-attempt.created`) alike (`refused: "turn"`); lowering the thread's mode, and commands that start no work, stay open there. The engine reads the policy once, when it starts, from a file only root can write in its default place (`/etc/t3code/policy.json` on Linux; the engine itself checks no ownership), so the same mode is refused until it is lowered or the engine restarts under another policy (**Read** at `59651c1`, `DispatchModeLimit.ts` `runtimeModeCeilingRefusal`, `ManagedPolicy.ts`, `managedPolicyFile.ts`). One refusal comes before the receipt is looked up at all: a staged file the engine cannot claim (`AttachmentClaimError`; **Read**, `ThreadMessageIntake.dispatchCommand`). The adapter derives every command id, and a dispatch's message id, from a key the server stored before the call, so a retry after a crash cannot start a second turn.
- **An error reply does not prove nothing was applied.** Steps that run after the commit can fail and turn an applied command's reply into an error (**Read**, `dispatchWithReceiptEffect`). While the engine starts, commands wait in a queue of its own and can be applied after the client gave up on them (**Read**, `serverRuntimeStartup.ts`, `makeCommandGate`). So the adapter reads a refusal only from positive evidence: the error reply names it. Over `/ws` the reply is an `OrchestrationV2DispatchCommandError` whose cause keeps the engine error's class name and message (**Read**, `ws.ts`, a `Schema.Defect`; **Verified** by the conformance suite, which sees a refused steer come back `DispatchRejected` on the first send and again on recovery). A reply naming a command refused while planning, or a replay of one, is `DispatchRejected` (the server never reuses the key); one naming the ceiling is `PermissionModeRefused`, and the engine keeps nothing for the key. A claim error is J3 Bots' own defect: the server names only files staged and still usable. Any other error gets the same command sent once more, and if that does not settle it either, the dispatch is `EngineIndeterminate`.
- **A subscription can mark where it caught up.** `subscribeThread` with `requestCompletionMarker: true` sends a `synchronized` item after the replay (or the snapshot) and before live events, so everything the engine had recorded for the thread when the subscription opened has arrived. **Read** at `db51b67`, `apps/server/src/ws.ts`. The adapter's `synchronize` is built on it.
- **Only a failed read's cause says the thread is missing.** `getThreadProjection` and `subscribeThread` report a missing thread, a projection read that failed and a replay that failed as the same `OrchestrationV2GetThreadProjectionError` (**Read** at `db51b67`, `ws.ts:2159-2183` and `ws.ts:930-1115`). Its `cause` crosses the wire as a chain of `{name, message, cause}` that keeps each engine error's name (effect 4.1.3's `Schema.Defect`, on both sides). A thread the engine has no record of ends that chain in `ProjectionStoreThreadNotFoundError` (**Read**, `ProjectionStore.ts:3859`, kept as is at `ProjectionStore.ts:8193` and wrapped at `Orchestrator.ts:16900`); a failed read ends it in `ProjectionStoreReadError` or a database error. The same name is raised for the source of a forked thread, and J3 Bots never forks one. So the adapter reports `SessionNotFound` only on that name. Every other failure of a read is `EngineUnavailable`, and a stream that fails that way is opened again once the engine is ready, so a busy database never records a session lost. The one other evidence of a lost session is the engine's own deletion: deleting a thread, from the engine's console for instance, keeps its projection and stamps `deletedAt` on its thread record, in the `thread.deleted` event too (**Read** at `db51b67`, `ThreadDeletion.ts:56-66`), so a read still succeeds. The adapter treats a thread record with `deletedAt`, from a read or a stream, as the thread missing: `SessionNotFound` from a read, a stream that ends with it, and a `synchronize` that fails with it. An archive, J3 Bots' own (`retireSession`) or one from the engine's console, stamps `archivedAt` on the thread record, in the `thread.archived` event too; after that event, the same dispatch cancels only the runs still queued or preparing there and gives a run already starting or running no end, which at most its provider session's detach may bring (**Read** at `59651c1`, `Orchestrator.ts`, the `thread.archive` dispatch). So a stream that sees `archivedAt` ends with `SessionNotFound` once none of the session's runs is queued or preparing, after those cancels, as a deletion's ends after the events before it, and so does every read of the live session (`synchronize`, `configureSession`); a read of the projection itself still succeeds, which is how `retireSession` sees an archive that came first.
- **Revoking the session closes the socket.** The adapter must reconnect and resume at any time. **Read**.

A token with `orchestration:operate` can start a full-access agent. It is equivalent to a shell as the server's user and is handled as such. `settings:write` lets it change the engine's settings while the engine runs (`server.updateSettings`, **Read** at `59651c1`, `RpcAuthorization.ts`, `requiredScopesForServerSettingsPatch`); J3 Bots writes only projects' overrides with it ([The browser](#the-bots-browser)). `providers:manage` lets it update a harness (`server.updateProvider`), and also decide where the engine keeps and sends provider credentials (**Read** at `59651c1`, `AuthProvidersManageScope` in `contracts/src/auth.ts`); J3 Bots uses it only for the update the operator asks for ([Harness versions and updates](#the-adapters-interface)). A stored token without it is refused at the next access check, as one missing any scope is, and replaced by a fresh one.

## The adapter's interface

The rest of J3 Bots sees the engine only through the `Engine` service exported by `packages/engine-t3`. It speaks of sessions, turns and requests; nothing in it names a T3 Code type, and nothing outside the package imports one. The TSDoc in `Engine.ts` and `events.ts` is the precise contract; this section is its outline.

- **Durable keys.** Every call that changes engine state (open a session, dispatch, stop, answer a request) takes a key the server has already stored. The adapter derives the engine's command id from it and, for a dispatch, the message id, and for an opening the thread id. A retry with the same key is the same command. A key the engine refused and kept a rejected receipt for is spent: the call reports the refusal, and the caller sends a fresh key when it tries again. A refusal for the permission mode keeps no receipt, so its key is not spent (`PermissionModeRefused` below). `configureSession` and `retireSession` take no key and send keys of their own on every call.
- **A session's settings.** `openSession` creates the thread with the model and permission mode it is given; a retried opening returns the thread as it was first created, with the settings it had then. `configureSession` sets a session's model and permission mode, and sends the engine only the one that differs from what its thread shows. A change can replace the session's provider session, which on Claude Code a permission mode always does, ending a turn running there (**Read** at `db51b67`, `Orchestrator.ts` L4715-4757, `ClaudeAdapterV2.ts` L577): so it refuses with `SessionBusy`, sending nothing, while it sees a turn preparing, starting or running (**Verified** with the scripted agent on release `4969`, in the conformance suite). The engine refuses a change that would end background work the replaced provider session still runs, which the adapter reports as `BackgroundWorkRunning`, recognized by the refusal's text (**Read** at `db51b67`, `Orchestrator.ts` L4744-4757, `ws.ts`). The server calls it after every opening and after every change of the bot's settings, with what the bot has then, once no turn runs in the session, and a session takes no work until the call succeeded, so it takes work only with the bot's current settings ([Server: sessions](server.md#sessions)).
- **Turn times are the engine's.** `turn-started` carries the time the engine started the run, and `turn-finished` the time it completed, also when the adapter tells of the turn after it ran, from a replay or a replacement. For a run with no completion time recorded, it is the latest time the engine did record: when the run started, or when it was asked for.
- **Engine starts.** `starts` tells which start of the engine is ready: `null` while it is not, and otherwise a number, one more each time the engine becomes ready again, so a restart shows even when no `null` came between. The adapter counts a start when its supervisor finds the engine healthy and taking J3 Bots' credential after it was not; the count begins again with each run of the server. An answer that depends on what the engine read when it started names the start that gave it: `PermissionModeRefused`, since the engine reads its policy then. The adapter reads the count before it sends the command, since nothing the engine reports names a start: the start named is the one the command went to, or, when the engine started again while the command was on its way, an older one, never a newer one. An older start costs one more ask under the start that is ready, as the server clears or sets aside the refusals of older starts ([Server: sessions](server.md#sessions)).
- **Ways to fail, and refusals.** `EngineUnavailable` and `EngineIncompatible` mean the command was not sent. `EngineIndeterminate` means it was sent and no answer settled it: it may have been applied, and it is never read as "not applied". `DispatchRejected` means the engine's reply named a refusal: nothing was applied and the key is spent. `SessionNotFound` and `SessionBusy` are local refusals of a first send, made before anything is sent; `SessionBusy` is also `configureSession`'s, while a turn runs. `BackgroundWorkRunning` means the engine refused a settings change that would end background work. A refused `respond` is `RequestClosed`; a refused `stop` step counts as done when it is moot, and is `StopRejected` otherwise (see Stop below). `OpenRejected` means the engine refused to open a session under the key: nothing was opened, and the key is spent. The engine plans a new thread by checking only that its id is free, which the key's own thread id is unless another client took it, so what it refuses is otherwise a projection read that failed while planning, which passes (**Read** at `59651c1`, `dispatchThreadCreate`). `PermissionModeRefused` means the engine refuses, by the mode limits above, the permission mode `openSession` or `configureSession` asked for, or the one a `dispatch` or `redispatch` would run its turn in, its session's: nothing was applied (a model `configureSession` sent first stays), the engine keeps nothing for the key, and the same mode is refused again until the engine starts again under another policy, so the caller asks again only for other settings or once the engine is ready again. It names the engine start that refused it, which the server binds the refusal to, and the highest mode the policy allows, when the engine reports one below the mode refused: a reply keeps only the error's name and message, so the adapter reads the ceiling from the engine's config, `server.getConfig`, whose `managedPolicy` is the summary the orchestrator takes its ceiling from (**Read** at `59651c1`, `ws.ts` `loadServerConfig`, `Orchestrator.ts` `runtimeModeCeiling`). Under a policy that limits threads to Supervised, an opening in Full access is refused naming Supervised, the same key then opens the session in Supervised, and a change of that session to Full access is refused naming Supervised (**Verified** on `0.1.11`, in the conformance suite's policy case, step 2 of [Upgrading the engine](#upgrading-the-engine)). For a dispatch the adapter reads the session's mode from the engine's projection of its thread after the reply, since the reply does not name it. Under the same policy, a session opened in Full access before the engine started under it has a first send and a recovery of the same key refused naming Full access and Supervised, and once the session is changed to Supervised the same key is accepted (**Verified** on `0.1.11`, in the same policy case). The adapter tells it by the class name the reply keeps, never by its words. `RetireRejected` means the engine refused a retirement's Stop round or its archive, and the session is neither archived nor gone: it refuses an archive while delegated tasks run in the thread, and the Stop before it only queues their end (**Read** at `59651c1`, `dispatchThreadMutation`, `dispatchThreadStop`; **Verified** on `0.1.11`), so the caller retires it again later. Once a call has sent a command, every later failure of that call is `EngineIndeterminate`, except `DispatchRejected`, `StopRejected`, `OpenRejected`, `PermissionModeRefused`, `RetireRejected` and `BackgroundWorkRunning`: an engine that becomes unreachable or incompatible, or refuses the token, after the first send says nothing about what that send did. That covers a dispatch's resend, the second command of `configureSession`, Stop's cancels and `retireSession`'s archive.
- **A first send and a recovery are two calls.** `dispatch` is the first send of a key; sending a key that was sent before through it is a defect. When its answer was lost, the server recovers with `redispatch`: the same key and the same input, with none of `dispatch`'s local checks, since the key may already have started the very turn that makes the session busy. Its success means the engine accepted the key, with no disposition: the engine does not say how a key it already had was applied, and delivery comes from the events. It fails only as `DispatchRejected` or `PermissionModeRefused`, or as unavailable or indeterminate, in which case the server tries again later, with backoff and a bound ([Server: recovery](server.md#3-a-dispatch-is-written-before-the-engine-is-called)). Staged file ids are the one input that may differ between sends: the engine claims files before it looks at the receipt (**Read** at `db51b67`, `ThreadMessageIntake.dispatchCommand`), so an id past its usable time is staged again, and the file staged for a key that was already applied is left unused.
- **Delivery is start or steer.** `start` runs a message as a new turn. `dispatch` refuses it with `SessionBusy`, sending nothing, when the adapter already sees a turn running or waiting in the session, but that check is best effort: a turn the engine starts itself can begin between the check and the engine applying the start, and the engine then queues the start behind it. `steer` adds a message to one named running turn. The adapter never asks for `queue_after_active`; waiting and priority belong to the server ([Server: the wake pipeline](server.md#the-wake-pipeline)).
- **A disposition is acceptance, not delivery.** `dispatch` answers `started`, `queued`, `steered` or `new-turn`, each with the engine turn. A dispatch is delivered when `turn-started` arrives with the cause `dispatch` and its key, or, for `steered`, when its steer settles as taken. `turn-finished` carries the turn's cause too, so a turn that ends without starting (cancelled from the queue, or failed before its provider took it) settles its dispatch by key, also one the server learned of only through `redispatch`, which names no turn. A start the engine queued behind another turn is reported once, before its `turn-started` or `turn-finished`, with `turn-queued`: the engine has it, live, also when it came through `redispatch` or after its reply was lost. The engine creates such a run with `status: "queued"` and no item for its message, where a start it begins at once is `starting` from the outset, and records the message, marked `inputIntent: "queued_turn"`, only as the run leaves the queue; a follow-up it queues for an unread steer reuses the steer's item, marked `queued_turn` at once (**Read** at `db51b67`, `Orchestrator.ts`: the queued run at L8012-8060, the start at L8451-8461, the promotion at L3035-3097, the reused item at L8192-8215). So the adapter reads a queued start from its run's status, and from that item once the run has left the queue, for this event and for the `queued` disposition alike. A start the engine begins at once has no `turn-queued`.
- **A steer settles when its turn ends.** Whether a steer was taken is known only once the run it steered has settled (**Read** at `db51b67`, `requeueUnreadSteers` runs as a reaction to the settled run). So the adapter reports nothing about a steer until that turn's `turn-finished`, and then the engine's own state decides exactly one of: `steer-requeued` when the engine queued it as a follow-up turn caused by the same dispatch; `steer-dropped` when Stop ended the turn first and the engine marked it cancelled (and shows its own notice); otherwise `steered`, taken. `steered` is the engine's claim, not proof that the model read the message: a Codex `turn/steer` is acknowledged when Codex accepts it, with no later confirmation that it was consumed, and Claude Code marks a steer completed on one path where offering it to the CLI failed (**Read**, `CodexAdapterV2.ts`, `ClaudeAdapterV2.ts`). The same rule covers a steer the engine could not apply at once: one sent before the target's provider turn started, which the engine keeps aside as a carrier run and steers in when it starts, or runs as the follow-up if the target ends first; and one to a provider that steers only by interrupting the turn and restarting it with the message, which stays one J3 Bots turn across its attempts and keeps the cause of its first attempt. A carrier the engine cancels as it promotes the steer is not a turn, so its cancellation is never reported.
- **Events resume by replay or by replacement, never both.** A cursor names the engine's position: the engine sequence of the batch that carried the event, the batch's part at that sequence (more than one only when the adapter fetched something between two engine events, see approvals below), the event's place in that batch, and the stream that emitted it; never the time the adapter emitted it. A replay has to start from what the stream had told at the cursor, because the engine replays each entity's state after a sequence, not what changed. So `events(session, after)` replays only from a batch this process still keeps, the last 32 per session: it emits the rest of that batch and every later part the stream kept at the same sequence, which the engine has nothing to replay for, then subscribes after that sequence from the state after the last part. Any other cursor, from an earlier process or an older batch, starts the stream with one `replaced` event carrying a new cursor and everything reconciliation needs: the open turns with their steps, the open requests, every turn that ended with its outcome and final steps, the host speech, the request resolutions and how each steer settled. When the engine answers a resume or a reconnect with a snapshot, the stream emits such a `replaced` as well, never a diff: the gap may hold a turn that started and ended, or a steer that settled, and a diff from a snapshot would lose them. A snapshot has no sequence per entity, so a replacement lists every ended turn and may repeat turns, speech and resolutions the server already applied; the server reconciles by stable ids, and applying one again changes nothing. Live events follow. The server applies each event and stores its cursor in one transaction. A cursor of `null` is only for a session that was never dispatched to.
- **Synchronization.** `synchronize(session, token)` puts a `synchronized` event with the token on each open stream of the session, after every event the engine had when it was called. Each stream catches up on a second subscription that asks for the engine's completion marker, and emits `synchronized` only once the marker has arrived. Without the marker within 30 seconds, or with a stream that cannot keep up, `synchronize` fails with `EngineUnavailable`, and the caller retries. A stream that closes meanwhile owes no marker. Each `synchronized` also says what background work the session has, with no run active, by the turn that started it: the turns whose work is pending, in the order they ran (`turns`), and whether any pending work belongs to no turn (`unattributed`). Whether there is any at all is `isBackgroundWorkPending`; whether any of it is what the engine's stop ends is `stoppable`. The work the adapter counts follows the engine's own rule (**Read** at `db51b67`, `packages/shared/src/orchestrationV2PendingBackgroundWork.ts:261`, `derivePendingBackgroundWork`) over what it mirrors from the stream: with no run active and the latest run settled, live command, dynamic tool and subagent items outside a rolled-back run, in the order the engine reads them, by ordinal (`ProjectionStore.ts:3911`), and provider threads' tasks (`provider-thread.updated`), one entry per task id. The rule then keeps one subagent per child thread, since follow-ups can share a child thread and it counts agents (`orchestrationV2PendingBackgroundWork.ts:318-326`). That never empties the list, so the adapter decides whether the stop fires before it, and reports the turn of every follow-up: each is the work of the turn that sent it, and the session's work says which turns own pending work, not how many agents run. A task with an empty `taskId` is no entry, as in the engine's rule (`orchestrationV2PendingBackgroundWork.ts:261-330`). Which of it the engine's stop ends follows `dispatchThreadStop` (`Orchestrator.ts:14141-14178`): the stop fires when the engine's rule counts work, which reads the live items and the tasks of the thread's active provider thread only, or of every provider thread while it has none; it then interrupts the latest run that is not queued, at that run's provider thread, and reaches another provider thread only at the provider turn of a live item (`dispatchRunInterrupt`, `:13560-13692`). So `stoppable` is the latest run's provider thread's tasks and the live items, while the stop fires. The active provider thread decides only whether it fires. It is the one the engine's projection takes: the latest a `provider-thread.updated` reports for the thread, unless it only reserves a seat for a queued run (**Read**, `ProjectionStore.ts:1142-1150`), so a late report from an old provider thread makes that one active again without moving the stop's target. Within what it reaches, the stop is the session's: it ends all of it, whichever turn started it. Another provider thread's tasks are still pending, and reported, not `stoppable`, while the engine keeps its provider session. A fresh-context start releases the old provider session only when the provider hosts one provider thread per session and the session runs no background work. A fresh start queued behind a turn, or sent by a schedule, leaves a busy session running, and any other start it would begin at once is refused (**Read**, `Orchestrator.ts:1520-1533`, `sessionsReleasedByFreshContext`, applied at `:2765-2808` and `:8325-8345`; the engine's testkit, "Fresh context with an old session's background task"). A provider that hosts several provider threads per session keeps the old one in the same session. Either way, the old provider thread keeps reporting its tasks until they end. Archiving the thread ends them: it detaches every session (`:4713-4736`). The engine's stop does not, as above. So the adapter also counts the tasks of each other provider thread that is one of the thread's own conversations, not a subagent's, while its provider session is bound to the thread and neither stopped nor failed. The engine binds a session to the thread when it is attached and unbinds it when it is detached, as it does for a session it releases, in the same command (`:3285-3296`, `:8701-8712`); an update changes only the session's status, so one for a session not attached, such as a late one after its detach, binds nothing (**Read**, `ProjectionStore.ts:2773-2826`). Those are the stored bindings, through which the engine reads a thread's sessions: the records its commands start from, the snapshots (`readCanonicalProjection`, `:4312-4335`) and recovery (`:5705-5720`). Its in-memory projector also upserts a session on an update (`applyToProjection`, `:1129-1134`), but only folds a command's own events onto the records that command read, so the adapter follows the stored bindings. J3 Bots never starts a fresh context, so this is work another client left. This path has two known limits. A snapshot can leave out a session bound to the thread, such as a stopped one: its windowed read keeps only busy sessions and those of the provider threads it returns (**Read**, `ProjectionStore.ts:4323-4333`). If such a session returns to ready without a new `provider-session.attached`, the adapter ignores its updates, and so its provider thread's tasks, until it is attached again. And a Stop may wait until its deadline on a live item of an old provider thread whose provider session is gone, since the engine's stop interrupts at that item's provider turn and nothing then ends the item; the engine's own stop waits on it the same way. Each piece goes to the run the engine gives it. A provider's task carries the run that was executing when it first appeared, which the engine's projection stamps on it; the stream carries the task as the provider reported it, so the adapter stamps it the same way (**Read**, `ProjectionStore.ts:936-954`, applied at `:1153-1159`; `contracts/orchestrationV2.ts:1105-1106`). A live item carries its own run. A task reported while no run executed carries none, and is `unattributed`. **Verified** on release `4969` with the scripted agent, by the conformance suite: a task the agent delegated with the engine's own `delegate_task` and still running after its turn ended is reported under that turn, whose end reported it as handed off, and once a Stop has ended it nothing is reported and no turn is left to run. A dynamic tool marked `persistent`, which the agent keeps running on purpose, never counts (**Read**, `orchestrationV2PendingBackgroundWork.ts:243-258`, `pendingBackgroundTurnItems`). The stream sends a dynamic tool's input above 16 KiB as `{summary, truncated: true}`, which drops that mark (**Read**, `WireProjection.ts:29`, `:69-107`, `:190-197`), so the adapter reads such a live tool's item whole with `getTurnItem`, off the loop and bounded at 10 seconds, as it fetches a held file change. Until a read succeeds the tool counts as pending. An item that is no longer a dynamic tool is transient: nothing marks it persistent. `getTurnItem` bounds the input too: above 256 KiB it cuts a string input as it is, or any other input's JSON text, and ends it with `"\n… output truncated for transport"` (**Read**, `ThreadManagementService.ts:1746`, `WireProjection.ts:30-31`, `:44-51`, `:212-224`, `:255-266`). Nothing the engine sends says whether a cut input was a string or an object: the stream's summary is the first line of either (`WireProjection.ts:69-107`), and the cut keeps no type. A cut text that does not open with `{` was no object, so it carried no mark: the tool is transient. One that does may be an object or a string that opens with an object's text, and only an object can be persistent, so the adapter reads no mark in it: the tool's persistence is **undecidable**. What the reads learned is kept per session, shared by its streams and by a Stop's reads, so a tool is read once at a time and once settled is not read again. Only a stream forgets it, from the latest view of the session it has: a tool that view shows ended. A view older than one that pruned before changes nothing, since a tool it shows ended may have been reopened, and a view that does not have a tool says nothing of it, since a Stop's read may claim one no stream has seen yet; the session's end forgets the rest. A read changes only the entry it claimed. So no stale view resets a read's backoff or lets a second read start while one runs. Each stream also drops what it learned of a tool once its mirror shows the tool ended or no longer has it, with the read it asked for: a tool reopened is read again, and the answer of a read asked for before counts for nothing. A read that fails or times out is retried on a later event or catch-up only once its backoff passed, from 2 seconds and doubling, as the server's recovery backs off, never on every catch-up of a Stop that waits; after 5 failed reads in a row the tool is undecidable too. An undecidable tool is decided where it counts, when a `synchronized` reports the session's background work, and counts for its own item's turn, by the engine's own projection of the thread's pending work: the shell row `getThreadFamily` returns for the thread (**Read**, `ws.ts:2116-2117`, `contracts/orchestrationV2.ts:4029-4044`), whose `pendingBackgroundTasks` the engine derives by the same rule from the stored items, their inputs whole (`ProjectionStore.ts:9050-9064` in `shellThreadStateFromRow`, from `selectShellPendingTurnItemRows` at `:8609-8623`), each item listed by the provider's id of it, or by its own (`orchestrationV2PendingBackgroundWork.ts:234-240`). A tool listed there is pending; one not listed has ended, or runs on purpose. The shell picks its runs by another rule than `thread.stop`: its latest run is the presented run, which skips held queued runs, silent compaction runs and some cancelled ones (`ProjectionStore.ts:8237-8264`), and its active run skips silent runs (`:8453-8460`), where `thread.stop` takes the last run that is not queued (`Orchestrator.ts:14165-14178`); and it lists nothing while its own gate holds, a run active or its latest run not settled (`orchestrationV2PendingBackgroundWork.ts:270-285`). So the adapter keeps the engine's rule over its mirror for everything else, and asks the shell only about undecidable tools, also when other work is pending, since each counts for its own turn: a shell whose gate holds, a missing shell, or a read that fails or takes more than 3 seconds cannot say, and the tools count as pending. The bound sits well inside the server's ten-second deadline for the whole `synchronize`, which also covers the wait for the marker, so that pending work still reaches the server in time and a Stop waiting on it keeps its grace and sends a fresh round, rather than deferring because the marker came too late. The other choices fail. Counting such a tool settled once the engine accepted a stop would confirm a Stop whose interrupt the engine then failed to plan, which leaves the tool running though the stop was acknowledged (`Orchestrator.ts:14183-14212`). Counting it pending until it ends would wedge the bot on a persistent tool, which the engine's stop leaves running as the agent meant: the Stop would never settle, and every message to the bot would wait. The shell, which reads the stored input, tells the two apart. A refused `thread.stop` interrupted nothing, so when the adapter checks whether a refusal is moot, an undecidable tool is something to stop: the refusal is `StopRejected`, and the server sends a fresh round on its backoff. Each `synchronized` also lists the session's runnable turns: every run the engine can still run, waiting in its queue (steers kept aside included), or preparing, starting or running. These are what a Stop ends: `thread.stop` interrupts the latest run preparing, starting or running and holds the queue, and the adapter cancels each waiting run (**Read**, `Orchestrator.ts:14165-14178`, `holdStoppedThread` at `:13115-13163`). A run the engine starts or queues on its own is listed as soon as it exists, whatever started it: a start for a message, also one a provider notification or a background task's completion dispatched, which no event tells of before it starts (**Read**, `Orchestrator.ts:8451-8461`), and a scheduled task's message, which the engine queues (`mode: "queue"`, **Read**, `ScheduledTaskService.ts:1062-1090`) and which no dispatch of the server's names. Such a run created after a Stop's commands, or after the adapter took its list of runs to cancel, was missed by them, and one queued behind the Stop's hold would start once the server resumes the queue. So the server keeps the Stop unsettled while the marker lists any, sending a fresh round each time the latest one's grace passes. A caller that gives up on `synchronize` cancels its catch-ups, those still queued and the one running; an item a catch-up has started to apply is applied whole, so the stream never skips or repeats one. The server bounds its own wait for the marker at ten seconds, shorter than this, so a late marker is a delay of that one session, which only its own work waits on, and never this `EngineUnavailable`, which ends a whole pass of the worker that met it ([Server: the workers](server.md#the-workers)).

- **Continuations.** A turn that failed at a usage limit, and that the engine will resume at the reset, ends with `continuation: {resumesAt}` on its `turn-finished`. The engine arms the resume asynchronously, so the adapter predicts it with the engine's own rule (**Read** at `db51b67`, `ProjectionStore.getLimitRecoveryCandidates`, `limitRecoveryCommand`): the thread's latest executed run, leaving out queued runs and runs cancelled before they started, failed; its root failure, the latest failed error on the run's root node, is a usage limit whose reset lies after the run's completion; the thread is neither archived nor settled; no request waits; and either the thread's `limitRecovery` is armed for that run and reset with auto-resume on, or it is not armed yet and the reset is less than a day past. It reconciles the prediction with the armed state and with the `usageLimitContinuationOfRunId` of the run that resumes it. Snoozing a thread only delays its continuation, and J3 Bots never snoozes one. Restart continuations are turned off ([Provisioning](#provisioning)).

A session's harness does not belong to the instance: the engine's session manager opens it in a scope of its own and keeps it, between turns too, until it releases the session, after 30 minutes without a turn or on a `provider-session.detach` (**Read** at `59651c1`, `sessionScopes` and `DEFAULT_IDLE_TIMEOUT_MS` in `ProviderSessionManager.ts`). So a session the engine has open keeps running the executable it started on, and the server, once the switch is made, has the engine release each session on that provider (`configureSession` with `reloadTools`, below), so its next turn starts the new executable and resumes the conversation. What becomes of a turn that runs across the rebuild is not known (**Assumed** unsafe), so the server switches only when no bot's session on that provider runs. Until then the adapter reports it `checking`, as after a start. The version compared is the first `x.y.z` in what the engine reports: for Codex, the part of its user agent after the slash (**Read** at `59651c1`, `CodexProvider.ts`); for Claude Code, what its check parsed from `claude --version` (**Assumed** to hold the version as the maker lists it). - **Requests.** Approvals and questions are answered with `respond`. A question card names its questions and options by position (`question-1`, `option-2`), and the adapter maps an answer back to the engine's own question ids and option values: an option's `value`, or its trimmed label when it has none, a list for a question that takes several choices, and a typed answer sent alone, as the engine's own client sends them (**Read** at `db51b67`, `pendingUserInput.ts`). A question takes typed text unless it sets `allowCustomAnswer: false`. A request a card cannot hold whole, with more than 4 questions or more than 6 options to one, arrives as `unsupported-question`, which the server shows as a question card that says so, and which takes no answer, so its turn waits for a Stop: no part of a question is ever left out. A question is never dismissed: the engine takes a dismissal only of a question whose request is answered by a later message (`responseCapability` `message`, which Codex gives a question its agent sends without waiting), and refuses it for every question a turn waits on, which Claude Code, Codex and ACP agents all ask with `live` (**Read** at `59651c1`, `Orchestrator.ts`, `dispatchThreadUserInputDismiss`, and the three adapters). **Verified** on `0.1.11` with the scripted agent's `question`: the dismissal was refused with "This question needs an answer. Answer it or stop the turn.", a resend under the same key with "previously rejected", and a Stop then ended the turn. An answer the engine refuses while its request stays open is `AnswerRejected`. The adapter learns it as it learns a dispatch's refusal, by a resend that finds the key's rejected receipt, and the engine keeps that receipt, so the key is spent (**Read** at `59651c1`, `dispatchRuntimeRequestRespond` and `dispatchWithReceiptEffect`; the resend of the refused dismissal above is that receipt, **Verified**). The engine refuses an answer to an open request when its provider session is gone or it cannot resume, and checks nothing else of an answer to a question a turn waits on, so none of these could be provoked with the scripted agent; the conformance suite does not cover it. Secret requests are answered with `respondSecret`, which carries the value as a redacted string to the engine's own secret path; the value never enters an event, a log or a stored record. The engine does not order two answers to one secret request: both can pass its pending check and both report success (**Read**, `SecretRequests.answer`), so the adapter submits one answer per request at a time, and a second submission finds the request closed (`RequestClosed`). A request closes as `answered`, `provided`, `declined` or `expired`, and every request open on a turn expires when the turn ends. While it is open, its card can change, as `request-updated`: only from what the engine records about it, and never after it closed. `respondSecret` has no key, and only its success proves that its own answer was the one taken: a retry after a lost reply that finds the request closed learns only how it closed, which may be another answer or `expired`.
- **Approvals show the exact action, or say they cannot.** An engine approval item carries only the provider's `prompt` and `reason` and the options it offers; the action it holds back is a separate item the provider records under the same native id. The adapter takes the action from that item, verbatim, whitespace kept: a `command_execution`'s `input`, or a `file_change`'s paths and `diffStr`. It takes the item only when the approval's runtime request has the item's native id, since one item can be held by several approvals that each ask about part of it, and it reports `exact` only when it found the item whole (a file change needs its diff, and a diff covers one file). A prompt that differs from the action becomes the reason; a prompt that gave the action, or trims to it, never does, so the provider's own reason, when it gave one, is the only reason left. With no such item, the prompt is passed on as a summary with `exact: false`. A text whose last line break follows a backslash is not exact either, since the card drops trailing line breaks and that one continues the line; nor is a text that holds a carriage return or any bidi control (Unicode's `Bidi_Control`: the marks, embeddings, overrides and isolates), which the card draws as something other than what runs: a carriage return looks like a space or a line break, and a bidi control reorders the text around it or draws as nothing. A unified diff's CRLF line endings are exempt, since they only end its lines. For a change that is not an update, `diffStr` is no unified diff: Codex records an added file's contents there (**Read**, `tool_call_restricted_granular` fixture), and Claude Code its tool's output, so such a change is exact only when the card drops none of it: contents that end in a line break would look the same as contents that end in two, or in none. The card gets the change's operation with its text (`add`, `delete`, `update`, or none when the engine names none) and reads only an update as a diff, so a new file's lines that start with `-` or `+` are its contents, not removals or additions.
  - **A file change's diff is fetched apart.** The engine strips `diffStr`, `oldStr` and `newStr` from every `file_change` it sends on a thread's stream unless the change failed, in live events, replays and snapshots alike (**Read** at `db51b67`, `WireProjection.ts:177–181`, `projectTurnItemForWire`, reached through `projectDomainEventForWire` at `ws.ts:974` for replays, `projectStoredEventForWire` at `EventSink.ts:1053` for live events, and `projectThreadProjectionForWire` for snapshots). So when an open approval holds a file change of one file that came without its diff, the adapter fetches the item with `orchestration.getTurnItem`, which returns it through `projectTurnItemForDetail` and keeps `diffStr` up to 256 KiB (**Read**, `ThreadManagementService.ts:1746`, `WireProjection.ts:255`). The approval opens as a summary meanwhile. The fetch runs off the event loop, once per version of the item (its `updatedAt`), and is bounded at 10 seconds; a fetch that fails or runs out leaves the card a summary with no grant, and is not tried again for that version. Fetches can land out of order and late, so a fetched item is kept only while an open approval holds the item at the version it was fetched for: it then becomes `request-updated` with the exact card. A fetch for any other version, or one that lands after the approval closed, changes nothing, and the version held is fetched on its own. What was fetched is let go as soon as its approval closes or its item moves on, and when a snapshot no longer holds it. A stream resumed by replay fetches at once what an approval it told only as a summary still needs, since the engine has nothing new to send for a turn the approval holds.
  - **A cut diff is not the change.** The engine stores a file change's diff cut to 32,768 bytes, with `"\n… output truncated for transport"` appended (**Read**, `boundFileChangeForStorage` at `WireProjection.ts:55`, applied by `ProviderEventIngestor.ts:582`), and `getTurnItem` cuts at 256 KiB with the same words. A diff that ends with them is shown as a summary, with no grant. A diff that happens to end with those words loses only its exactness. `sessionGrant` is set here too: what "Allow for session" allows from then on, so the card can say it in words. It is set only for an exact command or file change, only when the provider takes a grant for the session (by its listed options, or, when it lists none, as the engine's own client offers "Always allow this session"; **Read**, `ComposerPendingApprovalActions.tsx`), and only for a provider whose grant has been read. Otherwise it is `null` and the card offers no grant. At `db51b67` (**Read**):
  - Codex keeps, per provider thread and runtime mode, the request kinds granted for the session. Accepting for the session adds "command" or "file-change", and every later request of that kind in the thread is answered `acceptForSession` without being asked, whatever it runs or changes (`CodexAdapterV2.ts`, `sessionAllowance` at 2227, used by `item/commandExecution/requestApproval` and `item/fileChange/requestApproval` at 5928–5985 and 5999–6057, and by `execCommandApproval` and `applyPatchApproval` at 6216 and 6285). So its grant covers `every-command` or `every-file-change`. The comment on `sessionApprovals` (`CodexAdapterV2.ts:2197`, "covers only the exact command or patch") contradicts that code; J3 Bots follows the code.
  - An approval of an MCP tool, a connector's, is an elicitation, which the engine answers with Codex's `_meta.persist: "session"` for `acceptForSession` (**Read** at `59651c1`, `CodexMcpElicitation.ts`). Codex keeps that in memory for the session and writes nothing to its `config.toml`; only its "always" answer, which J3 Bots never gives, is written there (**Read** in Codex `rust-v0.171.0`, `core/src/mcp_tool_call.rs`: `ApprovedForSession` calls only `remember_mcp_tool_approval`, `ApprovedMcpPolicyAmendment` calls `maybe_persist_mcp_tool_approval`). So no approval of the operator's lives in a file that provisioning rewrites.
  - Claude Code is offered no grant. It answers one with `updatedPermissions`: the CLI's own permission suggestions, moved to the session, or, when it suggests none, an allow rule for the whole tool (`ClaudeAdapterV2.ts`, `permissionResultFromDecision` at 4453, `toSessionPermissionUpdates` at 4497). A suggestion can be a `setMode` (only an administrator's ceiling drops it, at 4473–4476), so a file change allowed for the session can switch Claude Code to `acceptEdits`: the engine's own test sends `{type: "setMode", mode: "acceptEdits", destination: "session"}` with an `Edit` grant (`ClaudeAdapterV2.test.ts:1076`). The suggestions never reach the approval the engine records: the permission callback passes them only to `permissionResultFromDecision` (12641–12650), not to `buildApprovalRequestArtifacts` (12584), whose presentation takes only the decision reason, the matched ask rule and `suppressAlwaysAllowRule` (`claudeApprovalPresentation`, 4419). So what a grant would cover cannot be told from the approval, and `sessionGrant` is `null` for its commands and file changes; Allow once stays.
  - Every other provider: not read, so no grant is offered. An approval opens once both its item and its runtime request are recorded, which the providers do in either order. At `db51b67` (**Read**, `CodexAdapterV2.ts` and `ClaudeAdapterV2.ts`):
  - Codex records the command item from its `item/started`, with the command as Codex reports it, so a command approval is exact when that came first. Its prompt is the escalation's reason when there is one, else the command. The approvals it raises for each subcommand of a script run through its shell bridge, and for input to a running command, have an approval id of their own under the command's item, so they are summaries. A file change's item comes only once the change is applied, so a file-change approval is always a summary: the reason, the list of paths, or the root it wants to write under. The command's working directory reaches the engine's adapter but not its records.
  - Claude Code records a tool's item as the tool call arrives, so the same match finds a shell command's item. That the SDK delivers the call before it asks for permission is **Assumed**. The item's command is trimmed (`commandInputFromClaudeTool`), so a trailing escaped space is lost from it, while the prompt is the tool input's `command` as given, whenever it is not blank. The card therefore shows the prompt, exact, when it trims to the item's command, and a summary otherwise; the prompt is then the action, never a reason, even where the card drops a line break it ended with. Other tools' prompts are the SDK's title or description, and `reason` is the permission check's own reason. An edit's item carries its path but its diff only once the tool has run, so an edit approval is a summary too. Neither provider gives a working directory.
  - Whether Codex's `item/started` reaches the engine before its approval request, which decides how often a command approval is exact, is **Assumed**: neither the protocol schema nor the adapter promises an order, and it has not been observed on a running server. If it comes later, the card opens as a summary and, while the approval still waits, becomes exact with `request-updated`.
  - So at `db51b67` neither Codex nor Claude Code has a file change's diff recorded when it asks, and the fetch above finds none for them: their file-change approvals stay summaries. The fetch matters for a provider that records the change, diff and all, before asking under the same native id. The engine's ACP adapter cannot either: it records an approval's native reference as weak (**Read** at `db51b67`, `packages/provider-acp/src/server/adapter.ts:6272`), and the adapter takes an item only by a strong reference, so ACP approvals stay summaries too, even when a diff is recorded.
- **Stop.** `stop` ends the session's running turn and the background work the engine can reach, cancels every turn waiting in the engine's queue, drops untaken steers and disarms a pending continuation. Each of its commands is resolved by its key, as a dispatch is: an error reply is answered by a resend of the same command, which the engine answers from the key's receipt (**Read** at `db51b67`, `Orchestrator.ts`: a refusal while planning commits a rejected receipt at L16018-16034, for instance when a projection read fails, and a resend replays it at L15867-15877). A lost reply is `EngineIndeterminate`, and the server sends the same key again. A refusal is moot, and counts as done, only when nothing the Stop targets can still run: no run that has not ended, other than those waiting in the queue, which the cancels end; no background work the engine counts as pending; no continuation it will start on its own. Any other refusal is `StopRejected`: the key is spent, and the server stops the session again with a fresh round. It always sends `thread.stop`, with delegated tasks stopped, also to a session with no running turn: the engine then interrupts the latest run if it still has background work pending, stops its delegated tasks, holds what waits and turns the usage-limit resume off (**Read** at `db51b67`, `Orchestrator.ts`, `dispatchThreadStop`, `holdStoppedThread`). Its success only acknowledges that the engine took the commands, `thread.stop` and then a `queued-run.cancel` per waiting run: the effects land afterwards and are confirmed by the session's events (the running turn's `turn-finished`, each waiting turn's, `steer-dropped`, `continuation-dropped`). In a session whose latest run already ended, the engine's stop interrupts that run when it has pending background work: it records the interrupt and queues the provider's interrupt as an effect run after the commit (**Read** at `db51b67`, `Orchestrator.ts:13908-13934`), so the work can still run when a marker arrives. That work is confirmed ended by a `synchronized` that reports none pending. A success does not promise the interrupt: when planning the run's interrupt fails, `thread.stop` logs it, discards that attempt's events and still succeeds, marking the run stopped (**Read** at `db51b67`, `Orchestrator.ts:14183-14212`). A run whose provider never starts stays `starting`, with no event to tell of it. Neither shows in the stop's answer, only in the session's state afterwards, so the server judges a Stop by that state alone, and sends a fresh round while it still shows work past the round's grace ([Server: Stop](server.md#stop)). A message that reaches the session between the commands can release the hold and start a turn the cancels miss, so the server sends a session nothing while a Stop of it is unsettled, and stops a dispatch that lands anyway on sight ([Server: Stop](server.md#stop)). It is the operator's Stop, also used when a room is archived; a rotation retires the old session with `retireSession`, which stops it the same way. Once a session is retired the server closes its event stream and never follows it again.
- **Held queues.** The engine holds a session's queue after an engine restart, a provider error, a model or provider change while the replaced provider session still runs background work, and a Stop. The adapter reports each hold as a `queue-held` event when a turn waits behind it, and a replacement says whether the queue is held (`queueHeld`). The server resumes it with `resumeQueue`, naming the hold's cursor: once per hold, never while a Stop of the session is unsettled. If the engine holds the queue again in answer, the adapter reports that hold only once something has moved (a turn started or finished, or background work that was live at the new hold ended), so the two never loop. A Stop's hold has nothing behind it once its cancels land.
- **Attachments.** `stageAttachment` uploads a file and returns the id the engine minted, with how long it stays usable; the server stores it with the dispatch before dispatching. Asking for the upload URL has a command's 30 seconds; posting the bytes has that plus a second per MiB, at most two minutes, since the engine runs on the same machine. Past either deadline the staging fails with `EngineIndeterminate`, so a stalled upload never holds the session's gate. `normalizeAttachmentMetadata` puts a file's name and media type in the form the engine's upload takes, and the server applies it at upload. `attachmentLimitViolation` checks a dispatch's files against the engine's limits, and `engineInputLength` measures its text as the engine does, against `ENGINE_INPUT_LIMIT`, so a dispatch the engine would refuse is never written.
- **Engine ids.** The engine's item and request ids nest provider and native ids and run to 287–343 characters (**Verified**), past what a J3 Bots id may hold. The adapter names each engine item and request by a digest of its engine id, the same every time, so a replay and a replacement agree; a turn's id is the engine run id, which is short.
- **Session ids.** A session's id is the engine thread id. The bot tool bridge receives the same id as its caller identity, and `sessionOfToolCaller(environment)` decodes it, so the server never names the engine's variable.

`@j3-bots/engine-t3/testing` provides an in-memory engine that honors these rules, with controls to drive the engine's side and tests for the ones a caller relies on: a key applied once and a recovery of it accepted with nothing applied again, a lost reply recovered into the key's own busy turn and delivered once, a rejected key refused again on recovery, a refused start that sends nothing, a start queued behind a turn the engine began while it was on its way, a steer that settles after its turn ends (taken, requeued, or dropped by Stop), a steer refused because its turn waits behind another or ended without completing, a late steer that becomes a new turn, Stop acknowledged before its effects land and then confirmed by events, Stop disarming a continuation, Stop ending background work a turn left running after that turn ended, a recovered dispatch that Stop cancels before it starts settled by its cause, a hold reported once and reported again after the engine holds it again and something moves, a turn that failed before it started told apart from one that ran unseen, tool calls closed with their turn and recorded late, a usage-limit continuation that runs or drops, replay, a replacement that repeats turns already seen end and carries host speech and resolutions, a synchronization marker, requests that expire with their turn, an open request whose card changes, which a replacement then carries as it shows, a secret handed over once, an opening refused for good under its key, permission modes above a ceiling refused naming it, and turns in a session already above it refused on a first send and a recovery, a steer into its running turn let through, a retirement refused for now, and nothing applied while the engine is unreachable. Its controls also hold a call in flight at the engine's door (a dispatch, a staging, a resume, a Stop), start a run while a Stop is on its way, delay a Stop's effects, whose cancels name the turns waiting when it was sent, so a turn queued meanwhile stays held, and lose a synchronization marker. Server tests run against it. Only the conformance suite runs a real engine.

## What J3 Bots uses, and what it leaves alone

J3 Bots keeps the engine surface it touches small, because every part it touches is a part an upgrade can break.

| Engine capability | Used | How |
| --- | --- | --- |

| Threads | Yes | The bot's main session and its side sessions |

## Provisioning

Before each start of the engine, while it is stopped, J3 Bots writes `<engine dir>/userdata/settings.json`, the engine's secret store and each harness's configuration, from what it keeps: the provider instances and the stored [provider connection](#reaching-the-models). It writes all of them whole each time, so a provisioning cut short is completed by the next start. The engine reads its settings at startup and watches them afterwards (**Verified**), but J3 Bots never writes them while it runs, so the engine's own web interface, which writes the same file, is never writing it at the same time. J3 Bots reads the file, sets its own keys and instances, and writes it back, keeping what the engine keeps there.

A file J3 Bots must read to provision is read, never assumed: a missing one is the first setup, and one it cannot read or edit safely is left as it is. For a harness's configuration (Claude Code's `settings.json` and `.claude.json`, Codex's `config.toml`), the file's path and the place in it are logged, never its contents, and the instance is written `enabled: false`, so that provider shows `unavailable` and the others still start; the next start tries again. When the engine's own settings or the stored connection cannot be read, the engine does not start, and the log names the file.

| Setting | Value | Why |
| --- | --- | --- |
| `sidebarAutoSettleAfterDays` | `null` | A bot's session must not be settled after a week of quiet. A settled thread loses usage-limit auto-resume. |
| `continueThreadsAfterServerUpdate` | `false` | Off, the engine arms no continuation message when it restarts (**Read** at `db51b67`, `ProviderRuntimeRecoveryService.prepareForShutdown`, `RestartContinuation.ts`). Whether one is pending is visible only over `/mcp`, so J3 Bots could not keep a dispatch open for it; a turn the restart cut short ends `interrupted` and the server handles it like any other. |
| `sidebarAutoSettleOnMerge` | `false` | Not applicable. |
| `idleCompaction` (Claude) | `beforeCacheExpires` | An unattended bot has nobody to press a compact button. |
| `autoResumeLimitedThreads` | `true` | A bot that hit a limit should continue at the reset. |
| `enableAgentDeviceAccess` | `false` | Bots do not drive phone simulators, and turning this off removes T3 Code's device instructions from every session. |
| `enableAgentBrowserAccess` | `false` | No bot uses the engine's browser unless the operator turned its switch on. That bot's project then turns it on in its overrides, which provisioning keeps ([The browser](#the-bots-browser)). |
| `enableProviderUpdateChecks` | `true` | The operator's update of a harness needs the engine to know its latest release; set, so a settings file an earlier J3 Bots wrote with it off is turned back on ([Isolation](#isolation)). J3 Bots checks for new versions of its own copies of the harnesses itself ([decision 0045](../decisions/0045-j3-bots-keeps-its-own-copies-of-the-harnesses.md)). |
| `providerInstances` | Generated | One Claude Code and one Codex instance, each with its own home, launch arguments and environment, and the scripted agent when the server offers it, whose environment carries the bridge's command and key, since the agent starts the bridge itself; and each of the engine's own default instances, turned off ([Isolation](#isolation)). |

An environment variable marked `sensitive` is not stored in `settings.json`. The entry carries `"value": "", "sensitive": true, "valueRedacted": true`, and the value lives in the engine's secret store, one file per variable named after the instance id and the variable name. **Verified**: an instance provisioned this way authenticated against its provider.

Provider instances are where J3 Bots attaches its prompt and its tools. Every item below is **Verified** on release `4969` unless marked.

For Claude Code:

- `homePath` points at a J3-owned config directory, which the engine passes as `CLAUDE_CONFIG_DIR`.
- That directory's `.claude.json` holds `hasCompletedOnboarding: true` and the `j3` MCP server under `mcpServers` (stdio: `command`, `args`, `env`, which holds the bridge's key (`ToolBridge.environment`), and `timeout`, how long one call may take, in milliseconds: twelve minutes, a minute past the bridge's longest deadline). Claude Code rewrites this file with its own state, so J3 Bots merges its keys into it and never replaces it.
- That directory's `settings.json` is applied to every session. It turns auto-memory off with `autoMemoryEnabled: false` (**Read** in Claude Code 2.1.328: "When false, Claude will not read from or write to" the memory directory). Once a connection is stored, it also carries the connection's URL and key helper ([Reaching the models](#reaching-the-models)). J3 Bots sets only these keys and keeps the rest of the file.
- `launchArgs` is `--append-system-prompt-file .j3/system.md --allowedTools mcp__j3__say,mcp__j3__ask,… --disallowedTools <tools>`:
  - The prompt file path is resolved inside each thread's project folder, so one instance serves every bot and each gets its own file.
  - `--allowedTools` names each of J3 Bots' own tools exactly (`toolList` in `packages/prompts`), which then run without an approval in every permission mode. Without it, a supervised bot's every `say` waits on an approval card. A connector's tool, which the same bridge lists, is not named, so it follows the session's permission mode ([decision 0027](../decisions/0027-connector-tools-reach-a-bot-through-the-j3-bridge.md)).
  - `--disallowedTools` removes the harness tools that reach a person or vanish with the session: the question tool, plan mode, the cron, wake-up and loop tools, and push notifications. A removed tool is absent from the model's tool list. The engine's own browser tools, `preview_evaluate` included, stay, on Claude Code as on Codex ([Security: filling a login](security.md#filling-a-login)).

For Codex:

- `homePath` points at a J3-owned directory, which the engine passes as `CODEX_HOME`. Codex writes its own state into its `config.toml` (trusted projects, its settings), so J3 Bots edits only its own part, by key and by table, and keeps the rest: the top-level `developer_instructions` and `model_provider`, and the `[model_providers.j3]` and `[mcp_servers.j3]` tables, however the file writes them (a table, a dotted key, an inline table). A change of the operator's name rewrites only `developer_instructions`. The editor reads the file by TOML's grammar, strings, quoted keys, arrays and inline tables whole, so a line inside a multi-line string or a `]` in a quoted table name is never taken for a header. It checks the file with a TOML parser ([smol-toml](https://github.com/squirrelchat/smol-toml)) before the edit, and after it that everything J3 Bots does not own reads the same. A file that is not TOML, or that the editor cannot follow, is left as it is, with a warning that names the file and the place, never its contents, and the Codex instance is turned off; the other harnesses start, and Codex gets its part when the engine next starts after the operator corrects or moves the file. Its part carries:
  - `developer_instructions`: the base prompt every bot shares, rendered by the server with the operator's name and written again when that changes. Codex takes no prompt file the way Claude Code takes `--append-system-prompt-file`, and one Codex process serves every thread on the instance, so the instance-wide text is the shared base prompt and the per-bot layers (profile, pinned memory) go into each workspace's `AGENTS.md`. **Verified** on release `4969`: the base prompt reached the model as a developer message. The engine's own text goes in each turn's `additionalContext`, never in `developer_instructions` (**Read**, `CodexDeveloperInstructions.ts`), and the `collaborationMode` it sends with every turn did not displace it.
  - once a connection is stored, `model_provider = "j3"` and a `[model_providers.j3]` table with `base_url = "<base>/v1"`, `env_key` naming the variable of the connection's key (below) and `wire_api = "responses"`. The provider's name must not contain a dot, which TOML's dotted keys would split.

  J3 Bots owns those keys and the two tables, however the file writes them: a table of its own, a dotted key, or a pair inside an inline table such as `mcp_servers = { j3 = {…}, other = {…} }`, which is edited in place with the other pairs kept as written. Each of its tables the file has is replaced where it is, under the comments above it, and one the file lacks goes at the end. Everything else stays. TOML's parser checks the file before the edit and checks after it that nothing J3 Bots does not own reads differently; a file it cannot edit that way is refused with its line, as above.
  - `[mcp_servers.j3]` with `command`, `args`, `env`, an inline table with the bridge's key (`ToolBridge.environment`), and `tool_timeout_sec`, the counterpart of Claude Code's `timeout`, and `tools`, an inline table with `{ approval_mode = "approve" }` for each of J3 Bots' own tools, the counterpart of `--allowedTools`. That is the same TOML as a `[mcp_servers.j3.tools.<name>]` table each, which is what was **Verified**, but keeps the server one pair, so it can be written into an inline `mcp_servers` as well. The server keeps Codex's default approval mode, so a connector's tool follows the session's permission mode. J3 Bots owns `[mcp_servers.j3]` with every table under it. The server's name must not contain a dot: T3 Code skips such names when it tags servers with the thread id (**Read**).
  - `[shell_environment_policy.set]` with `HOME`, the server's own, which Codex puts in the environment of every command it runs (its shell, `exec_command` and hooks; **Read** in Codex 0.171.0, `protocol/src/shell_environment.rs`). J3 Bots owns that table. It is left out when the server has no `HOME`.
  - `[features]` with `shell_snapshot = false` and `mcp_tool_list_changed = true`. The second makes Codex list the `j3` server's tools again when the bridge says they changed, so a connector granted to a bot reaches it mid-session; the feature is still marked in development in Codex 0.171.0 (**Read**, `features/src/lib.rs`), and its effect is **Verified** below. With the snapshot, Codex runs the login shell once with its own environment, whose `HOME` is the empty folder below, and runs each command in a plain shell that reads that capture, so a bot's commands would miss what the operator's profile sets. Without it, each command is a login shell (`bash -lc`) with the `HOME` above (**Read** in Codex 0.171.0, `core/src/shell_snapshot.rs`, `core/src/tools/runtimes/mod.rs`, `core/src/shell.rs`). J3 Bots owns that table: Codex writes it only from its terminal client and `codex features`.
- When the server has a `HOME`, the instance's environment in the engine's settings sets `HOME` to a folder of the adapter's own, `<engine dir>/j3/codex-homes/<instance>`, created empty, so Codex finds no user skills or plugin marketplaces of the operator's ([decision 0019](../decisions/0019-codex-runs-with-a-home-of-its-own.md)). The engine sets it for every Codex process of the instance, its checks included (**Read** at `59651c1`, `mergeProviderInstanceEnvironment`, used by `CodexDriver.ts`). **Verified** on `0.1.11` with Codex 0.171.0: the instance's `codex app-server` ran with that `HOME`; and through a real `exec_command`, with the `config.toml` and environment the adapter provisions, a command got the server's `HOME`, a variable the operator's `~/.profile` exports and a program it puts on `PATH`; with the snapshot back on, it got the `HOME` but neither of the others. Like any login shell that is not interactive, it does not read `~/.bashrc` unless the profile sources it. Without a `HOME`, as is usual on Windows, Codex keeps the server's environment, since Git for Windows would read the empty folder before `USERPROFILE`. On Windows, Codex finds its home folder for skills from the system rather than from any variable (**Read**, `dirs-sys` 0.5.0; **Verified**, [Isolation](#isolation)), so the folder would not hide the operator's skills there anyway.

For both, the shared skills ([Skills](../prompts/architecture.md#skills)):

- Each harness lists the skills of its home's `skills/` folder, one folder with a `SKILL.md` per skill, following links: Claude Code `$CLAUDE_CONFIG_DIR/skills` and Codex `$CODEX_HOME/skills`. **Verified** with Claude Code 2.1.328 (the `skills` of its `init` message, and the listing in the request it sends) and Codex 0.170.0 (its app server's `skills/list`), each with a fresh home holding linked skill folders: both listed them and both left out a link to a folder that was gone. Each also lists project skills from the thread's folder (`.claude/skills`; `.agents/skills` and `.codex/skills`). On a name both define, Claude Code lists only its home's skill and Codex lists both (**Verified**, same versions). In a real turn on release `4969`, a Claude Code bot (`claude-sonnet-5-5`) and a Codex bot (`gpt-6.2-sol`), asked to list their skills, each named `j3-routines` from the shared skills.
- At every provisioning, the adapter makes the home's `skills/` a folder of its own and puts in it one link per shared skill, `<name>` leading to `<J3_HOME>/shared/skills/<name>` by a relative path computed from the real path of the home's `skills/`, links resolved, which is where the system resolves it from. On Windows each link is a junction instead, which holds the skill's absolute path: a symbolic link there takes a privilege an ordinary user does not hold unless Developer Mode is on, and a junction takes none. A junction is taken to hold what was recorded when it leads where the recorded path leads from the home's `skills/`, compared without case, so after the data directory moves the old junctions are left as the operator's and those skills are not linked again until they are removed (**Verified** in CI on Windows Server 2025, which runs these cases). It records the links it made in its own folder, `<engine dir>/j3/skill-links/<instance>.json`: a link enters the record once it exists, and leaves it before it is removed, so the record never names a link the adapter did not make; a start cut short can only leave a link unrecorded, which is then treated as the operator's. At the next provisioning, a recorded link that is still a link holding what was recorded, and still leads where its skill is, is kept as it is; one whose skill is no longer shared, or has moved, is removed with a plain unlink, never a recursive removal. So a skill removed from the shared folder loses its link. The server also has the adapter link again after every change it makes to the shared skills (`linkSharedSkills`), under the same rules and one provisioning at a time, so a skill added or removed there reaches each harness home while the engine runs, with no restart. The record is read only when it is a regular file in private state; otherwise the home is left as it is, with a warning. A shared skill is a folder whose name does not start with a dot and whose `SKILL.md` is a regular file. An entry of the shared folder that cannot be read (a link loop, say) is skipped with a warning, and a shared folder that cannot be read as a folder counts as empty, with a warning. Linking never stops the engine's start: a write, link or removal that fails in a home (a read-only `skills/`, say) stops the linking there with a warning naming the home, and what was already there is kept.
- Nothing else in the home's `skills/` is touched, no dot entry ever: Codex installs its own skills in `skills/.system`, and anything already at a shared skill's name (a skill of the home's own, one a harness saved there, or a link someone else made) wins over the shared skill, which is then not linked; that is logged.
- Each link goes through the containment check: where it leads, from the real path of the folder that holds it, links resolved, must be private state (`<J3_HOME>`). A shared skill whose folder leads out of private state is not linked, and its link from an earlier start is removed. A home whose `skills` is a link or a file is left as it is, with a warning, and gets no links, so the adapter never makes or removes one in a folder outside private state.

A bot's own skills, in its workspace's `skills/`, are the project's: no harness reads that folder, and none reads a folder the other does, so the adapter links each skill there into `.claude/skills` and `.agents/skills` of the workspace (`linkBotSkills`), which Claude Code and Codex list for a thread in that folder (**Verified**, same versions). It does so when it provisions the bot's project and after every change the server makes to the bot's skills, with the rules above: one link per skill, recorded in `<engine dir>/j3/skill-links/` by the workspace's path, a folder already at a skill's name left as the bot's or the operator's, and the containment check on each.

### Reaching the models

A J3-owned home holds no sign-in at first, so each instance needs a way to its models. J3 Bots offers one: a **provider connection**, an endpoint that speaks Anthropic's Messages API and OpenAI's Responses API, such as [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) in front of the operator's own subscriptions, and the key it takes.

- The operator runs `j3-bots provider connect` on the host. It asks for the endpoint's base URL, unless `--base-url` gives it, and for the key without echo, or reads the key from standard input, so the key never reaches the command line, the shell's history or the process list. The base URL must be `https`, or `http` to this machine only (`localhost`, `127.x.x.x`, `[::1]`): the key travels with every request. The command hands both to the running server over the admin socket, and the server to the adapter (`connectProviders`). The app's endpoint form, in local mode ([Sign-in from the app](#sign-in-from-the-app)), sends the same request over the `provider.connect` RPC, which answers the same outcomes; it carries no command ID, since a stored receipt would keep the key.
- The server first pauses its first sends: one under way gets its answer recorded, and none starts until the connection is applied or refused, so no work starts between the check below and the restart. It then asks whether any bot has work running in the engine: a turn running, a dispatch the engine has or one sent whose answer was lost, or, from a synchronization marker, a turn the engine can still run or background work it counts as pending; a session whose state cannot be read, the engine having gone away meanwhile included, counts. It reads up to four sessions at a time. When one has, the command says that restarting the engine stops that work and asks before anything is stored; `--yes` answers for the operator, and without a terminal (the key piped) and without `--yes` it refuses, storing nothing. With no work running it goes on without asking.
- The connection, its base URL and its key together, is one file in the engine's secret store (`<engine dir>/userdata/secrets/j3-provider-connection.json`, mode 0600), written whole and renamed, so a new connection replaces both at once and a write cut short leaves the one before it whole. The engine never reads it: it reads and removes only the secrets its settings name (**Read** at `db51b67`, `serverSettings.ts`). It is the single source of what provisioning writes.
- Then the adapter restarts the engine through its supervisor, and the provisioning before the start writes the connection out ([Provisioning](#provisioning)). It answers `applied` once the engine is back, which then runs on the stored connection; `stored` when it is not back within a minute, or at once when nothing will start it again, as after the engine was found incompatible, and it then starts with that connection whenever it starts. Connection changes go one at a time, each through its restart, so two run at once never both answer for an engine that started with only one of them. The restart interrupts every turn and every background task in the engine, which the server handles as any engine restart. J3 Bots applies a connection only this way, never while the engine runs: a harness that is already running keeps the environment it started with, Codex one app-server for every thread on its instance and Claude Code one process per thread, until the engine unloads the session, not when the instance is rebuilt (**Read** at `db51b67`, `supportsMultipleProviderThreadsPerSession` in `CodexAdapterV2.ts` and `ClaudeAdapterV2.ts`; **Verified** on release `4969` with a change of the key alone, written while the engine ran: the running Codex app-server kept the old key, also for a new session). The engine has no call that restarts an instance's running harnesses short of signing it out (**Read**, `ws.ts`).
- The key reaches a harness in the variable `J3_PROVIDER_KEY`, which the engine's settings declare `sensitive` with an empty value and the engine's secret store holds, once per instance (`<engine dir>/userdata/secrets/provider-env-<instance>-<variable>.bin`, **Read** at `db51b67`, `settingsSecrets.ts`). Each harness's own configuration carries the base URL together with the name of that variable: Codex's `[model_providers.j3]` above, and for Claude Code its home's `settings.json`, with `env.ANTHROPIC_BASE_URL` and `apiKeyHelper = "printenv J3_PROVIDER_KEY"`, which Claude Code runs to get the key it sends. **Verified** with Claude Code 2.1.328 against a CLIProxyAPI endpoint: a turn answered with the URL in `settings.json` and the key only in the variable, and without the variable it failed with the helper's error. The engine reads that `env` too, so a custom endpoint is not taken for a missing sign-in (**Read** at `db51b67`, `readClaudeSettingsEnv` in `ClaudeSkills.ts:662`, used at `ClaudeProvider.ts:829`). One name serves every connection: with nothing written while the engine runs, no harness that started with one connection is still running when the next one is written. The server keeps no copy. The variable reaches the live environment of the commands a bot runs in its shell: under Codex **Verified** with Codex 0.171.0, through `exec_command`; under Claude Code **Assumed**. Codex's shell snapshot is off ([Codex](#provisioning)), so no file under its home captures it any more; the snapshots it wrote under `providers/codex/shell_snapshots/` before that change held the key (**Verified** on release `4969`), are not removed, and can still be there on an upgraded home ([Security](security.md#secrets)).
- **Verified** on release `4969` against a CLIProxyAPI endpoint, with a server on a fresh data directory: with the engine running and no bot, `provider connect` restarted it and answered once it was back; both instances went from signed out to ready about 15 seconds later, while the engine probed them, and bots on Claude Code (`claude-haiku-5-5`) and Codex (`gpt-6-luna`) answered through the endpoint. A second `provider connect`, with the key piped and no `--yes`, while the Claude Code bot ran a turn, was refused and changed nothing: the engine kept running and the turn completed. Run again with both bots idle, it restarted the engine without asking; both bots answered in their existing sessions, and after a fresh start each answered in a new one. Of the files checked in that run, the key was in the secret store, in files of mode 0600, and in none of the engine's settings, the harness configuration or the server's log; Codex's shell snapshot, on at the time, also held it. The prompt a terminal shows when work is running is not part of that run.

**Models.** J3 Bots syncs no model catalog. A bot picks from the models the engine reports for the instance, and the endpoint has to route those names. Claude Code's list is the engine's own catalog for the installed version plus what Claude Code's probe reports (**Read** at `db51b67`, `ClaudeProvider.ts`), the standard Claude model ids, which a proxy in front of a Claude subscription routes as they are (**Verified** with `claude-haiku-5-5` behind CLIProxyAPI). A Claude Code instance lists that catalog signed out and while its first check runs too (**Read** at `59651c1`, `ClaudeProvider.ts` and `makePendingClaudeProvider`), so a bot can be given a Claude model before any provider is connected. Codex's list is what Codex's `model/list` answers (**Read**, `CodexProvider.ts`). **Verified**: behind CLIProxyAPI, the Codex instance listed no model before the connection and the proxy's GPT models after it. A model the engine does not list cannot be chosen; an operator whose endpoint names models otherwise has no way to add one in this release.

**Direct sign-in** is the other way, for an operator without an endpoint: the harness signed in with its own account inside its J3-owned home. Two ways start it, on the same code (`providers/signIn.ts`): `j3-bots provider login claude-code` or `… codex` in a terminal, as the user the server runs as, and the app, which asks the running server to run it with no terminal ([Sign-in from the app](#sign-in-from-the-app)). What the command does is **Verified** on a test machine against stand-in scripts for both harnesses, never a real one:

- It signs in to the data directory the server runs with, found as `doctor` finds it: the installed service's `J3_HOME`, else this shell's (`J3_HOME`, or `~/.j3-bots`). `provider connect` reaches the server through that directory's admin socket too. It prints that directory. It refuses when the directory does not exist yet, saying to start the service once first, or the server when no service is installed, and when it is not private to this user and writable, as the server refuses at start. Inside a directory that exists, it creates the provider home, mode 0700, when it is missing, and nothing else.
- It finds the harness on the `PATH` the engine starts it with, by the lookup `doctor` uses: the installed service's `PATH`, else this shell's. The sign-in runs with that `PATH`. When the harness is missing, it says what `doctor` says and runs nothing.
- It refuses when the provider home or the `providers` folder above it is a symbolic link, so the sign-in cannot act on what the link points to, such as the operator's own. For Claude Code it also refuses a linked `.credentials.json`, the file it keeps its sign-in in. It refuses a provider home other users can open, by its mode or, on Windows, its access list, as the server refuses such a data directory; on Windows an inheritable grant on a folder above it reaches it, so its own list shows that.
- Codex signs in in a new folder inside its provider home, `.sign-in-*`, mode 0700; only once the sign-in succeeded is the `auth.json` it wrote renamed into the provider home. The folder is removed however the sign-in ends: success, failure, Ctrl+C, and a terminal that hangs up (`SIGHUP`, as when an SSH connection drops), which the command takes as Ctrl+C, since Node's own answer to it is to exit with no cleanup and `NodeRuntime.runMain` handles only `SIGINT` and `SIGTERM`. Only a process killed outright (`SIGKILL`) leaves it, private inside the private home, with the `auth.json` it may hold; it is not removed at the next start, which could be another sign-in's. Before the folder goes, what Codex logged of the sign-in there, `log/codex-login.log`, is added to the same log in the provider home, mode 0600, where Codex keeps it when it signs in in its home (**Read** in Codex 0.171.0, `init_login_file_logging` in `codex-rs/cli/src/login.rs`). Signing in in that folder, Codex finds no `config.toml`, since nothing is copied into it, so settings written by hand into the provider home's `config.toml` that change how it signs in, such as `cli_auth_credentials_store` or `forced_login_method`, do not reach the sign-in. Codex revokes the sign-in stored in its home before either of its interactive sign-ins starts, even one then cancelled (**Read** in Codex 0.170.0, `clear_existing_auth_before_login` in `codex-rs/cli/src/login.rs`, with `codex-rs/login/src/auth/revoke.rs`), so a sign-in into the home itself would end the session of an `auth.json` the operator copied there from their own machine. The rename replaces a linked `auth.json` rather than what it points to, so no refusal is needed for one. A sign-in that writes no `auth.json`, as one set to keep it in the system keyring would, changes nothing. Claude Code 2.1.328 replaces its stored sign-in only once the new one's tokens arrived, without revoking it first (**Read** in its bundled JavaScript), so it signs in in its provider home itself.
- A sign-in cancelled with Ctrl+C, or by a hangup, says so, and for Codex that the sign-in stored in the home is as it was. One that succeeded says how to have the engine check the provider again: restart the service, or, with no service, stop `j3-bots serve` and start it again.
- It runs the harness's own interactive sign-in in the terminal: `claude auth login` with `CLAUDE_CONFIG_DIR=<J3_HOME>/providers/claude-code` (the command the engine itself names for a signed-out instance, **Read** at `db51b67`, `ClaudeProvider.ts`), and `codex login` with `CODEX_HOME=<J3_HOME>/providers/codex`. The environment is the one the engine gives harnesses ([Isolation](#isolation)), plus what a sign-in in a terminal uses: `TERM`, `COLORTERM`, `LANGUAGE`, `BROWSER`, `DISPLAY`, `WAYLAND_DISPLAY` and `XAUTHORITY`. Nothing else of the shell reaches it: not a `CLAUDE_CONFIG_DIR` or `CODEX_HOME` the operator set for their own use, nor `ANTHROPIC_*`, `OPENAI_*` or any other variable that changes where a harness signs in or how.
- `--device-auth`, for Codex only, adds Codex's own `--device-auth`. Codex's usual sign-in waits for the browser on this machine to come back to it, which a machine reached over SSH, such as a Pi, does not have; with this flag Codex shows a page and a code to enter on any device instead (**Assumed**, from Codex's documentation). Claude Code is given no such flag.

What happens inside the harness is its own, and none of it has been run here. That Claude Code keeps its sign-in in `.credentials.json` in its home on Linux is **Assumed**, from its documentation. That Codex keeps it in `auth.json` by default is **Read** (Codex 0.170.0, `AuthCredentialsStoreMode` in `codex-rs/config/src/types.rs`). The engine has no sign-in flow of its own for these instances: its `provider.auth.subscribe` answers "This provider does not support sign-in in T3 Code" (**Verified**). That the engine notices a new sign-in only when it checks its providers again, at the latest at its next start, is **Assumed**; the command says that restarting the server makes it check now, and a sign-in from the app asks the engine to check that instance at once (`server.refreshProviders`).

**When both are there**, the connection wins, as far as the configuration J3 Bots writes decides it (**Read** in `Provision.ts`): once a connection is stored, Claude Code's `settings.json` sends every request to the endpoint, with `ANTHROPIC_BASE_URL` and the `apiKeyHelper`, and Codex's `config.toml` selects the connection's model provider with `model_provider = "j3"`, which takes its key from `J3_PROVIDER_KEY`. A ChatGPT sign-in belongs to Codex's built-in OpenAI provider, which that setting no longer selects (**Assumed**). That Claude Code ranks an `apiKeyHelper` above a subscription sign-in is **Assumed**, from its documentation, which does not say whether it ever falls back to the sign-in when the helper fails. No command removes a stored connection, so once one is stored a sign-in is not expected to be used; `provider login` says so before it runs. None of this, nor that a sign-in made this way keeps working inside a J3-owned home past an access token's lifetime, has been run: [open question 2](../open-questions.md#2-does-a-subscription-sign-in-work-inside-a-j3-owned-provider-home) names the run that settles it.

The operator can inspect the engine through T3 Code's own web interface, reached with a pairing link J3 Bots prints on request.

#### Sign-in from the app

In local mode, where the server runs on the computer the app is on, the app signs a harness in itself, so the operator never needs a terminal for it. The server runs the same sign-in for J3 Bots' home for that harness, found on the server's own `PATH`, with no terminal: standard input closed and its output read by the server. The `provider.signIn` RPC starts one, or follows the one under way, and streams where it stands: `starting`, `waiting-for-browser` with the page to sign in on, then `succeeded`, `failed` with a reason, or `cancelled`. `provider.cancelSignIn` stops it and `provider.harnesses` says where the server finds each harness. One sign-in runs per harness at a time; it belongs to the server, not to the socket that started it, so a window that reconnects follows it again and never starts a second one.

- **The page.** The sign-in runs with `BROWSER` naming a small script that writes the address it is given to a file, which the server reads; the address the harness prints is the fallback. The script and its file are in a folder of their own in `<J3_HOME>/providers`, mode 0700 and removed when the sign-in ends: in J3 Bots' private home rather than the system's temporary folder, which is often mounted so that nothing in it runs. **Verified** without a terminal on Linux, with Claude Code 2.1.330 and Codex 0.171.0 and no account: both start, call `BROWSER` with their full authorization address and wait for the browser to return to a server they listen on, Claude Code on `localhost` at a random port and Codex on `127.0.0.1:1455`. That is why the browser has to be on the same computer. Claude Code also prints a `claude.ai` address, which answered a plain request with 403; the address `BROWSER` is given is the one the app opens.
- **Only the harness's own page.** The server passes on only an address on its harness's sign-in pages, by origin and path: `https://claude.com/cai/oauth/authorize`, `https://claude.ai/oauth/authorize` and `https://platform.claude.com/oauth/authorize` for Claude Code, and `https://auth.openai.com/oauth/authorize` for Codex. An address with a user name or password, another port, or any other address the harness prints, such as its documentation or a diagnostic one, is never passed on, whatever it carries. The two `claude.com` pages are **Read** in Claude Code 2.1.330's bundled JavaScript (`CLAUDE_AI_AUTHORIZE_URL` and `CONSOLE_AUTHORIZE_URL`), and the `claude.ai` one is the page it printed; Codex's is the page Codex 0.171.0 gave (**Verified**, both on the test machine above). A harness release that moves its page fails the sign-in with `needs-terminal` until the list in `engine/harnesses.ts` follows it.
- **Opening it.** The client that started the sign-in opens the page once, unless the harness opened it itself, with `window.open`, which the desktop app hands to the system's browser with `shell.openExternal`. A harness is taken to have opened it only where the server could give it no `BROWSER`, on Windows (**Assumed**); a page it only printed elsewhere is opened by the client. The app always offers the page again.
- **A harness that needs a terminal.** One that gives no page within 30 seconds, or ends saying it needs a terminal, fails with `needs-terminal`, and the app says so and offers an endpoint instead. Nobody finishing on the page within 10 minutes gives `timed-out`.
- **Stopping it.** However a sign-in ends (a cancel, either deadline, the server stopping), the harness and every process it started, its process group, are asked to stop with `SIGTERM` and killed with `SIGKILL` 3 seconds later, as every command the engine adapter runs is: a harness that ignores the request cannot hold a cancel or a deadline up, and the next sign-in can start. **Verified** on Linux against a stand-in that ignores `SIGTERM`, as does the child it starts.
- **What it never passes on.** Only the page leaves the server. What the harness prints is kept in memory, for the `needs-terminal` check, and never logged or returned, so a code or token it prints goes nowhere. The log names only the harness and why a sign-in ended.
- **Windows.** The lookup of a harness tries the extensions in `PATHEXT`, and a `.cmd` or `.bat` shim, as npm installs, runs through `cmd.exe`, which Node gives the command line as `cmd.exe /d /s /c "<line>"`. Every word of the line is quoted, the shim's path included, so `& | < > ^ ( )` in a folder's name stay part of the path. What quotes cannot keep from `cmd.exe` is refused rather than run as something else: `%` and `!`, which it would expand, a `"`, and a control character. The command line is checked by a test on every platform; the same test running a `.cmd` in a folder named `R&D^(Co)` through `cmd.exe` runs only on Windows, and passed there (**Verified** on Windows 11). The tests that run a whole sign-in stand in for the harness with sh scripts, so they run everywhere but Windows: a whole sign-in on Windows has not been run.
- **Once it succeeded**, the server asks the engine to check that instance again, and answers with the stored provider connection, if there is one, which the app shows: the connection still wins, as [When both are there](#reaching-the-models) says.

The RPCs are new in 0.3.0 without a protocol version change: a client calls them only on the server on its own computer, which is always as new as the app, and reads a server that answers them with a defect as one that cannot sign in from the app, offering the command instead ([Clients](clients.md)).

## The bot's browser

**Whether a bot may use the engine's browser is its project's agent browser access.** Provisioning turns `enableAgentBrowserAccess` off engine-wide; a bot whose browser switch is on has `enableAgentBrowserAccess: true` in its project's settings overrides, which J3 Bots writes over the socket with `server.updateSettings`. An update replaces a project's whole set of overrides except its `providerInstances`, and `null` removes it, so the adapter reads the set with `server.getSettings` and writes it back with only that key changed, one write at a time (**Read** at `59651c1`, `contracts/src/settings.ts`, `ServerSettingsPatch`). Deleting a bot's project removes its overrides: the engine drops them itself (**Read**, `ProjectService.ts`, `clearProjectSettingsOverrides`). The engine reads the setting when it starts a thread's provider session: a project with access gets the `preview` capability on that session's tool credential (**Read**, `ProviderSessionManager.ts`, `agentAccessSettings` and `prepareMcpSession`). The capability decides whether the engine takes the session's calls to its browser tools (`preview_*`, `t3_preview_list`, `t3_preview_close`); it does not hide them. The engine lists every one of its tools to every session, and refuses a browser tool call from a session without the capability with `PreviewAutomationUnavailableError` (**Read**, `McpHttpServer.ts`, `layerDeferredListing`, and `McpInvocationContext.ts`, `requireThreadMcpCapability`). Codex is also told, in each turn's context, whether it has the browser (**Read**, `CodexAdapterV2.ts`, `buildCodexAdditionalContext`). A provider session that is already running keeps the credential it started with.

**Turning the switch on applies from the bot's next turn; turning it off takes effect at once.** Either is a settings change, like a new model or permission mode, and goes through the same alignment ([Server: sessions](server.md#sessions)). The session row records whether its tools were brought to the browser setting (`sessions.browser`). When they were not, the rotator, between turns, writes the project's access and then asks `configureSession` to reload the tools, which sends `provider-session.detach` for each provider session of the thread the engine has not released: the engine unloads it, and the next turn starts it again and resumes the conversation natively, as a detach does on demand ([Behaviors](#behaviors-j3-bots-designs-around)). A reload is refused while a turn runs (`SessionBusy`) and while the session's background work runs (`BackgroundWorkRunning`), as a permission mode change is, and the bot's conversation is told the change is held. A session opened after the change, and a routine's side session, is opened after its project's access is written, so it starts with the tools the switch says.

That is enough for a browser given, not for one taken away. A provider session keeps the credential it started with for as long as the engine keeps it, which for an idle one is up to 30 minutes (**Read**, `ProviderSessionManager.ts`), and every thread of the project has its own: the bot's session, a delegated task's child, a thread another agent launched there. The engine also starts turns there on its own: a run queued behind the running one, a steer it requeues as a follow-up. So turning the switch off records the bot's Stop in the same transaction ([Server: Stop](server.md#stop)), and the next write of the project's access withdraws it (`withdrawBrowserAccess`): it writes the access off, lists the project's threads with `GET /api/orchestration/shell` (`threads` and `archivedThreads`, each with its `projectId`), and in each sends `thread.stop` with `stopDelegatedTasks` when a turn runs there, which holds the thread's queue, then `provider-session.detach` for each provider session the engine has not released. A detach does not revoke the credential, and no command revokes one (**Read**, `Orchestrator.ts`, `dispatchProviderSessionDetach`; only deleting a thread does). But a thread's next turn has to start a provider session again, which prepares its credential again, and one whose capabilities differ from the project's is revoked and replaced by one without `preview` (**Read**, `prepareMcpSession`). The bot counts each time it lost the browser (`bots.browser_withdrawals`) until a withdrawal succeeds, so one the engine did not take is made again at the next write, which the rotator retries.

**Verified** on the pinned engine with the scripted agent, by three conformance cases that have a thread call `t3_preview_list`:

- A session, before its project allows the browser, after, and after it is turned off again with a reload: refused, taken, refused.
- A delegated child, taken; after a withdrawal, its parent sends it the same task again with `t3_thread_send`, and it is refused. The engine gives a child's new task a new credential on its own, so this case passes without the detach too.
- A run another client queued behind a running turn, after a withdrawal and the queue's release: refused. With the withdrawal's stop but no detach, the same call is taken.

That Claude Code and Codex pick up the new credential the same way is **Assumed**: they start their provider session the same way.

**Every bot with the switch on uses the same profile**, the engine's `default` profile, in `<engine dir>/userdata/server-browser/profiles` (**Read**, `ServerBrowser.ts`). The operator's sign-ins there are every such bot's. **Sign out of all sites** calls `preview.clearProfile` on it ([What J3 Bots uses](#what-j3-bots-uses-and-what-it-leaves-alone)).

**What the browser needs from the host.** The engine downloads `chrome-headless-shell` 157.0.8103.78, about 105 to 128 MB, the first time an agent uses the browser, into `<engine dir>/tools/chrome-headless-shell/<platform>/<version>/` (**Read**, `PreviewBrowser.ts`). The engine has no command that downloads it before that (**Read**, `cli/browser.ts` offers only `browser setup`), so `j3-bots engine fetch` does not fetch it. On Linux it needs a sandbox AppArmor allows (on Ubuntu 23.10 and later, `/proc/sys/kernel/apparmor_restrict_unprivileged_userns` is `1` and only the profile at `/etc/apparmor.d/t3-chrome-headless-shell` allows it), the shared libraries it loads, and a font Fontconfig finds; it refuses its sandbox to root (**Read**, `PreviewBrowserHost.ts`). The engine's own fix is `t3 browser setup --base-dir <engine dir>`, run as root: it writes and loads the profile and installs the libraries and fonts with `apt-get`, choosing among package names with `apt-cache policy` (**Read**, `cli/browser.ts`). J3 Bots does not offer it: it runs, as root, the engine's executable, a file the service's account can change. The adapter checks the same things the same way, reading the files and running the downloaded browser with `--version`, `ldd` and `fc-match`, each time the engine becomes ready and each time a bot is given the browser, and reports them as the engine status's `browser` (`ready`, or `setup-required` with what is missing), which the bot's details show under its switch. `j3-bots doctor` makes the same check and prints the same steps as commands that run, as root, only system tools: the profile's text piped to `sudo tee` and `sudo apparmor_parser -r`, then `sudo apt-get update` and `sudo apt-get install` of the same packages, chosen the same way; or, on a host with `dnf`, `sudo dnf install` of each missing library by the file name a package provides (`libnss3.so()(64bit)`, **Assumed**: not run on Fedora). A library name the browser reports goes into a command only if it has the shape of one, since the browser is a file the service's account can change too. J3 Bots never runs `sudo`. **Verified** on Ubuntu 24.04, with the AppArmor restriction on and a browser lacking a library: `doctor`, run as the service's user, printed these commands, and run as that user under `strace`, everything they ran as root was a file root owns that the user cannot change, `sudo`, `tee`, `apparmor_parser`, `apt-get`, `dpkg` and what those run.

### Its tabs, shown to the operator

The engine runs a headless Chromium of its own, and a bot opens tabs in it with the engine's preview tools (`preview_open`, `preview_act` and the rest) from inside its session, as T3 Code intends. J3 Bots does not drive that browser. It follows the tabs and shows them to the operator, through `BrowserBridge` in `packages/engine-t3`, which nothing outside the package sees past: the server names a tab by a ref of its own, and a client never meets the engine's thread or tab ids. Every fact below is **Read** at `59651c1` unless it says otherwise, in `apps/server/src/preview/` (`ServerBrowser.ts`, `ServerBrowserStream.ts`, `SessionControl.ts`).

**Which tabs.** The adapter lists only tabs that an agent opened in the engine's own browser: a snapshot with an `automationOwner` and the `server` runtime. A tab with no agent owner is taken by the first viewer that may act on it as soon as it attaches, so a viewer J3 Bots opened would take it from whoever had it. A pop-up a bot's page opens is a tab of its own with the same owner (`ServerBrowser.ts` L1715-1724), so it is listed as one, and the engine's `popup` frame, which it sends only for tabs with no agent owner (L1732), is never needed.

**Following them.** `BrowserBridge.tabs` subscribes to `subscribePreviewEvents` first, then lists each live session's tabs with `preview.list`, and applies the events after the list: `opened`, `navigated`, `resized`, `failed` and `closed`. A list's revision is a floor: an event older than the list it follows changes nothing. The feed starts once the engine is ready and starts again two seconds after it fails, from a fresh list. The subscription is asked for before the list, but the engine gives no sign of when it holds: the stream is a `Stream.fromPubSub` with no first item (**Read** at 59651c1, `preview/Manager.ts` L133-134 and `ws.ts` L3298), so the adapter cannot wait for it. An event the engine publishes after it read the list but before the subscription took hold would be missed until the feed starts again, and that tab would show as it was listed until its next event. The feed starts when the engine is ready, before a bot can have a tab, so the gap matters only when the feed starts again while tabs are open. That the engine sets the subscription up before it answers the list asked for after it is **Assumed**; it was not seen to miss an event.

**One stream per viewer.** Each J3 Bots viewer is one connection to `/api/preview-stream/ws?threadId=&tabId=&maxWidth=&maxHeight=&quality=&wsTicket=`, with a ticket from `POST /api/auth/websocket-ticket/media` bought for it. What the stream carries:

- **Pictures.** A JPEG is one binary message, and the engine sends the next only once the viewer answered `{"type":"ack"}` (`ServerBrowserStream.ts` L45). The server acknowledges only once its client drew the picture ([Server: the bot's browser](server.md#the-bots-browser)). Chromium sends a picture only when the page repaints, so the engine gives a new viewer one still when it attaches (`ServerBrowser.ts` L3369-3371) and drops that still without a word when its capture fails (L3300-3314). A viewer of a page that does not repaint then gets no picture at all until something changes on the page. **Verified**: on a page that never repainted by itself, 7 of 18 conformance runs got the viewer's `control` and `viewport` but no picture. That a failed still caused it is **Assumed**: it is the only path in the source that leaves such a viewer with nothing, and why the capture would fail is not known. A client shows that it waits for the first picture rather than assuming one comes.
- **Text frames.** `viewport`, `control` (who acts: `agent`, `you`, `another-viewer` or `unclaimed`, a generation that grows with each change of hands, and the dialog the page waits on), `probe`, the agent's `pointer`, `clipboard`, `download`, `fileChooser` and `popup`. The adapter decodes each with a schema. It passes on the first four, with `agent` read as the bot and `pointer` as the bot's cursor, which the engine sends only while the agent acts (L2433-2444). It drops the rest, and anything that does not decode, unread.
- **Close codes.** `4404` when the tab is gone (L31). `4503` when the browser cannot start until the host is set up, with a JSON reason that names what it lacks (`PREVIEW_STREAM_HOST_SETUP_CLOSE_CODE`, L103-124). `1012` when the viewer should connect again (L176). The adapter reads any other code as a lost stream.
- **Input.** `mouse`, `wheel`, `key`, `text`, `navigate`, `history`, `reload`, `probe`, `dialog`, `takeControl` and `releaseControl`, which the adapter writes from the contract's own input frames.

**Control.** A human who takes a tab holds it until they release it or their viewer disconnects, which releases it (`SessionControl.ts` L189-205). While a human holds it, the agent's actions on the tab fail with `humanControl` (`SessionControl.ts` L113-127, `ServerBrowser.ts` L2724-2745), and the agent's preview tool answers "A human controls this browser tab. Wait until they release control." (**Verified** at the pin, by the conformance case below). Reads (`status`, `snapshot`, `waitFor`) still work. So J3 Bots keeps a held tab's engine viewer open for as long as the operator's device keeps the tab, and closing that viewer is what gives the tab back to the bot.

**Checked on the pinned engine.** The real-engine conformance case "streams a bot's tab to a viewer, which takes it from the agent, uses it and gives it back" drives the adapter as the server does, with the scripted agent's `browse` script:
- the agent opens a local page;
- the tab is listed and a viewer gets JPEG pictures;
- the viewer takes the tab, and the agent's next action is refused;
- the viewer clicks into the page and types, and the page receives the text;
- the viewer releases the tab, and the agent's next action works.

All of this is **Verified**.

**Reading one tab.** `BrowserBridge.readTab` lists the tab's session with `preview.list` and answers with the tab's committed page, from the snapshot's `navStatus`: blank, loading an address, loaded at one, or failed, or none when the tab is gone. The server reads it to fill a login, apart from the tab feed, which follows the events and can trail the engine. The engine reports `Loading` when the main frame sends a navigation request, and `Success` at the frame's address on its `load` event and on each main-frame navigation that loads no document, so a `history.pushState` shows as loaded at the new address with the same document (**Read** at `59651c1`, `ServerBrowser.ts` L1253-1291). The snapshot says nothing of which document is shown. So the fill takes only `Loading`, a failure or a closed tab as a page that left ([Server: filling a login](server.md#filling-a-login)).

**The server as a viewer.** To fill a login, the server opens a viewer of its own, as a device's would be, takes the tab, sends `text` and `key` input and closes the viewer, which gives the tab back. The engine does not tell a viewer which element has focus or in which frame: the `probe` frame answers a point with whether it is over an editable element, not which (**Read** at `59651c1`, `ServerBrowserStream.ts`). So the server types where the page's focus is, as a person's keyboard would.

**Input runs in order, and a release drops what waits.** The stream forks each input message (`ServerBrowserStream.ts` L188), and the engine runs a holder's input, `probe` included, one action at a time through the tab's control queue (`ServerBrowser.ts` L3430-3434). An action records the control epoch when it is queued and fails when the epoch has moved by the time it runs; a release moves the epoch (`SessionControl.ts` L84-99). So input still waiting when the viewer releases the tab is dropped, and the answer to a `probe` sent after other input says that input ran. All **Read** at `59651c1`. That the forked messages reach the queue in the order they arrived is **Assumed**: each fork runs to the queue without waiting on anything first.

## Behaviors J3 Bots designs around

Each of these was found by reading or running the engine and would break a naive design.

**An engine restart cancels what was running and holds what was queued.** The running run ends `cancelled` (**Verified** on Claude Code), and the adapter reports it `interrupted`, also after a crash (**Verified** on the scripted agent by the conformance suite). A pending approval or question ends `cancelled` with `responseCapability: {type: "not_resumable"}`, so its card must close. Runs that were queued stay queued with `queueHeld: true`, and `queue.resume` starts them. **Verified**. A provider error holds the queue the same way, and a new run queued behind a held queue is held too; a usage limit makes the queue wait without holding it, until the reset; a message stamped as coming from a user on a web or mobile client releases a held queue (**Read** at `db51b67`, `Orchestrator.ts`, `startNextQueuedRun` and `message.dispatch`). A queued run that would move the thread to a new provider session, after its model or provider changed, while the replaced session still runs background work holds the queue too, and holds it again on every resume until that work ends (**Read**, `Orchestrator.ts`, `startNextQueuedRun`, the `restart_and_resume` switch). J3 Bots resumes a held queue once per hold the adapter reports, which is why the two cannot loop. The adapter reports a hold when the `queueHeld` flag of the waiting runs goes from unset to set. Why the engine holds the queue again after a resume is not on the wire: whether the replaced provider session still runs background work is a runtime probe (**Read**, `sessionHasBackgroundWork`). So the adapter reports such a hold again only once something has moved: a turn started or finished, or a piece of background work the thread showed live at the new hold ended. This is an approximation of the engine's own reason, and its failure mode is a queue left held until the next turn moves, never a loop.

**A start can be queued.** `start_immediately` does not refuse a thread with an active run: it queues the new run behind it, exactly as `queue_after_active` would, and the active run can be one the engine started itself (**Read** at `db51b67`, `Orchestrator.ts`, `message.dispatch`: `shouldQueue` when an active run exists and the mode starts or queues a run). So the adapter's busy check is only a pre-check, and a start can be accepted as `queued`.

**A steer does not always steer.** The engine turns a steer into a new turn when the target run or its provider turn has already completed, and queues it behind the running turn when the provider can neither steer nor restart, or the target is a compaction or a sign-out (**Read** at `db51b67`: `Orchestrator.ts`, `CommandPolicy.ts` `resolveMessageDispatchIntent`). A steer to a run whose provider turn has not started yet becomes a queued run marked to steer that run when it starts (`steerWhenReadyRunId`); when the target's provider turn starts, the engine cancels the carrier and steers the same message in (`queued-message.promote-to-steer`), and if the target ends first the carrier runs on its own (**Read**). A steer still pending when its run settles is dispatched again by the engine as a follow-up run with the same message id, in its place among waiting runs, unless Stop ended the run: then the steer is marked cancelled and the engine adds a "Steer delivery not confirmed" notice to the run (**Read**, `requeueUnreadSteers`, run after the run settles, before each `message.dispatch` and at recovery). A follow-up of a cancelled run is queued held. When the engine promotes a carrier to a steer, it cancels the carrier run; the adapter reports neither the carrier nor its cancellation. A steer is refused with a rejected receipt when its run is anything but running: Stop already reached it, it waits in the queue, or it ended any way but `completed` (**Read**, `dispatchSteerIntoRun`; only a `completed` target is turned into a new turn first). So a late steer after a Stop is `DispatchRejected`, not a new turn. A run's `waiting` status is not a request: it means its provider turn ended while background work keeps the run open, and a steer to it becomes a new turn (**Read**, `RunExecutionService.ts`).

How a provider takes a steer decides which of these happen (**Read** at `db51b67`, the adapters' `capabilities`, `CommandPolicy.decideSteeringExecution`):

| Provider | Steers a running turn | Restarts it with the steer | What a steer becomes |
| --- | --- | --- | --- |
| Claude Code | Yes | No | Taken in the running turn, or requeued if the turn ends first |
| Codex | Yes | Yes | Taken in the running turn, or requeued if the turn ends first |
| ACP agents, including the scripted agent | No | Yes | The engine interrupts the run and starts a new attempt of the same run with the steer as its message: one turn, taken unless Stop ends it first |
| GitHub Copilot through the ACP registry | No | No | A new turn after the running one (`new-turn`) |

**Stop holds the queue; it does not empty it.** `thread.stop` interrupts the active run and marks every queued run `queueHeld`, cancelling only buffered provider notifications; when no run is active but the latest run still has background work pending, it interrupts that run; on a thread with nothing active it holds the thread and turns its usage-limit resume off (`holdStoppedThread`, which sets `limitRecovery.autoResume` to false). Either way `holdStoppedThread` also ends the thread's pull-request watches (`Orchestrator.ts:13164-13176`). Its reply comes before the interrupt has ended anything (**Read** at `db51b67`, `Orchestrator.ts`, the thread stop path). J3 Bots' Stop must end what it dispatched, so the adapter follows `thread.stop` with `queued-run.cancel` for each queued run of the thread. Between the two, a message the engine counts as an operator's releases the hold: one stamped `createdBy: "user"` with `creationSource` `web` or `mobile` (**Read**, `sentByUserFromClient`). The engine stamps every message sent over `/ws` as the user's but keeps the `creationSource` the client sent (**Read**, `ws.ts`, `withCreationProvenance`), and the adapter sends `server`, so its own dispatches release no hold. Another client's message can, so the server still sends a session no dispatch while a Stop of it is unsettled, and the TestEngine models the release.

**A snapshot has no history.** A thread snapshot is the current projection with the highest event sequence of the thread (**Read** at `db51b67`, `ProjectionStore.ts`, `getThreadSnapshot`). Runs, turn items and requests carry their state but no sequence of their own, so after a snapshot the adapter cannot tell which runs ended after a given cursor. Its replacement lists more than what was missed, and the server's reconciliation tolerates repeats.

**The engine names the attachment.** `attachments.createUploadUrl` mints the attachment id and returns an upload URL that is valid for ten minutes; the bytes are posted to it once, and posting different bytes under the same id fails (**Read** at `db51b67`, `assets/AttachmentUpload.ts`, `packages/contracts/src/assets.ts`). Its input takes a trimmed name of 1 to 255 characters and a trimmed media type of 1 to 100; an image must name one of the four inline types exactly and be 1 byte to 10 MiB, any other file 1 byte to 50 MiB (**Read**, `AttachmentCreateUploadUrlInput`). The `message.dispatch` command puts no limit on a message's text (**Read**, `orchestrationV2.ts`), but a start and a steer both refuse text over 120,000 characters once assistant-quote links (`[Assistant quote](t3-citation://v1/…)`) are expanded: a start fails its turn with "Message is too long", a steer is refused (**Read**, `PROVIDER_SEND_TURN_MAX_INPUT_CHARS` in `chatAttachment.ts`, `ProviderTurnStartService.ts:680`, `Orchestrator.ts:6223`). An upload no message names is removed after 24 hours, and a claimed upload stays as the source of copies until then (**Read**, `attachmentStore.ts`). A message carries at most 100 files; an image the model sees inline (GIF, JPEG, PNG or WebP) is at most 10 MiB, all of them together at most 80 MiB; other files 1 byte to 50 MiB (**Read**, `packages/contracts/src/chatAttachment.ts`).

**Interrupting a run loses a delegated task's result.** A delegated task's completion is delivered to the parent run that started it. `run.interrupt` always stops the run's remaining work, and without a held queue that disposes of the run's delegated-completion cohort as stopped, so the completion is never delivered (**Read** at `db51b67`, `Orchestrator.ts`, the `run.interrupt` path and `stopRemainingWork`). J3 Bots never interrupts a run to end it after its delivery. Only the operator's Stop ends a run.

**`send_to_user` only echoes.** The engine's tool returns its input with "Shown to the user" and does nothing else; its text exists only as the tool call in the turn's items (**Read** at `db51b67`, `apps/server/src/mcp/toolkits/message/handlers.ts`). The adapter reads it from there as host speech.

**Secret requests have their own answer path.** A `request_secret` call becomes a `secret_request` turn item with a label, a reason, an optional URL and placeholder, and a status (pending, saved, declined, cancelled). It is answered by the `secrets.answerRequest` RPC with the thread, the item and `save`, `decline` or `reference`, not by `runtime-request.respond`; a second answer fails as already answered (**Read** at `db51b67`, `packages/contracts/src/secretRequest.ts`, `orchestrationV2.ts`, `rpc.ts`, and `apps/server/src/ws.ts`).

**The engine starts runs nobody dispatched.** Four cases are known. If background work was running when the engine restarted, the engine sends the session its own continuation message (`createdBy: "agent"`, `creationSource: "server"`, beginning "Note: the T3 server restarted") and a new run starts (**Verified** on Claude Code); J3 Bots turns this off ([Provisioning](#provisioning)). If a command the harness ran in the background finishes after its turn ended, the harness's notice arrives as a new run (`createdBy: "agent"`, `creationSource: "provider"`; **Verified** on Claude Code). So does a Claude Code monitor's event, which comes as a bare turn with no notice (**Read** at `db51b67`, `ClaudeAdapterV2.ts:6207-6208`; the `claude_background_task_wake` and `claude_background_monitor_wake` fixtures). Each `turn-finished` says whether the turn handed off to such work (`backgroundWork`): it left a live subagent, a command whose completion wakes the session, or a task the provider reports under the turn's run that holds the agent's completion by the engine's rule, one the agent marked `awaited`, or a subagent or background task (**Read**, `orchestrationV2PendingBackgroundWork.ts:102-121`, `backgroundWorkHoldsCompletion`; `contracts/orchestrationV2.ts:1107-1111`). The stream carries a provider's tasks without their run, so the adapter attributes each to the run it first appeared under, as the engine's projection does (**Read**, `ProjectionStore.ts:936-954`, applied at `:1153-1159`). A background shell or a monitor the agent did not mark awaited may still wake the session, but it is not a hand-off: it is as often a dev server left running as a wait, and the server's `undelivered` wake then asks the bot to reply ([Server](server.md#4-the-turn-is-observed-and-admitted)). At a usage limit's reset the engine dispatches "Continue where you left off." with `usageLimitContinuationOfRunId` naming the thread's latest run, if that run failed at the limit, the reset is less than a day past, and the thread is not archived, settled, snoozed or waiting on a request (**Read** at `db51b67`, `UsageLimitRecoveryWorker.ts`, `limitRecoveryCommand`). A scheduled task bound to the thread sends its prompt with `mode: "queue"`, which queues a run behind whatever runs or is held (**Read**, `ScheduledTaskService.ts:1062-1090`); J3 Bots schedules none, but the engine's own tools let an agent or the operator make one. Every run names the message that started it (`userMessageId`), but a provider that steers by restarting moves that field to the steer's message (**Verified** on the scripted agent). The adapter matches a run to its dispatch by the run's first user-message item that is not a steer, which keeps the message of the first attempt, and falls back to `userMessageId` only for a run with no message item yet. A usage-limit continuation is reported as a `continuation` of the run it names; any other run is a `background` turn. Neither closes a wake by itself, and anything the bot says in them still comes through `say`.

**Only a delegated task's wake names the turn it continues.** A `background` turn's `origin` is the turn whose work woke the session, when the engine says which. Only the engine's own delegated tasks do: the message their completion starts a run with carries the run that delegated them (`delegatedCompletion.parentRunId`) (**Read** at `db51b67`, `ProviderContinuationService.ts:177-192`). That holds only for a completion that starts a run: one arriving while any run of the session is running is steered into that run instead, which J3 Bots does not see yet (**Read** at `59651c1`, `Orchestrator.ts:7631-7673`; [#98](https://github.com/JPSAUD501/j3-bots/issues/98)). The engine records that message in the command that creates the run, after `run.created`, whether the run starts at once or waits in the queue (`Orchestrator.ts`: the queued run at `:8128` and its message at `:8184`, a start at `:8617` and `:8669`). A run that starts at once is `starting` until a later command, so its origin is known when its turn starts; a queued one is created before its message, so the adapter holds its `turn-queued` until the message has arrived. The adapter records each run's origin from the message the run opened with, as the run's first record names it, and keeps it for the life of the turn: a steer adds an item to the run, and a steering restart moves the run's `userMessageId` to the steer on the same run (`:6805-6815`), and neither changes the turn's cause. **Verified** on release `4969` with the scripted agent, by the conformance suite: the turn its delegated task's completion starts names the turn that delegated it. A harness's own wake carries no run id: the run carries no link to another (`contracts/orchestrationV2.ts:766-803`), and the message the engine dispatches for it carries only a notice, whose source says what kind of work reported (a command, a monitor, a subagent, a background task) and, for a single native subagent, may name the child thread it ran in (`childThreadId`), but never the run or task of the engine's that started it (**Read**, `ProviderContinuationService.ts:247-264`, `ProviderContinuationRequests.ts:15-35`, `notification.ts:136-170`; Claude Code's at `ClaudeAdapterV2.ts:10198-10253`). Its turn's `origin` is `null` (**Read**). A turn another client started has no origin either (**Verified** on release `4969` by the conformance suite, which starts one; it does not provoke a harness's wake). For a harness's wake the server knows which earlier turns still had work pending, from `synchronized`, but not which of them woke the session.

**Tool calls are turn items.** A call to an MCP tool becomes a `dynamic_tool` turn item, `running` while the call is in progress, with the call's input: Codex names it `j3.say` (`CodexAdapterV2.ts`, `projectCodexDynamicToolItem`), Claude Code `mcp__j3__say` (`ClaudeAdapterV2.ts`, `ensureToolCallStarted`), and ACP agents carry the MCP identity (`provider-acp`, `adapter.ts`). **Read** at `db51b67`. Only ACP records a call's input more than once in a way that changes it: an agent may report a call with no `rawInput`, which the engine records as `{}`, and send its arguments in a later `tool_call_update` when the call runs; the engine merges the update and records the item again with them (`adapter.ts:4657-4658`, `:4711`; `runtimeModel.ts`, `mergeToolCallState`, L956-976). Codex records the input from the item's `arguments`, the same on `item/started` and `item/completed` (`CodexAdapterV2.ts:588`, `:5413`, `:5568`). Claude Code keeps the input a call started with: `ensureToolCallStarted` returns an existing call unchanged but for its presentation (`ClaudeAdapterV2.ts:8596-8624`). The adapter reports every change of an open call's digest all the same, whichever harness made it. The item is committed by the engine while the harness calls the tool, with no ordering against the request the `j3` bridge receives, so it may appear after that request. An input whose JSON exceeds 16,384 bytes is replaced on the wire by a one-line summary (**Read**, `WireProjection.ts`, `summarizeDynamicValue`), so its digest could never match the bridge's; J3 Bots' tool schemas refuse arguments over 12,288 bytes and tell the bot to split them. A Claude Code subagent's tool call is recorded on the subagent's own child thread, with no run (**Read**, `ClaudeAdapterV2.ts`, `startSubagentToolCall`): it never appears in the bot's turn, so the server refuses it as matching no turn. **Verified** on `0.1.11`: a Claude Code subagent's call to `say` was refused as matching no turn. That Codex records a subagent's call the same way is **Assumed**. That the item's input equals the arguments the bridge receives is **Verified** on `0.1.11` for Claude Code and Codex on the real-harness tier ([Upgrading the engine](#upgrading-the-engine)): the calls checked matched by digest, one of about 11,900 bytes included. For an ACP agent it is **Verified** on `0.1.11` with the scripted agent, which reports each call with `rawInput` `{server, tool, arguments}` and calls the bridge itself: `create_bot`, `start_room` and `say` matched by digest in `apps/server/scripted/team.test.ts`.

**A `j3` tool not pre-approved asks, and a long call is cut off at the harness's timeout, whatever it reports.** **Verified** on `0.1.11` with Claude Code 2.1.330 and Codex 0.171.0, through the adapter, with a test MCP server in the bridge's place and a scripted model endpoint:

- **Approvals.** With only J3 Bots' own names pre-approved, `say` ran with no request in Supervised, and a connector tool (`notion__search`) opened an approval: on Claude Code a `command` approval naming `mcp__j3__notion__search` and its input, on Codex a `tool` approval asking to let the `j3` server run it. In Full access neither asked.
- **New tools mid-session.** On `notifications/tools/list_changed`, Claude Code lists the tools again at once, and a new tool reaches the model from the bot's next turn, not later in the same turn. Codex without `mcp_tool_list_changed` never listed again, not even at the next turn; with it, Codex listed again at once and the model called the new tool in the same turn.
- **Long calls.** A call of 150 seconds completed on both at their default timeouts. With a timeout of 40 seconds, a call of 60 seconds was cut off on both, also while the server reported progress every five seconds: progress extends neither harness's timeout. When it cut a call off, each harness sent the server `notifications/cancelled` for it. So the bridge relays no progress: the harness's timeout is set above the bridge's longest deadline, and a cancellation reaches the server ([Server: bot tools](server.md#bot-tools)).
- **Events.** The engine's `tool-call` events for a connector tool carry its bare name (`notion__search`) and its input digest, as for `say`. On Codex the call runs inside its code-mode `exec` tool, and the engine closed the `tool-call` when `exec` yielded, after about 30 seconds, not when the MCP call returned. The server matches a call while it is open, at its start, so that close does not affect the match.
- **What the tools cost.** On Claude Code with a provider connection, every tool is in each request, none deferred: the request's tool definitions came to 112,902 bytes with J3 Bots' own tools, 129,262 with 20 connector tools of about 800 bytes each, and 162,022 with 60, so 60 such tools add about 49 KB, some 12,000 tokens at four bytes a token (the ratio is **Assumed**). With `ENABLE_TOOL_SEARCH=true`, Claude Code deferred every MCP tool, J3 Bots' own included, and the 60 added about 1.3 KB. Codex defers MCP tools behind its code-mode tools: its request's tool definitions were 29,402 bytes whatever the count. How a subscription's sign-in changes Claude Code's deferral is not measured.
- **Tool search is on.** So every Claude Code instance runs with `ENABLE_TOOL_SEARCH=true` in its environment ([Provisioning](#provisioning)), and a connector's tools are found when a turn needs them instead of filling each request. J3 Bots' own tools ask to stay loaded with `_meta["anthropic/alwaysLoad"]` in their listing, since a bot speaks only through `say`; and `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH=8192` keeps a description whole up to 8,192 characters, where Claude Code would cut at 4,096, since `set_routine`'s is longer. Both are **Assumed** from Claude Code's documentation, not run. Codex ignores both.

**Provider sessions are unloaded after 30 minutes idle.** The next wake starts a new provider process and resumes the conversation natively. This is the normal state for a bot, not an error. It is also when a changed system-prompt file takes effect. **Read**. `provider-session.detach` unloads one on demand, and the next turn resumes natively. **Verified**.

**Supervised Codex cannot write.** T3 Code runs a Codex thread in `approval-required` mode with approval policy `untrusted` and a read-only sandbox (**Read**). An approval lets the command run, but still inside that sandbox: an approved write failed with "Read-only file system" (**Verified**). `auto-accept-edits` gives a workspace-write sandbox (**Read**). See [Security](security.md#permission-modes).

**Claude Code deletes its own transcripts after 30 days.** A bot that was silent for a month cannot resume natively; the engine falls back to a new session with a summary. J3 Bots does not depend on a session living that long: it can rebuild a session from memory and the recent conversation at any time.

**Cost per dispatch grows with the number of runs in a thread** unless a compaction exists. J3 Bots rotates a bot's main session after 200 turns, a provisional threshold. See [Server](server.md#sessions).

**There is no admission control.** The engine will start as many provider processes as it is asked to. J3 Bots' wake dispatcher enforces the concurrency limit.

**Migrations go forward only.** Once an engine upgrade commits, the older version refuses the database. `j3-bots update` copies the engine's database files before it starts a release pinned to another engine, and puts them back if that release does not become ready ([Upgrading the engine](#upgrading-the-engine)).

**Messages sent through `/mcp` get a note prepended** saying they did not come from the user. Messages sent through the client RPC do not. J3 Bots uses the client RPC and writes its own wake envelope.

**The engine always adds its own instructions and tools.** Whenever its MCP server is attached to a session, which is always, T3 Code adds its own text: on Claude Code appended to the system prompt (6,245 bytes at `9bb92a4`, **Read**); on Codex sent as five `additionalContext` entries with every `turn/start` (6,001 bytes with device access off, **Verified**). It covers delegation and subagents, thread tools, secret requests, charts and the preview browser, pull request linking, and, for Claude, a tool for showing text mid-turn. Its tool list comes with it. There is no setting that removes either; only the device section can be turned off. J3 Bots' base prompt names the parts it replaces. See [Prompt architecture](../prompts/architecture.md#coexisting-with-the-host).

**A session may list a skill only from its next turn.** Claude Code 2.1.332 keeps a file watcher on its skill and command folders and reloads them on a change, and Codex 0.172.0 has a skills watcher that clears its skills cache (**Read** in each release's shipped build). That a session already running offers a skill linked meanwhile is **Assumed** for both, not run. So J3 Bots restarts no session for a skill, and tells a bot it has a skill it saved from its next turn.

## Footprint

Measured on 2026-11-20 on release `4969`, on an x86-64 Linux laptop, with providers reached through an API proxy. The target host is a Raspberry Pi; these numbers bound the design until they are repeated there. **Verified**.

| What | Resident memory |
| --- | --- |
| Engine, idle, no session loaded | 450 to 490 MB |
| Claude Code, per loaded session | about 230 MB, one CLI process per session |
| Codex, per instance | about 150 MB, one app-server shared by all its sessions |
| `j3` bridge, per loaded session, both harnesses | one process each; 50 MB when written as a plain Node script |

A turn adds no measurable memory beyond its loaded session. Codex keeps a session's bridge process until the session unloads, so a host with many recently active bots holds many bridges: the bridge must be a thin relay, and its runtime is chosen for size.

| Trivial turn ("reply ok"), input tokens per model call | Claude Code (Haiku 4.5) | Codex (gpt-5.6-luna) |
| --- | --- | --- |
| Under the engine | 59,100 to 59,800 | 14,800 |
| Of which cache reads when the session is warm | 59,100 to 59,700 | 12,900 to 14,600 |
| The same harness alone, same home, same prompt file | 37,400 | not measured |

About 22,000 of Claude Code's tokens per call are the engine's text and tool list. A turn that calls a tool pays the whole context once per model call. On a turn that resumes a session, the engine reports the resumed transcript's earlier usage as `otherUsage`; it is not new spend and is not counted.

Latency was dominated by the provider: about 4 seconds from dispatch to a one-word answer, with the provider session loaded or not. Starting the run took 0.1 to 0.3 seconds on Claude Code and up to 0.9 on a cold Codex instance.

The browser was measured on 2026-11-23 on an x86-64 Ubuntu 24.04 virtual machine with 8 cores of an AMD Ryzen 9 9950X; no arm64 machine was available, so on a Raspberry Pi the CPU figures will be several times higher. It was the engine's own `chrome-headless-shell` 157.0.8103.78, started with the engine's flags (no GPU, device scale factor 2) on a 1280 by 800 tab, and a viewer took its screencast the way the engine's viewer does (JPEG at quality 70, at most 1280 by 800, each frame acknowledged). The figures are the browser's processes only, by proportional set size; what the engine spends relaying frames to a client is not in them. **Verified**.

| One tab in the engine's browser | Memory (PSS) | CPU |
| --- | --- | --- |
| A static page, nobody watching | 196 MB, 8 processes | none |
| A static page, a viewer attached | 219 MB | none: one frame, then a frame only when the page changes |
| A page that animates without pause, a viewer attached | 231 MB, 245 MB at peak | 1.75 cores, at 40 frames a second |

A page that keeps changing is the worst case: every change is painted in software at twice the tab's size and encoded as a frame. A page at rest costs memory only.

## Upgrading the engine

1. Change the version and commit in `engine.json`, run `pnpm vendor:t3-contracts` (which also writes the new digests), and move the catalog's Effect packages to the versions T3 Code pins at that commit. The protocol changes show up as type errors in `packages/engine-t3`. Some do not: the adapter tells a provider the engine has not checked yet by the shape of the engine's placeholder ([Providers](#the-adapters-interface)), so read again `makePendingClaudeProvider` and `makePendingCodexProvider`, the branches of the Claude Code and Codex checks that do not find the harness, the background first check in `makeManagedServerProvider`, and the probe timeouts that `FIRST_CHECK_BUDGET` must stay above, and change `notCheckedYet` and the budget in `Providers.ts` if they moved. Read `BUILT_IN_DRIVERS` in `apps/server/src/provider/builtInDrivers.ts` too: each driver there with a default instance must be in `ENGINE_DEFAULT_INSTANCES` in `Provision.ts`, or the engine runs it on the operator's own setup ([Isolation](#isolation)).
2. Run the adapter conformance suite against the new version (`pnpm --filter @j3-bots/engine-t3 test:conformance`). It installs the pinned engine into an isolated data directory, starts it through the adapter layer with only the scripted agent, and runs the same scenarios the TestEngine passes: a dispatch key applied once and a recovery into its own busy turn accepted, a start refused in a busy session, a turn caused by its dispatch and its end, a steer into a running turn and into one the engine has only just begun (both taken by restart, with no event naming another turn), a resume from inside the batch that ended a steered turn that still delivers the steer, a late steer that becomes a turn of its own, a steer into a stopped turn refused by name on the first send and on recovery, Stop of a running turn and of an idle session, a recovered start queued behind a running turn that Stop cancels before it starts, settled by its cause, an approval held until answered, a question, a secret taken once, speech through the engine's own tool, a turn nobody in J3 Bots dispatched reported as background with no origin, a turn the engine's own delegated task woke reported as background naming the turn that delegated it, resuming from a cursor, and a synchronization marker on two streams that follows an answer the engine had recorded. Three scenarios need the real engine: a crash during a turn, after which the stream resumes, the cut turn is reported `interrupted`, the turn waiting behind it is reported held, resumed once and runs, and the next turn completes; a new J3 Bots server process, which recovers an earlier key and resumes an old cursor by replacement; and a resume the engine answers with a snapshot, after more events than it replays, which the stream tells as a `replaced` listing the turns that ended in the gap. It also reads a settled thread's shell through `getThreadFamily`, as the adapter does for undecidable tools, and judges it with the adapter's rule, and reports a delegated task still running after its turn ended as that turn's pending work until a Stop ends it, leaving no turn to run. **Verified** on releases `4969` and `0.1.11`, with the adapter as this page describes it: the whole suite passes, the background-work cases included. Then run its policy case, `pnpm --filter @j3-bots/engine-t3 test:conformance:policy`, which needs sudo: it starts the engine under a policy that limits threads to Supervised, written in a private mount namespace, as a new file on a fresh memory file system mounted at `/etc/t3code` inside an overlay over `/etc`, so no other T3 Code on the machine sees it, and a symbolic link the machine's `/etc/t3code` may hold is never written through (`conformance/with-policy.sh`). It fails if the engine stops refusing a mode above its ceiling without a receipt, renames the error the adapter tells that refusal by, or stops reporting the ceiling in its config. It also opens a session in Full access with no policy, starts the engine again under the policy, and checks that a turn there is refused on a first send and on recovery, with nothing kept for the key, until the session is lowered; for that, the script hands the policy's folder in the namespace to the suite's user, which rewrites the file it removed. **Verified** on `0.1.11`. Work an old provider session runs after another client's fresh-context start is not in it, since J3 Bots never starts one: the adapter's own cases cover it, from the engine's events as **Read** above. Not yet in the suite, so checked by hand on an upgrade: a start queued behind a turn the engine began, Stop with a held queue and a message sent mid-Stop, a turn that fails before it starts, and an attachment. **Verified** by hand on `0.1.11`, through the adapter on the scripted agent: a start sent while another client's turn was beginning is `queued` and delivered by a turn of its own after that one (sent once the adapter has seen the turn, it is refused as busy instead); Stop interrupts the running turn and cancels the turn waiting behind it, a start J3 Bots sends during the Stop is refused as busy, and one a web client sends then is queued and cancelled with the others; a turn whose provider cannot open a session ends `failed` (`provider-error`) with no `turn-started`; a dispatch carrying a staged file is accepted and its turn completes. **The real-harness tier** needs a model, so it runs on Claude Code and Codex before a release rather than on every upgrade: a `j3` tool call recorded and closed with the digest the bridge computes, an input just under J3 Bots' cap matched and one over it refused, a call from a subagent refused as matching no turn, and steers taken in the running turn, requeued unread or dropped by Stop, which need a provider that steers without restarting. **Verified** on `0.1.11`, with Claude Code (`claude-haiku-5-5`) and Codex (`gpt-6-luna`) behind a proxy endpoint: the `j3` calls checked matched by digest and closed with their turn; on both, a call of about 11,900 bytes matched and one of 12,914 bytes was refused by the cap; a Claude Code subagent's call was refused as matching no turn; a steer was taken in the running turn on both, and one sent while a Claude Code tool was still running was dropped by Stop. Not exercised on `0.1.11`: a Codex subagent's call (the bot declined to start one), a steer requeued unread (in four tries per harness, a steer sent just after the bot's last message was still taken in the turn), and a Codex steer dropped by Stop (Codex took the steer at once, before the Stop).
3. If it passes, release. On the operator's machine, `j3-bots update` moves to it ([decision 0016](../decisions/0016-an-update-keeps-a-snapshot-to-roll-back-to.md)): the new release's `j3-bots engine fetch` installs its engine beside the running one while the old server runs; then the update stops the service, copies J3 Bots' database and the engine's state into a snapshot (`statev2.sqlite` with its write-ahead log, and the engine's `settings.json`, the files the adapter names in `stateFiles`), and starts the new release, which must report its engine `ready` within five minutes. `ready` means the engine answers with the pinned version and orchestration protocol in its descriptor. The [upgrade check](../operations/releasing.md#the-upgrade-check) runs this through the service with turns before and after, a rollback and a second update, and checks that the bot's next turn runs in the same engine thread. **Verified** on a VM from a release pinned to `4969` to one pinned to `0.1.11`, back and forward again: every entry kept, the same engine thread throughout, and the engine's descriptor reporting database migration 102 on both, so that move adds no migration.
4. If the new release does not become ready, the update stops it, puts the snapshot back and starts the previous release, whose engine it keeps installed: an update leaves the engine runtimes of the two releases it moved between. `j3-bots update --rollback` does the same on request, after the new release has run.

The conformance suite is the adapter's main test. It exercises the real protocol against the real server, which is the only thing that can tell us an upgrade is safe.

**The scripted agent.** The suite spends no allowance. Its turns run on a small Agent Client Protocol agent that J3 Bots owns, registered in the engine as a provider instance with driver `acpRegistry` and `{source: "local", commandPath, commandArgs}`. It needs no model and no network. A directive in the request (`[[script:<name>]]`) chooses what it does: answer at once (`plain`, the default), ask for a permission (`session/request_permission`, which the engine shows as an approval), ask a question (`elicitation/create`, shown as a question whose answers are keyed by the form's field names), stream until it receives `session/cancel`, speak (`speak`), call one of the engine's own tools (`request_secret` to ask for a secret), work through a few command steps, each reported running and then completed, before it speaks (`steps`), so a turn's work can be watched as it goes, or call J3 Bots' own tools to build a team (`team`, and `room-answer` for each member it wakes). The engine gives an ACP agent its tools as a stdio bridge, its own binary, whose environment names the HTTP endpoint behind it (`T3_ACP_MCP_ENDPOINT`, `T3_ACP_MCP_AUTHORIZATION`); the scripted agent calls that endpoint directly (**Read** at `db51b67`, `provider-acp` `adapter.ts` and `mcpTransport.ts`). It starts no work after its turn: the engine offers a continuation only to ACP agents it recognizes by name (**Read**). The engine sends it the request wrapped as `<t3_code_instructions>…</t3_code_instructions>` followed by `<user_request>…</user_request>`. **Verified** on release `4969` for the first six, plus resuming after a dropped socket; `steps` is **Assumed** to show the same way, since its steps are the tool calls the others report. Its `j3` tool calls go through the real bridge, as described below.

J3 Bots provisions it like any other harness: `ProviderInstance` has an `acp-command` kind (a command and its arguments) next to Claude Code and Codex, and the conformance suite starts the engine through the same adapter layer with only that instance. The engine offers an ACP agent only its own MCP server, so the adapter gives an `acp-command` instance the `j3` bridge's command line in its environment (`J3_TOOL_BRIDGE`, a JSON array). The scripted agent starts the bridge from it for each call to J3 Bots' own tools, and the bridge inherits the agent's environment, where the engine puts the session's thread id (**Verified** on `0.1.11`: the calls of `apps/server/scripted/team.test.ts` reached their bots' sessions). It speaks as a bot does when the bridge lists `say`, which it asks once per process: `speak`, `steps` and a `plain` answer to a wake that owes the operator a reply (from the operator, or a system event other than a profile change) go through `say` with `done: true`, so the server counts the turn delivered, and a `plain` turn a room, a teammate or a routine woke stays silent, as a room settles. Without it, as on the conformance bench, whose bridge answers nothing, `speak` and `steps` go through the engine's `send_to_user` and `plain` only streams its text (`scripted-agent/agent.test.ts` runs the agent on a stand-in bridge and host tools).

T3 Code's own replay provider is the same mechanism, an ACP agent the engine seeds only on a development server. Its fake CLI is a helper for its own tests, not a provider. Neither is usable from a release build, and the scripted agent replaces both.

The behavior evals and the real-harness tier still need a model.
