# The browser

J3 Bots runs the browsers its bots use, on the person's desktop first and on the server when no desktop is there. The engine's browser is off ([decision 0110](../decisions/0110-j3-bots-runs-its-own-browsers-and-the-engines-is-off.md)). This page names the pieces, what each owns, and which part of the 0.16 work builds it. It is rewritten as each part lands.

## The pieces

```
  bot's session ──browser_* tools──┐        viewers (web, desktop, phone)
                                   v                    │ media socket
                 +-----------------+--------------------v---+
                 | J3 Bots server: Browser service           |
                 |  tab registry, placement, leases, the     |
                 |  person's hold, the sealed jar, fill, help|
                 +------+-------------------------+----------+
                        | BrowserHostRpcs          | BrowserHostRpcs
                        | (in process)             | (over the desktop's connection)
                 +------v---------+         +------v---------------------+
                 | server host    |         | desktop host                |
                 | Chrome for     |         | Electron views, one CDP     |
                 | Testing, new   |         | relay per tab, Playwright   |
                 | headless       |         |                             |
                 |  DriverPage    |         |  DriverPage                 |
                 +----------------+         +-----------------------------+
```

A tool call crosses the network once. The server decides which tab and whether the bot may act, then asks the tab's host for one piece of page work. The host runs it beside the page with the shared driver.

## Boundaries

- **`packages/browser` knows nothing of T3 Code:** not its protocol, its types or its files. Some of its code is adapted from T3 Code under the MIT license; each such file says so, and `packages/browser/NOTICE` carries the license.
- **Clients never reach a host.** They watch and use tabs through the server, by the tab's ref.
- **A client learns at once that a tab's host is gone.** A desktop's tab waits 45 s for its app to come back, listed as `away` meanwhile, and is parked if it does not. A tab with no host sends no new picture, its viewers keep the last, and the server refuses the person's input to it with a `refused` frame saying why, rather than passing it to a host that is gone or holding the tab for nothing.
- **Opening a tab for the person says why it did not.** `browser.open` tells apart no browser to take the tab, a server that runs only an app's, a full server browser, and a page the host could not open: not in time, at a refused address, or a failure ([Server: the bot's browser](server.md#the-bots-browser)).
- **A host never speaks raw CDP to the server.** One call is one piece of page work.
- **The server owns every ref.** A host mints one only for a tab it opens by itself, such as a pop-up or the person's new tab, with at least 128 bits of randomness.

## Sign-ins

The person's sign-ins are one jar on the server, which every host's store agrees with ([Server: sign-ins](server.md#sign-ins)):

- **Hosts only read, write and clear.** A host implements `cookies.read`, `cookies.write`, `storage.read`, `storage.write` and `storage.clear` (an origin's site data besides cookies, or every origin's, for signing out), and reports what its pages change (`cookies.changed`, `storage.changed`) when it can. `storage.clear` also empties the `sessionStorage` of the host's open tabs of those origins and loads a tab of one again, so a signed-out page keeps nothing in its memory. What to take, what wins and what to send each host is the server's.
- **A host with `indexedDb` carries databases too**, in `BrowserIndexedDb`: Playwright's `storageState` shape and value encoding. What it promises:
  - `storage.read` with `indexedDb` gives each origin's databases whole, every record, and `[]` when it has none. An origin whose databases hold a value that shape cannot carry (a `CryptoKey`, a `Blob`) comes back without `indexedDb`, never read in part or wrong.
  - `storage.write` makes an origin given with `indexedDb` hold exactly those databases, and leaves them as they are when it is given without. A write that fails leaves the origin's databases as they were.
  - A change that needs a version change (a database deleted, or opened at another version) waits on every page that holds the database open, and cannot be called back once asked for. So a host never leaves one waiting: it writes nothing of that origin, names it in `waiting`, and writes every other origin given. The server writes it again later.
  - The host speaks host protocol 2 (`BROWSER_HOST_PROTOCOL_VERSION`), whose `storage.write` answers `BrowserStorageWritten`: `{}` once every origin given is written, `{ waiting }` with the origins it wrote nothing of.
  - `readDatabases` and `replaceDatabases`, in `packages/browser`, do this from a page of the origin; `versionChanges` says whether the host lets a version change be made now. The limits on what is carried are the server's: a host is asked for no databases of an origin too big to carry.
- **The server's own host reads and writes storage in a probe**: a page of the origin, past any service worker (`Network.setBypassServiceWorker`), whose every request is answered with an empty page, so no site's code runs where its storage is read. It clears an origin's site data with `Storage.clearDataForOrigin` from a page of its context, then the `sessionStorage` of its open tabs of that origin: a test against a page it serves on the loopback checks both (**Verified** on Playwright's Chromium build 1234; CI runs the same test on Chrome). It reads and writes IndexedDB there too (`indexedDb`), in Playwright's `storageState` shape, with `readDatabases` and `replaceDatabases` from `packages/browser`, which follow Playwright's own storage script and value encoding (Apache License 2.0; see `packages/browser/NOTICE`). That the bypass covers the probe's navigation is **Assumed**.
- **A host names its store and its browser's run.** `cookieStore`, in its hello, stays the same for as long as the store keeps its cookies, and changes once it is cleared. With it, a host that comes back is agreed three ways, from what both held when they last agreed; without it, the host is treated as new. `browserRun` is a new random id each time the host's browser starts, so the server tells a session cookie lost to a restart from one the site removed.
- **Cookies cross the protocol in one shape**, `BrowserCookie`, keyed by their whole partition. `cookieOfCdp`, `cdpParamOf` and `cdpRemovalOf` in `packages/browser` map it to and from the DevTools protocol's `Storage.getCookies` and `Storage.setCookies`, for a host that reads raw CDP; the server's own host uses them. A cookie for its host alone has no leading dot on its domain, one set without SameSite stays without it, and one under an opaque partition is not read, since it cannot be set again.
- **The move from the engine's profile** reads it with `readProfileSignIns`, in `packages/browser`: a copy of the files it needs, opened by the Chromium that wrote it with the network off, every request answered by an empty page in the process. The origins whose storage it kept are found in its own files, by a small reader of LevelDB's log and table files (`leveldb.ts`, Snappy included).

## The driver

`makeDriverPage` drives one Playwright `Page` for as long as its scope lives. The host gives it the page and a CDP session of that page, since only the host knows how to open one.

- **Snapshot.** Playwright's accessibility tree in its `ai` mode, with boxes. Each ref is rewritten as `j3-<driver>-<document>-<native>`. The browser keeps an element's number within one document, so a ref holds across snapshots, and one bot's snapshot takes nothing from another. It ends when the main frame navigates or a frame detaches. A ref the document did not give out, or whose element is gone, is refused as `stale-ref`, which tells the bot to take a new snapshot. A ref goes alone, as `aria-ref=<ref>`: a selector that mentions `aria-ref` any other way is refused. A tree over 20,000 characters is cut at a line's end, or at the limit when no line ends in reach.
- **Masking.** Before the tree is read, and again after, each frame's password values, and values a page hides behind dots, are read in an isolated world of their own. Every form of them is masked wherever the tree or the title shows them. A value that changed between the two reads restarts the snapshot once. `data:` payloads are cut before masking.
- **Actions.** Click, type (focusing a text field first; pickers and sliders take their value whole), hover, select, drag, upload, press, scroll. A ref's element is found once, while no snapshot numbers elements, and the action runs on that element alone: an action still waiting when the page navigates fails as `stale-ref`, and never lands on the next page. Each action has a deadline, its own or 15 s. An action that opens a dialog returns at once, for the bot to answer it. A timeout says whether the target still matches, since the action may have happened.
- **Dialogs.** While one waits, the page runs no script, so a snapshot, an action, a script or a wait is refused until the dialog is answered, by the bot or by the person.
- **Evaluate.** Over CDP `Runtime.evaluate`, retried in the console's REPL mode only when the parser refused a top-level `await`. A script over its time is stopped without waiting for the renderer to acknowledge it. Results over 64 KB are refused.
- **Navigate.** Stops a script that keeps the page from answering, waits for the commit, then for the readiness asked. A page whose resources stall past the time is reported loading, not failed. A page that fails to load reports the browser's net error as `loadError`, and the tab keeps the address that failed. Only `http:` and `https:` open.
- **Screencast.** One per tab, which the server shares among its viewers. A second takes the place of the first, which ends, and its end stops nothing of the second's. A screencast that ends acknowledges the frames it held, whether another took its place or its stream ended. The one asked for last is the one watched: the first may belong to a feed the server closed, which a desktop host lets go of only after the next has asked (see [server.md](server.md), "One feed per tab"). One frame is out at a time. While it is, only the newest waits, and every frame dropped is acknowledged to Chromium at once.

The snapshot, the masking, the actions and `evaluate` follow T3 Code's `ServerBrowserPage.ts` (**Read** at `bc0f04d`). T3 Code gives refs out per snapshot and runs one step on a tab at a time; J3 Bots keeps refs per document and finds a ref's element once, since several bots read and act on one tab.

## The server's browser

The server's own host runs full Chrome for Testing in its new headless mode, one version pinned per platform by size and SHA-256 (158.0.8127.88 in 0.16: 208 MB to download on `linux64`, 413 MB unpacked). It starts when a tab needs it, keeps at most three tabs live, parks a tab unused and unwatched for 5 minutes, and closes once it has had no tab for a sweep ([Server: the bot's browser](server.md#the-bots-browser)). What it needs from a host, and how to give it, is in [Operating: the browser](../operations/operating.md#the-browser).

**What a tab costs.** Measured on 2026-11-27 on an x86-64 Linux machine with 8 cores, with Chrome for Testing 158.0.8127.88 at a device scale factor of 1, on a page that repaints a full canvas every frame, the worst case. Each figure is the memory of the whole browser (PSS) and the cores it kept busy. **Verified** there; no arm64 machine, such as a Raspberry Pi, was measured.

| Tabs | Memory | Cores |
| --- | --- | --- |
| One still tab | 340 MB | 0 |
| One moving tab | 360 MB | about 1.4 |
| One moving tab, watched | 384 MB | about 1.4 |
| Three still tabs | 380 MB | 0 |
| Three moving tabs | 469 MB | 3.8 |

A device scale factor of 2 adds 90 MB to one moving tab, and 207 MB and nearly a core to three; in the same test of `chrome-headless-shell` it halved a viewer's frame rate at the same picture size. So the server keeps 1. Chrome for Testing takes about 160 MB more than `chrome-headless-shell` at every point, for a browser sites cannot tell from Chrome.

## The desktop host

The desktop app's own browser (`apps/desktop/src/browser`) is the page host for the bots' tabs on that computer, and a browser the person uses. What the person sees of it is in [Clients: desktop](clients.md#desktop); what it keeps from pages, in [Security: the desktop's browser](security.md#the-desktops-browser).

- **Tabs are views.** Each tab is a `WebContentsView` in one persistent partition, `persist:j3-browser`, which holds the shared sign-ins; a private tab has an in-memory partition of its own, which a tab a site opens from it shares, and which is forgotten with its last tab. A tab no window shows lives in the shelf, a window of the app that stays shown but is never seen: a single see-through pixel, far off the screen, that takes no focus and no mouse, asks to be left out of the taskbar, and on macOS out of Mission Control and the Window menu. On Wayland, where the compositor places every window and lists it, the shelf stays hidden instead, and a tab no window shows waits hidden in one of the app's windows on the person's screen (`onScreen`), the main window or the browser's. Each of these tabs' views is 1280 by 800, the size its page takes, whatever the window it waits in.
  - **Why it stays shown.** A page whose renderer begins while its window is hidden never paints, though it is watched with background throttling and focus emulation off, and nothing asked of it later makes it: a new tab in a hidden shelf, and a page a navigation moves to another site in a window hidden since, sent no picture at all, while the same pages in a shown window, on screen or off it, painted as soon as they were watched. A page that began in a shown window paints when watched after that window hides.
  - **A window that leaves the screen.** As the main window or the browser's window hides or is minimized, its tabs go aside, to the shelf or, on Wayland, to another of the app's windows on screen, and they are drawn in it again once it is back (`app.ts`), so no page begins in a window off the screen; on Wayland it takes back the tabs the shelf kept meanwhile. That a window going off the screen says so (`hide`, `minimize`) is **Verified** for `hide` under Xvfb and **Assumed** for the rest: a compositor on Wayland may never report a minimize, and macOS may report a window that another covers as hidden.
  - **Where it still cannot paint.** On Wayland, while none of the app's windows is on screen, as with the app in the tray, the shelf keeps the tabs and a page that begins anew there, a bot's new tab or a navigation to another site, sends no picture until a window of the app shows again. On macOS, hiding the app from its menu or from quick access (`app.hide()`) hides the shelf with every other window, so the same holds there (**Assumed**).
  - **Verified** on Linux, Electron 44.10.1, under `xvfb-run`, with a page that repaints a canvas every frame and a screencast of it with background throttling and focus emulation off: in a shelf shown once and hidden, a new view sent 0 frames in 3 s whether it was hidden, shown, shown and hidden again, or added while the shelf was shown for a moment, and a screenshot timed out; in a shown one-pixel window off the screen, 120 frames in 2 s, at the view's 1280 by 800, and again after a navigation to another site; in a shown window later hidden, 120 frames, and 0 after such a navigation. `apps/desktop/test/unshownTab.test.ts` fails on 0.16's shelf and passes on this one. On Linux, Electron 44.10.1, on a headless GNOME Shell 50 under Wayland: the shown shelf is placed in the middle of the screen and listed among the windows Alt+Tab offers, not left out of the taskbar; a view in a hidden shelf sends 0 frames; a hidden view in a shown window, with background throttling and focus emulation off, 61 frames in 2 s, a 1280 by 800 screenshot, and the same after a navigation to another site; and `unshownTab.test.ts`'s pictures of a tab no window shows come at once, while its tab whose page begins anew with no window on screen sends none. **Assumed** the X11 behaviour on macOS and Windows, where a window off the screen may be taken as hidden, as Xvfb, with no window manager, does not; a window manager on X11 that moves the shelf on screen shows a see-through pixel.
- **Driving a tab.** The view loads `about:blank` first, and only then is its debugger attached: attached before a view's first load, it leaves the view drawing no frames (**Verified** on Electron 44.10.1). Playwright then reaches the page through that debugger, behind the CDP relay, over a one-use loopback socket on a random path (`relay.ts`). The relay holds each of its page sessions to one screencast frame it has not acknowledged and keeps the newest that comes meanwhile; the debugger's own frames wait unacknowledged while every session is busy, so Chromium sends no more until one is free. A session's `Page.stopScreencast` frees its slot. Chromium numbers a new screencast's frames afresh, so a slot kept past the stop would hold back every frame of the next screencast, and the tab would send no picture to anyone until the app restarted (**Verified** on Electron 44.10.1: `apps/desktop/test/watchedTab.test.ts` failed so while the relay kept it, with the server's acknowledgement of the last socket's leaving alone and with the driver's of an ending screencast alone; as the relay reads, the acknowledgement just before the stop hands the session the frame that waited, which fills the slot again). A hidden tab keeps painting while it is watched or driven: background throttling and focus emulation are off only for as long as that lasts. The focus emulation command is not awaited, since a page held by a dialog answers no command until the dialog closes.
- **Identity.** The partition's user agent is Chrome of Electron's Chromium version, on the system it runs on, without `Electron` or the app's name, and its requests carry the matching client hints with the Google Chrome brand (`identity.ts`). Each tab sets the same through `Emulation.setUserAgentOverride` once its debugger is attached, so the page's script sees what the headers name.
- **Sign-ins.** The hello names the store the shared sign-ins are kept in (`cookieStore`: a random id kept in a file in the partition's own folder, `j3-cookie-store`, so a partition removed takes it along; minted when the file is missing, and again before the device's sign-ins are emptied, so no hello names an emptied store by its old name; when it cannot be written the file is removed and the hello names no store, and the server takes the host as new) and this run of the browser (`browserRun`, minted as it starts). Cookies are read and written through the probe's debugger with `Network.getAllCookies` and `Network.setCookies`, in the shape every host shares (`cookieOfCdp`, `cdpParamOf`, `cdpRemovalOf` in `packages/browser`): through a view's debugger, `Network` reaches that view's partition, a partitioned cookie's whole partition included, while `Storage` reaches the app's default session instead, and Electron's own cookie API loses a cookie's partition (**Verified** on Electron 44.10.1). Neither depends on the origin the probe shows, so cookies never wait behind site storage. Changes gather for 1 s and go to the server as `cookies.changed`, never the host's own writes and never a private tab's; a look at the jar and a write the server asks for take turns, so a write is never seen half done, and a write that fails is not taken as known. An expiry that comes back below the second from a write is no change. Every origin a frame of a shared tab shows, by the frame's own origin (one on `about:blank` or `srcdoc` has its maker's), and every origin a frame of it came to since, embedded ones included, is offered to read again (`storage.changed`) when the tab leaves it, when it closes, and every five minutes; a quit can lose up to that much of a site's storage. The server decides what it reads, within its limits ([Server: the bot's browser](server.md#the-bots-browser)).
- **Site storage.** An origin's `localStorage` and IndexedDB are read and written through a probe: a view of the partition that is never shown, whose every request is answered with an empty page and that passes the site's service workers by, so no site code runs (`probe.ts`). **Verified** by `browserHost.test.ts`: without the bypass, a site's worker answered the probe's visit and its script wrote the origin's storage. `localStorage` goes through the debugger's `DOMStorage`; the databases through the same `readDatabases` and `replaceDatabases` the server's browser runs, evaluated in the probe's page from JSON text (`storage.read`, `storage.write`, `indexedDb`). The probe visits an origin as a page of its own, so it carries what the origin keeps as a site; what it keeps embedded in another site's page, which Chromium keeps apart under that site, is not carried (**Verified** on Electron 44.10.1: a cross-site frame's `localStorage` was not the probe's; **Assumed** the same on the server's browser, whose probe visits the same way, since the protocol names origins, not the sites they are embedded in). A write whose databases need a version change (deleting one, opening one at another version, or making one again in another shape) waits while a frame of a shared tab shows the origin, asked again just before the change: that origin alone is answered `waiting`, with nothing of it written, and the server writes it again later, while cookies and the other origins go on. Before such a change the origin's service workers are stopped (`ServiceWorker.stopAllWorkers`; **Assumed** to reach the partition's workers, as `Network` reaches its cookies). A read or a write takes at most 8 s, its wait for the probe included, within the server's limit on a call: an origin not written by then is answered `waiting`, and one whose databases were not read by then comes back without them, which the server takes as databases it did not see. An origin cut off while a page of it held a change back may be partly written: a deletion already asked for still happens once that page lets go (**Read**: an IndexedDB delete waits for the database's open connections to close), and, answered `waiting`, the origin is written again whole. Signing out (`storage.clear`) clears the origins' site data but cookies with Electron's `clearData`, matching each origin in every context, so one embedded in another site's page loses what it keeps there too, or the whole partition's with `clearStorageData`; then each shared tab's frames of them lose their `sessionStorage`, each given 2 s, since a page held by a dialog answers nothing, and a tab whose page is of one loads again. What a tab keeps in `sessionStorage` for an origin it has since left stays with that tab until it closes, as on the server's browser: the page's storage is the tab's, and no frame of that origin is left to clear it from. **Verified** by `browserHost.test.ts`, on fake local pages: a sign-in a page keeps in IndexedDB as a Firebase app does is read from the desktop, one written by the server is the page's once it reads it, deleting a database waits while a tab shows its origin, signing out leaves the tab neither `localStorage` nor `sessionStorage`, and signing out of a site embedded in another's page clears what it kept there. A private tab's partition is never read, written or cleared.
- **Files.** A file a bot's action downloads is reported as it starts (`download.started`) and again once complete, and kept in a scratch folder of the app's until the server takes it (`download.take`, in chunks of at most 1 MiB); one larger than the server keeps (`MAX_ATTACHMENT_SIZE`) is reported complete with its size, so the server tells the bot it is not kept, and is moved to the person's downloads folder instead, or copied off the main thread where the folder is on another disk, where the downloads list lets them open it; one cancelled, cut short or not kept here is reported ended without a file (`outcome`), and the server tells the bot so; one the person downloads goes to their downloads folder without a dialog, and is never sent. A bot's upload is written to the scratch folder and handed to the page's file chooser; an upload may name only files the server sent for that tab (`putFile`), since the server is another computer and must not reach this one's files. The folder is emptied as the app starts.
- **The link.** Once the page hands it the device credential, the main process dials `HTTP_PATHS.browserHost` with the token as a bearer and answers `BrowserHostRpcs` on it (`link.ts`, `serveHostOnSocket`). Its hello speaks `BROWSER_HOST_PROTOCOL_VERSION`, names the device, says the person can open private tabs and that it sends its sites' changes itself (`changeEvents`), and never names a private tab the person opened. A private tab the server asked for, and a pop-up a site opened from it, which is private too, would be listed apart from the shared ones (`privateTabs`); the server asks for none. A link that drops is dialed again after 1 s, doubling to 30 s while each fails at once; one that lasted 30 s starts the waits over. When a link ends, the app asks the server for a socket ticket with the token: a 401 means the device was revoked, so the app clears the shared sign-ins and stops dialing. That emptying is marked first in a file of the app's (`j3-forget-sign-ins`): one that fails, or is cut short, is done again as the browser next starts, before it links, and until then what the jar holds is still known, so none of it is told to a server as new.
- **The person's browser.** `places.ts` keeps where each tab is shown (beside the conversation in the main window, or in the browser's window), their order, the tab in front of each and the closed tabs to reopen, and knows nothing of a window. `commands.ts` carries out what the person asks from the windows' pages, and `historyStore.ts` keeps the history (`history.ts`) in a file between launches. `app.ts` holds the windows, the person's downloads and the drawing of each place's front tab, and answers the windows' pages over the bridge. The pages draw the tabs and the toolbar (`Toolbar.tsx`, made of `AddressBar.tsx`, `DownloadsButton.tsx`, `HistoryPopover.tsx` and `BrowserMenu.tsx`), and report where the page goes (`BrowserPlacement`); the main process lays the view there. While something of the window lies over the page, it captures a still of the page, sends it, and hides the view, and the page draws the still. The find bar takes the strip at the top of the page's area (`PageArea`'s `strip`) rather than lying over the page, so the page needs no still while finding.
- **Presence in the page.** The page itself shows the bots on a tab, with the component a view of a server-hosted tab draws over its picture: an isolated world in the page, and a closed shadow root in it. There the pointer moves only for what the bot does (`still`): it glides, clicks, opens its tag and steps aside, but it does not bob while the bot thinks, and its face holds its state's still form, neither living on its own nor answering a click or the person's take. The screencast sends a picture of every frame the page paints: with a living face, a watched page that did not change sent about 60 pictures a second to a viewer on the loopback once a bot had pointed in it, and now sends none in 3 s once the pointer rests (**Verified** by `watchedTab.test.ts` on Electron 44.10.1, whose check allows two). So the pictures of the page a person gets, a card's still, a live view's, a grid's, show the pointers as the person at the desktop sees them. The host says so in its hello (`pointers`), the server carries it on the tab's place (`where.pointers`), and no view draws its own pointers over such a tab's pictures (`pointersInPicture`, in `client-runtime`), which would show each one twice; over an older app's, which leave them out, it still does.
  - **Who is on a tab.** The main window's page, whose client knows from the server who is on each tab (the shared tab list the viewers read), tells the main process the bots on each tab, most recent first, with each one's face, name and whether it is thinking, and whether the person here holds the tab (`browserPresence`, a `BrowserPresence`). A client that stops telling, as on signing out, tells of no bot first; a main page that loads again or is gone leaves none either. The browser's window and the panel draw the same faces on each tab and the same line by the address, with no **Now** or **Continue**: the desktop has no call that gives a tab back, and a hold here ends as the person stops using the page.
  - **The drawing.** While a bot is on a tab that is on the person's screen or watched by a viewer, the main process runs the drawing in a world of the page's own (`presence.ts`; world 1710, apart from the page's, 0, and Electron's, 999), and hands it each change and every point a bot's action aims at, as the host hears it (`pointer`). It runs nothing in a page no bot was drawn in. The drawing (`presence.js`) is the web client's: `apps/web/src/browser/desktop/presence/overlay.tsx`, built by `vite.presence.config.ts` and carried in the app's `dist`. It renders `TabPointers` and `BotCursor`, the viewers' own, over the viewport without its scrollbars, where a bot's point is measured, on the `pointer` tokens and `presentation/botPointer.ts`: the arrow in the bot's color and the white tag with its face and name, moving on the curve and never turning, the bob while it thinks, the squash on a click, the step aside, faded, while the person holds the tab, the fade in, and moves at once under reduced motion. The pointer is the tab's most recent bot's, since the host's pointer names no bot. A drawing begun later, as the tab comes on screen or a viewer starts watching, shows the bot where it last pointed in that document. It fades in, so a still of a tab no window shows, the first picture of a watch that begins the drawing, may have no pointer yet, or a faint one; a live view's next pictures have it.
  - **Out of the page's way.** It lives in a closed shadow root on an element of its own at the page's root, `aria-hidden`, fixed over the viewport, taking no pointer events, with its own style set property by property as `!important`, which a page's policy that refuses style attributes lets through. The page's scripts cannot reach in, a page that takes the element out gets it back while a bot is on the tab, and the snapshot a bot reads never lists it: the driver's reading of the page goes only into open shadow roots. It is hidden only while a bot's screenshot or a snapshot's image is taken, as a bot reads the page and never its own pointer: hidden by its opacity, since the face's own parts set their visibility again for themselves, and with the bot's caret given back meanwhile. A page held by a dialog, or busy, runs no script: once a call to it goes unanswered for 1 s, the tab's page is sent nothing more until that call settles, and is then drawn as it should be by then; so a bot's capture waits at most that second on the page, and a capture meanwhile may show the pointer it last drew (**Assumed**: such a page keeps its last frame).
  - **Its sheet.** The tokens' sheet for a shadow root (`shadow.css`, whose root is `:host`), with Tailwind built from the pointer's and the face's sources alone. A shadow root's sheet registers no custom property, so each one Tailwind registers starts at its initial value on every element instead, in a layer below Tailwind's own. Its lengths are in pixels, since a shadow root's `rem` is the page's root size, which a site sets as it likes. The page shows the light palette.
  - **The bot's caret.** While a bot is on the tab and the person does not hold it, the field that has the focus, through open shadow roots and into frames of the page's own origin, takes the acting bot's color as its caret, in the field's own style; the field has its own back as the focus leaves it, the person holds the tab, a picture of the page is taken for a bot, or no bot is left. A frame of another origin keeps its caret.
  - **Its limits.** The page can see that an element is at its root, and its observers see the caret's color written into a field's style, so a site can tell a bot's pointer is drawn while the tab is on screen or watched; nothing of the drawing's inside reaches it. The page's top layer, a modal dialog, a popover or an element in full screen, lies over every element, and so over the pointers (**Assumed** from CSS's top layer). A transform or a filter on the page's root element makes the element fixed to that root instead of the viewport (**Assumed**, as CSS has it). While a bot's screenshot is taken of a watched tab, the pointer leaves that viewer's picture for as long. A phone app from before `pointers` draws its own pointers over a newer desktop's pictures, so each shows twice until it is updated. The client's typefaces are not in the page, as a shadow root's sheet declares none, and a page's own font faces apply in its shadow roots: the tag's name is in the system's sans-serif, named by generic families alone, which no font face replaces. The drawing is about 400 kB of script, run again in each new document a bot is drawn in.
  - **Verified** by `browserHost.test.ts`, on a fake page whose policy lets in nothing but its own inline script: the element is there, closed and `aria-hidden`, covering the viewport, as a bot clicks; the bot's snapshot names neither the bot nor the element; the element under the button's middle is the button, and the person's click there lands; on a page that is orange and black throughout, what the window shows of the page has the pointer's blue and the tag's white, while the bot's screenshot of it has not one pixel of either; it shows again after; the screencast a viewer gets of it has both, as a bot's click opens the tag again; a tab no window shows, with the bot on it, has no drawing until it is watched, and then its pictures show the pointer where the bot last clicked; and a field the bot types in has the bot's caret.
- **A login fill.** While a bot types a saved login into a tab (`tab.fill`), the page takes none of the person's input, from before the first character until the fill ends, whether it worked or not: the view's own input hooks (`before-input-event`, `before-mouse-event`) drop every key and mouse event of theirs, so one cannot land in the half-typed form. The bot's keys pass, since those hooks never see the debugger's key events; they do see its mouse events, which a fill sends none of (**Verified** on Electron 44.10.1). Meanwhile the view is hidden behind its still, with a line saying a bot is signing in, and a person who was typing in the page has the keys there again once it shows.
- **Whose input it is.** The person's input to a tab's page, and only theirs, holds the tab for them (`person.input`, and the server's 10 s hold), while a bot's typing and clicking, which reach the page through its debugger, never do (`tab.ts`). The app's own controls for the tab count as the person's use too: an address they enter in it, Back, Forward and Reload (`personUsed`).
  - **Keys.** A key is the person's when it passes the view's own key hook (`before-input-event`), which the debugger's keys never pass, whenever they land: they reach the view's `input-event` alone, and do so while `debugger.sendCommand` is still running. It is told once every listener of the hook has had it, so a key the login fill stops, or one of the browser's shortcuts, which go to the window and never reach the page, does not count. So a bot's typing, through `keyboard.type`, `fill` or the select-and-delete of a clear, never holds the tab.
  - **Presses and touches.** Nothing tells the debugger's from the person's: both pass the view's mouse hook (`before-mouse-event`) and `input-event` with the same fields. So a press, a touch or a tap is the bot's while a command of its that makes one is on its way, counted from before the command is sent until the page answers it: a mouse button going down (`Input.dispatchMouseEvent`, `mousePressed`), a touch starting or ending (`Input.dispatchTouchEvent`, `touchStart`, `touchEnd`), a tap gesture (`Input.synthesizeTapGesture`). The bot's keys and moves make none, so the person's click while a bot types or moves its pointer holds the tab. One of the person's while such a command is on its way is taken as the bot's; that lasts until the page answers, which a busy page delays, and a dialog the press opened holds off until it closes (**Assumed**, as a page held by a dialog answers no command).
  - **Verified** on Linux, Electron 44.10.1, under `xvfb-run`, with the debugger's `Input.dispatchKeyEvent`, `Input.dispatchMouseEvent`, `Input.dispatchTouchEvent` and `Input.synthesizeTapGesture`, Electron's `sendInputEvent`, and real X input through XTEST, in 20 to 40 rounds each: every key and press of the debugger's reached `input-event` while its command was being sent, and every touch and tap after it was sent but before its answer, each from the command named above; the view's own keys, from `sendInputEvent` and from XTEST, passed `before-input-event`, and a listener added later stopping one was seen once the hook had run. **Assumed** the same on macOS and Windows, where the keys reach the view another way.
- **Searching.** What the person types in the address bar is a search with Google when it has a space, or when it is a single word that is no loopback host and was typed without a scheme (`address.ts`).
- **Local mode** starts the server with `J3_BROWSER_SERVER_HOST=off`, so its bots use the desktop's browser only.

The desktop host's placing of downloads, the hidden painting, the relay's reach and the permission list follow T3 Code's `apps/desktop/src/preview/DesktopBrowserHost.ts` and `BrowserSession.ts` (**Read** at `bc0f04d`); `apps/desktop/NOTICE` carries the license, and the package ships it with `packages/browser/NOTICE` in `dist/notices`.

## Testing

`packages/browser`'s driver tests run on a real Chromium, over fake pages the test serves itself; nothing leaves the machine. They run when `J3_TEST_CHROMIUM` names a Chrome or Chromium binary, which CI sets to the runner's Chrome, and are skipped otherwise. The desktop app's own browser is checked five times under `xvfb-run` on Linux, against fake pages served on the loopback. `apps/desktop/test/browserPanel.test.ts`, in the desktop smoke, opens it from a bot's conversation in the development build: the page's view lies below the toolbar and beside the conversation, moves down for the find bar, a private tab is apart from the shared sign-ins, and a tab sent to the browser's window comes back when that window closes. The desktop host's check (`apps/desktop/test/browserHost.test.ts`) runs the browser in Electron on its own, under `xvfb-run` on Linux, against a server the test plays and fake pages it serves on the loopback; its main shows the tab at `/presence` in a window, with a bot on it, so its page draws the bot's pointer from the web client's build, which the check builds first. `apps/desktop/test/unshownTab.test.ts` has a bot open a tab on the desktop behind the person's, never shown, and a paired phone's viewer socket gets the first picture of it within 5 s, three times, as a card's still and a live view each take one; then, with the main window hidden, the person's own tab, which it showed, goes to another site and still sends its picture, and once the window shows again the tab is back in it and still sends one. `apps/desktop/test/watchedTab.test.ts` has a bot work on a desktop tab whose page keeps changing, while a card's socket and a phone's watch it: the card never draws its first picture and the phone leaves with the newest in flight, then the card leaves, each a second apart, and the next socket gets pictures, one after another; then, on a page that never changes, the bot clicks, and its viewer gets pictures while the pointer moves and at most two in 3 s once it rests. `apps/desktop/test/botTyping.test.ts` pairs the development build with the server's testing layer, which serves the host socket as a real server does, and has a bot drive a tab the desktop hosts through the server's own `browser_*` tools: it types in a field, types again clearing it first, and clicks, and none of it is refused or holds the tab for the person; then a click of the person's, given to the view as its own input, holds the tab for them, and the bot's next click is refused as the person holds it; in a new tab, whose address the person enters once it is in front, and which that address holds for them until their hold ends, the bot types, and a key of the person's holds that tab the same way. Everything else uses `makeFakePageHost`.
